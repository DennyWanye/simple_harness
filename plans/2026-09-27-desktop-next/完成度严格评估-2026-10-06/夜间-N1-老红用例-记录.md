## 1. `step02/test_store_and_budgets.py::test_cas_and_idempotent_events`

- **现象**：断言 `first.seq == second.seq == 1`，实际是 3。
- **原因**：HTN 补齐阶段 G 第 2～6 批（`061f1e29`，10-04）加了"存储层记整行变化"。每个最外层事务提交前，都会给业务行写入记一条 `RowsWritten`。用例前面先建任务、再改任务，各记一条，所以 Probe 事件的序号变成 3。
- **判断依据**：用存档的源码各跑一次旧用例。`1c442b82`（第 1 批）上通过，`061f1e29` 上失败。这个变化是设计要求的（"能由事件重建"统一在存储层收口），不是缺陷。
- **怎么改**：序号不再写死为 1，改为"追加前的最大序号 + 1"。另外加了几条断言：
  - 重复追加返回的整条事件与第一次相同；
  - Probe 事件只有 1 条；
  - 重复追加不新增任何事件；
  - 崩溃回滚后，总条数和最大序号都不变（`RowsWritten` 也一起回滚）。
- **守的保证**："同一个幂等键只存一条、返回同一条"和"事务中途崩溃全部回滚"，仍在本条用例里守，而且比原来更严。
- **改坏**：把 `append_event` 改成"键已存在就先删再插"，用例变红（3 ≠ 4）。已用 cp 备份恢复，并清掉 `__pycache__`。

## 2. `step06/test_governance.py::test_a_reviewer_at_the_cap_is_told_to_conclude_now`

- **现象**：`'NoneType' object has no attribute 'list_files'`。
- **原因**：第 2 批车道 G（`afc692b6`，10-06，K01）以后，审阅绑定不再有任务工作区（`review_key` 不为空时工作区为 None）。审阅员只有四件工具：两件证据工具，加 `knowledge_list` / `knowledge_read`。用例还在让审阅绑定调 `workspace_list`，这不是审阅员的工具，所以碰到空工作区。
- **判断依据**：ASSURANCE-EXEC §4 规定审阅绑定"不拥有任务工作区，只列只读证据工具"。产品行为符合计划。
- **怎么改**：审阅员改用它的真实工具 `assurance_find_evidence`，并给它装一个桩读取器，上限仍是 1 次。另加一组执行者对照：执行者绑定查满次数时，仍收到通用提示，不会被叫去"按格式给结论"。
- **守的保证**："审阅员查满次数时，拒绝理由叫它别再查、马上作答"（09-29 第六局），仍在本条守。
- **改坏**：把提示里的"立即根据已经看到的证据……"改成"请继续。"，用例变红。已恢复。

## 3. `assurance_exec/test_method_review_gate.py::test_a_method_review_that_ends_without_a_verdict_is_reported_to_the_planner`

- **现象**：审阅员两次回复格式都错以后，系统问用户（`adjudicate-method:`）。用例还在等"直接给规划器报 NO_VERDICT"，等不到。
- **原因**：阶段 C（`09657376`，10-03，"审查没有结论 → 记成判不下来并问人"）以后，第 2 次回复仍不能用时，会按"没有可采用的回复"导入成一份判不下来记录（`INCONCLUSIVE`，各条为 `UNKNOWN`，限制写 `REVIEW_NO_USABLE_REPLY:`），然后问人裁决。
- **判断依据**：这符合用户 2026-09-30 的决定："判不下来 → 同模型新会话复审 1 次 → 仍不行问用户裁决"。产品对，用例口径过时。
- **怎么改**：用例改名为 `test_a_method_review_without_a_usable_reply_asks_the_person_and_is_never_adoptable`，按现行流程断言：
  - 出现一道待答的 `adjudicate-method:` 裁决题；
  - 审阅员只被调用 2 次（原回复加一次修复），没有第 3 次；
  - 正式记录是判不下来，各条为 UNKNOWN，带 `REVIEW_NO_USABLE_REPLY:`；
  - 人答之前，规划器不被叫醒，也没有采用任何做法；
  - 人答"打回"以后，结论为 REJECTED，带人的裁决，规划器被叫醒；
  - 规划器再去采用时，提交闸门按 `METHOD_NOT_AUTHORIZED` 具名拒绝，采用列表仍为空。
- **守的保证**：
  - "没有结论不是通过、不能采用"仍在本条守，经真实提交闸门。
  - "审阅调用两次都没回来 → 给规划器报 NO_VERDICT"由 `full_target/test_service_intent_provider_blocker.py::test_a_method_review_that_never_answers_is_reported_as_no_verdict` 守。
  - 做法审阅"两次回复不可用 → 问人"原来没有专门用例（产品同形世界的 `test_review_no_verdict.py` 只覆盖终审和操作结果审查），本条补上了。
- **改坏**：把消费者里的 `unusable_second` 改成恒为 False，等于把第 2 次格式错误送回旧的"格式用完"路径。同时备份并重新生成部署清单，用例在"等裁决题"那步变红。源码和部署清单都已用 cp 备份恢复，并清掉 `__pycache__`。

## 4. `assurance_exec/test_c_assurance.py::test_real_migration_and_legacy`

- **现象**：`verifications` 的建表语句多了引号，逐字比对不相等。
- **原因**：用例要求旧库里除了列明要删的表，其他表的建表语句逐字不变。但后续迁移有意改了好几张旧表，用例没有跟上：
  - 迁移 38（`f64e8adb`，10-03，删金额计价）在 `budget_accounts` 等表上 DROP COLUMN；
  - 迁移 39 有 ADD/DROP COLUMN，还删了 `support_members`、`justification_sets`；
  - 迁移 40、41 又删了一批表（`summaries`、`method_evaluations`、`bound_inputs` 等）；
  - 迁移 42～45（`f6370f85` 起，10-04～10-06）重建了 `verifications`、`data_requirements`、`input_manifest_bindings`、`knowledge` 四张表。SQLite 的 `RENAME TO` 会把表名加上引号写进建表语句。

  报错先落在 `verifications`，修掉以后又依次露出 `budget_accounts`、`summaries`。按时间算，这条用例从迁移 38 起就是红的。
- **判断依据**：这些都是有记录的有意迁移（开发期不兼容旧数据）。产品没有缺陷。
- **怎么改**：豁免名单不再手写，而是从后续迁移的 SQL 里读出来。只有被 `DROP TABLE x`、`ALTER TABLE x ADD/DROP/RENAME COLUMN`、`RENAME TO x` 点到名的表才豁免。每张被豁免的表，升级后的状态必须和全新库完全一致：要么同样不存在，要么建表语句逐字相同。其他旧表仍要求建表语句逐字不变。原来手写的"已删表"名单和断言保留。
- **守的保证**：
  - 没被迁移点名的旧表，建表语句不能变（本条仍守）；
  - 有意改动的表，升级结果必须和全新库一致（新加的逐表断言，加上原有的全库建表哈希一致）；
  - 任务和事件的数据原样保留、迁移链校验和、备份、校验和被篡改时拒绝、迁移失败整体回滚，这些断言都没有改。
- **改坏**：没有做。SQLite 改旧表只能通过 ALTER 或 DROP，这两种写法都会被名单读到。"升级结果和全新库不一致"这类错误，原本就由全库建表哈希断言守。

## 5. `assurance_exec/test_accept_the_reviewed_package.py`（4 条）

- **现象**：`_stored_package() got an unexpected keyword argument 'reviewed'`。
- **原因**：A′ 删除批三（`eb749104`，10-03，"删不走保证通道的旧审阅路径"）执行了用户 10-02 的决定。叶子验收从此只剩保证通道一条路，`_stored_package` 也去掉了 `reviewed` 开关，主体相同时总是接管已审过的包。
- **判断依据**：用户 10-02 的决定是"不走保证通道的旧审阅路径删"，同一件事只留一条路径。
- **怎么改**：
  - 三条改成按现行签名调用：主体相同时接管已审包；主体不同交给存储拒绝；第一次验收直接插入。
  - **删除** `test_outside_the_assured_lane_a_differing_package_is_still_a_conflict`。理由：它守的是"保证通道之外"那条路径，这条路径已经整条删除，现在没有能触发它的入口。
- **守的保证**：主体不同一律不接管、交给存储拒绝，由 `test_a_different_subject_is_never_taken_over` 继续守。
- **改坏**：去掉接管条件里的 `binding` 比较，`test_a_different_subject_is_never_taken_over` 变红。已恢复。
