## 2. 第 1 批：看得到、救得回（原计划 §9.1、§10.2、§10.3、§11）

**原计划要求**
- 收敛进入"放弃"必须是明确的放弃动作（§9.1）。
- 被挡住的通知要有人工重置（§10.2）。
- 有离线图重建（§10.3）。
- 后台服务提供快照、为何未就绪、差异、收敛四个读接口，界面"树和执行图读同一个读取令牌"（§11）。

**现状**
- `SDK/orchestrator/taskgraph_operator.py:90`（放弃收敛）和 `:110`（重试通知）在，带版本比对，但 Host 和界面都调不到。
- 控制通道 `Host/handlers.py:35-38,242-245` 已放行四个读接口，但前端只用执行过程快照（`tauri-app/src/views/liveGraph/LiveGraph.tsx`）。旧的 `MissionTaskGraph.tsx` 和 `taskgraphStore.ts` 在 `b927004d` 被删了。
- `SDK/observability/taskgraph_replay.py:157` 只有一个测试在调。

**改动**
1. **两个操作动词**：控制通道新增"放弃这次改计划"（`taskgraph.abandon_convergence`）和"重新发送被挡的通知"（`taskgraph.retry_notification`），调 SDK 操作员服务，带期望版本号。
   - 界面在任务详情里卡住的收敛或通知旁边放按钮，点了先二次确认。
   - 主 Agent 在对话里也能发这两个动词（编排的使用者是主 Agent，人工把关要能在主对话里完成），同样要用户确认。
   - **先核对**操作员服务是否满足 §9.1 的"放弃前证明没有在途的危险动作，证明不了就保持等待并报告"。不满足就在 SDK 补上，并加一条拒绝用例。
2. **界面补回解释视图**（读接口都已存在，主要是前端工作）：
   - 点一个节点，显示"为什么还不开工"（调 why_not_ready）；
   - 有收敛任务时显示"改计划进度"面板（调 convergence），里面列出未决对象和上面两个按钮；
   - 版本切换时，历史版本用历史结构模式只读显示，并标注"历史，不可执行"。先核对现在的版本切换是不是这么做的，不是就改；
   - 两个版本之间可以看差异（调 diff）。
3. **诊断动作"核对执行图历史"**：Host 在诊断导出里调 `replay_taskgraph`，在只读副本上重建，结果写进诊断包。不调模型，不重放外部动作（不变量第 16 条）。

**验证**
- Host 处理器测试：动词放行、参数校验、版本冲突时拒绝。
- 前端组件测试：四个视图和两个按钮。
- SDK 测试：放弃条件不满足时拒绝。
- 真机一局：故意制造一次卡住的收敛，在界面上看到原因并处理掉。

## 3. 第 2 批：输入来源补实（原计划 §3.2 来源表、§5.3、§5.5）

**2.1 版本策略名实相符（§5.5"钉住不自动升级；跟随授权版本只在新绑定或新尝试前解析"）**
- 现状：编译器把所有数据边写死成"钉住"（`SDK/planning/htn/compiler.py:717`）。但产品里从来没有地方写钉住表（`pinned_revisions` 无生产方），于是实际退化成"候选里任选，有歧义就报告"（`SDK/artifacts/input_bindings.py:585-628`）。
- 改动：
  - 默认改为"跟随授权版本"，和现在的实际行为一致，并符合 §5.5。
  - "钉住"只在两种情况下用：方法或规划决定里明确声明的输入；以及某个消费者已经冻结过一次的输入，它重试时沿用第一次冻结的版本。钉住值从该消费者已有的冻结输入记录读，不新建表。
  - 哪个输入要钉住由规划器判断，系统只执行。
- 验证：上游重做产生新版本后，下游新尝试拿到新版本；已冻结的旧尝试恢复时不跟着变；声明钉住的输入不升级。

**2.2 格式兼容不再自己比自己（§3.2"格式兼容：相同身份或真实注册方向规则"）**
- 现状：验收时产出的格式引用取自需求本身（`SDK/orchestrator/leaf_acceptance.py:371-389`），比较永远相等；兼容登记表是空的。
- 改动：
  - 产出的格式引用改为取生产步骤类型声明的输出端口格式。
  - 格式不同、又没有登记过方向规则的，报"数据未绑定"，不放行。
  - 登记表在桌面领域保持为空，只认相同格式。
  - **内容对不对仍由审阅员判断**，不新增程序内容校验（核心思想）。
- 验证：两个端口格式不同时被拒绝；相同时照常通过。

**2.3 写入目标有输入（§3.2"写入目标规则未知不能放行写入"）**
- 现状：资源冲突检查在跑（`SDK/graph/projection_validation.py:805`），但没有步骤声明资源，等于空转。系统操作方案已经做过"步骤声明产出文件"：一条 `file:X` 要求链接到某个步骤后，那个步骤的任务行 `outputs` 就含 X（`plans/2026-09-28-system-operations/00-PLAN.md` D5）。
- 改动：
  - 编译时把每个叶子步骤声明的产出文件，变成写入目标（工作区命名空间加标准化路径，访问模式为写）交给冲突检查。
  - 两个可以并行的步骤声明写同一个文件，定计划时就报冲突，退回规划器（复用现有退回通道）。
  - 没声明产出文件的步骤，保持现有工作区写权限规则。不改成"一律不放行"，否则桌面任务几乎全会被拒。这一点作为接受的偏离写明。
- 验证：并行两步声明同一文件，提交时被拒；串行的不受影响。

**2.4 共享在产品里可用（§5.3"共享只读结果"）**
- 现状：桌面领域的叶子类型都是"本地写"，按 §5.3"写型工作默认不可共享"，注册时就拒绝共享（`SDK/planning/htn/registry.py:1586-1599`）。这符合原计划，但导致原计划 §15 的真实模型场景"分支共享并换方法"在产品里造不出来。
- 改动：桌面领域新增一个只读叶子类型"收集资料"，只给读工具，只读，允许复用。
  - 规划器可以让两个分支共用同一份"收集资料"结果。
  - 共享条件（合同、参数、输入版本、范围一致）由 SDK 现有校验负责（`SDK/graph/taskgraph_sharing.py`）。
- 新增类型要同步更新规划器能看到的类型目录和提示词，规划器提示词要升一版。
- 验证：脚本化通道里一局，两个分支共用一份"收集资料"；其中一个分支换方法，共享的生产者不被取消（不变量第 10 条）。

## 4. 第 3 批：用户中途改要求（§3.2 需求行、§5.6 末段）

**原计划要求**：要求变化必须是"原授权的要求修订"，不能让规划器自己减掉难的准则。

**现状**
- 要求修订只在建任务时写第 1 版（`SDK/orchestrator/assurance_factory.py:92`）。
- 修复请求里"要求已更新"的触发器，靠修订上的授权凭证字段（`SDK/orchestrator/planning_repair_requests.py:474-479`），但全库没有地方写这个字段。

**改动**
1. 控制通道新增"修改要求"（`mission.amend_requirements`），界面任务详情和主 Agent 对话都能发，用户确认后才写。
2. SDK 新增受控提交：写第 n+1 版要求修订，带用户授权凭证，同一个事务里发"要求已更新"事件。复用现有触发器，交给规划器出新计划。
3. 影响范围用现有的"屏障 + 使用前重验"。已通过、但对应准则被改的步骤，由规划器决定保留还是重做。程序只保证一点：被删或被改的准则不能再被当成已满足。
4. 根终审读最新一版要求。
5. 规划器提出的修订一律不受理，只有用户授权的修订才写入。

**验证**
- 定向测试：修订落库并触发规划；没有授权凭证的被拒；根终审用新版。
- 真机一局：任务跑到一半加一条要求，看到出第 2 版计划并按新要求交付。

## 5. 第 4 批：口径统一（§10.1 事件合同、§12 错误分类）

1. **错误表统一**
   - 现状：内部有约 174 处 `StoreError("TASKGRAPH_…")` 自由字符串；统一错误合同 `TaskGraphErrorV1`（`SDK/graph/notification_contracts.py:152`）只在只读接口用。
   - 改动：建一张枚举表，把现有拒绝码按 §12 归类：来源不可用、结构损坏、环、数据未绑定或等待数据、绑定过期、延后、预算、命令冲突、历史不可用。
   - 优先级按 §12 排序。给规划器的反馈带上类型码和字段路径。未知码一律拒绝。
   - 加一条"枚举全集"测试。
2. **补两种事件**
   - 派发已绑定：在派发事务里写。
   - 收敛已推进：在收敛状态每次变化时写。
   - 都只由对应的提交写，按命令号去重。
3. **删旧任务迁入基线**（`SDK/orchestrator/taskgraph_baseline.py` 及相关策略分支）：开发期旧路径直接删；用户已定旧任务不转换。

**验证**：枚举全集测试；两种事件各一条测试；删除后相关定向测试仍通过。

## 7. 不补、写成"接受的偏离"

1. 接续步骤会顺带交出它收到的文件（PLAN-STATUS 2A.1d 方案②）。
2. 新任务默认开执行图，不另设门禁（用户决定）。
3. 来源装配做成类方法（功能等价）。
4. 编码清单原地改写（开发期不兼容）。
5. 局部影响分析换成"屏障 + 使用前重验"（用户 09-30 决定）。
6. 修复和补后继步骤已开放执行（片 C）。
7. 同一步多次尝试择优已删（用户 10-02 决定）。
8. 模型从 GPT-5.6 改成 DeepSeek（用户决定）。
9. 原计划写的前置门禁已被后来的整体验收替代。
10. 42 组只做轻量映射；真实模型每场景 1 局，不是 3 局（用户偏好轻测试）。
11. 没声明产出文件的步骤不按"写入目标未知就不放行"处理（见 2.3）。

## 8. 顺序、发布与风险

- **顺序**：1 → 4 → 2 → 3 → 5。
  - 第 4 批的错误表会被第 2、3 批的新拒绝用到，所以放前面。
  - 第 5 批的真实模型场景依赖第 2 批的共享。
- **每批的流程**：先写测试，再改实现；跑定向测试；用 `scripts/release_sdk_opt.sh` 发版并让 Host 钉版；重新生成部署清单；用户看得到的改动真机跑一局；记录写进 `TaskGraph-补全-实施记录.md`；推送。
- **风险**
  - 第 2 批会让规划器和执行者提示词升版，在跑的旧任务起不来。按开发期规则不兼容，发布前停掉隔离版里的旧任务。
  - 第 2.3 批可能让现有任务因为同名写入在定计划时被退回，会增加规划轮次。真机局要观察规划次数。
  - 和知识库方案（`审阅通过结论入知识库-方案.md`，用户说先放着）都会改审阅和执行者提示词，到时合并到同一次升版。
