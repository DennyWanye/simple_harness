## 1. 失败类型 1 · L1 AppWorld 20 局 `management_exhausted`

### 1.1 现象

Worker 的 `REPORT.md` / `profile.json` 一致报 `tool_not_exposed`：

> `tools_and_permissions.allowed_tools` includes `appworld_execute`, but this attempt's **exposed tool schema** only contains: `workspace_list` / `workspace_read_file` / `workspace_write_file`

证据（`runs/h-arm/episodes/H-L1-0d8a4ee_1-r0/orchestrator/orchestrator.db` 的 `dispatch_intents`，`kind='attempt'`）：

```
prompt_version      = "worker-hierarchical-v1"
allowed_tools       = ["workspace_read_file","workspace_write_file","workspace_list"]     ← 实际暴露
fragment_execution.allowed_tools = [..., "appworld_execute"]                              ← Task Contract
agent_config.instructions = "[role:worker] … run_tests(path?) 在工作区里运行 pytest …"    ← 代码域提示词
```

同一局的 `manager` intent 是 `manager-appworld-v1`（领域模板生效），**只有 worker 掉回了代码域模板**。

事件序列（截断）：

```
MissionCreated(domain_id=appworld-v1) → MissionPlanning → PlanRevisionCommitted
→ AttemptCreated ×1 → ResultSubmitted(outcome="blocked")
→ OutcomeRecorded("appworld_execute … was not in the exposed tool schema")
→ ManagementRequested(round 1) → HierarchicalGraphChangeRefused(SEMANTICS_IS_HIERARCHICAL) → ManagementDecided(rejected)
→ …（重试 2/3/4 轮，每轮都被同一条拒绝挡住）
→ TaskFailed(stop_reason="management_exhausted", rounds=4, max_manager_rounds=4)
→ MissionFailed
```

### 1.2 根因 D1（SDK 缺陷）：分层 Worker 模板硬覆盖领域模板，丢掉领域工具

调用链：

1. `src/agent_orchestrator/orchestrator/event_handler.py:6624`
   `role = self._hierarchical_worker_template(role, mission.id)`
2. `event_handler.py:2308-2328` `_hierarchical_worker_template()`：
   只要 `role.prompt_version not in HIERARCHICAL_WORKER_VERSIONS`（该集合只有 `worker-hierarchical-v1`），
   就**无条件**返回 `WORKER_HIERARCHICAL`，把上一行 `self._template(role_for_task(task), mission.id)`
   经 `template_for_domain()`（`runtime/role_templates.py:816-829`）选出的 `worker-appworld-v3` 整个丢掉。
3. `runtime/role_templates.py:632-652` `WORKER_HIERARCHICAL = _revise(WORKER, …)`，
   而 `_revise`（同文件 128-142）**原样继承 `tool_names`**，即 `WORKER_V2.tool_names`
   =`("workspace_read_file","workspace_write_file","workspace_list","run_tests")`（同文件 163）——**没有 `appworld_execute`**。
4. `event_handler.py:6806-6816` → `governance/policies.py:165-175` `effective_tools()`：

   ```python
   allowed = set(mission_tools) & set(task_tools) & set(deployment.allowed_tools)
   return tuple(name for name in role_tools if name in allowed)   # 以 role_tools 为遍历基
   ```

   `appworld_execute` 在 Mission / Task / Deployment 三集合里都有，**唯独不在 role_tools 里，于是被丢弃**；
   `run_tests` 又因 `local_code_execution=False` 被 deployment 过滤掉，**剩下正好是三个 workspace 工具**，与 REPORT 完全吻合。

F 臂为什么正常：F 臂不走 `install_hierarchical`，不命中第 1 步，
worker 保持 `template_for_domain` 选出的 `worker-appworld-v3`（`runtime/appworld_templates.py:51-57` 明确带 `appworld_execute`）。
两臂的 `OrchestratorConfig` / `MissionSpec.allowed_tools` 是**逐字节相同**的（`run_h_arm.py:429-437,456` vs `run_f_arm.py:281-283,310`），
runner 没有任何差错。

**附带损伤**：同一条覆盖还把 AppWorld 的角色提示词换成了代码域提示词——
L1 的 Worker 被告知"用 run_tests 跑 pytest"，却在操作一个 AppWorld 模拟世界。即使工具补回来，提示词也必须一起补。

### 1.3 归属与修法

- **归属：SDK 缺陷**（runner 无合法接线可绕过：`HIERARCHICAL_WORKER_VERSIONS` 是模块级冻结集合，
  runner 只能 monkey-patch，那会破坏 §21.4 的冻结口径）。
- **修复位置**：`runtime/appworld_templates.py` + `runtime/role_templates.py` + `orchestrator/event_handler.py:2308-2328`
- **最小修法**（三步，不动 `effective_tools`、不动 DAG 模式字节）：
  1. 在 `appworld_templates.register_appworld_templates()` 里，用与 `WORKER_HIERARCHICAL` 相同的
     "outputs 端口"增量，对 **AppWorld 的 worker 文本**再派生一版 `worker-appworld-hierarchical-v1`，
     `tool_names` 用 AppWorld 那四个（含 `appworld_execute`）。
     注意 `_revise` 的锚点必须按 AppWorld 文本重写（AppWorld 的 envelope 示例与代码域不同，
     直接复用 `WORKER_HIERARCHICAL` 的锚点会在 import 期抛 `RuntimeError`，这正是 `_revise` 的设计意图）。
  2. `HIERARCHICAL_WORKER_VERSIONS` 从单值集合改为
     `frozenset({"worker-hierarchical-v1", "worker-appworld-hierarchical-v1", …})`，
     并在 `governance/domains.py` 的 `APPWORLD_DOMAIN.role_templates` 里把 hierarchical 语义下的 worker 指向新版本。
  3. `_hierarchical_worker_template` 的兜底从"常量 `WORKER_HIERARCHICAL`"改为
     "按 `commit.domain_for(mission_id)` 选该领域的 hierarchical worker 版本，没有登记才回落到 `WORKER_HIERARCHICAL`"。
- **兜底备选**（若上面来不及）：把兜底改成 `replace(WORKER_HIERARCHICAL, tool_names=role.tool_names)`，
  只补工具不补提示词——**不推荐**，因为 AppWorld Worker 仍会读到"跑 pytest"的指令，L1 成绩不可信。
- **回归**：`tests/orchestrator/` 需新增一条"appworld-v1 + hierarchical 的 attempt intent 的 `allowed_tools` 含 `appworld_execute`"的断言，
  这是本缺陷唯一一条能挡住它的不变量。

## 2. 失败类型 2 · L3 code C1/C2/C4 各 2 局 `planning_failed`

### 2.1 现象（六局逐字相同）

```
MissionCreated(domain_id=code-v1) → ObligationDemandAdmitted → MissionPlanning
→ MethodApplicabilityAssessed{refusal_count:3, 三条方法全部 verdict=NEEDS_EVIDENCE}
→ PlanningRejected{ordinal:1, reason:"proposal_unreadable",
     error:"method 'code.fix-by-patch' is NEEDS_EVIDENCE for task task-root; a method is grounded only where it applies (§7.2)"}
→ PlanningRejected{ordinal:2, reason:"proposal_unreadable", block_defect:"block_missing"}
→ MissionFailed{attempts:2, stop_reason:"planning_failed"}
```

三条方法被拒的**同一个原因**（`MethodApplicabilityAssessed` 全量 payload）：

| 方法 | unknown_preconditions | verdict |
| --- | --- | --- |
| `code.fix-by-patch` | `code.test-is-failing@1#d3d427e5…` | NEEDS_EVIDENCE |
| `code.fix-by-revert` | `code.regression-commit-known@1#3e6b06ac…` | NEEDS_EVIDENCE |
| `code.fix-by-assessed-revert` | 上面两条 | NEEDS_EVIDENCE |

而 `observations` 表里这两个命题**都有记录**，`polarity = 0`（FALSE），观察器 `code.test-observer` / `code.history-observer`，
`coverage = BEST_EFFORT`。`result.json.evidence_round.recorded` 也逐条记着 `polarity:false`。

### 2.2 根因 D2a（runner 接线）：L3 的根目标断言了一个事实上为假的前置条件

`runner/run_h_arm.py:187-188`：

```python
if task.layer == "L3":
    return "code.fix-failing-test", {"repository": str(worktree), "failing_test": "tests"}
```

C 系列题目的设计是"**可见测试是绿的，只有隐藏评分器会失败**"（FREEZE.json 的 `hidden_targets` 与
`code-tasks/C*/repo/tests/test_public_*.py`）。于是 `SuiteObserver`
（`planning/htn/observers/code.py:768-846`）跑 `pytest tests` 拿到 exit 0，如实给出
`code.test-is-failing = FALSE`。

SDK 的四值语义（`contracts/evidence_state.py:266-269`）：

```python
def support(self) -> SupportCount:
    if self.polarity: return POSITIVE_SUPPORT
    return NEGATIVE_SUPPORT if self.is_authoritative_negative else NO_SUPPORT
```

`code.test-is-failing` 在 `planning/htn/seed_methods/code/predicates.json` 里是 **`world_assumption: OPEN`**，
OPEN 域的非权威否定观察 → `NO_SUPPORT` → `atom_truth` 返回 **UNKNOWN**（`knowledge/predicates.py:316-331`），
所以不是 `PRECONDITION_FALSE` 而是 `NEEDS_EVIDENCE`。

这**不是 SDK bug**：SDK 自己的真实模型冒烟
（`tests/orchestrator/full_target/test_real_provider_hierarchical_smoke.py:79-84`）把这条语义写成了注释，
并刻意挑了一条**真失败**的测试：

> `code.test-is-failing` 是 OPEN 谓词，观察器发现测试通过会产生一条非权威否定——§6.6 读作 UNKNOWN 而不是 FALSE，方法会永远停在 NEEDS_EVIDENCE。**指定一条会通过的测试会让这个文件测错东西。**

H runner 恰恰指定了一条会通过的测试（整个 `tests` 目录）。`run_h_arm.py:170-172` 的注释里已经预期
"没有种子方法适用时走 §7.3 合成轮（gap G3）"——但这条退路在 SDK 里是关着的，见 D2b。

### 2.3 根因 D2b（SDK 设计缺口）：NEEDS_EVIDENCE 被排除在方法合成之外，形成活锁

`orchestrator/hierarchical_dispatch.py:265-271` + `2789-2836`：

```python
SYNTHESIS_WORTHY_REFUSALS = {PRECONDITION_FALSE, CAPABILITY_UNAVAILABLE, TYPE_ERROR}
...
if any(report.status not in SYNTHESIS_WORTHY_REFUSALS for report in seen):
    continue  # the answer is "look" or "settle", not "invent"
```

设计意图是"NEEDS_EVIDENCE 的解法是再看一眼（`run_evidence_round`），不是凭空发明方法"。
但在 OPEN 谓词 + 真否定观察这种组合下，**再看多少眼答案都一样**：观察器每轮都记一条 `polarity=false`，
每条都贡献 `NO_SUPPORT`，真值永远停在 UNKNOWN。
于是 `_gather_evidence`（`event_handler.py:2027-2053`）永远返回"记录了观察"=进展，
`_request_method_synthesis`（同文件 2055-2086）永远拿到空列表，规划永远无解。

### 2.4 根因 D2c（SDK 缺陷）：语义拒绝被错标成 `proposal_unreadable`，白烧掉规划梯子

第 1 轮的 Planner **给出了合法的 `<plan_revision_proposal>` 块**，只是选了一条 NEEDS_EVIDENCE 的方法。
`event_handler.py:3730-3742` 把 `apply_planner_reply` 抛出的任何 `ContractError` 一律记成
`reason="proposal_unreadable"`，只有 `__cause__` 是 `BlockError` 时才另加 `block_defect`。
结果：

- 事件里"读不懂"与"读懂了但语义违规"混成一类，**排障读数失真**；
- `max_planning_attempts` 默认 **2**（`runtime/assembly.py:92`；`__main__.py:526` 的 CLI demo 用 3，runner 未覆盖），
  一次语义拒绝就吃掉一半梯子，第二轮模型放弃输出块，Mission 当场判死。

### 2.5 归属与修法

| 编号 | 归属 | 修复位置 | 最小修法 |
| --- | --- | --- | --- |
| D2a | **runner 接线** | `runner/run_h_arm.py:187-188` | L3 的根目标不要用 `code.fix-failing-test` + 绿色可见套件。二选一：(a) 给每道 C 题在 `code-tasks/C*/` 里声明 `construction.json#root_goal`（像 L4 那样），用一个**前置条件在该题上真成立**的目标类型；(b) 若坚持 `code.fix-failing-test`，题目夹具里必须放一条**真失败**的可见测试，并把 `failing_test` 指到它。改题单会动 FREEZE 哈希，需按 §21.4 重新生成冻结候选。 |
| D2b | **SDK 设计缺口** | `orchestrator/hierarchical_dispatch.py:265-271,2789-2836` | 最小：在 `goals_needing_method` 里加一条"**证据已饱和**"判定——同一 `proposition_key` 已被同一观察器以 `OBSERVED` 结局记录过 ≥N 次且真值仍是 UNKNOWN，则该 NEEDS_EVIDENCE 视同 `PRECONDITION_FALSE`，准许进入合成轮。不放宽"UNKNOWN 不开安全闸"（I18 不动），只放宽"要不要发明新方法"。 |

## 3. 失败类型 3 · L3 C3 ×2 + L4 M1 ×4 / M2 ×4 / M3 r2 = `no_dispatchable_work`

这一类**恰恰是最值得看的**：它们的计划、派发、执行、验证**全部成功**，
`code_test` PASS、`TaskCompleted`、`AcceptanceCommitted` 一路打到根验收，**只在最后一步倒下**。
其中 C3 ×2、M1 ×4 官方隐藏评分器还是 **PASS**（`official_utility=true`）——**交付物是对的，编排没认**。

### 3.1 现象（M1-r0 为例，10 局完全同构）

```
PlanRevisionCommitted(adopted_method_instances=[mi-…])
→ facts 叶：AcceptanceCommitted{accepted_outputs:[{port:"facts"}]}
→ reproduce 叶：AcceptanceCommitted{accepted_outputs:[{port:"diagnosis"}]}
→ patch 叶：AcceptanceCommitted{accepted_outputs:[{port:"patch"}]}
→ verify 叶（终结步）：VerificationPassed → TaskCompleted
   → AcceptanceCommitted{accepted_outputs: []}          ← 空
→ HierarchicalRootReviewCut(4 contributions)
→ HierarchicalRootReviewRejected{criteria:{c-test-passes:"FAIL"},
     finding:"c-test-passes has no readable proof … evidence.kind=none: no artifact was delivered on a declared output port"}
→ RootGoalResolutionRefused{SUCCESS_EXPRESSION_NOT_PASS, REVIEW_VERDICT_NOT_ACCEPT, COMPOSITION_OBLIGATION_FAILED}
→ HierarchicalMissionStalled{code:"hierarchical_no_dispatchable_work"}

```

统计核对（10 局全中，无一例外）：

```
H-L3-C3-r0/r1、H-L4-M1-r0..r3、H-L4-M2-r0..r3
AcceptanceCommitted 共 4 条 / 其中 accepted_outputs 为空的恰好 1 条（终结步）
```

### 3.2 根因 D3（SDK 缺陷）：终结步的输出端口"既不告知、也不强制、却被根验收要求"

三处用的是**同一条规则**——"端口 = 有 `DataRequirement` 边消费它"：

1. `orchestrator/accepted_outputs.py:99-112` `declared_output_ports()`
   > Read from the `DataRequirement` edges rather than from the producer's own port list, because **a port with no consumer feeds nothing**
2. `orchestrator/hierarchical_dispatch.py:1643-1690` `declared_output_ports_for()` —— 喂给 Worker 上下文的那份
3. `orchestrator/resolution_commits.py:209-216 + 798-816` `_declared_ports()` / `OUTPUT_PORT_UNCLAIMED` —— 验收侧强制的那份

种子方法 `code.fix-by-patch`（`planning/htn/seed_methods/code/methods.json`）的 steps 是
`facts → reproduce → patch → verify`，`composition.finalizer_step = "verify"`，
`criterion_links` 把 **`c-test-passes` 挂在 `verify` 的 `c-green` 上**。
而 `verify` 对应的 `code.verify-tests` 在 `task_types.json` 里声明了 `port_key:"report", required:true`——
**但没有任何下游步骤消费它**（它是终结步）。于是：

- 第 2 处：`verify` 叶的上下文包里**根本没有 `declared_output_ports` 段**。已逐字节核对
  （`H-L4-M1-r0` 的四个 attempt intent，前三个都有 `declared_output_ports`，
  `task-13b737…:attempt-1`（verify）是 **NONE**）。Worker 无从得知有 `report` 端口。
- Worker 的 envelope 因此没有 `outputs` 字段（`results` 表原文已核对）。
- 第 3 处：`consumed` 为空 → `unclaimed` 为空 → **`OUTPUT_PORT_UNCLAIMED` 不触发**，验收静默通过，`accepted_outputs = []`。
- 根验收侧（`orchestrator/root_review.py` 的 `request` 读 `list_acceptance_outputs`，见 P2.3c journal §5 第 3 轮）
  看到该贡献 `evidence.kind=none` → `c-test-passes` FAIL → REJECT。

也就是说：**根目标的成功准则通过 `criterion_links` 消费了终结步的产物，但这条"消费"没有被建模成 `DataRequirement`**，
三处规则于是一致地把它当成"没人要的端口"，唯独根评审员把它当成"必须交付的证据"。

### 3.3 关键旁证：P2.3c 冒烟的 COMPLETED 是评审员宽容，不是机制成立

`simple-harness-sdk/.local-test-evidence/2026-09-16/htn-smoke/part3a-round04-events.json`（第 4 轮，即 journal 记为 COMPLETED 的那轮）：

```
AcceptanceCommitted [{"port": "facts"}]
AcceptanceCommitted [{"port": "diagnosis"}]
AcceptanceCommitted [{"port": "patch"}]
AcceptanceCommitted []                      ← 同一个空终结步
HierarchicalRootReviewCut → GoalResolutionCommitted → MissionSuccessJudged → MissionCompleted
```

**缺陷一模一样**，只是 deepseek-flash 的根评审员在 `evidence.kind=none` 的情况下仍判了 ACCEPT。
grok-4.6 的评审员判 FAIL，**而且它是对的**。所以 §21.4/§21.5 里"层次 Mission 已走到 COMPLETED"这条交付
**不能作为机制成立的证据**，本次 H 臂 0/40 才是这条路径的真实状态。

### 3.4 根因 D5（SDK 缺陷）：根验收被拒后没有任何修复路径；嵌套 compound 永远不会被细化

两个独立后果，同一个成因——**一个 Mission 一生只有一次规划轮**。

`event_handler.py:1969-1972`：

```python
for mission in self._active_missions():
    if mission.status is MissionStatus.CREATED:
        await self._start_planning(mission)
```

`_start_planning`（2167-2168）是 `begin_planning` 的唯一调用点；
`_planning_rejected`（3470-3486）只在 Mission 仍处于 PLANNING 时按 ordinal 递增重试。
**一旦 `PlanRevisionCommitted`，Mission 转 ACTIVE，Planner 再也不会被问第二次。** 逐局核对 `dispatch_intents` 全部印证：

## 4. 失败类型 4 · L4 M3 r0/r1/r3 `no_progress`

### 4.1 现象

```
AttemptCreated(ordinal 1) → VerificationFailed(code_test: "pytest failed: 1 error in 0.06s")
AttemptCreated(ordinal 2, retry) → VerificationFailed(同)
→ ManagementRequested(round 1)
   → PolicySuggestionRefused{operations:["add_task"], keys:[allowed_tools,budget,verification_policy]}
   → HierarchicalGraphChangeRefused{reason:"SEMANTICS_IS_HIERARCHICAL"}
   → ManagementDecided{decision:"rejected"}
→ ManagementRequested(round 2) → 同样三步
→ TaskCancelled ×2 → TaskFailed{no_progress_count:2, no_progress_limit:2, stop_reason:"no_progress"}
→ MissionFailed
```

### 4.2 根因 D4（SDK 缺陷）：分层 Mission 里 Manager 仍走 legacy `TaskGraphChange`，100% 被拒

- `orchestrator/event_handler.py:4894-4953` `_request_management()`：只有 `dynamic_graph` 一个开关，
  **没有任何 hierarchical 分支**，分层 Mission 照样开 manager intent。
- Manager 回复经 `_collect_manager`（5209 起）→ `commit.commit_graph_change`（5367/5377）
- `orchestrator/commit_service.py:1303-1329`：语义是 hierarchical 时**无条件**发
  `HierarchicalGraphChangeRefused` 并抛 `CommitRejected`，注释明说"开着的那扇门是 `PlanRevisionProposal` + `commit_plan_revision`"——
  **但没有任何代码把 Manager 引到那扇门**。

于是每一轮管理都是必然空转：

- L1 里它消耗 `max_manager_rounds=4`（`runtime/assembly.py:145`）→ `management_exhausted`（§1 的第二重死因）；
- M3 里它消耗 `no_progress_limit=2`（`assembly.py:144`）→ `no_progress`。

换句话说：**L1 的 20 局是 D1 + D4 叠加**——D1 让 Worker 什么都做不了，D4 让唯一的补救机制空转到耗尽。

### 4.3 归属与修法

- **归属：SDK 缺陷**
- **修复位置**：`orchestrator/event_handler.py:4894-4953`（请求侧）与 `5209-5390`（收集侧）
- **最小修法（二选一，优先 (a)）**：
  - (a) **短路**：`_request_management` 开头加 `if self._new_mode(mission) is not None: return None`，
        并在原地记一条结构化事件（例如复用 `HierarchicalGraphChangeRefused` 的理由码或新增
        `ManagementNotApplicableUnderHierarchical`）。效果：不再白烧 manager/no_progress 额度，
        失败沿"验证失败→重试→Task 自己的失败路径"如实收口。改动最小，风险最低。
  - (b) **接通**：给 Manager 一个 hierarchical 变体，产出 `<plan_revision_proposal>` 走
        `commit_plan_revision`。这与 D5-A 的修复是同一条路径，可以合并做——但工作量远大于 (a)，
        建议放到 P3/TaskGraph 阶段。
- 顺带：`no_progress` 的判定（`no_progress_limit=2`）把"系统自己拒绝了自己的修复提案"算成了
  "Task 没有进展"，语义上应把 `ManagementDecided{decision:"rejected", error:SEMANTICS_IS_HIERARCHICAL}`
  排除出 no_progress 计数——这是 (a) 的自然副产品。

## 5. 官方评分口径核对（对验收结论有实质影响）

### 5.1 `official_utility` 与 Mission 完成度是**两条完全独立的线**

`runner/run_h_arm.py`：

- **L1/L2（AppWorld）**：`result["official_utility"] = episode.finalize()["success"]`（`run_h_arm.py:578-581`），
  由 AppWorld 官方评估器判定，与 `mission_status` 无关。
- **L3/L4（code）**：`run_h_arm.py:543-545` 先用 `_accepted_files()` 导出 delivery，
  再 `common.grade_candidate()` 跑隐藏评分器，`official_utility = grading["hidden"]["status"] == "PASS"`（600 行）。

**关键**：`_accepted_files()`（`run_h_arm.py:710-725`）的 docstring 写的是"每个 Task 的已验收产物"，
**实现却是遍历每个 attempt 的整个 workspace，后写覆盖先写**——
它导出的是**模型改过的文件**，不是"被编排系统验收过的产物"。
所以 L3/L4 的 official 分数**完全不经过 Acceptance / 根验收**，
Mission FAILED 也照样能拿 PASS。本次 40 局里 `official_true = 9`、`COMPLETED = 0`，就是这么来的。

### 5.2 `valid_success` / `false_completion` 的口径

`run_h_arm.py:622-631`：

```python
false_completion = declared_complete and official_utility is not True
valid_success    = no error and admission_denials == [] and unknown_usage_calls == 0 and official_utility is True
```

注意 `valid_success` **不含 `mission_status == COMPLETED`**。
于是出现了 `H-L3-C3-r0` 这种：`mission_status=FAILED, stop_reason=no_dispatchable_work, valid_success=True, official_utility=True`。

`false_completion` 在 H 臂恒为 0——因为 `declared_complete` 恒为 False（一局都没 COMPLETED）。
**"错误宣称完成 = 0"这条 §21.5 硬门槛在 H 臂是平凡成立的，不构成任何正面证据。**

### 5.3 `pair.py` 的判定同样只看 official

- `pair.py:105-106` McNemar 配对用 `official_utility`；
- `pair.py:137-142` cost/`official_true` 用 `official_utility`；
- `pair.py:251` L1 不退步门槛 `hc["official_true"] >= 23`（H 现在是 0/20，**必然 FAIL**）；
- `pair.py:226-230` 的 `false_completion` 不变量如上所述平凡 PASS；
- **没有任何一条不变量断言"H 臂的 Mission 应当 COMPLETED"**。

### 5.4 对验收结论的影响（必须写进报告）

1. **不能只报 `official_true`**。L3/L4 的 official 是"模型改的文件过没过隐藏测试"，
   分层编排是否成立**完全没被它度量**。建议在 `pair.py` 增加一条硬性不变量：
   **`mission_status == COMPLETED` 的比例**，并作为 §21.5 H 臂的独立门槛列出；
   或至少在报告的 H 臂表里把 `completed / official_true / stop_reason 分布`三列并排。
2. `mechanism-receipt v2` 的 `official_pass` 字段由 `run_h_arm.py:606` 用 `official_utility` 回填，
   L4 的 `mechanism_verdict` 又以它为基准重评（609-616），**同样继承了这条脱钩**。
3. 结论表述上：本次 H 臂的正确说法是
   **"分层编排 0/40 走通；其中 9 局模型交付物本身通过了隐藏评分器，但编排从未认可它们"**，
   而不是"H 臂 official 9 局通过"。
