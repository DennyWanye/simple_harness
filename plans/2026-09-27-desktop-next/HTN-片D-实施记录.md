# HTN 精简 片 D　其余越位：实施记录

日期：2026-10-02
版本：SDK opt.122、opt.123（Host 同步钉版）
依据：`HTN-后续-方案.md` 片 D（六小项）、`HTN-精简审计-2026-10-01.md` 第一节第 5、6、9、10 条与第三节第 8 条。

## 一句话

Harness 里剩下的几处"替模型判断"收掉了：任务停在原地时先把局面如实交给规划器一次再判停；
文档任务的文字要求满足与否以最终审查的结论为准，程序只做秩序检查；Host 不再用词表猜一条要求
是不是"操作"；契约里的文字不再被猜"像不像代码"；产品里关掉保证通道的开关删除，旧审阅路径在
产品里不可达。

## 做了什么

### 1　判停之前先问规划器一次

此前：计划停在原地（没有一步可以派发，也不在等任何东西），程序多看一轮确认之后直接判任务
失败。真机里按这个原因失败的有 21 局，是第一大失败类。

现在：确认停滞之后记一条通用修复请求（触发来源"没有可派发的工作"），与步骤失败、证据失效、
目标没有做法走同一条路，规划器被叫来一轮。请求里只有事实：

- 哪些步骤被哪道闸挡住（原因与原因代码）、哪些放行了却没派发、哪些要求还欠着；
- 最终审查或中间目标的组合审查**没有给出结论**时（审阅员的回复用完仍无法采用），写明是哪
  一次审查、原因代码是什么；最终审查被打回时带上它的状态与意见。

改计划、问用户还是别的，由规划器定。程序这边只有秩序：

- 每个计划版本只问一次。同一版计划问过之后又停在原地，才按"没有可派发的工作"结束，停机
  报告写明问过、规划器那一轮有没有开出来；
- 请求的范围是整个计划，任何一步上的计划改动都算处理了它；计划换了版本，旧版本的这条请求
  由系统了结；
- 请求的幂等键含任务号和计划版本号；
- "最终审查打回的修复次数用完"这个有名字的停机排在它前面，不受影响。

顺带补了一个如实上报的缺口（片 C 真机两局暴露）：停机报告里"审查的回复用完了"此前只认
"格式重试用完"一种事件；第二次回复能解码但不能采用（比如引用了没展示给它的证据）同样是
终局，却不报；中间目标的组合审查没有结论也不报。现在两种结局、三类审查（最终审查、组合
审查、操作结果审查）都报。连带效果：操作结果审查以这种方式结束时，不再被当成"还在等"
一直挂着；新做法的审阅以这种方式结束时，规划器更早拿到确切原因。

规划器提示词加了一段，说明这种请求里各字段是什么（提示词版本第 16 版，仍只有一份）。

### 2　文档任务以最终审查的结论为准

此前：文档领域里，程序的"文档覆盖"裁判排在已认证的最终审查结论前面。一条文字要求只有在
某条被接受的声称**原文与要求字面相等**时才算通过；"不确定"的要求占比超过阈值就按"证据
不足"停机。审阅员逐条读过成果给出的结论被它盖掉。

现在（走保证通道的任务，即产品里的全部任务）：

- 文字要求满足与否 = 已认证的最终审查对这一条的结论；
- 覆盖结果对文字要求只做秩序检查：引用能解析、资料是当前版本、声称状态可用、评估可用、
  "不确定"必须附说明。没过记"未通过"，这一条就不算满足，不管审阅员怎么说；没有问题记
  "通过"（有贡献）、"不确定"（如实声明了）或"没有结论指向这一条"；
- 字面相等不再是通过条件；"不确定"占比不再停机；没有声称指向的要求不算秩序问题；
- `cite:` 这类确定性要求（有没有引用到那份资料）仍由程序判；
- 判定、留存判定的重看、提交三处走同一条规则（`document_judgment` / `coverage_objection`），
  不再各写一份。

前端文档页补了三个标签（最终审查、引用与资料检查未过、没有结论指向这一条）。

### 3　最终审查打回时把全部意见交给规划器

片 0 已经做完（最终审查打回改成一条通用修复请求，带审阅员的全部意见），这里没有新改动。

### 4　Host 不再用词表猜"操作"

此前：自动模式下，Host 用一张词表（发布、上传、发送、部署、deploy……）判断一条白话要求是
不是"操作"，是就留给人点确认。"说明如何发布"的文档任务也会被挡住。

现在：一条要求是内容还是操作，只认主 Agent 整理任务时写好的结构化前缀 `action:`（主 Agent
的建任务工具说明里本来就要求发布写成 `action:file_publish.publish:<文件名>`）。词表删除；
白话要求按内容确认，它满足与否由最终审查判。

### 5　契约里的文字不再被猜"像不像代码"

此前：登记做法、任务类型、谓词时，对每个字符串做子串匹配（"update "、"select "、
"delete from"、"lambda "……），作用于整份做法 JSON，包括模型写的自由文字——英文一句
"update the README" 就会被拒。条件解释器只走结构化节点，字符串从来不会被执行，这个匹配
没有安全价值。

现在：只留"不许出现可调用对象"；条件必须是结构化节点（写成一段字符串、未知操作符照旧
拒收）。子串表删除。

### 6　不走保证通道的旧审阅路径：调查结论与处理

调查结论：**还走得到，但产品里只有一个入口**。

- 新任务走哪条通道在创建时定：装了保证通道且选中 → 保证通道；否则是"只有规划协议、没有
  保证通道"的旧通道，最终审查由不带认证的旧根审阅员做、文字要求由旧的裁判 Critic 判。
- 产品（Host）里，保证通道默认开；唯一能让新任务走旧通道的是设置项 `assurance_profile: off`。
  真机库里 118 个带通道记录的任务中有 3 个走了旧通道（最近一个在 09-27）。
- SDK 自己的测试里有几百条是在"不装保证通道"的世界里跑分层任务的。

处理：

- Host 的关闭开关删除——设置里不再有这一项，写了也不起作用，新任务一律走保证通道。产品里
  旧审阅路径从此不可达。
- SDK 里的旧根审阅员与裁判 Critic 代码**这次没有删**：它们是那几百条测试的地基，与片 0 记下
  的"旧分层旁路"是同一件事，并入片 D 之后那次单独清理。

## 与方案不一样的地方、当场决定

1. **第 2 项只改了保证通道。** 方案写的是"删字面相等与占比阈值"。实际上这两样还被不走保证
   通道的旧平面模式用着（那条线的验收测试有十几个文件、几十条是围绕它写的），整条删要连
   旧平面模式的文档验收一起重写。这次做法是：覆盖结果按任务所在的通道读——保证通道只做
   秩序检查，旧平面模式行为不变；旧的那一半随"旧平面模式整条线"一起处理（待用户定）。
   文档领域配置里的阈值字段同理没有动。
2. **第 5 项连带改了一处哈希登记。** `contracts/semantic_base.py` 的内容哈希登记在执行图的
   编解码清单里（清单哈希是执行图文档的身份之一）。改了文件就要更新登记；此前按旧清单存下
   的执行图文档不再能读（开发期不兼容旧数据）。
3. **第 6 项没有删 SDK 代码**，见上。
4. **第 1 项的整条路测试停在"规划轮开出来了"。** 现有的停滞夹具没有规划授权，规划意图会
   停在等授权，模型不会被调用；规划器被叫来之后如何作答，由"目标还没有做法"那一组测试
   覆盖（走的是同一条路）。真机复验见下。
5. **没有动审阅员回复的格式口径。** 片 C 真机第 2 局：组合审查两次结论都是"通过"，一次外面
   包了代码围栏、一次多写了一个值为空的字段，都被按格式错误拒收。从严是用户 09-24、09-26
   定的，这里不改，列入最终报告请用户定。

SDK 24 项、Host 3 项，全部被抓住（`.local-test-evidence/2026-10-02/sliceD/mutations/results.txt`、
`host-results.txt`）。两处值得记：

- "提交时按旧平面口径比对"第一轮**没抓住**——当时提交环节只有源码文字检查，而被改坏的那一行
  有两处同样的写法。把逐条比对收成一个函数（`reconcile_document_judgments`）、补了行为测试后

  就是这条路不空转的保证，键的写法有测试钉住。

## 独立核验（一名 Opus 子代理，只读，只报阻断级，一轮）

结论：**没有阻断问题**。它逐项核对了：

- 判停前问规划器不会让主循环空转（同一版计划第二次停住时请求已存在，直接判停；要再问只能等
  规划器提交新版本）；请求记下之后没有"规划轮开不出、任务也不判停"的悬挂路径；有名字的
  停机没有被抢先；根任务号作触发引用不会让影响分析抛错。
- "审查用完"口径变宽后三个使用点都没有被带出错误行为；"第二次回复被拒"这个事件只在这次
  审查到头时才写。
- 不走保证通道时覆盖结果逐字段不变；保证通道上原来的五项秩序否决都保留，资料过期又没有
  别的合格贡献时仍判未通过。
- 契约里的字符串不会被拿去执行或拼进 SQL；清单里登记的哈希与文件一致。
- Host 里已没有地方读那两样被删的东西。

它另提了三条"不是阻断但值得一提"，处理如下：

1. 记请求时要算影响范围，操作台账读不了会抛一种不属于契约错误的异常，原来接不住，会冲出
   主循环。**已修**：接住，问不成就照旧判停，报告里如实写没问过；补一条测试。
2. "停住 → 问 → 规划器提交新版本 → 又停住"每版只问一次，但版本数只受任务额度和总时限约束；
   规划器这一轮答错次数用完时，停机原因是"规划失败"而不是"没有可派发的工作"。**没有改**：
   每一圈都是规划器真提交了一版新计划，花的是真实额度，额度与时限就是它的上限；停机原因
   如实反映最后发生的事。记在这里备查。
3. 两处与"行为完全不变"的细小出入。**已修**：旧平面口径下过期判定仍只改原来那三个字段；
   就地改写一行判定时先清掉上一种判法留下的字段（否则界面上可能对着已满足的一行显示
   "未通过"）。各补一条测试。

修补后相关定向测试重跑见"测试"一节。

## 发布与真机

**发布**：SDK opt.122（提交 `5f39458c`，Host 钉版 `475e9875`；Host 与前端改动单独一个提交
`5d746949`），随后 opt.123（提交 `f56a3aef`，Host 钉版 `f317eff1`）。都已推送 origin main。

**opt.122 上真机第一次就出了问题：主循环连续报错，新任务走不下去。**

- 现象：新建的任务在规划器第一次回答之后不再前进；后端每分钟记一次"编排循环失败"，报的是
  "执行图文档的编解码清单不受支持"。那一局取消（`mission-e174ec99fb225bb3`，日志留在
  `run1-opt122-loop-failing.log`）。
- 原因：第 5 项改了 `contracts/semantic_base.py`，它的内容哈希是执行图文档身份的一部分，库里
  77 份旧任务的执行图文档从此读不了——开发期不兼容旧数据，这本身是预期的。没预期到的是：
  保证层每轮评估"能不能收尾"时会去读一个旧任务的执行图，读取抛的是契约错误而不是"提交
  被拒"，那里只接后一种；保证层轮询对单项工作也只接保证层自己的错误和额度错误。于是异常
  冲出轮询、再冲出主循环，每一轮都这样，所有任务一起停。
- 为什么测试没测出来：测试里的库都是当场新建的，没有"按旧清单存的文档"。日志里的调用栈
  被脱敏遮掉了，是给隔离版应用的后端临时挂了一个只写调用栈的调试钩子才定位到的（不改
  产品代码）。
- 修法（opt.123，秩序而不是兼容）：一个任务的数据读不了，是这个任务自己的事。收尾评估读
  不回计划时如实记成"根网络不可用、未就绪"；保证层轮询里任何一项工作读自己任务的数据
  出错，只影响这一项，按原有的持久重试上限再看，别的任务照常。旧文档仍然读不了，不迁移、
  不回落。新测试 6 条（`assurance_exec/test_unreadable_mission_is_isolated.py`），保证层相关
  定向测试 402 通过，2 项变异都被抓住。
- 复验：opt.123 上主循环 0 次失败，新任务越过了之前卡住的地方。

**真机（opt.123，三层题）**

- 第 1 局 `mission-a0e253654aa61e91`：主循环全程 0 次失败。规划器拆出中间目标、为它单独提做法并过审，中间目标下两步验收通过、组合审查通过并形成中间结论；规划器 5 次回答里 1 次少写字段、重试后恢复。随后上游模型线路整体不可用（极小的请求也在 125 秒后返回 524，转发程序重启后依旧），一步执行和连续 7 次规划轮都没拿到回复，任务按"运行环境不可用"如实停下（服务故障宽限用完）。**判停前问规划器、文档任务以最终审查为准这两条路这一局没有走到**，等线路恢复后补跑，结果追加在这里。

证据：`.local-test-evidence/2026-10-02/sliceD-real/`。
