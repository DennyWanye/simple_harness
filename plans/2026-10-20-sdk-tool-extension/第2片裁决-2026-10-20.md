- 它是第 7 步平面模式时代的测试服务。平面模式 10-02 已删；现在 `begin_handoff` 对没有操作链接的动作一律 `operation_link_missing`（`action_commits.py:951`）。

### 4. 申请单的参数现在怎么准备

- 系统准备（`AUTHORIZED_SLOT`，产品现在唯一在用的路）：系统从已确认效果覆盖的那条 `action:` 要求读出连接器、操作、目标；在已接受的内容产出里找与目标同名的唯一产物；生成申请单 JSON `{"artifact_path": 那个产物}`；`bind_artifact_params` 再填 `artifact_id/content_hash/size/storage_uri`。
- 人提交（`USER_COMMAND`）：Worker 写 `actions/*.json`，确认页列出来，人点提交。
- **两条路都以"一个已接受的候选产物"为锚。** 意图、冻结提案、请求哈希里都有 `candidate_artifact_ref`、`candidate_file_hash`、生产步骤的任务与出现编号；生产步骤的接受记录还必须是同一义务下的 CONTENT/PREPARATION 贡献（`operation_intent_sources.py:170-200`）。

### 5. 对账与重交

- 挂了操作链接的动作，"查无记录"不再等于"没发生"（`actions.py:298-304`）。必须由档案登记的对账适配器给出一种登记过的"没生效证明"（`NonapplicationProofKind`）。
- 证明成立后，同内容会开**新版本、新幂等键**（`action_commits.py` 的 `proven_failure` 分支，键是 `{action_id}:v{版本}`）。
- 同一任务、同一连接器、同一操作、同一目标只算一个业务动作（`business_action_id`）；成功过一次，再提就是 `action_already_executed`。
- `kind="event"` 的操作要部署显式列进 `enabled_event_operations`，否则 `event_operation_not_supported`（`policies.py:252-263`）。

### 6. 审批记录

- `decide_approval` 记的事件一律是 `actor_type="user"`，没有"批准来源"字段。
- L3 要 2 次批准，且默认要两个不同的人（`l3_distinct_principals=True`）。

## 二、6 条裁决

### 裁决 1：事实核对的结论

- **裁决：** 第九节"操作链已完整存在、只差档案"的判断**不成立**。除了档案，还差三样：申请单的锚点（见阻断 A1）、通用的"没生效证明"（A2）、L0/L1 的系统准备（A3）。
- **理由：** 现在的意图合同按"内容步骤产出文件 → 把它发出去"设计，参数、锚点、证明都围着那份文件。
- **对 AgentOS：** NAS 删除/移动没有任何内容产物，按现状连申请单都建不出来。MCP 写入如果内容由模型生成，能套现有形状。
- **对 AIPhone：** 拍照没有内容产物，而且是 L1；发消息若文字在建任务时写好，也没有内容产物。两者按现状都走不通。

### 裁决 2：参数从哪来——选"甲"，但改三处（记为"甲′"）

- **裁决：**
  1. **参数放进要求本身。** 在 `Criterion` 上加一个结构化字段（例如 `action_params`），只允许出现在 `action:` 要求上，进要求版本的内容哈希。不另开 `create_mission(actions=[...])` 旁表。
  2. **产物引用只做引用，不内联内容。** `{"$artifact": "路径"}` 由系统绑定成 `{artifact_path, content_hash, size, storage_uri}`，和发布现在绑定的四个字段一致。连接器按 `storage_uri` 读字节，自己核哈希。
  3. **发布也走同一个解析器。** 发布的参数就是隐含的 `{"artifact_path": {"$artifact": <目标>}}`；现有 `_sources` 的找法改成 `$artifact` 的解析器，供两类操作共用。系统准备申请单只剩一条路。
- **理由：** 参数只有一个来源，改要求（`amend_requirements`）就是改参数，确认页确认的规格哈希就盖住了参数；自动审批批的就是这份。乙让模型写参数文件，等于把 09-29 因"模型写申请单反复出错、耗光 12 次尝试"而换掉的那条路又开回来，并且和发布形成两条路径。
- **对 AgentOS：** 主 Agent 建任务时写 `action:nas.move:/photos/a.jpg` 加 `{"to": "/archive/a.jpg"}`。MCP 写入的正文由内容步骤产出，参数写 `{"body": {"$artifact": "notes/x.md"}}`。
- **对 AIPhone：** 拍照写 `action:camera.capture:<槽位名>` 加 `{"resolution": "..."}`；发消息写目标与固定文字。要发模型生成的文字，用 `$artifact` 引用一份内容产物。

参数校验：建任务时只查"必填键齐全、是规范 JSON"。`OperationSpec` 加的参数 schema 只作说明（给主 Agent 和审批卡看），SDK 不引入 JSON Schema 校验库。更细的错误由连接器在 `execute` 里抛 `ConnectorRejected`（确定没执行）。

### 裁决 3：auto 模式自动审批

- **裁决：** 按用户决定做。做法改两处、加一条约束：
  1. **自动审批是一种审批来源，不是假装人点。** 审批请求照常建；自动的那次决定记 `approval_source=HOST_AUTO_PERMISSION`，事件里的执行者标成主机，不标 `user`。走 `DeploymentDuties` 一处（与"自动授权规划""自动确认纯内容要求"同一个地方），不在 Host 里另写一条。
  2. **一次自动决定直接关单，不伪造第二个人。** L3 要两个不同的人，系统拿同一个主体点两次会被 `distinct_principals` 拒；改主体名去凑就是伪造事实。规则写成："来源为 HOST_AUTO_PERMISSION 的决定，一次就让请求成为 GRANTED"，并把这条记进请求。
  3. **宿主收到连接器时，`max_action_level` 必须显式给，不给默认值。** `OrchestrationHost` 默认 `auto_mode=True`；不显式封顶，消费方注册一个 L3 连接器就会在零人参与下执行删除。这不改用户的决定，只是让消费方自己写下封顶。
- **理由：** 记录要如实（谁批的）；伪造多人批准会让审计失真；封顶是秩序，不是语义判断。
- **两个授权事实源的问题：** 不构成两个。SDK 的审批回答"用户同不同意这件事发生"（auto 下由主机按用户的模式代答），连接器回答"按应用规则这个身份能不能做"（只答能或不能）。前提有两条，必须写进接入说明：
  - 连接器不在 `execute` 里"等人"。要等就会超时，变成"不确定"。
  - 应用不为同一动作另弹确认框。
  - 由此推出：交接文件里"应用可以让动作进持久人工等待"，在 auto 模式下**做不到**。manual 模式下就是 SDK 的审批卡。回执里照实写。
- **风险（不阻断，需写进文档；要不要再收紧由用户定）：**
  - auto 下从建任务到外部生效没有任何人。剩下的闸门只有：部署封顶、每任务交接上限（默认 8 次）、预算、审阅员（LLM）、连接器自己的授权。
  - "批的是用户写下的那份"，严格说是"主 Agent 整理用户对话后写下的那份"。
  - 读工具读回来的外部内容（NAS 文件、MCP 返回）可能带注入指令，经 `$artifact` 进到发消息、写入这类操作里，零人参与地发出去。缓解靠封顶和连接器侧的白名单（收件人、目录）。
  - 可选的收紧办法（建议问用户一次）：连接器按操作静态声明"这个操作总要人批"，auto 模式也不代批。这属于"应用授权在连接器里判"，不是第二个事实源。
- **对 AgentOS：** NAS 删除若定为 L3，auto 下会直接执行。建议 AgentOS 把 `max_action_level` 定在 L2，删除走回收站语义（L2）。
- **对 AIPhone：** 拍照 L1 本来就不要人批；发消息 L2 在 auto 下自动批。收件人白名单放在连接器里判。

确认页代签另需两条：

- `operation_completion.py:182` 的硬拒删掉，`duties.py` 里"带 action: 的跳过"改成按档案默认映射代签。两处只留 duties 一条路径。
- 效果要挂到唯一的义务上。确认页上不止一个未满足义务时，不猜；任务停在确认页，并写一条事件说明"自动确认需要人：有 N 个义务"。

### 裁决 4：通用档案的最小形状

- **裁决：**
  - **里程碑只要一个"已生效"（例如 `APPLIED`）就够。** 判据是纯函数，不做 I/O：回执 `applied=True`；回执的连接器、操作、目标、参数哈希、幂等键与动作行一致（沿用 `receipt_mismatch` 的 5 项，不只第九节写的 2 项）；交接事件全覆盖（照发布解读器的写法）。不在解读时再调 `lookup`：解读跑在事件循环上，而通用连接器的 `lookup` 可能是网络调用。
  - **证据策略 = 连接器回执。** 一份通用的证据策略文档、一份通用的里程碑策略文档，全部通用连接器共用；连接器身份由档案哈希单独钉住。"已生效"只表示"连接器说执行了"。任务是否真满足，由结果审阅员（LLM）读回执的 `before/after` 判断。
  - **档案身份取连接器的声明，不取源文件。** 发布档案用 `inspect.getsourcefile` 算源码摘要；对消费方的连接器不适用（闭包、编译包、源码一改在途任务全失效）。改成：连接器名 + 类的限定名 + 每个操作的声明（等级、必填参数、参数 schema、说明、`kind`、`mutates`）+ `supports_*` + `lookup_authority` 的规范 JSON 摘要。声明变了，在途任务按任务报"档案已变"，不拖垮宿主（与第 1 片裁决 3 同一要求，同样先用测试钉实）。
  - **对账：** `lookup` 返回回执 → 按回执结案（过同一道 `receipt_mismatch`）。`lookup` 返回空，且连接器是 authoritative **并且声明了"查询即封口"** → 给新的证明类型（例如 `CONNECTOR_LOOKUP_FENCED`）。其余情况不给证明，留给人裁定。见阻断 A2。
  - **非权威连接器（best_effort）：** 只许 L1（现有规则：L2+ 必须权威）。它的"不确定"永远等人裁定；**auto 模式也不自动裁定**——系统不知道的事不能替人编。
- **理由：** 最小形状只表达秩序上能证明的事实；"做得好不好"交给审阅员。
- **对 AgentOS：** NAS 若能按幂等键记账并封口，就能自动对账；MCP 远端多半做不到权威，只能 L1，"不确定"要人看。
- **对 AIPhone：** 设备守护进程在本机维护一份按键记账的台账，就能做到权威加封口；做不到时，拍照的"不确定"要人看。

### 裁决 5：异步连接器

- **裁决：**
  1. **把第 1 片的"取消→宽限→交后台继续等"抽成一个共用函数**，领域工具执行器和动作执行器都用它，只是结局映射不同。不另写第二套。
  2. 动作执行器对 `async def` 的 `execute`：在事件循环上跑；**超时就取消内层任务**（结果已记"不确定"），给宽限期；不退出就交后台继续等。**动作键一直留在 `_inflight` 里，直到协程真正结束**，这期间不对账。现在的 `wait_for(shield(...))` 对协程不能照搬：挂住的协程永远不结束，`_inflight` 永远不清，对账永远不跑。
  3. 外层被取消（宿主关闭、任务取消）：同样先取消内层，不记结局；动作停在 HANDED_OFF，租约过期后由对账接手（与线程版现在的行为一致）。
  4. `lookup` 同样支持 `async def`，走同一个函数。对账适配器做成纯函数：执行器先做 `lookup` 这次 I/O，再把结果交给适配器。现在 `adapter.observe` 是丢进线程跑的，线程里等不了协程。
  5. 同步/异步在注册时判（`inspect.iscoroutinefunction`，含 `__call__`）。运行时若同步函数返回了协程：关掉它，记"不确定"。
  6. 执行根检查（`_require_execution_root`）在创建协程之前、同一事件循环上做，不留间隙。
- **理由：** 第 1 片的教训是"被取消时只等不取消，协程挂住就关不掉宿主"。动作和工具的区别只在结局：动作超时一律"不确定"，从不"失败"。
- **对 AgentOS：** async 的 NAS/MCP 客户端可以直接写，不用自己桥接。接入说明要警告：`async def` 里做阻塞 I/O 会卡住整个宿主，包括 30 秒租约续期。
- **对 AIPhone：** 设备 socket 若是同步的，照旧在线程里跑。socket 必须设超时，否则线程停不下来，`_inflight` 一直占着，这个动作就一直不对账。

### 裁决 6：本片可以砍掉的范围

见第四节。要点：连接器上的只读操作、乙方案、JSON Schema 校验、内联内容、条件写入、给 Worker 展示通用操作的申请单合同，都不做。

## 三、阻断级设计改正（开工前必须改进方案）

### A1. 申请单的锚点：没有内容产物的操作建不出申请单

- **问题：** 意图、冻结提案、请求哈希都要一个已接受的候选产物，还要同一义务下的生产步骤接受记录（事实 4）。NAS 删除/移动、拍照、发固定文字的消息都没有内容产物。按第九节的做法，系统根本准备不出申请单。
- **改法：** 意图合同出新版本（开发期直接替换旧版，不留双版本）：
  - 锚点改成"拥有这个效果的计划步骤的当前接受记录"。`_leaves` 本来就要求全部步骤都已接受，这个锚点总是存在。
  - `candidate_artifact_ref` 变成可选，只在参数里有 `$artifact` 时出现，指向被引用的那些产物。
  - 申请单 JSON 由系统从要求里冻结的参数生成，计入请求哈希。
  - 发布同样按这个形状走（它的 `$artifact` 就是要发的文件）。
- **先钉实再动手：** 先写一条测试，只有一条 `action:fake.op:x` 加固定参数，对着假连接器跑，记下链路在哪一步拒。这和第 1 片裁决 3"先测再写文档"是同一要求。

### A2. 通用"没生效证明"必须带封口语义，否则会重复执行

- **问题：** 证明成立后，同内容开的是**新版本、新幂等键**（事实 5）。远端连接器（NAS、手机守护进程）上，原请求可能还在网络里，查询说"没有"之后才落地。新键不会被它去重，同一件事就发生两次。发布不怕这个，因为它在进程内、在台账锁下判断，进程死了请求就没了。
- **改法：**
  - 新证明类型的条件写死："authoritative，且查询某个键返回空之后，这个键以后再来的执行一律拒绝（封口）"。连接器必须显式声明这项能力。
  - 没声明封口的权威连接器：查询为空只允许**同键重交**（服务端会去重，安全），不给证明，不开新版本。
  - 例子 `tools_effect.py` 加一个"响应丢失，查询为空，原请求随后落地"的场景，验证不重复。

### A3. L0/L1 操作没有系统准备的路

- **问题：** `operation_materialization_inputs.py:270` 与 `system_operations._needs_approval` 只代办要人批的操作。拍照（L1）这类操作在产品里没有路。
- **改法：** 参数由用户在建任务时冻结后，"系统代办"不再替模型做选择，这条限制失去原来的理由，删掉。L0/L1 照现有等级规则，不要人批，系统准备后直接执行。L0 见第四节（不收）。

### A4. 自动审批必须如实记录，L3 不能伪造第二个人

见裁决 3 第 1、2 条。现在 `decide_approval` 没有来源字段，事件一律标 `user`；直接"代点"会把主机的决定记成人点，与 `HOST_AUTO_PERMISSION` 的既有约定冲突。

### A5. 参数只能有一个来源

见裁决 2 第 1 条。参数放在建任务的旁表里，`amend_requirements` 改不到它，确认页的规格哈希也盖不住它。结果是批准的是一份、执行的可能是另一份。

### A6. 里程碑与档案登记必须按操作分

- **问题：** 确认页的里程碑是全局一张表（事实 1 最后一行）；`facade._require_effects_supported` 与 `policy_for` 假定只有一个档案。装了发布和一个通用连接器后，页面或代签可能把通用效果挂到发布的里程碑上，到物化时才被拒。
- **改法：** 一个组合登记处，按（连接器，操作）分发：发布走发布档案，其余走通用档案。确认页的 `milestones` 改成按操作给（桌面端 `OperationWorkspace.tsx` 的默认映射同步改：按效果所属操作取它的默认里程碑，不再按"标签含'哈希'"去挑）。结果接收（`operation_outcomes.py:662`）改成"里程碑属于该操作登记的档案"。

### 实现级必须项（不改方案，但漏了会出错）

1. **回执要过规范 JSON 校验**（第 1 片 M1 的同类问题）。连接器返回的 `Receipt.before/after` 过不了 `canonical_json`、或超过大小上限时，事情多半已经发生，记"不确定"，不记"失败"。
2. **异常文字不原样入库。** 现在 `hand_off` 把 `str(ConnectorRejected)` 与 `f"{type}: {error}"` 写进动作行、事件和卡片。改成：拒绝原因保留（对人和规划器有用），但截断并过密钥扫描；其他异常只记类型名。
3. **事件型操作。** 拍照、发消息每次都产生新事实，是 `kind="event"`。宿主按连接器声明把它们列进 `enabled_event_operations`（这是声明到配置的确定映射）；事件型操作仍须幂等、权威（现有规则）。接入说明写明：同一任务里同一操作、同一目标只会成功一次，要发两条就给两个目标（槽位名）。
4. **公开连接器模块前，把 `TestConfigService`、`PaymentConnectorStub` 移出** `runtime/connectors.py`，放进测试包。否则测试替身会进公开合同。

## 四、建议砍掉的范围

| 砍掉 | 理由 |
|---|---|
| 连接器上的只读操作（`mutates=False` / L0） | 读走只读工具（第 1 片），同一件事只留一条路。宿主注册时拒。 |
| 乙方案（模型写参数文件） | 见裁决 2。 |
| 通用操作给 Worker 展示申请单合同 | 系统准备申请单，Worker 不写。 |
| 人提交模型写的申请单（`USER_COMMAND`）用于通用操作 | 只留系统准备一条路。发布现有的人提交入口是否一并删，另开一单问用户。 |
| SDK 内的 JSON Schema 校验 | 只查必填键与规范 JSON；schema 只作说明；细的错误由连接器拒。 |
| `$artifact` 内联内容 | 只绑引用。审批卡会展示参数，内联会把大段内容与可能的密钥带进卡片和事件。 |
| 条件写入（ETAG 等） | 只支持 `ConditionalWriteKind.NONE`。 |
| 没有幂等或没有查询能力的连接器 | 宿主注册时拒（任何等级）。best_effort 只许 L1。 |
| 独立回读外部状态的里程碑（AppWorld 那种状态观察器） | 本片只做"已生效"；状态核对交给结果审阅员读回执。 |
| 连接器内部的"等人批准" | 不支持；要人就用 SDK 审批卡（manual）。 |

## 五、实施顺序建议

每一步只跑改到文件对应的测试，不跑全量回归。

1. **先钉事实（只写测试，不改实现）：**
   - (a) 只有一条带固定参数的 `action:` 要求的任务，对着假连接器，记下在哪一步拒（A1）；
   - (b) 远端假连接器"查询为空后原请求落地"，记下现在会不会重复执行（A2）。
2. **合同：** `Criterion` 的参数字段，建任务与改要求时校验；`OperationSpec` 加说明与参数 schema；连接器协议（含 async、封口声明、事件型）公开；测试替身移出公开模块。
3. **组合登记处与通用档案：** 声明摘要、"已生效"纯解读器、通用对账适配器与封口证明、结果接收与确认页按操作分（含桌面端页面）。
4. **意图新版本与系统准备：** 新锚点、`$artifact` 解析器（发布共用）、去掉 L0/L1 限制、按参数生成申请单 JSON。旧版本删掉。
5. **执行：** 共用的取消/等待函数；`execute`、`lookup` 的 async 支持；回执校验；异常文字处理。
6. **auto：** duties 代签确认页（唯一义务，否则停下并说明）；自动审批作为一种审批来源，一次关单；`max_action_level` 必填。
7. **宿主入口与交付：** `OrchestrationHost(connectors=[...], max_action_level=...)`，拒名字冲突、拒只读操作、拒无查询能力；事件型映射；例子 `tools_effect.py`（加 A2 场景）；接入说明（manual 与 auto 各自谁点什么；"持久人工等待"在 auto 下不可用；注入风险与封顶建议）。
8. 独立核验只看阻断级，然后发版。
