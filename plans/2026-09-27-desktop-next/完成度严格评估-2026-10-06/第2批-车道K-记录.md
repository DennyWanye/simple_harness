## 二、每条做了什么

### H11（架构 C8，原计划 §18.2 Global Budget、§28 "多 Mission 配额"）

现状：SDK 的全局账户（`commit_service.py` 的 `GLOBAL_ACCOUNT`，每个任务账户挂在它下面、子不超父）一直在，Host 构造 `OrchestratorConfig` 不传 `global_budget`，这一层从没开过。

做法：

1. `backend/deskpet/orchestration/settings.py`：新增 `global_max_tokens`，默认 20 亿（= 100 个默认上限 2000 万的任务；单步 300 万不变，2026-09-26 用户决定）。读配置时下限是单任务默认上限（再小默认任务一个都建不了），上限 10¹²，坏值回默认。
2. `backend/deskpet/orchestration/service.py`：`_open` 把 `Budget(max_tokens=global_max_tokens)` 传给 SDK；`status()` 新增 `global_budget`（上限 / 是否已打开 / 已预留 / 已结清 / 剩余，读 SDK 账本的全局账户）。
3. 超配额走 SDK 现有路径，没加 Host 规则：任务预算大于全局上限 → SDK `BudgetError`（§18.2 原话）→ 门面 `invalid_request` → Host 如实报；全局池耗尽 → 新任务第一轮规划以 `budget_exhausted（scope=global）`具名停下，在跑的同样停下。
4. 设置页说明：`tauri-app/src/components/SettingsPanel.tsx` 新增「任务全局预算」只读段（`GlobalBudgetSection`，`formatTokens` 按万/亿显示），讲清累计不归零、用完怎么办（改 `config.toml [orchestration] global_max_tokens` 重启）；`stores/missionsStore.ts` 的 `OrchestrationStatus` 加字段。

关于"多任务配额"的读法：§28 第三阶段的"多 Mission 配额"在 SDK 里就是全局账户这一层（所有任务共用一个池、每个任务不超过它）；并发名额已有 `max_concurrency`。`Budget.max_concurrency` 在全局层没有任何读者，所以只接 token 一维，不假装接了别的。

注意：SDK 全局账户是**累计**的（已预留 + 已结清一直加，不随任务结束归零），所以这个默认值是"这台机器一生的总额"。用户若觉得不该是累计语义，要改 SDK 账本，不在本车道。`global_budget` 在政策漂移白名单里（`governance/policies.py`）：已有的开发库会记一条 `PolicyConfigDrift`，账户照开。

改的文件：`settings.py`、`service.py`、`SettingsPanel.tsx`、`missionsStore.ts`。测试：`backend/tests/orchestration/test_global_budget_setting.py`（3 条）、`tauri-app/src/components/SettingsPanel.globalBudget.test.tsx`（3 条）。既有相关测试：`test_mission_budget_default.py` 14 条绿；`SettingsPanel.*.test.tsx` 8 文件 28 条绿；`tsc` 通过。

改坏：`service.py` 不传 `global_budget` → 3 条里 2 条红（账户不开、超配额不被拒）；恢复后 3 条绿。

### U04（保证 C-20 后半，原计划 §7.3 "Host 按 event_id 去重、重连从 seq 补读"）

现状：Host 只在启动 / 重建运行时整表补读一次（`backfill`），运行中掉的推送要等下次重启；前端通道断了再连也不重新拉通知列表（上一个没应答的请求号还占着，重连后永远不再拉）。

做法：

1. `backend/deskpet/orchestration/notices.py`：记住已读到的事件序号 `last_seq`，随通知记录落盘（文件版本 2）；`backfill` 改成 `catch_up(store)`，只读 `type=AssuranceStatusNotified AND seq > last_seq` 的事件，读到表尾就记下表尾序号；没动静不写盘。文件丢了 → `last_seq` 回 0 → 整表补读（原保证不变）；按 `event_id` 去重不变。
2. `backend/deskpet/orchestration/service.py`：启动、重建运行时都改调 `catch_up`；`pending_notices()`（前端拉列表、主 Agent 读上下文都走它）应答前先 `catch_up` 一次——前端重连后重新拉，Host 就从已读序号把断线期间丢的推送补回来。
3. `tauri-app/src/views/ChatMissionNotices.tsx`：订阅通道状态，断开再连上就作废旧请求号、重新拉一次。

Host 侧的"断线"在产品里是运行时关闭/重建或推送回调没送到；SDK→Host 是进程内回调，没有网络序号，所以"续读序号"用的是 SDK 事件表的 `seq`（§7.3 的原意）。

改的文件：`notices.py`、`service.py`、`ChatMissionNotices.tsx`；既有测试 `test_mission_notices.py` 的替身加了 `catch_up`，说明文字里 `backfill` 改成 `catch_up`。新测试：`backend/tests/orchestration/test_notice_seq_resume.py`（3 条）、`ChatMissionNotices.test.tsx` 加 1 条（文件共 5 条绿）。既有 `test_mission_notices.py` 2 条绿；`tsc` 通过。

改坏：Host——`_save` 不写 `last_seq` → 第一条红（重启后从文件读不回序号）；前端——删掉状态订阅 → 新用例红。都已恢复。

### A27（保证 B-2 / F05，原计划 §6.2 "原 Provider UNKNOWN → 原 intent 由 runtime 核对 → 不能靠 ordinal2 重复请求"）

现状：交接后结果不明的服务回合（规划器、保证通道审阅）等满 `_service_blocker_limit` 就放弃，下一轮用新序号 / 新会话再问；放弃前不看同一调用键有没有后来的结果，也不记新一轮替代了哪次调用。SDK 自己的同一 invocation 再交接（`dispatch.py`）早就只认 `confirmed_not_started`，但编排层"开新一轮"绕过了它。

做法：

1. `runtime/provider_budget_guard.py` 新增 `check_unknown_handoff(store, uow, intent_id)`：按意图找它最后一次授权（`provider_token_grants` 的 invocation_id + handoff_ordinal），重读 SDK 同一调用的记录与对账结论，给出类型化结论 `HandoffOutcomeCheck`：
   - `result_known`：记录已 succeeded / failed，或对账 completed；
   - `confirmed_not_started`：对账确认未发出；
   - `refused_on_wire`：记录 unknown 但带 `http_status`（服务端收到并以状态码拒绝，没产出回答）；
   - `unresolved`：unknown 且没有服务端回话、仍 handed_off、或读不到运行时；
   - `no_handoff`：这条意图没交接过（或 SDK 从未 claimed）。
   另加 `resend_record(check, ordinal)`：`{replaces_ordinal, replaces_invocation_id, replaces_handoff_ordinal, ground}`，ground 按结论映射（`nothing_sent` / `result_known_import_pending` / `confirmed_not_started` / `provider_refused_on_wire` / `outcome_unconfirmed`）。只读，不动授权状态（仍由 `observe` / `recover` 结算）。按类型码与数值字段判，不看异常文字。
2. `orchestrator/event_handler.py` 交接那一段（`_resolve_provider_blocked_service` 规划分支、`_end_overdue_review_call` 的 blocked 形状）：时限到了先核对。`result_known` → 不放弃不重问，交回普通收集，只多给一个时限窗（回合永远不醒也能收口）；其余 → 走原门，但 `PlanningRejected` 的 detail / 审阅放弃记录里写 `handoff_check`（核对结果）与 `resend`（替代了哪个序号、哪次调用、依据）。新增 `_unknown_handoff_check(intent)`（从 `bridge_for(intent).runtime.uow` 读；池没了就 unresolved）。
3. 部署清单重生成（源码变了）。

改的文件：`provider_budget_guard.py`、`event_handler.py`、`taskgraph_deployment_manifest.json`（重生成）。新测试：`tests/orchestrator/full_target/test_a27_handoff_recheck.py`（11 条：7 条参数化纯函数、1 条无交接、418 世界用例、传输断世界用例、"结果已知只收集不重问"）。既有相关测试：`test_service_intent_provider_blocker.py` 6 条、`test_assured_planner_unknown_bounded.py` 4 条、`test_after_handoff_unknown_bounded.py` 2 条，全绿（它们的行为没变，只是记录多了字段）。`ruff` 新增报错为零（`event_handler.py` 原有 21 条、守卫文件原有 6 条行长，未动）。

改坏：`check_unknown_handoff` 不重读调用记录（一律 unresolved）→ 纯函数 7 条 + 418 世界用例共 8 条红；恢复、重生成清单后 11 条绿。

## 三、偏差单（请主会话 / 用户裁决）

**A27-偏差 1：真正不明（没有服务端回话）的调用，是否仍允许新序号再问。**

- 计划原话（§6.2 / 车道说明）："只有确认未发出才重发"。严格执行 = `unresolved` 时不开新一轮，任务以 `runtime_unavailable` 具名停下。
- 没有严格执行，现行仍按阶段 B 裁决第 6 类走原门（新一轮 / 新会话），只是记录如实写 `ground: outcome_unconfirmed`。原因三条：
  1. 用户 2026-09-28 决定"服务端报错 / 重启打断不计入规划次数上限、原地重试"——重启打断正是结果不明的典型情形，严格执行与它直接冲突（B-2 认为该决定只讲计次，用户没有定过"结果不明不许重问"）。
  2. 产品上 DeepSeek 调用没有对账端口（`planning_selection.py` 原注释"a DeepSeek call never becomes reconcilable"），`confirmed_not_started` 永远不会出现：严格执行等于每次网络断流都终止任务。
  3. 模型调用重问没有外部副作用，代价只是可能的重复计费，而被放弃的那次已按上限计入预留（多算不少算）。
- 若用户要严格：切换点只有一处——`event_handler.py` `_resolve_provider_blocked_service` 规划分支，`check.verdict == "unresolved"` 时改调 `_fail_runtime_unavailable(mission, reason="provider_outcome_unknown", detail=…)`；审阅分支同理把 `abandon_assurance_review` 换成具名停止。随之 `test_service_intent_provider_blocker.py` 第 3、4、5 条（审阅 transport_loss 后重开）与 `test_after_handoff_unknown_bounded.py` 第 1 条要改口径。

**H11-说明：** 全局账户是累计语义（SDK 账本不归零）。默认 20 亿是按"一生总额"给的；如用户要"同时在跑合计"或"按日/按月"的配额，需要 SDK 账本加周期或改语义，不在本车道。
