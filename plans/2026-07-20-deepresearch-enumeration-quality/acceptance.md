# 验收标准：DeepResearch 显式数量完整性与业务终态

## 范围

- 包含：识别“前十 / Top N / 列出 N 个”等显式枚举数量；让主 Agent 的拆题、子代理验收、最终综合都保留该交付约束；数量或逐项引用不足时诚实降级；在进度卡上区分工作流完成与报告业务结果。
- 包含：新增 immutable `deep_research/v8`，保持 v7 的六节点简单图、2–6 个子方向、每个子代理最多 2 次尝试、统一综合、`DeepResearch/` 落盘与原有文件操作不变；新调研默认走 v8。
- 明确不包含：恢复 v5/v6 的复杂研究 brief/循环策略；改造搜索供应商；改变 Agent Harness；为某个固定榜单硬编码模型名称或排名。

## 功能验收条款

| ID | 功能点 | 验收条件（可验证） | 优先级 |
|---|---|---|---|
| AC-1 | 显式数量识别 | 对“前十个”“Top 10”“列出 5 个”等自然表达得到 2–50 的 `requested_count`；年份、版本号等普通数字不被误判。 | 必须 |
| AC-2 | 拆题保约束 | 存在 `requested_count` 时，2–6 个子方向中至少一个明确要求逐项列出该数量的不同对象、逐项给出请求字段并附引用。 | 必须 |
| AC-3 | 子代理质量门 | 承担枚举清单的子代理只有在报告中出现不少于 N 个不同命名项且每项带有效脚注引用时才为 `valid`；否则主 Agent 诊断后进行第 2 次有界补救，最终仍不足则标为 `insufficient`。 | 必须 |
| AC-4 | 最终综合质量门 | 最终报告对显式 N 请求必须提供不少于 N 个不同命名项并逐项引用；首次综合不满足时只允许一次基于已有子报告和引用的修复，不得编造来源。 | 必须 |
| AC-5 | 诚实业务终态 | 枚举数量/逐项引用不足或任一子方向证据不足时，工作流引擎仍可正常完成，但业务结果为 `partial`；无可用报告证据时为 `insufficient_evidence`；仅全部门槛满足时为 `completed`。 | 必须 |
| AC-6 | UI 明示 partial | v8 进度卡在引擎“已完成”之外显示“报告完整 / 报告部分完成 / 证据不足”；屏幕阅读文本也同时包含流程终态与业务终态。 | 必须 |
| AC-7 | 文件与交付兼容 | `completed` 和有可用内容的 `partial` 继续保存到既有 `DeepResearch/` 目录并生成报告卡、另存为/打开等文件操作；`insufficient_evidence` 不伪装成可用报告产物。 | 必须 |
| AC-8 | 版本兼容与幂等 | v1–v7 定义、checkpoint 与投影行为不变；v8 final/children 乱序重放后业务终态和最新子方向快照均保持正确。 | 必须 |

## 非功能 / 边界

- 错误态：解析或修复失败不得令已获得的证据丢失；降级原因写入 coverage/errors，并在 UI 以业务终态呈现。
- 幂等：同一 final 事件重放不重复创建卡片或改变业务终态。
- 性能：普通非枚举调研不增加 LLM 调用；枚举报告仅在首次综合未过门时最多增加 1 次修复调用。
- 兼容：v7 保持 immutable；显式数量仅支持 2–50；超出范围或语义不明确时按普通调研处理，避免把年份/版本号当作清单数量。
- 安全：完整性审计只认可已有 Markdown 项及合法脚注，不以模型自报“已列出 N 项”作为通过依据。

- `ARCHITECTURE/DeepResearch.md` 与 `ARCHITECTURE/PROJECT_STATUS.md` 同步当前生产事实与验证证据。
- dirty worktree 中 Agent Harness 及其他无关改动不被覆盖或混入。
