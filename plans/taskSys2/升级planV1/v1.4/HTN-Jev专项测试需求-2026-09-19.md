# simpleHarness：HTN + Jev 专项测试需求

版本：1.0  
日期：2026-09-19  
用途：交给开发／测试 Agent，在当前工作分支执行局部验收。  
测试终点：**HTN 的局部分解结果，以及 Jev 的决策／影子观测结果。到这里就停止，不继续执行任务。**

> 本次只回答三个问题：HTN 能否正确处理当前的分解输入；Jev 能否接收真实决策输入并返回可用结果；开启 Shadow 后，是否确实没有改变正式行为。不是 simpleHarness 整体验收，也不是后续 TaskGraph 的交付门槛。

### 1.1 已核对的部分与待映射的部分

- 不要求切换到上述提交，更不能覆盖你当前尚未提交的实现。最终测试报告记录实际工作分支和 SHA。

### 2.3 测试隔离方式

工程用例使用：真实 HTN 代码、真实 Jev 适配与模式控制代码、可控的模型返回值。

可替代的是外部模型推理和下游执行；不可替代的是被测的分解、请求映射、结果校验、Shadow 分支与回退代码。

```text

        ↓
真实 HTN 局部入口
        ↓
```

## 3. 共用测试材料

### 3.1 一个主要业务输入

下面这段可用于真实 Planner 的局部冒烟，也可作为固定夹具的目标文本：

```text
请为“分析一个本地 Python HTTP 重试模块的问题”制定分层任务计划。

已知：本地已有源码片段和一次测试失败日志。
目标：定位可能原因，提出最小修复建议，并说明建议如何验证。
限制：本轮只生成计划；不联网、不执行命令、不修改文件、不部署。

请保留原目标和限制，把需要继续分析的复合任务与可直接处理的叶任务区分开。
信息不足时明确指出缺少什么，不要假装问题已经修好。
```

固定夹具只需要一个小型已注册方法集，例如：

```text
分析重试问题（compound）
├─ 收集已有证据（compound）
│  ├─ 阅读给定源码片段（primitive）
│  └─ 阅读给定失败日志（primitive）
└─ 形成分析建议（compound）
   ├─ 对照证据定位原因（primitive）
   └─ 给出最小修复与验证建议（primitive）
```

这只是测试材料，不是生产规划必须照抄的树。不要断言真实 LLM 必须输出完全相同的任务名称、任务数量或 JSON 字节。

### 3.2 两组局部决策材料

只使用当前代码已经接入的类型。以下是参考材料，不是要求新增接口。

**材料 A：候选优先级。** 提供三个已经被现有代码认定合法的候选：

| 候选 ID | 内容 |
|---|---|
| `candidate-a` | 补充问题的最小复现信息 |
| `candidate-b` | 整理现有日志中的错误证据 |
| `candidate-c` | 改善报告的展示格式 |

**材料 B：继续尝试或交回规划。** 提供归一化错误、已经尝试的次数、是否发生输入变化，以及当前已允许的候选动作。只测试这次选择，不真正启动下一次 Attempt。

若 Jev 当前接的是方法候选排序，而不是以上两类，使用实际方法候选替换这些材料；不要额外实现 Ready Queue 或重试链路来满足本文件。

### 3.3 可控 Jev 返回值

至少准备以下返回行为，复用同一个轻量测试替身即可：

| 行为 | 具体设置 |
|---|---|
| 与正式路径一致 | 正式选 A，Jev 也选 A |
| 与正式路径分歧 | 正式选 A，Jev 选 B；分布可以设为 A=0.05、B=0.90、C=0.05 |
| 不明确 | A=0.49、B=0.48、C=0.03 |
| 非法结果 | 不存在的候选 ID，或非法分布 |
| 推理错误 | 抛出当前适配层能够收到的异常 |
| 延迟返回 | 用 Event／Barrier 控制返回时机，不靠随机 sleep |

以上概率是**测试注入值**，不是 NanoJev 的实测能力或可信度。

## 4. 核心工程用例

建议分成 **9 个核心用例**。相近的错误输入用参数化子例覆盖，不扩展成数十份重复测试。

### T01：HTN 正常分解与叶任务停止

**目的**：确认已有方法可以正常细化，同时不会把已满足叶条件的任务继续无意义拆分。

**操作步骤**：

1. 用现有 constructor／fixture 建立第 3.1 节的小型任务类型、方法和必要事实；关闭 Jev。
2. 调用真实 HTN 局部入口，对根 compound 执行一轮细化。
3. 捕获返回的子任务／方法实例／待细化项，不提交后续执行。
4. 对仍为 compound 的子项再细化一轮；已经是可处理叶的项单独调用停止判定。
5. 用相同材料的新状态再执行一次，确认测试自身可重复。

**通过条件**：

- 合法复合任务能返回当前实现对应的细化结果；已有 SDK 中可对应 `REFINED`。[S1]
- 必要目标、参数和输出要求没有在细化中丢失。
- 已满足条件的叶不继续产生一串重复子任务；已有 SDK 中可对应 `LEAF`。
- 不出现“任务已经修复／业务已经完成”的伪造结果。
- Jev、Worker、后续业务执行的调用次数均为 0。

**不检查**：完整图结构、精确任务 ID、并行调度、最后是否修好真实代码。

### T02：不满足前提、未知前提和非法输入

**目的**：确认模型建议不能把不合法或信息不足的输入变成可用细化。

在 T01 的材料上分别改变一项，每个子例重建独立状态：

| 子例 | 改动 | 预期检查 |
|---|---|---|
| A | 必需参数缺失或类型错误 | 在当前对应的参数／grounding／准入边界明确拒绝，不默默补造参数 |
| B | 唯一方法的必需前提为 FALSE | 不把该方法作为成功细化结果采用 |
| C | 必需前提为 UNKNOWN，且有合法取证方式 | 返回需补证据／取证请求，不把 UNKNOWN 当 TRUE |
| D | 没有任何适用方法 | 返回无适用方法或既有方法合成请求，不制造一个“已经注册”的方法 |

**执行细节**：记录输入差异、结果类别和拒绝／缺失原因即可。C、D 在提出取证或合成请求后立即停止，不实际启动取证 Agent 或完整合成闭环。

如果当前 Jev 会对候选打分，另外注入“高分选中已排除候选”的返回：该返回不得绕过当前硬检查获得采用。

**注意**：不同入口可能先返回 `ContractError`，也可能返回结构化结果。按实际契约断言，不为了统一错误名称修改生产代码。

### T03：递归有界，重复展开不算进展

**目的**：只测 HTN 当前已有的局部终止保护，不测试整个 Mission 的预算机制。

**操作步骤**：

1. 创建同一个 Obligation，递归 fuel 设为 2。
2. 执行两次不同的合法展开；再请求第三次展开。
3. 在另一个新夹具中，执行一次展开后，重复提交相同 Obligation、方法、参数和世界快照。
4. 在已经消耗燃料的夹具中改变方法或参数，再读取剩余额度。

**通过条件**：

- 燃料用尽后停止继续展开，返回 `BOUND_REACHED` 或当前等价边界结果，不宣称世界中问题必然无解。
- 相同展开被拒绝或合并，不重复产出同一批子项、不额外扣燃料。
- 换方法或参数不重置同一 Obligation 的燃料。
- 不需要等待 Worker 或图调度器启动。

当前 SDK 已有直接对应的局部测试，可优先复用，不必再写一套：[S4]

```bash
python -m pytest -q \
  tests/orchestrator/full_target/test_htn_recursion_fuel.py::test_exhausted_fuel_reports_bound_reached_never_unsolvable \
  tests/orchestrator/full_target/test_htn_recursion_fuel.py::test_the_same_unchanged_expansion_is_refused_without_burning_fuel \
  tests/orchestrator/full_target/test_htn_recursion_fuel.py::test_changing_parameters_method_or_agent_does_not_refill_the_tank
```

### T04：Jev 请求与返回没有映射错位

**目的**：确认传给 Jev 的确实是当前决策，而不是丢字段、错配候选或错误解析。

**操作步骤**：

1. 从实际接入点构造三个合法候选；捕获适配层实际送给 Jev 的请求。
2. 检查目标摘要、当前决策类型、候选 ID 和候选描述是否保留。
3. 让测试替身选择 B；检查返回到调用方的仍是 B。
4. 把候选顺序由 `[A,B,C]` 改为 `[C,A,B]`，让返回继续指向 B；检查没有按旧数组位置误选。
5. 参数化注入下面的非法返回。

| 非法返回 | 必须观察到的行为 |
|---|---|
| 返回不在请求中的候选 ID | 不得作为合法选择交回正式路径 |
| 重复候选 ID，或请求／返回候选无法对应 | 明确拒绝，不能覆盖字典后假装正常 |
| 概率含 NaN、Infinity、负数或大于 1 | 分布出口校验失败，进入当前错误处理 |
| 应有分布缺项，或和明显不为 1 | 按协议拒绝；不能悄悄捏造概率补齐 |
| 空候选仍返回某个选择 | 拒绝该选择，保留当前无候选处理 |

上述分布断言只适用于接口声明的 Choice 概率分布；Boolean／评分接口按各自实际契约检查，不要求多个独立问题的结果合计为 1。若原始模型输出是 logits，在**适配层转换后的概率出口**检查分布，不能直接对 logits 套概率规则。和为 1 的比较使用合理浮点容差，例如 `1e-5`，不是逐位相等。

候选只有一个时优先走当前确定性分支；若既有协议允许调用 Jev，本轮只记录该行为，不为减少一次调用新增改造任务。

### T05：Shadow 同意或反对，都不改变正式结果

**这是本轮最重要的测试。**

**操作步骤**：

1. 冻结正式决策输入和正式路径的返回，使正式路径稳定选择 A。
2. 用新夹具执行关闭 Jev 的基线，保存正式返回和业务状态快照。
3. 重建同一初始状态，开启 Shadow，让 Jev 选择 A。
4. 再重建初始状态，开启 Shadow，让 Jev 以 0.90 的注入概率选择 B。
5. 等待这两个 Shadow 观测完成，再分别读取正式返回和业务状态。

**通过条件**：

- 三次正式选择都是 A。
- Jev 选择 B 的观测被如实保留，不被改成 A 来制造一致率。
- Shadow 不额外细化 HTN，不替换方法，不修改正式候选、不消耗额外的正式规划燃料。
- Shadow 只能增加观测；不能使正式业务状态相对同输入基线发生额外变化。
- 不触发 Worker 或后续任务执行。

**比较方法**：正式输出按语义比较，允许排除时间戳、耗时、观测 ID 等瞬态字段；不能排除方法身份、实际选择、参数、结果状态等关键字段。正式路径原本会改变的局部状态，应与关闭 Shadow 的基线比较，而不是要求所有状态绝对不变。

### T06：Shadow 出错不带坏正式路径

**目的**：确认 Jev 故障不会把本来能够完成的局部 HTN／决策请求变成失败。

分别测试：推理异常、模型不可用的错误、T04 的非法结果。

**操作步骤**：

1. 先确认关闭 Jev 时当前请求能够正常返回 A。
2. 打开 Shadow，在真实适配边界注入一种错误。
3. 调用同一个正式入口，检查返回。
4. 读取已有观测出口，确认错误被保留。
5. 随后再执行一次正常请求，确认适配层没有残留失败状态。

**通过条件**：正式结果仍为 A；错误可定位到本次请求；不伪造成功的 Jev 预测；下一次请求能够继续处理。

这里测试错误处理本身，不要求真的卸载依赖、损坏模型文件或制造本机 OOM。

### T07：慢 Shadow 不成为正式结果的前置等待

**目的**：确认“影子模式”不只是分支名字不同，而是真的不需要等它决策完再返回正式结果。

**操作步骤**：

1. 正式路径配置为立即返回 A。
2. Jev 测试替身进入推理后等待一个 Event；测试暂不释放它。
3. 调用真实 Shadow 包装入口，检查正式结果能否在 Jev 完成前返回。
4. 释放 Event，让影子结果完成并产生观测。
5. 再运行超时子例：让 Shadow 超过当前配置的超时界限，检查正式结果与清理行为。

**通过条件**：

- 第 3 步取得 A 时，Jev 仍未完成；这是主要断言。
- 超时只影响本次影子观测，不能覆盖已返回的正式结果。
- 用例结束时没有自己留下的悬挂任务；使用现有 close／drain／取消机制完成收尾。

测试可以设置几秒级的防挂保护，但它不是产品性能 SLA。不要以某台机器上“少于 20ms”作为该用例的正确性条件。

若现有实现已知会同步阻塞，这项应记录为当前 Shadow 缺陷，而不是修改测试把阻塞判为通过。本轮不要求为了修复它新增完整队列平台。

### T08：两条局部决策的观测不能串线

**目的**：用最小规模检查请求／候选／结果对应关系，不做并发压力测试。

**操作步骤**：

1. 创建两个不同决策请求 X、Y，使用不同候选 ID；正式路径分别选 `x-a`、`y-a`。
2. Shadow 分别选择 `x-b`、`y-b`，通过 Event 控制 Y 比 X 先返回。
3. 等待两条观测完成。
4. 检查观测中的请求标识、正式选择和影子选择。
5. 检查请求原始上下文没有被另一次请求或后来的状态更新覆盖。

**通过条件**：X 只关联 X 的候选与结果，Y 同理；每次调用有一条可归属的终结观测；晚到结果不能覆盖正式结果。

不要求全局消息 exactly-once、不要求数据库回放。已有日志／内存观测记录足以支撑本用例。

### T09：HTN → Jev 的最短局部接线

**目的**：避免“HTN 单测通过、Jev 单测通过，但二者实际没有接上”。

**操作步骤**：

1. 使用第 3.1 节的小型 HTN 夹具，走真实 HTN 入口。
2. 在当前实际 Jev 接入点构造一个有至少两个合法候选的局部决策。
3. 正式路径固定选择 A，Shadow 固定选择 B。
4. 执行从 HTN 到该决策入口的最短真实调用链。
5. 捕获正式结果及 Shadow 观测，在提交后续 TaskGraph／派发任务之前停止。

**通过条件**：

- HTN 目标与参数能正确进入实际决策输入。
- 确实调用了当前 Jev adapter，不是绕过适配层直接调用测试替身。
- 正式采用 A；影子观测保留 B；能关联同一局部决策。
- 本测试创建的下游执行替身没有被调用。

**TaskGraph 尚未完成时的处理**：若 Jev 接入点需要 ready candidates，直接注入少量合法候选快照。此时报告写“验证了 HTN 结果传递与 Jev 接线，ready 集合由夹具提供”；不能声称验证了真实图调度，也不能因此要求补完图调度。

## 5. 真实模型测试：少量、可解释，不追求大而全

### R01：真实 Jev 接口与局部 Planner 冒烟

这部分必须调用真实 Jev。FakeProvider 通过不等于真实模型已经可用。

**执行步骤**：

1. 使用本地当前已经安装的模型与适配代码，记录 checkpoint／版本、实际 device、运行配置。
2. 通过正式 Jev adapter 发送 3 个短请求，每次至少两个合法候选。
3. 保存适配前后结果，检查没有候选错位、非法概率或异常。
4. 使用同一份已冻结的正式决策输入，开启真实 Jev Shadow，确认正式选择不因它的实际预测而改变。
5. 当前 HTN 已有真实 Planner 接口时，对第 3.1 节提示词执行一次“仅规划”请求，检查目标、限制和未解决信息得到保留，然后停止。不要启动任务执行。

**通过条件**：真实模型身份和实际 device 可查；返回符合协议；真实 Shadow 不改变正式行为；实际 Planner 不伪造已完成结果。

若当前 HTN 阶段本来只暴露结构化输入，不要求为了第 5 步新增自然语言入口；记录该步不适用即可。

**环境限制的记录**：缺权重、MPS 不支持或服务未启动时，记录 `BLOCKED_ENV`。CPU 能跑只证明 CPU 路径，不能写成 MPS 已通过。本轮不要求移植 MLX 或补齐硬件适配。

### R02：Jev 小样本决策质量检查

**目的**：看它是否理解当前已接入的决策，而不只是“返回了一个 ID”。这不是接管生产的充分证明。

准备 **12 条短样例**，全部来自当前已实现的决策类型。每条提前写好：输入、合法候选、可接受答案集合、简短理由。

| 分组 | 数量 | 构造方式 |
|---|---:|---|
| 明确偏好的常规选择 | 4 | 多个候选均合法，目标明确偏向其中一个 |
| 目标／上下文变化 | 4 | 与前组配对，只改变一个决定性事实，使合理偏好改变 |
| 信息不足或近似等价 | 4 | 不人为编造唯一正确答案，允许多个合理选择 |

可参考以下配对，但仅使用项目确实已经接入的类型：

| 参考类型 | 上下文 A | 上下文 B | 检查点 |
|---|---|---|---|
| 候选优先级 | 目标是先理解失败原因 | 诊断已由给定证据确认，当前目标是整理对外说明 | 是否随目标变化，而非永远选第一个候选 |
| 候选优先级 | 关键日志尚未解读，报告素材不足 | 日志结论已明确，当前缺最终摘要 | 是否识别当前真正缺少的信息 |
| Retry／Escalate | 临时连接失败，允许重试且没有已知副作用 | 相同输入下重复出现确定性错误，没有任何修复 | 是否区分暂态失败与原样重试无益 |
| Retry／Escalate | 一次可逆、只读尝试失败 | 上次可能已有副作用且结果未确认 | 是否避免把“结果未知”当成“什么都没发生” |

硬性不合法的候选应由 Runtime 排除，不能用模型分数替代硬检查。这里评价的是合法候选内的偏好；安全约束本身的完整测试不属于本轮。

**执行步骤**：

1. 在看模型输出前固定 12 条样例与答案；不要看到结果后改答案。
2. 每条调用真实 Jev 一次，记录选择、分布与错误。
3. 从明确答案样例中选 6 条，只交换候选排列后再测一次。
4. 以稳定候选 ID 比较结果，不以候选的列表位置比较。
5. 列出错例：缺了什么上下文、选了什么、为什么不接受。最多写到能复现即可。

**报告内容**：有效返回数／12、明确答案命中数／该类样例数、6 条换序复测的一致情况，以及信息不足样例的原始分布。不要求模型在信息不足时一定输出某个固定概率。

**必须分开三种结论**：

- 与 Existing 选择相同：一致性。
- 符合事先标注的可接受答案：本样例上的决策质量。
- 降低实际业务总耗时／提高最终成功率：本轮没有测，不能宣称。

尤其不能把正式路径 A 的成功归到未执行的 Shadow 路径 B 上。高 top-1 或大 margin 也不自动等于高正确率。

## 6. 本机运行记录：只附带一次轻量测量

这一节复用 R01／R02 已经启动的模型，不另做长时间性能压测。

在用户实际使用的 16GB Mac mini 或 MacBook Air 上记录：机型、芯片、macOS、Python、实际推理 device、精度、输入 token 数／候选数。

```bash
uname -m
sw_vers
sysctl -n hw.memsize
```

**测量步骤**：

1. 把加载模型的耗时单独记录，不混进 warm inference 延迟。
2. 做 5 次短请求预热，再用相同量级输入连续测 20 次。
3. 记录 adapter 调用的端到端 p50、p95、错误数和样本数；样本太少，不强调 p99。
4. 看连续调用期间是否每次重新加载模型，以及内存是否持续增长。
5. 开启／关闭 Shadow 各执行同一个局部正式请求，记录额外等待；不扩大成全系统性能测试。

macOS 上可辅助使用：

```bash
/usr/bin/time -l python -m pytest -q \
  tests/htn_jev_focus/test_jev_real.py
```

该命令中的测试文件是本轮拟交付文件，生成后才能运行。`time` 的内存统计不能直接当成“整个系统统一内存占用”；Jev 在独立进程或已有本地服务中时，还要观察实际模型进程。MPS／驱动分配也需分开解释。

不把之前讨论中的“2–3GB”或“几十毫秒”当验收硬指标。本轮报告实际测量，优先确认能稳定返回、没有重复加载和明显持续增长；性能是否值得替换 Existing 单独判断。若 Existing 是纯规则，Jev 不一定更快。

## 7. 可选：Primary 已实现时才验证切换

### P01：只改当前模式配置即可采用 Jev，并正确回退

**不属于当前 Shadow 验收的必做项。没有实现时写 `NOT_IMPLEMENTED / 不纳入本轮门槛`，不要为了跑测试先实现它。**

仅在临时测试配置上执行：

1. 同一输入：Existing 选 A，Jev 选 B；Shadow 模式应仍返回 A。
2. 改为当前 Primary 配置；当返回满足现有接纳规则时，应返回 B。
3. 注入不满足现有接纳规则的结果、非法结果和推理异常；检查当前规定的回退是否生效。
4. 恢复 Shadow／关闭模式，再次得到 A。

若当前已有 probability／margin 阈值，读实际阈值，在边界两侧注入返回，检查比较符号是否符合当前约定。不要把测试示例里的 0.80、0.20 变成新的生产策略。

通过只证明“切换与回退机制可用”，不代表本次测试已批准把 Jev 切到生产 Primary。不要自动修改真实用户配置。

## 8. 交付与执行顺序

### 8.1 测试文件组织

优先补充既有局部测试。需要新建时，控制在以下小范围：

```text
tests/htn_jev_focus/
├── conftest.py                  # 最小夹具、入口适配、可控 Jev
├── test_htn_local.py            # T01–T03，已有测试可直接复用
├── test_jev_shadow.py           # T04–T08
├── test_htn_jev_local.py        # T09
├── test_jev_real.py             # R01–R02，明确调用真实模型
└── test_jev_primary_optional.py # P01，仅实现时新增
```

测试适配层只负责把共用材料转成现有类型，以及捕获结果；不得在测试里重新实现 HTN、候选筛选或 Shadow 逻辑再测自己。

### 8.2 实际执行顺序

**第一步：关闭真实模型，先跑核心局部用例。**

新测试完成后执行：

```bash
mkdir -p .local-test-evidence/htn-jev

python -m pytest -q \
  tests/htn_jev_focus/test_htn_local.py \
  tests/htn_jev_focus/test_jev_shadow.py \
  tests/htn_jev_focus/test_htn_jev_local.py \
  --junitxml=.local-test-evidence/htn-jev/unit.xml
```

若 T03 直接复用旧测试，将第 4 节的三个 node ID 加到命令中，或者在报告中记录独立执行结果。

**第二步：显式运行真实模型测试。**

```bash
python -m pytest -q \
  tests/htn_jev_focus/test_jev_real.py \
  --junitxml=.local-test-evidence/htn-jev/real.xml
```

真实测试必须明确识别模型与配置；不能连接失败后自动换成 FakeProvider 仍返回 PASS。模型缺失时如实标为环境阻塞。

**第三步：只有 Primary 已实现，才运行可选文件。**

```bash
python -m pytest -q \
  tests/htn_jev_focus/test_jev_primary_optional.py \
  --junitxml=.local-test-evidence/htn-jev/primary.xml
```

不默认执行 `pytest tests/`、整个 `full_target`、全项目 E2E 或全量门禁脚本。那些测试失败也不自动归类成这次 HTN + Jev 的缺陷。

### 8.3 不通过时怎么处理

- 被测局部功能违反上述约定：记 `FAIL`，附最小输入与实际返回。
- 模型权重／设备／服务缺失：记 `BLOCKED_ENV`，不能写 PASS。
- 被标为可选的功能尚未实现：记 `NOT_IMPLEMENTED`，不扩大开发范围。
- 无法在当前代码中定位 Jev 接线：记 `BLOCKED_INTERFACE`；单独报告 HTN 已测结果，不能声称 HTN + Jev 整体已覆盖。

不能通过修改预期答案、吞掉断言、无理由 skip／xfail 或开启完整执行链来“让报告变绿”。

## 9. 验收口径与报告模板

### 9.1 什么算本轮完成

| 结论 | 成立条件 |
|---|---|
| HTN 局部通过 | T01–T03 实际执行并通过 |
| Jev Shadow 工程接入通过 | T04–T09 实际执行并通过 |
| 真实 Jev 接入已验证 | R01 确实调用真实模型并通过 |

**本轮不出“完整任务系统通过”“TaskGraph 已完成”或“Jev 已证明可接管全部决策”的结论。**

只有 Fake 测试通过、真实模型被环境阻塞时，报告应写“Shadow 工程测试通过，真实 Jev 尚未验证”，不能合并成全部通过。
