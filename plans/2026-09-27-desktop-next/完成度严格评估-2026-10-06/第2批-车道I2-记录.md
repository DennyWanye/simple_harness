## 一、每条做了什么

### A08 失败码 `SOURCE_NOT_CURRENT`（完成）

- 含义：引用的身份还在，钉住的版本不是来源现在持有的那一版。按资产 `ref-resolution-map.json` 用自己的名字报，不再混进 `SOURCE_UNAVAILABLE` / `REF_REVISION_MISMATCH`。
- 改法：`storage/assurance_reads.py` 带版本列的种类（要求书、任务、做法、做法实例）按 (id, revision) 找不到时，再探一次"这个 id 在不在"，在就报 `SOURCE_NOT_CURRENT`，不在才是 `SOURCE_UNAVAILABLE`。`storage/assurance_blobs.py` 资料（path+version_hash 找到但生命周期 revision 不同）和产物（id 找到但 version 不同）同样改报 `SOURCE_NOT_CURRENT`。
- 不变：不可变种类带了非 0 版本号仍是 `REF_REVISION_MISMATCH`（那是引用写错，不是当前性）。
- 既有用例 `test_review_findings.py` F02 里"版本号 +1 → SOURCE_UNAVAILABLE"的期望改为 `SOURCE_NOT_CURRENT`。
- 这是保证通道内部码（`AssuranceError`），不是规划器/执行图的跨边界码，不进 `contracts/error_table.py`；Host 侧 `api/assurance.py` 对 `AssuranceError` 统一映射，不需改。

### A09 回执解析核写者与回执种类（完成）

- 改法：`read_exact_metadata(ref, *, receipt_kind=None, receipt_subject=None)`。对 `commit_receipt`：行上的 `kind` 就是写者身份（每个写者只用自己的常量写）、`subject_id` 是它写的对象；调用方说出期望的，不符按名拒：`REF_ISSUER_MISMATCH`（与事件桥"不是系统写的"同一码）/ `REF_SUBJECT_MISMATCH`（新码）。归属（`mission_id`）仍先于种类核。`ResolvedRef.issuer` 对回执就是行上的 `kind`。
- 把两处原来手工核 `row["kind"]`/`subject_id` 的消费点改成把期望交给解析器、删掉手工那两行：`assurance_review_transport.py`（`AssuranceReviewInvocationEnsured`，subject=intent_id）、`assurance_review_import.py` 的官方记录绑定读取（`AssuranceReviewImported`，subject=record_id）。通用重查（`recheck`、`pins`）不知道种类，不传，照常解析。
- 没动 `proposal_hash`：各写者的 `proposal_hash` 含义不一（有的是正文哈希，有的是绑定哈希），不能在解析器里统一核，仍由各消费点按自己的约定核。

### A10 解析器按计划返回 `ResolvedRef`，解析时核用途与访问（完成）

- 形状：`ResolvedRef(ref, body_json, tenant_id, mission_id, issuer, state_witness_json, permission)`。`ref`=kind+pin；`tenant_id`/`mission_id` 来自任务行真实查询；`issuer`=原 typed writer 的表 / 回执 kind / 事件 actor_type；`state_witness_json`=行上除正文之外的列（原 `lifecycle_json` 改名）；`permission` 只在读取器带授权时填，`compare=False`（许可租期按"现在"重发，重查比较不能看它）。
- 解析时核访问：`AssuranceReader(store, tenant_id=, mission_id=, authority=None, identity=None)`，授权与身份必须一起给（否则 `CURRENT_READ_AUTHORITY_REQUIRED`），身份的任务要和读取器一致（否则 `REF_SCOPE_MISMATCH`）。带授权时每次 `read_exact_metadata(ref, now_ms=)` 都调同一个 `_permission`。
- 只留一条判断：`_permission` / `_require_same_permission` / `CurrentAuthority` 从 `assurance_check_use.py` 迁到 `storage/assurance_reads.py`（解析器拥有这道判断）；所有原来从 `check_use` 导入它们的模块改从读取器导入（check_use、purpose_reviews、content_review、validity、review_import、review_handoff、review_consumer、reviewer_evidence_tools）。
- 五处原来"读元数据一遍 + 另起循环逐个 `_permission`"的使用点改成读取器带授权、许可随解析结果回来：`assurance_check_use.py` 准备、`assurance_purpose_reviews.py`、`assurance_content_review.py`、`assurance_review_import.py` 官方审阅准备、`assurance_validity.py` 候选准备。最终屏障 `_require_same_permission` 与资料读取的 `authorize=` 回调不动（它们就是在调同一个 `_permission`）。
- 名字取舍：计划写 `body`，代码里保留 `body_json`（本库"canonical 文本"字段的一贯后缀，70 余处调用方在用；`state_witness_json` 同理）。记在这里供主会话定。

### A13 完成范围与规格经 OCC 读者读（完成）

- `completion_spec` / `completion_scope` 从固定 SQL 表 `_EXACT` 里拿掉，改走 `OperationCompletionStore.get_spec_by_id` / `get_scope_by_id`（新加两个按 id 的读法，复用它自己的 `_decoded`：合同解码 + 行身份 + 批准回执 / 任务绑定校验）。OCC 读者报 `StoreConflict` → 解析器报 `REF_BODY_CONFLICT`；查无 → `SOURCE_UNAVAILABLE`；哈希仍按引用核。
- 任务说明里点名的是 `orchestrator/completion_status`：那一层（`OperationCompletionReader.read_scope`）按 (plan_revision, occurrence_id) 取，精确引用按 id 取，所以接在它下面那一层 `OperationCompletionStore`（同一套校验）。

### A15 审阅绑定轮次按复审递增（完成，附偏差说明）

- 改法：`assurance_purpose_reviews.next_review_round(connection, mission_id=, review_key=, purpose=, owner_task_id=, occurrence_id=)` = 同一个审阅对象（任务 × 用途 × 出现）已有绑定（不含本 review_key 的重放）的最大 `round_no` + 1。用途审阅与内容审阅两处写绑定都从它取，不再写常量 1。
- **偏差说明（对任务说明里"复审（SECOND_OPINION）时递增"）**：计划 #144 "一个 review_key/round → 一个 ReviewPackage → 至多两个 transport invocations。格式修复不是新语义 round；不同独立二审必须显式新 round/package"，表 #176 "获准独立二审或内容返工 → 新 round/package，ordinal 1"，建表注释也写 "invocations are bounded children, not new rounds"。现有 SECOND_OPINION（09-30 用户决定）实现为同一绑定下的 ordinal 2 调用、原请求原样再发；绑定是冻结文档，第二次调用时不能改它的 `round_no`，否则绑定哈希、请求正文、`assurance_review_bindings.review_key` 唯一键、调用表外键全都要重做。所以本条按计划口径做：**新一轮 = 同一对象再准备一份新审阅包**（返工后的新结果、改要求后同一结果再审、显式独立二审都会走到这里），SECOND_OPINION 仍是同一轮的 ordinal 2，审计看 `assurance_review_invocations.ordinal/reason`。若主会话要 SECOND_OPINION 也算新 round，需要另立方案改绑定/包的结构，本车道没动。
