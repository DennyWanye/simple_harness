## 2. 实现决定

1. **销毁顺序**：先 `AgentRuntime.close_agent`（不接新输入、有界排空），若仍有开着的 Turn 再 `cancel_turn`（协作取消，不杀 Run）；然后释放本进程内的分区连接与检索服务；在会话 FileGuard 内开一个执行事务：写 `session_destroy` 原始回执 → 冻结 `PurgeProgress`（phase DRAINING，source/trash 相对目录由 root + session + destroy 命令派生，`expected_marker_hash` = 创建时协议行记录的 marker 哈希）→ `generation+1` + `destroy_command_id/hash` → `RuntimeSessionStateChanged`（schema 2，带 purge_progress_hash）→ 取消该会话尚未开始的 INDEX/BIND_IMPORT 作业（PENDING/BLOCKED，租约中的留给其持有人自行收敛）。事务外再把该会话未终态的召回沿协调器自身路径推成 STALE（J7）。
2. **七类见证的真实来源**：TURNS = `list_agent_turns` 中 queued/running/result_pending；CALLS = `list_effects_for_run` 中 prepared/handed_off；UNKNOWN = 效果 unknown + `list_incomplete_provider_invocations` 中属于该 Run 的；PENDING_IMPORTS / INDEX_WRITERS = 该会话 BIND_IMPORT / INDEX 作业中 PENDING/LEASED/BLOCKED；TEMP_ROOTS = SCRIPT 技能使用中执行器未给出终态的；READ_HANDLES = 未终态召回行。每类 `set_hash = digest(refs)`，`complete=True`，`all_safe` 由 `rules.complete_disposal` 判定。见证回执只在证明封存（DRAINING→PURGING）时落库，等待期间不增长事件日志。
3. **封存**：证明完整才写 `session_disposal` 回执（= `delete_proof_ref`）、`sealed_highwater` = Journal 高水位、phase RENAME_PENDING、状态 PURGING，并在同事务创建 PURGE 作业（semantic_key = destroy 命令号，payload.disposal_ref 指向处置正文）。DRAINING 期间没有作业行，由 tick 的 `drive_draining` 逐会话求证。
4. **观察→唯一动作**：PURGING 每步先在 FileGuard 内读两个精确目录（目录存在且 marker 可解析并等于 `expected_marker_hash` → MATCH；存在但 marker 缺/坏/不同 → MISMATCH；不存在 → ABSENT），交给 `purge_rules.recovery_action`：RENAME_EXACT 做 `os.rename`；DELETE_EXACT 做 `shutil.rmtree`；RECORD_RECOVERED_RENAME / RECORD_DELETION_ABSENCE 只记录事实回执（`recovered:true` / `absence:true`），不补造旧执行回执；FINALIZE_SAME_DESTROY 转 PURGED；BLOCK_* 写 typed blocking + 观察回执，状态与 phase 不变。文件操作失败：PermissionError 或 EBUSY/ETXTBSY/EACCES/EPERM → FILE_BUSY（SAME_DESTROY_BACKOFF，60s 后同身份重试），其余 → IO_ERROR（MANUAL）。
5. **恢复入口**：`resume_destroy` 校验 session/agent/destroy id/hash（不符 → `PURGE_IDENTITY_MISMATCH`）、generation/row_version（不符 → `GENERATION_STALE`）；同 command_id 重复只返回当前行；写 `session_destroy_resume` 回执后 `advance(force=True)` 重新检查，仍有问题就用新观察更新 blocking（保留 first_seen），干净则清 blocking 并继续原 phase，同时把 BLOCKED 的 PURGE 作业放回 PENDING。没有路径参数、没有 ignore_marker。
6. **重建门**：`rebuild` 在权限检查后先拒绝任何 destroy 身份（DRAINING → `SESSION_DRAINING`，PURGING/PURGED → `SESSION_PURGED`），再按 `can_rebuild` 只接受 QUARANTINED；资源引用必须等于部署的 chunker/view/embedding 指纹（否则 `POLICY_CONFLICT`），`old_index_generation` 必须等于当前已发布代；成功则退役旧代、开新代、重排全部已闭合组的 INDEX 作业、QUARANTINED→ACTIVE。`quarantine` 提供 ACTIVE→QUARANTINED（generation+1）的管理隔离。
7. **保留许可**：`permit_session_erasure` 只对 PURGED 会话签 `arp_agent_sessions` 行的许可（body_hash = create_command_hash），其他状态 `RETENTION_BLOCKED`；删除本身仍由保留服务执行，SDK 不做反射式删表。
8. **SessionView**：`deletable` = ACTIVE/QUARANTINED；`blocking_refs` = DRAINING 时最近一次见证的阻塞引用（召回用 `operation` 种类以同时满足两份 Schema），PURGING 阻断时为观察回执；`last_lifecycle_receipt_ref` 取 destroy/inspection/rename/delete 中最新者，否则创建回执。
9. 未新增错误码；所有 DTO 走 `codec.check`（SessionDelete / SessionDestroyResume / PurgeProgress / PurgePathObservation / CompleteSessionDisposal / CollectionWitness / PurgeJobPayload / IndexRebuildCommand / SessionView / JobResult / 事件体）。
