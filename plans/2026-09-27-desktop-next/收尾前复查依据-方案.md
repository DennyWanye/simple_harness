# 收尾前复查"通过的依据还有效吗"（完成度评估第 4 项）

2026-10-01 凌晨起草。用户睡前拍板：按方案直接做，不等审阅。**红线：证书失效绝不接到 `goal_resolutions.validity` 列，只接到"重审"。**

## 一、现状（核对代码与真机库后）

- 每一步验收通过、根目标结论成立时，系统都发一张"通过证书"（`assurance_use_certificates`），证书上记着它读过的每一项（读集 `read_set`：具体对象 OBJECT、固定查询集 QUERY_SET、权限 ACCESS、策略 POLICY；真机一张根证书 75 项、验收证书 101 项）。
- 有一个"有效性观察者"（`AssuranceValidityConsumer`）在来源变化、到期时重看每张证书，记"仍有效 / 已过期"（`AssuranceUseValidityChecked`）。但它判"来源变了"的依据是**整任务的时钟**（mission_epoch 等三个数）——任务里任何一件事（下一步验收、一次审阅）都会拨动时钟，于是**证书一签发几乎立刻被判"来源已变"**。这就是 09-25 独立审查说的"读集太粗"。也正因为它太粗，这个观察结果**没有接到任何决定**上（接了就永远收不了尾）。
- 收尾评估（`AssuranceCloseoutConsumer._evaluate_locked`）看根结论、判定、完成度、效果、排空，**不看**"当初通过的依据现在还成立吗"。资料换版有单独的触发（架构方案 B），但那只覆盖"资料"这一种依据。

## 二、改法（都在 SDK）

1. **读集判断改为逐项重读**（`assurance_consumers.AssuranceValidityConsumer._observe_locked`）：
   - OBJECT 项：按 (kind, id, revision) 重读当前正文，指纹不同才算变（这些对象基本不可变，换版本是新行，所以极少变）；
   - QUERY_SET 项：把固定查询集在当前库里重跑一遍，比对内容指纹；**查询集的指纹不再含时钟**（`CompleteRead.read_item` 去掉 epochs，只留 schema、行数、行内容），否则永远比不上；
   - ACCESS / POLICY 项：观察者没有权限评估器，保持不比（权威变化由 ROOT_CHANGED 覆盖）；
   - 时钟不一致只记一条说明性理由 `EPOCH_MOVED`，不影响"仍有效"；真正变了的项列在 `changed_items` 里。
2. **收尾前复查**（`AssuranceCloseoutConsumer._evaluate_locked`）：读根结论的证书和每条贡献验收的证书（消费方 ROOT_RESOLUTION / ACCEPTANCE），当场按第 1 条重查；任何一张真变了 → 收尾 `NOT_READY`，理由 `EVIDENCE_STALE`，并**给受影响的步骤记一条"证据失效"修复请求**（与资料换版同一条路：`EvidenceInvalidated` → 规划器决定重做 / 后继），同一张证书同一处变化只记一次。重做通过后产生新验收、新证书，收尾再评估。
3. 不改 `goal_resolutions.validity`，不改验收记录，不改提示词。

## 三、测试

- 夹具级：验收后取得证书 → 任务里再发生无关变化（比如再写一个事件、拨时钟）→ 观察结果**仍有效**（此前立刻"来源已变"）；把它读过的一项改了（如给该范围新增一条观察 / 换资料版本）→ "已过期"，`changed_items` 指出哪一项。
- 收尾：证书失效时收尾 NOT_READY + 修复请求一条；重做通过后可收尾。
- 变异：去掉逐项重读、去掉收尾复查、去掉"只记一次"，各应有测试挂。
- 相关组：assurance_exec、operation_completion、编排全组。
- 真机一局：资料换版但换在**根终审之后、收尾之前**，看收尾能否拦住并重做。
