## 5A 执行存储类

### 5A.1 按业务域拆成 mixin（纯移动）

| 项 | 拆前 | 拆后 |
|---|---|---|
| uow.py | 17807 行，一个 15504 行的类 | 约 1000 行：组合类（只剩 close、事务入口、几个只读方法）与少量辅助定义 |
| 领域文件 | — | 子包 execution/sqlite/uow_domains/：20 个领域 mixin、core（公共基类）、support（多域共用辅助函数） |
| 最大的类 | 15504 行 | 1453 行（派生结果 mixin） |

做法：
- 工具 scripts/code_quality/split_class.py，分组写在 scripts/code_quality/split_specs/uow.json。方法源码逐字搬，模块级辅助定义按使用方放置（只一个域用→放进该域；多域用→support；只组合类用→留下）。
- **公共基类 core**：领域 mixin 调用的组合类方法（插入事件、取运行、核对租约与围栏、起始回执等 23 个）和原类的 `__slots__`、`__init__` 一起搬进 `ExecutionUnitOfWorkCore`，每个 mixin 继承它。原因：只搬 mixin 时 mypy 报 441 个"没有这个属性"，其中 388 个指向这些共用方法。
- 跨领域调用（约 25 个方法）在调用方 mixin 里写 `if TYPE_CHECKING:` 同签名存根，沿用原有 ProviderAccountingMixin 的写法。原类对 ProviderAccountingMixin 的继承改挂到提供方调用 mixin 上。
- 唯一的非搬移改动：`SqliteExecutionUnitOfWork._invalidate_cancel_activation(...)`（静态方法里按类名调用）改成 `WorkflowCancelMixin._invalidate_cancel_activation(...)`。
- mypy 范围（pyproject）加入新子包；24 个文件 0 错，SDK 总数仍 314。

验证：350 个方法与辅助定义 AST 逐字比对，只差上面一处；类的方法解析顺序与 `__slots__` 核对（实例仍无 `__dict__`）；单片校验全过（导入冒烟、启动与控制通道快照、禁区比对、棘轮、启动耗时、导入隔离、改坏清单资产测试）；直接引用执行存储的 83 个 SDK 测试文件 0 失败。后端测试用的是钉版 SDK 包，看不到工作树改动，留到 5F 全量回归。

执行存储类没有改坏清单条目、没有接缝条目，所以无需改清单。

计划顺序是 5B.1 状态分组 → 5B.2 mixin 纯移动 → 5B.3 协作对象。实际先做 5B.2：两步互不依赖；纯移动可以逐字比对，先做风险最低；分组时按领域文件逐个改，更好审。

### 5B.2 按领域拆成 mixin（纯移动）

做法与 5A.1 相同，差别：
- `__init__`（全部实例字段）与三个只读访问器放进公共基类 `OrchestratorCore`，类常量也搬进去；`recover` 构造 `RecoveryCoordinator(self)`，要的是协调者类型，留在协调者类里。
- 跨领域调用 149 个方法。按 5A 的写法要在 16 个文件里写 293 个存根；改为集中写在公共基类的 `if TYPE_CHECKING:` 块里一处（分组 JSON 的 "stubs_in_core"）。mypy 结果与拆前相同：30 个旧错误，报错里的类名从 Orchestrator 变成 OrchestratorCore。
- 拆分工具修了一个缺陷：原文件在代码中间还有两条导入，旧做法把"第一条到最后一条导入之间"整段替换，会吞掉中间的常量定义。改为逐条删导入、在第一条位置放新导入块。（5A.1 的 uow.py 导入是连续的，不受影响，核验员已逐个比对。）

### 5B 拆长函数：规划决策收集（1342 → 274 行）

这个函数里有三个闭包，闭包按调用时的值读外层变量，不能随便把段抽走。做法：
- 新增冻结数据类 `PlanningReply`：11 个构造后不再变的值（意图、任务、原文、请求号、尝试序号、决策号、原文哈希与存放位置等）装进去，构造后的读取改为 `reply.X`（语法树反向比对一致）；两个别名内联。
- 开头准备段（绑定请求、重放检查、写原文）抽成 `_open_planning_reply`，重放时返回 None。
- "记录进度"闭包改为显式传参的方法；它只在编译阶段读预览三项，所以 `preview_command`、`source_principal` 与 `planning_commit_admission` 一样先初始化为 None（原来能走通的路径行为不变，原来不读的仍不读）。
- "记录评估"闭包的方法体搬成方法，闭包只留三行转交（三项在任何调用前都已赋值，调用时读当前值）。
- 以 return 结束的段（六个决策类型分支、提交尾段、未准入拒绝、预览不可用、共享秩序被拒、解码错误、仅留痕决定）抽成方法；预览段抽成方法，被拒返回 None、成功返回具名元组。
- 两个修复分支依赖分支条件对 `decision.payload` 的类型收窄，方法开头加 `assert isinstance(...)`（沿用本文件已有写法，调用方已检查同一条件）。
- ContractError 解码分支没抽：解析失败时 `decision`、`canonical_json` 还没赋值，原代码靠条件短路不读，作参数传就会报错。
- 抽取工具加了两项检查：段内给闭包读的变量赋值时，要求它在返回值里且段内不调用该闭包；传入了段内先赋值再读的参数时报"多余参数"。推导式变量与 `except … as` 变量不再误判。
- mypy：本文件旧错误从 3 个降到 2 个（一处多余的类型注解随预览段搬走）。
- 棘轮"超 150 行的函数"一度多 2 个（抽出的提交尾段 218 行、方法或求助路由 176 行），再各抽两三段（提交失败拒绝、计划被拒、规划后端求解、无法路由拒绝）后降到 150 行以内。
- 独立核验 PASS（阶段5B-规划决策收集拆分核验.md，内联回原函数比对语法树，差异只有别名内联、删一句纯注解、两句 None 初始化）。核验员提醒改坏条目 F1-13 锚点文字变了（`reply.mission.id`），已改，改坏检验 KILLED。
- 相关测试 98 个文件：恢复协调器"不一致任务被隔离"在并行负载下超时一次，单独重跑两次通过（45 秒的时间敏感用例）。

## 中途发现

- **函数内相对导入漏扫，编排器整体停摆**：第一次跑测试，几十个端到端用例超时。对照（拆分前的代码）全过。用调用计数比对两边，发现 `run` 每次在恢复步骤后就返回；恢复协调器的恢复状态是"降级"，原因是它在函数里写了 `from .event_handler import DeferredPlanning`，这个名字已搬走，导入失败被恢复流程当作"恢复失败"，于是不进调度周期。外部引用扫描工具当时只认绝对导入，漏了相对导入。已修工具（相对导入换算成绝对模块名），重扫后只此一处；处理见上（DeferredPlanning 单独成文件）。以后拆模块：外部引用扫描必须覆盖源码里的函数内相对导入，且必须跑几个端到端用例，不能只靠逐字比对。

- **提交时误带文件**：先 `git add` 了新子包、再按路径提交计划文档，第二次提交把暂存区里的新子包一起带上，导致禁区比对把 HEAD 当成"新旧两份都在"而报字面量减少。撤回该提交（未推送）后重新提交。以后按路径提交前先看暂存区。
- **重生成文件时后台测试仍在跑**：重跑拆分工具会先删子包再写回。这次内容只差两行文档字符串，测试没受影响；以后跑测试期间不重生成。
