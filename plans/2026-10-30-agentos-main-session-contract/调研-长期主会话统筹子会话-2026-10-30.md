# 调研：让一个长期存在的主会话统筹多个子会话，并充分用上 SDK 的编排能力

日期：2026-10-30。基线：SDK `0.13.0.dev20260925+opt.222`。
需求方两家：AgentOS（《需求原文-AgentOS-v1.0-2026-10-30.md》）、AIPhone（《需求原文-AIPhone-统一交接-2026-10-30.md》及两份附件）。
本文只写核对过源码的事实。本文不改代码。

## 0. 一句话结论

两家要的是同一样东西："一个长期主会话 + 多个长期子会话 + 子结果自动回到主会话 + 重启不丢"。
SDK 现在有一半底子（会话、委派、任务编排、收件箱、幂等重放、单进程锁），缺另一半（父子关系、多委派并存、结果驱动的自动续办、宿主授权回调、全宿主统一并发门）。
但在这之前，**有一个紧急缺陷要先修**：用户点一次"停止回答"，这个主会话就永远不能再用。这条不修，长期主会话无从谈起。

## 1. 两家需求对照

| 项目 | AgentOS 合同 | AIPhone 交接 | 一致吗 |
|---|---|---|---|
| 主会话长期存在、不进 HTN | 是 | 是，明确"主 Session 自己不使用 HTN/TaskGraph" | 一致 |
| 子会话 | 工作会话，可多轮追加输入 | 长期子会话，完成一次工作后可继续追问、改要求，不销毁 | 一致 |
| 层数 | 深度 1 | 一层，不做递归 | 一致 |
| 多任务并行 | 至少两个独立 Mission 同时跑 | 多个子会话各自一个在途 Mission | 一致 |
| 结果回主会话 | 结果驱动的自动续办，宿主策略 enqueue/hold/deny | 子工作完成后主会话自动汇总并通知，受预算与合并频率限制 | 一致。AgentOS 要可关，AIPhone 要默认开 |
| 命令幂等与回执 | command_id + request_hash + CommandReceipt | 创建、追加输入有稳定幂等键 | 一致 |
| 宿主授权 | AuthorizationRequest/Decision 回调、grant_ref | 权限只缩不放，用户是唯一审批主体 | 一致，AgentOS 要得更细 |
| Goal 对象 | 要，有版本、完成条件、grant_ref | 没提 | 只有 AgentOS 要 |
| 全宿主统一并发门 | 容量 2 时两任务真并行、主控不饿死 | 总上限 1 时绝不超发；每池上限不是全机上限 | 一致 |
| 执行者换代 / 停止后继续 | SDK-05/10 提到 | **F1 紧急缺陷**，前置条件 | AIPhone 已踩到 |
| 语音 | 没提 | 语音绑定期间也要能自动汇总/播报；F2 中继协议错误；F3 上下文来源混淆 | 只有 AIPhone 要 |

结论：做一套，两家都能用。AgentOS 特有的是 Goal 和细粒度授权回调；AIPhone 特有的是语音和手机资源。核心是同一个。

## 3. 紧急缺陷 F1：停止回答后会话不可用（根因已核实）

现象（AIPhone 真机）：用户在模型已接请求、答案没回来时点"停止回答"。之后这个会话任何新输入都立刻失败，报 `react_cost_exceeded`，模型调用 0 次。重启也不好。

根因（源码核对）：

1. 取消让那次模型调用的费用变成"不明"（`provider_cancelled_after_handoff`，金额为空）。这符合"可以多算不可以少算"。
2. `chat.py` 的 `_given_up` 只在两种情况换新执行者：Agent 已关闭，或开着的回合卡在结果不明的调用上。取消后回合已结束、Agent 仍开着，所以**继续复用这个 Agent**。
3. `simple_harness/runtime/termination.py:625`：只要预算里有一笔不明费用，下一次输入在调模型前就按 COST 终止。加预算没用。

要改什么：取消后的"不明费用"保留在账上（不清零、不重放），但换一个新一代执行者接着聊，原会话身份、历史、委派关联不变。这是执行层的一处判断加一处换代，不碰编排。要先红后绿。

## 4. 主要矛盾

**矛盾一：会话身份要长期，执行者寿命是短期。** 会话要跨重启、跨执行者换代、跨取消保留身份、历史、委派、结果。现在 SDK 的产品层只把"会话"做到了"一个会话一个在途任务、停了就坏"。F1 是这个矛盾最直接的表现。

**矛盾二：结果要主动回来，主会话的模型回合是被动的。** 现在只有用户说话才起回合。两家都要"子结果到了主会话自己动"。但自动起回合要受预算、合并频率、宿主策略约束，还不能和用户正在进行的回合、语音通道抢同一把锁。

**矛盾三：并发要全宿主统一，现在每个池各管各的。** 多会话一上，模型并发会按会话数翻倍。手机受不了。要一个宿主级的门，所有会话、所有任务都过它。改默认数值会动池身份（已知坑），注入共享门对象不动数值可以避开。

**矛盾四：开发期不兼容 vs 两家要上线。** 用户已定继续开发期。两家都接受"这次新根"，但 AIPhone 写明"长期能力发布后要给兼容范围"。这条留到开发期结束再谈。

## 5. 接入差距（SDK 之外）

| 接入方 | 差距 |
|---|---|
| AgentOS | 把 chat→主会话映射做稳；SSE 只订阅不持有执行；删掉自己的同步等待父阻塞；写 ContinuationPolicy；画子会话与审批卡片（AO-01～08） |
| AIPhone | IPC 只开固定 main，没有子会话目标；UI 只读一个会话的任务；事件从 0 补读；只有三个只读工具，没有检索工具 |
| 桌面端 | 主会话一个只读工具都没注册；前端拒收附件（上一轮已指出） |

## 6. 建议的做法与顺序

1. **先修 F1，单独小版本发布。** 不等大功能。先红后绿，AIPhone 真机复验"停止后同会话新 key 能继续"。
2. **再做主子会话（一套设计，两家共用）。** 按 AgentOS 合同的 M1～M3 结构，加上 AIPhone 的三条：子会话长期、自动汇总默认开且受限、宿主统一并发门。语音期间的自动汇总走现有播报接缝，不并行起第二个文字模型。
3. **语音 F2/F3 并行查。** F2 要中继方配合（给 chinzy 的对外稿 10-28 已写好，没发）。F3 在 SDK 侧核验来源标记。
4. **开发期不做迁移。** 每次新根。能力发现 + 版本探测 + 旧库明确报错。
