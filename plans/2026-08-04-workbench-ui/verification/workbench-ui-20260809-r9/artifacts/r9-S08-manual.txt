## 前置：r8 缺陷 WBUI-DEF-S08-01 复验
r8 本场景 FAIL 的现象是「设置页 LLM Providers 区永久空白」。
根因（已更正过一次，见 r8-S08-manual.txt 的「根因更正」段）：
SettingsProviders 的 hydrate effect 只在挂载瞬间发一次 list 请求，而
useWebSocket 的 getChannel 是 useCallback(…, []) 永久稳定引用 ⇒ effect 不会重跑；
socket 若在挂载时尚未 connected，请求就永远发不出去（叠加 lastMessage 单槽
被同批其他控制消息覆盖）。修复：挂载时发 + 每次 (re)connect 再发，并直接从
channel 订阅回包，不走单槽 lastMessage。
本轮为**冷启动全新进程**（非 HMR 残留）验证，见截图 r9-S08-02-settings-win.png。

### 第一次尝试暴露真缺陷 WBUI-DEF-S08-02（附件 r9-S08-step7-defect.md）
新版打开旧版目录 → 后端 lifespan 抛 CapabilityStoreConflict → 8100 持续不绑定
（轮询 30s listen=0）→ 前端永远「未连接/正在恢复身份…」。
根因：capability 操作幂等复用检查里 request.source.uri 存**绝对安装路径**并参与身份比对，
而 idempotency_key 是内容哈希与路径无关——口径不一致。

### 修复（同轮内完成）
backend/deskpet/capabilities/store.py: 新增 _operation_identity_request_json()，
身份比对时对 source.type=="builtin" 的请求把 uri 归一化为 None（builtin 包随应用走，
安装路径不是身份）；git 等外部来源 uri 保留（那是真实身份）。落库仍存原文。
回归测试 2 个（backend/tests/capabilities/test_pack_store.py）：
  · builtin 换路径重放 → 命中原记录不冲突；其他字段变了仍冲突
  · git 来源换 uri → 仍冲突
capabilities 套件 259 passed / 4 failed——4 个失败经 git stash 对照确认**无本修复也同样失败**
（godot 平台不兼容 + universal_action_fixture_preparer 既存债务），与本修复无关。
