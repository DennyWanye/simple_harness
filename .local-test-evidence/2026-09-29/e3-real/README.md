## 结论（2026-09-29 19:15）
- 结构修复链路在真实模型下走到了：原问题（执行者如实报卡住）→ 修复请求（影响范围正确，无关已通过贡献保留）→ 规划器受信提案（第 3 轮可读、被正式评估）。**没走到"第 2 版计划并收敛"**：三轮里一次被初始规划预先覆盖、一次卡在格式、一次规划器选择宣告受阻。
- 新发现的产品缺口（未修，另记）：**缺外部输入时任务直接失败、不问用户**。规划器在修复轮里倾向"宣告受阻"而不是"升级给人"；宣告受阻在方法仍有效时不产生任何动作，最后以"没有可派发的工作"失败，用户只看到失败。修法需要改规划器模板（出新模板版本，旧执行池身份不变），建议作为收口后的下一项。

辅助：`mission_peek.py <任务ID>` 只读查看步骤与最近事件。

## 第 4 轮后的结论（2026-09-29 20:05）
- 修好的：缺外部资料时系统会问用户（真实模型下规划器主动提问，问题写得清楚）；即使规划器仍宣告受阻，也会转成问题等回答而不是静默失败。
- 新暴露的缺口：**用户的回答只交给规划器，执行者看不到**。现有可用的修复动作里，没有"按用户给的内容新增一个前置步骤"的合法路子（后继步骤必须保留原目标契约；换方法要有已注册方法；方法合成只在没有任何方法时才开），于是规划器只能原样重试，执行者照样缺数据，直到规划次数用完。
