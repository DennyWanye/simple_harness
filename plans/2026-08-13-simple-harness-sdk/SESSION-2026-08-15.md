## Key Architectural Insights

### 1. Workflow Profile Pattern

Discovered that capability_build uses a **profile configuration** pattern rather than implementing a new workflow graph:

```python
# Profile specifies:
WORKFLOW_NAME = "durable_task"  # Reuses existing graph
WORKFLOW_VERSION = "v1"
DEFAULT_PROPOSAL_BUDGET = 40    # Constrained budget
DEFAULT_FIX_BUDGET = 3          # Constrained repair attempts
```

This is a bounded variant - same graph logic, different constraints and capabilities.

### 2. Builder Contracts Pattern

Seven contracts cover the complete builder lifecycle:
1. Search evidence (what was searched)
2. Lineage (where it came from)
3. Launch (admission contract)
4. Install request (how to install)
5. Evidence (what was built)
6. Completion (terminal value)
7. Admission (execution identity)

All use frozen dataclasses with cryptographic fingerprints for verification.

### 3. Conformance Testing Architecture

Two-layer approach:
- **CLI tool** - Standalone execution with JSON reports
- **Pytest plugin** - Same logic, test framework integration

Both use the same host factory pattern for flexibility.

### 4. Protocol Version Strategy

- Semantic versioning with fail-closed compatibility
- Major version match required (1.x SDK requires 1.x host)
- Minor/patch differences within same major are compatible
- Clear upgrade path for future versions
