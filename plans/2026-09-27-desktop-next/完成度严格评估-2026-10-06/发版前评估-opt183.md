## 必须处理

### M1：做法审阅、终审的归属任务不能"停步骤"，新收口抛错并永远等

**机制**

1. 审阅第二次调用的预留在哪个账户，由审阅对象定（`assurance_review_transport.py:239`）：
   - 内容审阅（TASK_CONTENT）：步骤账户。
   - 做法审阅（METHOD_PLAN）、终审（MISSION_FINAL）：任务总账户。
2. 这两类审阅的归属任务（`assurance_review_bindings.owner_task_id`）是复合目标或根任务，状态是 BLOCKED。真实库可证：
   - parse 第 6 次：两条做法审阅归属 `desktop-root-…`、`task-3a72…`，都是 BLOCKED。
   - docopt 第 5 次（已完成的任务）：终审 `assurance-mission-final:…` 归属根任务，任务结束后根任务仍是 BLOCKED。
3. 新代码 `_review_owner_task` 对所有 `review-import:` 工作项都返回归属任务，然后 `_stop_task_budget_exhausted` → `orchestrator._commit_stop_task`。
4. `_commit_stop_task` 先跑 `_prepare_terminal_ledger`（`event_handler.py:1744`）：把这个任务所有未结束的派发意图（PENDING / CLAIMED / AGENT_CREATED / SUBMITTED）记成 FAILED。这一步单独提交。
5. 再跑 `commit.stop_task`：只接受 READY / VERIFYING / ACTIVE（`commit_service.py:3573`）。BLOCKED 抛 `CommitRejected("task … is BLOCKED; cannot stop it")`。
6. `_settle_failure` 只接 `StoreConflict`（`assurance_tick.py:402`）。`CommitRejected` 是 `StoreError`，不是 `StoreConflict`。它冒出 `_settle_failure`、冒出 `tick()`。`work.wait` 没有执行。
7. `tick()` 在 `_cycle_inner` 里不在任何边界内。`_cycle` 把 `CommitRejected` 当"提交被拒"，整轮跳过（`event_handler.py:3849`）。这一轮后面所有任务的调度都没做。
8. 工作项停在 RUNNING。租约到期后再领、再准备、再抛。每次都重复第 4～7 步。

**后果**

- 任务不结束，仍是"永远等"。这正是本次要修的毛病，只是换成了做法审阅和终审。
- 每次重领都把任务里在跑的派发意图记成 FAILED，任务却没停。做法审阅时兄弟步骤可能正在跑。
- 每次重领都跳过一整轮调度。
- 归属任务已是 COMPLETED（重审已验收结果）时，`_stop_task_budget_exhausted` 直接返回，照旧记 BUDGET_WAIT，每分钟再看，永远等。

**能不能走到**

- 前提：做法审阅或终审的第一次调用格式错或回合失败，第二次在任务总账户上预留不下，链上没有活着的预留。
- 第一次调用回合失败：parse 第 5、6 次都撞过"流以 [DONE] 结束但没有 finish_reason"，审阅员也撞过。
- 任务总账户预留不下：本次固定额度让各步上限之和可以超过任务总额，任务总账户成了真正挡住的那一层。终审在任务最后，正是总额用得最多的时候。
- 所以产品路径可达。

### 1. 固定额度模式（`plan_commits.py`、`occurrence_tasks.py`）

**任务总额守不守得住**

- `reserve`（`budgets.py:220`）先对 `_chain(account_id)` 每一层查余量，任一层不够就抛 `BudgetExhausted`，全部够才逐层加。
- 步骤账户的父账户是任务总账户（`plan_commits.py:1513-1517` `parent_id=mission_account(...)`）。所以各步上限之和超过任务总额时，任务总账户仍然挡。
- `grow`（`budgets.py:322`）、`transfer_tail`（`tail_budget.py:233-245`）同样逐层查。调用前的增长也挡在链上。
- `open_account` 的 `fits_within`（`models.py:192`）逐维比较。1000 万 ≤ 2000 万成立；次数 12 ≤ 12 成立；其余维度由 `inherit_limits` 继承任务的值。
- 任务总额 < 1000 万时：`share = min(cap, pool)`（`plan_commits.py:1445`）。用例 `fixed-too-big`（池子 200 万、固定额度 300 万）验证叶子拿 200 万。

**"还剩多少"按任务账户算，是否包含下级**

- 包含。`reserve`、`grow`、`settle`、`settle_at_upper_bound`、`transfer_tail` 都对整条链逐层 `_apply`。任务总账户的 reserved / settled 就是下面所有步骤与它自己的预留、结清之和。

- 新口径下这个库的 `available` = 2000 万 − 858,870 − 4,501,814 = 14,639,316。

### 2. 审阅等额度不再永远等（`assurance_tick.py`）

**`_budget_can_still_change` 的覆盖面**

| 可能还回额度的主体 | 现在算不算"还会变" | 说明 |
|---|---|---|
| 尝试预留（步骤账户） | 算：尝试非终态 | 对 |
| 在线路上的审阅员、规划器调用 | 算：意图 AGENT_CREATED / SUBMITTED | 对 |
| 已建但未派发的审阅员、规划器意图（PENDING / CLAIMED） | 不算 | 它派发后结清通常低于预留，会还额度。见建议 S1 |
| 意图已 FAILED、上游没报用量的预留（UNKNOWN 挂着） | 不算 | 等迟到对账。见建议 S2 |
| 首审尾款 HELD | 不算 | 见下 |
| 兄弟步骤的预留（出错在任务总账户时） | 不算 | 查询只看出错账户的祖先，不看下级。见建议 S1 |

**parse 第 6 次库里的 HELD 尾款**

- `first-critic:task-bf03…:attempt-3` 是 HELD，但它的预留 `tail:first-critic:…:attempt-3` 已是 0：745,472 在第一次审阅调用时已整笔转给 `…assurance-content:355494…:1`（`transfer_tail`）。
- 它在第 3 次尝试进终态（现在是 VERIFYING）或步骤、任务停止时释放（`release_terminal_tail_holds`，`commit_service.py:1717`、`:2395`）。释放的是 0，不放出额度。
- 所以它不是"还会变"的来源。用副本跑真实判定：步骤账户、任务总账户都返回 False。判定在这个库上是对的。
- 第二次审阅要 745,472。步骤账户（旧上限 500 万）剩 295,895，释放尾款后不变，装不下。
- 唯一能放出额度的是第一次审阅调用那笔 UNKNOWN：若迟到对账补上，按已知 125,246 + 未知那次上限 92,739 结清，步骤账户剩 823,382，装得下。但这条线路的这种失败没有迟到用量，等不到。按"多算不少算、不冻结"，不等是对的（建议 S2）。
- 新口径下步骤账户上限 1000 万，剩约 529 万，这次本来就装得下。

**`_stop_task_budget_exhausted` 能不能正常收口**

- 内容审阅（归属步骤 VERIFYING）：能。探针 `test_zz_probe_stop.py`：步骤 VERIFYING → ACTIVE → FAILED，在跑的尝试 CANCELLED，任务 FAILED，`stop_reason=budget_exhausted`，详情带 `source_kind / account / requested / remaining`。
- 做法审阅、终审（归属 BLOCKED）：不能，见 M1。
- 事务：`_settle_failure` 在 `tick()` 的 `except` 里调用，此时准备的事务已回滚，`tick()` 开头也断言不在事务里。`_prepare_terminal_ledger` 与 `stop_task` 各开各的事务，没有嵌套。`StoreConflict` 被 `_settle_failure` 接住。
- 漏了一步：其余 12 处停步骤入口停完都 `await self._release_mission(...)`（解绑工作区、取消被级联关掉的尝试的回合），这条新路径没有。兄弟步骤的回合要等关 Agent 的清扫（30 秒一次）才停（建议 S6）。

**之后 `work.wait` 记 BUDGET_WAIT，下次领取怎么处理**

- 触发事件是第一次调用的 TURN_FAILED / 格式错。准备直接走格式修复分支（`assurance_review_consumer.py:236-241`），在 `review_subject_stopped`（`:262`）之前，不走 `_prepare_late`。
- 格式修复入口在预留前先过现行性检查（`assurance_review_transport.py:282` → `assurance_review_handoff.py:34`），任务已结束，报 `REVIEW_SUBJECT_STOPPED`。
- 这是 `AssuranceError`，走 `recheck`：前 3 次立即，之后 0.5 / 1 / 2 秒，32 次或 300 秒后成 `MANUAL_REQUIRED`，之后不再空转（`assurance_tick.py:136-142`）。
- 探针里 25 秒内已重算 14 次。不是每分钟永远重试，不挡。实施记录"等它被'步骤已停'收掉"不准确（建议 S3）。

## 建议（不计入结论）

- **S1：判定查的范围。**`_budget_can_still_change` 查的是出错账户和它的祖先，不是它的下级。
  - 出错在任务总账户时，兄弟步骤在各自步骤账户上的预留不在查询里，判"不会变"会偏早。
  - 出错在步骤账户时，任务总账户上规划器的活预留算"会变"，但它结清只回到总账户，回不到这一步账户。只会多等，规划器结束后自然收口，不挡。
  - PENDING / CLAIMED 的服务意图不算活着，但它派发后结清通常低于预留。
  - 建议：查"出错账户及其下级账户"上的预留；活着的意图状态加上 PENDING、CLAIMED。
  - 新用例里"在任务总账户上跑的尝试"在产品里不存在（尝试只在步骤账户上预留），建议改成兄弟步骤账户上的尝试。
- **S2：UNKNOWN 预留的取舍写进记录。**意图已 FAILED、上游没报用量的预留，现在算"不会变"。迟到对账若补上，能放出额度（parse 库里会放出约 52.7 万，第二次审阅就装得下）。这条线路的这种失败不会有迟到用量，按"多算不少算、不冻结"不等是对的。建议在实施记录第九节写明。
- **S3：停步骤后的工作项。**现在要重算 32 次或 300 秒后才成 `MANUAL_REQUIRED`，留在已结束的任务上。建议格式修复分支之前先判 `review_subject_stopped`，走 `_prepare_late` 作废，并更正实施记录里"等它被'步骤已停'收掉"的说法。
- **S4：平分路径去留（意见）。**
  - Host 永远传 `task_max_tokens`，产品只走固定额度。平分只在 SDK 测试世界（默认 cap None）与不传这个值的嵌入方里用。
  - 它不是"兼容旧数据"的旁路，但按"同一件事只留一条路径"，它是第二条活路径，产品不走它，SDK 大部分端到端用例却走它。
  - 意见：下一版把固定额度作为唯一模式（`CommitService` / 测试世界默认给值），删 `share_tokens` 与平分分支，测试一起迁。这一版不挡。
