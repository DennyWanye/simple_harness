**取消（cancel）入口：本轮无法在 UI 上取证——不是没找到，是结构上不可观测。**
证据链（三段，缺一不可）：
 ① 渲染条件：CapabilityOperationCard.tsx:237 起，动作按钮来自
    `operation.available_actions.map(...)`，标签表 ACTION_LABEL.cancel = "取消"。
    即 UI 只在后端把 cancel 放进 available_actions 时才画这个按钮。
 ② 后端何时给 cancel：backend/tests/capabilities/test_capability_center_service.py:278
    `assert operations[0]["available_actions"] == ["cancel"]` —— 该断言的前置是
    用 _SlowManager 人为拖住一个 uninstall，让它停在 running。
    也就是说 cancel 只在操作 **status='running'** 期间提供。
 ③ 真实操作能 running 多久（本 profile 全量实测，非估计）：
    sqlite3 .testenv/cold-A/data/workflow.db \
      "select kind,status,count(*),min(ended_at-started_at),max(ended_at-started_at)
       from capability_operations where ended_at is not null group by kind,status;"

    **历史全部 24 条操作，running 窗口 8ms–55ms，上限 0.055 秒。**
 ⇒ 「取消」按钮在真机上的存在时长 ≤ 55 毫秒。任何人手点击或截图观测周期都在
    数百毫秒量级，比它长一个数量级以上。这不是取证手法不够，是该 UI 态的寿命
    短到人类和截图都无法命中——**对真人用户同样不可见**。
    （同一类问题 r8 已遇到过一次：用 SQLite 的 started_at/ended_at 差值证明某 UI
     态结构上不可观测。r7 把 S06 记成 BLOCKED，很可能就是卡在这里。）

已排除的错误做法（都不做）：
  · 滚动 24 条操作找「取消」——全是「已完成」，条件上不可能出现，滚到底也是白费
  · 拿 ① ② 的代码/单测当 UI 证据交差——项目纪律明写脚本/协议层证据不替代真模拟点击
