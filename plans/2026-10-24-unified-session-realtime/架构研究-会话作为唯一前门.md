# 架构研究：会话作为 SDK 的唯一前门

日期：2026-10-25。问题：后面要接 Realtime 语音，主会话要有完整能力，SDK 还要让接入方更省事。什么结构最合理？
方法：先答四个问题，再给方案、备选对比、迁移路径和裁判标准。所有"已核实"都来自今天读的源码与消费者代码。

## 0. 一句话结论

**把"会话"做成 SDK 唯一的前门。** 聊天、后台任务、语音都是会话下面的引擎，不再是三套并列的 API。接入方只做三件事：给输入输出适配器、注册自己的工具与连接器、消费一条事件流。委派、结果回传、审批路由、预算、断线恢复全部在 SDK 里。桌面端先当第一个消费者，把它现在那 4400 行适配层删掉换成会话调用，AIPhone 拿到的就是打磨过的接口。

## 1. 四个问题

### 一、顶尖专家会做而没人要求的

| 专家会做的事 | 现状 | 本方案 |
|---|---|---|
| **先数一数接入方今天要写多少代码。** 接口好不好用，不看方法多不多，看接入方为了跑通一个场景要写多少行、要懂多少概念。 | 没人量过 | 已量（第 2 节）：Host 53 个公开方法；桌面端适配层 4406 行；AgentOS 一个场景脚本 100～165 行，其中约 50 行是轮询循环 |
| **把三个消费者写的同一段东西收回 SDK。** 桌面端写了 `mission_start` 工具（721 行）、通知台账（`notices.py`）、事件泵（`pump.py`）；AgentOS 脚本写了轮询驱动；AIPhone 现在要求 SDK 再提供一套。同一件事写了三遍。 | 分散在消费者 | 收回成会话的内置能力：委派命令、inbox、事件流 |
| **先定"一个最小程序长什么样"，再写接口。** 先写 30 行的目标程序，接口反推。 | 文档里 18 处调用示例，没有端到端最小程序 | 第 3.4 节给出目标程序，作为验收标准 |
| **让主会话的模型拥有判断权，SDK 只管约束。** 这是项目 10-01 的核心思想。今天的聊天池却把主会话做成"残废模式"：没有回读历史的工具、不能委派、模型调用上限 8 次、有副作用只能"建议建任务"。 | 聊天是降级模式 | 主会话给齐：只读工具 + 历史回读搜索 + 委派/查询/取消 + 连接器经审批做副作用；上限按会话配置，不按"聊天"写死 |
| **把语音当成会话的一种绑定，不是另一个产品。** 否则每个宿主都要自己把语音通道和文本会话缝起来，AIPhone 的交接文就是在要求我们替它缝。 | Service SDK 的本地通道协议只有 call.start/stop/audio_ack/barge_in，和会话无关 | 会话上 `attach_voice()`，工具目录自动从会话的工具生成 |
| **把记忆留位置。** 桌面端的记忆组件现在是空桩（等 memory SDK 集成）。会话的上下文装配要留一个"组件插槽"，否则接记忆时又要动会话。 | 桩 | 会话上下文由组件组成：窗口、折叠摘要、历史回读、（将来）记忆 |
| **删旧路径，不做兼容层。** 开发期规则。 | — | 桌面端的 `mission_start`、`notices`、`pump` 在会话落地后删除 |

### 二、最原始的材料

| 判断 | 不采信 | 采信的原始材料 | 看到了什么 |
|---|---|---|---|
| 接口有多重 | "方法数" | `host.py` 公开方法清单 | 53 个方法，按概念分 7 类：生命周期 10、配置 6、聊天 3、建任务 3、人机互动 9、查询 12、诊断 10 |
| 接入方实际怎么用 | 文档示例 | `~/sh-ext-accept5/sol_approval_loop.py` | 驱动循环：`drain(60)` → `snapshot` → `plan` → 找待答问题 → `answer_planning_question` → `approvals` → `decide` → `sleep(3)`；再分页 `events(after_seq)`。约 50 行，每个消费者都得写 |
| 桌面端怎么委派 | 记忆里的描述 | `backend/deskpet/orchestration/chat_tool.py` | 一个 721 行的 `mission_start` 工具：幂等键从聊天 Run 与调用派生、12 条成功条件上限、资料 8 份上限、auto 模式代批。这些逻辑全是通用的，不属于桌面端 |
| 结果怎么回到对话 | — | `backend/deskpet/orchestration/notices.py` | 一本通知台账：按终态事件 id 去重、从上次 seq 补读、人点"已收到"才 ack、模型只能读不能 ack。这就是 inbox，已经设计好，只是放错了地方 |
| 推送怎么做 | — | `backend/deskpet/orchestration/pump.py` | 只读连接每隔几秒看 mission 状态与最高 seq，变化就广播带白名单事件。也是通用的 |
| 语音接入方要做什么 | 能力标志 | `realtime/local_channel.py` 消息类型 | 宿主要实现 `local.hello`、`call.start/stop/ready/audio_ack/barge_in/closed/error/state`，加 PCM 帧。和会话、任务没有任何关联字段 |
| 聊天池能力 | — | `host/chat.py` | 工具只有应用只读工具；没有 `session_history_read`；8 次模型调用、8 次工具、180 秒；有副作用只能"说这要建任务" |
| 配置负担 | — | `host/settings.py` | `HostSettings` 36 个字段，`ModelConfig` 11 个。大多数接入方只需要 4 个（模型、密钥、数据目录、当事人） |

### 三、专家的方法与工具

1. **接口面审计**：把 53 个方法按"接入方必须懂 / 可以不懂 / 只有调试才用"分三档。目标：必须懂的不超过 10 个。
2. **目标程序法**：先写 3 个目标程序（文本+委派+重启；语音三轮+委派+播报；桌面端替换），再定接口。
3. **决策记录（ADR）**：三个备选架构的对比表，写明为什么选、什么情况下换。
4. **消费者替换验证**：桌面端用新会话接口重写一遍，删旧代码。删掉的行数就是接口省下的工作量。
5. **文档只读接入测试**：给一个没看过源码的子代理只发文档，让它写 AIPhone 风格的接入程序。一次写对算过。
6. **公开接口清单比对**：两个 SDK 都已有 `public-api` 检查；新接口进清单，旧接口删清单。

### 四、外部裁判

| 要证明的事 | 裁判 |
|---|---|
| 接口更省事 | 桌面端适配层行数前后对比；AgentOS 场景脚本行数前后对比；轮询循环消失 |
| 接口能被外人用对 | 文档只读接入测试一次通过 |
| 主会话能力完整 | 同一组 20 条用户输入，在桌面端和 AIPhone 风格程序上得到同样的委派/直答/澄清决策 |
| 语音和文字是一个会话 | 文字建任务语音查，语音建任务文字取消，历史在同一本日志里 |
| 没偷改旧行为 | `public-api.json` 比对；编排 SDK 消费者边界检查；两边发版门 |
| 手机上真能用 | AIPhone B01–B07，对方判 |

## 3. 方案

### 3.1 三层结构

```
宿主（桌面端 / AIPhone / AgentOS）
  只做：文字输入输出、音频输入输出、界面卡片、注册工具与连接器、给凭据
            │ 一个对象、一条事件流
编排 SDK：Session（唯一前门）
  身份/历史/预算/权限 · 回合仲裁 · 内置控制命令（委派/查询/取消/回答）· inbox · 恢复
     ├─ 文本引擎：现有 ReAct 执行池（补齐工具：历史回读、委派）
     ├─ 任务引擎：现有 HTN + TaskGraph + 审阅（不改）
     └─ 语音绑定：attach_voice()（可选 extra [realtime]）
                     │ 工具目录、上下文注入、播报调度、重连
Service SDK Realtime：provider 中立的语音客户端（Qwen / OpenAI 线路）
```

### 3.2 会话的公开接口（目标形态）

| 方法 | 作用 | 来源 |
|---|---|---|
| `Session.open(root, principal, model, tools=, connectors=, policy=)` | 打开或恢复 | 现有 `OrchestrationHost.open` 包一层 |
| `session.send(text, idempotency_key)` | 文字回合，返回回执 | 现有 `chat()` |
| `session.events(after=)` | **一条**异步事件流：正文片段、回合提交、已委派、任务进度摘要、需要人答、结果已到、错误 | 合并 `output_stream` + `events()` + 通知台账 + 泵 |
| `session.respond(request_id, decision, version)` | 回答规划问题或审批 | 现有 `decide` / `answer_planning_question` 二合一 |
| `session.interrupt()` | 停当前回合，不动任务 | 现有 `chat_cancel` |
| `session.tasks()` / `session.task(id)` / `session.cancel_task(id)` | 会话名下的任务 | 现有 `missions/snapshot/cancel` 加会话过滤 |
| `session.attach_voice(audio_io, profile)` → `VoiceBinding` | 绑语音 | 新 |
| `binding.playback_position(ms)` / `binding.barge_in()` / `binding.detach()` | 播放回执、打断、挂断 | Service SDK 本地通道改接 |
| `session.close()` | 关会话，任务保留 | 现有 `close` |

模型在会话里看到的内置工具：`delegate_task`、`task_status`、`task_cancel`、`session_history_read`、`session_history_search`，加宿主注册的只读工具与连接器。模型不传身份；SDK 注入 principal、session_id、turn_id、call_id。

现有 53 个方法不删，降为"高级/调试"层，从首页文档移走。

### 3.3 关键机制

| 机制 | 做法 | 为什么 |
|---|---|---|
| 一本历史、两个引擎 | 文本引擎（DeepSeek ReAct）和语音引擎（Qwen 原生）各自调模型，但只往同一本会话日志提交：用户输入（文字或转写）、助手回复（文字或转写）、工具调用、委派、结果。回合仲裁器保证任一时刻只有一个引擎在答 | 语音要原生听说的延迟与音质；文字要 ReAct 的工具循环；两者共享"发生过什么" |
| 委派 = 内置控制命令 | 把桌面端 `mission_start` 的逻辑搬进 SDK：幂等键派生、上限、door 检查、auto 代批。不是 DomainTool | 已有 721 行写好的通用逻辑；只读工具约束不动 |
| inbox = 通知台账搬家 | `notices.py` 的设计原样进 SDK：按终态事件 id 去重、从上次 seq 补读、人才能 ack | 已验证过的设计 |
| 事件流 = 泵搬家 | `pump.py` 的"只读看 seq 变化就推"进 SDK，和逐字片段、通知合成一条流 | 消费者不再写轮询 |
| 聊天池 v2 | 新池编号、配置版本；v1 池与提示词一字不动 | 工具说明是池身份，改了旧数据起不来 |
| 上下文组件化 | 窗口装配、折叠摘要、历史回读已有；加"组件插槽"给将来的记忆 | 桌面端记忆组件是空桩，迟早要接 |
| 语音工具目录自动生成 | 从会话的内置命令与宿主工具的 schema 生成，下发到 `session.update.tools`，以 `session.updated` 回显为准 | 不靠 instructions 文本约束 |
| 主动播报 | `session.announce(text)`：按阶段 0 试验通过的那条路实现（文本 item / 二次 session.update / 重建连接） | 官方文档没写文本注入，先试再承诺 |
| 打断与取消分离 | `barge_in()` 只清本地队列并 cancel 生成；任务取消只走 `cancel_task` | 交接文 6.3 |

### 3.4 目标程序（接口的验收标准）

文本 + 委派 + 重启，目标 30 行以内：

```python
session = await Session.open(root, principal, model, tools=[device_status])
async for event in session.events():
    ...  # 宿主只把 event 画到界面
await session.send("帮我把这周的照片整理成相册", key="t-1")   # 模型自己决定委派
# 进程重启
session = await Session.open(root, principal, model, tools=[device_status])  # 同一会话号
async for event in session.events(after=last_seen):                             # 补到 result_ready
```

语音三轮 + 委派 + 播报 + 打断，目标 60 行以内：宿主只实现 `AudioIO`（三个方法：读 PCM、写 PCM、报播放位置）。

### 3.5 备选架构对比

| 备选 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A 一个引擎 | 语音转写 → 文本引擎 → 语音合成 | 一个模型、一套工具循环、最简单 | 延迟高、丢掉原生语音的听说质量、打断难做 | 作为公开的降级档位保留，不做默认 |
| **B 一本历史、两个引擎** | 文本 ReAct + 原生语音，同一本日志，回合仲裁 | 各取所长；AIPhone 要的就是它 | 要做仲裁与上下文注入；注入能力待线路验证 | **选它** |
| C 两个会话、宿主缝合 | 现状：文本会话与语音通道独立，宿主自己接 | 不改 SDK | 每个宿主重写一遍；AIPhone 明确拒绝 | 否 |

### 3.6 迁移路径

1. 阶段 0 可行性门（已在主计划里）。
2. 编排 SDK 加 `Session`：先只包文本引擎与任务引擎。桌面端切到 `Session`，删 `chat_tool.py`、`notices.py`、`pump.py` 与对应的 handlers。删掉的行数记进证据。
3. Service SDK 0.3.13：工具目录、注入、播放回执、改钉版。
4. 编排 SDK extra `[realtime]`：`attach_voice`。桌面端语音也切过来（它本来就是 Service SDK 的消费者之一）。
5. AIPhone 接入；AgentOS 的脚本用 `Session` 重写一遍作为第二个外部消费者证据。

## 4. 风险

| 风险 | 对策 |
|---|---|
| 语音线路不支持文本注入 | 阶段 0 先试；不过就用重建连接，公开行为 |
| 桌面端切换期间两条路并存 | 开发期规则：切完即删，不留兼容层；切换在一个发版内完成 |
| 聊天池身份变化 | v2 新池；v1 不动 |
| 事件流过大 | 事件分级：界面级（默认）与诊断级（可选）；payload 白名单沿用 `project_event` |
| 预算三本账 | 会话账本只引用，不重复结算；音频 token 按官方 `usage` 的分项原样记 |

## 5. 外部参考设计对照（子代理 2026-10-25 实抓官方文档）

| 框架 | 主动说话 | 长工具调用 | 文字+语音同会话 | 持久化/续接 | 宿主接音频 | 最小程序 |
|---|---|---|---|---|---|---|
| LiveKit Agents | `session.say` / `generate_reply` → `SpeechHandle`（可等播完、知道被打断） | `ctx.update()` 第一次即应答；后续更新排队；**空闲时自动跟进播报**；可取消；同名去重 | 是，`lk.chat` 文字进同一会话，运行中可关音频 | 断线可续；进程重启要自己灌历史 | WebRTC 房间 | 30～40 行 |
| OpenAI Agents Realtime | `send_message` 或原始 `response.create` | 后台跑，但结果只按普通工具结果回 | 是 | 未见 | 宿主推 PCM、读 `audio` 事件 | 约 25 行 |
| Pipecat | `TTSSpeakFrame`、`LLMMessagesAppendFrame(run_llm=True)` | `cancel_on_interruption=False`，晚到结果作 developer 消息注入并触发推理 | 是，都是帧 | 未见 | transport 处理器 | 40～60 行 |
| Vapi | 控制地址 POST `say` / `add-message` | `async:true` + 之后 `add-message` 回填 | 部分 | 只有事后报告 | 平台托管 | 配置 + 一个 webhook |
| OpenAI Realtime 原语 | `conversation.item.create(message)` + `response.create(instructions)`；带外回复 `conversation:"none"` | 自己实现 | 是 | 不支持，60 分钟上限 | 原始音频 | — |

五条启示，以及本方案怎么采纳：

1. **会话是 SDK 自己的对象，不是模型连接。** 所有框架的真实状态都在 SDK 内存或自家上下文里；原生线路有时长上限且不能续接。采纳：会话日志由编排 SDK 持久化，Realtime 连接只是可替换的"嘴和耳朵"，重连时按 SDK 规则灌回摘要与最近几轮。
2. **长任务分三段：马上应答 → 进度 → 空闲时播报。** LiveKit 的 `ctx.update` 最完整。采纳：任务建好即作为工具应答说出；规划/执行/审阅里程碑只进上下文不打断；终态结果在会话空闲时播报；提供 `cancel_task` 与同意图去重。
3. **主动播报要过回合仲裁。** 用户在说话或模型在回复时先排队；需要"空闲检测 + 前台锁"；播报返回句柄，报告播完或被打断。采纳：`session.announce()` 返回 `SpeechHandle`。Qwen 无 truncate，被打断时本地记录为准（已列为公开限制）。
4. **结果注入与发声分开成两个原语。** "追加消息（可选触发回复）"与"带外生成"。采纳：Service SDK 提供这两个原语的 provider 中立接口；Qwen 线路哪个能用由阶段 0 试验定，不能用的报 `unsupported`。
5. **宿主只接音频管道，接口要小。** 采纳：宿主实现 `AudioIO` 三个方法；文字模式就是不接音频的同一个会话，不是另一套聊天池（这一条正好否定现在聊天池与任务池分家的做法）。

一处要提醒：OpenAI 原语有 `truncate` 与带外回复，Qwen 官方客户端事件都没有。对照表里"会话 60 分钟上限、不能续接"是 OpenAI 的数字，Qwen 的时长上限官方页没写，阶段 0 顺手测。
