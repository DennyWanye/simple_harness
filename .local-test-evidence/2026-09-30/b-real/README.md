# 架构方案 B 真实模型验证（2026-09-30，SDK opt.92，隔离环境 ui-full，DeepSeek 经本机转发）

`b_run.py`：建任务时带资料 `sources/sales.csv`（华东 100 / 华北 50）→ 报告那步开始执行就换版本（华东 999 / 华北 50，一次批准）→ 只读跟随。任务 `mission-f7cc803f42ccf0d4`，记录 `run1.json/log`。

事件链（编排库只读查得）：
1. 换版本 `SourceSuperseded`（seq 64590）→ **系统当轮发出修复请求**（64610，`source_key=source:…`，reason=`source_superseded`，触发引用 = 正在跑的 `attempt-1`，影响范围含该步骤与根），新登记时没有发请求（64343 只登记）。
2. 规划器对这条请求先后两次回复 WAIT，都被协议拒绝（64821、64847）——它想等正在跑的尝试结束，但修复轮不允许 WAIT。
3. 尝试 1 用旧数据写完 → 审阅员对照**当前**资料判不通过（64898："资料为华东=999，产物写华东=100"）→ 普通的验收失败修复请求（64899）。
4. 规划器 REPAIR（原方法重试，64917–64919）**一次处理掉两条请求**（`repair_request_ids` 含资料变更那条与验收失败那条）。
5. 尝试 2 挂载新版 → 验收通过（65025 `AcceptanceCommitted`）→ 终审切包无过时原因（65040，包切在变更之后）→ **任务完成**。最终 `sales_report.md`：华东 999、华北 50、总计 1049。

结论：资料变更的触发、影响范围、请求消费在真实模型下都走通，任务用新数据完成。系统消费出口这局没用上（被计划改动消费），由单测覆盖。

具名后续（未修）：**尝试正在跑时资料变了，规划器的自然反应是 WAIT 等它跑完，但修复轮拒绝 WAIT**，白白花掉两轮规划次数；可选做法：这类请求等尝试结束再交规划器（反正验收会对照当前资料），或修复轮允许"等这个尝试"。
