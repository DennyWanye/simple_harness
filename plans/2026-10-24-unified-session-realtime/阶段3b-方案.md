最后更新：2026-10-25。状态：独立评审 BLOCKED，SDK 公开接缝及依赖交付未完成；桌面切换未实施。

## 当前生产入口

- 实际主界面是 `PrimaryChatView`，经 `primary/controller.ts` 的 `queue.enqueue`、`human_memory_request` 进入 `ForegroundRuntimeExecutionAuthority._drive_claimed`，冻结提供方、工具与上下文，再交 SDK ReAct 执行。不能只改旧 `chat_v2` 就声称主对话完成切换。
- `chat/chat_v2` 另经 `control_chat._cc_chat → harness_chat._run_product_harness_chat`。`sdk_runtime_stack.py` 给产品 Agent 注册 `mission_start/status/amend/list/source_update/method_library`；其中 `mission_start` 自建委派、幂等与自动授权。
- `OrchestrationService` 已独占 `<user_data>/data/agent-orchestrator` 的 SDK Host，任务页读取此 Host。`MissionNotices` 另写 `mission-notices.json`；`MissionChangePump` 直接轮询任务库并广播 `mission_changed`。主对话通知、任务卡和任务页多处消费该广播。
- Host 钉版为 opt.217；opt.218 仍是待复核候选，不切换到未验收候选。

## 唯一目标链路

桌面主对话只有一个稳定会话号 `desktop-main`，principal 继续使用现有 `_principal(user_data)`，数据根不变。SDK Session 使用其 v2 聊天 Agent、内置 `delegate_task/task_status/task_cancel`，不再注册桌面委派工具。任务页保留 `mission_create[_with_sources]`、查询、审批等现有 Host 接口；这些接口确实由 `MissionsView` 使用，不能按名称全部删掉。

| 控制消息 | SDK 调用 / 输出 |
|---|---|
| `session_send` | `await session.send(text, idempotency_key)`；原键只在显式重试时复用 |
| `session_events` | `session.events(after)`；以现有 WebSocket 广播 `session_event`，只投影白名单 |
| `session_history` | `session.history(limit)`，刷新与重连读取持久终稿 |
| `session_respond` | `session.respond(request_id, decision, version, **fields)`；传输请求号与人工请求号分开 |
| `session_interrupt` | `await session.interrupt()`，不取消后台任务 |
| `session_tasks/task/cancel_task` | 对应 `tasks/task/cancel_task`，保持会话所有权检查 |
| `session_inbox/ack` | 对应 `inbox/ack(event_id)`；已应用与人已收到独立 |
| `session_budget` | `session.budget()`，不另记费用 |

前端主界面文字提交、片段、终稿、委派卡、人工提问、已收到统一消费上述接口。`ChatMissionNotices` 改读 inbox/result_ready/ack；主对话卡改读 Session 快照和 needs_response。任务页相关组件只把刷新触发改为统一事件，仍读原任务页接口。删除旧 `mission_notices/mission_notice_ack/mission_changed` 的处理与合同映射，不搭建新旧兼容层。遇到旧通知开发数据明确报告不兼容，不迁移、不静默丢弃。

## 公开接缝阻断

已检查仓库源码及实际安装的 opt.217：`Session.open()` 会新开并独占 Host；既有 Host 没有公开的会话工厂，Session 也没有公开的附着/启动方法。直接二次打开同一根目录会锁冲突；另建目录会使任务页看不到主对话委派；读取 `Session._host` 或启动 `_chat/_pump` 会越过公开接入边界。方案采用 SDK 补齐公开的“在现有 Host 打开 Session”生命周期接缝，但该 SDK 修改及本地发版超出任务书钉版约定，已经向用户提出选择，未获答复前不实施依赖它的生产改动。

## 独立复核后的依赖交接

依据 [独立评审](阶段3b-独立评审.md) 的 B1，先由独立 SDK 工作交付公开生命周期接缝，再实施桌面接线；本阶段不改 SDK 源码或擅自换用候选轮子。接缝名不限定为 `open_on_host`，现有同名断言只是最初的提案门槛，依赖交付后须改成真实公开 API 的行为测试，不能把换个名字本身判为缺陷。

SDK 接缝必须满足以下可验收行为：

1. 在已启动、已持有根目录锁的 Host 上打开指定会话号，不二次构造 Host 或争用同根锁；主对话与任务页看到同一任务库。
2. SDK 内部完成聊天池打开、配置与身份绑定、委派恢复、inbox 补读、会话事件泵启动；桌面只调用公开接口。
3. 关闭会话释放该会话资源，保留任务页 Host 与任务驱动；打开失败也不关闭或解锁外部持有的 Host。Host 关闭与重建时会话的生命周期须明确。
4. 提供定向测试、公开接入说明、通过发布门的正式轮子与清单；在 Host 实际钉版后再运行接缝行为测试，不能拿仓库内未发源码代替已安装依赖。

本轮额外用真实公开 `Session.open` 证明：同一根的 Host 已持锁时打开会话报 `HostUnavailable`，且原 Host 锁仍保留。这是前置条件反例，未调用模型，也不是桌面切换验收。
