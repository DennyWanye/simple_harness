## 四、第 4 条：一步接多个上游（textkit 局）

### 4.1 做法与接法

做法的五步：wordstats、slugify（两个独立模块）→ cli（接两者）→ tests（接三者）→ readme（接 cli、tests）。

| 接收步 | 上游条数（`data_requirements`） | 做法里 `delivery` 数组顺序 | 冻结清单里的端口顺序（`port_ordinal`） | 开工时拿到的文件数 |
|---|---|---|---|---|
| cli | 2 | wordstats, slugify | wordstats=0, slugify=1 | 5（序号 705） |
| tests | 3 | wordstats, slugify, cli | wordstats=0, slugify=1, cli=2 | 7（序号 985） |
| readme | 2 | cli, tests | cli=0, tests=1 | 10（序号 1295） |

- 汇合步拿全了上游文件。例：cli 拿到 wordstats 的 3 个文件与 slugify 的 2 个文件。
- 端口顺序与做法数组一致。
- 冻结清单只给端口文件（每个上游 1 个）配了见证编号；其余文件是顺带转交。这属于偏离第 6 条，不在本次修复范围。
- `AttemptCreated` 里的输入列表按路径字母排序，不反映端口顺序；顺序要看冻结清单。
- 没有出现写入冲突。

### 4.2 是否并行

| 尝试 | 开始～结束（秒） |
|---|---|
| wordstats | 108～168 |
| slugify | 210～258 |
| cli | 306～377 |
| tests | 449～561 |
| readme | 633～692 |

- 时间窗两两不重叠。5 次派发的 `AllocationDecided` 都是并发上限 2、可派发数 1。
- 不重叠的原因：规划器在做法的 `ordering` 里自己写了 `{"before":"wordstats","after":"slugify"}`。系统按此生成先后约束（`order_constraints` 第 1 行）。序号 209 的"暂不派发"事件（`HierarchicalDispatchWithheld`）对 slugify 写明 `reason: WAITING_ORDER`，`detail: predecessor outcome RUNNING does not satisfy release condition accepted`。
- 规划器的说明文字自己写了"两个互不依赖的模块"，却仍排了先后。为什么这样排，从数据里看不出。
- 按修复方案（挑战第 21 条），"同一时刻两步在跑"只记录、不作通过条件。所以本条判符合。真正的并行仍没有在任何一局发生过。
