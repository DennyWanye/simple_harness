## 逐项核验

### 1. 单轮时限 3600 秒与其他时限的关系

**Host 实际用的值**

- Host `service.py` 构造 `OrchestratorConfig` 时不传 `turn_deadline_seconds`，所以用 SDK 默认值。opt.181 起默认值是 3600。
- Host `settings.py` 没有这个设置项。`config.toml` 也改不了它。

**SDK 里谁读这个值**

| 位置 | 用法 | 判断 |
|---|---|---|
| `event_handler.py:5060` 规划器回合 | `turn_deadline_seconds=config` | 3600 |
| `event_handler.py:11002` 执行者回合 | `min(config, task.budget.max_runtime_seconds or config)` | Host 和 SDK 都不设置 `max_runtime_seconds`（grep 结果为空），所以取 3600 |
| `assurance_review_runtime.py:250/452` 审阅回合 | `config`，或 `min(config, 剩余等待)` | 3600 |
| `event_handler.py:584` `_critic_wait` | 默认等于 `turn_deadline_seconds`；构造时要求 `≤ turn_deadline` | Host 不传 `critic_wait_seconds`，所以是 3600，与回合时限一致 |
| `taskgraph_execution_policy.py:197-208` | 交接复查：冻结请求的回合时限不能大于当前策略 | 只会放宽。之前冻结的 900 秒请求小于 3600，复查照样通过 |
| `provider_budget_guard.py:447`、`legacy_provider_slots.py:276` | 排队等模型名额的上限 = 回合建立时间 + 回合时限 | 排队最长从 15 分钟变成 1 小时。排队期间 liveness 标为 blocked，不计入卡死。行为自洽 |

**SDK 执行层怎么执行这个时限**

- `agents/execution.py` `_turn_limits` 取 `min(lifetime.max_wall_seconds, 回合起点偏移 + turn_deadline_seconds)`。
- 外层上限来自 `AgentRuntimePorts.termination_limits`，`max_wall_seconds` 是 365 天。`AgentConfig.termination_limits()` 用的是 `lifetime_wall_seconds`，也是 365 天。
- `TerminationLimits` 的默认值 900 和 `AgentLimits.turn_deadline_seconds` 的默认值 900 都在产品路径之外。编排里 4 处 `AgentLimits(...)` 都显式传了时限（grep `AgentLimits(` 全部核对过）。
- 时限只在下一次调用或下一批工具之前检查（`termination.py` `_check_common`）。已经发出去的调用不会因时限到点被打断，所以一轮最多超出约一次调用的时长。这一点以前就是这样，与本次无关。

**更内层的时限（都比 3600 短，这是设计如此）**

| 时限 | 值 | 作用 | 与 3600 的关系 |
|---|---|---|---|
| Host 思考线路的 httpx `timeout`（`service.py:1007`） | 900 | httpx 按单次读写算超时，是**空闲**超时，不是整次调用的总时长。流一直有数据就不会触发 | 只挡断线，不限制一轮 |
| Host 非思考线路（`build_provider` 默认值） | 180 | 同上，空闲超时 | 同上 |
| `provider_call_seconds` | 900 | 一次调用已交出、没结清、不到 900 秒时，不算卡死（`_provider_call_facts`） | 一次调用超过 900 秒后，回到卡死判断；距上次进展超过 `stall_seconds` 就终止。所以一次调用实际封顶约 900 秒，一轮能放 3 次以上 |
| `stall_seconds` | 180（真实跑旋钮 300） | 不在调用中、也没有进展的时间 | 两次调用之间的空档 |
| `lease_seconds` | Host 60，SDK lease TTL 30 | 编排者对尝试的租约，活着就续 | 与回合时限无关 |

**Host 更外层有没有 900 秒或 15 分钟**

- 在 `backend/deskpet/orchestration` 里 grep `timeout`、`deadline`、`900`、`wall`：只有上面的 httpx 超时、泵和停机等待（1～60 秒）、技能脚本运行器的单脚本时限，以及 `drain` 测试辅助函数。没有任何东西包住整轮或整个尝试。
- 在整个 `backend/deskpet` 里 grep `900`、`15*60`，命中的都不在编排路径上：
  - `execution/termination_budget.py`：前台主对话 ReAct 的时限链。编排不引用它（grep `termination_budget`、`FOREGROUND_ACTIVE`、`max_wall`，在 orchestration 里结果为空）。
  - `agent/turn_preparer.py`、`product_domain_sink.py`：等人确认计划的 900 秒。
  - `sdk_adapters/delegation.py`、`workflows/*`、`companion/*`：别的子系统。
- 结论：**没有更外层、更短的时限**。3600 在产品路径上生效，不存在"改了等于没改"的情况。

**一个附带变化（不挡）**

- 审阅调用"在跑但没有进展"时，原来最多等 900 秒就按被打断结束。现在最多等 3600 秒。
- 原因是 `_review_call_overdue` 用 `_critic_wait`，而 `_critic_wait` 跟着回合时限走。见建议 S4。
