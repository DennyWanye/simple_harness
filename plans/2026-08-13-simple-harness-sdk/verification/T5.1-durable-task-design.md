## 2. 核心原则

### 2.1 Port-based Architecture

SDK 实现**不包含**产品特定逻辑，所有能力通过 **Ports** 注入：

```python
# 产品代码（删除）
from ...tools.registry import get_tool_handler
from ...permissions.checker import check_authorization
from ...companion.capability import search_capability

# SDK 代码（Port 注入）
@dataclass
class DurableTaskPorts:
    """Host-provided capabilities for durable task execution."""
    
    proposal_port: ProposalPort  # LLM proposal generation
    capability_catalog: CapabilityCatalogPort  # Capability search/binding
    workspace_port: WorkspacePort  # File operations
    artifact_port: ArtifactPort  # Artifact management
    authorization_port: AuthorizationPort  # Permission checks
```

### 2.2 通用 Graph 结构

Workflow graph 定义保持产品行为，但节点实现通过 Ports 调用：

```
intake → clarify? → plan → wait_approval? → 
llm_proposal → tool_execution → completion_decision → 
(test → audit → finalize) | (fix_round → llm_proposal)
```

### 2.3 删除产品特定逻辑

**必须删除**：
- DeskPet 工具名称硬编码（`desktop_create_file`, `run_shell` 等）
- 产品特定正则规则（中文提示词匹配）
- DeskPet Companion/capability platform 直接调用
- 产品 UI/WebSocket/TTS 集成
- DeskPet 权限策略

**保留通用逻辑**：
- Graph 节点转换规则
- Proposal 状态机（convergence/gate/outcome）
- Tool 批处理和重试策略
- HITL 中断点（clarify, wait_approval）
- 完成判定逻辑（基于 receipt，不基于猜测）

## 4. 状态机简化

### 4.1 产品 proposal_state.py 结构

产品有复杂的 `ProposalStateV1`、`GateStateV1`、`ConvergenceStateV1`，包含大量产品特定逻辑。

### 4.2 SDK 简化策略

保留核心状态机逻辑，但：
- 移除产品特定的 gate 配置（硬编码工具名）
- 通过 Port 查询可用工具，而非硬编码白名单
- 完成判定基于 receipt（plan executed, tests pass, output validated），不猜测语义
