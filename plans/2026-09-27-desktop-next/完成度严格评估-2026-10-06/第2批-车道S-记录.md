# 第 2 批 车道 S 记录：格式错 + 用量说不清时审阅永久卡在预算等待

- 日期：2026-10-06
- 工作树 / 分支：`simple_harness-b2s` / `batch2-s`（基线 main 42c897f4）
- 来源：独立复核 7.3 第 1 条

## 一、核实：真卡

造局（产品同形世界）：审阅员第一次内容审查回一段不是 JSON 的话（格式错），且那次调用中转站没报用量。

红用例结果（修前）：等 40 秒，内容审查只有第一次调用；审阅工作一直是 `WAITING / BUDGET_WAIT`。

成环的原因：

1. 格式修复（第二次调用）开出前要求第一次调用先结清；第一次调用的用量说不清，结不清，抛预算错误。
2. 放行只认"这一轮没提交"（TURN_FAILED）。格式错（FORMAT_INVALID）一律要求先结清。
3. 轮询把预算错误记成预算等待，按设计永不转人工，卡死检测也把它当合法等待。
4. 按用户 2026-09-26 决定，用量说不清的调用要到收尾才按上限结清；收尾要等这次审阅的结论。

没有别的路径接住：任务结束后按上限结清那条要任务先结束；收尾按上限计入要先有根结论。

## 二、修法

文件：`sdk/simple-harness-sdk/src/agent_orchestrator/orchestrator/assurance_review_transport.py`（`_require_format_repair`）。

- 放行条件从"只有 TURN_FAILED 且预留仍 RESERVED"改成"预留仍 RESERVED"。
- 不新增规则。TURN_FAILED、格式错、导入不了、第二意见，都是同一口径：
  - 第一次调用已关闭（意图已 SETTLED / FAILED，前面已校验）；
  - 它的花费证明不了时，整笔预留按上限挂着计数，账上可见；
  - 第二次调用用它自己的预留开出来；
  - 第一次预留已不在挂着（RESERVED 以外）时照旧拒绝。
- 注释里"格式错是完成的调用，必须先结清"的理由删掉，改写成：等结清会成环，挂着按上限计数即可。

## 三、不会少算的核实

- 结清：`BudgetLedger.settle` 遇到用量不明拒绝结清，预留一直挂着（RESERVED），账户的已预留数一直含这一笔。
- 收尾：`assurance_consumers` 的收尾评估把仍 RESERVED 的主体列进按上限计入清单；收尾 READY 时调用 `settle_at_upper_bound`，按"预留与已知用量取大"计入，并发 `ReservationCountedAtUpperBound` 事件（原因 `unknown_usage`）。
- 用例实测：第一次调用预留 294912，收尾计入 294912（第二次调用实际 150 照实计入）；用量事实本身仍记作不明。

## 四、用例

新文件 `tests/orchestrator/full_target/assurance_exec/test_format_repair_unknown_usage.py`：

- 开出第二次调用（原因 FORMAT_REPAIR），第一次调用的回执是 FORMAT_INVALID、用量不明。
- 开出时：第一次预留仍 RESERVED、额度大于 0；第二次有自己的预留；账户已预留数包含两笔。
- 任务走完（COMPLETED），内容审查恰好两次，验收一次，没有审阅还在预算等待。
- 收尾按上限计入第一次调用那笔，原因 `unknown_usage`，计入数不少于预留。

共用种子 `_review_world.py`：`ReviewScript` 加一种脚本结论 "PROSE"（一段不是 JSON 的话）。

车道 Q 的用例 `test_c_assurance.py::test_a_budget_blocked_review_does_not_hold_back_later_events`：

- 它原来靠"格式错 + 用量不明"造出预算等待。修后这条路不再卡，造局失效。
- 改造法：保留同一个审阅员替身，加任务预算 40 万。第一次审阅预留约 29.5 万装得下，按上限挂着之后第二次装不下，真的预算不够，卡在预算等待（等用户加预算）。
- 断言目的不变（卡住的审阅不挡后续事件入箱，合并成同一项，不重复入箱）。
- 新增两条造局断言：卡住的原因全是 `BudgetExhausted`；内容审查只有一次调用，第一次预留仍挂着。
