## 一、缺陷 1：人裁定"已生效"后任务永远完不成

### 1. 真正的卡点（和车道 C 的诊断有一处不同）

车道 C 记录说卡在 `Receipt.from_json({})` 出错。实际跑复现用例看事件：每轮 `OperationOutcomeDeferred` 的理由是 **`OP_OUTCOME_PENDING`**，来自 `operation_outcomes._execution_sources`：

```python
if action is None or link is None or action["state"] != "SUCCEEDED" or not action.get("receipt"):
    raise OperationOutcomeError("OP_OUTCOME_PENDING")
```

"成功了但没有回执"被当成"等一等"，而回执永远不会来。`Receipt.from_json` 根本没被执行到。此外 `_has_pending_operation_completion` 把这项效果算作合法等待，所以卡死检测也不接手。

### 2. 二选一的裁决：写一份"人裁定回执"（选项一）

两个候选：
- 选项一：人裁定时同事务给动作写一份具名的"人裁定回执"，结果审阅读到的是它。
- 选项二：结果审阅遇到"人已裁定"直接按裁定记效果结果。

选**选项一**，理由：
1. 效果"已验收"的读路径（`completion_status._effect_ready`、`_assured_outcome_use`、`accept_operation_outcome`）全部要求：结果审阅绑定 + 正式审阅记录（审阅员通过或人裁决通过）+ 使用证书 + 验收。选项二要"直接记结果"，就得在这条读路径里再开一个"人裁定"分支——第二条完成路径，违反"同一件事只留一条路径"。
2. 选项一只改"事实从哪来"：回执字段身份抄动作行，过的是和连接器回执同一道 `receipt_mismatch` 门；之后准备审阅、审阅员判、使用证书、验收、步骤完成全部复用现有代码，一行不加。审阅员判不下来 → 走现有 `_ask_person_to_adjudicate_outcome` 问人 → 使用证书验收，正是 Assurance 原计划"人裁决 → 使用证书路径验收"的那条路。
3. 符合核心思想：Harness 只负责如实呈现事实（谁、何时、凭什么裁定；没有执行过任何登记检查），够不够由审阅员（LLM）判。不写"人裁定即通过"的硬规则。
4. 规划器侧读操作台账（`planning_operations._classify`）对 SUCCEEDED 动作要求"有匹配的成功回执"，人裁定回执自然满足，规划器看到的是 APPLIED；选项二下规划器会一直读到 `success_without_matching_receipt`。

连接器的回执解读器（`FilePublishReceiptAdapterV1`）对人裁定回执不适用：它查连接器台账、读文件哈希，而这个局面下台账说的就是"没发出去"（回执丢了）。所以人裁定回执不过解读器，观察事实就是裁定本身——`milestone_source=HUMAN_RULING`、`executed_check_ids=[]`，如实告诉审阅员"没人跑过登记检查，是人看过"。观察到的里程碑写成效果要求的那个里程碑（读路径按它匹配效果槽），来源字段说明它是人裁定出来的。

### 2. B 口径做了什么

`assurance_consumers._evaluate_locked`：每个根先读完所有必需效果的当前状态；根没满足时分两类——**只差结果不明的效果**（内容已就绪、每项必需效果不是 `ACCEPTED` 就是 `RECONCILIATION_REQUIRED`，且至少一项不明）记进 `blocked_root_occurrences`、不加 `ROOT_SCOPE_UNMET`，不明效果照旧进 `unknown` → `_drain_decision` 报 `BLOCKED_UNKNOWN`（原因 `EFFECT_UNKNOWN`）；其余（内容没好、效果还在等申请单 / 审阅 / 执行）照旧 `ROOT_SCOPE_UNMET`。判断抽成纯函数 `unmet_only_by_unknown_effects(status, effect_states)`。没有写第二条 `BLOCKED_UNKNOWN` 判断——仍只有车道 B 之后那一处 `_drain_decision`。

新用例 `test_a_root_short_only_of_an_unknown_effect_is_blocked_unknown_not_scope_unmet`（纯函数）：正例两种；内容没好、效果在等审阅 / 申请单 / 执行 / 范围过期、没有必需效果、全部已验收都不是。

### 3. 终审开门条件与计划 F06 / §7.2 的核对——**不一致，偏差单**

计划 §7.2：根结论（业务要求已满足）可先记历史，任务仍 ACTIVE，`assurance_closeouts.state=BLOCKED_UNKNOWN` 等效果真实收敛。F06："root 满足与 closeout 分开；root 后 UNKNOWN/hold/退出正确"。

代码里把"根结论"挡在效果之后的有两处，不止 `root_review_ready`：

| 位置 | 现状 | 后果 |
|---|---|---|
| `hierarchical_dispatch.root_review_ready` | 每个根 `read_occurrence_completion(...).effects_ready` 才开终审 | 首次发布结果不明时终审不开，根结论不形成，收尾 `NOT_READY / ROOT_RESOLUTION_MISSING`，且不写收尾行（`_write_locked` 无根结论不插行） |
| `event_handler._decide_actions` | 根结论形成后，判定（`judge_mission`）要等每个要求动作 SUCCEEDED；有动作不在"可交接 / 已成功"就原地等 | 即便终审先开了，`MISSION_JUDGMENT_MISSING` 仍让收尾 `NOT_READY` |

所以 B 口径下 `BLOCKED_UNKNOWN` 能到的局面是：根结论与判定都已形成、**之后**才出现结果不明（A07 的全任务 UNKNOWN 动作；或改要求后再发布结果不明）。车道 C 那条用例（首次发布结果不明、终审没开）在这两处不改之前到不了 `BLOCKED_UNKNOWN`，**xfail(strict) 保留**，理由改写成上面这段。

要让它绿，得重排终态顺序：终审不等效果、判定不等要求动作 SUCCEEDED（判"业务要求已满足"只看根有效性，效果交收尾）。这改的是终审 / 判定 / 收尾三处的职责分工，车道 C 的"结果不明时终审没有开"断言也要反过来。这是计划与代码的冲突，不先斩后奏；由主会话 / 用户定：
- 选项 A：认可现状，F06 口径改为"效果不明 = 终审未开 / 判定未形成 → NOT_READY，仍不收尾"，xfail 用例删除或改写；
- 选项 B′：按 §7.2 重排（终审与判定不等效果），本车道或下一批做，顺带改车道 C 用例。

"不收尾"这条保证两种选项下都成立（`test_an_unknown_publish_result_holds_the_mission_open` 守着）。
