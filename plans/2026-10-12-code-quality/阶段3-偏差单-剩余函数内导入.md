# 阶段 3 偏差单：剩余函数内导入的目标与循环处理

日期：2026-10-14　分支 cq-phase3（73df82c76）

## 计划原文

- 3.3：会成环的逐环处理，共用部分抽到下层模块或改成参数传入，不留延迟导入。
- 3.5：剩余函数内导入 ≤ 100（后端加 SDK），每处注释写原因。

## 实测现状（3.2 上提做完后）

函数内导入：3044 → 512（后端 1531 → 345，SDK 1513 → 167）。剩余按原因分：

| 原因 | 后端 | SDK | 说明 |
|---|---|---|---|
| 上提会成环 | 79 | 113 | 约 140 对模块互相依赖；四个包入口再导出子模块只占一小部分（估算瘦身后 233 处成环路径只降到约 208） |
| 重型或非轻量第三方包 | 50+7+6 | 7 | 语音识别、图像、浏览器、表格等；上提会拖慢启动（启动耗时门已拦过一次） |
| 可选依赖（try ImportError） | 35 | 3 | 没装时走降级分支 |
| 测试整个换掉模块（往 sys.modules 塞替身） | 44 | 9 | 上提后替身不生效 |
| 测试钉住的导入隔离约定 | 15 | 2 | 测试断言导入某入口时不得加载某些模块 |
| 代码里明说按需加载（本行、上方注释或整个文件） | 31 | 2 | 原作者写明的懒加载边界 |
| 平台专用、名字冲突、打桩别名冲突 | 约 10 | 约 15 | |
| 目标不存在（死代码路径） | 7 | 0 | 导入不存在的模块或名字，留给阶段 8 删死代码 |

另外有些文件不在上提范围内（禁区、脚本目录），它们的函数内导入也算在 512 里。

## 冲突

1. 降到 ≤ 100，就必须把"重型包、可选依赖、测试替身、导入隔离、作者声明的懒加载"这些也上提。这样会拖慢启动、没装可选包时导入就失败、测试契约被破坏。这违反整治计划的总原则"行为不变"。这几类合计约 300 处，它们本来就是函数内导入的正当用法。
2. 3.3 要求循环全部重构掉。剩余约 140 对互相依赖的模块，多数在 SDK 核心（执行单元、提交服务、事件处理）和 Host 执行层。全部重构属于大规模搬代码，风险与阶段 5（拆大文件、分层）重叠：阶段 5 拆文件时，很多环会自然消失或换形状。

## 选项

- **A 照原文**：循环全部重构，并强行降到 ≤ 100。会改变行为、破坏测试契约。不可行。
- **B（建议）**：
  - 3.3 只处理结构性根因：(a) 四个包入口（SDK 执行存储包、Host 执行包、工作流存储包、工具目录包）不再再导出会引起环的重型子模块，调用方改从子模块直接导入；(b) 互相依赖的模块对，凡能把共用的常量、类型、小函数下沉到下层模块就下沉，限时 2 个工作日；剩下的留在函数里，注释写"循环依赖：A ↔ B，待阶段 5 拆分时解开"，并把清单交给阶段 5。
  - 3.5 目标改成：剩余每一处函数内导入都带固定口径的原因注释（可选依赖 / 重型包 / 平台专用 / 测试替身 / 导入隔离 / 按需声明 / 循环依赖 / 死代码待删）；棘轮锁住总数，以后只降不升；"循环依赖"一类单独计数，阶段 5 结束时须 ≤ N。
- **C 只加注释**：不做任何循环处理。不符合 3.3 的本意。

## 请裁决

1. 选 A、B 还是 C；
2. 如果选 B，"循环依赖"一类在阶段 5 结束时的上限 N 定多少；3.3 的限时是否合适。

## 裁决（2026-10-14，独立裁决员，模型 Opus 5.5）

选 B，并做三处修改：

1. **环的清单分开交。** 阶段 5 只拆 SDK，后端的 79 处环在执行层和各存储类里，归阶段 6。SDK 的清单交阶段 5，后端的交阶段 6。
2. **包入口不再再导出子模块，按删除处理。** 这等于删一条导入路径（总原则第 9 条）。动手前在全仓库（Host、测试、脚本）查这四个包入口再导出的名字有没有人用；删除单独提交；SDK 部分随阶段末 opt 版本发出，Host 同步改钉版。
3. **计划里的数字统一。** 第 1.1 节、阶段 3 第 3.5 条、附录指标表统一改为"棘轮锁总数只降；循环依赖类单独计上限"。

上限与限时：

- 循环依赖类：SDK 在阶段 5 结束时 ≤ 30；后端在阶段 6 结束时 ≤ 20；合计 ≤ 50（现在 192）。阶段 5、6 先原样搬代码时环可能临时变多，只在阶段末考核。
- 3.3 限时 2 个工作日合适；3.4 另算。
- 数据抽查 15 处，归类合理，未发现数据问题。

已落实：整治计划升为 2.4 修订（第 1.1 节、阶段 3、附录指标表）。
