# 交接：chinzy（TokenSeller）中继连不上阿里云，Realtime 与文字路线同时失败

日期：2026-10-25。来自：Simple Harness SDK 侧。给：chinzy / TokenSeller 运维与开发。
本文可独立转发。不含任何密钥。

## 1. 一句话

中继本身在线、能签发临时凭据、WebSocket 能接上；但中继回"上游不可用"，连不到阿里云（DashScope）的 Qwen 模型。文字路线同样失败。请查生产中继的阿里云凭据池和实时语音的工作区配置。

## 2. 我们怎么测的

客户端：`simple-harness-service-sdk` 0.3.12（源码 `47f372a`）自己的 `TokenSellerHttpsCredentialMinter`、`RelayWebSocketTransport`、`RelayControlCodec`，控制协议 `tokenseller.realtime-control/2026-08-28.3`，SDK 协议 `simple-harness-realtime/1`。没有手拼协议。
中继地址：`https://chinzy.com`。时间：2026-10-25 00:50～01:40（本机时间）。

| 步骤 | 请求 | 中继回复 | 耗时 |
|---|---|---|---|
| 1 铸造凭据 | `POST /v1/realtime/qwen/client_secrets`，按冻结 schema 的完整请求 | 200；`websocket_path=/v1/realtime/qwen`，`expires_at` 60 s 后；capability 里 `tool_calling: true`、`truncate_output: false`、`resume: false` | 350～570 ms |
| 2 连接 | `wss://chinzy.com/v1/realtime/qwen`，`Authorization: Bearer <临时凭据>` | 握手成功 | 340～390 ms |
| 3 开会话 | `tokenseller.session.open`（带 control_version、sdk_protocol_version、correlation、capability_digest） | `{"type":"tokenseller.error","code":"unavailable","retryable":true,"fatal":true,"message_class":"upstream_unavailable"}` | 约 420 ms |
| 重试 | 同上，1 小时内 10 次 | 全部同样回复 | 同上 |

旁证（文字路线，同一把 API key）：

| 请求 | 回复 |
|---|---|
| `GET /v1/models` | 200，目录正常，含 `ali-qwen-flash`、`ali-qwen3.7-flash` 等 |
| `POST /v1/chat/completions`，`model=ali-qwen-flash`，一句话 | **503** `{"message":"No healthy route for ali-qwen-flash","error":"Service Unavailable"}`，933 ms |

两条路线一起失败，说明问题在"中继→阿里云"这一段，不在客户端、不在这把 key、不在实时协议本身。

## 3. 从中继源码看可能的原因

分支 `origin/codex/archive-main-before-live-sync-20261019`，文件 `apps/api/src/modules/relay/realtime/realtime-native.gateway.ts`，函数 `connectProvider`。`upstream_unavailable` 只会从三处抛出：

1. 环境变量 `REALTIME_QWEN_WORKSPACE_ID` 为空或不匹配 `^[a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?$`（第 652 行附近）。**这一条在连阿里云之前就判掉，回包很快。**
2. `credentials.listHealthyForProvider(DASHSCOPE_PROVIDER)` 返回空——凭据池里没有健康的 DashScope 凭据（第 664 行附近）。
3. 对每个凭据 `dialProvider` 都失败，并逐个 `recordFailure`（第 674 行附近）。

本次回包只要 420 ms，更像第 1 或第 2 条，不像拨号超时。文字路线的 503"No healthy route"与第 2 条一致：DashScope 这一家的凭据被整体标为不健康或为空。
另注意到最近一次提交"fix(deploy): move relay to verified Singapore egress"，请顺手核对迁移后环境变量与凭据是否完整带过去，以及新加坡出口到 DashScope `cn-beijing`（capability 里 `region: cn-beijing`）的连通性。

## 4. 请检查

1. 生产中继进程的 `REALTIME_QWEN_WORKSPACE_ID` 是否设置、格式是否合规。
2. 凭据池中 provider=DashScope 的记录：是否存在、是否被标为不健康、失败计数、最近一次失败原因；阿里云侧 key 是否过期/禁用/额度用完。
3. 若凭据正常，再看中继日志里 `dialProvider` 对 DashScope 的拨号错误（DNS、TLS、401/403、超时）。
4. 修复后请回复：改了什么、何时生效、是否需要我们这边换 key。

## 5. 修好的判定（我们这边会复验）

1. `POST /v1/chat/completions` `model=ali-qwen-flash` 能回话（不再 503）。
2. Realtime：铸造 → 连接 → `tokenseller.session.open` 后收到 `tokenseller.session.created`，随后 `session.update` 收到 `session.updated`。
3. 发一段 16 kHz PCM 录音，能收到转写与音频回复。

## 6. 接下来会向中继提的需求（提前知会，不是本次故障）

我们正在做"语音里让模型调用工具（函数调用）"。阿里云官方文档确认 Qwen3.5-Omni-Flash-Realtime 支持 `session.update.tools` → `response.function_call_arguments.done` → `conversation.item.create(function_call_output)` → `response.create`。需要中继：

1. `session.update` 里的 `tools` 字段原样转发给上游，不剥、不改；上游回的 `session.updated` 原样回给客户端（里面会多一个 `tools` 字段）。
2. `response.function_call_arguments.delta/done`、`response.output_item.added/done`（item 为 `function_call`）、`conversation.item.created`（item 为 `function_call_output`）原样下发。
3. 客户端在会话中途再发 `session.update`（改 instructions）和 `conversation.item.create`（文本 message）时原样转发；是否被上游接受由上游决定，中继不要先拒。
4. 这些是否已经支持，请回复一句；若中继协议清单 `tokenseller-realtime-control-2026-08-28.3` 对客户端事件有白名单，请告知白名单内容。

线路恢复后我们会用真实录音跑完这四项并把结果回传。
