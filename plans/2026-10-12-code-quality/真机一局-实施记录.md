## 二、两个缺陷

### 缺陷 1：主对话用量环永远没有实测

- 现象：每轮的实测用量写进了历史表（`session_context_usage_history` 有两条），但公开状态一直是"只有绑定"。
- 根因：主对话每轮一个执行会话，没有会话绑定记录，状态按纪元 0 建立；运行绑定的纪元是提供方配置版本 1。归并函数把纪元不等的样本当作旧纪元丢掉。单元测试用的是假读取器，没测到真库这一段。
- 修复（Host，77d5ec215）：归并时样本纪元比状态新，先把状态跟到样本纪元（绑定信息取样本自带的提供方与模型），再计入实测；纪元更旧的样本仍不计入。改绑定会在同一事务推进状态纪元，所以"样本更新"只出现在没有绑定记录的会话。查询时从历史重建状态走同一个函数，同样修好。
- 证明：新测试 `tests/memory/test_context_usage_binding_epoch.py` 三条（真库：新纪元样本计入、从历史重建也计入、旧纪元样本不计入），改前两条失败；用量相关测试 11 个文件全过。

### 缺陷 2：编排规划每轮被流解析器拒收

- 现象：规划调用 7 次全部失败，报 `invalid chat stream: id changed or is not a string`。
- 根因：本机中转现在在一次流式回复里交替用两个 id：正文片段挂临时 id `chatcmpl-wb`，思考、工具调用、空片段挂真 id（用 `probe_ids.py` 直接抓流证实）。SDK 流解析器原规定 id 变了就拒收。主对话不走流式，所以不受影响。
- 修复（SDK opt.193）：一次 HTTP 响应就是一次回复，id 只是标签，按第一次出现的记账，之后改名不拒收；模型名改了仍拒收，id 或模型名不是字符串仍拒收。改坏清单加 SM-34（已验证能抓到）。
- 独立核验：PASS（`.local-test-evidence/2026-10-18/taskgraph-gate/review-opt193.md`，回执 `review-235942.json`）。下游只把这个 id 当日志与调用记录里的引用，用量对账用我方自己的请求 id。
