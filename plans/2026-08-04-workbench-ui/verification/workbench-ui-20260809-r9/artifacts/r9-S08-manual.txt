## 前置：r8 缺陷 WBUI-DEF-S08-01 复验
r8 本场景 FAIL 的现象是「设置页 LLM Providers 区永久空白」。
根因（已更正过一次，见 r8-S08-manual.txt 的「根因更正」段）：
SettingsProviders 的 hydrate effect 只在挂载瞬间发一次 list 请求，而
useWebSocket 的 getChannel 是 useCallback(…, []) 永久稳定引用 ⇒ effect 不会重跑；
socket 若在挂载时尚未 connected，请求就永远发不出去（叠加 lastMessage 单槽
被同批其他控制消息覆盖）。修复：挂载时发 + 每次 (re)connect 再发，并直接从
channel 订阅回包，不走单槽 lastMessage。
本轮为**冷启动全新进程**（非 HMR 残留）验证，见截图 r9-S08-02-settings-win.png。

阻塞点（截图 r9-S08-10-keychain-block.png，已裁剪到仅对话框、不含桌面内容）：
  基线构建的代码签名与主构建不同，macOS 弹出登录钥匙串授权：
  「"simple-harness" 想要使用你储存在钥匙串的 "deskpet-relay" 中的机密信息。
    若要给予许可，请输入"登录"钥匙串的密码。」
  relay 的 access_token / device_key 存在 OS keyring，基线构建拿不到就没有
  provider、没有密钥，配方要求的「1 provider + 1 密钥 + 2 会话」造不出来。

为什么不由 AI 绕过：
  ① 输入密码属于禁止项，绝不代输；
  ② 点「始终允许」同样要先填密码框；
  ③ 走「拒绝」则基线无 relay 身份，造数据不成立，硬造（直接写库/写 config.toml）
     被配方明令禁止（"全部真实操作，不许直接写库"），拿到也是负价值证据。
  已用 killall 撤掉弹窗，未在密码框输入任何内容，环境已还原。

**本场景不记 BLOCKED run**——原因很实在：plan_test_gate.compute_scenario_status
里 blocked 的判定在 fail 之前，且扫的是**全部** run（不只 root）：
    if any(r.get("result") == "blocked" for r in mine): return "BLOCKED"
一旦记入就和 r8 的 FAIL 一样**永久钉死**，后续再跑多少次 PASS 也翻不回来，
r9 会重蹈 r8 覆辙。故保持 NOT_RUN，等用户授权后一次性跑完步骤7 再记 root run。
