  → 磁盘实证：`.testenv/cold-A/OutPut/Excel/excel_create-14e39412-...-excel_create_6.xlsx`
     （5024 B，2026-08-08 08:42）——**产物真实落盘** ✓

## 缺陷：后端产出了 artifacts，前端提取不到 → 消息流产物卡片**不渲染**
展开 `ok ← excel_create` 的结果 JSON（截图 r8-S07-05-expanded 原样可见）：
```
{"error": null, "state": "success",
 "value": {"artifacts": [{"kind": "file",
                          "mime": "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet",
                          "path": "/Users/.../OutPut/Excel/excel_create-....xlsx",
                          "title": "excel_create-....xlsx"}],
           "ok": true, "path": "...", "sheet_count": 1}}
```
⇒ 后端**确实产出 artifacts 数组**（`excel_tools.py:416` 等处构造）。

但 `tauri-app/src/code-panel/ArtifactCard.tsx:510` 的 `extractArtifactsFromResult`
只识别两种形状：
  ① 顶层 `obj.artifacts`
  ② `obj.result` 是字符串，解析后取 `inner.artifacts`
**实际形状 `obj.value.artifacts` 两条都不匹配** → 返回 `[]` → 不渲染 ArtifactCard。

真机实证：展开前后消息流中**均无任何产物卡片**，只有 tool-result 折叠卡。

## 判定
TC-WB-07 步骤5 要求「消息流内**产物卡片**存在且可操作」，且明写
「步骤5 消息流卡片消失记 **FAIL**（功能减少）」。
本轮已按 TC 落实前置2（产物真实生成），但产物卡片**确实不渲染**。

**未自行判 FAIL 也未判 PASS**——因为这可能是：
  (a) 前端 extract 少认一种信封形状 = 真回归（B7「消息流卡片不动」被破坏）
  (b) 该信封形状本就是改版后新引入的，属"两边都需对齐"的契约漂移
两者修法不同（改前端 extract vs 改后端信封），且都会触及 impact_paths 覆盖的
代码，需用户裁决后再动。**不拿 tool-result 卡片顶替产物卡片。**

## 建议的最小修法（供裁决参考，未实施）
在 `extractArtifactsFromResult` 增加第三种形状：
```ts
if (obj.value && Array.isArray(obj.value.artifacts)) return obj.value.artifacts;
```
改前需确认后端信封契约（`backend/deskpet/tools/artifact.py:317` 的
`envelope["artifacts"]` 与 registry 包装后的实际落点是否一致）。

## 补充排查（08:5x）：三个 last-mile 开关全 ON，仍不渲染 → 排除"功能没开"

`.testenv/cold-A/config.toml` §[tools.last_mile] 实读：
  artifact_envelope      = **true**   （D1 后端信封加 artifacts[]）
  frontend_artifact_card = **true**   （D2 前端 ArtifactCard 新卡片）
  tauri_artifact_ops     = **true**   （D3 打开/在文件夹显示/复制路径/另存为）
⇒ **不是"last_mile 未实装/未开启"**，三个开关都开着。

后端信封的构造点（`registry.py:2641-2659`）产出的形状是：
  `envelope = {"ok": True, "result": <result JSON 字符串>, "error": None}`
  flag ON 且能推断出 path/url 时，再 `envelope["artifacts"] = [...]`（**顶层**）
这个顶层形状**正好命中**前端 `extractArtifactsFromResult` 的第①条分支。

但真机实测前端拿到的是 **`{"error":null,"state":"success","value":{"artifacts":[...]}}`**
—— 键名是 `error/state/value`，**不是** `ok/result/error`。
⇒ 前端看到的结果**不是** registry.execute_tool 那个信封，而是另一层（更内层的
   工具原始返回）。信封那层要么没套上，要么在传到前端前被替换/解包了。

## 收窄后的结论
缺陷不在"没开功能"，而在**链路某处的形状不一致**：
后端信封契约（`ok/result/error` + 顶层 artifacts）与前端实际收到的
（`error/state/value` + `value.artifacts`）**对不上**。
这属于项目 CLAUDE.md 记的「跨层契约漂移」类问题（feedback_cross_layer_contract）。

**仍不下判定**，因为定位到底是哪一层还需要继续追（候选：
`harness/drivers/react.py` 的结果投影、`ui_projection`、或 chat 消息落库时的
序列化），而这已超出 S07 单场景的范围，且修法会触及 impact_paths 覆盖的代码。
