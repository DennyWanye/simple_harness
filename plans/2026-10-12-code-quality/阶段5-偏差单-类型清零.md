# 阶段 5 偏差单：5E 类型检查清零中遇到的四件事

日期：2026-10-16。范围：SDK 全部源码，mypy 起点 539 个错误、121 个文件（计划写的 514 是拆分前的数）。

## 已经在做、不需要裁决的部分（供核对口径）

只改类型、不改运行逻辑，改动后用 `scripts/code_quality/ast_equiv.py --typing-only` 证明：

- 去掉 `cast(...)`、所有 `if TYPE_CHECKING:` 块和导入；
- 函数内的「x: T = v」算成「x = v」，只声明的「x: T」去掉；
- 之后与改前的语法树逐字相同。

用到的写法有这几种：

- 参数或返回值的注解改准确（如 `Mapping[str, object]` 改成 `Mapping[str, Any]`，注解过时的改成实际类型）；
- 调用处加 `cast(...)`；
- 混入类在 `if TYPE_CHECKING:` 里写组合类提供的方法、属性存根；
- 同一个局部变量先后装不同类型：在第一次绑定处声明更宽的类型；
- 少数地方给局部变量改名。改名不能被上面的工具证明，逐个人工核对，并在实施记录里列出文件。

## 需要裁决的四件事

### 一、「没判空」一类（约 100 处，清单见附件 none_list.txt）

**现象**：值的类型是 `X | None`，代码直接取属性或当参数传（如 `store.get_intent(id).agent_id`）。

**现在的运行行为**：值真为 None 时抛 AttributeError 或 TypeError，不是模块自己的领域错误。

**选项**：

- A. `cast` 成非空类型。只改类型，行为不变；掩盖了"可能为空"这件事。
- B. 显式判空，抛本模块已有的领域错误（如 AssuranceError、StoreConflict）。只改变"本来就会崩"的那条路径的报错类型。
- C. `assert x is not None`。AttributeError 变成 AssertionError，`python -O` 下失效。
- D. `# type: ignore[union-attr]` 加原因注释。

**我的建议**：逐处看。

- 前面几行刚写入或刚校验过、确实不可能为空的，用 A，并加一句注释说明为什么不会空。
- 其余的用 B，错误码沿用该模块现有的"来源不可用"一类错误码，不新增错误码。
- B 的改动单独提交，跑相关测试；实施记录逐处列出。

### 二、真缺陷：持久任务工作流引用了不存在的属性

**位置**：`simple_harness/workflows/durable_task/nodes.py`

- `call.effect_type`（批准后发放授权时）；
- `call.args_hash`（整理工具结果时）。

**问题**：`PreparedToolCall` 是只有 4 个字段的冻结数据类，没有这两个属性。走到这两处就抛 AttributeError。

**影响**：整理工具结果那一处，只要有一次工具调用就会走到。测试没有覆盖这条路径。

**选项**：

- A. 本阶段修：先补一条能复现的测试；按语义补字段，或改为从已有字段算出来。
- B. 本阶段不修：写 `# type: ignore[attr-defined]`，原因注释指向缺陷记录，另开任务。

**我的建议**：B。修它要定这两个字段的语义（效果类型从哪来、参数哈希怎么算），属于功能修复，不是类型整治。用一个单独的任务卡片转交，附复现路径。

## 独立裁决（2026-10-16）

裁决员只读代码，没有改代码、没有跑测试或 mypy。抽查位置以当前工作区为准（行号可能与附件差几行）。

### 一、「没判空」：同意建议的大方向，判别口径收紧如下

**结论**：A 与 B 并用，C、D 都不用。但"确实不可能为空"要有代码证据，不能凭经验判断。按下面四类分：

1. **本函数里已经排除了 None，只是 mypy 看不出来**：用 A。注释写明是哪一行的哪个条件排除的。
2. **构造契约保证非空**：用 A。注释写明契约出处。例：读取器带了现行授权，读出的行一定填 `permission`（assurance_reads.py 字段说明）。
3. **按编号从库里读、编号来自持久数据或外部输入，函数里没有核过"存在"**：用 B。错误码沿用本函数里最近的同类 raise；没有就用本模块已有的同类错误码。"库里应该有"不算不可能为空的证据。
4. **JSON 值联合里的 None**：这是 JSON 的 null，不算"没判空"。前面已有 isinstance 校验的用 cast；没校验的属于形状校验，沿用本模块已有的格式错误码。附件里 graph_repair.py 那一条（生成器传给 Sequence）跟空值无关，按普通注解问题处理。

**理由**：抽查了 10 个文件，共 13 处。其中 7 个文件属第 1、2 类：
- assurance_check_policy（第 94 行的二选一校验保证 scope 非空）
- carried_review（stored 为 None 时已经 continue，隐含 task 非空）
- scoped_content_review（同上，frozen 为 None 隐含 result 为 None）
- runner.py（已有 `is not None` 判断）
- taskgraph_execution_view、tools/executor（前面已经 isinstance）
- assurance_check_use（读取器带授权，permission 必填）

属第 3 类或证据不足的有三处：
- assurance_review_import 的 `get_intent`：编号来自外部提交的行，没有核过存在。
- mission_lifecycle 的 `get_mission`。
- tool_gateway 的 workspace：评审绑定或证据工具会让 workspace 是 None。"评审绑定只开放四件工具"的准入检查不在本函数里，本函数里找不到证据。这里要逐处核：准入检查能在调用前的代码里指认出来，就用 A；指认不出来，就用 B，抛 WorkspaceError。注意：本函数的 `except WorkspaceError` 会接住它并转成拒绝回执，这就是下面说的控制流变化。

因此 B 的实际数量应该远小于 100。统一抽一个"取非空"的公共函数本阶段不做：它会新增公开接口，也会让改动无法用 `--typing-only` 证明。

**执行条件**（阻断级）：
- 每处 B 都要查调用链上有没有 `except <该领域错误>`。原来的 AttributeError 会一路崩上去；改成领域错误后，可能被上游接住，转成拒绝、跳过或 continue（例如 carried_review 外层接 OperationCompletionError 后会 continue）。这种控制流变化在实施记录里逐处写明。
- 不许新增错误码。错误码、状态码字面量属禁区。
- B 单独提交，只跑改动文件对应的测试。不跑全量回归。
- B 落在工作流节点或路由函数里的，同样会改清单哈希，按第四件处理。

### 二、PreparedToolCall 缺属性：同意 B，本阶段不修，转交

**结论**：选 B。两处各加一个只针对该行的 `# type: ignore[attr-defined]`，原因注释指向转交任务。另开任务卡片。

**理由**：核实属实。state.py 的 `PreparedToolCall` 只有 4 个字段：stable_call_id、tool_name、arguments、raw_arguments。全 SDK 也没有别的同名类可以改指。
- nodes.py:777 的 `call.effect_type`：批准后，只要有一个调用就会崩。
- nodes.py:932 的 `call.args_hash`：只要有一个工具结果就会崩。

补字段要先定语义：效果类型从目录还是从提案来？参数哈希按哪种规范化算？这是功能修复。而且崩溃是直接抛错，不会悄悄写坏数据，推迟不扩大损害。

**执行条件**：
- 任务卡片必须写明三件事：
  - 复现路径（上面两条触发条件）；
  - durable_task 已经在 Host 产品里注册（backend/host/startup_workflows.py 注册了 "durable_task"），这是在用的产品代码，不是死代码；
  - 动手前先确认"工作流线删除"第 3 片会不会整体删掉 durable_task。会删就关掉卡片，不修。
- 不许为了让测试过而写固化错误行为的测试。
