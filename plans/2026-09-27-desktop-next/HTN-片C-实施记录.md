# HTN 精简 片 C 实施记录（规划包与提示词收口）

- 时间：2026-10-02
- 依据：`HTN-后续-方案.md` 第 4 版 片 C；`HTN-精简审计-2026-10-01.md` 第二节第 6、7、8 条，第三节第 3、6、7 条
- 上一片：`HTN-片B-实施记录.md`（Host 钉 SDK opt.120）

## 一句话

规划器收到的东西只剩"一份提示词 + 一份只组装一层的规划包"：方法合成器这个角色连同它的
九个提示词版本、重问机制全部删除；规划器、分层执行者、根审阅员各只留一份提示词；"允许
哪些决定"只有一张表；规划包不再把同一批事实发两遍，一步失败的完整记录只放在待处理的
修复请求里。

## 做了什么

### 1　方法合成器角色删干净

片 A 把"现有做法都不合适时提一个新做法"交给规划器之后，合成器已经没有运行路径，但角色
本身还留着。这一片删掉：

- 提示词 `method-synthesizer-v1`～`v9`（`runtime/role_templates.py`）；
- `planning/htn/synthesis.py` 整个模块。里面仍在用的两件事——给规划器准备"写做法的材料"、
  把规划器提的做法交给注册协议——改写成 `planning/htn/method_proposals.py` 里的两个函数
  `build_context` 与 `admit_proposal`。随角色一起删掉的：重问反馈（"上一次回复没通过解码"
  "被注册协议拒绝"两段话）、"哪些拒绝码值得再问一次"的分类表、专给合成器用的字段
  （输出标签、提示词版本、两种反馈）、允许调用方改写作者的 `author_override`；
- 受理入口此前把规划器已经解码过的做法重新拼成文本块再解析一遍，现在直接接解码后的对象；
- 各处角色清单里的名字（任务来源登记、ARP 来源种类、执行图视图、规划请求判断）、前端
  执行图里"设计步骤"这个角色显示分支；
- 注册协议里只给"步骤数超限可重问"用的原因标记（`AdmissionProblem.reason`）。

### 2　提示词每个角色只留一份

- 规划器：只登记 `planner-hierarchical-v15`（内容即片 A 重写、片 B 增补的那一份，本片按
  新规划包改了"请求包怎么读"几段）。删 v1～v13 的 `_revise` 历史链与六层叠加。
- 分层执行者：只登记 `worker-hierarchical-v5`，写成完整的一份，不再从平面执行者经四层
  `_revise` 拼出来。文字与改写前逐字相同。
- 根审阅员：只登记 `root-reviewer-v5`，同样写成完整的一份，文字逐字相同。
- 版本表 `HIERARCHICAL_PLANNER_VERSIONS`、`…_BY_PACKAGE`、`hierarchical_planner_versions`
  删除；配对检查只认"当前规划包版本 + 当前提示词版本"这一对。规划器模板的选用不再读
  部署钉的版本。
- **规划请求末尾挂着的一段英文"协议提醒"删除。** 它每次都追加在规划包后面，讲的是旧协议
  字段、"第 7 版包""第 10 版提示词"、已经删掉的"声明受阻"，等于第二份提示词。其中仍成立的
  两条写法（原样重做时失败尝试编号怎么写、运行环境受阻的原因怎么写）并进唯一的那份提示词。
- 钉历史版本哈希的测试与基线删除（`fixtures/h0/prompt-digests.json`、
  `test_planning_decision_prompt_v8.py`、各文件里的 `FROZEN_*`）；`test_output_port_claims.py`
  的冻结表只留平面模式的几份和分层执行者当前这一份。

改写前后对全部已登记提示词拍了哈希快照：170 份 → 140 份，删掉的正好是上面 30 份历史版本，
其余 140 份逐字未变。

### 3　"允许哪些决定"只有一张表

- 四层叠加的表（H1 → H3 → V14 → H4，每项带"能解码 / 能受理 / 能执行"三个开关）删除，
  只留 `ENABLED_DECISIONS`，直接由"决定类型""修复种类"两个枚举得出：能解码的就是能执行的。
- **"声明受阻"（DECLARE_BLOCKED）与"修复里的升级问人"（REPAIR/ESCALATE）连类型一起删。**
  片 A 之后它们停在"只能解码"——规划器写了会被解码、落库、然后被拒。"卡住了"只有一种说法
  （问用户），留一个永远被拒的入口没有意义。契约、JSON Schema、受理、适配器、事件处理里
  的分支一并删除；"运行环境受阻"是基础设施事实、带恢复条件，保留。
- 规划包里的清单此前先按第一层生成、另一处再按第四层覆盖；现在只生成一次。
- 规划授权策略三个历史版本号并成一个，允许的种类就是这张表。
- 重试预算里恒为 0 的"合成次数"字段删除；规划预算视图里的 `synthesis_remaining` 改名
  `method_proposals_remaining`。

### 4　规划包只组装一层

此前是三层：旧收集器生成一份映射（`plan`、`method_library`、`applicability`、`facts`、
`operators`、`planning_rejected`……）→ 转换层从映射转出九个视图 → 叠加层把两者**一起**发给
模型。现在：

- `orchestrator/planner_views.py::read_planner_package` 读一遍库、计划、做法库、证据快照，
  直接得到模型看到的每一行；`planning/htn/planner_package.py::assemble_planner_package`
  是纯函数，负责协议字段、可引用对象、条数上限与整包大小上限。`planner_package_v1.py`
  （转换层、视图类、编解码器）整个删除。
- 顶层只剩：协议字段（`planning_protocol`、`planning_subjects`、`visible_refs`、
  `previous_feedback`、`decision_limits`）、九个视图 `views`、待处理的请求
  （`repair_requests`、`human_answers`）、每个待定目标的工作材料（`method_selection`、
  `method_proposal_contexts`）、候选清单（`sharing_candidates`、`successor_types`、
  `compensation_candidates`、`evidence_predicates`）。旧映射的字段全部不再出现。
- 每件事只说一次：
  - 目标与步骤只在 `views.goals`（`open` 标出还没有做法的目标、`adopted_method` 是已采用的
    做法实例、`under_repair` 标出修复请求指向的目标、任务状态）。原来 `plan` 段的三张表和
    `views.goals` 是同一批对象的两种写法。
  - 做法只在 `views.methods`，每条带步骤、参数、前置条件、适用性检查结果、被退役记录、
    审阅情况。引用只有一种写法（与 `visible_refs` 相同的四元组），可以原样抄进决定；此前
    同一个做法在一条记录里有三种写法。
  - 已采用的做法实例只在 `views.plans`（带引用四元组与各步骤）；数据绑定只在
    `views.plans.data_requirements`（带改接时要照抄的哈希）。
  - **一步失败的完整记录只在待处理的修复请求里。** `views.failures` 只是索引：哪次尝试、
    各检查层的一句话摘要。此前审阅员意见连同整份提交内容在两处各放一份，单这一项就占到
    整包的六成以上。
- 包里曾带着一段写给旧协议的英文说明（`constraint`：让模型照 `expected_plan_revision`、
  `read_set` 写）和 `output_contract`，一并删除——怎么写回复只在提示词里说。
- 规划包版本升到 10，包里直接写这个整数；原来"字符串标签 ↔ 整数版本"的换算删除。
- 可引用对象超过 128 条时直接拒绝（此前纯函数里是截断、生产路径里是拒绝，两种行为）。

## 与方案不一样的地方、当场决定

1. **"声明受阻 / 升级问人"类型连类型一起删**（方案写"定是否连类型一起删"）。理由见上面
   第 3 节：只留一条"问用户"的路径。
2. **规划请求末尾的英文"协议提醒"**不在方案清单里，盘点时发现，按"提示词只留一份"删除。
3. **领域版本集合没有收**（审计第三节第 7 条）。试着把文档领域三个按版本号的判断收成
   "只认文档领域"后，平面模式文档领域的测试（`tests/orchestrator/p33`～`p35`）有一百多条
   变红——它们的场景是照历史版本的领域配置搭的，每个版本开的闸门不一样。这是"旧平面模式
   整条线"的一部分，改动已撤回，留到那条线一起处理。
4. **平面模式的提示词与领域提示词的历史版本没有动**（`planner-v3/v4`、`worker-v2/v3`、
   文档 / AppWorld 各版本）。同样属于旧平面模式那条线，等用户决定。
5. `parse_method_proposal` 与 `<method_proposal>` 标签在源码里已无人调用，只剩旧协议的测试
   在用，留到片 D 之后清理旧分层旁路时一起删。

## 独立核验（一名 Opus 子代理，只读，只报阻断级，一轮）

逐项核对了六件事：还有没有代码读规划包里已不存在的字段；受理与新包是否自洽；提示词叫
模型去读去抄的字段是否都在；删掉两种决定类型后有没有残留路径；失败详情只放一处会不会让
某个决定做不了；Host 有没有依赖被删的东西。结论：

- **1 个阻断问题，已修**：失败索引里"规划回复被拒"的行没有尝试引用（空值），而核对"原样
  重做点名的那次尝试在不在本次请求里"的代码遇到空值会抛异常，异常一路冒到主循环——某步
  失败 → 规划器第一轮被拒 → 第二轮选"原样重做"就会崩。改成一个纯函数
  `attempt_is_indexed`，没有尝试引用的行直接跳过。
- 两条"值得留意"也一并处理：
  - 规划连续被拒超过 16 次会把步骤的失败尝试挤出索引（新实现按时间混排）。改为先列步骤的
    失败尝试、再列被拒的规划回复（`failure_index`）。
  - 新包里"已接受的结果"也进了可引用对象清单，离 128 条上限更近。保留"凡是带引用给模型看
    的行都可以被引用"，改成超限时先裁可选行（已接受结果 → 失败索引 → 观察 → 做法）并如实
    标注，只有目标本身就超限才拒绝。
- 其余五项没有阻断问题；前端还剩一个"声明受阻"的显示标签，一并删了。
