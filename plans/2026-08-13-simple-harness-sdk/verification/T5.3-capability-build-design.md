## Overview

T5.3 implements the capability_build workflow profile. Initial investigation revealed that capability_build is **not a new workflow graph**, but rather a **bounded profile** of the durable_task workflow with constrained budgets and specific capability tags.

From product source analysis (`backend/tests/harness_simplification/test_product_workflow_profiles.py` lines 128-156):

```python

```

This means:
- capability_build uses the **same workflow graph** as durable_task
- It's differentiated only by **configuration/constraints**:
  - Tighter budgets (proposal_budget: 40, fix_budget: 3)
  - Different workflow_key: "capability.build.v1"
  - Specific capabilities: {"workflow", "capability_build"}
  - Reserved launch_policy: "reserved_control" (not model-spawnable)

## Architecture

### Profile Pattern

The capability_build workflow follows the **profile specialization pattern**:

1. **Profile Definition**: Constants that reference the base workflow
   - `WORKFLOW_PROFILE_KEY = "workflow.capability_build"`
   - `WORKFLOW_NAME = "durable_task"` (references base graph)
   - `WORKFLOW_VERSION = "v1"`

2. **Budget Constraints**: Tighter limits for safety
   - `DEFAULT_PROPOSAL_BUDGET = 40` (vs unlimited in general durable_task)
   - `DEFAULT_FIX_BUDGET = 3` (vs 8 in general durable_task)

3. **Graph Reuse**: No new nodes, edges, or handlers
   - Uses all 10 nodes from durable_task
   - Uses same conditional routes and retry policies
   - Same HITL interrupt points

### Implementation Scope

The implementation is intentionally minimal because:
- The workflow graph already exists (durable_task)
- Node handlers already exist (durable_task/nodes.py)
- State contracts already exist (durable_task/state.py)

What's needed is only:
- Profile constants that identify this as a bounded variant
- Budget defaults that constrain execution
- Documentation of the relationship to durable_task

```python
"""Capability builder workflow profile.

This is a bounded profile of the durable_task workflow, specialized for
building, testing, and installing capability packs. It uses the same workflow
graph as durable_task but with:

- Restricted budgets (proposal_budget: 40, fix_budget: 3)
- capability_build capability tag
- Reserved control launch policy (not model-spawnable)
- Host-issued admission contracts for candidate-only builds

The workflow reuses durable_task's graph definition and node handlers. This
module only documents the profile boundary and provides the builder-specific
data contracts already defined in simple_harness.capabilities.builder_contracts.
"""

WORKFLOW_PROFILE_KEY = "workflow.capability_build"
WORKFLOW_NAME = "durable_task"
WORKFLOW_VERSION = "v1"
DEFAULT_PROPOSAL_BUDGET = 40
DEFAULT_FIX_BUDGET = 3
```

**Design Rationale**:
- Minimal surface: only constants, no graph definition
- Clear documentation that this reuses durable_task
- References to builder_contracts (already implemented in earlier phases)

## Relationship to Builder Contracts

The capability_build profile works with the builder contracts implemented in earlier SDK phases:

**From `src/simple_harness/capabilities/builder_contracts.py`** (707 lines, delivered earlier):
1. `CapabilityBuildSearchEvidence`: Search attestation
2. `CapabilityBuildLineage`: Parent goal tracking
3. `CapabilityBuildLaunch`: Admission contract
4. `CapabilityManagerInstallRequest`: Install request
5. `CapabilityBuildEvidence`: Validated draft
6. `CapabilityBuildCompletion`: Terminal value
7. `CapabilityBuildCandidateAdmissionV1`: Host-issued execution identity

These contracts are the **data layer** for capability builds. The capability_build profile is the **execution layer** that uses durable_task's graph with these contracts.

## Product Integration Points

When the product runtime uses capability_build:

1. **Launch**: Host issues `CapabilityBuildLaunch` admission contract
2. **Execution**: Runtime uses durable_task graph with capability_build budgets
3. **State**: Uses durable_task state schema (GateStateV1, ProposalStateV1, etc.)
4. **Handlers**: Uses durable_task node handlers (proposal, tool_execution, test, etc.)
5. **Output**: Produces `CapabilityBuildCompletion` with validated draft

The profile simply configures how durable_task runs for capability-specific work.

## Design Decisions

### Why Not a Separate Graph?

**Decision**: Implement as profile constants, not a new workflow definition.

**Rationale**:
1. Product evidence shows capability_build **reuses durable_task's graph**
2. All capability-specific behavior is in:
   - Input contracts (CapabilityBuildLaunch)
   - Output contracts (CapabilityBuildCompletion)
   - Budget constraints (tighter limits)
   - Authorization policy (reserved_control)
3. Creating a duplicate graph would violate DRY and create maintenance burden
4. The profile pattern is the canonical way to specialize workflows

### Why So Few Lines?

**Decision**: Keep implementation minimal (35 lines).

**Rationale**:
1. Profile's job is to **document** the relationship, not reimplement the graph
2. All execution logic already exists in durable_task
3. Defensive copies or elaborate abstractions would be over-engineering
4. Simple constants are easier to audit and maintain
