## 一、缺陷 1：人裁定"已生效"后任务永远完不成

### 1. 真正的卡点（和车道 C 的诊断有一处不同）

车道 C 记录说卡在 `Receipt.from_json({})` 出错。实际跑复现用例看事件：每轮 `OperationOutcomeDeferred` 的理由是 **`OP_OUTCOME_PENDING`**，来自 `operation_outcomes._execution_sources`：

```python
if action is None or link is None or action["state"] != "SUCCEEDED" or not action.get("receipt"):
    raise OperationOutcomeError("OP_OUTCOME_PENDING")
```

"成功了但没有回执"被当成"等一等"，而回执永远不会来。`Receipt.from_json` 根本没被执行到。此外 `_has_pending_operation_completion` 把这项效果算作合法等待，所以卡死检测也不接手。

### 2. 二选一的裁决：写一份"人裁定回执"（选项一）

两个候选：
- 选项一：人裁定时同事务给动作写一份具名的"人裁定回执"，结果审阅读到的是它。
- 选项二：结果审阅遇到"人已裁定"直接按裁定记效果结果。

选**选项一**，理由：
1. 效果"已验收"的读路径（`completion_status._effect_ready`、`_assured_outcome_use`、`accept_operation_outcome`）全部要求：结果审阅绑定 + 正式审阅记录（审阅员通过或人裁决通过）+ 使用证书 + 验收。选项二要"直接记结果"，就得在这条读路径里再开一个"人裁定"分支——第二条完成路径，违反"同一件事只留一条路径"。
2. 选项一只改"事实从哪来"：回执字段身份抄动作行，过的是和连接器回执同一道 `receipt_mismatch` 门；之后准备审阅、审阅员判、使用证书、验收、步骤完成全部复用现有代码，一行不加。审阅员判不下来 → 走现有 `_ask_person_to_adjudicate_outcome` 问人 → 使用证书验收，正是 Assurance 原计划"人裁决 → 使用证书路径验收"的那条路。
3. 符合核心思想：Harness 只负责如实呈现事实（谁、何时、凭什么裁定；没有执行过任何登记检查），够不够由审阅员（LLM）判。不写"人裁定即通过"的硬规则。
4. 规划器侧读操作台账（`planning_operations._classify`）对 SUCCEEDED 动作要求"有匹配的成功回执"，人裁定回执自然满足，规划器看到的是 APPLIED；选项二下规划器会一直读到 `success_without_matching_receipt`。

连接器的回执解读器（`FilePublishReceiptAdapterV1`）对人裁定回执不适用：它查连接器台账、读文件哈希，而这个局面下台账说的就是"没发出去"（回执丢了）。所以人裁定回执不过解读器，观察事实就是裁定本身——`milestone_source=HUMAN_RULING`、`executed_check_ids=[]`，如实告诉审阅员"没人跑过登记检查，是人看过"。观察到的里程碑写成效果要求的那个里程碑（读路径按它匹配效果槽），来源字段说明它是人裁定出来的。
