# ARP-EXEC-1.1.1 主体施工 RP-E3：原生运行平面接入编排装配层与 Host

日期：2026-09-24。提交：SDK `37c3a3ac`（RP-E3a 装配层）、`7308e50b`（RP-E3b DeepSeek 计量认证 + 先前输出储备；版本 `0.13.0.dev20260924+arp.1`）、Host `b510a60d`（Host 五端口、控制通道动词、评估 Mission 链接、钉版）+ 核验修复提交（见 §4）。

## 1. 交付物

**SDK（编排库）**
- `runtime/native_plane.py`：`NativePlaneAssembly`（一个池要跑在原生平面时，由部署方提供：`arp_ports(执行库路径)`、真实授权端口、`caller_for(intent)`、`after_build(runtime)` 迟绑定钩子）；`intent_caller`：由已认领的派发意图派生 `TrustedCaller`（主体=部署 principal，命令回执=意图本身的 id/mission/kind/creation_key/input_hash）；`RunPriorReserve`：从该池自己的执行库汇总本 run 先前所有已结算调用的输出 token 作为 `P`，`claimed` 跳过，未结算/无用量一律 `PRIOR_RESERVE_UNAVAILABLE`，不猜。
- `runtime/assembly.py`：`RuntimeProfile.native_plane` 非空时用 `build_arp_runtime`（AllowAll 在装配时就被拒 `AUTHORITY_SOURCE_MISSING`），桥带 `caller_for`；旧池一行不改。
- `runtime/agent_worker.py`：`AgentBridge.create(..., intent=)`，原生池没有意图就拒绝；`event_handler.py` 创建时传入已认领意图。
- `runtime/deepseek_meter.py`：`CertifiedDeepSeekCounter`（官方 tokenizer + 官方请求渲染器，`count_mode=EXACT`，`count_request_tokens` 直接给出最终线上请求的精确计数）；`deepseek_meter_binding`（`input_limit_scope=WIRE_PLUS_PRIOR`、`requires_prior_output_reserve=True`，必须带先前输出储备读取器；认证回执写明规则、recipe 版本、tokenizer sha）。

**Host（backend/deskpet/orchestration）**
- `native_plane.py`：`HostNativePlane`。授权端口 = 部署策略允许的工具名（不是 AllowAll，策略有身份）；计量 = 上面的 DeepSeek 认证绑定（测试用注入的认证夹具计数器）；每池一个 ARP 会话根（`execution-<profile>.db.arp-root`）；验收读口 = `AssuranceSkillAcceptance` 迟绑定编排 store 与保证根门 `require_execution`；产物读取 = 编排产物库按内容哈希；嵌入 = BGE-M3（INT8 本地，权重缺失/未装 FlagEmbedding 显式报 lexical-only，加载失败记一次不再重试）；脚本执行器 = 无（按名拒绝，见 §5）。
- `runtime_profile.py`：官方 DeepSeek 或部署声明的兼容主机（`deepseek_compatible_hosts`）才出认证计数器；tokenizer 路径优先 `DESKPET_ORCH_TOKENIZER_PATH`，否则 `<models>/deepseek-v41/tokenizer.json`；原生池 `deepseek-native-256k-v1 / -512k-v1` 与旧池并列，新 Mission 默认落原生池（`native_plane=off` 退回旧池；已有 Mission 保留其冻结的池）。
- `service.py` / `handlers.py`：`agent_runtime_request`（SDK `HostRequest` → `HostResponse`，调用方只由 Host principal 派生，失败以 SDK 的 Error DTO 回）、`agent_skill_evaluation_mission`（评估的原始 Mission，幂等键 = `evaluation_mission_key`）、`agent_skill_evaluation_dispatch`（核对租户归属、幂等键、任务归属后写 `record_evaluation_dispatch`）；`status.native_plane`。
- 钉版：SDK 升到 `0.13.0.dev20260924+arp.1`（源提交 `7308e50b`），vendor 轮子 + 候选清单 + `sdk_candidate.py` + `pyproject.toml`（加 `deepseek-recipe==0.1.1`）+ `uv.lock`；本机装了钉定的 DeepSeek V4.1 tokenizer（sha 与 SDK 钉值一致）到用户模型目录。

## 2. 接线过程中发现并处理的事

- 规划 Agent 在原生池创建时被 `SOURCE_UNAVAILABLE: MISSION owner mode needs exact sources` 拒绝：ARP 的 MISSION 模式要求 TaskGraph/InputManifest/Assurance 精确来源集（RP-B 未实现，SDK 按名拒绝）。Host 池改用 `STANDALONE_CHAT`（编排层的 Agent 本来就由冻结的派发意图创建，不依赖 Mission 模式来源）；MISSION 模式来源集列为遗留。
- Host 新规划协议的启动门要求先批准"完成规格"，否则 Mission 停在 CREATED（交接里 26 个旧用例中的 6 个正是这个原因）；测试里按 Mission 自带需求修订批准后，循环把规划意图派到原生池：Agent 创建（创建意图回执指向 `dispatch-intent:intent-plan-…`）、上下文计量（484 / 243712）、提供方交接都走通；夹具提供方没有 `method_synthesizer` 角色脚本，所以规划停在那里（Assurance 交接第③项，不属本片）。
- 新设置字段起初用元组，写入部署清单后与内存不一致，改为字符串。
- SDK 目录名空间由会话根 id 与池 owner scope 派生（`host:<tenant>:<profile>/agent-orchestrator/-`），Host 在状态里报同一个值供控制请求使用。

## 4. 独立核验（opus 5.5，只报阻断级）

一轮，报了 2 条阻断级，都在 Host `native_plane.py`，已修（Host 提交见下）：

| 问题 | 为什么阻断 | 修法 | 回归 |
|---|---|---|---|
| 两个原生池共用一个 `AssuranceSkillAcceptance`；SDK 每建一个池都 `bind_lifecycle`，读取器最后指向 512k 池的目录库 | 默认 256k 池上"评估派发 → 验收 → 准入"永远 `EVALUATION_NOT_DISPATCHED` | 每池一个读取器（`acceptances[profile_id]`），`bind_orchestrator` 逐个绑 store | 测试断言每池读取器的 `dispatches` 指向该池自己的 lifecycle、store 是编排 store |
| 部署策略授权端口拒掉 `assurance_find_evidence` / `assurance_read_evidence`；Mission 所有角色（含 Assurance 审阅员）都跑在 Mission 选定的池上 | 新 Mission 默认落原生池且 Assurance 默认开启，审阅员一取证就被拒，只能 INCONCLUSIVE/REWORK，静默倒退 | 放行名单 = 部署策略工具 ∪ `ASSURANCE_EVIDENCE_TOOLS`（只读；工具网关仍按角色约束） | 测试断言两个取证工具 allow、`shell_exec` deny |

核验确认无阻断的点：控制通道/意图调用方只由 Host principal 与部署 owner contract 派生，重放哈希稳定，不同意图不撞回执；授权端口不会被 `is_allow_all` 误判；`model_limits` 与 `MeterBinding` 三个哈希一致；`RunPriorReserve` 口径与 `provider_budget_guard` 一致（handed_off/unknown 判不可用，不低估）；旧执行库上下文身份不变、每池都有计数器、已有 Mission 保留原 profile；`native_plane=off`/夹具场景/非 DeepSeek 三条旧路径不变；根门缺失按名拒绝；评估派发链接无绕过。

## 5. 未做 / 遗留（排入 RP-E4 或后续）

1. `script_runner=None`：SCRIPT 类技能按名 `RUNNER_UNAVAILABLE`。Host 沙箱执行器是异步接口，SDK 端口是同步 `run`，需要一个不阻塞事件循环的适配（或 SDK 端口改异步）。
2. ARP profile `owner_mode=STANDALONE_CHAT`：MISSION 模式的精确来源集（TaskGraph/InputManifest/Assurance）SDK 尚未实现。
3. 评估派发链接的成功路径（`record_evaluation_dispatch` 写入）在 Host 测试里到不了（夹具无 `method_synthesizer` 脚本，规划不出任务），由真实模型局验证；Host 夹具迁移是 Assurance 交接第③项。
4. 本机 FlagEmbedding 导入失败（transformers ABI），原生会话实际是 lexical-only；状态里如实显示 `embedding: bge-m3-int8`（配置存在）但首次调用会记 FAILED 回执并降级。要么修 ABI，要么把探测提前到装配。
5. 日卡通道经本机转发（127.0.0.1）不是官方主机：真实模型局前需在 `[orchestration]` 写 `deepseek_compatible_hosts = "127.0.0.1"`（或网关域名），否则没有认证计数器 → 没有原生池（状态会写明）。
6. ARCHITECTURE 文档、`verify_development_handoff.py` 清单在 RP-E4 交付时统一更新。
7. Host 的模型目录是 `~/Library/Application Support/com.dennywanye.simpleharness/models`（不是 `deskpet/models`）：tokenizer 已装到该处；BGE-M3 权重不在该处 → 原生会话 lexical-only（状态如实显示）。
