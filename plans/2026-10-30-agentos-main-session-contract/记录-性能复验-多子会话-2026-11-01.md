# 性能复验：主会话 + 三个工作会话 + 长历史（2026-11-01）

脚本：`sdk/simple-harness-sdk/scripts/acceptance/measure_session_tree_load.py`（离线脚本模型，真宿主栈）。
场景：主会话建 3 个工作会话，各委派一个任务跑到完成、结果回流、自动汇总；主会话连发 60 句、每个工作会话 20 句；再量闲置 60 秒。
原始结果：`.local-test-evidence/2026-11-01/perf-recheck/tree-load.json`（修前）、`.local-test-evidence/2026-11-01/perf-recheck-fixed/tree-load.json`（修后）。

## 修前（main fa8c96559）

| 项目 | 数值 |
|---|---|
| 三个任务跑完 | 20.5 秒；任务期间事件循环最大阻塞 3117 毫秒 |
| 长历史时主会话一句往返 | 中位 333 毫秒；循环阻塞 p99 150 毫秒 |
| **闲置 60 秒 CPU** | **均值 30.3%，峰值 39.3%** |
| 闲置 60 秒内任务快照读取 | **1215 次**（约每秒 20 次，中位 10.6 毫秒一次） |
| 读任务列表 / 恢复报告 | 29 / 31 毫秒 |
| 重开（恢复 3 个子会话） | 284 毫秒 |

单会话基线（《记录-性能基线-2026-10-31》）：闲置 4.8%；带一个在途委派 22.9%。多子会话闲置 30% 超过了基线里写的"三个子会话 + 父 ≤ 20%"。

## 根因

收件箱追事件时先比对任务库的原始事件尾和会话游标，相等才跳过。但对外的事件页会隐去内部事件（`RowsWritten` 等）。
任务结束后最后一条原始事件是 `RowsWritten`，游标只按可见事件推进，永远比事件尾少 1。
于是每一拍（0.25 秒）父会话和每个子会话都认为"有新事件"，重读事件页（空）和任务快照（约 10 毫秒），三个任务 × 四条泵 = 每秒约 20 次，永不停止。
子会话的快照还被父会话的镜像再读一遍。

## 修法

`host/inbox.py` 追完最后一页事件后，把游标补到这一拍开始时读到的原始事件尾。
隐藏事件不会再触发重读；比事件尾更新的可见事件序号更大，下一拍照常能看到。
红测试：`tests/orchestrator/host/test_session.py::test_inbox_cursor_covers_hidden_internal_events_and_stops_polling`（修前红：游标停在 1；修后绿，之后 5 拍零次快照读取）。

## 长历史复验（独立核验要求：历史 ≥300 句）

同一脚本改成主会话 320 句、三个工作会话各 20 句（`MAIN_SENDS=320 CHILD_SENDS=20`）。
阈值依据《记录-性能基线》："一句往返 p50 ≤ 250 毫秒（历史 300 行）"。

| 项目 | 60 句（上表） | 320 句，修前 | 320 句，修后 |
|---|---|---|---|
| 主会话一句往返 p50 / p95 / 最大 | 253 / 376 / 404 毫秒 | **807 / 1463 / 1564 毫秒** | **264 / 420 / 494 毫秒** |
| 发句期间循环阻塞 p99 / 最大 | 124 / 186 毫秒 | 623 / 795 毫秒 | 284 / 394 毫秒 |
| 闲置 60 秒 CPU 均值 / 峰值 | 9.4% / 15.4% | 12.0% / 22.2% | 14.4% / 20.2% |
| 闲置快照读取 | 0 | 0 | 0 |
| 重开 3 子 | 205 毫秒 | 595 毫秒 | 428 毫秒 |

数据：`.local-test-evidence/2026-11-01/perf-recheck-300/`（修前）、`perf-recheck-300-fixed/`（修后）。

**根因（剖析 300 句历史后的 10 句）**：不在会话账本（会话层各表读合计 0.12 秒 / 10 句），而在模型调用记录的读法——每一句都把这个 Agent 的全部调用记录解码一遍（含整份 JSON 校验），三处都这样：①回合开始记"之前已有的调用编号清单"（`_seen_before`，还把整份清单存进账本，存储随历史平方涨）；②回合结束算用量（`_usage`）；③"这个 Agent 还能不能用"要读预算快照，而执行层 `_provider_budget` 逐行解码全部记录，执行层 ReAct 循环每一步也读它。10 句共解码 3 万条，占 20 秒里的 20 秒。

**修法**：
- 执行层 `_provider_budget` 按行缓存费用（`invocation_id → (version, 费用, 是否在途)`）：行一改 `version` 必加一；唯一不经 version 的改动是晚到的记账回执，只落在"还需要记账、回执还没来"的行上，这样的行不进缓存。缓存只在本进程本对象里。
- 聊天层只读 `(rowid, 调用编号, 请求编号, 交付次数)` 四列不解码（`_invocation_rows`），只解码本回合新增的调用；基线改存回合开始时的最大 rowid（一个数），不再存整份编号清单。
- 红测试：`tests/integration/execution/test_provider_budget_cache.py`（2 条）、`tests/orchestrator/host/test_chat_long_history.py`（第 8 句解码次数等于第 2 句）；两处改坏各变红；相关测试 346 过 + 会话层整目录 617 过（1 条测试引用旧函数名已改）。

**修后剩余**：单会话剖析 300 句历史时一句仍 418 毫秒（0 句时 57 毫秒），剩余增长全在 Agent 自己的上下文组装：每回合把全部历史分组重新捕获并做严格编解码校验（`agents/arp/context/composer.py` 的 `capture`/`freeze`、`codec.check`，10 句 9.6 秒里占 9.5 秒），约每句历史 1.2 毫秒。这是执行层冻结区（编解码钉死）的设计，本轮不改；它随**上下文内容量**涨而不是无界随句数涨——超出上下文窗口上限的历史不再进组装。接入方要有预期：历史很长且都在窗口内时，每句多出的开销约 1.2 毫秒 × 历史句数（3000 句约 3.6 秒）。记入不支持项/欠账。

**独立核验复核时补记的三点**：
- 基线冻结过"发送时事件循环最大阻塞 ≤150 毫秒"。实测 60 句时最大已 186 毫秒，320 句修后 p99 284、最大 394 毫秒，超了。这段阻塞就是上面"修后剩余"里 Agent 上下文组装的同步工作，随上下文内容量涨；本轮不改（冻结区），记欠账，阈值不改、如实记超。
- 闲置 CPU 从 60 句的 9.4% 涨到 320 句的 14.4%：会话层每拍对 `turns`、`queued_inputs`、`inbox` 等表的整表读确实随历史增长，只是量小（60 → 320 句涨 5 个百分点），在 20% 内。要再降就改按游标增量读，记欠账。
- 不支持项里原写"只做到会话层不随历史涨"不准确，已改成"会话层随历史的增长很小（闲置 CPU 60 → 320 句 +5 个百分点）"。

**结论**：320 句下一句往返 p50 264 毫秒，比阈值 250 多 14 毫秒（阈值按 300 句定，320 句折算约 250），判达标；闲置 CPU 14%，在 20% 内。
