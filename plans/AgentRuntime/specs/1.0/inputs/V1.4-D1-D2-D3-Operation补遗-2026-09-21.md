# D1：从接受候选到生产操作

## 2. 唯一默认流程与生产 caller

### 2.1 新协议的默认顺序

```text
Worker 交付报告和/或 actions/*.json 候选
  → 原独立内容检查与准备贡献 Acceptance
  → accept_result 只接纳准备成果、记录候选可用事件，不建 action
  → 已认证 Host/已委派 Mission 控制器明确提交操作意图
  → 固定本次候选、参数、效果合同与 ACTION_PROPOSAL ReviewPackage
  → 原持久 Review 派发 → 独立 Verifier → official ReviewRecord
  → materialize_reviewed_operation（同库一次事务）
       bind OperationEnvelope + propose_action(planning_origin) + identity link + receipt
  → 原审批入口（必要时人工；可自动批准时使用真实 deployment policy）
  → 原执行准入：先持久 HANDED_OFF，再真实调用
  → 原回执导入/OPERATION_OUTCOME → 根验收
```

这不是“先完成 Mission 才执行”：准备产物 Acceptance 只是贡献接受。Task/根要求包含真实动作时，结果归档不得顺带宣告该完整责任完成；只有动作里程碑满足后原 GoalResolution/closeout 才能完成。

**不采用默认的 accept+action 一次大事务。**独立 ACTION_PROPOSAL 需要模型/工具，不能塞进 accept_result 写事务，也不能拿旧内容 Review 充当它。旧协议保持原 accept→propose_action 行为与字节。

### 2.3 提交的是明确操作意图，不是“接纳一个文件就自动操作”

`SubmitOperationIntentV1` 只允许以下字段，全部必填（nullable 字段必须明确 null）：

```text
schema_version = 1
mission_id: str
idempotency_key: str                         # 一个真实控制命令的重送身份
intent_source: {kind: USER_COMMAND}
            | {kind: AUTHORIZED_SLOT, origin_receipt_id: str, slot_key: str}
candidate_artifact_ref: TypedRef(kind=artifact)
prepared_acceptance_refs: nonempty tuple[TypedRef(kind=acceptance)]
supersedes_intent_id: str|null
```

`intent_source` 的核验分两条：
- USER_COMMAND：这一次已认证 `submit_operation_intent` 调用本身就是明确“执行此操作”的命令；**不要求用户先找一个不存在的 receipt 签发器**。系统在 T0 产生本命令的 OperationIntentSubmitted receipt，将它同时作为 origin_receipt，slot 固定为本命令内唯一 `operation`。模型/请求体不能填写此 origin ID。选择准备结果/打开详情/Worker 回复不等于这种命令。
- AUTHORIZED_SLOT：从原用户命令/版本化 Requirements 的**明确操作义务 slot**取真实委派来源，receipt 必须绑定允许对象、动作范围、数量和唯一 slot。若已有来源不含这些信息，不能用 task/target 相似性推断授权；返回 `OP_INTENT_SOURCE_UNRESOLVED`，等待同一正式入口的用户命令。补充该来源不需要 Worker 产出前冻结 envelope。

**去重键是 `(mission_id, origin_receipt_id, slot_key)`。**它表示同一个明确授权意图，而不是相同内容。重复 event/Attempt/换方法沿用这个来源；第二次相同目标的真实操作需要另一条明确授权来源/slot。Worker 无权 mint 来源 receipt、slot 或 OperationId。

`idempotency_key` 同键同命令体回原 receipt；同键异体冲突。同来源 slot 携带不同候选也冲突，不能把修改 payload 伪装成重试。修订候选走新显式命令，带 `supersedes_intent_id`；旧意图已物化时先按原核对/替代规则处理，UNKNOWN 不允许跳过。

## 3. 生产方法与事务

### 3.1 `accept_result` 改动

在原 `orchestrator/commit_service.py::accept_result` 的已批准新协议分支：
1. 仍按原规则保存结果、产物、真实内容审阅、准备贡献 Acceptance。
2. 遇 action candidate 记录 `OperationCandidateAvailable`（candidate/result/Acceptance 精确 refs）；**不调用 propose_action、不调用 bind_operation、不签发 OperationId。**
3. 不为动作尚未发生的准则填 PASS；不要调用必须先有整个 Mission 完成的逻辑。
4. 若存在已核验 AUTHORIZED_SLOT，原 Orchestrator 的持久事件消费者用稳定来源触发 `submit`；否则由 Host 显式提交。不让 LLM 生成启动权限。

这条事件只唤醒/通知，不是执行授权。幂等由原事件 id/command receipt 负责，不新增第二套 outbox。

### 3.2 准备事务 T0：`OperationMaterializationCommitsMixin.submit_operation_intent`

生产 owner 为 CommitService 新 mixin；先按 caller/idempotency_key 查询已提交 receipt，存在则返回原 intent。不存在时用原 ID 工具生成**暂存于内存**的 intent_id，读取原 CAS、严格解析候选、通过**当前真实 connector profile**归一化/绑定参数，准备三个含该 intent_id 的 CAS 对象（§6）。网络/模型不在写事务内。并发提交在 T0 再查 receipt；失败/输掉竞争的暂存 ID 没有正式身份，其孤儿 CAS 不赋予任何权限。

T0（同 Store.transaction/connection）：
1. tenant/current caller guard；先查既有命令 receipt，同内容返回。
2. USER_COMMAND 核验本次 authenticated command，预计算其真实 receipt ID；AUTHORIZED_SLOT 核验原 receipt/slot 的实际授权。检查唯一 slot 未被其他意图占用。
3. 重新检查原候选 metadata/hash、准备 Acceptance 当前性、任务/要求/计划身份、当前 policy/connector profile。CAS 已读字节必须匹配这些精确引用。
4. 将上述系统暂存 `intent_id` 与唯一来源键一起正式落库（来源身份不是由内容 hash 反推）。
5. 插入三个 payload 元数据引用、`OperationIntentSubmitted` 事件、真实 source receipt、`operation_intent_bindings`。
6. 同事务创建原 ReviewPackage（subject=本次 **FrozenActionProposalV1 artifact**，purpose=ACTION_PROPOSAL）、相应 review work/dispatch intent 及必要原预算预留。review 账户按原 `account_for_purpose(ACTION_PROPOSAL)` 的 operation_task 归属，绑定本次产生操作候选的实际 Task 账户/既有审阅预留，而不是尚未创建的 OperationId。账户或保护尾额度不可用则 `OP_REVIEW_BUDGET_UNAVAILABLE` 并不派发；不能使用免费的 Planner 调用或已结算账户的假额度。
7. Commit 后原 AgentBridge 派发真实独立 Review。

CAS blob 可以先写，事务失败时成为无权限、未被引用的孤儿，交原 GC；不能为适配 artifacts.attempt_id 外键伪造 Worker Attempt。三个对象的元数据用 §9 `operation_payload_objects`，CAS 内容仍只有原存储一份。

### 3.3 ACTION_PROPOSAL 的真实发起和回流

NEW `orchestrator/operation_reviews.py`：

```text
ensure_action_proposal_review(intent_id, caller) -> 原 ReviewDispatchReceipt
consume_action_proposal_review(record_id, service_principal) -> MaterializationReceipt|具名拒绝
```

`ensure` 用 intent_id+draft_hash+purpose 的稳定 review identity；重复不会新开 Reviewer。T0 调用其无外部 IO 的持久准备部分；原 reviewer runtime 执行模型。

ReviewPackage 冻结：draft artifact、params/effect refs、原 candidate 文件 ref、已接受准备输入、任务合同 ref、要求 ref、选定效果里程碑、已知缺陷；`producer_agent_ids` 取原 result/attempt，Reviewer 不得是生产者，不得修改被审对象。必需准则至少覆盖：
- 操作符合原明确意图且未扩大目标/权限；
- 实际参数和待交付字节正确；
- 要求的效果里程碑有真实能力支持；
- 写入前提/条件写及既有安全 policy 满足。

`consume_action_proposal_review` 由原已认证服务主体调用，只获得物化登记权，不代替用户签人工审批。只有 `official=true + purpose=ACTION_PROPOSAL + verdict=ACCEPT` 且必需检查实际完成，才进入物化。REWORK/REJECTED/INCONCLUSIVE 均不建 action。新增证据通过原追加记录，不改 package/hash。Review 完成事件由原 Orchestrator 消费，生成稳定 `materialize:<intent_id>` 命令，不等待模型再说一次“执行”。

### 3.4 物化事务 T1：唯一入口

```python
materialize_reviewed_operation(
    *, intent_id: str, official_review_ref: TypedRef,
    command_id: str, principal: Principal,
) -> OperationMaterializationReceipt
```

实现于同一个新 mixin，按顺序：
1. 当前 caller 权限；同 command 先取原 receipt（返回仍检查当前读权）。
2. 精确读取 T0 intent/source receipt、三个 payload、原 official Review/inputs；对照 §7 的全部绑定、当前 validity、原要求。新 materialization 必须符合当前 plan/demand，不能用已退役原任务发新动作。
3. 核对原 Operation/Actions 全集合、supersedes 的真实结果；UNKNOWN 保持拒绝。保持现有 alias 冲突规则，不为本次改造 business_action_id。
4. 系统签发 OperationOccurrenceId/OperationId（仅此次真实意图，事务内持久；重送从 receipt/link 取回，不重新生成）。冻结 **OperationEnvelope 现有 V1**。
5. `HtnStore.bind_operation(envelope, ...)` 使用真实 principal/生产 occurrence。构造 `BoundPlanningOperationOrigin`：
   - provenance_receipt_id = **T0 的 OperationIntentSubmitted command receipt ID**；其 producer 是第 3.2 节真实提交，不是 Review 或模型字段。
   - source receipt 仅证明来源/冻结内容，不声称已执行/已批准；official Review、当前授权分别验证。
6. 调原 `propose_action(raw_candidate, ..., planning_origin=origin)`：传**原始未绑定 candidate**，不是把 effective_params 中的系统 artifact_id 等字段倒灌进模型参数校验。沿原 `check_candidate/bind_artifact_params`，使用原精确 accepted-artifact index 重算；归一化目标和 bound params 必须逐值/原 params_hash 等于 T0 冻结值，否则拒绝，不把新值覆盖旧值。新分支写入已核对的冻结 effective_params。产生既有 action 和对应审批请求；检查 action 与 envelope 的目标/参数/候选/ref 全部相符。
7. 同事务建立 `planning_operation_action_links`；冻结来源精确 join。不同 occurrence 被旧 business_action_id 合成同一 action 时返回原 `operation_occurrence_alias_conflict`，共同 rollback；不扩大此次范围去重写 legacy 身份。
8. 写 `OperationMaterialized` 事件、原 CommitReceipt（包含 envelope_hash、intent/source/Review refs、action_key/version/link_hash）、原审批/调度待处理记录，Commit。

**任何第4–8步失败：envelope/action/link/receipt/outbox 共同 rollback。**不得外层 Commit 前跑 Connector。生产 `begin_handoff` 仍强制 link 和来源完整。

### 3.5 为什么审批可以在 action 落库之后

原 approvals 需要引用 action 身份。本方案允许审阅后建立 **待审批、不可交接** action；这不是 AER §14.1 的实际执行授权，也不违反“先授权后执行”。
- 人工审批：T1 原 policy 返回 AWAITING_APPROVAL，只写审批需求，不写可执行 handoff。
- policy 自动许可：T1 必须保存真实 deployment policy 结果/身份，仍已完成 ACTION_PROPOSAL；原 runtime 在真正 handoff 时再检查当前许可。
- 原 `ApprovalApi` 负责批准/拒绝，不增加第二种 approve boolean。授权完成事务才释放原调度条件。
- 执行段 T2：原预算/执行准入、fence、冻结 request，先持久 HANDED_OFF，事务外真实调用。
- 结果段 T3：原 runtime receipt/usage 先持久，再导入编排；OPERATION_OUTCOME 达到指定 milestone 后才能完成相应义务。

这相当于将 AER 的 A 段明确拆为“不可执行注册”和“可执行授权”，不是颠倒操作 Review/授权/实际执行顺序。

# D2：payload、引用、hash 与实际 connector 证据

## 4. 谁决定哪些字段

| 数据 | 唯一生产者 | 不是谁决定 |
|---|---|---|
| connector/operation/target/未绑定 params/reason | Worker 的原 candidate（只当建议） | 不能设置 level/operation id/approval/artifact identity |
| adapter version/namespace/schema/能力范围 | 实際配置加载器＋注册 connector adapter 的 `operation_profile()` | 不是模型，不从类名或 OperationSpec 空缺推断 |
| bound params/要求 milestone/条件写策略 | `prepare_operation_payloads()` 根据 candidate、Acceptance、原要求与部署 policy | 不由 resolver 临时改内容 |
| 参数/效果/draft refs | T0 CAS 写入＋metadata/receipt | 不伪造 artifacts Attempt |
| Review/Acceptance refs | 既有正式 Review/Acceptance writer | 不接模型自报 PASS |
| OperationEnvelope/身份/link | T1 Commit | 不在 preview/Worker/查询接口创建 |
| no-late-apply 事实 | 实际 connector 的已持久服务回执 adapter | 不由 Planner、人工 bool 或本地超时构造 |

## 5. ConnectorOperationProfileV1（最小新增声明）

`runtime/operation_payloads.py` 或等价现有 runtime 模块新增 frozen 内部类型；注册器从真实 adapter 构造，不改旧 OperationSpec 的序列化：

```text
schema_version: 1
connector_id, adapter_version, adapter_code_digest: str/hash
namespace: {service_id, account_scope, environment}              # 非秘密标识
operation_name: str
parameter_schema_ref: VersionedRef
outcome_contract_version: str
supported_milestones: tuple[str,...]                            # 非空、注册枚举
receipt_adapter: {id:str, version:str}
conditional_write: NONE | {kind:ETAG|TRANSACTION|FENCE, protocol_id:str}
idempotency: UNKNOWN | {kind:ATOMIC_KEY, namespace:str,
                        retention_basis_ref:TypedRef,
                        minimum_retention_ms:int, conflict_protocol_id:str}
nonapplication_proofs: tuple[SERVER_CANCELLED_BEFORE_APPLY|SERVER_DEADLINE_FENCED|
                             EXECUTOR_NO_SEND_FINAL]
authority_source_ref: TypedRef                                 # 部署合同/实际能力文档，不是真实结果
```

`UNKNOWN/NONE/()` 是**真实 adapter 明确声明无此保证**，不是读取失败的默认。profile producer 不存在→`OP_PROFILE_UNAVAILABLE`。输入要求的 milestone/条件写不支持→`OP_CAPABILITY_UNSUPPORTED`；不得自动降为 HTTP 200。没能力证明安全重发时，首次执行仍按原风险 policy 判准入，但后续 UNKNOWN 不自动重发。L2/L3 原本要求更强保证的，继续拒绝，不降低已有门。

版本必须来自实际绑定 adapter/实现制品，不把包名/version 字符串当运行制品证明。部署热更新后新的 profile 与冻结引用不同，拒绝新交接；旧 outcome 的核对可使用仍保留的原版本只读 adapter，不能重编码后发送。

## 6. 三个专用 payload（完整 Schema 在 contracts.schema.json）

### 6.1 `OperationParametersV1`

```text
schema_version: 1
intent_id: str
connector_id, connector_version, operation_name: str
connector_profile_hash: hash
normalized_target_ref: str
expected_target_version: str|null
parameter_schema_ref: VersionedRef
effective_params: JsonObject
params_hash: hash
candidate_artifact_ref: TypedRef(artifact)
accepted_input_refs: tuple[TypedRef(acceptance), ...]             # 非空
```

`effective_params` 是调用原 `check_candidate` 和 `bind_artifact_params` 后**实际准备传给 connector 的参数**。原 candidate 中 artifact_path 由系统解析到该 Result 的已接受 artifact；若夹带模型写的 artifact_id/storage_uri/content_hash，沿原规则拒绝。原函数不具备的跨 Result 引用不能悄悄开放。

上限：每个 payload UTF-8≤256KiB、JSON depth≤16、键不重复、NaN/Infinity 拒绝、schema整数不能接受 bool；沿项目现有更严格限制取小值。不改现有 canonical_json 算法，编码 `canonical_json(obj).encode('utf-8')`。冻结后不删字段、重排数组、重绑定 latest；秘密只用现有凭据引用，不持久 raw token/key。

## 7. 最小 resolver 与三个 revision

新增 `OperationRefResolver`，不是扩展 SourceCitation-only 的 EvidenceResolver：

```python
resolve_payload(ref: TypedRef, expected_kind: PayloadKind, access: ReadScope) -> FrozenPayload
resolve_review(ref: TypedRef, expected_draft_ref: TypedRef, read: ConsistentRead) -> OfficialReview
resolve_acceptance(ref: TypedRef, purpose: WitnessPurpose, consumer: str,
                   read: ConsistentRead) -> CurrentAcceptance
resolve_profile(profile_hash: str, registry: FrozenRegistry) -> ConnectorOperationProfileV1
```

- ARTIFACT：先按精确 metadata 所属种类找 `operation_payload_objects` 或原 artifact store；两处同 ID 同时存在→`OP_REF_AMBIGUOUS`。核对 Mission/scope/访问、revision、hash，再从原 CAS读固定字节；不接受 URI/path 作为权限，不通过 ID 前缀猜类别。TypedRef 用原字段 `kind/id/revision/content_hash[/produced_by]`，不是 PlanningRef 的 semantic_revision。
- REVIEW：读原 `review_records`、其 `review_packages`，核对 ID/hash、同 Mission、official=1、purpose=ACTION_PROPOSAL、verdict=ACCEPT、subject 为该 FrozenActionProposal、原 producer/reviewer 独立性、全部必需 check receipts、绑定要求和 input manifest。`ReviewRecord` 稳定身份的 revision 沿原 resolver，不编“最新 Review”。
- ACCEPTANCE：读原 acceptance/Review/Artifact 链，并取现有 ValidityService 的指定用途/consumer witness；CURRENT 且 permitted、support/epoch/期限匹配。历史 ACCEPTANCE 存在≠今天可披露/可执行。源撤回、新反证/隐私撤销都要经原有效性规则判断。L0 也不免掉本 lane 的操作审阅。
- 必需 Kind 未支持→`OP_REF_KIND_UNSUPPORTED`；对象缺失/错 hash/当前性未知分别返回具名拒绝，不能降级为字符串或调用模型解释。

| revision轴 | 真正来源 | 何时检查 |
|---|---|---|
| Task contract | 原 task_semantics 对该 Task 的**精确 binding/contract revision 与原合同 hash**，不是 tasks.version/heartbeat | T0 冻结，T1/materialize 与 handoff 看合同/输入/代次仍适用 |
| Requirements | 原 requirements_revisions 的指定 revision＋content_hash，必须是该 Mission 当前批准版本 | T0、Review、T1；变化不自动把旧 Review 挪给新要求 |
| Plan | 原 ACTIVE plan_revisions revision＋snapshot_hash 与 occurrence 采用关系 | T0 冻结、T1 按 H1 精确门；不是 Method version 或 Task revision |

Task contract 字段的本地属性名按现有 codec/Store解析，SQL列的 `binding_revision` 不能用最新行重写历史。T1 之前 plan变动按当前H1保守规则拒绝；T1已成功后，无关plan变动不改Envelope。真正handoff检查该原occurrence的当前采用/输入/generation/许可，受影响则拒绝；不把旧plan provenance当今天仍获准。

## 8. “未应用且不能迟到”的实际证明

只允许实际 connector/executor 的核对入口记录 `ScopedReconciliationObservationV1`，沿**原 action history/执行回执**追加，不能由 UI/model 向业务 API 填三个 true。

必需共同字段（字段结构见JSON Schema；语义proof检查不能只靠Schema）：

```text
schema_version: 1
action_key, action_version, operation_id, operation_occurrence_id
request_hash, params_hash, idempotency_key
connector_profile_hash, namespace, normalized_target_ref
covered_handoff_ids: nonempty sorted tuple[str,...]
queried_at_ms, observation_receipt_ref: TypedRef(tool_receipt)
observation_origin: REMOTE_QUERY|LOCAL_EXECUTOR
query_scope: {namespace, request_identity, consistency_kind, high_watermark:str|null}
outcome: APPLIED|NOT_APPLIED_FINAL|PENDING|PARTIAL|UNKNOWN
proof: typed union（以下之一或 UNKNOWN 的缺失原因）
```

`observation_receipt_ref` 指实际查询或实际本地执行检查收据。LOCAL_EXECUTOR 必须标为本地观察，不伪造一个未发生的远端查询；SERVER 类 proof 必须有真正远端回执。足够的 proof 只能是：
- `SERVER_CANCELLED_BEFORE_APPLY`：原服务原子取消确认、覆盖 request/key/全部交接，确认既未应用也不会再应用；保存原始服务回执 hash。
- `SERVER_DEADLINE_FENCED`：实际服务端强制执行 deadline/fence 的版本、时刻与回执，加覆盖此前全部请求的权威未应用查询；本机钟或本地lease不够。
- `EXECUTOR_NO_SEND_FINAL`：仅限原执行引擎能证明未跨发送边界、已永久封锁所有原交接且没有任何外发记录的情况；需真实执行事务/排队取消回执。只有日志缺项不足。存在历史 HANDED_OFF/PENDING 却不能排除发出时不适用。

adapter 负责解析特定服务的原始回执并验证具体协议语义；框架核对全部身份、覆盖和 registered proof kind。若服务只支持 best-effort lookup、没有水位/截止/原子取消保证，返回 UNKNOWN/`OP_NONAPPLICATION_PROOF_INSUFFICIENT`，保留待核对责任。

证明是**针对所覆盖的 handoff**，不是永远对整个 Operation 宣称未发生。先证明 H1 未应用、后获准 H2 应用并不冲突；后来新增 H2 时，旧 H1 的负证明不覆盖 H2。handoff集合完整读取/版本变化必须使旧重发资格失效。

即使证明未应用，也要通过原当前授权/预算/次数/退避门才可重发；证明不是自动批准。retention 过期、服务端不支持相同key原子去重或查询结果不足时不能靠新OperationId重做。

## 9. 持久化扩展（完整SQL在附件，且附于本文末尾）

只增加以下三张表；若本地存在完整等价记录，则扩展/复用唯一原入口，禁止同语义双写：

### 9.1 延期字段与状态

保存：decision/request、raw artifact/hash、codec/prompt/package hash、原base plan/requirements/scope/grant绑定、proposal command id、冻结target清单、当前 preview hash、截止/重读计数、下一次核对、lease/version和拒绝原因。

两个 JSON 列必须用以下精确内部 codec，未知字段拒绝，不能只检查 json_valid：

```text
authority_binding_json = {

}

```

targets非空且ID集合无重复，按稳定ID排序；后续新call不能靠这份旧清单漏掉，resume/Commit按同一task重新完整读实际Attempt/intents/actions集合。初始targets是fence范围，原记录中的attempt_ids是开始时的证据，不是永久免读新结果的白名单。

内部状态：

```text
WAITING → READY → APPLIED
WAITING/READY → PAUSED → WAITING/READY
WAITING/READY/PAUSED → MANUAL_REQUIRED
任一非APPLIED状态 → STALE_FENCED
STALE_FENCED/MANUAL_REQUIRED/PAUSED → CLOSED（仅完成真实安全收尾）
```

WAITING、READY、PAUSED、MANUAL_REQUIRED、STALE_FENCED 都保持 stop gate。READY 不是可绕过来源复查的证书。公开 PlanningDecision 保持原 ADMITTED/COMPILED 等合法非终态；延期阶段写原 `planning_admission_checks.phase=DEFERRED`。只有实际原Commit成功才COMMITTED；真实request过期才终态REJECTED，不能先REJECTED再复活。

### 9.2 原子 defer，不先破坏计划

`defer_planning_repair(preview, source, caller)`：
1. 必须已有合法纯结构预览和真实在途目标；参数/结构坏的提案直接拒绝，不建stop gate。
2. 同事务重读request/current grant/base plan；系统从原退休实例和真实共享demand计算targets，不信模型列表。
3. 写continuation（unique decision_id）+原DEFERRED check+事件/原待处理唤醒记录；此刻先封锁相关任务的**后续派发/handoff**，不改原plan/request/合同输入。
4. 事务后使用现有 P2.3s 停止/核对；停止命令key由continuation+原Attempt确定，重复有同回执。

新协议所有 provider/tool/action handoff与attempt创建入口统一调用 `planning_repair_stop_gate(mission_id, task_id)`。它读取未关闭continuation的**完整targets**，是临时执行权撤销。不是把lease改短、不是凭Task.CANCELLED判无在途。真实generation仍由原执行/正式plan commit规则处理；外部已交接请求不能被本地gate召回。

为避免自己的收敛动作使原request永久失效，初始defer不得改变原contract/input/plan revision。若现有取消路径必然改变被request绑定的scope/generation/合同，按真实STALE处理；不修改冻结request掩盖变化。继续接收原回执/费用，获准的只读reconcile不被业务新操作stop gate禁止。

### 9.3 唯一唤醒与暂停/重启

NEW `orchestrator/planning_repair_continuations.py::resume_pending_planning_repairs` 由**原 Orchestrator 的持久事件循环**驱动；不建后台独立线程或新Agent管理器。多个runner实例靠原/新行 CAS lease领取，只有一个owner消费，所有读写命令幂等。

触发：原Attempt/intent结束、action核对、有效性/授权变化、Mission恢复、启动扫描和有界timer。事件通知是提示，每次重读真实来源。

```text
读取 continuation + 原 planning_requests/planning_decisions
→ 从CAS读取原 raw，核对hash及原codec/prompt/package身份
→ 解码/复用原canonical Decision（不新增模型回复）
→ 原 pre-admission → adapter → pure preview → Plan Admission
→ 仍在途：保存新DEFERRED检查和下次时间
→ 已收敛且绑定有效：同command进入现有唯一guarded Commit
→ 提交成功：同事务continuation APPLIED，Decision COMMITTED，释放stop gate
```

原 `_retry_deferred_repair()` 按持久**protocol version**分派：legacy仍走旧proposal-text路径；新协议只进入上述resume函数，不调用旧 `apply_planner_reply(stored_proposal)`。原raw丢失/错hash/codec不可用→`REPAIR_SOURCE_UNAVAILABLE`，保持fenced/manual，不生成替代文本。

暂停不丢continuation、不延长授权期限、不派发新业务；允许保存已有结果/费用和获准核对。重启恢复lease所有权必须沿原进程身份规则，过期lease只允许重新领取协调工作，不等于旧外部操作已结束。

### 9.4 精确变化判定与超时

| 变化 | 原决定能否继续 |
|---|---|
| Attempt结束、取得匹配回执、原action由UNKNOWN变成有据结论 | 可以；重读并重preview同Decision，不用旧runtime digest冒充新快照 |
| 纯heartbeat/UI显示/协调lease变动 | 不自动使内容身份失效 |
| grant revision/hash/policy变化或过期、scope/manager epoch改变 | REQUEST_BINDING_STALE；不自动续签/重绑定 |
| requirements revision/hash变化 | REQUEST_BINDING_STALE；不降低要求 |
| base PlanRevision变化（即使声称无关） | 按当前H1精确门STALE；不新增一般化rebase |
| 选中Method、使用输入/证据、contract发生影响性变化 | 原guard拒绝/STALE；不是恢复忽略校验 |

有界默认内部政策 `planning-repair-wait-v1`：从首次defer起累计300000ms，最多64次有意义resume检查；轮询退避1/2/4/8/16/30秒并受原调度间隔约束。项目已有更紧的冻结限制取小值；政策不是环境变量，值存入continuation，重启不归零。

期限/次数达到→MANUAL_REQUIRED，追加一次可见报警/接管记录，保持原未决后果和stop gate；不是Mission成功/外部失败/自动清理。deadline的“终止”只指自动resume停止。旧raw照存；后续新Planner请求要有真实新条件/用户裁决，不能用模型重试掩盖相同未收敛操作。MANUAL_REQUIRED安全关闭需原运行核对和明确恢复旧需求/永久撤销的命令；CLOSED不删除原历史。

### DDL后的必需应用检查与CAS SQL

SQL外键不是same-Mission完整证明；`put_operation_intent`还须检查Task/Attempt/Result/Artifact/ReviewPackage全部归属同Mission、payload object_kind与列用途相符、source grant与caller匹配、两个semantic revision与真实来源一致。三张表不允许外部直接写。对象/intent immutable：同key异内容拒绝；不在数据库更新字段来修复Review对象。

协调领取在同一 `BEGIN IMMEDIATE`/原Store事务内先读due行，再执行以下CAS；rowcount必须1，否则本owner没有取得权限。当前任务暂停/终态及完整stop/operation来源在领取后仍复核。禁止长期持有事务等网络：

```sql
UPDATE planning_repair_continuations
 SET owner_id=:owner, lease_until_ms=:lease_until,
     row_version=row_version+1, updated_at_ms=:now
 WHERE continuation_id=:id AND row_version=:version
   AND state IN ('WAITING','READY') AND next_check_at_ms<=:now
   AND (owner_id IS NULL OR lease_until_ms<=:now);
```

状态变化必须先通过 §9.1 的纯状态机，再CAS：

```sql
UPDATE planning_repair_continuations
 SET state=:new_state, row_version=row_version+1,
     last_reason_code=:reason, updated_at_ms=:now,
     owner_id=NULL, lease_until_ms=NULL
 WHERE continuation_id=:id AND row_version=:version
   AND state=:old_state AND owner_id=:owner;
```

超时与PAUSED/MANUAL_REQUIRED等事件更新使用同一版本CAS，由原Orchestrator系统命令负责；不能只根据lease过期清除stop gate。对 `targets_json` 必須完整strict解码；读失败保持拒绝，不能回空集合。

T0/T1/DEFERRED的写入原子性以实际Store嵌套事务行为验证。DDL没有新增trigger；已有H1H/TG的trigger不能删除。fixture建表成功不等同SDK迁移通过。
