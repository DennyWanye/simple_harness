# LLM-native HTN 执行计划（HTN-LLM-NATIVE-1.0）修订需求

日期：2026-09-18　提出者：执行指挥（依据 Grok 对照 SDK 0.12.2 源码写的《H1-PlanningDecision协议-实施拆解-2026-09-18》）
对象：`simpleharness-llm-native-htn-execution-plan.zh-CN.md`
结论：方向与原则足够；作为交给编码 Agent（Grok）照做的执行规格不够细。H0 可立即开工；H1 的代码须等「第一组」裁定；H2–H8 各自开工前须补到与 H1 同等粒度。

## 第一组：H1 开工前必须裁定（影响线上格式，定错要返工）

1. **线上格式没有精确定义。** 需要给出 `PlanningDecisionEnvelopeV1` 及各 payload 的 JSON Schema：字段名、必填/可选、枚举大小写、长度与数量上限（rationale 字数、reason_refs / assumptions / alternatives 条数）、未知字段策略（拒绝还是忽略）、是否算规范字节与哈希。另附每种决定类型 1 个合法样例、每个拒绝码 1 个反例，作为黄金测试数据。
2. **一条回复能装几个决定。** 旧提案一次可带多个操作（展开、退役方法、绑定共享目标、提出后继）。新信封是一个类型一个 payload。须写明：一条回复只许一个信封还是可多个；现网修复轮要求的「退役 + 展开」成对操作在 H4 之前怎么表达；「绑定共享目标」「提出后继」两个旧操作没有对应的决定类型，是新增类型、并入 REFINE，还是暂留旧格式。
3. **引用种类词表。** 计划示例用 `kind: "fact"`，现有类型引用枚举里没有 fact（只有 observation 等）。须给出 reason_refs / visible_refs 允许的种类全集，以及各自对应现有哪种标识（事实、方法、任务、验收、责任、操作……）和校验方式。
4. **拒绝码不全。** 拆解中不得不新增：模型写了系统字段、决定对象与本轮不符、类型已识别但本阶段未启用、选了已退役方法。须补进第 46 节，或写明「允许实现阶段扩充枚举」的规则和命名约定。
5. **计划版本号的归属。** 旧格式允许模型抄写「期望的计划版本」，新信封禁止模型写权威版本。须写明：过期检测改由什么绑定（请求包编号 ↔ 发包时的计划版本），晚到的旧决定如何识别并以什么码拒绝。
6. **decision_id 由谁生成、用来做什么。** 模型生成还是系统生成；是否用于去重与幂等；重复提交同一编号怎么处理。
7. **H1 的线上接线范围。** 第 68 节 H1 验收只写了「旧行为不变、往返一致、系统字段不可设、未知引用被拒」。须明确 H1 是「只做合同与编解码、不上线」，还是「开关后接入真实派发，准入通过后转回旧提案再走现有编译」（拆解选了后者）。两种工作量和风险差一倍。
8. **开关放哪、默认值、何时转默认。** `planning_protocol_version` 记在任务上下文还是策略快照（后者会改快照摘要）；默认关；谁能开；哪个阶段结束后变默认；关着的路径必须字节级不变（包版本串、提示词哈希）要写成硬约束。
9. **各阶段启用哪些决定类型。** 需要一张「阶段 × 决定类型」表：每个阶段哪些类型只解码、哪些可准入、哪些可执行。REFINE 与 SELECT_METHOD 的线上差别也要写清。
10. **提示词第一版。** 计划只有原则（第 58–59 节）。需要给出提示词正文或至少必含段落清单、版本命名、与请求包版本的配对规则、冻结哈希政策、旧提示词保留方式。
11. **反馈怎么回到模型。** `PlanningFeedbackV1` 放进请求包的哪个字段；`retry_budget_remaining` 取自现有哪个上限（合成最多问两次、规划轮数、根评审修复次数）。
12. **决定是否落库。** 第 77 节要求可解释，第 78 节说恢复不依赖模型内部状态，但没说决定本身存不存。须写明：是否新增事件或表、载荷内容、库结构迁移、旧模式下不得多发任何事件（否则旧模式黄金事件会红）。
13. **未定义的类型。** 计划引用但没定义：AlternativeSummary、ReuseHint、OrderHint、PlanningDecisionPayload 的联合形式、PlanningProblemDetail，以及请求包里的各个 View（目标、责任、计划、方法、事实、已验收结果、失败、能力）。H1 用到的须在 H1 前定义，其余标明归属阶段。

## 第二组：全计划层面需要补的

14. **适用基线过期。** 计划写 f2dfa64；现为 0.12.2（发布提交 7f839f0，代码 c0e13a4）。之后新增了四片机制：修复轮收敛在跑的兄弟工作、按准则驱动的写步骤与测试端口、只读叶写保护、相同失败三次早停与写型产物登记。
15. **与现有确定性修复机制的关系没写。** 现网已有：修复轮（退役 + 展开）、只读叶拒绝有界并升级、证据饱和跳过规划直接合成、合成最多问两次、根评审修复上限、相同失败早停、交接后未知结局有界停机。H3/H4 会和它们正面相撞。需要一节逐项写明：保留为确定性兜底、改由模型决定、还是映射成哪种修复动作。已知问题（早停后未退役所属方法实例，导致修复提案接不上）应并入 H4。
16. **每阶段的验收门槛要量化。** 回归基线（新模式 2960 通过 / 2 跳过，旧模式 560 / 13 / 0）；新模式哨兵计数（现 19）允许涨到多少；每片至少几个变异测试；独立核验（实施与核验分属不同会话）；每阶段是否要真实模型验收、跑哪些题、开关状态、通过标准（建议：同 14 局不劣于 0.12.2 成绩，硬不变量全真）。
17. **合同目录的改动许可。** 现行纪律是合同目录只读。计划要在该目录新增三个文件。须明示：允许新增文件；既有合同的规范字节一律不变。
18. **版本与发布节奏。** 这是 0.13.0 还是 0.12.x；每个阶段是否单独发候选版；Host 何时跟进钉版。
19. **审计要求。** 用户已要求计划、真实模型做题记录、修补过程、重跑都成文入库。计划第 69 节的交付物清单应加上「更新审计包」。

## 第三组：H2–H8 各自开工前须补到 H1 同等粒度

20. **H2 请求包。** 各 View 的字段；「删除分散拼包逻辑」具体指哪些调用点；包大小预算；旧包版本串如何并存。
21. **H3 方法选择。** 多候选时问模型的触发条件（几个算多、什么叫高价值）；确定性快路的政策开关；对模型调用数与成本的影响上限；和「证据饱和直接合成」的先后。
22. **H4 修复决定。** 第 14 节只列了动作类型，`RepairAction` 本身的字段没定义；每种动作的准入规则与编译产物；影响分析的算法输入输出；五个触发源各自的接线点。
23. **H5 领域包。** ObjectSchema、TaskTypeSpec、ObserverRegistration 未定义；现有代码领域与 AppWorld 领域怎么迁；「核心」的目录边界在哪（否则「核心里不许出现 if domain」无法用脚本检查）。
24. **H6 方法生命周期。** 评估集从哪来；评估结论枚举；晋级门槛；离线评估的运行方式。
25. **H7 后端端口。** PlanningProblemSnapshot、PlanningLimits、各 Backend* 类型未定义；现有 PANDA 适配器的迁移步骤。
26. **H8 跨领域验收。** 无人机领域用模拟器还是真机；安全边界；验收题目清单；第 62 节四臂评测里「强单体」臂的定义、题集与预算。

## 可以先做什么

- **H0 冻结基线**：不依赖以上任何裁定，已安排。
- H1 中纯新增、不上线的部分（类型骨架、编解码、反例测试）技术上可先做，但其字段名与枚举取决于第一组第 1–4 条；建议等这四条裁定后再开，避免返工。
