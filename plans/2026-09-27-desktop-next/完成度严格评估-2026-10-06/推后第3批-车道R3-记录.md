### H08 预算补"执行者数""搜索次数"两维

- **原计划**：原文第 333 行 Mission 预算示例 `max_agents: 100`；第 1196～1209 行 §18.1"Budget 不只是钱"列 Token、Agent 数量、并发、GPU 时间、总运行时间、工具调用次数、搜索次数、真实费用。条目 `07-补齐清单.md` 第 29 行；排序 `09-推后必补-排序清单.md` 第 64 行（"桌面现在不用本机 GPU，可先做前两样"）。
- **现状**：`SDK/contracts/models.py:157-190` 的 `Budget` 只有 tokens、attempts、runtime、concurrency、tool_calls 五维；`SDK/governance/budgets.py:198-264` 的 `reserve` 只核 token、尝试次数、工具次数。
- **改成**：
  1. `Budget` 加 `max_agents`（执行者数）与 `max_search_calls`（搜索次数）。`None` 仍是"不限"。`inherit_limits` 一并继承。对外门面把两维列为"不对这个入口开放"（与 `max_tool_calls` 同列）。
  2. **执行者数**：每建一个执行尝试就起一个执行者会话，`reserve(counts_attempt=True)` 时在整条账户链上核"已起执行者数 < 上限"，并给 `agents_started` 加一。它和"尝试次数"的区别：尝试次数按 09-28 用户决定会退还非模型原因的失败；执行者数数的是真起过的会话，不退。超了按现有路径抛 `BudgetExhausted("agents")`，停止原因沿用 `budget_exhausted`。
  3. **搜索次数**：只数"检索类工具"的执行次数。检索类工具是网关里写死的一张表：`knowledge_list`（查黑板目录）、`assurance_find_evidence`（审阅员查证据目录）。读一条原文、读文件、列工作区不算。照工具次数的办法：建尝试时按账户链剩余（上限 − 已结清 − 在途预留）预留给这次尝试，网关按这个数拦，结清时按工具调用表里这次尝试真执行过的检索类调用数记账。**搜索次数用完不停任务**：预留为 0 的尝试照常开工，只是检索类工具被网关拒绝（拒绝码 `search_budget_exhausted`），执行者照样可以读文件、写文件、交结果。
  4. 库表加第 48 版迁移：`budget_accounts` 加 `agents_started`、`reserved_search_calls`、`settled_search_calls`；`budget_reservations` 加 `reserved_search_calls`、`settled_search_calls`。

- **GPU 时间**：不做。桌面不用本机 GPU，没有可数的事实来源。写偏差单 R3-偏差-1。
- **守的保证**：两维默认 `None`，默认路径不预留、不拦、不停，现有任务结局不变；子预算不大于父预算（§18.2）照旧；预留在前、结清按事实（§18.3）。

### H10 执行者"申请更多资源"的通道

- **原计划**：原文第 840～853 行 §12.3 Agent 可产出"资源申请"；第 983～1000 行 §15"Agent 可以提出：……申请更多预算"，"Agent 不直接扣减或增加全局预算"；第 1707～1718 行第 9 步"Resource Request"。条目第 31 行；排序第 65 行（"申请走'提案 → 核预算 → 提交'，不由 Harness 判该不该给"）。车道说明第 3 条。
- **现状**：执行者模板 `SDK/runtime/role_templates.py:564` 结果信封里没有资源申请字段；`SDK/orchestrator/event_handler.py:8078-8121` 解析信封时未知字段一律拒；资源不够只能交 blocked / failure，再由修复请求交规划器。
- **改成**（三步，一条路）：
  1. **提案**：结果信封可带 `resource_request: {"dimension": "tool_calls", "amount": 正整数, "reason": 文字}`。只认 `tool_calls`（这是 Harness 按尝试发放、执行者会用完的那一份额度；token 预留本来就按需增长，不用申请）。解析时像 `outputs` 一样先从块里取下再按合同校验；只能跟 blocked / failure / no_progress 一起交，跟候选结果一起交按"信封不合格"拒（同一件事只有一个时机）。
  2. **核额度与上限**（只核数，不判该不该给）：上限 = 部署的单回合工具次数（一次申请最多再要一份基础额度，重试那一回合最多两倍）；额度 = 账户链上工具次数还剩多少（不限时不核）。核的结果连同申请原样写进 `ResourceRequested` 事件，与这次结果的 `OutcomeRecorded` 在**同一个事务**里落库。核不过的也照实记（`fits: false` 带数字），不另开分支。
  3. **提交给判断方**：这一步失败本来就会生成修复请求交规划器；请求明细里多带一段 `resource_request`（申请、核的结果、"若批准原样重试，下一次尝试多给这些工具次数"）。**该不该给由规划器按现有路径判**：它选"原样重试"（`RETRY_SAME_METHOD`）就是批准，选别的就是不批。批准后建下一次尝试时，Harness 再核一次额度，把 `resource_grant` 冻进这次尝试的派发配置，工具上限 = 基础额度 + 批准数，并在建尝试的同一事务里记 `ResourceGranted`；额度这时已不够就不发放，记 `ResourceGrantLapsed`（带数字），尝试照常按基础额度开工。执行图的派发核对（`SDK/orchestrator/taskgraph_execution_policy.py:183-195`）认这份冻结的发放：只有能在库里找到对应的 `ResourceRequested`（同一步、同维度、同数量、核过、且不超上限）时才放宽上限。
- **为什么没把语义判断写进 Harness**：Harness 只回答两个数——"要的数超不超部署上限""账上还有没有"。"这一步值不值得多给"交规划器，它看得到执行者的原话和失败事实；Harness 不按执行者理由的文字分类，不按次数自动批准。
- **删掉的旧路径**：没有。现有"失败 → 修复请求 → 规划器"就是判断通道，申请挂在它上面，不另开旁路。
- **守的保证**：执行者不能自己加预算（§15）——只有规划器的重试决定落库后、且额度再核一遍通过，才发放；发放有上限（≤ 基础额度）、可审计（申请、发放、过期三个事件）；默认路径上执行者不会带这个字段，结局不变。
- **偏差**：执行者模板与工具说明不能改（会让已有执行池起不来、也会改变每个执行者的输入），所以执行者现在不知道有这个字段。写偏差单 R3-偏差-2，停在"告诉执行者"这一处，Harness 一侧做完。
- **怎么测**：新文件 `tests/orchestrator/test_defer3_r3_resource_request.py`。①合同：字段形状、只认 tool_calls、跟候选一起交被拒；②核额度：超上限 / 超账户剩余记 `fits: false`；③产品同形任务：执行者交 blocked + 申请 → `ResourceRequested` 与 `OutcomeRecorded` 同事务 → 修复请求明细带申请 → 规划器原样重试 → 下一次尝试工具上限 = 基础 + 批准数、记 `ResourceGranted`；规划器不重试则不发放。改坏：去掉派发核对里"库里必须有对应申请"那道查。

### H12 审阅积压时补"加审阅并发""暂停新拆分"

- **原计划**：原文第 1266～1295 行 §18.5 Backpressure 六种应对，其中第 1279 行"提高 Verifier 资源"、第 1281 行"禁止新任务继续分裂"；第 1282 行"合并重复候选"按排序清单第三节（第 104 行）不做——判断两个候选重不重复是语义判断。条目第 33 行；排序第 66 行（警告：并发上限在准入身份里，按事件动态调，不改默认值）。车道说明第 2 条。
- **现状**：`SDK/scheduling/backpressure.py:28-200` 只观测三维、出"升起/回落"信号；`SDK/orchestrator/event_handler.py:9185-9218` 每轮观测；积压时只会降执行并发、缩预留（`SDK/scheduling/allocator.py`、`event_handler.py:10760-10761`）。审阅并发固定读 `verifier_workers`（`event_handler.py:3948、3955、3963`，`SDK/runtime/assembly.py:118` 默认 2）；规划轮在积压时照常开（`event_handler.py:3183-3200`）。
- **改成**：
  1. `backpressure.py` 加纯函数 `backlog_response(state, ...)`：只看"待审结果"这一维是否升起及升起多久，算出两件事——这一轮审阅并发是多少、要不要暂停新拆分。
  2. **加审阅并发**：待审结果维升起时，审阅并发 = 新配置 `verifier_workers_ceiling`（默认 `None` = 2 × `verifier_workers`，必须 ≥ `verifier_workers`）；回落后回到 `verifier_workers`。**不改 `verifier_workers` 默认值、不改 `max_concurrent_model_calls`、不碰准入身份**；真正同时发出的模型调用仍受执行池准入名额管。审阅循环三处直接读配置的地方改成读这一个函数，只留一条路。
  3. **暂停新拆分**：待审结果维升起时，已有计划的任务不再开**新的**规划轮（`_resume_planning_services` 原地等）；正在进行的规划轮、同一请求的格式重试、首次规划不受影响。暂停有上限：连续暂停超过新配置 `decomposition_pause_seconds`（默认 600 秒）就自动解除并记原因。暂停期间空闲判定把它当合法等待（`VERIFICATION_BACKLOG`），不会因此走"没有可派发的工作"停任务——默认路径上不加新的停止条件。
  4. **可审计**：两件事的状态一变（升起、回落、暂停到期），在每个在跑任务的时间线上记一条 `BacklogResponseChanged`（审阅并发前后值、上限、是否暂停、原因、起始时刻）；状态存在调度器状态 `backlog_response`。
- **为什么没把语义判断写进 Harness**：触发只看一个计数（待审结果数）过高低水位；动作只有"多开几个审阅名额""先不开新规划轮"，都是秩序。不判断哪个规划轮会拆、哪个候选重复；"合并重复候选"不做。
- **删掉的旧路径**：审阅循环里三处直接读 `self._config.verifier_workers` 的判断删掉，换成同一个函数。
- **守的保证**：并发上限默认值与准入身份不变；动态值有上限（`verifier_workers_ceiling`）；暂停有时限；积压消退后两件事都恢复；不产生新的停止原因。
- **怎么测**：新文件 `tests/orchestrator/test_defer3_r3_backlog_response.py`。①纯函数：积压升起 → 并发到上限、暂停；回落 → 恢复；暂停超时 → 解除；②"积压时动态加并发有上限、积压消退后恢复"：用水位状态机连走升起、维持、回落三步，并发值依次为上限、上限、基础值；③产品同形任务：积压时 `_resume_planning_services` 不开轮、空闲判定为等待、记 `BacklogResponseChanged`；回落后照常开轮。改坏：让函数在回落后不恢复基础值。

- **改成**（每项的口径，全部只数事件或表行）：
  1. 新思路数 = 各次 `PlanRevisionCommitted` 里"采用的做法实例"个数之和。
  2. 剪枝率 = 各次计划修订"退掉的做法实例"个数之和 ÷ 采用个数之和（分支 = 做法实例）。
  3. 重复率 = 沿用 H06 的结果内容哈希计数（`stop_conditions.result_hashes` / `duplicate_count`）：重复数 ÷ 结果数。
  4. 知识污染率 = 已验证知识后来被新结论顶出争议（`ClaimDisputed` 且当时对方状态为 `VERIFIED`）的不同条目数 ÷ `KnowledgeCommitted` 数。
  5. 误报率 = 根终审打回次数（`HierarchicalRootReviewRejected`）÷ 根终审送审次数（`HierarchicalRootReviewCut`）。根终审只在全部叶子都已验收通过后才送审；它打回，就是"下层都判通过、独立上层判不通过"——事件上最接近"判了通过其实不该过"的事实。

  8. 每成功任务成本：单个任务给本任务 token 合计与"成功时的成本"；全库给已结束任务的 token 合计 ÷ 成功任务数。编排只记 token，不记金额。

- **守的保证**：只读、不写库、不调模型；口径写进函数说明，界面不改。
- **怎么测**：新文件 `tests/orchestrator/test_defer3_r3_metrics.py`（SDK）：在产品同形任务上补齐事件后逐项核对数值；空任务各比率为空不报错。Host：`backend/tests/orchestration/test_diagnostics_contract.py` 改断言（新块、新键）。改坏：重复率改成数不同哈希。

## 五、口径说明（请主会话评估时确认）

1. **H12"暂停新拆分"的范围**：Harness 事先不知道一个规划轮会不会拆新步骤（那是规划器的判断），所以按秩序做成"积压期间，已有计划的任务不开**新的**规划轮"（细化、修复都暂停）；首次规划、已开的规划轮、同一请求的格式重试不受影响。有 600 秒时限，期间空闲判定当合法等待，不会因此停任务。
2. **H12"加审阅并发"的实际效果**：多开的是审阅任务名额；真正同时发出的模型调用仍受执行池准入名额（`max_concurrent_model_calls`，默认 2）管——这一项按要求不动。所以准入名额小于审阅名额时，多开的审阅会排队等名额。
3. **U05 误报率**：没有"判通过其实不该过"的直接事件，取"根终审打回 ÷ 根终审送审"（根终审只在全部叶子验收通过后才送审）。新思路数取"采用的做法实例数"，剪枝率取"退掉的做法实例 ÷ 采用的做法实例"。知识污染率取"已验证知识被顶出争议的不同条目 ÷ 入库数"。
4. **H08 执行者数不随"非模型原因失败退次数"退还**：09-28 用户决定讲的是任务尝试次数；执行者数数的是真起过的会话，两者分开。默认不限，不影响现有任务。
