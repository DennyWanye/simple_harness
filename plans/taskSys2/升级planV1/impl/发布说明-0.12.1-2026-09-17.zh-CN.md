## 2. 变了什么

完整清单见 SDK 仓库 `CHANGELOG.md` 顶部的 **0.12.1 — P2.3d：Grok 验收暴露的分层闭环缺陷修复**
条目，以及 Host 这份 `sdk-docs-release-v0.12.1.md`（SDK `docs/release/v0.12.1.md` 的底稿，
验收重跑期间不进 SDK 主树）。细节来自 SDK `plans/2026-09-16-full-target/P2.3c/journal.md`
第四部分。一句话：

> Grok 验收 H 臂 40 局 `mission_status = COMPLETED` 为 **0**，四类失败全部可复现、全部
> 确定性。本版按诊断顺序修了七条分层闭环缺陷；旧模式（`orchestration_semantics_version=legacy`，
> 默认）零回归。

七条：

1. **D1 AppWorld 分层 Worker 模板**。新增提示词 `worker-appworld-hierarchical-v1`
   （由 `worker-appworld-v3` 派生，保留六个 AppWorld 工具含 `appworld_execute`，
   加 decision 4 的 `outputs` 字段）。`HIERARCHICAL_WORKER_VERSIONS` 改为域模块注册后冻结；
   兜底按 `domain_for(mission)` 选域版本。域→版本指针放在
   `governance.domains.HIERARCHICAL_WORKER_TEMPLATES`，**不进** `DomainProfileV1.role_templates`
   （那张表被调用方整体遍历为角色名）。域档 `APPWORLD_PROFILE` 逐字节未动。
   此前 L1 20 局 Worker 报 `tool_not_exposed` 且读到代码域「跑 pytest」的提示词。

2. **D2b 证据饱和准入合成轮**。`goals_needing_method` 新增「同一命题被同一观察器
   OBSERVED ≥N 次且真值仍 UNKNOWN」的判定，该 `NEEDS_EVIDENCE` 视同可被别的方法绕开、
   准入合成轮；N = `HierarchicalDispatch.evidence_saturation_rounds`（默认 2）。
   **I18 未放宽**：不把 UNKNOWN 变成 TRUE，也不开安全闸。此前 L3 六局活锁。

3. **D2c 规划拒绝理由码拆分**。`__cause__` 是 `BlockError`（或回合根本没 COMMITTED）→
   `proposal_unreadable`；读懂了但被内容规则拒 → 新理由码 `proposal_not_grounded`。
   `max_planning_attempts` 出厂默认仍是 2（改默认会动配置快照字节；runner 显式传参）。

4. **D3 终结步输出端口**。端口集合的定义由「被 `DataRequirement` 消费」扩为
   「被 `DataRequirement` 消费 **∪** 被 `composition.criterion_links` 引用
   （尤其 `finalizer_step`）」。新增 `accepted_outputs.output_ports_in_revision()`，
   上下文包、验收索引与 `OUTPUT_PORT_UNCLAIMED` 三条生产路径共用同一答案
   （另含诊断漏点的第四处 `leaf_acceptance._outputs`）。此前终结步叶子从未被告知端口、
   `outputs` 永远为空、根评审以 `evidence.kind=none` 判 FAIL，10 局倒在最后一米。

5. **D4 分层 Mission 不开 legacy 管理轮**。`_request_management` 加模式分支，记新事件
   `ManagementNotApplicableUnderHierarchical{SEMANTICS_IS_HIERARCHICAL, redirect: commit_plan_revision}`；
   不再产生 `ManagementRequested` / `ManagementDecided`。manager 轮次不再被必然失败的
   修复循环烧掉，`no_progress` 上限也不再作用于分层 Task（短路后不进 `_enforce_no_progress`，
   重复验证失败只受 `max_attempts` 约束）。此前 L1 20 局 `management_exhausted` + L4 3 局
   `no_progress`。

6. **D5-A 根验收拒绝后重开一轮 Planner**（§9.1 最小分支）。findings 含 `severity=blocker`
   时，把 findings 作为 `PlanningRejected{root_review_rejected}` 反馈重开一轮 Planner；
   上限 `OrchestratorConfig.max_root_review_repairs`（默认 1 次/plan_revision），超限才进
   idle stall。

7. **D5-B 嵌套 compound 细化**。规划触发条件扩为「`CREATED` 或存在未细化的 compound 占位」，
   每 plan_revision 一轮；判据与 `goals_needing_method` 相同（`adopted_instance_for is None`，
   不是 `ReadinessReason.NEEDS_REFINEMENT`）。已提交计划的 Mission 不再被一次事后规划轮判死。
   界限本身落成 durable 事件 `HierarchicalRefinementRequested`。

另外：冒烟收口断言现在要求**每一条** `AcceptanceCommitted.accepted_outputs` 非空——
0.12.0 的 COMPLETED 是评审员宽容而非机制成立。独立审阅「需修后合」的处置（P0-1 预算耗尽
走 `_stop_planning_round`、P1-1 合成轮在途时梯子等待、P1-2 新注册 `worker-hierarchical-v2`
等）已并入本版。真实模型冒烟已跑到 **COMPLETED**（`deepseek-flash`，
`mission-3243bfd86e5035d5`，四叶含终结步 `report` 端口全部有产物，根评审 1 刀 ACCEPT，
137 906 token）。

要点：

- **旧模式零回归**：不传 `orchestration_semantics_version` 的调用方行为与 0.12.0 一致。
- **新模式入口仍是** `orchestration_semantics_version="hierarchical"`。
- **存储**：schema 版本 18（未升）。
- **配置 digest 变了**：多 `max_root_review_repairs` 键。域档版本未变。

## 3. 另一台电脑：安装步骤

### 3.0 前置

- macOS 或 Linux；`git`；[`uv`](https://docs.astral.sh/uv/)（发布机用的是 0.12.8）。
- Python **3.11 或更高**。Host 的 `backend/.venv` 实测用 **3.12**；
  **不建议用 3.14**（见 §6 已知限制的 p33）。
- 不需要预装 SDK：Host 的 wheel 是 vendored 的。

### 3.1 克隆两个仓库（**必须是同级目录**）

SDK 的真实 Provider 夹具在找不到环境变量时，会回落去读
`<公共父目录>/simple_harness/.env`。两个仓库放成兄弟目录才能用这条回落路径。

```bash
mkdir -p ~/PROJECTS/SimplaHarness && cd ~/PROJECTS/SimplaHarness
git clone git@github.com:DennyWanye/simple_harness.git
git clone git@github.com:DennyWanye/simple-harness-sdk.git

cd simple-harness-sdk && git checkout v0.12.1 && git rev-parse HEAD
# 期望：05cfbb83a38d8342bf525992d56dab2491bba576
```

目录应长这样：

```text
~/PROJECTS/SimplaHarness/
├── simple_harness/          # Host
└── simple-harness-sdk/      # SDK 源码（跑 SDK 自己的测试用）
```

### 3.2 装 Host（钉死的 0.12.1 wheel）

```bash
cd ~/PROJECTS/SimplaHarness/simple_harness/backend
uv sync --extra dev
```

`uv sync` 会从 `backend/vendor/` 装那个 exact wheel（`pyproject.toml` 的
`[tool.uv.sources]` 与 `override-dependencies` 都钉了它）。**验证身份**：

```bash
.venv/bin/python -c "import simple_harness; print(simple_harness.__version__)"
# 期望：0.12.1

shasum -a 256 vendor/simple_harness_sdk-0.12.1-py3-none-any.whl
# 期望：18fbd91cdac24f53419b6d8bdcc0049bd51fcb5bf9be180ab15f3e81c07d34a7

.venv/bin/python -m pytest -q tests/sdk_adapters/test_sdk_candidate.py \
                               tests/sdk_adapters/test_sdk_source_identity.py \
                               tests/sdk_adapters/test_runtime_paths.py \
                               tests/sdk_adapters/test_conformance.py
# 期望：50 passed
```

最后一条会把 wheel 字节、候选清单 SHA-256、清单里的 commit 与
`sdk_candidate.py` 的常量**互相绑死**校验一遍 —— 任何一处对不上就 fail-closed。

### 3.3 装 SDK 源码环境（跑 SDK 自己的测试）

```bash
cd ~/PROJECTS/SimplaHarness/simple-harness-sdk
uv sync --frozen --group dev
```

**注意**：`tests/orchestrator/gap_phase1/` 与
`tests/integration/test_shared_capacity_dispatch.py` 用了
`@pytest.mark.asyncio`，而 `pytest-asyncio` **不在** dev 依赖组里；
仓库开了 `--strict-markers`，所以裸跑会在收集阶段直接 `Interrupted`。
跑到这些目录时要临时带上：

```bash
uv run --frozen --group dev --with pytest-asyncio --with 'pydantic>=2' pytest -q <路径>
```

### 3.4 配置真实模型（**不要把 key 写进仓库**）

两个互相独立的配置面，用途不同：

**(a) Host 产品运行时** —— 文件（macOS）：

```text
~/Library/Application Support/com.dennywanye.simpleharness/llm_runtime.json
```

JSON 字段名（**只列字段名，值自己填**）：

```json
{
  "base_url": "<OpenAI 兼容端点，通常以 /v1 结尾>",
  "model": "<模型 id>",
  "api_key": "<你的 key>"
}
```

> 这个文件就是产品既有的配置面，明文 key 是既定做法。**不要**把它复制进仓库、
> 日志或证据目录。若用 `--userdata` 指向某份数据副本，**决定 provider 的是那份副本里的
> `llm_runtime.json`**，`--model` / `--env-file` 不生效。

**(b) SDK 的 opt-in 真实 Provider 测试** —— 优先读环境变量，其次回落 Host 仓库的 `.env`：

| 环境变量 | 回落到 `simple_harness/.env` 的键 | 含义 |
|---|---|---|
| `SH_BASEURL` | `BASEURL` | OpenAI 兼容端点 |
| `SH_APIKEY` | `APIKEY` | key（夹具的 `__repr__` 会打成 `<redacted>`） |
| `SH_MODEL` | `MODEL` | 模型 id，缺省 `gpt-5.6-luna` |

`base_url` / `api_key` 任一缺失 → 测试 **skip**，不会假装通过。

**模型建议**：`deepseek-flash`。注意官方端点的 id 就是 `deepseek-flash`；
请求 `deepseek-v4-flash` 会 echo 回不匹配的 id。

## 4. 跑一个最小的 code 域分层 Mission（新能力）

**不要手搓**。分层 Mission 需要装配 `PlanningWorld`、注册根 Obligation、
admit demand、安装观察器 —— 这些步骤仓库里已经有一个**就是为此写的**端到端用例：

```text
tests/orchestrator/full_target/test_real_provider_hierarchical_smoke.py
    ::test_real_hierarchical_planner_round
```

0.12.1 起它还断言**每一条** `AcceptanceCommitted.accepted_outputs` 非空
（终结步 `report` 端口必须有产物）。

**怎么跑**：

```bash
cd ~/PROJECTS/SimplaHarness/simple-harness-sdk

export SH_BASEURL='<端点>'
export SH_APIKEY='<key>'          # 不要 echo 出来、不要进 shell history 文件
export SH_MODEL='deepseek-flash'

uv run --frozen --group dev pytest -q \
  tests/orchestrator/full_target/test_real_provider_hierarchical_smoke.py \
  --run-real-provider -m real_provider
```

两个开关**都要**：

- `--run-real-provider` 是 opt-in 开关（`tests/conftest.py`），不给就整条 skip；
- `-m real_provider` 只选真实 Provider 用例。

**怎么读结果**（这个用例断言的是**闭包**，不是模型的措辞）：

- 任何一轮出现 `proposal_unreadable` → **失败**（这是 P2.3b 修掉的旧缺陷）；
- Mission 要么 `COMPLETED`，要么是**诚实的停**：没完成，且每一次拒绝都带结构化机器可读理由
  （如 `no_dispatchable_work`、`READ_SET_UNRESOLVED`、`OUTPUT_PORT_UNCLAIMED`）。
  「诚实地停」也算用例通过 —— 模型是随机的，规格是「永不假装成功」。
- 原始收据落 `.local-test-evidence/`（已 gitignore），key 不会进去。

发布机上这条链路在 P2.3d 已真跑通过一次：`mission-3243bfd86e5035d5`，
`COMPLETED / verification_passed`，四叶含终结步 `report` 端口全部有产物，
根评审 1 刀 ACCEPT，结算 137 906 token。

**预算提醒**：分层 Mission 收尾会花**两次** mission 账户的模型调用（根评审人 +
既有的 Mission Judge）。按两次算预算。

## 6. 已知限制（遇到不要当成新 bug）

1. **Grok 两臂验收重跑尚未完成。** 本版修的就是 H 臂 40 局 COMPLETED=0 的确定性缺陷；
   修完之后的两臂重跑还没跑。journal 第四部分 §2e 也记了：§2d 那次 COMPLETED 跑在
   审阅处置之前的代码上，Grok 重跑前值得再跑一次冒烟。
2. **M3 共享复用依赖 P3.2 未并入。** 本版不包含共享子目标复用；那条轴在 P3.2。
3. **PANDA/HDDL 后端是 stub**。本机没有 cmake / gengetopt，`planning/htn/backends/panda.py`
   走 stub 路径。配置 `SH_PANDA_PARSER` 指向真 parser 后，相关真实用例会自动启用。
4. **AppWorld 相关用例需要独立的 `appworld-venv`**，不在 Host 的 `backend/.venv` 里。
   没有它时那些用例是 skip / error，属环境缺口。
5. **策略快照 digest 又变了**：`to_json()` / `policy_snapshot()["config"]` 多
   `max_root_review_repairs`（默认 1）。0.12.0 的 `7cf60224…` 不再成立。
   仓库里没有钉死该 digest 的常量，但**任何依赖旧 digest 做外部对照的脚本必须重取基线**。
6. **分层 Mission 收尾两次 mission 账户模型调用**（根评审人 + Mission Judge）。
   预算守恒按两次算。
7. **L2 `appworld` 谓词的 `app` 参数受 `PUBLIC_READ_APIS` 限制**。
   非 `supervisor` 应用读不到，返回 `OBSERVER_UNAVAILABLE`（诚实的 UNKNOWN）。
   runner 把 `app` 钉成 `"supervisor"` 的做法仍然有效且仍然必要。
8. **Python 3.14 下 `p33` 已知红**：
   `tests/orchestrator/.../p33::test_legacy_check_ast_and_default_retrieval_bytes_are_unchanged`
   断言的是历史 AST 字节 hash，3.14 的 AST 变了。**用 3.12 就不会红**。
9. **`reuse lint` 在 SDK 仓库是红的**（本次扣除构建产物后 174 个文件缺 SPDX 头；
   0.12.0 记 184）。同类既有缺口，不是这一版引入的。
10. **`mypy` 17 errors / 4 files 是基线**（评测适配层缺可选依赖）。
11. **SDK 全仓裸 `pytest -q` 会被收集错误打断**，全部是环境缺口（缺
    `pytest-asyncio` / `pydantic` / 已下线的 `simple_harness_memory`）。按 §3.3 加两个
    `--with` 即可。
12. **`tiktoken` 是个没被任何依赖组声明的可选依赖**。不装它，`tests/agents` 有 15 条红、
    `tests/orchestrator/p33` 有 6 条红。**必须装进 `.venv`**（`uv pip install tiktoken`），
    `uv run --with tiktoken` 不管用 —— 相关代码在子进程里 import，拿不到 uv 的临时叠加层。
13. **`psutil` 同理**（`local-capacity` extra）：不装，`tests/execution/test_shared_capacity.py`
    11 条红。
14. **不要给全仓跑加 `pytest-asyncio`**：装上 1.4.0 后
    `tests/integration/test_shared_capacity_dispatch.py` 会永久挂起，`tests/orchestrator`
    全量也会卡在 56%。gap_phase1 单独跑。

### 6b. 从 0.12.0 留下的两条真实遗留（SDK 侧，不影响 wheel 运行）

- **F-REL-1**：`tests/unit/contracts/public-api.json` 的版本戳仍是 `0.11.1`，
