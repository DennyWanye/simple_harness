## 2. 这个版本解决了什么

一句话：0.12.1 修完「分层 Mission 根本跑不完」之后，Grok 真实验收又暴露出一串确定性缺陷（规划循环提前退出、provider 一卡住就挂死、合成器格式对不上、根评审看不见证据、修复轮没方法库、只读叶子乱改文件、测试写了却不进树……）。**0.12.2 把 P2.3e 到 P2.3v 这十八片全部合进去。** 默认旧模式没动。

用人话概括几件你会碰到的：

- 规划时模型还在想，编排不再自己把循环烧完然后假装没活干。
- 模型接口抖一下（超时、未知用量）会有界重试，再不行就具名停机，不再空等到墙钟。
- 合成新方法时，格式不对或引用写错会再问一次，而不是直接判死刑。
- 根评审能读到叶子产物摘要和用户原话目标，不再对着空包乱 REJECT。
- 根评审说「不行」之后，系统会带上拒绝理由换方法或再合成，而不是方法库空空如也。
- 只读检查叶子改不了已有源码（事前挡住）；需要新增的测试由写代码那一步声明，检查叶子负责跑。
- 下游检查能看到上游已经改好的文件；写型步骤只交 diff 时也会把文件登记进工作区。
- 同一处连续失败三次就早停，停机原因写得清楚（不再靠烧光预算来停）。
- 账本：用量是否全部已知（`usage_fully_known`）和预算是否守恒（`budget_conserved`）分开看。

旧模式（不传 `orchestration_semantics_version`）行为与 0.12.1 一致。新能力入口仍是 `orchestration_semantics_version="hierarchical"`。

## 4. 另一台电脑：怎么装、怎么验

### 4.0 前置

macOS 或 Linux；`git`；[uv](https://docs.astral.sh/uv/)。Python **3.11+**（实测 3.12；**别用 3.14**）。两个仓库必须是**同级目录**。

### 4.1 克隆并对齐标签

```bash
mkdir -p ~/PROJECTS/SimplaHarness && cd ~/PROJECTS/SimplaHarness
git clone git@github.com:DennyWanye/simple_harness.git
git clone git@github.com:DennyWanye/simple-harness-sdk.git

cd simple-harness-sdk && git checkout v0.12.2 && git rev-parse HEAD
# 期望：7f839f0e3d83aa17a0d0e2e54157ca9b1c9465a5
```

**注意**：在指挥者把 SDK 的 `main` 和 tag `v0.12.2` 推上去之前，另一台机器 `git checkout v0.12.2` 会失败。本机已经打好本地 tag。

### 4.2 装 Host（钉死的 0.12.2 wheel）

```bash
cd ~/PROJECTS/SimplaHarness/simple_harness/backend
uv sync --extra dev

.venv/bin/python -c "import simple_harness; print(simple_harness.__version__)"
# 期望：0.12.2

shasum -a 256 vendor/simple_harness_sdk-0.12.2-py3-none-any.whl
# 期望：303aaf32b96a56edbe399fb3503be7c573d76951e73aba94fbcd8e5b1834b58d

.venv/bin/python -m pytest -q tests/sdk_adapters/test_sdk_candidate.py \
                               tests/sdk_adapters/test_sdk_source_identity.py \
                               tests/sdk_adapters/test_runtime_paths.py \
                               tests/sdk_adapters/test_conformance.py
# 0.12.1 钉版时这四套是 50 passed；身份对不上会 fail-closed
```

### 4.3 装 SDK 源码并跑回归冒烟

```bash
cd ~/PROJECTS/SimplaHarness/simple-harness-sdk
uv sync --frozen --group dev

PYTHONPATH=src uv run pytest tests/orchestrator/full_target -q -p no:cacheprovider \
  -k "frozen or version or changelog or sentinel"
# 发布机：102 passed / 2860 deselected

uv run --frozen --group dev pytest -q tests/orchestrator/full_target
# 流水线口径：2960 passed / 2 skipped
```

### 4.4 真实模型（可选）

**不要把 key 写进仓库。** Host 产品用用户数据目录里的 `llm_runtime.json`；SDK 测试读 `SH_BASEURL` / `SH_APIKEY` / `SH_MODEL`（或同级 Host 仓库 `.env` 的 `BASEURL` / `APIKEY` / `MODEL`）。缺了就 skip，不会假装通过。

```bash
cd ~/PROJECTS/SimplaHarness/simple-harness-sdk
export SH_BASEURL='<端点>'
export SH_APIKEY='<key>'
export SH_MODEL='deepseek-flash'
uv run --frozen --group dev pytest -q \
  tests/orchestrator/full_target/test_real_provider_hierarchical_smoke.py \
  --run-real-provider -m real_provider
```

两个开关都要。Mission 要么 COMPLETED，要么诚实停机（带机器可读理由）。「诚实停」也算用例通过。

## 5. 迁移注意（分层调用方）

- 方法升到 `@2`：`code.fix-by-patch` / `fix-by-revert` / `fix-by-assessed-revert`。旧 `@1` 还在库里，新提案不要点名 `@1`。runner 的 FREEZE-candidate 要按本版重生成。
- 默认提示词：Worker `worker-hierarchical-v4`，Planner `planner-hierarchical-v7`，合成器 `method-synthesizer-v7`，根评审 `root-reviewer-v3`。旧版字节没改，可以 pin。
- 新停机原因：`planning_failed`、`runtime_unavailable`、`root_review_repairs_exhausted`、`repeated_verification_failure`。
- `usage_fully_known` 和 `budget_conserved` 是两件事，不要把「有未知用量」当成「账不平」。

## 6. 已知问题（遇到别当成新 bug）

1. **N18（P2，不挡发布）。** M3 连续三次相同测试失败后正确早停，但修复提案编不进当前网，终态 `planning_failed`。M3 题目本来就没有根要求，不进 COMPLETED 地板。
2. **C1 两局是「隐藏测试未覆盖」，不是编排放水。** 编排走完了，根评审员自己填的 ACCEPT；红的是题面没写的窗口/时钟用例。
3. **C3 / M1 / M2-r0 没在第 6 版上重跑**，成绩来自第 5 批 `f2dfa64` 归档。
4. **N16**（交接后 5xx 短退避）本批没出现，仍是以后可选增强。
5. **F-REL-1 / F-REL-2** 从 0.12.0 留下：公开 API 快照版本戳、依赖锁哈希过期。不影响装载与执行。
6. 环境类：`tiktoken` / `psutil` 未声明会红一批测试；不要给全仓跑加 `pytest-asyncio`（会挂起）；Python 3.14 下 p33 AST 已知红。
