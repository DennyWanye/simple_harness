# 多层任务的中间层：审阅结果真正用起来（完成度评估第 3 项）

2026-09-30 深夜起草。第 5 项（审阅判不下来升级）之后做。

## 一、现状（核对代码与真机库后）

- 大任务分层：根目标 → 中间目标（比如"评估回归"下面拆成两个小步）→ 叶子步骤。叶子步骤通过验收后，中间目标要形成一份"目标结论"（GoalResolution），它后面按顺序排着的步骤才能开工，根终审也要它。
- 非保证通道下，中间目标的结论是**机械算出来的**（`composition_review._record`：每条判据只要有一个子步骤的验收记录上该判据通过，就算通过；审阅员名字是固定假名 `composition-reviewer`），没有模型看"拼起来对不对"。这就是"自己给自己打分"。
- **保证通道下（现在默认开）**，`resolve_one` 会向审阅运输层**发起**一次独立的组合审阅（`ensure_composition`，用途 COMPOSITION，真实审阅员、新会话），然后直接返回 None，代码注释写明"消费正式 COMPOSITION 记录、提交目标结论是终端写入方的活，这里不做"——**这个活从来没人做**：正式记录进来后没有任何代码读它去形成目标结论。
- 后果：保证通道下任何带中间层的计划，中间目标永远收不了尾，后面的步骤永远等，任务最后以"没有可派发的工作"失败。本机真机库里：0 条组合审阅、0 条非根目标结论——所有真机任务都是"根 → 叶子"两层，从没跑过三层，所以没暴露。
- 通过证书这一层也没有 COMPOSITION：`USE_TARGET_KINDS` 只有内容 / 终审 / 操作结果三种。

## 二、改法（都在 SDK）

1. **证书支持组合审阅**：`assurance_validity`：`USE_TARGET_KINDS["COMPOSITION"] = "task"`；新增 `prepare_composition_use(record, resolution_id)`（消费方 `COMPOUND_RESOLUTION`，其余同根终审的 `prepare_root_use`）。
2. **消费正式记录、形成目标结论**（`composition_review.resolve_one` 保证通道分支）：发起审阅后不再直接返回——若该包已有正式 COMPOSITION 记录：
   - **通过**：像根终审一样，读记录的有效评级，准备证书，构造 GoalResolution（判据结论从记录读，没判的写 UNKNOWN，不替审阅员补通过），`commit_goal_resolution`；提交里对保证通道的 COMPOSITION 用 `_require_assured_compound_use`（镜像 `_require_assured_root_use`）。
   - **打回 / 拒绝**：记一条修复请求（`PlanningRepairRequested`，原因 `composition_rejected`，带审阅员的具体意见，触发范围 = 该中间目标），交规划器处理（重做子步骤或换方法）；同一份记录只记一次。
   - **判不下来**：与第 5 项同一原则——运输层的"第一次判不下来就复审一次"对所有用途通用，已经生效；复审仍判不下来时，中间目标没有可挂起的"结果"，改登记一条阻塞式人工问题（选项：通过 / 打回，附审阅员疑点），用户选"通过"→ 写裁决回执 → 按"通过"分支走；选"打回"→ 修复请求。
   - 没有正式记录：照旧返回 None 等下一轮。
3. 非保证通道的机械算法保留（开发期不删旧路是因为它是非保证通道唯一的路，不是兼容）。
