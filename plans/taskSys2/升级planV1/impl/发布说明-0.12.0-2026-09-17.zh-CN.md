## 2. 变更摘要

完整清单见 SDK 仓库 `CHANGELOG.md` 顶部的 **0.12.0 — FULL-TARGET-1.4 P0–P2：HTN
递归任务分解端到端** 条目，以及 SDK `docs/release/v0.12.0.md`。一句话：

> 这一版把 **HTN 递归任务分解**从契约一路接到了端到端可跑：方法注册/准入/grounding/
> refinement → 编译成 TaskNetwork → `commit_plan_revision` 整数闸门提交 → `allocate_v2`
> 派发 → 叶子验收落 `acceptance_outputs` → 根 MISSION_FINAL 评审裁剪 → 根 GoalResolution
> 触发 Mission COMPLETED。

要点：

- **旧模式零回归**：`MissionSpec.orchestration_semantics_version` 默认 `legacy`。
  legacy 事件字节 golden、allocator/frontier 源码 hash、冻结提示词摘要全部未变。
  不传这个字段的调用方行为与 0.11.x 一致。
- **新模式入口**：`orchestration_semantics_version="hierarchical"`。
- **存储**：schema 版本 18（迁移 16、17 的校验和逐字节未动）。
- **观察器**：code / appworld 只读谓词观察器 + 6 条 L2 业务状态谓词，三态
  （TRUE / FALSE / UNAVAILABLE），解析失败**永不**变成 FALSE。
- **真实模型冒烟**（`deepseek-flash`）：分层 Mission 由根 Resolution 触发到 COMPLETED。

## 3. 另一台电脑：安装步骤

### 3.0 前置

- macOS 或 Linux；`git`；[`uv`](https://docs.astral.sh/uv/)（发布机用的是 0.12.8）。
- Python **3.11 或更高**。Host 的 `backend/.venv` 实测用 **3.12**；
  **不建议用 3.14**（见 §6 已知限制的 p33）。
- 不需要预装 SDK：Host 的 wheel 是 vendored 的。

### 3.1 克隆两个仓库（**必须是同级目录**）

SDK 的真实 Provider 夹具在找不到环境变量时，会回落去读
`<公共父目录>/simple_harness/.env`。两个仓库放成兄弟目录才能用这条回落路径。

```bash
mkdir -p ~/PROJECTS/SimplaHarness && cd ~/PROJECTS/SimplaHarness
git clone git@github.com:DennyWanye/simple_harness.git
git clone git@github.com:DennyWanye/simple-harness-sdk.git

cd simple-harness-sdk && git checkout v0.12.0 && git rev-parse HEAD
# 期望：a8e902a6ad18ade512fe38830de551819adb323c
```

目录应长这样：

```text
~/PROJECTS/SimplaHarness/
├── simple_harness/          # Host
└── simple-harness-sdk/      # SDK 源码（跑 SDK 自己的测试用）
```

### 3.2 装 Host（钉死的 0.12.0 wheel）

```bash
cd ~/PROJECTS/SimplaHarness/simple_harness/backend
uv sync --extra dev
```

`uv sync` 会从 `backend/vendor/` 装那个 exact wheel（`pyproject.toml` 的
`[tool.uv.sources]` 与 `override-dependencies` 都钉了它）。**验证身份**：

```bash
.venv/bin/python -c "import simple_harness; print(simple_harness.__version__)"
# 期望：0.12.0

shasum -a 256 vendor/simple_harness_sdk-0.12.0-py3-none-any.whl
# 期望：76150c61e32eba233b95783db838bead15b6b7c15927682b7010be59ee1d533c

.venv/bin/python -m pytest -q tests/sdk_adapters/test_sdk_candidate.py \
                               tests/sdk_adapters/test_sdk_source_identity.py \
                               tests/sdk_adapters/test_runtime_paths.py \
                               tests/sdk_adapters/test_conformance.py
# 期望：50 passed
```

最后一条会把 wheel 字节、候选清单 SHA-256、清单里的 commit 与
`sdk_candidate.py` 的常量**互相绑死**校验一遍 —— 任何一处对不上就 fail-closed。

### 3.3 装 SDK 源码环境（跑 SDK 自己的测试）

```bash
cd ~/PROJECTS/SimplaHarness/simple-harness-sdk
uv sync --frozen --group dev
```

**注意**：`tests/orchestrator/gap_phase1/` 与
`tests/integration/test_shared_capacity_dispatch.py` 用了
`@pytest.mark.asyncio`，而 `pytest-asyncio` **不在** dev 依赖组里；
仓库开了 `--strict-markers`，所以裸跑会在收集阶段直接 `Interrupted`。
跑到这些目录时要临时带上：

```bash
uv run --frozen --group dev --with pytest-asyncio --with 'pydantic>=2' pytest -q <路径>
```

### 3.4 配置真实模型（**不要把 key 写进仓库**）

两个互相独立的配置面，用途不同：

**(a) Host 产品运行时** —— 文件（macOS）：

```text
~/Library/Application Support/com.dennywanye.simpleharness/llm_runtime.json
```

JSON 字段名（**只列字段名，值自己填**）：

```json
{
  "base_url": "<OpenAI 兼容端点，通常以 /v1 结尾>",
  "model": "<模型 id>",
  "api_key": "<你的 key>"
}
```

> 这个文件就是产品既有的配置面，明文 key 是既定做法。**不要**把它复制进仓库、
> 日志或证据目录。若用 `--userdata` 指向某份数据副本，**决定 provider 的是那份副本里的
> `llm_runtime.json`**，`--model` / `--env-file` 不生效。

**(b) SDK 的 opt-in 真实 Provider 测试** —— 优先读环境变量，其次回落 Host 仓库的 `.env`：

| 环境变量 | 回落到 `simple_harness/.env` 的键 | 含义 |
|---|---|---|
| `SH_BASEURL` | `BASEURL` | OpenAI 兼容端点 |
| `SH_APIKEY` | `APIKEY` | key（夹具的 `__repr__` 会打成 `<redacted>`） |
| `SH_MODEL` | `MODEL` | 模型 id，缺省 `gpt-5.6-luna` |

`base_url` / `api_key` 任一缺失 → 测试 **skip**，不会假装通过。

**模型建议**：`deepseek-flash`。注意官方端点的 id 就是 `deepseek-flash`；
请求 `deepseek-v4-flash` 会 echo 回不匹配的 id。

## 4. 跑一个最小的 code 域分层 Mission（新能力）

**不要手搓**。0.12.0 的分层 Mission 需要装配 `PlanningWorld`、注册根 Obligation、
admit demand、安装观察器 —— 这些步骤仓库里已经有一个**就是为此写的**端到端用例：

```text
tests/orchestrator/full_target/test_real_provider_hierarchical_smoke.py
    ::test_real_hierarchical_planner_round
```

它做的事：起一个只有一个失败测试的小仓库，提交一个

```python
MissionSpec(
    goal="修复仓库里失败的测试 tests/test_kv.py::test_parse_kv_strips_whitespace，"
         "并说明改动；不要改测试本身。",
    success_criteria=("pytest:tests/test_kv.py", "改动有说明"),
    allowed_tools=("workspace_read_file", "workspace_write_file",
                   "workspace_list", "run_tests"),
    budget=Budget(max_tokens=600_000, max_attempts=8),
    orchestration_semantics_version=HIERARCHICAL_SEMANTICS,   # = "hierarchical"
    workspace_seed={"kvlib.py": ..., "tests/test_kv.py": ...},
)
```

然后 `build_planning_world(mission.id, domains=("code",), ...)` +
`orchestrator.install_hierarchical(planning=world)`，让真实模型走完
Planner → 编译 → 派发叶子 → Worker 改代码跑测试 → 验收 → 根评审 → COMPLETED。

**怎么跑**：

```bash
cd ~/PROJECTS/SimplaHarness/simple-harness-sdk

export SH_BASEURL='<端点>'
export SH_APIKEY='<key>'          # 不要 echo 出来、不要进 shell history 文件
export SH_MODEL='deepseek-flash'

uv run --frozen --group dev pytest -q \
  tests/orchestrator/full_target/test_real_provider_hierarchical_smoke.py \
  --run-real-provider -m real_provider
```

两个开关**都要**：

- `--run-real-provider` 是 opt-in 开关（`tests/conftest.py`），不给就整条 skip；
- `-m real_provider` 只选真实 Provider 用例。

**怎么读结果**（这个用例断言的是**闭包**，不是模型的措辞）：

- 任何一轮出现 `proposal_unreadable` → **失败**（这是 P2.3b 修掉的旧缺陷）；
- Mission 要么 `COMPLETED`，要么是**诚实的停**：没完成，且每一次拒绝都带结构化机器可读理由
  （如 `no_dispatchable_work`、`READ_SET_UNRESOLVED`、`OUTPUT_PORT_UNCLAIMED`）。
  「诚实地停」也算用例通过 —— 模型是随机的，规格是「永不假装成功」。
- 原始收据落 `.local-test-evidence/`（已 gitignore），key 不会进去。

发布机上这条链路在 P2.3c 第三部分 a 已经真跑通过一次：`mission-7ebe2d5cafa71266`，
`COMPLETED / verification_passed`，4 次 TASK_CONTENT ACCEPT + 1 次 MISSION_FINAL ACCEPT，
结算 172 864 token。

**预算提醒**：分层 Mission 收尾会花**两次** mission 账户的模型调用（根评审人 +
既有的 Mission Judge）。按两次算预算。

## 6. 已知限制（明天遇到不要当成新 bug）

1. **PANDA/HDDL 后端是 stub**。本机没有 cmake / gengetopt，`planning/htn/backends/panda.py`
   走 stub 路径。配置 `SH_PANDA_PARSER` 指向真 parser 后，相关真实用例会自动启用。
2. **AppWorld 相关用例需要独立的 `appworld-venv`**，不在 Host 的 `backend/.venv` 里。
   没有它时那些用例是 skip / error，属环境缺口。
3. **策略快照 digest 变了**：`85d78ea5…` → `7cf60224…`，差异恰好一条
   `config.max_root_review_cuts: null → 3`。仓库里没有钉死该 digest 的常量，
   但**任何依赖旧 digest 做外部对照的脚本必须重取基线**。
4. **分层 Mission 收尾两次 mission 账户模型调用**（根评审人 + Mission Judge）。
   §13 v1.4 的映射表原文只写了一次；预算守恒按两次算。
5. **L2 `appworld` 谓词的 `app` 参数受 `PUBLIC_READ_APIS` 限制**。
   非 `supervisor` 应用读不到，返回 `OBSERVER_UNAVAILABLE`（诚实的 UNKNOWN）。
   G8 修的是「假 FALSE → 诚实 UNKNOWN」，**没有**放宽白名单 ——
   runner 把 `app` 钉成 `"supervisor"` 的做法仍然有效且仍然必要。
6. **Python 3.14 下 `p33` 已知红**：
   `tests/orchestrator/.../p33::test_legacy_check_ast_and_default_retrieval_bytes_are_unchanged`
   断言的是历史 AST 字节 hash，3.14 的 AST 变了。**用 3.12 就不会红**。
7. **`reuse lint` 在 SDK 仓库是红的**（184 个文件缺 SPDX 头）。
   已核对 `REUSE.toml` 与 0.11.1 逐字节相同，是长期既有缺口，不是这一版引入的。
8. **`mypy` 17 errors / 4 files 是基线**（`evaluation/are_benchmark.py` 缺可选依赖
   `are.simulation.*` 与 `pydantic`，`evaluation/agentdojo_runner.py:383` 一条 misc）。
9. **SDK 全仓裸 `pytest -q` 会被 18 个收集错误打断**，全部是环境缺口（缺
   `pytest-asyncio` / `pydantic` / 已下线的 `simple_harness_memory`）。按 §3.3 加两个
   `--with` 即可。
10. **`ReceiptObserver` / code 域观察器的 `coverage_scope` 仍是描述性字符串**，
    与锚点层要求的「等于决策 scope」对不上。域级遗留问题，记在 SDK
    `plans/2026-09-16-full-target/P2.3c/journal.md` 第三部分 c §4。
11. **`tiktoken` 是个没被任何依赖组声明的可选依赖**。不装它，`tests/agents` 有 15 条红、
    `tests/orchestrator/p33` 有 6 条红。**必须装进 `.venv`**（`uv pip install tiktoken`），
    `uv run --with tiktoken` 不管用 —— 相关代码在子进程里 import，拿不到 uv 的临时叠加层。
12. **`psutil` 同理**（`local-capacity` extra）：不装，`tests/execution/test_shared_capacity.py`
    11 条红（`shared capacity requires the SDK local-capacity extra`）。
13. **不要给全仓跑加 `pytest-asyncio`**：装上 1.4.0 后
    `tests/integration/test_shared_capacity_dispatch.py` 会永久挂起，`tests/orchestrator`
    全量也会卡在 56%。gap_phase1 单独跑。

### 6b. 这一版留下的两条真实遗留（SDK 侧，不影响 wheel 运行）

- **F-REL-1**：`tests/unit/contracts/public-api.json` 的版本戳仍是 `0.11.1`，

  （四个 `__all__` 列表的元素与顺序）与快照**完全一致**，只有版本戳过期。

  `SDK_DEPENDENCY_LOCK_HASH` 仍是 `9b1bebc8f2bf…`，而仓库 `uv.lock` 已是
