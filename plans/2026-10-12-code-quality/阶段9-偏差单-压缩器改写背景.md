# 阶段 9 · 9I 偏差单：压缩器把 `background: transparent` 改写成 `background:0 0`

日期：2026-10-17
关联：阶段9-9I-设计.md 裁决执行条件 1（WebKit + 产物构建逐元素比对，全等才算通过）。

## 事实

- 第一批（设置类 12 个文件、280 处）转换后，WebKit 26.5 产物比对 156 个场景×主题，只有一种差异：
  `background-position-x` 与 `background-position-y` 的计算值，原内联为 `0%`，转类后为 `0px`；
  共 168 个元素（另含它们的悬停取样），全部是原内联写了 `background: "transparent"` 的元素。
- 原因：发版构建用 Lightning CSS 压缩，它把 `background: transparent` 输出为最短等价写法 `background:0 0`
  （实测 lightningcss 1.32 对 `transparent`、`none`、`transparent none` 都输出 `0 0`）。`0 0` 解析成长度 0，
  WebKit 计算值写成 `0px`；内联样式不经过压缩，背景位置保持初始值 `0%`。
- 这两个元素的 `background-image` 计算值都是 `none`。按 CSS 背景规范，`background-position` 只决定背景图片的位置；
  没有背景图时它不影响任何绘制。且 `0%` 与 `0px` 定位结果也相同。
- 现有作者样式里已有 22 条 `background: transparent`，发版产物里同样被改写成 `0 0`（现状如此，分层前后都一样）。
- 规模：已转的第一、二批生成类里含 `background: transparent` 的声明共 14 条（一条类可用于多个元素）；后续三批还会更多。

## 可选做法

1. **比对脚本加一条窄等价（推荐）**：只有当两边该元素（或伪元素）的 `background-image` 计算值都是 `none`，
   且两边 `background-position-x/-y` 的值都属于 {`0%`, `0px`} 时，不算差异；其余任何属性、任何非零值照旧逐字比对。
   比对输出单列"按此条放过的元素数"，入记录。理由：被放过的属性在该元素上没有绘制效果，属于压缩器的等价改写。
2. 发版构建改用 esbuild 压缩 CSS（实测保留 `transparent`）：影响全部产物 CSS（现有 22 条也会变回 `0%`），
   且 esbuild 不是本项目直接依赖，要新增依赖，属于构建配置变更，超出 9I 范围。
3. 含 `background: transparent` 的元素不转：涉及上百处，指标到不了 ≤ 200。
4. 转换工具改写声明（如拆成长写）：生成类与 React 的声明表不再逐条相同，违反条件 3。

## 独立裁决

日期：2026-10-17。裁决员：独立子代理，模型 Opus 5.5。只报阻断级问题。

### 实测核对

1. **基线来源对得上。** 转换前取样 layered.json 来自 HEAD 产物（e054d65aa，已含"全部作者样式进层"）。转换后取样是 A/after.json。两边都是 WebKit 26.5，都是 156 个场景×主题，符合条件 1 的"HEAD 产物对比转换后"。
2. **差异只有一种。** 我用 `diff_styles` 把元素、伪元素、悬停全部重算了一遍：
   - 结构差异为 0：元素数、标签、伪元素槽位、悬停目标都一致，两边都没有报错，运行时 `<style>` 只有 sh-theme。
   - 元素差异 168 个：164 个 button，4 个 div，都在元素本身，伪元素没有差异。
   - 悬停差异 164 次。
   - 差异属性只有 `background-position-x` 和 `background-position-y`，值全部是前 `0%`、后 `0px`。
   - 没有任何其他属性有差异。
3. **背景图两边都是 none。** 上面 168 个元素和 164 次悬停，两边的 `background-image` 计算值都是 `none`。
4. **原因确实是压缩器。**
   - 我用 node 实测了 tauri-app/node_modules 里的 lightningcss 1.32.0：`transparent`、`none`、`transparent none`、`rgba(0,0,0,0)`、`transparent 0% 0%` 都输出 `background:0 0`。
   - `var(--x)`、`#fff`、`red url(a.png)` 保持原样。
   - 前端用的是 vite ^8，它默认用 lightningcss 压缩 CSS。
   - 画廊产物 style-gallery-*.css 里有 10 条生成类含 `background:0 0`，例如 `.sh-AddProviderModal-5`。发版产物 App-*.css 里也是这 10 条。
   - 作者样式里的 `background: transparent` 在产物中同样变成 `0 0`，产物里一条 `background:transparent` 都没有了。
5. **等价性成立。** 百分比定位是"(区域宽 − 图宽) × p"，p 取 0 时位置就是 0，和 `0px` 相同。所以即使有背景图，`0%` 和 `0px` 也定位一致。没有背景图时，这两个属性根本不参与绘制。
6. **两处出入，不阻断。**
   - 偏差单写"14 条"和"22 条"，我按文件 grep 的口径和它不同，没有逐条对。
   - "这些元素原内联都写了 transparent"这一点，我没有逐个回查 DOM 来源。但它和生成类的数量、压缩器实测都对得上。

### 结论

修改后同意做法 1。

不同意做法 2：它改的是构建配置，超出 9I 范围。也不同意做法 3 和做法 4。

### 阻断级执行条件

1. **只在比对阶段放过，不改取样。** 等价规则只写在 `compare()` 里。dump 的输出和 JSON 原数据一律不改，也不做预处理。
2. **等价的精确边界。** 一个比对单位指元素本身、`::before`、`::after` 或一次悬停取样。下面五条必须同时满足，才不算差异：
   - (a) 这个单位的全部差异属性，只能是 `background-position-x` 和（或）`background-position-y`，不含任何其他属性，也不含 `background-position` 简写。
   - (b) 每个差异属性在前后两边的值，都必须完全等于字符串 `0%` 或 `0px`，只允许单层。带逗号的多层值、`calc()`、关键字（如 `left`）、带偏移的值、其他单位的 0（如 `0em`）都不放过。
   - (c) 前后两边这个单位的 `background-image` 计算值都必须完全等于 `none`。
   - (d) 只要这个单位有任何其他属性不同，就照常报错。报错时列出完整差异，包括背景位置，不许先把背景位置过滤掉再报。
   - (e) 场景只在一边、报错、元素数、标签、伪元素槽位、悬停目标这些结构检查，照旧逐字比对。
3. **放过必须计数，并写进记录。**
   - 比对输出要单列三个数字：按此规则放过的元素个数、伪元素个数、悬停次数。
   - 结论行写成"通过（压缩器等价放过 元素 N / 伪元素 P / 悬停 M）"。
   - 每批的批次记录都要写入这三个数字，并附至少前 5 条明细（场景|主题、元素下标、标签）。
   - 记录里要写明 lightningcss 和 vite 的版本。如果这两个版本有变化，先重跑本裁决第 4 点的压缩器实测，再用这条规则。
4. **用金丝雀测试锁住规则，并入库。** 给比对脚本加用例，下面 5 种情况都必须仍然报"不通过"：
   - `0%` → `1px`；
   - `0%` → `50%`；
   - 一边的 `background-image` 是 `url(...)` 或渐变，背景位置仍是 `0%` 和 `0px`；
   - 背景位置是 `0%`/`0px` 差异，同一单位另有一个属性不同；
   - 多层值 `0%, 0%` → `0px, 0px`。

   再加一个正向用例：用第一批的真实数据（或从中抽出的最小样本）跑比对，结果必须是通过，放过 168 个元素和 164 次悬停，其余问题为 0。
5. **不许外推。** 这条规则只覆盖"`background` 简写被 lightningcss 压缩成 `0 0`"这一种改写。后续几批如果出现其他属性、其他值的压缩器差异，或背景图不为 none 的元素，一律另写偏差单交裁决，不许扩大这条规则。
6. **改条款原文。** 9I 设计执行条件 1 里的"全等才算通过"，改成"全等，或仅有《阶段9-偏差单-压缩器改写背景》裁决列明的等价差异才算通过"。偏差单连同本裁决一起入库。
7. **每批重新比对。** 每批转换都要用当批产物重跑完整的 WebKit 比对，并分别统计放过的数量。第一批的结果不能沿用到第二批及以后。
