## 1. 交付物

**SDK（编排库）**
- `runtime/native_plane.py`：`NativePlaneAssembly`（一个池要跑在原生平面时，由部署方提供：`arp_ports(执行库路径)`、真实授权端口、`caller_for(intent)`、`after_build(runtime)` 迟绑定钩子）；`intent_caller`：由已认领的派发意图派生 `TrustedCaller`（主体=部署 principal，命令回执=意图本身的 id/mission/kind/creation_key/input_hash）；`RunPriorReserve`：从该池自己的执行库汇总本 run 先前所有已结算调用的输出 token 作为 `P`，`claimed` 跳过，未结算/无用量一律 `PRIOR_RESERVE_UNAVAILABLE`，不猜。
- `runtime/assembly.py`：`RuntimeProfile.native_plane` 非空时用 `build_arp_runtime`（AllowAll 在装配时就被拒 `AUTHORITY_SOURCE_MISSING`），桥带 `caller_for`；旧池一行不改。
- `runtime/agent_worker.py`：`AgentBridge.create(..., intent=)`，原生池没有意图就拒绝；`event_handler.py` 创建时传入已认领意图。
- `runtime/deepseek_meter.py`：`CertifiedDeepSeekCounter`（官方 tokenizer + 官方请求渲染器，`count_mode=EXACT`，`count_request_tokens` 直接给出最终线上请求的精确计数）；`deepseek_meter_binding`（`input_limit_scope=WIRE_PLUS_PRIOR`、`requires_prior_output_reserve=True`，必须带先前输出储备读取器；认证回执写明规则、recipe 版本、tokenizer sha）。

**Host（backend/deskpet/orchestration）**
- `native_plane.py`：`HostNativePlane`。授权端口 = 部署策略允许的工具名（不是 AllowAll，策略有身份）；计量 = 上面的 DeepSeek 认证绑定（测试用注入的认证夹具计数器）；每池一个 ARP 会话根（`execution-<profile>.db.arp-root`）；验收读口 = `AssuranceSkillAcceptance` 迟绑定编排 store 与保证根门 `require_execution`；产物读取 = 编排产物库按内容哈希；嵌入 = BGE-M3（INT8 本地，权重缺失/未装 FlagEmbedding 显式报 lexical-only，加载失败记一次不再重试）；脚本执行器 = 无（按名拒绝，见 §5）。
- `runtime_profile.py`：官方 DeepSeek 或部署声明的兼容主机（`deepseek_compatible_hosts`）才出认证计数器；tokenizer 路径优先 `DESKPET_ORCH_TOKENIZER_PATH`，否则 `<models>/deepseek-v41/tokenizer.json`；原生池 `deepseek-native-256k-v1 / -512k-v1` 与旧池并列，新 Mission 默认落原生池（`native_plane=off` 退回旧池；已有 Mission 保留其冻结的池）。
- `service.py` / `handlers.py`：`agent_runtime_request`（SDK `HostRequest` → `HostResponse`，调用方只由 Host principal 派生，失败以 SDK 的 Error DTO 回）、`agent_skill_evaluation_mission`（评估的原始 Mission，幂等键 = `evaluation_mission_key`）、`agent_skill_evaluation_dispatch`（核对租户归属、幂等键、任务归属后写 `record_evaluation_dispatch`）；`status.native_plane`。
- 钉版：SDK 升到 `0.13.0.dev20260924+arp.1`（源提交 `7308e50b`），vendor 轮子 + 候选清单 + `sdk_candidate.py` + `pyproject.toml`（加 `deepseek-recipe==0.1.1`）+ `uv.lock`；本机装了钉定的 DeepSeek V4.1 tokenizer（sha 与 SDK 钉值一致）到用户模型目录。

7. Host 的模型目录是 `~/Library/Application Support/com.dennywanye.simpleharness/models`（不是 `deskpet/models`）：tokenizer 已装到该处；BGE-M3 权重不在该处 → 原生会话 lexical-only（状态如实显示）。

## 7. RP-E4：真实模型 12 局运行器第一轮的机制失败与修复（2026-09-24 03:20–04:20）

### 7.1 根因一：独立部署的 ARP 运行时在"交接之后"才冻结上下文（SDK 缺陷，已修）

- 现象：SDK 层 12 局运行器第一轮全部 turn 失败，错误码 `PRIOR_RESERVE_UNAVAILABLE`，明细 `state: handed_off`——先前输出储备读取器把本次请求自己的调用当成了"未结算的先前调用"。
- 对照：Host 金丝雀（canary-native-2）没有触发。Host 总有编排层的准入端口，内核在"认领 → 冻结（prepare_request）→ 交接"顺序下执行；没有准入端口时，旧线路在 `invoke` 里、交接之后才 prepare。ARP 的"冻结请求先于物理交接"是接口约定（INTERFACES §1），独立部署违反了它。
- 修法（SDK `78eb1e0e`）：`build_arp_runtime` 在部署未提供任何准入端口时，装上 SDK 自带的 `LocalProviderAdmission` + 空操作生命周期栅栏（`_admitted_ports`），并发上限从线路信号量原样搬到准入。并列修两处：读取器用 `collections.abc.Mapping` 判断用量（真实记录是只读映射，不是 dict——这个问题在 Host canary-native-3 里也以"succeeded 调用 PRIOR_RESERVE_UNAVAILABLE"的形式出现过）；会话销毁的清点不再把从未交接的 `claimed` 调用算作 UNKNOWN（内核自己的对账也跳过 claimed）。
- 测试：新增 `tests/agents/arp/test_arp_standalone_admission.py`（两回合真跑：每个上下文请求的冻结时间 ≤ 该调用的交接时间；第二回合的储备 = 第一次调用记录的输出，按名）；ARP 套件 353 通过。
- Host 重钉 `0.13.0.dev20260924+arp.2`（`195e166d`、`dea1da70`），Host 原生池定向测试 13 通过。

### 7.2 根因二：运行器自己的缺陷（已修，`99cb4aa5`、`535a986c`）

| 问题 | 修法 |
|---|---|
| 崩溃窗口恢复：重建的进程立刻接管，旧租约（30 s）未过期，回合以 `ProviderInvocationConflictError` 失败 | 运行器像真实重启一样等旧租约过期再接管；第二进程用不同 owner；接管后调 `kernel.reconcile()`；部署自己的对账端口（`RunnerReconciliation`）根据传输门的记录如实回答：从未发出的请求 `CONFIRMED_NOT_STARTED`，已发出的 `STILL_UNKNOWN` |
| 崩溃切点不可控（等到上下文行出现时请求早已上线） | `TransportGate` 包住真实提供方，可把下一次调用扣在发出之前（内核已记交接、传输未进入），在那里 kill；离线回放（脚本提供方）：t3 在恢复后提交、同一请求指纹、rehandoff=1、单次计费 |
| "请求哈希漂移"不变量拿内核的原始请求指纹和清单的线上哈希比（口径不同，误报） | 传输门用 SDK 同一函数对实际上线请求取哈希，与冻结清单的 `planned_request_hash` 比（含重交接） |
| 没有任何工具到线上（LM03 模型答"当前未提供 skill.discover / skill.load 工具"） | 曝光按 `AgentConfig.tool_names` 注册名给出；授权白名单改用注册名（下划线） |
| LM01 填充回合太短（问答回合线上 1643 token / 预算 3439），早期事实从未被挤出、召回无事可做 | 填充改为约 450 token/条 |
| `dataclasses.asdict` 深拷贝只读映射失败；回合状态大小写比较错 | 按字段读取；小写比较 |

### 7.3 根因三：日卡网关对部分提示返回"空完成"（环境缺陷，未解决，阻塞真实模型局）

### 7.13 思考模式与不思考模式双支持（用户决定，2026-09-24 14:00–14:40）

**起因。** 用户问思考要不要带、现在怎么处理、是否符合最佳实践。核对结果：运行器显式关思考，符合；产品后台编排不发开关、又丢弃思考内容，在默认开思考的线路上属于"开着却不回传"，带工具时官方会返回 400。用户决定两种模式都要支持。

**官方规则（DeepSeek 思考模式文档）。** 思考默认开、强度 high；带 tools 的请求必须把之前各轮的 reasoning_content 完整回传，否则 400；不带 tools 时回传被忽略。官方渲染器（deepseek-recipe 0.1.1）支持助手消息上的 reasoning_content，也读取请求的 thinking 字段，开/关渲染不同。实测：带工具、开思考、带回传 389；不带回传 344；关思考 319。原计数器一律按开思考渲染，运行器发的是关思考，所以此前每次多算约 25，属于安全方向。

**设计与对抗审阅（opus 5.5，两轮）。** 第一轮挑出 5 条阻断，全部采纳：带工具时每条助手消息都要带思考，缺一条就会反复 400；粗估计数器也要计入思考；模式要在 Agent 创建时冻结；对 DeepSeek 不允许"不表态"；开思考时要加大输出上限。第二轮核验挑出 1 条：产品后台所有 Agent 共用一个提供方，改配置会让已有 Agent 全部失配。改为独立的思考池。

**实现。**
- 适配器：`thinking=enabled|disabled`（另有仅限开思考的 reasoning_effort），写进目标身份和计数负载；不允许再通过附加字段传。开思考时的延续模式是新增的"思考回传"（REASONING_REPLAY）；流式和非流式都能取出思考内容，作为回复的私有字段保存。
- 落盘：延续部分的格式版本 2 多存一份私有思考原文，只有"思考回传"模式允许；公开消息的元数据仍必须为空。日志只存公开内容，所以思考不会被检索、召回，也不会成为证据。
- 回传：发出前先补思考、再补工具调用。每条助手消息都按调用编号从账本取思考原文，取不到补空串。ARP 组装器、普通路径、Assurance 的线上重建比对都走同一规则。
- 模式贯通：提供方声明的延续模式同时进入提供方绑定和驱动指纹，所以一次运行不会中途换模式。
- 计数：精确计数器按绑定的模式渲染，指纹里带模式；DeepSeek 认证计数器必须显式选开或关。粗估计数器和组装器的规划都会计入回传的思考。
- 产品后台：DeepSeek 共享提供方一律显式关思考，所有原有池的延续模式不变。两种长度各新增一个开思考原生池（`deepseek-native-256k-thinking-v1`、`deepseek-native-512k-thinking-v1`），各自有独立的提供方（共用 HTTP 客户端）、计数器和执行库。配置 `[orchestration] thinking` 默认关，只决定新 Mission 的默认池。
- 运行器：`--thinking on|off`；开思考时输出上限 2048，窗口同步加大到 7168。

**验证。** SDK 定向测试全部通过：思考端到端测试证明回传只进请求副本不进日志、每条助手消息都带、计数正好多出思考的字数、关思考时什么都不存。产品后台新增 5 个测试通过，原生平面测试通过。运行时配置那组有 5 个失败，经对照是原来就有的，与本次无关。SDK 提交 `ffd62d3d`（arp.4），产品后台提交 `860a4445`。

**未核实（需要真正会思考的线路）。** 当前的旧日卡线路开了思考也不返回思考内容，缺思考内容也不报 400。所以"缺失必 400""空串可被接受""输出上限是否包含思考"三点还没在真实思考线路上验证。产品后台打开思考之前，必须先用官方端点或会思考的线路实测。

**用户决定（2026-09-24 15:10）：以 DeepSeek 为主要适配模型；新 Mission 默认开思考。** `[orchestration] thinking` 默认改为 enabled，运行器 `--thinking` 默认 on。已有 Mission 留在原来的池里，不受影响；如果在会思考的线路上验证发现问题，把配置改回 disabled 即可回退。GPT、Grok 等其它型号的思考开关不在本次范围内，它们的请求不变。开思考金丝雀（旧日卡线路）：17 次成功调用全部按思考回传模式落盘，没有出现 400，但线路没有返回任何思考内容；另有 3 次服务端错误；30 分钟超时没跑完。这条线路无法验证思考模式。

### 7.14 中转线路的工具前言余量（用户同意，2026-09-24 15:20–16:40）

**实测。** 当前中转不支持思考：不发开关、开思考、流式、非流式各试一遍，6 次请求都没有思考内容；早些时候有一次报了 128 个思考 token，但正文为空，说明它偶尔会切到另一个上游。关于少算，计数器按线上实际模式（关思考）渲染后：不带工具时两边完全一致；带工具时，1、5、10、20 个小工具都多出 110；1、5、10 个大工具（18 个参数，含嵌套、数组、枚举）分别多 108、100、90。也就是说，这段多出来的是固定前言，和工具个数、参数多少都无关。

**做法（用户同意）。** 中转带工具时多留一段余量：下限 160（实测最大值 110 加 50），之后按每次回报的用量自动学习。余量只增不减；实际差值一旦超过当前余量，就调到"差值加 50"并报警；可以持久化。官方端点不加余量。
- SDK：`RelayToolMargin`；`RelayDeepSeekCounter`，属于上界计数，身份里只记下限，不记当前值，所以余量变大不会让已冻结的运行失配；`CalibratingProvider` 包在适配器外面，看到的就是最终线上请求。
- 产品后台：官方主机用精确计数；配置里声明的兼容主机用中转计数器，每个主机一份余量，存在 `evidence_root/relay-tool-margin/<host>.json`；各池的提供方都做用量学习。运行器也改成同样的做法。

**独立核验（opus 5.5，两轮）。**
- 第一轮一条阻断：计数器身份一变，已冻结的池会失配，编排启动失败。另有一处可能冻住 Agent：普通路径的规划没算余量。
  - 修法：SDK 保留主分支已发布的计数器身份（`LegacyPriorOutputDeepSeekCounter`），用 merge-base 的原代码对 2 个型号 × 2 种模式现算比对，全部一致。产品后台按每个池冻结的身份选计数器（`counter_for_pool`）：旧身份的池继续用旧计数器；原生池和身份认不出的池不注册，任务会明确失败，不会让整个编排起不来。普通路径的 `tool_tokens` 计入余量。
- 第二轮一条阻断：中转上的旧身份池仍会少算约 80 到 90。另需确认一点：没有身份文件的默认池，准入身份可能对不上。
  - 修法：`LegacyRelayDeepSeekCounter` 身份不变，但计入该主机的余量。编排器允许一个池提供几个候选估算器，按已冻结的派发意图里的准入身份挑选，没有冻结记录时用第一个。没有身份文件的默认池同时提供"当前、旧身份"两个候选。
- 按"核验不超过两轮"的规矩，第二轮的修复不再送审，改由测试钉住：编排器级别测试覆盖"旧身份冻结后，给两个候选会选旧的；只给新的会拒绝；全新的池用第一个"。

**提交。** SDK `3e12a076`（arp.5）、`ff320153`（arp.6）、`925c694a`（arp.7）；产品后台 `1f66080b`、`a4bf5339`、`a20a393f`，目前钉在 arp.7。

**金丝雀（中转，开思考，1 局）。** 答对；硬性检查全部通过；用量校对 20 次，没有一次少算，最接近的一次我们也多算 71；余量保持 160，实测最大差值 89，没有报警；1 次服务端错误。

**完整 3 局（中转，开思考，证据 `games-lm01-relay-margin/`）：3/3 答对，硬性检查全部通过。** 3 局都召回到了早期信息。用量校对共 59 次，没有一次少算，最接近的一次我们也多算 71。余量保持 160，实测最大差值 89，没有报警。线路另有 5 次服务端错误，出错的回合失败了，但不影响最终答题。

### 7.15 思考模式在真实思考线路上验证（2026-09-24 17:00–17:40）

**纠正前面的结论。** 此前说"当前中转不支持思考"是错的。严格复测时，同一道需要推理的题每种设置跑 3 次：只发开思考开关，非流式、流式都是 0/3 返回思考，答案也错；开关加思考强度 high 或 max，11/11 都返回了 `reasoning_content`，思考 1292～8091 字，全部答对；计费的输出 token 远大于正文。结论是：这条中转只有在请求里带上思考强度时才会思考。此前开思考的金丝雀因为只发了开关，其实没有走到回传路径。

**修改。** 开思考时同时发 `reasoning_effort: high`。官方文档里的默认强度就是 high，所以对官方端点没有影响。产品后台的思考池（`THINKING_EFFORT`）、运行器、计数器都按同样的参数。运行器新增一项线上级别的思考回传检查：每次真正发出请求时，统计每条助手消息是否带思考字段、有几条是真实思考、总字数。开思考时要求：每条都带字段；前面存下过真实思考，后面就必须有请求把它送回。这一项列为硬性检查。

**结果（中转，开思考 + 强度 high，证据 `games-lm01-thinking-effort/`）。** 3 局中 2 局答对，3 局硬性检查全部通过。

| 局 | 答对 | 存下的真实思考 | 送回了真实思考的请求 | 缺思考字段的请求 | 少算 |
|---|---|---|---|---|---|
| 1 | 否（提问那一回合线路返回服务端错误，保留为失败） | 1 | 1 | 0 | 0 |
| 2 | 是 | 2 | 10 | 0 | 0 |
| 3 | 是 | 2 | 11 | 0 | 0 |

- 送回的思考最多一次 809 字。3 局对话记录里都找不到任何思考原文。
- 用量校对 58 次，没有一次少算，最接近的一次我们也多算 46。余量保持 160，实测最大差值 114，没有报警。带上真实思考后，差值从 89 升到了 114。
- 线路共 5 次服务端错误，其中第 1 局提问那一回合正好碰上，所以没有给出答案。

**结论。** 思考模式在会思考的真实线路上，"存下 → 逐条送回 → 计数"整条链路已经走通，没有出现 400，也没有少算。"缺思考就 400"这一点在这条中转上不成立：它对缺失的思考也不报错。

### 7.16 向量模型本地可用：BGE-M3 INT8 + 后台计算（用户决定，2026-09-24 18:00–20:30）

**原来的问题。** Host 的嵌入端口依赖 FlagEmbedding + torch，而 FlagEmbedding 和本机的 transformers 5.x 不兼容，模型目录里也没有权重，所以原生池的向量车道在本机一直是"未配置"，召回只能走词法。用户在 WeMM 2B（常驻约 6.8 GB）和 BGE-M3 之间选了 **BGE-M3 INT8**，并同意下载权重。

**做法。**
- 权重：BAAI/bge-m3 官方 ONNX（修订 `5617a9f6`，`model.onnx_data` 2,266,820,608 字节，sha256 `1eebfb28…` 已校验），在本机做动态 INT8 量化，并改成外部数据格式：`model.int8.onnx`（图，1.1 MB）+ `model.int8.onnx.data`（567,669,760 字节）。放在 `~/Library/Application Support/com.dennywanye.simpleharness/models/bge-m3-int8/`，同目录有 tokenizer 文件。量化工具 `onnx` 只装在临时环境里，产品不依赖它。
- Host 端口（`native_plane.BgeM3EmbeddingPort`）重写：只用 onnxruntime + tokenizers + numpy，不再需要 torch / FlagEmbedding；输出 `sentence_embedding`（1024 维，归一化）；每批 8 条，最长 8192 token；指纹由文件名、大小、配置、分词器内容和长度上限决定。`onnxruntime`、`tokenizers` 在 Host 依赖里直接声明（原来只是 OCR 顺带装的）。缺任何一个文件时，端口给出具体原因而不是报错。
- 常驻内存：单文件 INT8 模型约 1.5 GB；改成外部数据后，加载模型 + 分词器实测增量约 1.07 GB。
- 后台计算（SDK arp.8）：真实模型一批要 0.2～2 秒，不能放在 Turn 的准备阶段里同步跑。端口可以声明 `prefers_background = True`；声明后，准备阶段不再内联处理索引作业，由后台泵调用 `tick_async` → `process_due_async`，在线程里算好向量，再交给原有的已记录嵌入调用使用（`_PrecomputedPort`）。账本、重试、代次检查都沿用原来的路径。没有声明的端口（测试夹具、确定性嵌入）行为不变。

**验证。**
- 真实模型：16 条文本约 4 秒；"工程暗号"查询对正确文档相似度 0.695，对无关文档 0.36。
- SDK：`tests/agents/arp/test_arp_background_embedding.py` 2 例（声明后台的端口不在准备阶段被调用、后台泵算出的向量被正确使用），加原有索引召回共 14 例通过。
- Host：`tests/orchestration/test_bge_m3_onnx_port.py` 3 例（缺文件原因、端口声明、真实模型的维度/归一化/语义排序；没装模型时最后一例跳过）。
- 提交：SDK `5755aa34`（arp.8），Host 重钉 arp.8。
- `tests/sdk_adapters` 里 effect gate 等一批失败在 arp.7 上同样失败，与本次无关（见 HANDOFF 基线）。
