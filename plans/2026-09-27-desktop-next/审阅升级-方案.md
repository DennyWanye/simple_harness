# 审阅判不下来时：换人复审一次，再不行问用户（完成度评估第 5 项）

2026-09-30 晚。用户决定：判不下来 → 同一模型（DeepSeek）**新会话**独立复审一次 → 仍判不下来 → **问用户**（不是判失败）。

## 一、现状（核对代码后）

- 保证通道下，审阅员回复的结论有四种：通过（ACCEPT）、打回（REWORK）、拒绝（REJECTED）、**判不下来（INCONCLUSIVE）**。判不下来的记录照样作为这次审阅的正式记录存下。
- 拿结论去用的地方（`assurance_review_runtime._verdict`）遇到"判不下来"直接报错 → 校验层记 ERROR → 结果按"没通过"处理 → 重做。可能对的活被反复重做，三次后按"反复失败"处理。
- **系统里已经有一整套"审阅员判不了就交给人"的机制**（旧通道的 D7-8'）：审阅结论带 `needs_human` → 校验层记 NEEDS_HUMAN → 结果挂起、登记一条"复核"审批 → 界面上出现"复核通过 / 复核不通过 + 理由"卡片（`MissionsView` kind === "review"）→ 用户决定后结果回到校验、人工那层取用户的结论 → 通过则验收、不通过则带着理由重做。**每个步骤只允许升级到人一次**。这套在保证通道下从没被触发过，因为"判不下来"在更早一步就报错了。
- 保证通道的通过证书（`assurance_validity._prepare_use`）是按正式审阅记录的清单重新判定的：记录是"判不下来"，证书就不是"可用"，验收会被拒。所以光让人点"通过"还不够，人的裁决必须成为证书认可的依据。
- 同一份审阅已经允许**第二次调用**（格式错 / 调用失败 / 引用没披露的证据时重问一次），新调用 = 新派发意图 = 新 Agent 会话，原样重发冻结的请求。复审可以复用这条路，只是理由不同。

## 二、改法（都在 SDK；界面与后端不用改）

1. **复审一次**（`assurance_review_consumer.prepare`）：第 1 次调用的回复解释出来是"判不下来"时，不导入为正式记录，改记一条"要求复审"回执（`AssuranceReviewSecondOpinionRequested`，classification=`SECOND_OPINION`），并按现有第二次调用的路建第 2 次调用（理由 `SECOND_OPINION`，同一冻结请求，**不带第一次的结论**，新 Agent 会话）。第 2 次的回复照常导入为正式记录（通过 / 打回 / 判不下来都算数）。只复审一次（调用序号上限本来就是 2）。
2. **仍判不下来 → 交给人**（`assurance_review_runtime._verdict`）：正式记录是"判不下来"时不再报错，返回"通过但需要人定"（`needs_human=True`）的结论，让现有机制接管：挂起 → 复核审批 → 界面卡片 → 用户点通过/不通过（可写理由）。每步一次的上限沿用。
3. **人的裁决进证书**：用户决定复核时（`human_commits.review_result`），在保证通道下写一条裁决回执（`AssuranceReviewAdjudicated`：任务、结果、正式记录、通过/不通过、谁、理由、决定回执哈希）并发事件；准备通过证书时把这条回执读进读集，记录"判不下来"而裁决为"通过"的，证书判为可用，理由里写 `human_adjudication:<回执>`。不通过的，校验层本来就已经判失败，走重做。
4. 规划器 / 审阅员的提示词一个字不改（改了已有执行池起不来）。不加策略字段（加了旧任务的策略解析会失败）。

不做（记为后续）：两个审阅员**都下了结论但相反**时的仲裁——按现在的路，第一次已下结论就不会复审，不会出现两份相反的正式结论。

## 三、测试

- 夹具级（`AssuredRuntime`，真实存储 / 提交 / Agent 运行时 / 审阅消费者 / 导入器，只有模型回复是脚本）：
  1. 回复 [判不下来, 通过] → 结论通过；调用两次，理由 [INITIAL, SECOND_OPINION]；两次是不同 Agent；正式记录只有一份且为通过；验收成功。
  2. 回复 [判不下来, 判不下来] → 结论"需要人定"；正式记录为判不下来；模拟挂起 + 用户复核通过 → 裁决回执存在 → 通过证书可用 → 验收成功。
  3. 同上但用户复核不通过 → 证书不可用（验收拒绝）。
  4. 第一次就有结论（通过 / 打回）→ 不复审（调用一次）。
- 变异：去掉"只在第 1 次复审"、去掉裁决进证书、去掉 needs_human 三处，各应有测试挂。
- 相关组回归：assurance_exec、p33（旧通道 needs_human）、operation_completion。
- 真实模型一局：严格引用文档任务，资料里故意让一条规则表述含糊，看审阅员是否判不下来、是否复审、是否问到用户。
