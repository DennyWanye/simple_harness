# 性能复验：主会话 + 三个工作会话 + 长历史（2026-11-01）

脚本：`sdk/simple-harness-sdk/scripts/acceptance/measure_session_tree_load.py`（离线脚本模型，真宿主栈）。
场景：主会话建 3 个工作会话，各委派一个任务跑到完成、结果回流、自动汇总；主会话连发 60 句、每个工作会话 20 句；再量闲置 60 秒。
原始结果：`.local-test-evidence/2026-11-01/perf-recheck/tree-load.json`（修前）、`.local-test-evidence/2026-11-01/perf-recheck-fixed/tree-load.json`（修后）。

## 修前（main fa8c96559）

| 项目 | 数值 |
|---|---|
| 三个任务跑完 | 20.5 秒；任务期间事件循环最大阻塞 3117 毫秒 |
| 长历史时主会话一句往返 | 中位 333 毫秒；循环阻塞 p99 150 毫秒 |
| **闲置 60 秒 CPU** | **均值 30.3%，峰值 39.3%** |
| 闲置 60 秒内任务快照读取 | **1215 次**（约每秒 20 次，中位 10.6 毫秒一次） |
| 读任务列表 / 恢复报告 | 29 / 31 毫秒 |
| 重开（恢复 3 个子会话） | 284 毫秒 |

单会话基线（《记录-性能基线-2026-10-31》）：闲置 4.8%；带一个在途委派 22.9%。多子会话闲置 30% 超过了基线里写的"三个子会话 + 父 ≤ 20%"。

## 根因

收件箱追事件时先比对任务库的原始事件尾和会话游标，相等才跳过。但对外的事件页会隐去内部事件（`RowsWritten` 等）。
任务结束后最后一条原始事件是 `RowsWritten`，游标只按可见事件推进，永远比事件尾少 1。
于是每一拍（0.25 秒）父会话和每个子会话都认为"有新事件"，重读事件页（空）和任务快照（约 10 毫秒），三个任务 × 四条泵 = 每秒约 20 次，永不停止。
子会话的快照还被父会话的镜像再读一遍。

## 修法

`host/inbox.py` 追完最后一页事件后，把游标补到这一拍开始时读到的原始事件尾。
隐藏事件不会再触发重读；比事件尾更新的可见事件序号更大，下一拍照常能看到。
红测试：`tests/orchestrator/host/test_session.py::test_inbox_cursor_covers_hidden_internal_events_and_stops_polling`（修前红：游标停在 1；修后绿，之后 5 拍零次快照读取）。

## 修后

| 项目 | 数值 |
|---|---|
| 三个任务跑完 | 17.3 秒；任务期间循环最大阻塞 2707 毫秒（任务本身的同步落盘，与修前同量级） |
| 长历史时主会话一句往返 | 中位 253 毫秒；循环阻塞 p99 124 毫秒 |
| **闲置 60 秒 CPU** | **均值 9.4%，峰值 15.4%** |
| 闲置 60 秒内任务快照读取 | **0 次** |
| 闲置循环阻塞 | p99 3.95 毫秒，最大 42 毫秒 |
| 读任务列表 / 恢复报告 | 62 / 32 毫秒（任务列表这一项是单次测量，波动大） |
| 重开（恢复 3 个子会话） | 205 毫秒 |

结论：闲置 CPU 从 30% 回到 9%，在基线里写的"≤ 20%"以内。剩余 9% 是四条泵各自每 0.25 秒一次的账本读取；单会话 4.8% 的量级乘以会话数，属预期。
