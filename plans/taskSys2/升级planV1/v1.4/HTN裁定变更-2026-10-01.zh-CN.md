# HTN 裁定变更（2026-10-01）：选做法由编排 Agent 判断；新做法由编排 Agent 提出并须过独立审阅

性质：对原始计划的**带日期修订记录**。原始计划正文不改；与本文件冲突之处以本文件为准。
决定人：用户，2026-10-01（对话中逐条确认）。
实施方案：`plans/2026-09-27-desktop-next/HTN-后续-方案.md`。

## 一、被修订的条款

| 原文位置 | 原文要点 | 修订后 |
|---|---|---|
| LLM 原生执行计划第 2 版 §49 | 选择策略三档 `DETERMINISTIC / MODEL_ON_MULTIPLE / ALWAYS_MODEL`，新协议默认 `MODEL_ON_MULTIPLE`：0 个适用 → 取证或合成；1 个 → 程序直接用；≥2 个 → 规划器选 | **只保留"由编排 Agent 判断"一种**：程序筛掉跑不了的做法后，不论候选 0 个、1 个还是多个，都由规划器回决定（采用 / 自己提新做法 / 取证 / 问用户）。另两档与 legacy 分支删除 |

## 二、未修订、需要说明边界的条款

当前主计划 `NEXT-TG-1.0` §0："只有确实需要新的语义规划时才请求规划器""不等于无条件增加模型调用"。

本变更与之不冲突，口径限定为：**只在"为一个目标选定做法"这一刻必须由编排 Agent 判断**——这本身是一次语义规划。推进过程中何时唤醒规划器，仍按主计划 §3 的四类推进判定，不因本变更增加。

## 三、理由（2026-10-01 真机库只读统计，101 个真实任务）

- 初始计划采用哪个做法：程序直接定 103 次，模型定 0 次。
- 做法来源：合成器现编 107 次，规划器提出 0 次。
- 新做法独立审阅 0 次；全库唯一接了该审阅的路径从未被走过，且审阅结论未接到"能否采用"。
- 桌面领域方法库为空，唯一候选永远是刚现编的那个、前提条件为空，程序的"适用"判定没有信息量。

即：原默认策略在"库由人维护、前提写得实"的前提下合理，在当前产品状态下导致"怎么拆"无任何模型把关，也使 v1.4 §7.3 第 4 条落空。

## 四、连带删除（开发期不做旧数据兼容）

方法合成器角色及其全部提示词版本、六处"跳过规划器"捷径、选择策略配置项、各角色提示词历史版本与历史链、旧规划包文件与按版本号分支的判断。按旧契约建立的开发库任务不保证能跑，遇到时明确报错。

## 五、同期补充（不是修订，是兑现）

v1.4 总计划 §7.1 的"递归细化"在产品中兑现：Host 注册通用"子目标"类型，做法里允许把步骤写成子目标，层数有上限。中间目标的组合审阅结论已在 SDK opt.109 接通。
