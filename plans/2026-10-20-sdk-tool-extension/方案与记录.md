# SDK 对外工具接入口（AgentOS / AIPhone 两份交接）——方案与记录

- 日期：2026-10-20
- 依据：AgentOS 交接《为 AgentOS 开放 Simple Harness SDK 的正式自定义工具接入能力》；AIPhone 交接《SDK 侧交接：AIPhone 手机 Linux 本机任务编排》（zip，含复现脚本与重建 wheel）。
- 基线：SDK opt.195（deb9e006c）。本仓库 main 已到 329f844cd（含下面第二节的 SQLite 修复）。
- 分工：SDK 只做通用机制。NAS/桌面/手机设备的具体工具、凭据、socket 路径、用户/家庭身份由消费方实现。

## 一、两份交接要什么（合并后）

| 编号 | 要求 | 来源 |
|---|---|---|
| T-1 | 应用经公开接口向 `OrchestrationHost` 注册自己的具名工具：名字、用途、参数 schema、执行函数、只读/副作用；从注册到模型可见、规划、执行、结果、审计、恢复整条链 | AgentOS A、AIPhone SDK-03 |
| T-2 | 支持 async 执行函数；同步兼容；不阻塞事件循环；取消/超时/异常/无结果语义明确 | AgentOS B、AIPhone 调度与资源 |
| T-3 | 调用带 SDK 可信身份（任务、尝试、调用号），模型参数不能伪造；应用能做自己的授权（角色/范围/设备能力）：拒绝、批准、或进持久人工等待；一个动作只有一个授权事实源；`auto_mode` 不绕过外部工具授权 | AgentOS C、AIPhone 调用上下文 |
| T-4 | 稳定调用/效果身份与 结果/失败/未知 状态；超时或中断不等于没发生；不盲重试；应用可按外部证据对账、提交"已完成/未执行/仍不确定"；重启不重置动作额度 | AgentOS D、AIPhone 恢复与重复 |

| T-6 | 公开边界、文档、三个仓库外可跑的例子（只读工具、异步工具、要批准且能拒的副作用工具）；固定版本 wheel 与清单 | AgentOS F、AIPhone SDK-04 |

## 二、事实核对（对着当前源码）

1. **T-7 属实，已修。** `storage/source_records.py` 触发器体内四处 `INSERT INTO temp.…`。SQLite 规则：触发器内 INSERT/UPDATE/DELETE 目标不能带库名；本机自带 SQLite 3.53.1 放宽了，系统 Python 的 3.51.0 复现（AIPhone 脚本：REPRODUCED）。改成不带库名（先解析到 temp），用系统 SQLite 3.51 对着真库结构装 142 个触发器通过；业务回放测试 16 条通过；新用例 2 条钉死脚本。提交 329f844cd。改坏清单 G-01/05/06/09 的锚行没动。
2. **SDK 已有两条外部通道，但都没通到宿主入口：**
   - 只读/领域工具：`runtime/domain_tools.DomainTool(schema, invoke(arguments, mission_id, call_id), read_only)`；网关把它放进工具目录与 schema、按任务加锁、在线程里跑同步 `invoke`、`_await_physical_call` 保证被取消时等物理调用结束并保持 UNKNOWN；部署策略 `domain_tools` / `domain_read_only_tools` / `allowed_tools` 已有校验（不能顶替内置名）。无人工授权环节。`drone_sim.deployment()` 是现成的接法样板。**模块不在公开清单。**
   - 副作用操作：连接器（`runtime/connectors.py`：`OperationSpec(level L0–L3)`、幂等键、`Receipt`、拒绝/传输错误两类异常、`lookup` 对账）。模型不直接调；规划器提操作申请单 → 审批（L2/L3 要人，`decide`）→ 动作执行器 `begin_handoff` 先写 HANDED_OFF 再调 → 失败 FAILED、不确定 UNKNOWN → `reconcile` 按幂等键问连接器，只有 CONFIRMED_NOT_STARTED 才允许同键再交一次 → 人可 `resolve_unknown`。**这正是 T-3/T-4 要的授权与未知恢复语义，已存在。模块只公开了 `connectors_publish`，基类协议不在公开清单；宿主入口只装了 `file_publish`。**
3. 工具集合进执行池身份：`DeploymentToolAuthorization.policy_id = hash(允许的工具名)`，池的准入身份含它；`dispatch_intents` 冻结了运行上下文，改了就拒绝重开。**所以注册工具改变部署身份，是既定规则，不是缺陷。**
4. 调用身份：网关给 `invoke` 的 `call_id = f"{run_id}:{call.call_id}"`，`mission_id` 来自绑定，不来自模型参数。每次调用记入 `tool_calls`，执行账本有 `provider_invocations`/回执。
5. T-8：`SandboxExecutorPort` 协议已公开（`runtime.sandbox`），但宿主写死建 Seatbelt，`resolve_executor` 的 sandboxed 模式只认 `SeatbeltExecutor` 类型，探测/成员识别/冷恢复依赖 macOS 实现。没有 Linux 实现。本机没有 Linux ARM64 设备。
6. T-9：`artifact_read` 正文上限 256 KiB、二进制 `content=None`。

## 三、方案

### 第 0 片（立刻）：发 opt.196 —— T-7 修复单独发版

AIPhone 被它挡在门口；修复小、风险低、先发。独立核验只看这一处。

### 第 1 片：公开工具接入口（T-1、T-2、T-5 的读接口、T-6）

- 公开模块：`agent_orchestrator.runtime.domain_tools`（`DomainTool`）、`agent_orchestrator.runtime.connectors`（`OperationSpec`、`Receipt`、`ConnectorRejected`、`ConnectorTransportError`、连接器协议）进 `public_api.PUBLIC_MODULES`，补 `__all__`。
- `DomainTool` 扩成正式合同（保持同一个类，不另造）：`name`（稳定名）、`description`、`schema`（JSON Schema 对象）、`invoke`（**同步或 async**：`(arguments, context) -> Mapping`；`context` 是 SDK 给的可信上下文：`mission_id`、`attempt_id`、`call_id`、`principal`、`tenant_id`）、`read_only`、`timeout_seconds`。旧三参同步签名删除（开发期不留两套）。
- 网关：async 函数直接在事件循环上 `await`（带 `timeout_seconds`，超时 → 结果 UNKNOWN 并记录）；同步函数照旧线程。结果必须是 JSON 可序列化的对象，超大按现有截断规则；返回 coroutine 当结果、返回非对象 → 拒绝并记入账本。
- 宿主入口：`OrchestrationHost(..., tools=(DomainTool, ...))`。拼装时并进 `DeploymentPolicy.domain_tools/domain_read_only_tools/allowed_tools` 与 `OrchestratorConfig.domain_tools`（照 `drone_sim.deployment()`）。名字与内置工具、技能工具冲突 → 构造时就拒绝（`ValueError`），不是起来以后才发现。
- 身份规则（写进文档，不改既有机制）：工具名集合进池身份；同一数据目录换了工具集合，已有在途任务按既定规则拒绝重开；新装目录无此问题。
- 读接口：`events(mission_id)` 已含模型调用与结果事件；补查并写明工具调用在事件流里长什么样（开始/结果/拒绝/未知），不够就加事件而不是加第二条读路径；`on_write` = "有写入"的刷新信号，内容从事件游标续读。
- 例子（`examples/orchestration-host/`）：`tools_readonly.py`（只读工具 + 脚本模型 → 规划用到它 → 结果进证据 → 报告产物）、`tools_async.py`（async 工具）。

### 第 2 片：副作用工具的正式通道（T-3、T-4）

- 不新造"带授权的工具"：**副作用一律走连接器**。宿主入口 `OrchestrationHost(..., connectors={"名字": 连接器})`，操作等级由 `OperationSpec.level` 声明，`max_action_level` 封顶；L2/L3 要人批准（`decide`），`auto_mode` 只放纯内容决定，与现在一致。
- 应用自己的授权（角色/范围/设备能力）：连接器在 `apply` 里判断，拒绝抛 `ConnectorRejected`（FAILED，不重试）；要人等待就让操作停在审批等待（`approvals` 可读、`decide` 可批/拒；过期/取消按现有审批有效期）。一个动作只有 SDK 这一个授权事实源；应用不另开弹窗。
- 未知恢复：复用 `reconcile`/`resolve_unknown`，连接器实现 `lookup(idempotency_key)`；不能对账的连接器不许开 L2/L3（既有规则）。
- 例子：`tools_effect.py`（假连接器：批准后执行一次；拒绝时执行 0 次；"执行后响应丢失" → UNKNOWN → `lookup` 对账 → 不重放）。
- 文档：授权/等待/批准/拒绝/取消/对账的完整调用顺序。

## 四、裁决（独立核验员 2026-10-20，记录 `独立核验与裁决-2026-10-20.md`）

1. **上下文用冻结数据类 `ToolCallContext`**（mission_id、task_id、attempt_id、call_id、principal、tenant_id），签名 `invoke(arguments, context)`；旧三参签名删除，`drone_sim` 一起改。
2. **async 工具同样套每任务的锁**，并且：超时从拿到锁后起算；锁持有到调用真正结束（超时、取消之后也一样）；文档写明同一任务内工具串行、任务之间并行。
3. **工具集合变化对已有数据目录**：不做"只增不减"兼容；方案原先说的"既定规则会拒绝重开"没有验证过（池身份只算内置工具名）。第 1 片先用测试验证：同一目录用 A 建任务，再分别用 A+B、A−B 重开，记下真实结果。目标行为：宿主照常启动；在途任务用到已删工具时按任务报明确原因，不拖累整个宿主。
4. **副作用一律走连接器；宿主入口只收只读工具**：注册 `read_only=False` 的工具在构造时拒绝（没有审批、没有对账口，是第二条更顺手更不安全的路径）；不需要人批的低风险副作用用 L0/L1 连接器表达。代价：副作用要在建任务时写成 `action:` 要求，任务中途临时起意的副作用做不了，文档写清。`drone_sim_command` 另开单子，不进公开合同。

**方案里的阻断级设计改正（核验员指出，照改）：**

- async 工具不能直接交给 `_await_physical_call`（它被取消时只等不取消，协程挂住会让宿主关不掉、锁放不开）：超时或被取消时先取消内层任务，再等它真正结束，记为"不确定"；同步工具的 `timeout_seconds` 同一套语义。测试覆盖：超时、外部取消、协程吞掉取消、协程抛错。
- 工具抛出的异常（KeyError/TypeError…）现在被当作工作区错误退回给模型：统一记为执行失败，消息不回显异常全文（可能带凭据）。
- 工具说明只放一处：模型读的是参数 schema 顶层的 `description`，不另加字段。
- 非阻断提醒：async 工具跑在宿主事件循环上，里面做阻塞操作会卡住整个宿主（含 30 秒租约续期）——文档警告；连接器目前只支持同步执行，第 2 片给连接器加同样的 async 支持（二选一里选这个，消费方不用自己桥接）；连接器申请单只给参数名没有用途与类型——第 2 片补；只读工具调用中途崩溃后对账永远"仍不确定"——验收加这个场景。

## 五、验收（最小合同，脚本模型）

1. 仓库外空项目只装 wheel：注册只读工具 → 脚本模型调用到 handler → 结构化结果进证据 → 任务 COMPLETED。
2. 无效 schema、未知工具名、与内置同名 → 构造/调用时明确拒绝。
3. async handler：能等、能超时（结果 UNKNOWN、driver 不卡）；同步仍可用。
4. 副作用连接器：拒绝时执行 0 次；批准后只执行原授权那一次；关库重开不重复执行；响应丢失 → UNKNOWN → `lookup` 对账或 `resolve_unknown`。
5. 未注册工具的既有应用（桌面端）行为不变：钉版用例、执行池身份字节测试、启动与控制通道快照。
6. 真实模型/真机：不作为最小合同验收前提；按交接要求不自动发起。

## 七、第 1 片实施记录（只读工具注册口，2026-10-20）

**做了什么**

- 公开合同 `agent_orchestrator.runtime.domain_tools`（进公开清单）：`DomainTool(name, schema, invoke, read_only=True, timeout_seconds=60)`、`ToolCallContext(mission_id, attempt_id, call_id, task_id, principal_id, tenant_id)`。名字、schema（必须是对象且顶层有 `description`）、超时在构造时校验。旧三参签名删除，无人机模拟一起改。
- 执行器 `runtime/domain_tool_runner.py`：同步在线程、`async def` 在事件循环；每任务一把锁，超时从拿锁起算；超时/取消先取消协程、给 2 秒宽限，没结束交后台等它真正结束再放锁（线程停不下来，直接交后台）；异常只记类型名；结果必须是 JSON 对象、≤1 MB。
- 网关：领域工具走新执行器；可信身份由宿主经配置传入（`tool_call_tenant_id` / `tool_call_principal_id`，策略快照里列为"不入快照"）。
- 宿主入口 `OrchestrationHost(tools=[...])`：拒有副作用的、与内置/技能/审阅工具同名的、重复的、非 DomainTool；并进部署策略与配置。`agent_orchestrator.host` 转出 `DomainTool`、`ToolCallContext`。
- 任务事件：`ExternalToolCallStarted / Succeeded / Failed / Unknown`，带 `call_key`（= `context.call_id`，去重用）、参数名、结果（32 KB 内原样，超了只留预览并标 truncated）、耗时、错误码与异常类型名。
- **只读工具的超时与重启打断不留"不确定"**：超时交回模型的是失败 `tool_timeout`（模型可再调，SDK 不自动重试）；重启后对账直接给失败结果 `tool_interrupted`。原因：只读调用外部什么都没改；留"不确定"会把整一步挂在对账上（例子实测：超时一次后任务 120 秒不结束）。
- 公开离线辅助 `agent_orchestrator.host.offline`：`ScriptedProvider`、`FixtureWordCounter`、`worker_reply` 的公开转出（`testing` 包仍是内部）；`demo.py` 改用它，两个新例子 `tools_readonly.py`、`tools_async.py` 只用公开模块。
- 接入说明加"注册应用自己的工具"一节（规则表、事件表、续读与去重）。

**途中修的缺陷**

1. 注册了工具后任务永远不派发：执行图绑定执行权限时"角色工具"没算应用工具，派发时算了，两边对不上 → `TASKGRAPH_EXECUTION_PERMISSION_CHANGED`。改为同一算法（`taskgraph_execution_policy.py`）。
2. 授权口（部署策略）拒掉的调用不进任务事件：模型调已删除的工具时，拒绝发生在网关之前。授权口加 `on_denied` 审计回调，经网关同一条拒绝审计路径写成 `ToolCallRejected`（回调不进身份）。
3. 第 2 片（桌面端切换）后端 16 个文件当时用后端自己的格式配置，仓库 CI 的格式检查会红：按 CI 配置重排（只动格式，AST 等价，提交 f90fdf70a）。另 `host/provider.py` 导入块按 CI 配置还原（棘轮多 1 条）。

**验证（脚本模型）**

- 新用例：执行器 12 条（同步/异步、四种超时取消、串行、异常不泄密、结果格式、注册校验）；宿主 6 条（注册拒绝、同步工具可信上下文与事件、异步失败再成功、换工具集合照常启动且旧调用被拒记事件、只读超时任务照常完成、重启打断对账成失败）。
- 已有相关测试：领域工具/无人机/网关/宿主/公开边界相关 418 条通过；策略快照预期名单补两个字段。
- 后端（对着 SDK 源码）：执行池身份字节、服务生命周期、原生池、复核修复、接线隔离 32 条通过。
- 三个例子（`demo.py --scripted`、`tools_readonly.py`、`tools_async.py`）退出码 0。mypy 0；CI 格式检查、棘轮、公开边界通过。

**第 1 片核验 FAIL 后的修复（核验记录见 `独立核验与裁决-2026-10-20.md`"第 1 片核验"）**

- 必须处理 1（结果检查与事件规则不一致）：执行器的结果检查改用与事件、账本同一套规范 JSON（`canonical_json`），元组、NaN、非字符串键都判 `tool_result_invalid`；不合格时不回显内容。用例 3 条。
- 必须处理 2（重启打断后事件停在"开始"）：对账给只读调用"失败"结果时，同时补一条 `ExternalToolCallFailed`（`tool_interrupted`，同一 `call_key`）；绑定还没恢复时编排按派发记录找回这一轮的尝试。用例核对审计回调。
- 必须处理 3（卡住的线程让后续调用无限等锁）：等锁上限 = `timeout_seconds`，超了判"失败"`tool_busy`、不发起调用；锁仍等物理调用结束才放。用例：第一次超时 → 第二次 1 秒内 `tool_busy`、只调过一次 → 线程结束后第三次成功。

## 十、Linux 隔离区（AIPhone SDK-02，2026-10-20）

用户 10-20 同意开工（第 2 片的两个待定问题先放着）。在本机 Lima 虚拟机 `sh-linux`（Ubuntu 24.04.x ARM64，内核 6.8.0-147，glibc 2.39，bubblewrap 0.9.0，4 核 4 GiB）实现与实测。

**做法**

- `runtime/sandbox.py` 新增 `BwrapExecutor`：每次运行新的用户/进程/网络/IPC/UTS 命名空间，`--disable-userns`（bwrap 支持时）、`--cap-drop ALL`、`--die-with-parent`、`--new-session`；根目录是空 tmpfs，只读挂系统位置（`/usr`、库、少量 `/etc` 文件）与解释器白名单，`/tmp` 新 tmpfs，可写只有本次副本和草稿目录（宿主路径原样挂）；解释器路径途中落在白名单外的符号链接照原样建（uv 的虚拟环境需要）。
- 进程归属按进程命名空间：bwrap 的 `--info-fd` 报第一个进程和命名空间编号；成员 = `/proc/*/ns/pid` 等于它的进程（不按用户过滤，不可转储的进程也认得出）；收尸时先 pidfd 钉住、再核对命名空间、再发信号；第一个进程一结束内核结束整个命名空间。

- 平台无关的改动：Linux 进程清单与进程身份改读 `/proc`（手机上可能是 busybox 的 `ps`）；身份的启动时间是"开机号:节拍数"；僵尸进程算"不在了"；`_holding` 在 Linux 读 `/proc/*/cwd` 与描述符；启动检查里"拒绝"按行为判（抛错且目标没被改动），后台进程是否结束改用文件锁判断（Linux 隔离区有自己的进程号空间）；Linux 多一项抽象 Unix 套接字检查；列 HOME 只看到白名单建出的空上级目录也算没漏。

6. **auto**：确认页由 duties 按档案默认映射代签（只有一个未满足义务时；否则停在确认页并写事件说明）；`operation_completion` 里"效果必须人确认"的硬拒删掉；审批加来源字段，`HOST_AUTO_PERMISSION` 一次决定即关单、执行者记主机；总要人批的操作不代批；宿主注册了连接器时必须显式给 `max_action_level`。
7. **删旧入口**：SDK `submit_operation_intent`（宿主、门面、命令）、确认页"候选申请单"列表、`USER_COMMAND` 来源、Worker 看的申请单合同与 `actions/` 候选端口（若只为人提交服务）、后端转发与前端残留、对应测试。
8. **宿主入口与交付**：`OrchestrationHost(connectors=[...])`（拒名字冲突、拒只读操作、拒无幂等或无查询能力的）；事件型操作按声明列入 `enabled_event_operations`；例子 `tools_effect.py`（auto 自动批、manual 拒绝、总要人批、响应丢失对账、封口与不封口）；接入说明；独立核验只看阻断级；发版。

**不做**：连接器上的只读操作；模型写参数文件；JSON Schema 校验；`$artifact` 内联内容；条件写入；连接器内部等人；独立回读外部状态的里程碑。

## 十三、第 2 片实施记录（2026-10-20）

**做了什么（按上面八步）**

- 合同：`OperationSpec` 加 `description` / `param_schema` / `always_needs_approval`；`Criterion.action_params`（只在有参数时进 JSON）；建任务、改要求时按 `check_action_params` 查（必填齐全、规范 JSON、最多引用一份产物、无密钥；文件发布不收参数）。`TestConfigService`、`PaymentConnectorStub` 移到 `agent_orchestrator.testing.connectors`。
- 档案：`DeploymentOperationProfiles` 按（连接器，操作）分发；通用档案 `operation_profiles_generic.py`（唯一里程碑 `APPLIED`、回执纯函数解读、封口查询证明 `CONNECTOR_LOOKUP_FENCED`）。确认页 `operations[*]` 按操作给里程碑与默认里程碑；结果接收按档案的 `supported_milestones` 判，不再写死两种发布里程碑；通用操作的结果事实只核回执本身。
- 申请单：通用操作的参数由系统从要求里取，`$artifact` 绑成 `{artifact_path, content_hash, size, storage_uri}`；审阅员判据改成通用说法，参数里绑定的产物同样核对来自已接受的输入。
- 执行：`execute` / `lookup` 可为 `async def`（在宿主事件循环上跑，超时后仍算"在途"直到真正结束）；回执必须是 `Receipt`、规范 JSON、≤64 KB，否则记"不明"；异常文字截到 500 字，像密钥只记类型名；封口适配器直接用执行器刚做的那次查询的答案。
- 自动模式：每轮职责 `auto_approve_actions` 代批动作审批（`HOST_AUTO_PERMISSION`，一次决定即批准，事件执行者 `system` / `host-auto:` 前缀）；`person_required` 的请求与非动作请求拒绝代批。完成要求按操作默认里程碑代签，多于一个义务时写 `OperationCompletionNeedsPerson` 停在确认页。
- 删旧入口：宿主 / 门面 / 编排器的 `submit_operation_intent`，`OperationIntentApi.submit`，`USER_COMMAND` 来源与它在来源核对里的分支（读模型写的候选字节、256 KB 限制），Worker 申请单合同（`worker_action_contract`、`declared_action_outputs`、`with_candidate_targets`、`action_candidate` 端口、`is_operation_candidate_path` 过滤）及任务包里的 `action_candidate_contract`；后端 `mission_operation_intent_submit` 转发；前端确认页的全局里程碑与按"哈希"字样挑默认。相应测试删除或改写。
- 宿主：`OrchestrationHost(connectors=[...])`，注册时拒重名（含内置发布）、无操作、只读操作、不能去重或查询、没写 `lookup_authority`；注册了连接器必须写 `HostSettings.max_action_level`（默认改为不写＝只发布时按 L2）；`kind="event"` 的操作随注册启用。建任务的要求可写 `{"statement", "params"}`。
- 例子 `examples/orchestration-host/tools_effect.py`、接入说明 4b 节。

**与方案、裁决不一致的地方（交核验员判）**

1. 候选产物没有改成可选：没有 `$artifact` 的通用操作用"锚点产物"（该义务下最下游已接受步骤的第一份已验证产物）当候选，申请单合同与库表不动。
2. 文件发布仍按发布档案平铺绑定（`bind_artifact_params`），通用操作用 `$artifact`（`bind_artifact_refs`），两套绑定并存；一个操作最多引用一份产物。
3. 权威但不封口的连接器：查询为空时**不**同键重交，停下等人裁定（方案第 3 步写"只许同键重交"）。理由：远端请求可能还在路上，同键重交依赖服务端去重，证明不了"没生效"；宁可等人。
4. 第 5 步"取消→宽限→交后台"没有和领域工具抽成共用函数：两边语义不同（动作超时记"不明"并保留在途，工具超时记"失败"交回模型），硬抽反而多分支。
5. 库表 `operation_intent_bindings.source_kind` 的 CHECK 仍允许 `'USER_COMMAND'`：合同已不能产生它，改建表语句不带来任何保护，不动库结构。
6. 例子只演示自动代批与"总要人批"；手动拒绝、回执丢失（封口 / 不封口）放在正式测试 `tests/orchestrator/product_world/test_generic_connector.py`。

**独立核验（opus，2026-10-20）**

- 第 1 轮：一条阻断级——`async def lookup` 的封口连接器查询为空后，系统先同键重交（必被封口拒，动作变"失败"），之后失败动作不再由执行器查询、适配器又问不了 async 查询，任务停在 ACTIVE（没有重复执行，但自动重做走不通）。六条偏差全部判"可接受"。
- 修复：封口连接器不再同键重交，直接记"证实没生效"（`lookup_fenced_key`）由系统换新键重做；失败动作对封口连接器也由执行器查询，把答案交给适配器。新增用例 `test_an_async_fenced_lookup_also_proves_nonapplication_and_redoes_once`。
