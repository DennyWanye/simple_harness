## 第 1 件：候选就绪（CANDIDATE_READY）

### 裁决

改计划条文。不做事件驱动。不另立项。

### 理由

1. 原计划自身有两处说法。
   - 事件消费表第 5～13 行：候选就绪喂给 REVIEW 消费者。
   - 附录 C.1 第 480 行：`ensure_assurance_review` 的唯一调用方是"六行切换表的现有 coordinator，去重不按通知 event"。
   - §6.1 第 158～163 行：六类审阅的触发都写成原入口 → 原协调器。
2. 正文比附件优先。
   - 附录 C 标明"本正文组成部分"，接口表写明"明确实现目标"。
   - C.5 第 520 行说事件消费表"定义内部事件类别与原 writer/receiver 对应"。它是对应表，不是另一套调度。
   - C.1 是唯一一处直接点名"谁来调"的条文。它明确排除"按通知事件去重"。
3. 现状正好是 C.1 写的样子。
   - 内容审阅：`verification/verifier_router.py:251` → `orchestrator/assurance_review_runtime.py:463`。
   - 方法审阅：`orchestrator/event_handler.py:6954`。
   - 操作提案 / 结果：`orchestrator/operation_runtime.py:128`、`:311`。
   - 组合 / 终审：`orchestrator/composition_review.py:220`、`event_handler.py:10084`。
   - 六处都按审阅键幂等。审阅键就是计划里的 `review_slot_key`。"只准备一次"已经做到。
4. 只留一条路径。
   - 改成事件驱动，就要删掉六个原入口，重写协调器。过渡期必然有两条路。
   - 现有一条路已满足计划要的"一次"。为对齐附件改写六个入口，没有用户可见收益。
5. 车道说的"拆事务会出半截状态"偏重了。事件 + 游标本身就是恢复手段。但这不影响裁决，决定性依据是 C.1。

### 建议条文改法

`event-consumer-map.json` 第 5～13 行改成：

```json
{
  "class": "CANDIDATE_READY",
  "source": "original result/verified-artifact writer",
  "consumers": [],
  "work_key": "review_slot_key(mission,purpose,subject,requirements,scope,round)",
  "action": "not a cursor consumer: the six §6.1 original coordinators call ensure_assurance_review directly in their own transaction; the review_key ensure receipt is the 'once' (Appendix C.1). Notification events never create or dedupe a review slot."
}
```

`ASSURANCE-EXEC-1.1.zh-CN.md` 附录 C.5 第 520 行末尾加一句：

> 候选就绪（CANDIDATE_READY）不经游标消费：由 §6.1 六个原协调器直接确保审阅，按审阅键去重（C.1）。

## 第 2 件：下一个组合审阅槽 / 根收尾（BUSINESS_OR_RUNTIME_SETTLED 的 REVIEW 侧）

### 裁决

改计划条文。组合审阅与终审切包仍由主循环扫描触发。车道已做的一半保留。

### 理由

1. 同第 1 件。§6.1 第 160 行：组合审阅的触发是"原 children 可组合 → composition coordinator"。第 163 行：终审是"root readiness → RootReviewCoordinator.cut"。C.1 第 480 行排除通知事件去重。
2. 根收尾已经按事件做。CLOSEOUT 消费者登记了结清事件（`orchestrator/assurance_consumers.py:52-81`）。计划这一格里的"根收尾"已经满足。
3. 扫描更稳。
   - `event_handler.py:9335` `resolve_ready` 每轮看"现在能不能组合"。任何让组合可做的事实都能接住。
   - 改成事件，要把每一种"让组合可做"的事件都登记全。漏一种，中间目标就永远收不了尾。
   - 这是秩序上的风险，不是判断。按"Harness 管秩序"取更稳的一条。
4. 车道做的"结清事件唤醒卡在预算上的审阅导入"正是计划这一行的动作原文（"fresh facts may unblock original pending work"）。它只唤醒已有的同一项工作，不另开路径。保留。

## 第 3 件：有效性与收尾登记的两个检查事件名没有写方

### 裁决

做。按"只留一条路径"：三个消费者都只经屏障事件得知"检查到了"。

### 事实

1. `assurance_consumers.py:62-63`（收尾）与 `:83`（有效性）登记 `AssuranceLocalCheckImported`、`AssuranceExecutorCheckImported`。
2. 这两个是回执种类（`assurance_check_import.py:28,35`），不是事件类型。全库源码没有写这两种事件。车道说法属实。
3. 每写一条检查绑定，屏障触发器在同一事务里写一条 `AssuranceEvidenceChanged`（`storage/assurance_barrier_v26.sql:2208` `assurance_source_assurance_check_bindings_insert`，`payload.source_table='assurance_check_bindings'`）。
4. 有效性、收尾、审阅三个消费者都已登记 `AssuranceEvidenceChanged`。所以"检查到了"今天已经能叫醒三者。
5. 车道在审阅侧又加了 `AssuranceCheckBound`（`assurance_check_import.py:233`）。同一次绑定因此叫醒审阅两次。车道记录第五节 A25-02 的说明自己也承认这一点。

### 为什么选屏障事件这一条

- 屏障事件不是副作用。它是计划 §8 / 事件消费表 SOURCE_OR_AUTHORITY_CHANGED 行写明的机制（"barrier already committed with source"）。检查绑定是 §8 的来源表之一。
- 它对三个消费者已经在用。只删不加，改动最小。
- 若改登记 `AssuranceCheckBound`，有效性就会被同一事实叫醒两次。那是两条路。

### 最小做法

1. `assurance_consumers.py`：
   - `CLOSEOUT_SOURCE_EVENTS` 删 `AssuranceLocalCheckImported`、`AssuranceExecutorCheckImported` 两项。计划里收尾本来就不消费 ACTUAL_CHECK_AVAILABLE。
   - `VALIDITY_SOURCE_EVENTS` 只留 `AssuranceEvidenceChanged`。
2. `assurance_review_consumer.py`（车道分支）：
   - `WAKE_EVENTS` 去掉 `CHECK_BOUND_EVENT`；`_woken` 删检查绑定那一支（连同事后按检查规格过滤的几行）。
   - 保留 `checks_pending` 与导入前 `CHECK_PENDING` 等待。这是 A25 真正的价值。
3. 用例：
   - `test_review_waits_for_late_check.py`：最后触发事件的断言改为 `AssuranceEvidenceChanged` 且 `source_table='assurance_check_bindings'`。其余断言不变（只调一次模型、没有复审、记过 `CHECK_PENDING`）。
   - `test_review_wakeups.py` 第一条：改测"检查绑定写入后，等检查的那项导入被同一条屏障事件叫醒；做完的导入不被叫醒"。
   - 补一条：有效性消费者对一次检查绑定只入箱一次（登记表里每个名字在源码里都有写方，可用一条静态断言顺带守住）。
4. 改坏：A25-02 改成"导入前等检查后，屏障事件唤醒查询漏掉 WAITING 行"，绑定上面改过的用例。
5. 计划条文：`event-consumer-map.json` 第 23～32 行 `source` 后补一句：

   > adapter: the actual signal is the §8 barrier AssuranceEvidenceChanged committed in the same transaction as the check binding (source_table=assurance_check_bindings); no separate check event is registered.

6. `03-Assurance-1.1-对照.md` 第 438 行"VALIDITY 收检查事件"改为"三个消费者都经屏障事件收检查；原登记的两个检查事件名无写方，已删"。

## 第 4 件：车道已完成部分有没有阻断级问题

### 裁决

无阻断。可以合并。第 3 件的改动随合并一起做（属同一处唤醒登记）。

### 查过的风险点

1. **会不会永远等检查（卡死）。** 不会，产品路径里没有"必检检查不写绑定"的情况。
   - 等检查只对对象是"结果"的内容审阅生效（`checks_pending`；全库只有 `assurance_content_review.py:143` 产出 `result` 对象）。
   - 必检项来自任务的检查层去掉审阅层（`scoped_content_review.py:106-115`）。用户要求本身是 SEMANTIC，无必检项（`deployment/root.py:48`）。
   - 格式、规则检查在审阅之前跑，绑定在同一事务写入（`assurance_local_checks.py:318-345` 写完成事件 + 回执 + `bind_scoped_check`）。
   - 代码测试在审阅前跑并导入（`verifier_router.py:216-232`）。本机不能跑代码时，`code_test` 不算已部署，要它的任务直接被拒（`governance/policies.py:246-253`），走不到审阅。
   - 检查层失败或出错会短路，不调审阅员。
   - 兜底：对象停了，下次到点按"对象已停"作废（`review_subject_stopped` 在等检查之前判断）。
2. **唤醒查询会不会因重复行卡住游标。** 不会。新连的 `assurance_review_bindings` 以 `review_key` 为主键（`storage/assurance_schema.sql:25`），每项工作一行。
3. **检查绑定唤醒时读不到绑定行。** 不会。绑定行与 `AssuranceCheckBound` 事件同一事务写入（`assurance_check_import.py:212-235`）。按第 3 件这一支也会删掉。
4. **结清事件很频繁。** 每条只多一次按任务的有界查询（上限 257 行）。不阻断。
5. **重算次数。** `recheck` 拒收 `CHECK_PENDING`（`storage/assurance_work.py:377`），只走 `wait`，不吃次数。符合 §9 第 5 步第 276 行。

### 非阻断提醒（不要求本车道处理）

- 审阅正在等检查时，若用户改了要求、完成范围变了，绑定按旧范围写，导入会一直等到对象停或审阅等待窗口到。以前这种情况是"判不下来 → 复审 → 问用户"。属少见竞态，上限由对象生命期兜住。留给真实模型验收时观察。
- 合并时：`mutations.json` 末尾两车道都追加，两段都留；部署清单合并后重生成；只跑车道记录第四节列的文件，不跑整目录。
