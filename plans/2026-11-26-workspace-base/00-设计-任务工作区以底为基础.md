# 设计：后台任务用 git 管开发流程，工作区以「底」为基础（方案 A · 第二版）

- 日期：2026-11-26
- 状态：**已拍板（11-26）**，P1 SDK 核心开工；发版、真跑到时各问一次
- 来源需求：OneOneTalk `apps/ios/harness-bridge/PRD-mac-harness.md` R18（R16 真机：后台任务工作区是空的，新写的测试导入不到仓库原有模块，三次验收全挂）
- 版本：第一版（`92060be99`）用「SDK 自管的快照 + 改动集」；CEO 11-26 定：**SDK 的开发工作管理流统一用 git，AIPhone、AgentOS 里也一样**。本版按此重写，第一版的不变式分析和使用方调研沿用。
- 使用方：OneOneTalk Mac 工作台（已知）、AIPhone、AgentOS

## 0. 一句话

SDK 在自己的数据目录里有一个**工作仓库**（git）。建任务时把使用方的底（Mac 是用户仓库的当前状态，含没提交的改动；AgentOS/AIPhone 是它们交来的文件）记成一个**底提交**；每个任务一条**任务分支**，每个尝试在从底提交检出的**工作树**里干活，交结果就是一个**提交**；验收绑定提交；验收通过的步骤**合并**进任务分支；任务级验收跑在合并后的提交上；交付 = 任务分支相对底提交的改动，宿主经审批写回，写回时三方比对，用户在此期间改过的文件不覆盖。

**根因**：任务的文件世界 = 种子 + 已验证产物，使用方已有的东西进不来；执行者「看得到」仓库，验收「用不上」，两边不是同一个世界。今天的「冻结 / 按记录重建 / 哈希绑定 / 合并冲突」是 SDK 用 CAS 和自定义清单手搓的版本管理，git 正好就是这件事的成熟实现。

## 2. 为什么用 git（对 CEO 决定的落地理由）

| SDK 现有不变式 | 现在怎么做 | 用 git 怎么做 |
|---|---|---|
| 派发即冻结：尝试起步的每个字节有内容寻址身份 | 种子逐文件进 CAS 写进 intent；上游输入清单 | intent 只记**起步提交号**；提交号就是整棵树的内容寻址身份 |
| 验收按记录重建，不读活目录 | 种子 → 输入 → 产物 → 受保护，逐层写 | 从结果提交检出，再叠受保护文件 |
| code_test 绑定副本全部文件的哈希 | 每次读全部文件算 sha256 | 树号（tree id）就是全部文件的哈希，不用重读 |
| 登记「本尝试改了什么」 | 和起步状态逐文件比哈希，草稿也算 | `git diff 起步提交..结果提交`，草稿目录被忽略 |
| 步骤间同一文件冲突 | 同路径不同哈希一律拒 | git 三方合并：改的不是同一处就自动合，同一处才冲突 |
| 交付「相对什么改的」 | 没有底，只能整文件覆盖、不覆盖同名 | `git diff 底提交..任务分支`，增 / 改 / 删 / 改名都有 |
| 审计、回退 | 自建账本 | 每个尝试一个带元数据的提交，`git log` 就是整条开发流程；交付可 `git revert` |

额外收益：模型本来就熟悉 git 的概念（分支、提交、diff、合并、冲突），规划器、审阅者、主会话给用户讲进度都能直接用这套话。

## 3. 目标与不做

**目标**

1. 执行者、验收、规划器在**同一个提交**上看世界：底 + 本任务改动。
2. 交付是任务分支相对底提交的改动，能改已有文件、删文件；写回前三方比对，用户在任务期间改过的文件不覆盖。
3. 三方共用：SDK 只认「工作仓库 + 底适配器」；Mac 的底本身是 git 仓库，AgentOS / AIPhone 的底不是 git 也行——由适配器把文件导进工作仓库，写回时再按改动导出。
4. 现有不变式全部保住（见 §2 表）。

**不做**

- 数据库记录、移动照片、发消息这类**业务操作**不进本方案，照旧走连接器 + 效果账本。
- 大文件 / 二进制产物（SDK-05）、Git LFS 不在本方案；二进制文件可以待在底里、原样保留，但不给模型看内容。
- **不碰用户仓库的 `.git`**（不建分支、不改索引、不 stash、不提交），除非交付形态选了「交成分支」（§9 问题 1）。
- 不把活目录挂进沙箱，不让执行者直接写用户的真实目录。

## 4. 设计

### 4.1 工作仓库与引用布局（SDK 内部）

- 每个宿主数据根下一个工作仓库：`<data>/git/work.git`（裸仓库，SDK 独占）。工作树放在 `<data>/workspaces/<attempt_id>/`（`git worktree add`），和现在的工作区目录同一位置，网关、沙箱、路径规则不变。
- 引用（ref）布局：

```text
refs/harness/base/<mission>            底提交（任务期间钉死）
refs/harness/attempt/<attempt>         每个尝试交结果的那个提交
refs/harness/mission/<mission>         任务分支：验收通过的步骤按计划顺序合并进来
refs/harness/delivery/<mission>        交付时那一刻的任务分支头（写进效果账本）
```

- 每个提交带结构化尾注（trailer）：`Harness-Mission / Harness-Attempt / Harness-Occurrence / Harness-Verdict`，提交人是固定的「SimpleHarness」身份，不用用户的 git 身份。
- 工作仓库用 SHA-1 对象格式（为了能从用户的 SHA-1 仓库取对象；git 的 SHA-1 / SHA-256 互通还不完整）。SDK 自己的业务表照旧记 sha256 内容哈希，提交号只当「身份 + 定位」，安全性不依赖 SHA-1 抗碰撞。
- 依赖：系统 `git` 命令行 ≥ 2.38（要用 `git merge-tree --write-tree` 在裸仓库里合并，不需要工作树）。开宿主时探测一次（和沙箱探测同一套路）；没有 git 或版本太低，宿主照常开、**只是不能接底**，`delegate_task` 带底时回 `error_code: base_unavailable`。Mac 自带 2.54；AIPhone（Droidian）、AgentOS（NixOS 容器）需要各自确认能装（§9 问题 3）。

### 4.2 底适配器（宿主实现，SDK 调用）

```python
class WorkspaceBase(Protocol):
    """宿主交给 SDK 的「底」。SDK 只认这个接口，不知道背后是 git 仓库、手机目录还是 NAS。"""

    def capture(self, scope: BaseScope, limits: CaptureLimits) -> BaseCapture:
        """给出底的当前状态。两种形式二选一：
        - GitSource(repo_path, head)：底本身是 git 仓库，SDK 从它取 HEAD 的对象，再叠工作区里没提交的改动；
        - Entries：(路径, 字节) 或 (路径, 扣留原因) 的序列，SDK 自己写成一个提交。
        超过 limits 抛 BaseTooLarge（带文件数 / 字节数）。"""

    def current_hashes(self, paths: Sequence[str]) -> Mapping[str, str | None]:
        """这些路径在底里现在的 git blob 号；不存在返回 None。写回前三方比对用。"""

    def apply(self, change: ChangeSet, *, operation_key: str) -> ApplyReceipt:
        """按改动写回，逐文件三方比对，冲突不写；同一 operation_key 重复调用要幂等。"""

    def lookup(self, operation_key: str) -> ApplyReceipt | None:
        """结果不明时按 key 查回执，不重放写入。"""
```

SDK 自带三个适配器（两个真实 + 一个测试替身，接缝成立）：

- `GitRepoBase(repo)`：Mac 用。`capture` 返回 `GitSource`；SDK 用 `git fetch <repo> HEAD` 把用户的提交对象取进工作仓库（只读用户的 `.git`，不写），再用 `git ls-files -co --exclude-standard` 列出「受版本管理 + 未忽略的新文件」，把工作区里**没提交的改动**写成一个叠在 HEAD 上的提交——这就是底提交。用户的 `.gitignore` 天然把 `.env`、构建产物挡在外面。
- `DirectoryBase(root)`：没有 git 的本机目录（手机、普通文件夹）。全量遍历成 `Entries`，SDK 写成一个无父提交（或以上次同一底的底提交为父，便于看历史）。
- `InMemoryBase`：测试用。

AgentOS 若要用，写自己的 `NasSelectionBase`（返回 `Entries`，按 `base_scope` 挑一小份），见 §6.3。

**写回也走 git 的三方语义**：`apply` 对每个文件比三个 blob 号——底提交里的（base）、底现在的（current）、任务分支头的（new）。`current==base` 写；`current==new` 跳过；其他冲突。`GitRepoBase.apply` 写的是用户的**工作目录文件**（临时文件 + 原子改名），不碰用户的索引和分支（交付形态另见 §9 问题 1）。

**登记方式**：开宿主时一次性交给 SDK：`OrchestrationHost.open(root, ..., workspace_base=GitRepoBase(repo))`。三方都是「一个进程 = 一个数据根 = 一个当事人」，底是宿主级常量；AgentOS 每成员一个宿主，天然分开。

### 4.3 建任务：记底提交

1. 主会话 `delegate_task` 新增可选参数 `base_scope`（路径 glob 列表，缺省 = 整个底）。**选范围是模型的判断**，SDK 只管上限：超限回 `error_code: base_too_large`（带文件数、字节数），模型缩小范围重交——和 opt.230 的 `file_criterion_not_a_path` 同一套路。Mac 一般不用填；AgentOS 必须填。
2. `door / create_mission` 在同一个事务里：`capture` → 写底提交 → 建 `refs/harness/base/<mission>` → mission 行记 `base_commit`；业务表 `base_snapshots(mission_id, base_commit, tree, scope, withheld, source_head)` 记来历（重放用）。
3. 写底提交时 SDK 再守一道：
   - 路径规则沿用 `Workspace.resolve`：不许绝对路径、`..`；**软链改为扣留**（仓库里有软链很常见，不再整单拒）；大小写冲突的路径都扣留。
   - 疑似密钥：沿用 `refuse_secrets` 判定，**命中的文件扣留，不整单拒**；`.env*`、`*.pem`、`*.key` 等按名字直接扣留（即使被 git 跟踪了）。扣留的文件不进底提交，清单里只记路径和原因。
   - 单文件 > 512 KiB 或二进制：照常进底提交（保证工作树里文件在，`import` 不断），但读工具返回「二进制 / 超大，不给内容」，写这个路径被拒。
   - SDK 保留根统一搬到 `.harness/`（`.harness/sources/`、`.harness/scratch/`、`.harness/assurance/` 等），并写进工作仓库的 `info/exclude`，**永远不进提交**；底里出现 `.harness/` 就扣留。
4. 底提交在整个任务里**钉死**。底在任务期间被改，SDK 不感知，到写回时三方比对发现。

### 4.4 尝试：工作树 + 提交

- **起步提交**：派发时由 SDK 算出——底提交，叠上任务种子（如有，作为一个提交），再**合并**本步骤声明的 DATA 上游的结果提交（`git merge-tree`，合不上就不派发，交给规划修复）。intent 只记起步提交号（取代逐文件写种子），工作区身份 = `sha256({起步提交, source_versions, retry_of})`。
- **物化**：`git worktree add <data>/workspaces/<attempt> <起步提交>`；资料按冻结版本写进 `.harness/sources/`（只读、不进提交）；受保护文件按现有规则检查。
- **重试**：新尝试从上一尝试的**结果提交**起步（不再复制上一尝试的活目录，顺带补上第一版 §10 记的那个「信任活目录」缺口）。
- **执行者工具**：读 / 写 / 列不变；新增 `workspace_delete_file`（受保护、扣留的不能删）。草稿根 `.harness/scratch/` 在工具说明里写明。执行者**不直接用 git**（不给它 git 命令），提交、合并都是 SDK 做——「Harness 只管秩序」。
- **交结果**：SDK 在工作树里 `git add -A`（`.harness/` 已排除）并提交 → `refs/harness/attempt/<attempt>`。登记的产物 = `git diff --name-status 起步提交..结果提交`：只有真改动，草稿不在里面，删除和改名也有。`Artifact` 行照旧写（路径、sha256、CAS 存储），另加业务表 `attempt_commits(attempt_id, start_commit, result_commit)`。
- **工作树清理**：任务结束过保留期删工作树（`git worktree remove`），提交和引用保留，重放、对账照常可用——和现在「删目录、留 CAS」同一口径。

### 4.5 验收

- **验收副本**：从结果提交检出一棵临时工作树（`-verify`），叠受保护文件（`pytest:` 点名的路径、资料），不读活目录。
- **code_test 绑定**：`workspace_hash` = 结果提交的树号 + 受保护叠层的 sha256 清单的合成哈希；不用再读全部文件。Assurance 的「运行绑定在本结果快照上」照旧成立。
- **沙箱不变**：只挂验收工作树、草稿目录、全局只读白名单，禁网。`.git` 文件（工作树里那个指向工作仓库的指针）在沙箱里不可读，测试看不到版本历史，也写不了工作仓库。
- **规划器视图**：`mission_file_view` = 底提交的文件清单（路径 + blob 号，不给内容）+ 已验证产物，`FILE_PRESENT` / `FILE_SHA256` 能落在仓库原有文件上；`code` 领域的观察器可以直接在任务分支的工作树上跑现有的只读 git 命令。

### 4.6 整合：验收通过的步骤合并进任务分支

- 步骤验收通过后，SDK 把它的结果提交**合并**进 `refs/harness/mission/<mission>`（`git merge-tree --write-tree`，裸仓库内完成，不需要工作树）。
- 两个并行步骤改了同一文件的**不同地方**：git 自动合。改了**同一处**：合并冲突 → 作为事实交给规划修复，由模型决定怎么办（例如加 ORDER + DATA 边，让后者基于前者重做）。这放宽了现在「同路径不同哈希一律拒」的规则。
- **自动合并的结果是验过的**：任务级判定树跑在任务分支头上（检出 + 任务级 pytest），所以交出去的就是验过的那一个提交，「验的就是交的」不破。
- 改了底里**已有的测试文件**：允许，但交付时单列成「测试改动」，判定树把它作为风险事实交给模型判断；要不要更严见 §9 问题 2。

### 4.7 交付：任务分支 → 使用方

- 任务结束（`judge_mission`）时，SDK 把任务分支头钉成 `refs/harness/delivery/<mission>`，算出改动集 `git diff --name-status 底提交..交付提交`，写进 `final_report.change_set`；`Session.tasks()` 快照里每个完成的任务带上它（逐文件：路径、操作、是否测试改动、底 blob、新 blob、读内容用的引用；另给整份 unified diff 供界面显示）。
- 写回是一次连接器操作 `base.apply`（SDK 内置连接器，L2），复用现有的授权端口 + 效果账本：
  - **AI 不能自己批准自己**：模型不能发起 `base.apply`，只有宿主（人点、或档位规则）能发起。
  - 可以只写一部分文件（用户只点了几张卡）；回执逐文件：applied / already / conflict / failed。
  - 冲突的文件不写，回执带三份 blob 号，宿主拿来显示「任务开始后你改过这个文件」及三方差异。
  - SDK 收回执后对 applied 的文件调 `current_hashes` 复核，核不上记 failed，不说假话。
  - 结果不明按 `operation_key` 查回执，不重放写入。
- 交付形态（Mac）三选一，见 §9 问题 1。

## 5. 数据流总图

```text
宿主开宿主 ── workspace_base=适配器 ──▶ SDK（探测 git ≥ 2.38）
主会话 delegate_task(goal, criteria, base_scope?)
  └─ door：capture → 底提交 ─▶ refs/harness/base/<mission>
       （太大 → base_too_large → 模型缩小范围；没 git → base_unavailable）
HTN 规划（看得到底提交的文件清单）
  └─ 每个尝试：起步提交 = 底 (+种子) ⊕ 合并 DATA 上游的结果提交
        git worktree → 执行者读/写/删；草稿进 .harness/scratch/（不提交）
        交结果：SDK 提交 → refs/harness/attempt/<attempt>；产物 = diff 起步..结果
        验收：检出结果提交 + 受保护叠层；code_test 绑定树号
  └─ 验收通过 → 合并进 refs/harness/mission/<mission>（合不上 → 规划修复）
  └─ 判定树：检出任务分支头 → 任务级验收
任务完成：refs/harness/delivery/<mission>；change_set = diff 底..交付
宿主（人点 / 档位规则）─▶ base.apply（连接器 + 效果账本）
  └─ 适配器逐文件三方比对：写 / 已是目标 / 冲突 → SDK 复核 → 回执
```

## 6. 三个使用方怎么接

### 6.1 OneOneTalk Mac 工作台（首个接入）

- 开宿主：`workspace_base=GitRepoBase(repo)`；`deny` 额外加 `*.p12`、`*.mobileprovision` 等。凭据零接触不变：`.env` 被 `.gitignore` 挡住，且按名字扣留。
- 删掉桥里的 `product_artifacts` / `named_in_task` / 整文件覆盖的 `deliver` / `oot-deliveries.jsonl`，改读 `change_set`、调 `base.apply`。
- 交付卡片：每个改动文件一张，显示相对底提交的 diff；冲突显示「任务开始后你改过这个文件」；测试改动醒目标注；另有「整个任务的改动」总览。
- 自动写回规则见 §9 问题 4。
- 有底以后，后台执行者不再需要桥注册的 `repo_*` 实时只读工具（读的是活目录，和底提交不一致），桥把这些工具收成只给主会话和子会话。

### 6.2 AIPhone

- 现有资料里 AIPhone 的后台任务都是「从零写文件、在 App 里读」。不接底时，SDK 仍可以在内部用工作仓库管尝试、提交、合并（底提交 = 空树），所以「git 管开发流程」对它同样成立，只是没有底。
- 以后要基于手机上的某个目录工作，用 `DirectoryBase`（手机没有 git 仓库也行，SDK 自己写底提交），`limits` 调小。沙箱侧不需要新能力。
- 前提：手机 Linux（Droidian）装得上 git ≥ 2.38（§9 问题 3）。

### 6.3 AgentOS（CEO 11-26 定：常驻镜像 + 指针文件 + 操作单）

- **文档区常驻镜像**：AgentOS 后台定时把 NAS 文档区增量同步进一个常驻 git 仓库（和它现有的 NAS 索引、备份同类）。适配器 `capture` 直接返回 `GitSource(镜像仓库, 最新提交)`，任务从最新镜像提交开工，整个文档目录可见，不用模型先挑范围；顺带得到文档的历史版本。
- **照片、录像只放指针文件**：镜像里每个媒体文件对应一个小文本（路径、大小、拍摄时间、sha256），模型看得到「有什么」，要看内容时用 AgentOS 的工具取。大媒体不进 git。
- **业务记录导成只读文件**：开工时把本任务相关的记录（例如记忆一条一个文件）导出进底，作为受保护的只读层，让任务有一份一致、可复现的快照。
- **改业务记录 / 移动照片写操作单**：任务不改上面那些只读文件，而是在任务分支里写操作单（`.ops/<名字>.json`：连接器、操作、参数），一张单一个操作。交付时一份 diff 里同时看到文件改动和操作单；批准后文件经 `apply` 写回 NAS，操作单交 AgentOS 连接器逐条执行、留回执（SDK 现有效果账本）。真正动数据库和照片的仍是 AgentOS。
- **成员隔离**：家庭共享文档一个镜像、每个成员私人文档各一个镜像；每个成员的宿主只能拿自己有权看的镜像。需 AgentOS 实测。
- 写回冲突：镜像比 NAS 晚几分钟，写回逐文件三方比对兜底，晚了只多报冲突、不覆盖。
- SDK 侧新增「操作单」：交付时按单执行连接器操作。放在 P4，Mac 不需要。
- 待 AgentOS 确认：同步频率、私人/共享文档的划分、操作单首批要支持哪些操作。
- 前提：`agentos-host` 容器里有 git ≥ 2.38（CEO 已确认能装）。

## 8. 风险

1. **新增系统依赖 git**：Mac 没问题；手机和 AgentOS 容器要装。缓解：探测失败就只是不能接底，其他功能照旧，不会把宿主拖死。
2. **两套身份并存**：git 提交号（SHA-1）和 SDK 的 sha256 内容哈希。约定：业务判断（哈希绑定、对账）一律以 sha256 为准，提交号只做定位；两者的对应写进 `attempt_commits` / `base_snapshots`。
3. **工作仓库会长大**：每个任务一份底提交，未改动的文件对象共享，增量小；工作树过保留期删除。需要一条 `git gc` 规则：只回收没有任务引用的对象，P1 一起做。
4. **自动合并的语义错误**：git 合得上不代表代码对。缓解：判定树在合并后的分支头上重跑任务级验收；合并本身不算通过。
5. **AI 改测试换绿**：`pytest:` 点名的路径受保护；测试改动单列给模型和人；更严与否见 §9 问题 2。
6. **底与活目录不一致**：任务期间用户还在改，交付冲突会变多。这是如实反映；冲突粒度是文件，不覆盖用户。
7. **保留根搬到 `.harness/`**：影响资料、Assurance、判定树的路径常量。按「不留兼容分支」一次改完；已结束任务的记录照原路径重放。发版说明写清。
8. **用户代码多了一份副本**：工作仓库在宿主数据根（Mac 在 `~/Library/Application Support/OneOneTalk/harness-repos/…`，在仓库外）。今天执行者已能经 `repo_*` 读全部内容，存盘是新增的副本；被 `.gitignore` 挡住和扣留的文件不进来。
