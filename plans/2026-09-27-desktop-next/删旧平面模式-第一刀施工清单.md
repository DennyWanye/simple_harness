## 〇、先看这几条（盘点中发现、会改变做法的事实）

1. **`planning/fragments.py` 不能整文件删。** 其中 `freeze_fragment_execution`（69-165 行）在 `commit_service.create_attempt`（3373-3402 行）里对**每一次尝试**都调用（只要装了来源制品库），产出意图配置里的 `fragment_execution`（每次尝试的冻结执行快照）。它有两个通用读者：`runtime/mission_sources.py:135`（ARP 清单读里面的 occurrence 上下文）和 `orchestrator/taskgraph_execution_view.py:166-167`（实时视图）。它还在执行图那一支做输入身份核对（`validated_input_identities`）。处理：把它（连同 `_path`、`_BOOKKEEPING`）迁到中性模块，删掉其中"片段验证任务"那一支（133-146 行），其余随文件删。
2. **`graph_changes` 表这一刀不能删。** 除了管理员改图，冲突任务开启时也往里写（`commit_service._open_conflict` 2758 行，`basis.trigger="conflict"`，第二刀的东西），`observability/graph_history.py`、证据导出、Host 投影的计数都读它。这一刀只删改图的写入方，表、`insert/get/list_graph_changes`、`graph_history` 留到第二刀。
3. **`testing/fixtures.py` 里的 `COMPARE_*` 不是"候选比较"。** 它是"知识共享"演示（冲突、仲裁、综合；`demo --scenario knowledge-sharing`）的夹具，名字撞了。这一刀不动，属于第二/三刀。第一刀在夹具里要动的是管理员那几样（`graph_change_step`、`recorder_manager_change`、`demo_dynamic_dag_provider` 的 `manager_steps` 参数）。
4. **`manager_epoch` 不是管理员。** 它是分层规划的作用域纪元（`PlanPrincipal.manager_epoch`、`SemanticReadSet.manager_epoch`、`plan_commits._check_manager_epoch` 等几十处），产品在用，**一个都不能删**。`planning/manager.py` 里也没有管理员角色的东西（全是冲突任务、综合任务、预算继承、`terminal_task`），这一刀不动。
5. **`selection_revision` 有三个使用方**：`protected_tail_commits.py:19/53`（保留的首次审阅尾预算）、`mission_tail_commits.py:15/84/129/207` 和 `governance/mission_system_tail.py:20/221/329`（系统尾池，第二刀删）。迁到中性模块后三处都改导入。
6. **改迁移链里已有的建表语句会让所有现有库打不开。** `Store` 打开库时逐条比对每个迁移的校验和（`storage/store.py:286-298`），任何一条旧迁移的 DDL 变了就整库报 `SchemaIncompatible`。方案第二节要求"库里遗留的平面任务按单个任务报错、不能让主循环或 Host 列表整体崩掉"，所以建议用**追加迁移 31（DROP TABLE）**的办法删表，见第三节。
7. **改图删掉后，`obligation_commits._inherit_obligation_on_replacement`（317-412 行）和 `_successor_obligation`（413 行起）没有调用方了**（唯一调用点在 `_commit_graph_change` 1824 行；分层任务进不了改图）。随改图一起删，`full_target/test_obligation_inheritance.py` 整文件随之删。
8. **平面路径上"会去找管理员/开选择轮"的地方，删掉后一律按原来"管理员关闭（`dynamic_graph=False`）/ 没有选择策略"的那一支走**——那一支本来就存在、行为明确：非候选结果只记历史、尝试进 RETRY_WAIT、按原次数上限再试；验证失败照常重试到 `max_attempts`；工作者附带的 `proposed_tasks` 不进图。逐处写在第一节 1.1、1.2 和第二节。

## 八、拿不准的

1. **删表方式**（3.2）：建议追加迁移 31 `DROP TABLE`，不改旧迁移文本；任务说明字面写"表直接从建表语句里删"，那样做会让所有现有库（含 Host 开发库）整库打不开。请主会话定。若选迁移 31，`storage/fragment_schema.py` 文件要留着（只剩历史 DDL 文本）。
2. **两个迁出函数的命名与哈希字面量**：`selection_revision` 的哈希体里有版本字面量 `"candidate-selection-v1"`。改名迁出时若把字面量也改掉，开发库里在途任务的首次审阅尾预算修订号会对不上（`protected_tail_commits` 会拒绝那笔预留）；不改则名字和内容不一致。另外意图配置键 `fragment_execution` 要不要改名成 `execution_snapshot`（三个读者：`commit_service.py:3397-3401`、`runtime/mission_sources.py:135`、`taskgraph_execution_view.py:166-167`）。按"不做兼容"都可以改，代价是开发库在途任务。
3. **消融（`OrchestratorConfig.ablations`）整体删不删**：评测删后只剩部署配置能设；`critic` 消融在运行时还有实现（event_handler 8925-8927、`verifier_router.verify(ablated=)`）。这一刀至少删 `graph_changes` 消融；整体删则 `step08/test_ablation.py`、根目录 `test_critic_test_evidence_order.py:268` 一起处理。
4. **执行图执行策略文档的形状**：删掉 `"selection_policy"` 键和 `"selection"` 权限输入后，执行策略来源文档变了；是否有钉住这个文档形状/哈希的测试或已存来源记录（`taskgraph_policy_sources`）没有逐一核实。`mode` 字段是留成恒 `"ordinary"` 还是一起去掉，看有没有编解码器校验它。
5. **`OrchestratorConfig.to_json()` / `BackpressureLimits.to_json()` 形状变化的连带**：`runtime/legacy_provider_slots.py:130` 用 `to_json()` 做旧执行池的准入身份哈希，`evaluation/htn_identity.py:18` 用它做部署身份。记忆里有教训"并发上限也在准入身份里，改默认值同样起不来"——删字段可能让已有执行池/部署身份对不上、Host 开发库里已冻结的意图起不来。开发期按"不兼容"接受，但真机局前要清库或确认。
6. **评测库与库角色**：`policy_pin`、`library_role` / `set_library_role` / `LIBRARY_ROLE_KEY` 只为评测服务，建议随评测删；`step09/test_policy_binding.py:247` 跟着删。若主会话认为"生产库/评测库"区分属于策略库本身，就只删 pin。
