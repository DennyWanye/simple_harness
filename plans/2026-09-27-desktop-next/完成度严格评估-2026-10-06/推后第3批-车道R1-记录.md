## 一、方案（动手前写，先提交一次）

### 1.1 T04：有转换声明而没有转换器时按名拒绝

**原计划原文**：TG 计划第 283 行（§5.5）："registry 声明需要 converter 时，实际转换必须形成新产物和验收；不能拿原字节加新 schema 标签。未部署转换执行路径就明确拒绝。"

**现状**

- `SDK/artifacts/input_bindings.py:640-648` `_check_schema`：登记表里找到声明，就返回 `rule.converter_ref`，不转换，也不拒绝。
- `SDK/artifacts/input_bindings.py:1019`：原产物字节照常绑定，绑定上只多记一个 `converter_ref`（第 368、430 行）。
- `SDK/artifacts/taskgraph_inputs.py:55-56`：冻结输入复核时比较 `converter_ref`；第 118 行解码时读它。
- 全 SDK 没有执行转换的代码。产品登记表恒空，产品走不到。
- `T/full_target/test_input_manifest_resolution.py:647-668` 用例把"带转换器声明照常绑定并记下转换器"当成正确行为。

**改成什么**

1. `ResolutionProblemKind` 加一种 `CONVERTER_NOT_DEPLOYED`，配一句摘要、一句补救（补救写"登记不需要转换的声明、加一个转换步骤、或对齐格式"）。
2. `_check_schema` 只返回问题或 `None`。声明带 `converter_ref` 时，返回 `CONVERTER_NOT_DEPLOYED`，点名声明号与转换器号。声明不带转换器（原样兼容）照常绑定。
3. `SCHEMA_MISMATCH` 的补救句去掉"带转换器的声明"这条建议（那条路现在一定被拒）。

**删掉哪条旧路径**：绑定上的 `converter_ref` 字段整条删掉（解析、`to_json`、冻结输入解码、冻结复核比较）。转换器存在就拒，绑定上永远是空，留着就是死字段。登记表的 `SchemaCompatibilityRule.converter_ref` 保留，它是"声明说要转换"的事实，拒绝靠它。

**守什么保证**：不拿原字节冒充新格式；没有声明照旧报 `SCHEMA_MISMATCH`；不需要转换的声明照旧绑定；冻结输入复核时声明变成"要转换"也会被拒（复核走同一个 `_check_schema`）。

**怎么测**：改写 `T/full_target/test_input_manifest_resolution.py` 的旧用例为"带转换器的声明按名拒绝、不出清单"（先红）；加一条"不带转换器的声明照常绑定"；加一条"冻结输入复核时，登记表换成带转换器的声明会被拒"。同步改 `T/acceptance_assets/seams_current.json` 里那条用例名。

**按核心思想自查**：这是秩序（有没有部署转换路径），不是语义判断。没有加新判断分支，只把"静默放行"换成"如实拒绝并说明"。

### 1.2 T05：输入端口补有序列表（LIST）和按键映射（MAP）

**原计划原文**：TG 计划第 284 行（§5.5）："SINGLE 一份；SET/LIST 按已有 PortOrdering/显式 order 列表；MAP 按声明 key，重复 key 拒绝。"

**现状**

- `SDK/contracts/htn.py:213-217` `PortCardinality` 只有 `SINGLE`、`SET`。
- `SDK/contracts/htn.py:1200-1236` `PortSpec`：集合端口要声明排序；`set_order_declared` 只看 `SET`。
- `SDK/artifacts/input_bindings.py:971-991`：单值端口多候选报歧义；集合端口按声明排序给序号；其余一律序号 0。
- 编译期检查只认 `SET`：`SDK/planning/htn/validation.py:335`、`SDK/planning/htn/compiler.py:1570`、`SDK/graph/projection_validation.py:716`（经 `undeclared_set_ports`）。
- `DataRequirement`（`SDK/contracts/htn.py:1372-1450`）没有"映射键"字段，没有地方声明 key。

**改成什么**

1. `PortCardinality` 加 `LIST = "list"`、`MAP = "map"`。
2. `PortSpec`：
   - `LIST` 与 `SET` 一样必须声明排序，排序规则完全复用（按生产者序号、按键、显式列表）。`set_order_declared` 改为"有序多值端口（SET、LIST）已声明排序"，名字不变，三处编译期检查自动覆盖 LIST（`validation.py:335`、`compiler.py:1570` 两处直接写了 `SET`，改为同一个判断）。
   - `MAP` 不许声明排序、不许声明 `order_key`（键由数据要求声明，不由端口排序）。
3. `DataRequirement` 加可选字段 `map_key`（标识符）。`to_json` 在为空时不输出，旧字节与旧哈希不变；`from_json` 认这个可选字段。
4. 解析（`input_bindings.py`）：
   - `LIST` 与 `SET` 走同一个排序函数。
   - `MAP`：每个候选的数据要求必须带 `map_key`，否则报新种类 `MAP_KEY_MISSING`；同一端口两个候选同一个键，报新种类 `MAP_KEY_DUPLICATE`（拒，不选新的）。通过后按键排序给序号，结果稳定。
   - 非 `MAP` 端口的数据要求带了 `map_key`：报新种类 `MAP_KEY_MISPLACED`（与"缺键"分开，补救不同）。
5. 绑定（`ResolvedInputBinding`）加 `map_key` 字段，随 `to_json`、冻结输入解码一起走（替代 T04 删掉的 `converter_ref` 位置）。

**删掉哪条旧路径**：无旧路径可删。"其余一律序号 0"的兜底分支改为只给 `SINGLE`。

**守什么保证**：多值端口不按"谁最后写"定结果；映射重复键一律拒；旧网络（只有 SINGLE、SET）字节和哈希不变。

**不做的**：规划器能用的方法合同里还没有写 `map_key` 的位置（产品目前不用 MAP），本条不改工具说明和模板；记入第五节。

**怎么测**（加在 `T/full_target/test_input_manifest_resolution.py`，先红后绿）：LIST 按三种排序给序号；LIST 不声明排序被合同或编译拒；MAP 按键绑定、序号按键排序、绑定带键；MAP 重复键拒；MAP 缺键拒；非 MAP 端口带键拒；MAP 声明排序被合同拒；`DataRequirement` 无键时字节不变、有键时往返一致（加在 `T/full_target/test_semantic_binding_codec.py`）。

**按核心思想自查**：端口形状和键冲突是秩序；用哪个键、怎么组织输入由规划方声明，Harness 只核对是否成立。

### 1.3 H02：大计划图持久分阶段准备、短事务切换

**原计划原文**：HTN 计划第 608 行（§9.4）："大型图使用持久 PREPARED 版本和激活屏障，最终短事务切换 active revision；不允许一半新图、一半旧图继续派发。冻结请求不能在切换中悄悄替换内容。"

**现状**

- `SDK/orchestrator/plan_commits.py:317-378`：所有关口、写图、激活、落地任务、事件、回执都在一个事务里。
- `SDK/orchestrator/plan_commits.py:1174-1223`：先写 `PREPARED` 版本行与成员、顺序、数据要求，再在同一事务里 `activate_plan_revision`。
- `SDK/orchestrator/planning_admission_commits.py:296`：产品入口再包一层外层事务。

**开工前核对到的冲突（见第四节偏差单 1）**：原计划要把 PREPARED 版本的行先持久写进计划表，再用短事务切换。代码里这四张表的性质与此冲突：

- `plan_revisions`、`plan_memberships`、`order_constraints`、`data_requirements` 都是保证通道的"来源表"（`SDK/storage/assurance_source_inventory.py:22-26`）。每次插入、改、删都会抬高 `assurance:mission` 时代号并记一条 `AssuranceEvidenceChanged`（`SDK/storage/assurance_barrier_v26.sql:1009-1270`、`SDK/storage/schema.py:1307-1369`）；保证通道读证据快照时读这些表的全部行，不分状态（`SDK/storage/assurance_reads.py:416-421`）。
- `order_constraints`、`data_requirements` 不许删也不许改（`SDK/storage/schema.py:1129-1132、1370-1373`）。
- 版本号必须连续：`plan_commits.py:647-664` 要求新版本 = 基础版本 + 1；收敛与执行图历史同样要求（`SDK/storage/taskgraph_convergence.py:276`、`SDK/orchestrator/taskgraph_plan_commit.py:72`）。

所以：准备好的行一旦先提交，放弃时删不掉（两张表不许删），也占住下一个版本号；准备本身还会改保证通道的证据时代号与快照。做不到"失败不留半套、可干净放弃"。

**本条处理**：按规则停在这一处，只写偏差单，不改代码。偏差单里给出两种可选做法与建议，等主会话裁决。

## 四、偏差单

### 偏差单 1（H02，编号待定）：PREPARED 版本先持久写入计划表，与保证通道来源表、不可删表、连续版本号冲突

- **原计划**：HTN 计划第 608 行（§9.4）——大型图用持久 PREPARED 版本加激活屏障，最后短事务切换。
- **冲突的代码事实**：见 1.3 节"开工前核对到的冲突"三条（来源表触发器与证据快照、两张表不许删、版本号连续）。
- **影响**：照原文做，准备阶段提交后若放弃，留下删不掉的数据要求与顺序约束行，占住下一个版本号，下一次提交起不来；准备本身还会抬高保证通道时代号、进入证据快照，让在跑的保证核对把一个没生效的计划当成证据变化。
- **可选做法**
  - **甲：单独的准备表。** 新增一张不属于来源表、可删的准备表，按（任务、基础版本、命令内容哈希）存准备好的整份网络与已通过的重活结果（结构复核、执行图结构核对、收敛影响）。激活事务做屏障核对（基础版本仍是当前、准备内容哈希一致、读集与预算等关口重查），再把准备好的行写进计划表并切换。崩溃后同一命令可接着激活；别的命令或关口失败就删掉准备行。代价：激活事务仍要逐行写成员、顺序、数据要求（只是插入，不再做校验和计算），不是严格意义的"只翻一个状态"。
  - **乙：照原文写进计划表。** 需要同时改三件别处的约定：保证通道触发器与证据快照对 PREPARED 行豁免（属车道 R2 与 Assurance 计划的范围）；`order_constraints`、`data_requirements` 允许删除"所属版本仍为 PREPARED"的行；版本号允许跳号或放弃的版本号可复用。牵涉面大，且改的是另一份原计划定下的不可变约定。
- **建议**：甲。理由：不碰保证通道与不可变约定；"不留半套、可继续、可干净放弃"都能做到；默认路径的结局不变。偏离点只有一处：切换事务里仍有按图大小线性的插入。
- **本车道状态**：停在此处，未改代码，等裁决。
