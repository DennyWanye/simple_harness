# 任务书通用规则（由 slice_pipeline.sh 自动追加到每一份实施/核验任务书末尾）

2026-09-22 起生效。起因：H1 两天里代理自己启动全量回归 102 次、耗时 4.9 小时，
与流水线自动检查重复；核验轮数不封顶，后几轮只挖测试缺口不挖功能错误。
**切片任务书里的明确要求优先于本文件**（例如热文件切片要求做变异）。

## 实施者

1. **只跑定向测试**：只跑你新增或改动的测试文件，以及与改动源码直接相关的测试文件。
2. **不要跑全量回归**：不要跑 `tests/orchestrator/full_target` 整目录，不要跑旧模式回归，不要跑 `sdk_gate.sh --full`。
   流水线的自动检查会在合并前跑一次、合并后在主干上再跑一次，你再跑一遍是纯重复。
3. **实施日志只记三件事**：改了什么、为什么这样改、遗留什么。测试尾行只贴最后一次定向测试的，不要反复抄。
4. 测试先行、不编数字、工作树保持干净——这些照旧。

## 核验员

1. **判定口径**：
   - **P0（挡合并）**：功能错误、合同/线上字段与规格不符、安全问题、越界改动、旧协议行为或字节被改变。
   - **P1（测试缺口）**：某个变异没被测试杀死、某个分支没有断言等。**列出来，但不单独挡合并**。
   - P2：建议。
   只有 P0 时判「不可合」；只有 P1 时判「修后可合」；都没有判「可合」。
2. **变异测试做 4～6 条，针对最可能出错的地方**。除非切片任务书明确要求更多（热文件切片会要求）。
3. **不要跑全量回归**，理由同上；只跑本片的定向测试和你自己构造的复现。
4. **基准提交以本任务书写的为准**。如果发现本分支变基过，用任务书里写的基准，不要自己往前找。
5. 报告用**纯英文文件名**，每轮在同一文件续写。

## 流水线的收口规则（机器执行，写给人看的说明）

- 核验默认最多 2 轮。
- 第 2 轮仍是「修后可合」（即只剩测试缺口、没有功能错误）→ 跑完整检查，全绿则判
  `PIPELINE GREEN-WITH-GAPS`，测试缺口清单写入 `gaps.md`，统一登记到阶段收尾的变异专项里补。
- 任何一轮判「不可合」→ 立刻 RED，交编排者处理。
