## 二、必须修复的阻断

### R1 / P1：主动播报的工具续答丢失来源，可借旧用户回合新建任务

位置：`sdk/simple-harness-sdk/src/agent_orchestrator/host/realtime_bridge.py:368`、
`:373`、`:537`。

`ResponseStarted` 仅把主动播报的第一个 response 绑定到 `source=announcement` 回合。
工具循环的后继 response 到达时，`_active.response_id` 已存在，代码进入普通回复分支，
将后继 response 绑定到仍保留的 `_current_turn`。随后 `_dispatch` 只根据这个错误绑定检查
`source`，因此绕过主动播报不得委派或取消任务的限制。

失败反例 `test_review_announcement_tool_followup_retains_non_authorizing_origin`：

1. 用户只说“Hello”，完成普通回复。
2. 主动播报任务结果，第一个 response 调用允许的 `task_status`。
3. 工具结果后的第二个 response 调用 `delegate_task`，中间没有新的用户输入。
4. 实际返回 `status=accepted`，真实 `Delegations` 在离线 Host 中创建 **1 个任务关联**；
   期望拒绝且创建数为 0。本例没有调用真实模型或外部任务执行器。

这是实际控制命令越权，不是模型措辞问题。同一来源判断也保护 `task_cancel`，不能让续答
重新借用旧用户授权。应让整个播报及其工具续答链继承同一个非用户来源与回合绑定，
禁止用“当前最近用户回合”补齐未知 response 的授权。修复回归还须覆盖续答中的取消命令。

### R2 / P1：打断后迟到的 completed 事件覆盖播放事实，未播全文进入正常历史

位置：`sdk/simple-harness-sdk/src/agent_orchestrator/host/realtime_bridge.py:379`、
`:411`、`:466`、`:698`。

`barge_in()` 当场把播放位置及当时已知文字写入 `voice_unheard` 和回执的 `playback`。
如果取消与服务端自然完成交错，后续全文及 `ResponseFinished(status=completed)` 仍会到达。
`_commit_reply()` 重建回执时没有保留 `playback`；completed 分支也不会刷新未播记录，
因此历史得到完整回复却丢失“只播了一部分”的标记，未播记录仍是打断时的旧文字。

失败反例 `test_review_late_completed_response_preserves_interrupted_playback`：

1. 接收 1000 ms 音频，实际只播放 120 ms，生成中执行打断。
2. 服务端随后补齐全文并返回 completed。
3. 实际 `session.history()` 包含完整文字，但没有 `playback`；数据库中的 `voice_unheard`
   仍只有旧的 `Partial`，没有最终未播结论。

文本引擎从 `session.history()` 补读时收不到该全文的未播事实；重连也只能注入不完整的
未播记录。违反“未播完不能当已听/已批准”及恢复状态一致性。应以 response 为单位持久保留
打断事实，结束事件合并而非覆盖播放状态，并随最终文字更新未播内容；completed 不能撤销
本地已发生的打断。

### R3 / P1：用户开口发生在播报请求与 ResponseStarted 之间时，迟到音频仍被播放

位置：`sdk/simple-harness-sdk/src/agent_orchestrator/host/realtime_bridge.py:365`、
`:388`、`:639`、`:723`。

`_flush()` 发出触发播报请求后，response_id 可能尚未知。此时 `SpeechStarted` 调用打断，
只能清掉 `_active`，不能将尚未分配的 response 标为静音。迟到的 `ResponseStarted` 被当成
新的普通回复接纳，`OutputAudio` 又只检查已知的静音集合，不检查用户仍在说话或播报请求
已经被打断，直接向输出设备写音频。

失败反例 `test_review_pending_announcement_cannot_play_over_user_speech`：

1. `announce()` 已发送触发请求，尚未收到 ResponseStarted。
2. 收到用户 SpeechStarted，并完成本地清队列。
3. 原播报的 ResponseStarted 和 4800 字节 OutputAudio 迟到，期间没有 SpeechStopped。
4. 实际 `user_speaking=True`、离线 AudioIO 输出口仍收到 **4800 字节音频**、取消次数为 0。

这会打断用户说话，并让已经打断的播报继续发声。应保存待确认播报请求的失效状态，在迟到
response 分配时继承取消/静音事实，并在最终媒体出口再次检查播放资格；不能只依赖发起播报
时的说话状态。

### R4 / P1：FIFO 来源在被打断的慢工具与新用户回复之间错位，旧播报重新获得用户授权及播放资格

`dispatch()` 在工具完成之前就将预期续答来源放进 `_pending_responses`。用户打断只将来源标为失效；新的用户转写仍追加在同一 FIFO 后面。`ResponseStarted` 没有验证 response 对应哪次请求，直接 `popleft()`。因此新用户回复先于旧工具续答到达时，两者来源互换：

3. 新用户的 `user-reply` 先开始，误取旧播报来源，被静音及取消。
