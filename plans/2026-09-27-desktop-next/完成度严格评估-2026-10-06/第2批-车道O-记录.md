## 一、为什么不能只改两处开门条件

任务书点名的两处（`root_review_ready` 要 `effects_ready`、`_decide_actions` 要每个要求动作 SUCCEEDED）只是四道门里的两道。读代码找全了挡在"根结论先于效果形成"前面的门：

| 门 | 位置 | 现状 |
|---|---|---|
| 1 | `hierarchical_dispatch.root_review_ready` | 每个根 `effects_ready` 才开终审 |
| 2 | `resolution_commits.commit_goal_resolution` | 根 `effects_ready` 才提交（`OP_REQUIRED_EFFECTS_INCOMPLETE`）；每个现行效果证明须在终审包锚点里、效果判据须认证 PASS |
| 3 | `commit_service._require_root_resolution`（`judge_mission` 入口） | 根 `complete`（内容 + 效果）才判定 |
| 4 | `event_handler._decide_actions` | 每个要求动作 SUCCEEDED 才判定 |

更要紧的一件事：根终审（MISSION_FINAL）的判据集是**整份要求**，含 `action:…` 效果判据。真机 2026-09-28 的记录（`assurance_purpose_reviews._root_effect_materials` 的注释）说明：没有效果验收材料时，真实审阅员对动作判据答 UNKNOWN，根结论就形成不了。所以"效果结果不明时照常开终审"如果仍让终审员判效果判据，只有脚本化审阅员（逢题 PASS）会绿，真实模型下根结论照样不成、`BLOCKED_UNKNOWN` 照样到不了。

原计划 §7.2 的意思是"root 满足（业务要求）与 closeout（效果收敛）分开"。按核心思想"判断交给 LLM、同一件事只留一条路径"：每项效果由它自己的结果审阅（OPERATION_OUTCOME）判一次，效果验收就是证明；根终审判内容。效果不该被两个审阅员各判一遍。这是本车道的结构性决定，下面所有改动都从它推出来。

## 二、做了什么

### 1. 根的内容投影（一个函数，所有读根的地方都读它）

`scoped_composition_review.root_content_projection(requirements, scope)`：根要求按人确认的完成映射分成内容判据与效果判据；投影 = 内容判据 + 它们的 ALL（部署给任务要求的公式也是 ALL）。完成映射一条内容判据都没有（只有动作的任务）时退回整份要求——与 `deployment/root.root_binding` 对这种任务"全部判据都算内容"同一规则。沿用中间目标已有的 `ScopedCompositionProjection` 形状。

读它的五处：

| 位置 | 改动 |
|---|---|
| `assurance_check_policy`（批准与无损推导两处 MISSION_FINAL） | 终审策略映射的判据 = 投影判据（原来是整份要求） |
| `root_review._cut_locked` | 终审包 `criteria` / `success_expression` = 投影；`_requirements` 同时返回根范围 |
| `resolution_commits.commit_goal_resolution` 根分支 | 新 `_root_projection` 读活跃计划的根范围算投影；`_check_resolution_identity(required_criterion_ids=投影)`；`acceptable_assured_root(projected_criteria=, projected_expression=)` |
| `hierarchical_dispatch.attempt_root_resolution` / `_root_criteria` | 根结论复述投影判据（第一个参数由 requirements 改为判据序列） |
| `completion_status._compound_content` MISSION_FINAL 分支 | 包与投影比、公式按投影求值（原来比整份要求） |

`verification/scoped_acceptance.acceptable_assured_root` 加 `projected_criteria` / `projected_expression`：包的判据与公式须与投影一致（`CRITERIA_NOT_MATCHED` / `SUCCESS_EXPRESSION_MISMATCH`，照 `_acceptable_scoped` 的写法）、硬约束结构 / 硬门 / 公式 / 根覆盖都按投影算；`requirements_content_hash` 仍钉整份要求。

### 2. 效果状态作为事实进终审包

`contracts/resolution.ReviewPackage.effect_facts`（行键 `effect_key` / `state` / `complete`，`_package_rows` 校验），切包时 `read_current_effect` 的快照；只在非空时序列化，旧包字节与哈希不变。`root_review._effect_facts` 写入。审阅员说明里说"审查包里没有这一节就不写"的是回复字段，这一节是数据，不改提示词。

效果验收不再是终审的贡献：`hierarchical_dispatch.root_contributions` 删掉 `current_effect_proofs` 那段（效果中途落地不再让终审重切、不再花切包预算）；已验收效果的材料照旧由 `_root_effect_materials` 给审阅员。`current_effect_proofs` 本身还被 `taskgraph_completion_sources` 用，不删。

### 3. 四道门重排

| 门 | 改法 |
|---|---|
| 1 `root_review_ready` | 不等效果**验收**，等效果**不在途**：根范围每项必需效果的现状在 `completion_status.EFFECT_SETTLED_STATES`（已验收 / 结果不明）里才开门，与收尾 `unmet_only_by_unknown_effects` 同一个定义（见第 7 小节为什么不能完全不等） |
| 2 `commit_goal_resolution` | `OP_REQUIRED_EFFECTS_INCOMPLETE` 门只留给**非根**目标（中间目标的效果要在后继开工前收敛，没有收尾替它等）；根的效果证明锚点检查与"效果判据须认证 PASS"两段删除 |
| 3 `_require_root_resolution` | 只要求根 `content_ready`；错误文案改为 `approved completion Scope still has unmet content` |
| 4 `_decide_actions` | 判定不等动作 SUCCEEDED；判定之后每轮仍走它（撤销 / 过期的批准照样停任务，该交接的照样交接），判定已记、收尾待收敛时答"没进展"。`_decide` 里"收尾待定直接返回"的判断挪到带动作任务的 `_decide_actions` 之后、无动作任务的 `_judge` 之前 |

判定里动作判据的记法（`_judge_with_actions`）：`judge=assurance_closeout`、`action_state`（判定时动作状态）、`met` 表示"业务要求已满足、效果交收尾核对"，不表示效果已生效；`reason` 写明。

### 4. 删掉的第二条路径

`_decide_actions` 原来对 REJECTED / FAILED 动作直接停任务、对"没有候选到达动作台账"判要求未满足。重排前这些分支到不了（判定等效果齐备），重排后会抢在系统操作那条线前面：人裁"没生效"后本该按原内容重交一张新卡，却被判 `ACTION_FAILED`（`test_operation.py::test_a_publish_the_service_refuses_is_proven_unapplied_and_offered_again` 与 `test_publish_variants.py::test_a_person_rules_on_a_publish_nobody_can_settle[failed]` 当场红）。系统准备的动作被人拒绝、没生效、还没产生、撤销后待重交都归 `system_operations` / `operation_runtime`（内容换了替代重交、证实没生效按原内容重交到上限、否则交规划器一次或具名停下），这里只留 REVOKED / EXPIRED（没有别的接手方）。

### 5. 已判定的任务只在收尾还能收敛时算合法等待

判定不再等效果，于是"判定已记、等收尾"要加一个条件。`event_handler._operation_dead_end`：把原 `_has_pending_operation_completion` 开头的五条具名死路（成功却无回执、物化一直被拒、结果审阅用完、交接被拒、结果裁决打回）抽成一处；`_idle_facts` 里 `closeout_pending` / `all_rows_terminal` 在死路成立时不成立、`root_resolved` 在判定已记后不成立，让卡死检测照旧先问规划器一次再具名停下。没有它，车道 E 的"成功却无回执具名停下"用例会永远 ACTIVE。

### 6. 收尾

收尾消费者只改一处：`unmet_only_by_unknown_effects` 的状态集改读 `EFFECT_SETTLED_STATES`（同一个定义），判断不变。其余没有改：根结论先成、判定先记后，`unmet_only_by_unknown_effects` 让"只差结果不明的效果"落 `BLOCKED_UNKNOWN` / `EFFECT_UNKNOWN`、`pending_effect_keys` 点名效果；在途效果仍 `ROOT_SCOPE_UNMET`；收敛后 READY → 唯一收尾写方写完成。`BLOCKED_UNKNOWN` 不是终态。

### 7. 为什么终审不能完全不等效果（第一版做法与探针）

第一版按任务书字面做：内容就绪即开终审（发布还在等人批准时就形成根结论、记判定）。目标用例绿了，
但 `product_world/test_operation_rejected.py` 4 条红：人拒绝发布 → 规划器按理由重写内容 → 新计划版本、
新步骤 READY → 被 `HierarchicalDispatchWithheld` 挡住，任务永远 ACTIVE、没有新卡。探针
（`scratchpad/probe_rejected.py`）看到：根结论已成、职责 SATISFIED、判定已记，新步骤不再派发。根结论
不可改（用户红线：不写 `goal_resolutions.validity`），"新要求走原后继机制"——所以根结论一成，内容就冻结了。
而原计划 §7.2 要的只是"根结论先于效果**收敛**形成、收尾 BLOCKED_UNKNOWN 等结果"，不要求在效果还在途
（可能把内容改掉）时就形成。于是改成等效果不在途：已验收或结果不明。结果不明 → 开终审 → 根结论 →
判定 → 收尾 BLOCKED_UNKNOWN（目标达到）；在途（等申请单 / 审阅 / 批准 / 执行 / 结果审阅、被拒待重交）
→ 仍等，被拒后重写内容那条线原样可走。`test_publish_variants.py` 里"等批准时没有根结论 / 终审不就绪"
的三处原断言因此恢复原样，第一版为它们写的 `_until_judged` 删掉。

## 六、留给主会话的事

1. **开发期不兼容旧数据**：旧任务里已批准的 MISSION_FINAL 检查策略带整份要求的判据，与新投影不符，终审时 `POLICY_CATALOGUE_MISMATCH`；按"开发期不兼容旧数据"处理，不做迁移。
2. **Host 侧**：终审策略由 Host 调 SDK `lossless_scope_mapping(purpose="MISSION_FINAL")` 推导再批准，推导与核对都在 SDK 同一处改，Host 不用动（本工作树里没有 Host 源码，没有核对真机）。判定报告里动作判据的 `judge` 从 `action_ledger` 变成 `assurance_closeout`、多了 `action_state`，`met=True` 不再表示效果已生效——Host 若按 `met` 画勾，需要同时看同一份报告里的 `assurance_closeout` 状态。
3. **只有动作的任务**（完成映射没有内容判据）：投影退回整份要求，终审员仍判效果判据，这种任务效果结果不明时到不了 `BLOCKED_UNKNOWN`（与重排前相同）。测试库里没有这种任务，没有专门用例。
4. **行为变化要知道**：带发布的任务在效果结果不明（等人裁定 / 对账）时也会做终审、形成根结论、记判定，收尾停在 `BLOCKED_UNKNOWN`；效果在途（等批准等）时顺序与以前一样。真机点击"发布结果不明"那条路会看到任务"已判定、收尾等效果"。
5. **旧红**（本车道之前就红、与本车道无关）：`assurance_exec/test_accept_the_reviewed_package.py` 4 条——测试调用 `LeafAcceptanceAssembly._stored_package(reviewed=)`，源码没有这个参数（本车道没碰 `leaf_acceptance.py`）。
6. 第 1 批车道 E 记录第二节第 3 条的偏差单由本车道落地为 B′；车道 E 记录里"xfail 保留"的描述已过时，没有改它。
