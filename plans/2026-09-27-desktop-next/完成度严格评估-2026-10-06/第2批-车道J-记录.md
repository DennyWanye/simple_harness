### H01 重启恢复协议整套（原计划 §25.1 第 11 条、§16.4、§23 P7.1）

做法：新模块 `orchestrator/recovery_coordinator.py` 做薄协调，八步固定顺序：`recovery_locked → manifest_check → reducer_rebuild → inbox_outbox → pending_reconcile → fence_converge → orphan_reclaim → ready`。每步结果写成 `RecoveryObligation`（表 `recovery_obligations`）；恢复锁与结果在表 `recovery_runs`（`RECOVERY_LOCKED / READY / DEGRADED_RECOVERY / SUPERSEDED`）。

- 第 1 步拿锁：上一个进程留下的 `RECOVERY_LOCKED` 行按进程身份核对（进程号 + 进程启动时间）：持有者不在了、或就是本进程上一个实例 → 标 `SUPERSEDED` 接管；还活着 → `RecoveryLockHeld`（`StoreBusy` 子类）拒绝。
- 第 2 步清单核对：迁移行与 `MIGRATIONS` 逐条一致；重放覆盖清单可读且它归类的表都在库里（运行时在迁移外建的表只记名，不算对不上）；有没结束的执行图任务时部署清单（已装源码字节）必须核验通过；各执行池执行库存在；库里记了产物时产物根必须在。
- 第 3 步重建一致：复用阶段 G 的全业务重放 v3 `verify_mission`，只核没结束的任务；`INCONSISTENT` → 失败；范围外（旧口径建的）如实计数不算。没写第二套重放。
- 第 4 步 inbox/outbox：启动绑定故障结算 + 冻结意图重绑（原 `recover()` 里的那段）。
- 第 5 步未决核对：`HANDED_OFF / UNKNOWN / 未证实的 FAILED` 动作只问结果，`allow_rehandoff=False`，不发通知。
- 第 6 步围栏收敛：每个活动任务 `heal_mission` + 未结算用量回导 + 解释器核对（原 `_recover_mission_round`）。
- 第 7 步孤儿回收：见 H04；启动时文件身份冷清理的结果一并记入。
- 第 8 步 READY：唤醒执行池（`pool.bridge.recover()`）、导入迟到用量。
- `SIDE_EFFECTS_DISABLED`：READY 之前不派发、不交接、不发通知、不唤醒执行池（唤醒放到第 8 步，交接核对不重交接）。
- 失败 → `DEGRADED_RECOVERY`：`recovery_runs.failed_step` 写明停在哪一步、`detail` 写明事实；`run()` 在 `recover()` 之后看到降级直接返回，不进周期；本进程不再重试，下一次启动重来。诊断读 `Orchestrator.recovery_status()`（状态、是否禁副作用、最近一次恢复含八步结果）。
- 同一进程里之后每次 `run()` 调 `recover()` 只重入第 4、6、8 步，不再锁、不再写义务行。
- 崩溃切点 K19 加进 `crash_points.json`：注入点 `after_recovery_step`（kind=步骤名），恢复 = 下一次启动接管锁、重走八步。

### H04 子进程身份与回收材料落库（§14.4）

做法：
- `runtime/sandbox.py`：新增 `SandboxExecutionLedger` 协议、`_Executor.ledger`；`execute()` 在子进程起来后立刻 `process_identity(pid)`（macOS：`ps -o lstart=,command=` 读启动时间与命令行；进程组/会话用 `os.getpgid/getsid`，因为 macOS 的 `ps -o sess` 只打印 0）并 `record_start`；账本写不进去 → 先 `_reap` 收掉刚起的进程组再抛 `SandboxUnavailable`（不留没有回收材料的子进程）；收尾 `record_finish(exited | residual)`。
- 新 `reclaim_recorded_executions(rows)`：对每条没记结束的子进程，按落库身份（启动时间必须相同，进程组/会话有记就要相同）核对此刻的进程：对上 → `killpg` + `kill`，最多 3 轮，记 `reclaimed`/`residual`；对不上 → `identity_mismatch`，一个不碰；进程不在 → `gone`；`ps` 不可用 → `unverifiable`。命令行只记录不参与判定（沙箱里的程序可改自己的 argv）。

- 恢复协议第 7 步调 `reclaim_recorded_executions`，结果写回行；`residual`/`unverifiable` → 降级。
- 只做 macOS（用户决定 A#9）：测试 `skipif(sys.platform != "darwin")`。

### H03 资源占用环死锁分析与具名停止（§10.5、§24.1 第 10 条）

做法：
- 新 `scheduling/wait_for.py`：四种等待建 wait-for 图——先后边（after 等 before）、数据边（消费者等生产者）、共用围栏（被围住的步骤等围栏；围栏等目标上还在跑的尝试）、交接等待（步骤等 `HANDED_OFF/UNKNOWN` 的对外操作）。只收"还在等"的边（等待方的任务没结束、被等方没完成）。Tarjan 强连通分量，大小 ≥ 2 或自环才算环；`WaitCycle.digest` 可重现。`collect_wait_facts(store, network)` 只读库与当前快照；`deadlock_facts()` 给规划器/停机报告用的事实（码 `resource_wait_cycle`）。只给事实，不按文字判断、不自动改计划。
- `contracts/state_machines.py`：`MissionStopReason.DEADLOCK = "deadlock"`。
- `contracts/error_table.py`：`SchedulingStopCode.RESOURCE_WAIT_CYCLE`，归"需收敛"、不算规划器答错；`classify` 认它。
- `orchestrator/planning_repair_requests.py::request_planner_for_stall`：停滞交规划器那一条请求的 `detail` 加 `wait_for`（环的事实），即"先把环的事实交规划器一次"（片 D 第 1 项，每个计划版本一条）。
- **没做的一处（偏差单 1）**：规划器不改之后停机时取名 `deadlock` 而不是 `no_dispatchable_work`，这一行在 `event_handler.py` 停滞路径（约 2995 行 `_commit_fail_mission(... NO_DISPATCHABLE_WORK ...)`），不在本车道可改的那一段。补丁见第三节。

改动文件：新 `scheduling/wait_for.py`；`contracts/state_machines.py`；`contracts/error_table.py`；`orchestrator/planning_repair_requests.py`（一处）；`graph/network_codec_manifest_v5.json`（`state_machines.py` 的源码哈希，见第三节第 3 条）。
