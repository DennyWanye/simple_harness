## 1. 共同背景（8 局共享的机制事实）

1. **根目标签名**：Host 构造把四题都建成 `code.fix-failing-test`（statement=「make the named failing test pass and explain the change」，coverage_criteria=`c-test-passes`、`c-change-explained`），`failing_test` 参数：C1=`tests/test_public_collector.py`（绿）、C2=`tests/test_public_pipeline.py`（绿）、C3=`…::test_window_sum_covers_the_whole_requested_range`（红）、C4=`tests/test_public_pager.py`（绿）。真正的验收在 `hidden/`，worker 不可见。
2. **规划轮**（C1/C2/C4）：`MethodApplicabilityAssessed` 3 条种子方法均 `NEEDS_EVIDENCE`（`code.test-is-failing` 观察 polarity=false 但 OPEN 谓词读作 UNKNOWN；`regression-commit-known` false；authorisation UNKNOWN）→ Planner 第 1 轮 `PlanningRejected(no_applicable_method)` → 触发合成轮 `MethodSynthesisRoundRecorded`。
3. **合成方法**（C1-r1、C2-r0、C2-r1、C4-r0、C4-r1 均相同形状）：`code.fix-by-reproduce-patch-verify-explain`（C2-r1 命名为 `code.fix-failing-test.by-…`），6 步 facts→reproduce→apply→{verify, inspect}→summarize；数据需求 4 条（facts→reproduce、diagnosis→apply、patch→verify、findings→summarize）；**inspect 步只绑 `repository` 参数，没有任何数据输入**；criterion_links：c-test-passes←verify.report（evidence_requirement「verify-tests report must show the named failing test now passes after the applied patch」）、c-change-explained←summarize.summary（「summarize-review summary of inspect-changeset findings must explain what the patch changed and why」）。`method_contracts.author` 记为 `system`，但 `MethodSynthesisRoundRecorded.author=model`。
4. **叶子工作区隔离**：每个 attempt 的工作区 = 题目快照 + 声明输入端口的文件（见 worker 包 `tools_and_permissions.workspace_files`）。因此 inspect/summarize 叶永远看到未打补丁的代码；verify 叶只拿到 `patch` 端口文件。
5. **根评审包**（`root-reviewer-v2`，policy `hierarchical-root-review-v1`）：`goal_statement` 来自目标签名模板，**不含 mission 的用户目标**；每个贡献带 4096 字符上限的摘录（包预算 32768）。

## 4. 新缺陷清单（按优先级）

### N3 · P0 · SDK · 根目标已解决后被遗留 artifact 冲突判定推翻

- 现象：C3-r0/r1 `GoalResolutionCommitted`（obligation SATISFIED, root review ACCEPT）之后立刻 `MissionFailed(artifact_conflict)`；hidden/public 全 PASS 的局被判 FAILED。违反 §21.5「层级 Mission 只在根 GoalResolution 形成后才 COMPLETED」的精神——反过来也应成立：GoalResolution 已形成的 Mission 不该再被非语义检查推翻。
- 定位：`src/agent_orchestrator/orchestrator/event_handler.py`
  - L6784–6801：`_root_resolution_formed` 成功后走 `_judge(current, live)`；
  - L7977 `_judge` → L8011 `_evaluate_criteria` → L8034 `merge_accepted(list(tasks), …, tasks_by_id=all_tasks)` → 抛 `ArtifactConflict` → L8037–8041 `commit.fail_mission(ARTIFACT_CONFLICT)`；
  - `src/agent_orchestrator/artifacts/versioning.py` L130–158 `merge_accepted`：用 `Task.dependency_ids` 算祖先闭包判「独立分支」；HTN 叶子的 `dependency_ids=[]`（`TaskCommitted.dependencies=[]`，顺序只在 `order_constraints`），于是任何两叶同路径不同内容都算冲突。
- 触发条件：hierarchical 模式 + 至少两个叶子写同一路径不同内容（用户目标里「改完在 REPORT.md 写清楚」几乎保证每叶都写 REPORT.md）+ 根评审 ACCEPT。C1/C2/C4 若根评审通过也会同样撞上。
- 复现：任意 HTN code 局，让两叶各写 REPORT.md，根评审 ACCEPT → 观察 `MissionFailed(artifact_conflict)`。单测可用 `tests/orchestrator/full_target/` 的 htn fixture 构造两叶同路径。
- 修法建议（任选其一，优先 a）：
  a. hierarchical 模式下 `_evaluate_criteria` 不再用 legacy `merge_accepted`；改用 `new_mode.root_resolution_inputs(mission.id)` / GoalResolution 的 `contributing_acceptances` 视图，`file:` 准则对该视图判定；
  b. `merge_accepted` 接受一个「顺序来源」参数：HTN 传 `order_constraints` 拓扑序（后写覆盖），legacy 仍用 `dependency_ids`；
  c. 最小改动：`_judge` 在 `GoalResolutionCommitted` 已存在时把 `ArtifactConflict` 降级为 warning 并按 ordinal/接受时间取最后版本。

### N1 · P1 · SDK 种子库 + 工作区语义 · inspect/summarize 叶看不到补丁

- 现象：5 局合成方法里 inspect 步 `inputs=[]`，其工作区 `workspace_files` 只有题目快照；findings/summary 一律描述未打补丁的代码并声明「未改产品代码」→ 根评审 c-change-explained 正确地 FAIL（C1-r1、C2-r1）；C2-r0/C4-r0/C4-r1 之所以 PASS，是模型在 inspect 叶里自己又改了一遍代码并把它写成「Applied change」。
- 定位：`src/agent_orchestrator/planning/htn/seed_methods/code/task_types.json` — `code.inspect-changeset.input_ports=[]`、`parameter_schema_ref=code.changeset-only`（它是给「审查外部 changeset」的 `code.review-changes-*` 用的）；`code.summarize-review` 只有 `findings` 输入。合成器（`method-synthesizer-v2`）无法把 `apply.patch` 或 `verify.report` 接进解释链——C1-r0 合成器试图绑 `summarize.report` 就被 `PORT_UNAVAILABLE` 拒，说明模型想接、库不让接。
- 修法建议：给 `code.inspect-changeset` 增加可选输入端口 `patch`(code.patch) 与 `report`(code.report)，`code.summarize-review` 增加可选 `report`；合成器提示模板加一条「承担 c-change-explained 的步骤必须绑定补丁或报告端口，否则拒绝准入」（可以在 P2.3j 的 admission 检查里实现为静态规则）。

### N2 · P1 · SDK 评审包 + Host 构造 · c-test-passes 对绿基线题按字面不可满足

- 现象：C2-r0/C2-r1/C4-r0/C4-r1 四次 c-test-passes FAIL 全部是「report 未展示 named failing test 由红转绿」。C1/C2/C4 的 `failing_test` 指向绿色可见套件，隐藏测试 worker 不可见，所以没有任何 worker 能给出这条证据。
- 两层根因：
  - Host（D2a 构造）：把「实现题面契约」题包装成 `code.fix-failing-test`；
  - SDK：`root_review.py` L1085–1089 `goal_statement` 只取 `goal_signature.statement`（模板），包内**没有 mission 用户目标**；evidence_requirement 由合成器照抄模板措辞（「named failing test now passes」），评审员没有材料去判断「这题根本没有 named failing test」。
- 修法建议：SDK 侧在 `RootReviewRequest` 加 `mission_goal`（`mission.goal` 原文）并在 `root-reviewer-v2` 模板说明「evidence_requirement 是方法作者的措辞，与 mission_goal 冲突时以后者判」；Host 侧给 C1/C2/C4 换一个目标签名（如 `code.implement-contract`，准则 `c-contract-tests-pass`/`c-change-explained`）或把 `failing_test` 指向一条真实红测试。

### N4 · P2 · SDK · 只读叶继承根的 code_test 层

- 现象：C3-r0/r1 的 facts、reproduce 叶 attempt-1 都 `VerificationFailed(code_test: 1 failed, 1 passed)`（基线红），attempt-2 模型被迫在 facts 叶修 `window.py` 才能通过；每局多 2 次 attempt、约 +30% token；C1-r1 的 reproduce 叶也因模型自加的红色复现测试被 code_test 打回。
- 定位：`TaskCommitted.proposal.verification_policy=["format_check","rule_check","code_test"]` 对每个 occurrence 一律复制根 Task 的策略（`PlanOccurrencesMaterialised`/`occurrence-tasks-v1`）。
- 修法建议：按 task type 决定 policy——`side_effect_kind=external_read` 的叶（facts/reproduce/inspect/summarize）不跑 `code_test`，只跑 format/rule；或 `code_test` 只在叶声明 `repo.write` 能力或为 finalizer 时启用。

### H1 · P1 · Host runner（非 SDK）· 交付文件由叶子 ordinal 决定

- 现象：`runner/run_h_arm.py:739 _model_changed_files` 按 `list_tasks` 顺序遍历所有 attempt 工作区，同路径后者覆盖；每个叶工作区都含题目快照，所以交付的产品文件 = ordinal 最大的叶的版本。C2-r0（summarize 叶 ordinal 6）、C4-r1（reproduce 叶 ordinal 6）交付了基线代码，补丁叶的正确版本从未被评分；C2-r1、C4-r0 恰好补丁叶 ordinal 6 才 PASS。
- 修法建议：按 `AcceptanceCommitted` 时间或 `order_constraints` 拓扑序覆盖；或 H 臂只导出 `acceptance_outputs` 端口文件 + 补丁叶工作区。docstring 里担心 F 臂空交付的问题可用「H 臂用接受顺序、F 臂保留旧逻辑，两臂各记录 source」解决。这会改变第 2 批 official 统计（C2-r0、C4-r1 应为 True）。

### 模型行为（非 SDK）

- C1-r1 补丁只改 reporter，把 `collector.py` 当只读输入未动，hidden 3 项失败。
- C4-r0/r1 inspect 叶第一次改写 `tests/test_public_pager.py` → `ResultRejected(protected_path_rewritten)`，各多 1 次 attempt（保护机制工作正常）。
- C1-r1 reproduce 叶自加的复现测试为红 → code_test 打回一次（与 N4 叠加）。
- C4-r1 verify 叶把「上游输入只读」误读成「本任务无法落补丁」，报告里用源码推演代替测试——评审员据此拒绝合理。
