# 设计：后台任务的工作区以「底」为基础（方案 A）

- 日期：2026-11-26
- 状态：**设计稿，等 CEO 拍板**；本轮不写实现、不发版、不跑付费模型
- 来源需求：OneOneTalk `apps/ios/harness-bridge/PRD-mac-harness.md` R18（R16 真机暴露：后台任务工作区是空的，新写的测试导入不到仓库原有模块，三次验收全挂）
- 使用方：OneOneTalk Mac 工作台（已知）、AIPhone、AgentOS
- 调研底稿（只读，本机临时目录，不入库）：SDK 工作区机制 8 问、三方使用方现状各一份；本文引用的代码位置都出自那两份

## 0. 一句话

宿主在开宿主时交给 SDK 一个**底**（一个能拍快照、能比对、能写回的文件树端口）；SDK 在建任务时把底拍成**不可变快照**，此后每个尝试、验收副本、判定树都从「快照 + 本任务改动」起步；任务结束时 SDK 算出**相对快照的改动集**，宿主经审批后按「三方比对」写回底，底在此期间被别人改过的文件报冲突、不覆盖。

**根因**：SDK 里任务的「文件世界」= 种子 + 已验证产物（`planning/htn/observers/workspace.py:76-96`），使用方已有的东西进不来；执行者靠实时只读工具「看得到」、验收却「用不上」，两边看的不是同一个世界。

## 2. 目标与不做

**目标**

1. 执行者、验收（rule_check / code_test / 判定树）、规划器看到的是**同一个世界**：底的快照 + 本任务改动。
2. 交付是**相对快照的改动集**（新增 / 修改 / 删除），能改已有文件；写回前三方比对，底被别人动过就冲突、不覆盖。
3. 一套 SDK 接口三方共用：Mac（本机 git 目录）、AIPhone（手机本地目录，待确认）、AgentOS（NAS 上按需挑一部分）各写一个适配器，SDK 不认识 git、NAS、手机。
4. 现有不变式全部保住：派发即冻结、验收按记录重建、哈希绑定的测试回执、崩溃恢复按身份重绑、重放口径一致。

**不做**

- 数据库记录、移动照片、发消息这类**业务操作**不进本方案，照旧走连接器 + 效果账本。本方案只管「文件树 + 文件内容改动」。
- 大文件 / 二进制产物（AIPhone、AgentOS 提过的 SDK-05）不在本方案里解决；本方案只保证二进制文件**可以待在底里不被破坏**（见 §4.3）。
- 不把活目录挂进沙箱，不让执行者直接写用户的真实底。
- 不做自动三方**合并**文本（冲突就停下等人）；是否以后做见 §9 问题 4。

## 3. 核心概念（术语）

| 词 | 意思 |
|---|---|
| **底（WorkspaceBase）** | 宿主交给 SDK 的端口：能列出并读出一棵文件树、能报某些路径的当前哈希、能把一份改动集写回去。SDK 只认这个接口。 |
| **底快照（BaseSnapshot）** | 建任务那一刻把底拍下来的不可变记录：清单 `{路径: 哈希, 大小, 可执行位}` + 按哈希存进内容寻址存储（CAS）的字节。快照 id = 规范化清单的 sha256。业务事实，可重放。 |
| **扣留（withheld）** | 底里存在但不给 SDK 内容的文件：疑似密钥、超大、二进制超限、宿主规则禁止。清单里只记路径和原因，执行者看得到「有这个文件」，读不到也不能改。 |
| **叠层顺序** | 尝试起步 = 底快照 → 任务种子 → 冻结的上游输入 → 资料（只读）→ 受保护文件。后一层覆盖前一层；同一路径在「底」和「种子」里都有时在建任务时拒绝。 |
| **改动集（ChangeSet）** | 任务结束时 SDK 算出的权威交付：`[{路径, 操作: add/modify/delete, 底哈希(add 为空), 新哈希}]` + 快照 id。只取验收通过、并被判定树采纳的贡献，不含草稿。 |
| **三方比对** | 写回每个文件时看三份哈希：底快照里的（base）、底现在的（current）、改动集要写的（new）。`current==base` → 写；`current==new` → 已是目标，跳过；其他 → 冲突。 |

## 4. 设计

### 4.1 端口（宿主实现，SDK 调用）

```python
class WorkspaceBase(Protocol):
    """宿主交给 SDK 的「底」。SDK 不知道它背后是 git 目录、手机目录还是 NAS。"""

    def capture(self, scope: BaseScope, limits: CaptureLimits) -> Iterable[BaseEntry]:
        """按范围列出底里的文件。BaseEntry = (路径, 字节) 或 (路径, 扣留原因)。
        超过 limits 时抛 BaseTooLarge（带实际文件数/字节数），由 SDK 变成给模型看的 error_code。"""

    def current_hashes(self, paths: Sequence[str]) -> Mapping[str, str | None]:
        """这些路径在底里现在的 sha256；不存在返回 None。写回前三方比对用。"""

    def apply(self, change: ChangeSet, *, operation_key: str) -> ApplyReceipt:
        """按改动集写回。必须逐文件三方比对，冲突的文件不写；同一 operation_key 重复调用要幂等。
        回执逐文件给出 applied / already / conflict / failed。"""

    def lookup(self, operation_key: str) -> ApplyReceipt | None:
        """结果不明（崩溃、超时）时按 key 查回执，不重放写入。"""
```

- 四个方法正好是现有连接器的形状（`execute / lookup_receipt`），所以**写回直接走 SDK 现有的连接器 + 效果账本 + 授权端口**：审批、幂等、结果不明对账全部复用，不另起一套。SDK 内部把底注册成一个内置连接器 `base.apply`（L2）。
- SDK 自带两个适配器：
  - `LocalDirectoryBase(root, *, list_files=None, deny=..., limits=...)`：本机目录。`list_files` 可注入，Mac 桥用 `git ls-files -co --exclude-standard` 拿「受版本管理 + 未忽略的新文件」，没有 git 的目录（手机）就全量遍历。写回用「临时文件 + 原子改名」，写前再比一次哈希。
  - `InMemoryBase`：测试用。
  - 两个真实适配器 + 一个测试替身，接缝成立（不是假想接缝）。
- AgentOS 若要用，写自己的 `NasSelectionBase`（见 §6.3）；SDK 不内置 NAS。

**登记方式**：开宿主时一次性交给 SDK：`OrchestrationHost.open(root, ..., workspace_base=LocalDirectoryBase(repo))`。三方都是「一个进程 = 一个数据根 = 一个当事人」，底是宿主级常量；需要按成员分底的 AgentOS 本来就是每成员一个宿主。

### 4.2 建任务：拍快照

1. 主会话 `delegate_task` 新增可选参数 `base_scope`：路径 glob 列表，缺省 = 整个底。**选范围是模型的判断**，SDK 只管上限：底太大时 `capture` 抛 `BaseTooLarge`，入口把它变成 `error_code: base_too_large`（带文件数和字节数）回给模型，让它缩小范围重交——和 opt.230 的 `file_criterion_not_a_path` 同一个套路。
2. `door / create_mission` 在**同一个事务**里：调 `capture` → 字节写 CAS（已有的文件内容哈希相同就复用，重复拍快照几乎不占新空间）→ 写一张新的不可变表 `base_snapshots(snapshot_id, manifest, scope, limits, withheld, captured_at)` → mission 行记 `base_snapshot_id`。
3. 拍快照时 SDK 自己再守一道：
   - 路径规则沿用 `Workspace.resolve`：不许绝对路径、`..`、软链（**软链改为扣留，不再整单拒**，仓库里有软链很常见）；忽略 `.git`、`__pycache__`、`.pytest_cache`；大小写冲突的路径对两个都扣留。
   - 疑似密钥：沿用 `refuse_secrets` 的判定，但**命中的文件扣留，不整单拒**（种子通道的整单拒对一个仓库太粗）。`.env*`、`*.pem`、`*.key` 等按名字直接扣留。
   - 单文件 > 512 KiB（现有工作区上限）或判定为二进制：字节**照存进 CAS**（保证工作区和沙箱里这个文件原样存在，`import` 不会断），但标 `readable=false`，执行者的读工具返回「二进制/超大，不给内容」，写这个路径被拒。
   - 保留前缀：SDK 自己用的根（`sources/`、`.assurance/`、`accepted-outputs/`）和底里同名目录会撞。**本方案把 SDK 保留根统一搬到 `.harness/` 下**（`.harness/sources/` 等），底里出现 `.harness/` 就扣留。按「不留兼容分支」，一次搬完，旧任务重放靠记录里的原路径，不受影响（见 §8 风险 5）。
4. 快照在整个任务里**钉死**：所有尝试、验收、判定树、规划器都引用同一个 `snapshot_id`。底在任务期间被改，SDK 不感知，到写回时由三方比对发现。

### 4.3 物化：尝试、验收副本、判定树

- `_bind_workspace`：在种子之前先铺底快照。工作区身份 `base = sha256({snapshot_id, seed 哈希, inputs 哈希, previous, source_versions})`，崩溃后重绑时快照 id 对不上就报 `workspace_identity_mismatch`（沿用现有机制）。
- `freeze_attempt_execution`：intent 只记 `snapshot_id`，**不再把底的每个文件写进 intent**（种子现在是逐文件进 intent 的，底照这样做会把整个仓库乘到每个尝试上）。
- `verification_copy`、`integrated_copy`、`exec_copy`：都从「快照 → 种子 → 输入 → 已登记产物 → 受保护文件」按记录重建，不读活目录，和现在的原则一致。
- 复制开销：底可能有几千个文件、每个尝试和每个验收副本都要铺一遍。实现上用写时复制（macOS APFS `clonefile`、Linux reflink，不支持时回退硬链接到只读 CAS 字节再按需复制）。这是实现细节，不改接口。
- code_test 的 `workspace_hash`：现在对副本**每个文件**读字节算哈希。改成「快照清单 ⊕ 叠层清单」合成的清单哈希——底文件的哈希已知，不用重读；含义不变（还是「副本里每个路径对应哪份字节」），Assurance 的「运行绑定在本结果快照上」照旧成立。
- 规划器视图 `mission_file_view` = 快照清单（只给路径和哈希，不给内容）+ 种子 + 已验证产物，让 `FILE_PRESENT` / `FILE_SHA256` 能落在仓库原有文件上。
- 沙箱不变：只挂副本、草稿目录、全局只读白名单，禁网。底的字节已经在副本里，**不需要也不允许**把活目录挂进去。

### 4.4 收结果与登记：只登记真改动

- `_read_only_initial`（「本次起步状态」）把快照清单并进去。于是登记规则「信封列出的 ∪ 相对起步状态新建或改过的」自然只登记真改动，不会把整个仓库登记成产物。
- **草稿**：给执行者一个明确的草稿根 `.harness/scratch/`（工具说明里写清楚：试验脚本、探针放这里）。草稿根下的文件不登记、不进改动集、不顺着 DATA 边传下游。顶层 `_` 开头的目录不再靠命名约定猜。
- **删除**：执行者新增工具 `workspace_delete_file`（只能删底文件或本任务新建的文件，受保护和扣留的不能删）。收结果时「快照里有、工作区里没有」= 删除，登记成一条删除记录。
- `Artifact` 不改结构；另起业务表 `base_changes(mission_id, attempt_id, path, op, base_hash, new_hash)` 记每个尝试相对快照的改动，作为改动集的原料。重放时它是业务事实。

### 4.5 受保护规则：底和「受保护种子」分开

- 现在种子里 `tests/` 下的文件默认受保护（`_protected_seed`）。**底文件默认不受保护**——方案 A 的意义就是能改已有文件。
- 仍受保护：`pytest:` 成功条件点名的路径（这是验收的尺子）、资料、未声明为输出的上游输入（现有规则不变）、扣留文件。
- 改了底里**已有的测试文件**：允许，但在改动集里单列成「测试改动」，交付卡片上醒目标出，判定树把它作为风险事实交给模型判断（「判断交给 LLM，Harness 只管约束」）。要不要更严见 §9 问题 3。

### 4.6 步骤间：底是公共的，不走 DATA 边

- 底是任务级、所有步骤共享的起点，和端口、交付绑定分开（和现在的种子同一地位）。
- 两个并行步骤改了底里同一个文件：各自的尝试互不可见（各自从快照起步）。到判定树合并时，同一路径两份不同内容 → 沿用现有「同一目标不同哈希 = 冲突」规则，交给规划修复，由模型决定谁先谁后（例如加一条 ORDER + DATA 边让后者基于前者改）。
- 下游步骤要基于上游对底文件的修改继续改：规划时声明 DATA 边，上游的修改作为冻结输入叠在底之上（叠层顺序保证「上游版本」覆盖「快照版本」）。这正是现有 P2.3o「上游改写过的种子就是下游基线」的推广。

### 4.7 交付：改动集 + 经审批写回

- 任务结束（`judge_mission`）时 SDK 从判定树采纳的贡献 + `base_changes` 算出**改动集**，写进 `final_report.change_set`，`Session.tasks()` 快照里每个完成的任务带上它（逐文件：路径、操作、是否测试改动、底哈希、新哈希、读内容用的产物引用）。
- 写回是一次连接器操作 `base.apply`：
  - 宿主的授权端口决定能不能写、写哪些（Mac：按档位和用户点击；AgentOS：按它的审批单）。**AI 不能自己批准自己**：模型不能自己发起 `base.apply`，只有宿主（人点、或档位规则）能发起。
  - 可以只写一部分文件（用户只点了其中几张卡）；改动集是整体记录，回执逐文件。
  - 冲突的文件不写，回执里带三份哈希，宿主拿来给人看「你改过这个文件」。
  - 结果不明按 `operation_key` 查回执，不重放写入（沿用效果账本）。
- 三方比对写在 SDK 的 `LocalDirectoryBase.apply` 里，也作为 `WorkspaceBase` 接口义务写进文档；SDK 收到回执后**再核一次**（对 applied 的文件调 `current_hashes` 看是否等于 new），核不上记为 failed，不说假话。

## 5. 数据流总图

```text
宿主开宿主 ── workspace_base=适配器 ──▶ SDK
主会话 delegate_task(goal, criteria, base_scope?)
  └─ door：capture(scope, limits) ─▶ CAS + base_snapshots(snapshot_id) ─▶ mission.base_snapshot_id
       （太大 → error_code base_too_large → 模型缩小范围重交）
HTN 规划（看得到快照清单）
  └─ 每个尝试：快照 → 种子 → 上游冻结输入 → 资料 → 受保护
        执行者读/写/删工作区；草稿进 .harness/scratch/
        收结果：相对起步状态的真改动 → artifacts + base_changes
        验收副本 / code_test：同样叠层按记录重建，哈希 = 快照清单 ⊕ 叠层
  └─ 判定树：快照 + 采纳的贡献 → 任务级验收
任务完成：final_report.change_set（add/modify/delete，含测试改动标记）
宿主（人点 / 档位规则）─▶ base.apply（连接器 + 效果账本）
  └─ 适配器逐文件三方比对：写 / 已是目标 / 冲突
  └─ SDK 复核 current_hashes → 回执
```

## 6. 三个使用方怎么接

### 6.1 OneOneTalk Mac 工作台（首个接入，验证方案）

- 开宿主：`workspace_base=LocalDirectoryBase(repo, list_files=git_ls_files)`；`deny` 加 `.env*`、`*.p12`、`*.mobileprovision` 等。凭据零接触不变：`.env` 永远扣留，只有桥自己读 SDK 那份 `.env`。
- 删掉桥里的 `product_artifacts` / `named_in_task` / 整文件覆盖的 `deliver` 和 `oot-deliveries.jsonl` 自建账本，改读 `change_set`、调 `base.apply`；回执由 SDK 效果账本保存。
- 交付卡片：每个改动文件一张，显示相对快照的差异（不是整文件），冲突显示「任务开始后你改过这个文件」，测试改动醒目标注。
- 自动写回规则（见 §9 问题 5）：建议 `acceptEdits / full` 档自动写回所有不冲突、非测试的改动，测试改动和冲突等人点；`readOnly` 档全部等人点。与主会话 `repo` 连接器的档位语义一致。
- 有底以后，后台执行者不再需要桥注册的 `repo_*` 实时只读工具（它们读的是活目录，和快照不一致，会让执行者和验收再次看到两个世界）。桥把这些工具的角色收成只给主会话（`tool_roles=("main", "child")`）。

### 6.2 AIPhone（底未知，先不接）

- 现有文档里 AIPhone 的后台任务都是「从零写文件、在 App 里读」，没有基于已有文件工作的需求。不接底时一切照旧（`workspace_base` 缺省为无，行为与今天完全一样）。
- 如果以后要基于手机上的某个目录工作，直接用 `LocalDirectoryBase`（手机是 Linux，没有 git 就全量遍历），`limits` 调小。沙箱侧不需要新能力：底的字节已经在副本里，两层 bwrap 照旧只挂副本。
- 需要 AIPhone 侧确认的见 §9 问题 1。

### 6.3 AgentOS（按需挑一小份）

- 底是 NAS（100 GB–2 TB）+ 数据库，整体拍快照不现实。AgentOS 写 `NasSelectionBase`：`capture` 只按 `base_scope` 挑文件（例如某个文档目录），超限就 `BaseTooLarge`，模型缩小范围；照片、录像这类二进制按 §4.2 存字节但不给内容。
- 写回：`apply` 写 NAS 文件，走 AgentOS 现有审批单；成员隔离靠「每成员一个宿主一个底」天然成立，但仍需 AgentOS 实测（它自己的合同要求）。
- 数据库记录、移动照片、记忆提交**不走本方案**，照旧用业务连接器。
- 需要 AgentOS 侧确认的见 §9 问题 2。

## 8. 风险

1. **大仓库成本**：每个任务拍一次快照要读全部文件算哈希。缓解：适配器可按「大小 + 修改时间」缓存哈希（Mac 可直接用 git 索引里的对象 id 作提示，最终仍以 sha256 为准）；CAS 去重，重复拍快照几乎不占新空间；物化用写时复制。设上限并让模型缩范围。
2. **用户代码进了数据目录**：快照字节存在宿主数据根（Mac 在 `~/Library/Application Support/OneOneTalk/harness-repos/…`，在仓库外）。今天执行者已经能经 `repo_*` 读全部内容并进模型上下文，存盘是新增的一份副本。任务结束过保留期后工作区目录会清，CAS 字节目前不清——需要一条快照字节的清理规则（只清没有任务引用的），P1 一起做。
3. **AI 改测试换绿**：底文件默认可改，模型可能改坏已有测试让验收通过。缓解：`pytest:` 点名的路径受保护；测试改动单列并交给判定树和人；是否更严由 CEO 定（§9 问题 3）。
4. **快照与活目录不一致**：任务跑的时候用户还在改仓库，交付时冲突会变多。这是如实反映，不是缺陷；冲突粒度是文件，不覆盖用户。以后可加「把冲突文件基于新底重跑一步」（不在本方案）。
5. **保留根搬到 `.harness/`**：影响资料、Assurance、判定树的路径常量和 AgentOS/AIPhone 读 `sources/` 的地方（若有）。按「不留兼容分支」一次改完；已结束任务的记录里存的是当时的路径，重放照记录走。需要在发版说明里写清。
6. **适配器写错三方比对**会覆盖用户文件：SDK 收回执后用 `current_hashes` 复核，核不上记 failed；`LocalDirectoryBase` 是 SDK 自带并测过的，使用方优先用它。

## 9. 需要 CEO 拍板的问题

1. **AIPhone 要不要接底？** 现有资料看不出它需要。建议：P1–P3 不管 AIPhone，接口保证「不接底行为完全不变」；请 AIPhone 侧回答「后台任务是否需要基于手机上已有的文件工作、是哪个目录、多大」。
2. **AgentOS 的底要不要做？** 建议：只做「按模型挑的范围、限量拍快照」这一种（只读资料为主，NAS 文件改动经审批写回）；数据库和照片移动明确不进本方案。请 AgentOS 侧确认现装版本和哪类任务需要。
3. **AI 能不能改仓库里已有的测试？** 选项：(a) 能改，交付时单列醒目、交给模型和人判断（建议）；(b) 默认不能改，任务目标里明说要改才放开；(c) 一律不能改。(a) 最灵活，(c) 最安全但「修测试」这类任务就做不了。
4. **冲突怎么处理？** 选项：(a) 冲突就停下等人，卡片显示三方差异（建议，和今天一致）；(b) 文本文件自动三方合并，合不上再等人。(b) 省事，但自动合并的结果没被验收过，违背「验的就是交的」。
5. **Mac 上后台任务的改动要不要自动写回？** 建议：`acceptEdits / full` 档自动写回不冲突、非测试改动；测试改动和冲突等人点；`readOnly` 档全部等人点。今天只自动写回「任务里点了名的文件」，有底以后改已有文件是常态，点名规则太窄。
6. **发版**：P1（+P2）做完要发 SDK opt.231 并让 Mac 桥钉新版；P3 最后要真跑一局（DeepSeek，约千万级 token）。两件事到时各问一次。
