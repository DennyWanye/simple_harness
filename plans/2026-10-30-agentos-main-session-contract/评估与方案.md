# AgentOS 需求合同 v1.0（持久主会话统筹多个工作会话）：评估与实施方案

日期：2026-10-30。基线：SDK `0.13.0.dev20260925+opt.222`。
需求原文见同目录《需求原文-AgentOS-v1.0-2026-10-30.md》。
本文只写核对过的事实。每条标"已有 / 部分 / 缺"。

## 0. 一句话结论

合同要的能力，现有 SDK 已有一半的底子：会话、委派、任务编排、收件箱、幂等重放、单进程锁、连接器幂等回执都在。
缺的是四块：**父子会话关系、多委派并存、结果驱动的自动续办、宿主授权回调**。
这四块都属于"秩序"，不属于"判断"，符合项目的核心架构思想。可以做。
有五处要先和 AgentOS 讲清楚，其中两处与用户已定的项目规则冲突（见第 3 节）。

## 1. 合同逐项对照现状

| 合同条款 | 现状（opt.222） | 判定 |
|---|---|---|
| 持久主会话、稳定身份、重开不调模型（I1，SDK-01） | `Session` 按 session_id 持久，配置冻结不符报 `session_config_frozen`，重开只补读账本 | 已有 |
| 主会话创建工作会话、父子关系、深度 1、不成环（I2） | 没有父子关系。所有会话平级，`host._sessions` 是一张字典 | 缺 |
| 一个主会话管多个工作会话，多个 Mission 并存 | 一个会话同时只许一个在途委派（`delegation.py` 报 busy）。宿主本身可以并行跑多个 Mission，`max_concurrency` 默认 2 | 部分 |
| 工作会话多轮追加输入（next_turn） | 会话本来就多轮。但委派后同一会话的下一句只是普通聊天，不会自动绑成"追加给这个任务" | 部分 |
| 运行中 steer（可选） | 宿主有 `amend_requirements`，能改在跑任务的要求。没有从会话层调它的命令 | 部分 |
| 命令幂等：command_id + request_hash，同 ID 同 hash 返原回执，异 hash 冲突（I5，SDK-04） | `send` 按幂等键做了同样的事；委派按 turn+slot 绑定（opt.222）。但没有统一的 `command_id` 和 `CommandReceipt` 类型，`respond` 没有幂等键 | 部分 |
| 受理即持久化，accepted 不等于已答（I3） | `send` 先落账再调模型。但 `send` 是同步等回复，没有"快速受理、稍后查"的异步形态 | 部分 |
| 结果可靠回到主会话：result_received / continuation / result_applied / user_seen 分开记 | inbox 记 result_ready；下一次用户输入时附进模型输入并记 `applied_turn_id`；`ack` 是人已读。四态里有三态，缺"自动续办"这一态 | 部分 |
| 结果驱动的自动唤醒 + 宿主 ContinuationPolicy（enqueue / hold / deny） | 没有。结果只在用户下一句到来时才被模型看到 | 缺 |
| 自动续办的预算上限、闲置不调模型（SDK-12） | 会话有每回合上限；任务有总预算。没有"每目标"的续办上限 | 部分 |
| Goal：有界目标、版本、完成条件、grant_ref（5.3） | 任务层有 goal + success_criteria + budget，冻结在 Mission 上。会话层没有 Goal 对象 | 缺 |
| 宿主授权回调 AuthorizationRequest / Decision | 没有回调。现有做法：`auto_mode` 代签、`decide()` 人答、`max_action_level` 封顶、`allowed_actions` 名单 | 缺 |
| 结果是资料不是授权（I6） | 已做：结果附进输入时标"不是指令，不授权新任务"，模型没有 ack 命令 | 已有 |
| 取消屏障、cancel_requested 中间态、迟到结果不倒退（I7，SDK-10） | 委派取消有 `cancel_requested` 持久 + 收敛；任务层取消有屏障。没有"取消整棵树 / 取消 goal"的范围合同 | 部分 |
| 失败、未知、审查拒绝如实保留（I8） | 已做：assurance 与 unknown 效果机制都在 | 已有 |
| owner 互斥、第二实例拒绝（SDK-11） | `.instance.lock` 文件锁，内核释放。没有 owner_generation 对外暴露 | 部分 |
| 业务效果 operation_key + params_hash + 权威回执，lookup 对账（§7，SDK-08） | 连接器协议已有 `execute(idempotency_key)` 与 `lookup(idempotency_key)`，回执有 hash，不能对账的连接器要声明 `supports_idempotency` | 已有 |
| 事件：树级游标、补读、游标过期 | 会话事件有 seq、schema_version=1、after 补读。只有单会话流，没有"主树"流 | 部分 |
| 错误码表（5.4） | 已有 8 个左右。缺 `stale_version`、`capacity_exceeded`、`active_work`、`unsupported_capability`、`incompatible_store_version`、`owner_conflict`、`cursor_expired` 等 | 部分 |
| 能力发现 capabilities（无模型调用） | 没有 | 缺 |
| 上下文压缩不丢关系、授权、回执（SDK-13） | 关系与回执都在账本里，不在提示词里。压缩只动模型上下文 | 已有（做完父子关系后要加断言） |
| 兼容、迁移、回退（§11，SDK-15） | 开发期不兼容旧数据（用户 2026-10-30 再次确认继续开发期） | **冲突**，见第 3 节 |
| 真实模型端到端示例（SDK-16） | 现有仓库外示例只有单主会话单委派 | 缺 |

## 2. 这些缺口属于"秩序"还是"判断"

对照 CLAUDE.md 的六条：

- 父子关系、命令幂等、版本、取消屏障、owner、对账、事件游标：全是秩序。归 Harness。
- "要不要开工作会话、委派什么、追加什么"：判断。归主会话模型。合同也是这样写的（模型只提参数，运行时注入身份）。
- "目标是否完成"：合同要求 finish_goal 做"机械对账"。这里要划清：Harness 只核对**结构事实**（全部委派到终态、无待审批、无 unknown 效果、必要结果已消费）。"结果好不好、算不算完成"仍交审阅员。不在 Harness 里写语义规则。
- ContinuationPolicy 和授权回调：都是宿主回调。SDK 不判业务权限。符合"少写领域规则，多提供通用机制"。

结论：合同没有要求 Harness 替模型思考。可以按原样接。

## 3. 与项目已定规则的冲突，以及给 AgentOS 的回复口径

| # | 合同要求 | 项目规则 | 处理 |

| 1 | §11 / SDK-15：store 前向迁移或回退、旧 wheel 可读旧数据、迁移失败可回原版本 | 用户 2026-10-30 定：继续开发期，不承诺数据兼容 | **不做迁移、不做回退。** 做能力发现和版本探测：`capabilities()` 报协议版本与能力集；旧库用新 wheel 打开报 `incompatible_store_version`，不原地损坏。新版本用新数据根。这条写进回复，由 AgentOS 决定能不能接受 |
| 2 | 5.2：新增原生控制命令（create_child、delegate、cancel 等） | 工具说明是执行池身份，改了旧数据起不来 | 开发期可接受。聊天池编号从 chat-v2 升到 chat-v3，旧会话起不来。随上一条一起说明 |
| 3 | I2 / SDK-07：跨 principal 隔离、家庭成员不串 | 宿主只认一个当事人；open_session 传别的当事人直接拒绝 | **用户 2026-10-30 定：一个 SDK 实例 = 一个 Agent 个体，现阶段只服务一个人，这个人是谁由 AgentOS 维护。** SDK 身份层不改：宿主上的当事人就是"这个 Agent 服务的那个人"。AgentOS 一个成员一个 Agent 实例、一个数据根。跨 principal 隔离由此自然成立。多人共用一个 Agent 留到以后，届时把人的身份下放到会话层 |

## 4. 实施方案（按合同的 M1～M4）

设计原则：不另造引擎。全部在 `agent_orchestrator/host/` 这一层加，任务层（HTN / TaskGraph / Assurance）不改。

### M1 身份与接口合同（SDK-01 / 03 / 04 / 07）

改动点：

1. **会话账本加三张表**：`relations`（parent_id、child_id、child_key、goal_ref、created_by_command）、`goals`（goal_id、version、spec、status、grant_ref）、`commands`（command_id、request_hash、receipt、status）。全部在 `session_ledger.py` 的 SQLite 里，同事务提交。
2. **统一命令入口**：所有写操作走一个 `_command(command_id, kind, body)` 内部通道：先查身份与归属，再查幂等，再查版本，再执行。`send`、`respond`、`cancel_task`、新增的 `create_child`、`put_goal`、`finish_goal` 都走它。`CommandReceipt` 按合同字段定。
3. **父子关系**：`Session.create_child(child_key, goal_ref, command_id)`。深度 1，子不能再建子。子会话用同一宿主、同一当事人、独立 session_id（`<parent>/<child_key>`），策略只能收窄。
4. **Goal**：`put_goal` / `finish_goal`。首版每主会话一个未收口 Goal。`finish_goal(succeeded)` 的结构核对见第 2 节。
5. **模型可见的控制命令**：在 `session_chat.py` 的 COMMAND_SCHEMAS 加 `create_child`、`delegate_task`（加 `child_key` 参数）、`child_status`、`send_to_child`（next_turn 指令）、`cancel`。模型只传参数，身份由运行时注入。池编号升 chat-v3。
6. **能力发现**：`Session.capabilities()`，不调模型。
7. **错误码**：按 5.4 补齐，挂在 `SessionError`。

### M2 原生异步统筹（SDK-02 / 05 / 06 / 12）

1. **多委派并存**：`delegation.py` 的 busy 判断改为"每个工作会话一个在途"，主会话按 Goal 内并发上限（默认 2，可配）。宿主总容量仍由 `max_concurrency` 管，子会话不能绕过。
2. **异步受理**：`send(..., wait=False)` 返回 accepted 回执和 input_id。回合在驱动里跑，结果从 `events()` 和 `task()` 查。同会话串行，主与子互不阻塞。
3. **追加输入绑到任务**：子会话收到 `next_turn` 指令时，记 input_id，等当前 Mission 终态后作为下一轮输入，终态后新委派通过该 input_id 建唯一关联。
4. **结果驱动续办**：inbox 收到子结果后，先记 `result_received`，再问宿主 `ContinuationPolicy`。`enqueue` 则生成一个幂等的主输入（kind=result_event，冻结 event_id 集合），进主会话队列；`hold` 只留待办；`deny` 记原因。处理完记 `result_applied`。`ack` 仍是人已读，不替代消费。
5. **续办预算**：每 Goal 的模型调用、轮次、工具调用、时间、并发上限。扣额原子化。用尽进可见等待，不重试。闲置不调模型：队列空就不唤醒。

### M3 恢复与安全收口（SDK-08 / 09 / 10 / 11 / 13 / 14 / 15）

1. **授权回调**：`AuthorizationPort`（宿主实现）。SDK 在命令受理、派发、每个连接器效果前各调一次。异常或超时等于不允许。决策可缓存但撤销要生效。`auto_mode` 保留为默认实现（全部 allow），AgentOS 换成自己的。
2. **取消范围**：`cancel(target_kind=goal|delegation|session_tree)`。屏障前已交接的效果标已交接 / 完成 / unknown。迟到结果可审计，不触发已取消 Goal 的续办。
3. **owner**：对外暴露 `owner_generation`；第二实例在公开入口报 `owner_conflict`。
4. **关闭**：`close()` 有未终态委派或未消费结果时报 `active_work`。`archive` 另加。
5. **恢复报告**：`RecoveryReport` 按合同字段。
6. **压缩断言**：父子关系、授权版本、回执在压缩前后 hash 一致的测试。
7. **版本探测**：旧库报 `incompatible_store_version`。不迁移。

### M4 可交付包

- wheel + SHA-256、CHANGELOG、公开接口参考、**合同名称到实际接口的逐项映射表**、SDK-01～16 矩阵、一个主→两子的仓库外示例（含 hold 与自动续办两种策略）。
- 发版走 `scripts/release_sdk_opt.sh`。
- 真实模型一局（SDK-16）用 DeepSeek。

### 顺序与测试口径

按用户 2026-10-03 的规则：先把 M1～M3 代码写完、主体跑通，中途只做定向测试，不跑全量回归。全部写完后一次相关回归 + 独立核验 + 一局真实模型。
每个里程碑完成后，子代理对照本文和合同评估"是否按合同做"，有偏差先改方案再改代码。

## 5. 规模判断

- 新增代码集中在 `host/` 下：`session.py`、`session_chat.py`、`delegation.py`、`inbox.py`、`session_ledger.py`，加两三个新模块（relations / goals / continuation / authorization）。
- 任务层不动。连接器协议不动。
- 测试：host 下现有 25 个测试文件，新增约 6～8 个，覆盖 SDK-01～15；SDK-16 是真实模型局。
- 池身份变一次（chat-v3）。

## 6. 用户已定的两件事（2026-10-30）

1. **身份模型**：一个 SDK 实例 = 一个 Agent 个体。现阶段一个 Agent 只服务一个人，这个人是谁由 AgentOS 维护。SDK 身份层不改。多人共用一个 Agent 以后再做（到时把人的身份下放到会话层，实例上的当事人改为"运营者"）。
2. **向 AgentOS 回复"不做迁移和回退"**：可以。

技术取舍（锁、队列、表结构、命名）按用户 2026-09-22 的规则由实现方定，不再问。

## 7. M1 细设计（2026-10-30 开工前定）

全部改动在 `agent_orchestrator/host/`。任务层、连接器协议、预算账不动。

### 7.1 账本（`session_ledger.py`，沿用 records/events 两张表，加命名空间）

| 命名空间 | 键 | 内容 |
|---|---|---|
| `commands` | command_id | `{kind, request_hash, status, receipt}`。同 ID 同 hash 返原回执；异 hash 报 `idempotency_conflict` |
| `children` | child_key | `{child_session_id, goal_ref, command_id, created_at}`。关系存在父账本 |
| `meta.parent` | — | 子账本记 `{parent_session_id, child_key}`。直接以根会话身份打开子会话号报 `permission_denied` |
| `goals` | goal_id | `GoalSpec` + `version` + `status`。每个根会话同时只许一个未收口 Goal |
| `queued_inputs` | input_id | 子会话排队的追加输入（`next_turn`）。M1 只登记与可查，M2 才处理 |
| `child_mirrors` | event_id | 父账本里镜像的子结果通知，带 `child_key`，进父 inbox |

`meta.configuration.version` 从 2 升到 3；旧库打开报 `incompatible_store_version`（原来是 `session_config_frozen`）。

`SessionError` 加 `retryable`、`safe_message` 属性。错误码按合同 5.4 列成常量表。

### 7.2 命令入口（`session.py`）

`Session._command(command_id, kind, body, apply)`：一个事务内，先查幂等，再调 `apply()` 写行与事件，最后记 `commands` 行并返回 `CommandReceipt`：
`{command_id, request_hash, status, session_id, version, event_seq, …具体 id}`。

走这个入口的：`create_child`、`put_goal`、`finish_goal`；`respond`、`cancel_task` 加可选 `command_id`。`send` 的 `key` 本来就是命令身份，不变。

### 7.3 父子会话

- `await parent.create_child(child_key, *, command_id, purpose="")` → `{child_session_id, child_key, created}`。子会话号 = `f"{parent}_c_{child_key}"`。先在父账本写 `children` 行并发 `child_created` 事件，再以子身份打开子会话（`sessions.open_session(..., parent=...)` 写 `meta.parent`）。中途崩溃，父重开时按 `children` 行把子会话重新打开。
- 深度 1：子会话上调 `create_child` 报 `invalid_request`。
- `parent.children()`、`parent.child(child_key)`。
- 委派到子：`delegate_task` 加可选 `child_key`。委派行写在**子账本**，turn_id 仍是父的回合。子账本的"一个在途"检查天然成为"每工作会话一个在途"；父自己直接委派仍是一个在途。
- 结果回父：父泵在 `catch_up` 里也走一遍每个子的 inbox，把子的终态通知镜像进父 inbox（同 event_id，加 `child_key`、`source="child_result"`），发父的 `result_ready` 事件。父下一次输入照旧把未处理通知附成资料；父提交后释放结果额度（同一本宿主预算账，结清幂等）。
- `parent.tasks()` 包含子会话的任务，每条带 `child_key`。
- 子会话的追加输入：`child_send(child_key, text, *, command_id)` 只登记到子账本 `queued_inputs` 并发 `input_accepted` 事件，返回 `input_id`。处理在 M2。

### 7.4 Goal

- `put_goal(spec, *, command_id, expected_version)`。`expected_version=0` 建，否则改。字段按合同 5.3。状态 `active|waiting|cancel_requested|succeeded|failed|cancelled`。
- `finish_goal(goal_id, outcome, *, command_id, expected_version, basis)`。Harness 只核结构事实：名下委派全部终态、没有未处理的结果通知、没有待答请求。不满足报 `active_work`。`outcome=succeeded` 还要求 `basis` 非空。好不好由审阅员判，不在这里判。
- 委派行记 `goal_ref={goal_id, version}`（建时在用的 Goal，可空）。

### 7.5 模型可见命令（`session_chat.py`）

加 `create_child`、`child_send`、`child_status`；`delegate_task` 加 `child_key`。提示词加一段"工作会话"说明。池编号 `chat-v2-c1-` → `chat-v3-c2-`。`put_goal`/`finish_goal` 不给模型，只给宿主。

### 7.6 能力发现

`session.capabilities()`：`{protocol_version: 2, session_config_version: 3, capabilities: [...], limits: {...}, pending: {...}}`。不调模型。

### 7.7 测试（M1 定向）

新文件 `tests/orchestrator/host/test_session_tree.py`，用 `test_session.FakeHost`：命令幂等矩阵、父子创建与重开恢复、直接打开子会话被拒、深度 1、委派到两个子并存、子结果镜像到父、Goal 建改收口、能力发现。改 `test_session.py` 的 `-chat-v2-` 断言为 v3；改 `test_session_replay.py` 的旧配置断言为 `incompatible_store_version`。
