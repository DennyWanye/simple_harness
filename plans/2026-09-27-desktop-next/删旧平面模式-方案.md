# 删旧平面模式：方案（第 2 版）

日期：2026-10-02　状态：第 1 步完成（SDK 工具 + 试点、Host 分层脚本化通道）；第 2 步归类进行中
依据：用户 2026-10-02 决定——旧平面模式整条线删；不走保证通道的旧审阅路径、只有测试在推进
的"周期"机制、不开执行图的分支，不必要的都删。CLAUDE.md"开发期不做旧数据兼容""同一件事
只保留一条路径"。
第 2 版改了什么：按一名 Opus 的两轮只读核验（第一轮 3 个阻断级问题，第二轮 1 个，均已改入）和第 1 步试点的发现重排。最大的
变化是把"删不走保证通道的旧路径"从这一轮挪到做执行图那一轮，原因见第三节。

## 一、现状（两轮只读盘点的结论）

产品新建任务一律是"分层 + 执行图 + 保证通道"。旧平面模式只剩四个入口：Host 的脚本化测试
场景、SDK 命令行的演示、三个基准评测的对照臂、测试夹具。

| 项目 | 规模 |
|---|---|
| 只给平面用的 SDK 核心源码 | 约 6000～7500 行 |
| SDK 里的平面夹具、演示、评测 | 约 4300 行 |
| Host 的平面夹具 | 约 1850 行 |
| SDK 涉及平面的测试文件 | 约 300 个（共 733 个） |
| 其中实际在保护两种模式共用机制的 | 约 120～150 个 |
| Host 涉及平面的测试文件 | 约 25 个（共 70 个） |

## 二、核实清楚的边界

| 机制 | 分层任务走得到吗 | 处理 |
|---|---|---|
| 管理员改图、片段验证 | 走不到（分层一进来就被拒） | 随平面一起删 |
| 候选比较（多个候选择优）、策略评测与晋级 | 结构上走得到，但产品里没有任何办法装上合格的策略，只有测试夹具装过 | 删功能，**但不能整文件删**（见下） |
| 冲突与仲裁 | **走得到**：两步对同一件事给出相反结论时，声明被标成"有争议"、不进知识库；有预留时还会建一个**永远派不出去**的平面冲突任务 | 只保留"标成有争议并如实写进最终报告"；冲突任务、仲裁、冲突预留删掉（做法见下） |
| 最终独立综合 | 综合任务在分层下从不创建，但它的预算照样被冻结、并从各步骤能分到的额度里扣掉——纯浪费 | 字段整个删，连同前端控件 |

核验指出、必须照办的三点：

1. **候选比较不能整文件删。** 选择轮的读取散在通用路径里（主派发每次都读、保证通道审阅
   读它的截止时间、预约链、任务快照的字段等十几处），要逐处改成"没有选择轮"的单路。其中
   一个函数实际是**每个带审阅步骤的尾预算修订号**（属于"预算预留"，在必须保留清单里），
   要改名迁到中性模块保留。策略库本身（建立、绑定、当前参数、并发上限）保留，只删评测与
   晋级。
2. **删冲突表之前先改三处读取。** 现在最终报告里的争议只来自冲突表，上下文摘要每次也读
   它。先把最终报告里的争议改成从声明本身派生（"有争议"状态和对方是谁），改掉摘要、压缩、
   文档上下文、Host 投影四处读取，加一条测试（两步结论矛盾时：报告里有争议条目、知识库
   里没有），再删表。把争议条目摆进最终审查包和规划包是**新增工作**，单列一项，不算"保留"。
3. **名字像旧路径、但保证通道在用的，不得误删**：任务收尾判定那一组（判定、判据评估、
   判定记录、文档覆盖、证据不足停机）、审阅入口、根审阅的切包与状态读取、组合审阅的
   取数与组包（只有"自拟组合记录"那两个函数是旧的）。`planning/manager.py` 里两个被通用
   路径使用的函数要先迁出再删文件。系统尾池的入口挂在通用路径上，删的那一刀里一起改掉
   调用点。

另外：
- "证据不足停机"的任务级那种（文档领域一步重试用尽）不分模式，保留。
- 请求里显式写旧模式，现在仍能在产品里建出平面任务；最后一刀改成拒绝。库里遗留的平面
  任务要按单个任务明确报错，不能让主循环或 Host 的列表整体崩掉。

## 三、试点的发现：SDK 测试里没有"产品同形"的世界

第 1 步做了试点（把"失败时任务次数怎么扣"这组老测试迁到分层世界），过程中摸清了一件
比预想更深的事：

- 产品里的任务同时装了三样：分层、执行图、保证通道。**SDK 的测试夹具没有一个同时具备
  这三样**：分层测试枢纽（208 个文件）两样都没装；保证通道那组没开执行图；执行图那组没装
  保证通道。产品这条路在 SDK 里没有端到端的测试，只靠 Host 层和真机局验证。
- 记账、结算、崩溃恢复在源码里按"是不是保证通道""开没开执行图"分支。老平面测试保护的
  是"两样都没有"的那些分支——**产品并不走**。
- 我试着把试点搬进三样都装的世界：计划能提交、第一次尝试能建、系统自己批准了重试，但
  到这里就走不下去了——执行图会核对真实执行者的历史，测试手工伪造的执行者通不过。也就是
  说，提交层的老机制测试**没法原样搬进产品同形的世界**，只能改写成"真实主循环 + 脚本化
  模型回复 + 真实执行者"的测试。

由此两个决定：

1. **这一轮只删平面模式**。老测试里保护共用机制的，迁到现有的分层世界（没装保证通道、
   没开执行图）。核验确认：源码里的通道判断只有"是不是保证通道"一种，平面与现有分层
   世界在记账、结算、崩溃恢复上走同一批分支；按"有没有绑定规划协议"分的那些分支，
   迁过去后反而从平面那支移到了与产品一致的那支。保护范围不减。
2. **"不走保证通道的旧路径"和"不开执行图的分支"合并，放到做执行图那一轮**。那一轮的第
   一件事是造出产品同形的测试世界，然后把保护改写过去，再把这两条旧路连同分层枢纽里
   依赖它们的测试一起删。现在就删"不走保证通道的旧路径"，会让分层枢纽 208 个文件和这
   一轮刚迁过去的测试同时失效。审阅员信息缺口也在那一轮修。

## 四、步骤（这一轮）

每一步：相关定向测试（按目录分组跑，带卡住看门狗）→ 删源码的步骤加故意改坏检验 → 一名
Opus 只读核验（只报阻断级）→ 发布 → 真机一局 → 文档 → 推送。不跑全量回归。

**第 1 步　分层版测试工具（不删任何东西）——已做试点**
- 工具：`sdk/simple-harness-sdk/tests/orchestrator/full_target/leaf_world.py`，两档：
  - 提交层（`leaf_world`）：一个已提交计划的分层任务，根做法是给定的几个原子步骤，返回每个
    步骤真实物化出来的任务行。适合"只需要一个能建第一次尝试的任务行"的测试。
  - 真实主循环（`loop_leaf`）：规划器选做法、计划提交；失败后的"再试一次"按生产顺序先拿
    "原样重试"的规划决定。分层任务没有这个决定就建不出下一次尝试，所以老测试里凡是
    "失败 → 再试"的都要用这一档。
- 试点：`step02/test_attempt_charge_by_fault.py`，3 条全过，断言一字未改。
- **Host 的分层脚本化通道——已做（2026-10-02）**：`backend/tests/orchestration/_layered_lane.py`。
  不带测试场景启动 Host 默认部署（分层 + 执行图 + 保证通道三样都装），自动模式；系统这
  一侧没有任何替身（完成要求由 Host 自动确认、规划由 Host 自动授权、执行图由 Host 启用），
  只把模型回复换成脚本：规划器提一个一步的做法、过审后采用；审阅员对包里每条准则判通过；
  执行者写文件、交结果、认领输出端口。每个角色可以换成自己的函数来写"某一步答错了会
  怎样"。**这是仓库里第一个与产品同形的脚本化测试世界。**
  - 两条测试（`test_layered_scripted_lane.py`）：①一个任务整圈跑完（7 次模型调用：提做法 →
    审做法 → 采用 → 写文件 → 交结果 → 步骤审查 → 最终审查）；②步骤审查第一次判返工，系统
    把失败交给规划器，规划器答"原样再做一次"，第二次通过，任务完成。
  - 耗时：两条测试 12 秒和 19 秒。最初是 29 秒和 44 秒，剖析后发现两处与编排无关的开销，
    测试里拿掉了（`quick_runtime`）：①执行面每轮调用前用真实向量模型给查询算向量，每次约
    1 秒 CPU（测试里按"向量模型没装"降级成按词检索，这是产品支持的降级）；②主循环等在途
    调用时退避到 1 秒。剩下的时间主要是**执行图每轮重新校验整张计划**（一个只有一步的小
    任务全程约 13 秒 CPU，计划解码 1700 多次）——这是产品代码的开销，没动，记作执行图那
    一轮的性能项；真机局里后端 CPU 很高也是这两样（向量计算的线程 + 每轮全量校验）。
  - 它不能挂在"测试场景"开关上：有测试场景时 Host 会跳过分层和保证通道的安装、并把新
    任务默认成平面。
  - 脚本化回复的计数器现在还从 `native_fixture` 导入，第 3 步第 3 刀删那个文件之前迁走。

**第 2 步　归类并迁移测试保护**
- 一名 Opus 子代理把约 300 个文件逐个归类并成表入库：①测的就是平面协议本身（删）；
  ②分层世界已有等价覆盖（删，写明对应哪个测试）；③保护共用机制且没有等价覆盖（迁）。
  **按"测试实际跑过哪些源码"归类，不按测试主题**：派发（平面与分层各有一套分配函数，只
  共用打分和背压）和产物合并（两套）这两类，迁过去保护不到原来那段代码，归到①。
- 按机制分批迁到第 1 步的工具上；体力活交 Opus 子代理，每批我复跑核实，并对被保护的源码
  做几项故意改坏检验。
- Host 的服务机制测试（排空、幂等、并发、审批、投影、重启恢复）迁到分层脚本通道。

**第 3 步　删平面专属功能（三刀，每刀一个版本）**
1. 管理员改图与片段验证；候选比较功能、策略评测与晋级（按第二节第 1 点逐处收成单路，
   尾预算修订号迁出保留）；前端"执行方式"下拉和候选比较面板。
2. 冲突任务、仲裁、冲突预留、最终独立综合（按第二节第 2 点先改读取再删表）；前端"冲突
   核对预留""最终独立综合"和仲裁审批界面。
3. 平面规划协议（旧的任务图提案、提交、改图）、平面调度与判定、平面角色的提示词、命令行
   演示、SDK 的平面脚本、Host 的测试场景和平面夹具。入口拒绝旧模式；按模式分支的约 80
   处收成单路。**这一刀按函数删、不按文件删**（第二轮核验的阻断级意见），保留清单：
   - SDK `testing/fixtures.py`：只删平面脚本（演示、候选比较、文本工具包几个系列，旧的
     任务提案/任务图提案脚本）。脚本化提供者、按角色/按任务路由、取角色、取规划包、
     模型名常量、结果信封与评审回复的脚本、记录器系列**留在原包内**（78 个分层测试文件在
     用；模块位置也不能挪——"是不是测试夹具"按包名前缀判断，会写进策略绑定）。
   - 提示词：只删平面的规划器、管理员、仲裁、综合和五个执行者变体。通用评审、默认执行者
     （分层靠它的名字换成分层版）、根审阅员、任务内容评审**保留**——现有分层世界还在用。
     保留的策略库的种子参数是从全部角色表生成的，删角色的同一刀里同步并重生成基线。
   - Host：七个平面夹具文件逐一列名再删（`native_fixture`、`native_cases`、`native_search`、
     `native_compare`、`native_context`、`native_load`、`native_arbitration`）；**`native_plane`
     是产品的执行面，不在其中**。`native_fixture` 里的脚本化回复计数器是所有脚本通道（包括
     按产品默认部署跑的 Host 测试）都要用的，第 1 步造分层脚本通道时先把它迁到中性的测试
     支撑模块。
   - 第 2 刀删"仲裁"时不波及两样同名的东西：验收规则里的"交仲裁"重试动作，和保证通道
     "判不下来交给人裁决"的机制。

**第 4 步　"周期"机制**
- 只有测试在推进。动手前先确认它与保证通道、执行图没有牵连；有牵连就也挪到执行图那一轮。

2. 把共用机制的保护改写到这个世界上。

## 六、需要用户知道的四件事

1. **前端会少四样东西**：新建任务表单里的"执行方式"下拉、"冲突核对预留"、"最终独立综合"，
   以及候选比较面板和仲裁审批界面。它们现在对产品任务要么不生效、要么只白扣预算。
2. **三个基准评测的旧对照臂**（AppWorld、AgentDojo、ARE 各一个建平面任务的跑分器）。九月
   冻结的 96 局基线就是用旧臂跑的，成绩已存档；删掉后旧臂不能再重跑，只能从历史提交里
   取回。**这一项放在最后，动手前单独问用户。**
3. **产品这条路在 SDK 里没有端到端测试**（第三节）。这不是这一轮造成的，但这一轮看清了：
   现在保护产品路径的是 Host 层测试和真机局。补上它是执行图那一轮的第一件事。
4. **工作量**：第 2 步最重（一到两天）；第 3 步每刀半天到一天。全程跨多个会话，每步结束
   都更新交接。

## 六之二、归类结果与新增的待定事项（2026-10-02）

老目录 243 个测试文件已逐个归类：`删旧平面模式-测试归类.md`（一名 Opus 子代理，按"测试实际
断言的是哪段源码"归类；其中两条结论主会话抽查过，文档领域那条有一半不对，已在下面更正）。

| 去向 | 文件数 |
|---|---|
| 删（测的就是平面专属的东西） | 76 |
| 迁：只需要一个能建第一次尝试的任务行 | 31 |
| 迁：涉及失败后再试 | 1（另有约 10 条散在别的文件里） |
| 迁：整圈跑真实主循环 + 脚本化回复 | 41 |
| 不动（其实不依赖平面；约 20 个只需删掉规格里的旧模式字段） | 80 |
| 拿不准，要定 | 14 |

没有一个整文件在分层测试里已有等价覆盖。很多文件里各条去向不同，执行时按条处理。

归类带出来、会改变做法的事实：

1. **分层测试自己也依赖平面夹具**（8 个文件：4 个动作测试、义务继承、旧库冷启动、固定任务
   额度、分配器闸门）。删平面的同一刀里要一起改，不能"另行处理"。
2. **现有两档工具还缺四样**：接受一个步骤的结果（要补输出端口声明和范围验收）；造动作
   （分层下动作只有"操作完成"一条入口，要改用现成的操作完成夹具）；造根结论；跳过规划器、
   只给执行者和审阅员脚本的整圈测试要在主循环自己的库里建任务。迁移前先补前两样。
   老目录 p35 的两个共用夹具改到分层上，约 12 个文件能一次迁完。
3. **任务总评审不是平面专属**：没装保证通道的分层任务根结论形成后照样走它。第 3 步只删
   "全部任务完成就开判"这个平面触发，评审本身留到执行图那一轮。
4. **知识与声明定级在分层测试里零覆盖**，是实打实的迁移量；"两步结论矛盾"的测试现在
   不存在，要新写。
5. **只在平面生效、可以一起删的机制**又找到几样：任务预算下限、任务级工具调用均分、角色
   可见性、系统尾池、选择轮尾预算。
6. 删文件的连带改动：领域档案里钉着冲突模板、综合策略和平面角色；部署清单列了所有平面
   源码文件的哈希，删文件要重生成（部署编号会变）；三个测试文件顶部导入了平面符号，要留
   的条目得先拆到新文件。

## 六之二点六（更正）：严格引用模式那一项的前提不成立，要用户重新定

主会话向用户建议"平面那套文档机制随平面删"时说过"它在分层下现在本来就没生效，所以产品
行为不变"。**这句话不成立。** 一名 Opus 只读逐项核实（2026-10-02）的结论：严格引用任务

停下。上面"六之二点六"第 1 条据此作废，等用户重新定。

实际在起作用的（严格引用任务比"通用任务附同样资料"多出来的）：

1. 每一步的引用核对：每条要求要么有一句结论与它字面一致且引用能在资料里找到，要么声明
   认领这条要求并写出局限说明；否则这一步的规则检查不通过。
2. 证据种类限制：不允许拿"跑过的测试""工具运行记录"当证据，否则结果被拒收。
3. 接受结果时重新核对逐条评估、查"不确定"的冲突、查引用的资料是不是当前版本，任一不过
   就拒收。
4. 缺局限说明连续两次：这一步停下，整个任务以"证据不足"失败。
5. 结论按文档规则定级，知识带资料版本，过期的不再给执行者看。
6. 收尾时程序核对的结果可以否决审阅员的"通过"；"引用类"要求完全由程序判。
7. 发布前查资料是否过期，过期可以让任务失败。
8. 界面上的文档面板、逐条引用查看、资料的登记/更替/撤销入口。

真正没生效的只有：文档专用的提示词、文档审阅证明门、规划包里的领域说明、"判不下来占比"

## 六之二点七、真机重启验证发现并修掉的一个缺陷（SDK opt.127）

为验证"重启后等待缩到 30 秒"，在真机一局（`mission-baddf1eb2442858e`）里做了两次重启：

1. **正常退出再启动**（当时审阅员的调用在进行中）：重启 17 秒后系统判那次审阅"原调用结果
   不明"，不算次数，自动批准重做，任务继续。符合预期。
2. **强杀（kill -9）再启动**（执行者的调用在进行中）：**任务直接失败**，原因"运行环境不
   可用"。查事件：新进程接着跑被打断的那一轮，准入拒绝了它（这次尝试的执行权还记在旧
   进程名下），主循环把这种拒绝当成不可重试。这违背用户 2026-09-28 的决定（重启打断不扣
   次数、原地重做）。

修法（只动秩序这一层）：准入守卫给"执行权已不在这个进程手里"单独的原因码；分类表把它
算作被打断；主循环不判停，交给已有的"非模型原因原地重做"（不扣次数，同一步合计 6 次
上限）。别的准入拒绝不变。测试与"把修复拿掉"的检验见 ARCHITECTURE/AGENT_ORCHESTRATION.md
顶部一段。

修复后的真机复验（`mission-9e7c8141010c97f0`）：执行者调用进行中强杀，重启就绪后约一分钟，
系统判那次调用丢失、不算次数、自动批准重做，第二次尝试开始执行；这一局最后**完成并交付**
（3 个步骤全部验收通过，计划提交 2 次）。审阅员 7 轮回复全部可采用，没有格式被拒。

为什么脚本化场景没先抓到：Host 脚本化通道里原来的"重启"是让服务正常关闭。已补一条**强杀**
场景（子进程跑到执行者的模型调用里停住，父测试 SIGKILL 它，再在同一个库上起新服务）。
要如实记一笔：强杀打断一次调用有两种落点——调用已交给模型（结果不明，系统等够时限判
丢失）和调用还没交出去（新进程接着跑、被准入拒绝）。新场景走的是前一种；真机第一次碰到
的是后一种，由 SDK 的单元测试 `full_target/test_lease_lost_is_redone.py` 保护。

| 调用进行中重启 | 新服务接着同一个库做完；被打断的那次判为丢失、不算次数、原地重做，计划不重做 |

写这些场景时确认的产品事实：重启打断一次模型调用后，系统原来要等满 180 秒才判那次调用丢失并
重做（期间任务看起来不动）。用户决定缩短到 30 秒，已在 SDK opt.126 改（测试里调成 3 秒）。

同日又补了四条，现在共十条（全部通过，整文件约 3 分钟）：通用任务附资料；后端在模型调用
进行中被强杀后重启续跑（子进程 + SIGKILL）；同一个幂等键重复创建只算一个任务；两个任务
并排跑、各自完成。

还没写的两条：预算用完；两步结论矛盾时标成有争议（后者等第 3 步第 2 刀把行为定下来时
一起写）。

## 七、不做的

- 不迁移库里已有的平面任务：删完后遇到就按单个任务明确报错。
- 不为被删的功能留开关或隐藏入口。
- 存储表（改图台账、选择轮、冲突、片段验证）随对应功能一起删，不为读老库保留。
