## 三、问题

1. 产品里只能拆一层，拆不出中间目标。
2. "怎么拆"没有任何模型把关：程序发现没做法 → 跳过规划器 → 合成器现编 → 格式合规 → 程序直接采用。
3. 原计划要求的"新做法独立审阅"从没发生；唯一接了审阅的那条路从没被走过，且审阅结论没接到"能否采用"。
4. 同一件事两套做法（规划器提 / 合成器编）、三档选择开关、大量历史版本。

## 四、目标流程

```
目标需要做法
  └─ 程序算候选，只筛掉跑不了的（缺能力、前提不成立、写法有错）
       └─ 编排 Agent（规划器）看目标 + 候选 + 已知事实，回一个决定：
            ├─ 采用某个候选（REFINE）
            ├─ 自己提一个新做法（PROPOSE_METHOD）
            │     → 解码 + 注册检查（不变）
            │     → 独立审阅（METHOD_PLAN）
            │          ├─ 通过 → 下一轮可采用
            │          ├─ 打回 → 审阅意见回到规划器，重提
            │          └─ 判不下来 → 新会话复审一次 → 仍不行问用户（复用审阅升级那套）
            ├─ 先取证（REQUEST_EVIDENCE）
            └─ 问用户（REQUEST_HUMAN）
```

口径（窄）：**只在"为一个目标选定做法"这一刻必须由编排 Agent 判断**；推进过程中的其它唤醒规则（主计划 §3 的四类推进判定）不变。

**留并复用**
- 做法解码器、注册协议检查、给模型的"写做法所需上下文"（规划包里已有 `method_proposal_contexts`）。
- 适用性评估（作过滤器）。
- 选择身份账本（同一候选集不重复花一次调用）。

**新写 / 改写**
1. 规划器提示词（只留一份）：并入合成器积累的经验——做法字段形状与完整示例、拆分粒度、被拒后按拒绝理由只改点名处、根终审打回后新做法须有实质区别；新增子目标规则（什么时候用、什么时候不用、层数上限）。字段说明与示例只在需要提做法时随规划包给出。
2. 采用前必须有通过的审阅：保证通道下，采用一个"本任务试用"的做法须有它的 `METHOD_PLAN` 正式记录为通过（或人裁决通过）；打回 → 修复请求带审阅意见回规划器；判不下来 → 复审 → 问人。
3. Host 注册通用"子目标"类型（复合，参数为目标陈述）；规划包向规划器提供可用的子目标类型。
4. "提做法被拒再提"的上限：并入规划轮次上限，另设每个目标的重提次数上限，耗尽时如实停机并说明原因。
5. 测试：SDK 21 个、Host 2 个依赖合成器角色的测试文件改走规划器路径或随角色删除。
