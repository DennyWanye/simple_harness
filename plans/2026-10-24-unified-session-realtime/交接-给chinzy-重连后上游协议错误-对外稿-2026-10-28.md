## 4. 每条连接的客户端发送序列

截至错误帧，按同连接顺序，连续重复项合并计数。每条连接只发一次 `session.update`，且是冻结 schema 的完整 session。

| 场景 / conn | 客户端发送序列 |
|---|---|
| 跨通道查询 / 0 | `tokenseller.session.open` ×1 → `session.update` ×1 → `conversation.item.create` ×1 → `input_audio_buffer.append` ×10 |
| 打断分层 / 0 | `tokenseller.session.open` ×1 → `session.update` ×1 → `conversation.item.create` ×1 → `input_audio_buffer.append` ×10 |
| 打断分层 / 1 | `tokenseller.session.open` ×1 → `session.update` ×1 → `input_audio_buffer.append` ×25 → `conversation.item.create` ×1 → `input_audio_buffer.append` ×9 |
| 语音建任务 / 0 | `tokenseller.session.open` ×1（即收到 busy） |
| 语音建任务 / 1 | `tokenseller.session.open` ×1 → `session.update` ×1 → `input_audio_buffer.append` ×67 → `conversation.item.create` ×1 → `response.create` ×1 |
| 断线重连 / 2 | `tokenseller.session.open` ×1 → `session.update` ×1 → `conversation.item.create` ×1 → `input_audio_buffer.append` ×10 |
| 断线重连 / 3 | `tokenseller.session.open` ×1 → `session.update` ×1 → `input_audio_buffer.append` ×23 → `conversation.item.create` ×1 → `input_audio_buffer.append` ×8 |

`conversation.item.create` 的内容都是 `message / user / input_text`，用于把文字侧已有的结果回灌给语音。中继都返回了 `conversation.item.created`。
第 1、2、6、7 条在 `conversation.item.created` 之后，先收到上游的 `response.audio_transcript.done`、`response.audio.done`、`response.content_part.done`、`response.output_item.done`，然后收到控制错误。我们没有发 `response.create`，这些 response 事件不是我们请求的。

## 5. 我们已经排除的

- 没有重复 `session.update`。没有只含 instructions 的部分更新。
- 没有改写中继帧，没有填造身份字段，没有改提示词或工具说明。
- 同一天、同一路线、同样的回灌方式，另外两个场景（A08 文本注入播报、完整示例）全部到达 COMPLETED，实播 5360 / 8320 毫秒。失败的三个场景与它们的区别是：文字先建了任务再接语音、同号重绑、工具调用后续答。
- Service SDK 侧没有 `adapter_rejected`，不是客户端解码拒绝。
- 10-26 之后我们修了桥的一处本地缺陷：对 `retryable=false` 仍自动重连。修后反例通过。但这个修复只是让桥如实停下，没有消除上述六条错误。

## 6. 请求

1. 按第 3 节的 correlation 和 event_id，返回每条的上游原始错误（分类、原文）和中继判定它对应的客户端事件。
2. 区分两类：入站事件校验失败，还是上游主动拒绝。
3. 补 `related_event_id`，或给一个等价的关联号。七帧全缺，我们无法归因。
4. 说明是否把上游非致命错误映射成了 `fatal=true / retryable=false`。
5. 说明同一 session 短间隔内重连或重绑，中继或上游有没有限制（例如上一条连接未清理、同 session 并发上限、上游 session 残留）。第 3、6、7 条都是重绑后几秒内出现。
6. 说明工具调用后 `function_call_output` → `response.create` 的续答，上游有没有额外约束。第 5 条在这里出现。

## 7. 复现步骤

1. 用正常凭据铸造临时凭据，建 WebSocket，发 `tokenseller.session.open`，再发一次完整 `session.update`，等工具目录确认。
2. 发一条 `conversation.item.create`（`message / user / input_text`，内容是一段文字结果）。
3. 发 16 kHz PCM 录音，每帧 100 毫秒。
4. 变体 A（第 1、2 条）：在步骤 1 之前，先用文字路线建一个后台任务，再接语音。
5. 变体 B（第 3、6、7 条）：步骤 3 进行中主动关闭 socket，几秒内用同一 session 重新 open，重做步骤 1～3。
6. 变体 C（第 5 条）：步骤 3 触发工具调用，提交 `function_call_output`，发 `response.create`。

我们的驱动脚本和原始 `events.jsonl` 在本机保留。需要哪条连接的完整事件序列（含每个 append 的 event_id，不含音频），说一声就发。
