### 接线与边界

1. `DesktopSessionBridge` 仅调用已运行 Host 的 `open_session("desktop-main")`。一个主对话一个稳定会话号，继承 Host 已认证 principal/tenant，根目录仍是原 `data/agent-orchestrator`，任务页与主对话共用任务库。打开并发由桥的锁串行；委派、额度、恢复、inbox、ack 与持久事件仍由 SDK 负责，没有复制 SDK 生命周期或访问其私有成员。
2. `PrimaryChatView → SessionClient → /ws/control → control_session._cc_session → session.send` 为主界面文字链路。发送后台等待，控制连接可以继续处理中断；WebSocket 断开只拆展示，已提交发送由 SDK 收尾。同输入显式重试保留原键，结果未确认时阻止换文覆盖；不会自动重发。原 PrimaryController 的文字队列实现删除，仅保留工作区/运行检查器所用类型；旧 human_memory 的 queue.enqueue 在控制入口拒绝。chat/chat_v2 的入口也只转发到同一 Session，不启动第二套主对话引擎。
3. session_events 为每条控制连接订阅 `session.events(after)`，沿用原 WebSocket 广播函数发送 session_event；重连只传实际收到的会话 seq，关闭连接取消订阅，关服务先关会话再关 Host。事件信封和各 kind 的 payload 均显式白名单，不透传 SDK 内部 payload。SDK text_delta 的 text/generation 实际在顶层，投影后放入线上 payload；前端按 turn/generation 更换预览，以 turn_committed/history 为终稿。
4. 人工回答走 respond，人工 request_id 留在 payload，传输 request_id 留在信封，审批版本按十进制字符串过 JavaScript 再在后端转整数，避免 60 位版本精度丢失。终态任务及已非 PENDING 的历史提问不再显示待批卡。tasks/task/cancel_task、inbox/ack/history/budget 均消费公开 Session 方法；预算不披露本机聊天账本路径。
5. `ChatMissionCard` 读 Session 任务及白名单详情，查询/取消不走旧 mission_get/mission_cancel；`ChatMissionNotices` 读 Session inbox/result_ready，人点击才 ack，历史 result_ready 不会复活已收到卡片。任务页继续原 Host 的 mission_create[_with_sources]、读取与审批等接口，未迁入 Session。各视图刷新触发改用 session_event；任务页独立创建的任务由原 Host 读取加 15 秒列表刷新兜底，不重建后端 seq 泵。
6. 删除旧通知上下文注入、工具注册/名单、handlers、合同映射与前端旧协议处理。mission_notices、mission_notice_ack、mission_changed、MISSION_START_TOOL_NAME 在相关生产源中均已不存在。旧 mission-notices.json 或 state.db 中已有 foreground_turns 时明确报 legacy_session_data，不迁移、不删除旧开发数据。

### 根因与当前行为

**A：失败尝试等待重试决定时，尚未进入派发的 deferred 字典。** 原停滞判定只认该字典，漏掉共享执行池冷却中的修复请求；同时把只记录请求、尚未开出的规划回合算成“问过”。现在按实际派发路由（含角色、任务类型、升级和 fallback）读取当前池健康，沿任务事件中的 RuntimeProfileUnavailable 计算本段连续不可用的起点；只在池仍冷却且距起点不超过 profile_wait_seconds 时列为合法等待。重复冷却事件不重置同一段等待，已到期、无关池及过期 deferred 均不能挡住判停。

确认停滞时，对超过等待时限的池具名按 runtime_unavailable 停止，覆盖重试决定未提交、无法再进入 _defer_for_profile 的路径。停滞请求只有 PlanningServiceResumed 证明回合开出才占用“问过”次数；判 no_dispatchable_work 前还须读到该回合已接受的 PlanningDecisionEvaluated 或请求处理回执。已开出、决定未落下以及仍在排队的请求继续有界等待；时限用尽按 runtime_unavailable 停止。规划器确实回答 NO_CHANGE 后，原来的停滞判停仍生效。

### 阻断根因与修复

原起点算法只看相邻 RuntimeProfileUnavailable 的旧 until 是否重叠，遗漏 record_profile_success 已持久化的实际恢复。连续九段 60 秒冷却、前八段各在第 20 秒恢复再过 20 秒进入下一段时，实际新段刚开始，旧算法却累计为 320 秒，在默认 300 秒上限下误停整个 mission。另一条路径中，当前 mission 没有共享池事件，旧实现每次取 store.now，当查询时间从 100 推到 401 时起点也跟着移动。

现在共享池健康持久化 **unavailable_since**，首次冷却确定本段起点；同一段续冷却保留它，成功恢复同时清除 unavailable_until 和 unavailable_since，下一段从新时刻开始。RuntimeProfileUnavailable 同步携带该起点，留下可回放的分段依据。停滞判断读取共享健康中的本段起点，不依赖当前 mission 恰好有事件，也不依赖内存缓存；重开 Store 后继续使用同一持久事实。

旧格式健康状态尚无该字段时，以 recovered_at 过滤已恢复的旧段，结合**所有 mission** 的池事件还原连续段；没有池事件则使用既有 last_failure_at，避免用每次查询的当前时间续期。读取只投影兼容结果，不修改旧台账；下一次失败在原事务中持久化还原的起点（含尚未达到下一次熔断阈值的失败）。真正恢复、冷却自然结束后才重新开段，原有 profile_wait_seconds、规划次数和真实停滞停止规则保持。

### 实现与边界

- 流请求使用 `httpx.Timeout(connect=10, read=N, write=30, pool=30)`，N 为宿主原 read 值与 180 秒的较小值；未设置 read 的结构化配置也收敛到 180 秒。普通池、思考池因此都为 180 秒，调用方更短的配置继续生效。首个正文原始字节也受同一上限约束。三分钟兼顾思考首包等待与故障发现；持续输出推理片段或心跳会刷新空闲时间，长思考的总时长由回合剩余时限兜底。

- Agent 回合并发等待原 ReAct 任务与 per-turn 取消令牌，并按持久回合创建时间计算剩余时限。取消或剩余时限耗尽会取消正在运行的任务，穿过 provider 的 ProviderCancelledError 与 dispatch 的 provider_cancelled_after_handoff 路径。回合以 agent_turn_cancelled 或 react_wall_clock_exceeded 落为 failed，检查点恢复 ready、Agent 回到 IDLE；HTTP 流关闭。空闲超时也结束本地回合，以 provider_timeout 留痕。
