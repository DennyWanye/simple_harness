## 二、每条做了什么

### A01（C-01 / B-1）收尾最终事务重读纪元、证书到期、时钟

现状：收尾评估把 `epochs` 列为可忽略（`VOLATILE`），预览与定稿事务之间纪元动了照样定稿；不查证书到期；不查时钟回拨。

做法：

1. **纪元**：`AssuranceCloseoutConsumer.prepare` 保留完整预览（`basis`），定稿事务里重评后调 `require_final_consistency(basis, evaluation)`：评估为 READY 时，任务纪元 / 环境纪元 / 时钟代次三元组必须等于依据读取时的，`as_of_ms` 不能早于读取时刻，时钟须 STABLE；任一不成立抛 `RECHECK_REQUIRED`（现成码），轮询按现有重算路径退回、下一轮再评。没到 READY 的评估只是投影，不比（任务进行中纪元本来就一直在动）。
2. **证书到期**：`assurance_recheck.stale_certificates` 多收 `now_ms`，按 `certificate_expired(row, now_ms)` 判到期，记成 `{"channel": "VALIDITY", "reason": "EXPIRED"}` 一项，走原有 `EVIDENCE_STALE` → 规划器修复请求 → `PlanningRepairAddressed` 这条路，不新造停机原因。到期判定抽成一个函数，有效性观察者（`_observe_locked`）、Host 诊断（`api/assurance.py::_certificate_use`）、收尾三处共用，不留第二套。
3. **时钟**：`storage/assurance_reads.py` 新增 `clock_discontinuous(epochs, now_ms)`（环境时钟不 STABLE，或现在早于高水位），`require_epochs_locked`（证书最终锁）与收尾评估共用；收尾评估不成立记 `TIME_DISCONTINUITY`（现成码）→ NOT_READY。

关于"未被吊销"：已签使用证书没有独立的吊销表；同一消费方身份更新的证书顶掉旧的，`live_usable_certificates` 只取最新一张，所以被顶掉的证书从来不是收尾依据。记录下来，不另造机制。

改的文件：`orchestrator/assurance_consumers.py`、`orchestrator/assurance_recheck.py`、`storage/assurance_reads.py`、`api/assurance.py`（只换判定函数）。

### A04（C-04）诊断接口只读

现状：`AssuranceApi.use_check` 走 `prepare_accept_use_for_result` / `prepare_root_use`——两者末尾 `_remember` 把候选写进共用缓存（顶掉同一条记录的真实候选），`finally` 再 `forget` 清掉。

做法：`AssuranceValidity._prepare_use` 加 `remember` 开关；新增纯算入口 `diagnose_accept_use_for_result` / `diagnose_root_use`（同一套计算，不记缓存、不动锁表）；`use_check` 改用它们，删掉 `forget`。真实路径不变。

改的文件：`orchestrator/assurance_validity.py`、`api/assurance.py`。

### A06（C-06）读错时终态通知照发

现状：`is_assured` 把一切 `AssuranceError` 都当"不是保证通道"返回 False，终态写入的通知请求被静默吞掉。

做法（选"照发并如实写明"）：新增 `assurance_lane_status(store, mission_id)` → `ASSURED` / `NOT_ASSURED`（没有建任务合同 `CREATION_CONTRACT_UNRESOLVED`，或合同不是保证通道）/ `READ_FAILED`（合同在、绑定读不回来等）。`request_assured_notification`：`NOT_ASSURED` 不发；`READ_FAILED` 照发，通知请求事件里加 `note: "保证状态读取失败：<码>"`。NOTIFY 消费者字段表允许 `note`；送往 Host 的仍只有 `{mission_id, event_id, state_version}`（原计划 §7.3 不夹正文）。`is_assured` 仍只对 `ASSURED` 为真，其它读者（定稿写入、主循环）行为不变。

改的文件：`orchestrator/assurance_final_writer.py`、`orchestrator/assurance_consumers.py`（`AssuranceNotifyConsumer._body`）。

### A07（C-07）收尾查尾部预留与范围外结果不明动作

读法核实（调用链）：

- 审阅员预留：`budget_reservations`（`governance/budgets.py::BudgetLedger.reserve`，state RESERVED/SETTLED）；首个审阅员尾部预留在 `budget_tail_holds`（`governance/tail_budget.py::TailBudgetLedger.hold_tail`，hold_id `first-critic:<attempt>`，purpose `critic`，state HELD/RELEASED），它的预留主体是 `tail:<hold_id>` 这一行；`release_tail` 先 `ledger.settle` 再把 hold 置 RELEASED；`protected_tail_commits.release_terminal_tail_holds` 在尝试 / 任务 / 任务终态时释放。此前收尾只查 `budget_reservations.state='RESERVED'`，不看 hold 表——两表一致时能带上，不一致（hold 仍 HELD、预留行已 SETTLED）就漏。
- 已交出动作：`actions` 表（`store.list_actions(mission_id, *states)`），状态 `HANDED_OFF`（交出未结）/ `UNKNOWN`（结果不明）；`completion_status.read_current_effect` 只把**根范围必需效果**对应动作的 UNKNOWN 翻成 `RECONCILIATION_REQUIRED`，范围外的动作收尾看不到。

做法：收尾评估新增 `_open_accounting`——`budget_reservations` RESERVED 的主体 ∪ `budget_tail_holds` HELD 的主体（以 hold 本身为准），进 `accounting_pending_refs`（`reservation_fact` 引用）并参与 DRAINING（`OPEN_RESERVATIONS`）与上限结清判定；`store.list_actions(mission, "UNKNOWN")` 全部进 `dangerous_work_refs` 与 `unsettled_operation_refs`（`operation` 引用，按动作键 + 版本钉住），有则 `BLOCKED_UNKNOWN`（现成原因 `EFFECT_UNKNOWN`）；`HANDED_OFF` 的只记进 `unsettled_operation_refs`，不改状态（它的预留本来就在 RESERVED 里拦着；不新造停机原因）。

改的文件：`orchestrator/assurance_consumers.py`。

### A17（C-17）收尾记录按 closeout-v1 写、钉要求版本

原计划资产：`plans/Assurance/specs/1.1/contracts/closeout-v1.schema.json`、`implementation/field-producers.json`（closeout 字段的生产者 = 定稿写入）。

做法：收尾评估正文与定稿记录按 closeout-v1 字段写——`schema_version`、`mission_id`、`root_resolution_ref`（`resolution` 引用：id + 正文指纹）、`requirements_ref`（与改要求同款 `requirements_amendment.requirements_ref`：id + revision + content_hash，钉住根结论形成时的要求版本）、`completion_spec_hash`（根范围的要求规格哈希）、`state`、`pending_effect_keys`（原 `unknown_effects`）、`unsettled_operation_refs`、`accounting_pending_refs`（原 `open_reservations`）、`dangerous_work_refs`、`report_ref`、`as_of_ms`（原 `evaluated_at_ms`）、`reasons`。删掉裸 id：`resolution_id`、`unknown_effects`、`open_reservations`、`evaluated_at_ms`（收尾行的 `resolution_id` **列**保留，由引用派生）。收尾事件 `AssuranceCloseoutEvaluated` 的 `resolution_id` 也换成 `root_resolution_ref`。

定稿（`finalize_assured_mission`）：定稿回执正文 = closeout-v1 文档（state FINALIZED，它自己就是收尾记录，`report_ref` 为空）+ 判定 / 版本字段；收尾行 FINALIZED 的正文与任务最终报告 `final_report["assurance_closeout"]` 是同一份文档，`report_ref` 指向这张回执（`commit_receipt` 引用）。为了算回执指纹，先按 `mission.version + 1` 定 `state_version`，再写任务、发完成事件、插回执（原来回执里的 `final_event_id` / `final_event_type` 改到 `AssuranceMissionFinalized` 事件负载里，接缝脚本读的就是事件）。

不写 `read_set`：收尾没有自己的读集，它依赖的证书各自带读集；记为与 schema 的已知差异（见第四节）。

读方：`api/assurance.py` 快照只读 `reasons` / `root_incarnation_id` / `epochs`（未变）；`assurance_recheck.closeout_stale_findings` 读 `reasons` / `stale_certificates`（未变）；诊断导出整行导出（未变）；Host `backend/scripts/assurance_model_scenarios/run.py` 只读 `state`（未变）；接缝脚本 `scripts/assurance_seams/final-writer-seam.py` 改读 `report_ref`。Host 投影里没有别的收尾字段读者（已 grep backend 与 tauri-app/src）。

改的文件：`orchestrator/assurance_consumers.py`、`orchestrator/assurance_final_writer.py`、`scripts/assurance_seams/final-writer-seam.py`。

## 五、偏差与裁决

1. closeout-v1 schema 要求 `read_set`（minItems 1），本次不写：收尾没有自己的读集，依赖的证书各自带读集。另外评估正文除 13 个 closeout-v1 字段外还带内部核对字段（`mission_version`、`epochs`、`root_incarnation_id`、`stale_certificates`、`open_intents`、`success_judgment` 等），定稿事务与快照读者要比它们。所以正文是"closeout-v1 字段齐全 + 内部字段"，不是对 schema 的严格校验。留给主会话：要不要在 schema 侧放宽，或把内部字段挪进回执。
2. `report_ref` 原计划没写明指向什么；本次定为指向定稿回执（`commit_receipt`），回执自身 `report_ref` 为空。
3. `HANDED_OFF`（交出未结）的动作只记进 `unsettled_operation_refs`，不单独改收尾状态——没有现成的停机原因，且它的预留本来就让收尾 DRAINING。要不要给它单独原因，留给主会话。
4. 没有新增错误码或停机原因；`error_table.py` 未动。未动车道 A 的三个文件。
5. 过程失误：一次跑既有测试时 zsh 把 `--include=*.py` 当通配符，文件列表为空，pytest 跑起了整个 `tests/`；发现后 10 分钟内停掉并清进程。停进程用的 `pkill -f "pytest -q -p no:cacheprovider"`，可能殃及同机另一会话（主检出 `simple_harness/sdk`）正在跑的变异用例进程（`mutation-as90_aix`），请主会话核对那边是否要重跑。
