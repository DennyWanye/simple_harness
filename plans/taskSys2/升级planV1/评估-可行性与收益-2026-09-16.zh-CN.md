## 3. 实质缺陷（按严重程度）

1. **W1 自相矛盾，无法按自身门槛验收。** `code-changes.json` 中 W1 的 8 条落点全部 `proposed_new`，没有任何 `modify_existing`；但 §17 要求 W1"执行选定叶子"，§20 要求"真正使用这些合同的 Commit 和 BaseAgent 执行链"。执行桥接必须改 `commit_service.py`（不在 JSON 中）与 `event_handler.py`（JSON 划给 W2）。AT-001～AT-005 在 W1 范围内不可能 PASS。
2. **并发原语要换，不是叠加。** 现状 CAS 只有整数 `base_graph_version`（commit_service.py:1284）；§15.3 要求多键结构化 read-set。这是替换核心并发语义，风险集中在此，计划把它写成"拟新增 mixin"低估了侵入。
3. **验证晚于被验证物。** §5.5 把 HDDL/PANDA 交叉核验放在 W1，对应需求 FULL-59 却在 W7。
4. **§14 表与 code-changes.json 不一致。** §14 有 9 个 [现有] 文件不在 JSON（commit_service、task_graph、planner、manager、candidate_selection、fragments、claims、composer、facade）；JSON 另有 3 个不在 §14。§19 要求的工作单溯源无法依赖这张表。另 `planning/planner.py` 只有 49 行两个 parse 函数，不是 HTN 接入点。
5. **84 条验收场景是模板。** `evidence_required` 全 84 条只有 2 种取值，`then` 第二句只有 2 种取值，全部铺在一个扁平目录。
6. **串行依赖过度约束。** W6 的 commitments/timers 是新目录，只与 schema 共享，可用假时钟独立测；W5 的参考适配落在已存在的 handler 上。W7 的对照测量按计划第 1020 行要求"W1 开始就加入"，却被 depends_on 排到 W6 之后。
7. **没有收益假设，也没有退出规则。** §18.1 第 4 层只说"跑对照、不得编造收益"，全文没有预期效应量、门槛或放弃条件；§18.4 明言"没有增益也不能从完整设计删除"。对照结果因此不影响投入决策，计划不可证伪。
8. **"Host 不可访问"已过时。** 本机 Host 可读，54 个 py 文件 import agent_orchestrator，UI 在 tauri-app/src。W4/W6/W16 的工作量应重估，不是缺口。

## 4. 优化效果评估

**能带来什么（确定的）**：方法切换、最小影响修复、真值维护、组合验收、长期承诺、完整业务重建。这些是正确性、可解释性与鲁棒性收益，是产品能力，不是任务成功率。

**不能承诺什么（当前证据）**：
- 现有动态 DAG 层（D/F 臂）尚未证明优于单 Agent（S/R 臂）。A96 v1：S 3/3、R 4/4、F 1/1、D 0/1（D 失败原因是输出预留 4096 不够，与规划质量无关）；Flash v1 19/96、Qwen 16/96；D/F 知识复用事件为 0。
- 在这个基础上再叠一层 HTN，先验收益证据为零。
- 更便宜的归因路径已经建好：`runtime/assembly.py` 的 `ablations` 已支持 graph_changes / blackboard / critic 三个开关；gap-review §3.3/§3.4 与 roadmap N7 给出的归因预算是 4～8 小时。
