## 1. 共同背景（4 局共享的机制事实）

1. **根目标签名未改**：Host 仍把 C1/C2 建成 `code.fix-failing-test`，`failing_test` 指向绿色可见套件（C1=`tests/test_public_collector.py` 4 绿，C2=`tests/test_public_pipeline.py` 6 绿）。真正的验收在 `hidden/`。`code.test-is-failing` 观察 polarity=**false**；谓词 `world_assumption=OPEN`，非权威否定读作 UNKNOWN → 三条种子方法（`fix-by-patch` / `fix-by-revert` / `fix-by-assessed-revert`，均为 `@2`）一律 `NEEDS_EVIDENCE`。这是题目构造 + 方法库前置，不是 applicability 实现回退（Q3b）。
2. **开局规划形态（4 局同形）**：`MethodApplicabilityAssessed` refusal_count=3、`applicable_methods=[]` → Planner 第 1 轮 `no_applicable_method` 或 `proposal_not_grounded`（有人仍点名 `code.fix-by-patch`）→ 合成轮 `MethodSynthesisRoundRecorded{TRIAL_ADMITTED}`（`method-synthesizer-v6`，asks=1）→ Planner 第 3 轮 `refine` 采纳合成方法 → `PlanRevisionCommitted` revision 1，6 叶。P2.3g/i/n 这条路通了。
3. **提示词版本**：planner `planner-hierarchical-v6`，synthesizer `method-synthesizer-v6`，root-reviewer `root-reviewer-v3`。叶验收的 TASK_CONTENT 评审全部是机械层（`critic_review=NOT_REQUIRED`），**没有独立的准则评估模型调用**；唯一的评审模型调用是根 `MISSION_FINAL`。
4. **修复轮现在会换方法**（P2.3j + P2.3n 活证据）：根评审 REJECT 或 P2.3m `read_only_leaf_needs_write` 之后，Planner 先写一轮 `no_applicable_method`（种子仍 NEEDS_EVIDENCE、被拒方法不可复用），然后**新的合成轮**准入一条不同 method_id，下一 Planner 轮 `retire_method` + `refine` 提交新 revision。4 局无一例外走到这一步。被拒方法进 `rejected_method_refs` 是 P2.3j 核验 P1-1 的故意设计（防振荡），不是「过严到修不了」——修得了，只是贵。
5. **N1 本批未再作为主因**：C1-r0 / C2-r0 / C2-r1 三次根评审 `c-change-explained=PASS`（P2.3k 的 inspect/summarize@2 + P2.3o 预铺）。C1-r1 根本没走到根评审。
6. **N3 未复发**：0 次 `artifact_conflict` / `ArtifactMergeNotApplicableUnderHierarchical`。
7. **交付规则已改**（Host H1）：`delivery.source=accepted_outputs_then_last_changed_accepted_leaf`，official 不再随最大 ordinal 的只读快照抖动。C2 两局 official=True 与 hidden PASS 对齐，不再是第 2 批那种伪阴性。
8. **三道天花板同时在场**：实验调用 80（MeteredProvider / `ExperimentBudgetExhausted`）、墙钟 1800 s（`_runtime_exhausted`）、attempt 12（`MissionSpec.budget.max_attempts`）。token 4M 从未成为约束（14–17%）。

## 4. 新缺陷清单（按优先级）

第 2 批 N1–N7 / P2.3i–p 本批均未作为主因复发。下列为第 4 批新项。

### N8 · P1 · Host runner · 局级 `calls` 接到每回合 `max_model_calls_per_turn`

- 现象：单叶 Worker 可连续调用直到实验 80 次用尽。本批单叶最高 C1-r1 reproduce 16 次、C2-r0 verify 11 次、多叶 9 次。一个 verify 重试就能吃掉修复轮预算。
- 定位：`runner/run_h_arm.py:441` `max_model_calls_per_turn=budget.calls`，同时 `common.py:264` 把同一 `calls` 写入 `ExperimentBudget`。两个不同粒度共用一个数字。
- 复现：任意 H 臂 L3 局，观察 `provider_token_grants` 按 `subject_id` 分组，必有 ≥1 叶 ≥9 次。
- 修法：局级 calls 只进 `ExperimentBudget`；`max_model_calls_per_turn` 单设 8–12（A96 单回合量级）。这会改变每叶调用分布，FREEZE-candidate 需重生成。属 runner，非 SDK。

### N10 · P1 · SDK 修复轮 + Host `max_attempts=12` · 整网重铺把 attempt/调用乘以方法轮数

- 现象：每次 retire+refine 物化一整棵新叶子（C2-r0 rev2 **funded_now=10**），已验收的 facts/reproduce 不 `share_active`。C2-r1 两轮 6 叶 + verify 重试 = 12 attempt，revision 3 零派发，`dimension=attempts`。
- 定位：
  - SDK：`compile_proposal` 的 retire+refine 走 membership 替换（P2.3j，TG §9.3），没有「保留已验收只读槽」的默认策略；code 域种子里 `share_active` 只出现在 `fix-by-assessed-revert`。
  - Host：`run_h_arm.py:479` `max_attempts=12` 是 A96 遗留，6 叶方法 × 2 轮已经顶格。
- 复现：绿基线 C 题，根评审 REJECT 一次后观察第二 revision 的 `funded_now` 与 `attempts_created`。
- 修法（可并行）：
  a. 修复轮默认把 facts/reproduce 标 `share_active`（或按 task type 白名单复用已验收只读叶）；
  b. Host 把 `max_attempts` 放到 24（与 L2 160 calls 配套：两轮 6 叶 + 重试 + 一轮 10 叶仍够）；
  c. 合成器硬上限方法宽度（本批出现 10 叶方法）。
- 优先级 P1：不修的话把 calls/seconds 放到 L2 值，C2-r1 这种「实现已经对」的局仍会死在 attempt。

### N9 · P2 · SDK `_runtime_exhausted` + runner 口径 · 墙钟不停 UNKNOWN grant

- 现象：C1-r0 `budget_conserved=false`，`unknown_usage_calls=1`，账本 remaining 3,256,685 + **reserved 100,000** + settled 643,315 = 4,000,000。UNKNOWN grant 仍在（verify attempt-2，`actual_tokens=0`，`total_upper=37171`）。
- 定位：见 Q2。不是 P2.3l N5 / P2.3p 复发——那两条只覆盖「连续 after-handoff 0-token UNKNOWN → `runtime_unavailable`」。墙钟路径 `_runtime_exhausted`（`event_handler.py:7292-7314`）注释写明「what was spent and reserved stays on the books」，只 `fail_mission(BUDGET_EXHAUSTED)` + `_release_mission`，**不**调 `_release_mission_unknown_grants`。
- 修法：墙钟 / admission-denied 终态与 P2.3p 同样 `release_held_grants` + `settle_subject_known`；runner `_budget_conserved` 对「未知用量已留账且等式成立」不要仅因 `unknown_usage_calls!=0` 判 false（或把该字段改名为 `usage_fully_known`）。P2：守恒等式本身成立，只是口径把「有未知」等价于「不守恒」。

### N11 · P2 · SDK P2.3p 诊断字段 · `error_class` 落到包装类

- 现象：C1-r0 唯一 UNKNOWN invocation 的 `usage_json` = `{"budget":{"kind":"unknown",…},"error_class":"UnknownProviderUsage"}`，**无 `http_status`**。
- 定位：`execution/dispatch.py:671-676` `_handoff_unknown_diagnostics(exc)` 拿到的是 `MeteredProvider` 在 `metered_provider.py:382` 抛出的 `UnknownProviderUsage("physical call failed; usage unknown") from error`，不是 `error.__cause__`。`UnknownProviderUsage` 没有 `status_code`。
- 修法：diagnostics 沿 `__cause__` / `__context__` 取底层异常短类名与 `status_code`；包装类可另记 `wrapper_class`。不写响应体。

### N12 · P2 · 模型措辞 / 包字段 · 只读取消被说成 `rejected_by_root_review`

- 现象：C1-r1 seq 219 Planner rationale「`rejected_by_root_review` blocks reuse」，本局 0 次根评审，系统事件是 `read_only_leaf_needs_write`。
- 影响：诊断读者会误判「P2.3j 根评审封禁」；本局合成与换方法仍发生，不阻塞。
- 修法：修复轮包把 `rejected_by_root_review` 与 `rejected_by_read_only_leaf` 分开；planner-v6 各写一句。可并进下一则提示词片。

### 编排侧可省的调用（Q1 点名的「明显多余」，单列）

这些不是新的停机缺陷，但直接放大 N8/N10：

1. **开局两轮注定失败的 Planner**（每局 2 次、约 15–20k token）：证据饱和后种子全 NEEDS_EVIDENCE，第 1/2 轮 `no_applicable_method` / `proposal_not_grounded` 是 D2b 现状。可在 `goals_needing_method` 已饱和且 `applicable_methods=[]` 时跳过 Planner、直接开合成（P1，SDK `hierarchical_dispatch`）。

### 7.2 外推：若无 80 上限，跑到 COMPLETED 要多少

算法（写明，便于打）：

```
avg_leaf = 已完成叶调用均值（本批 6.4）
svc     = 本局已发生的 planner+synth+root
remain  = 当前 ADOPTED 方法尚未验收的叶子
repair  = 若还需要 1 次根评审拒绝后的换方法：
          新方法叶数（本批 6 或 10）× avg_leaf
          + 1 次合成 + 1 次 planner + 1 次根评审
          − 可 share 的只读叶（当前实现 = 0）
calls_hat = 已用 calls + remain×avg_leaf + (需要第二次评审 ? 1 : 0) + repair
tokens_hat = calls_hat × (本局 tokens/calls)          # 本批 7.0–8.4k / 次
seconds_hat = calls_hat × (本局 seconds/calls)        # 本批 17.6–22.5 s / 次
```

代入：

| 局 | 已用 | 当时还差什么 | calls_hat | tokens_hat | seconds_hat |
|---|---|---|---|---|---|
| C1-r0 | 80 | rev2 还剩 verify 收尾 + inspect + summarize + 根评审；若再拒则第三轮 | 80 + 3×6.4 + 1 ≈ **100**；悲观再 +1 轮 6 叶 ≈ **140** | 0.83–1.2M | 2200–3200 s |
| C1-r1 | 80 | rev2 verify 起的 3 叶 + 根评审；大概率再拒一次（C 类） | 80 + 3×7.5 + 1 + 6×7.5 + 3 ≈ **130** | 1.1M | 2600 s |

取「典型 C 类绿基线、1 次根评审拒绝、1 次换方法、第二次评审通过」：**约 110–130 次调用、0.8–1.2M token、2000–3000 s**。乐观（第一次评审就过，本批未发生）：6×6.4 + 8 开销 ≈ **50 次 / 0.4M / 1100 s**。悲观（两次拒绝 + 10 叶方法 + 只读改写满额）：**150–160 次 / 1.3M / 3600 s**。

## 8. Q2 硬不变量：C1-r0 `budget_conserved=False` 是谁的口径

**两层都有贡献，主因是 runner 口径；SDK 墙钟路径按自己的注释故意不释放 UNKNOWN grant。不是 P2.3l N5 / P2.3p 的回归。**

1. **Runner 判决**（直接让字段变 false）  
   `runner/run_h_arm.py:1079-1088` `_budget_conserved`：
   - `known_usage.total_tokens` 必须存在且 ≤ 局级上限；
   - **`unknown_usage_calls != 0` → 直接 False**；
   - 否则 `_account_conserved`：`remaining + reserved + settled == max_tokens`。  
   C1-r0 第三条成立（4,000,000），第二条失败。C1-r1/C2-r0 有 reserved=100k 但 `unknown_usage_calls=0`，故 true。

2. **SDK 墙钟路径不释放 UNKNOWN grant**（让 reserved 停在 100k、grant 停在 UNKNOWN）  
   `event_handler.py:7292-7314` `_runtime_exhausted`：超过 `max_runtime_seconds` 则 `fail_mission(BUDGET_EXHAUSTED, detail.dimension=runtime)` + `_release_mission`。注释原文：「what was spent and reserved stays on the books。」**不**调用 `_release_mission_unknown_grants`（1279 / 1283 / 7161，那是 P2.3l/p 给 `runtime_unavailable` 用的）。  
   末笔 grant：`provider_token_grants.state=UNKNOWN`，subject=`task-38bc…:attempt-2`，`handoff_ordinal=1`，`actual_tokens=0`。ORCH §12.2 / `_settle_if_known`：有未知用量就 `ReservationHeld`，attempt 预留 100k 不结算。known_usage 659,352 − settled 643,315 = 16,037，正好是该 attempt 上 3 笔已 SETTLED 的调用——它们进了 meter，没进 mission settled，因为 attempt 被 UNKNOWN 钉住。

3. **对照 P2.3l N5、P2.3p**  
   - N5：UNKNOWN grant 卡住**后续规划** `authority_rejected`。本局规划早已结束，卡的是 Worker attempt-2，后续没有新 Planner。未复发。  
   - P2.3p：同一 Mission **连续 N=2** 次交接后 0-token UNKNOWN 才 `runtime_unavailable` 并释放预留。本局 `handoff_attempt=1`、`rehandoff_count=0`、streak=1 < 2，P2.3f 的 300 s 重交接还没到，墙钟先到。P2.3p **正确地没有开火**。  
   C1-r1 / C2-r0 的 UNKNOWN grant 是 `provider_admission_denied`（未交接），meter 不计 unknown，runner 判 conserved=true——同一 SDK 账本形状，不同 meter 计数。

结论：把 C1-r0 记成「§21.5 账本破裂」不准确；等式在含 reserved 时成立。`budget_conserved=false` = runner 把「有未知用量」定义为不守恒 + SDK 墙钟选择留账。若验收硬不变量要「终态无 HELD UNKNOWN」，那是 N9，不是 N5 复发。

## 9. Q3 规划死路

指挥者看到的 `no_applicable_method` / `NEEDS_EVIDENCE` 都真实存在，但**不是终态**：后面都有合成准入 + 新 revision。4 局合成轮次数：C1-r0 2（含 P2.3i 重问）、C1-r1 2、C2-r0 2、C2-r1 3。`MAX_SYNTHESIS_ASKS=2` 是**同一 round 的重问上限**，不是全局合成次数；P2.3j 在根评审拒绝后另开 `synthesis_round = plan_revision+1`。

**(a) `rejected_by_root_review` 永久封禁是否过严？P2.3j 为何没介入？**

- 封禁的是**方法名**跨 revision 不可再 adopt（P2.3j 核验 P1-1，防 StoreConflict / 振荡）。这要求修复轮必须换一条方法，不能「同一方法再跑一遍带反馈」。
- **P2.3j 介入了**：C1-r0 / C2-r0 / C2-r1 都在根评审（或 P2.3m 升级）之后合成了**不同** method_id 并 `retire+refine`。C1-r1 没有根评审，是 `read_only_leaf_needs_write` 走同一修复通道，同样换了方法。
- 「没介入」的观感来自 Planner 在合成前先写一轮 `no_applicable_method`（包里种子仍 NEEDS_EVIDENCE、被拒方法已排除，当时还没有新 APPLICABLE）。这是多余的一轮（§4 可省调用 #2），不是死路。
- 过严吗？**对「同一方法带反馈再跑」过严，对「换方法」不过严**。C 类绿基线题换方法的价值已经在 C2-r0 rev2 上证明（red-green 报告写出了 v3 要的证据）。建议保持封禁，但饱和后跳过空 Planner 直接合成（P1）。

**(b) `code.test-is-failing=false` 让 fix-by-patch 永 NEEDS_EVIDENCE：方法库还是 applicability？为何不合成？**

- **方法库前置设计**，applicability 实现符合规格：OPEN 谓词非权威否定 → UNKNOWN → `NEEDS_EVIDENCE`；三条种子的 `applicable_when` 都要求 test-is-failing 或 regression-commit-known 为 TRUE。`construction.json` 自己写了这个后果，并依赖 D2b 合成轮接管。
- 合成**有触发**，开局 4/4、修复轮 4/4。不是 MAX_SYNTHESIS_ASKS 挡住。
- 真正的结构问题：C 类题面是「实现不可见契约」，种子库没有 `code.implement-contract`。合成方法仍挂 `c-test-passes`（措辞来自 fix-failing-test 模板），v3 评审员按 mission_goal 要「覆盖用户目标的测试红转绿或新增通过」。Worker 有时加测试（C2-r0 rev2）有时明确不加（C2-r1 rev2），于是第一次根评审几乎必然 REJECT → 必须再烧一整轮方法。这是第 2 批 N2 的 **Host 半边未做**（D2a 仍用 `fix-failing-test` + 绿 `failing_test`），不是 P2.3k SDK 半边回退。

修法建议与优先级：

1. **P1 Host**：C1/C2/C4 换目标签名 `code.implement-contract`（或等价），准则 `c-contract-tests-pass` / `c-change-explained`，不要绑绿色 `failing_test`。题目夹具不动。与第 2 批 N2 建议相同，本批实证「v3 评审员已经在按这个精神判，但方法还在旧签名上」。
2. **P1 SDK**：证据饱和且 `applicable_methods=[]` 时跳过空 Planner、直接合成；修复轮同样。
3. **P2 方法库**：给绿基线实现题一条种子方法（前置只要 `code.repo-checked-out`），避免每局必合成；`c-test-passes` 的 evidence_requirement 改成「覆盖 mission_goal 的测试新增并通过」，与 v3 对齐。
4. 不要放宽 I18 / 不要把 OPEN 谓词的 false 观察改读 FALSE——那会让 `fix-by-patch` 在「可见测试全绿」时变成 APPLICABLE，语义是假的。

## 10. Q4 provider 停摆

**与第 3 批 C2×2 是同一 error_code 家族，不是同一局面。P2.3p 的诊断字段有值，但落到了包装类。**

| | 第 3 批 C2×2（P2.3p 动机） | 本批 C1-r0 末笔 |
|---|---|---|
| 阶段 | planner:1 + synthesizer 成功后，后续 **planner 全灭** | 修复轮 **Worker verify attempt-2**，规划早已结束 |
| 次数 | 连续多次 0-token UNKNOWN，P2.3f 300 s 重交接 → 新 ordinal，直到墙钟 | **1 次**，`handoff_attempt=1`，`rehandoff_count=0`，300 s 未到墙钟先到 |
| 停机 | PLANNING / `stop_reason=null` 或空转 | ACTIVE / `budget_exhausted` dimension=runtime |
| error_code | `provider_error_after_handoff` | **相同** `provider_error_after_handoff` |
| 用量 | 0 token，`usage_json.kind=unknown` | 相同 |

C1-r0 invocation `e0448990…`：

- `state=unknown`
- `error_code=provider_error_after_handoff`
- `usage_json={"budget":{"amount_micros":null,"estimator_snapshot_id":null,"kind":"unknown"},"error_class":"UnknownProviderUsage"}`
- **`http_status`：无**
- `response_json=null`
- `handed_off_at` → `settled_at` ≈ 5.3 s（不是 300 s 超时，是交接后很快未知）

`error_class=UnknownProviderUsage` 来自 `MeteredProvider` 在物理调用失败且无 usage 时抛出的包装异常（`metered_provider.py:382`，并 `unknown_usage_calls += 1`）。P2.3p 的 `_handoff_unknown_diagnostics` 记录的是这个包装类，没有沿 `__cause__` 取底层 HTTP/传输异常，故无状态码（N11）。

其余三局：C1-r1 / C2-r0 各 1 条 `provider_admission_denied`（调用预算耗尽，**未**交接，不是 after-handoff）；C2-r1 78 笔全部 `succeeded`。没有第 3 批那种「规划期连续 UNKNOWN」。P2.3p 的 N=2 有界停机本批没有机会开火，也没有该开火却没开的漏。
