## 二、每条做了什么

### A05（C-05）预算等待与"需重算"分开

现状：轮询 `assurance_tick.py` 的 `except (AssuranceError, BudgetError, …)` 把 `BudgetError` 也送进 `work.recheck(reason="BUDGET_UNAVAILABLE")`，与 RECHECK_REQUIRED 共用 32 次 / 300 秒的累计上限；长时间预算等待被打成 MANUAL_REQUIRED，要新事件才重开。

做法：

1. `storage/assurance_work.py` 新增 `BUDGET_WAIT`、`BUDGET_WAIT_MAX_MS = 60_000`、`budget_wait_delay_ms(tries)`（2 秒起翻倍，封顶 60 秒）；`recheck` 拒收 `BUDGET_WAIT`（`WORK_RECHECK_REASON_INVALID`），预算等待永远不计入重算次数。
2. `assurance_tick.py` 把"准备失败后放回去"的决定抽成 `AssuranceTick._settle_failure(claim, error)`：`BudgetError` → `work.wait(reason=BUDGET_WAIT, not_before=now+退避)`，不碰 `rechecks`；`TimeoutError` → `recheck("RECHECK_REQUIRED")`；`AssuranceError` → `recheck(error.code)`；本任务数据读不回来 → `recheck("MISSION_DATA_UNREADABLE")`。两个 `except` 都只调它。消费者自己返回的 `AssuranceWait("BUDGET_WAIT", …)` 本来就走 `wait`，没变。

**关于"各自上限"的裁决**（见第五节第 1 条）：预算等待的上限是退避上限（60 秒），不是次数上限、不转 MANUAL_REQUIRED——预算是外界条件（结算、用户加预算都是新事件，会把目标升上来重开），"等久了就要人工"正是本条要修的缺陷。重算的 32 次 / 300 秒上限只管重算。

改的文件：`storage/assurance_work.py`、`orchestrator/assurance_tick.py`；既有 `test_unreadable_mission_is_isolated.py` 里查源码字符串的那条改为查 `_settle_failure`。

### A20（C-20 前半）通知待办与完成事件同事务建

现状：终态写入只发 `AssuranceStatusNotificationRequested` 事件；NOTIFY 待办要等下一轮轮询的游标摄取才入箱。

做法：`assurance_final_writer.py` 新增 `notification_body(event)` 与 `notification_work_target(event)`（待办键 + 指纹），`request_assured_notification` 发完事件后在**同一事务**里 `AssuranceWorkStore.seed(mission, "NOTIFY", event, (target,))`；`AssuranceNotifyConsumer.classify` 改用同一个 `notification_work_target`，所以之后游标摄取到同一事件时按同目标（同 seq、同指纹）合并，不冲突、不重建——事件重放一致。定稿写入（`finalize_assured_mission`）、取消 / 失败 / 超时的终态写入、停机后动作了结通知都经这一个函数，都受益。

边界：保证状态读取失败（A06 的 `READ_FAILED`，绑定行读不到）时只发事件不建待办——待办表外键指向绑定行，没有可挂的行；待办仍由游标摄取建（行为同以前）。

改的文件：`orchestrator/assurance_final_writer.py`、`orchestrator/assurance_consumers.py`；既有 A06 三条测试（替身库没有待办表）改为钉住 `AssuranceWorkStore.seed`，顺带核对"同事务建了哪条待办"。

### A02（C-02 / B′-4）库标记不符或状态文件缺失进隔离，不是起不来，也不自动写回

现状：`assurance_root_commits.install_native_root` 在已有回执时按部署身份重新 `_publish` 状态文件（状态文件缺失 / 被改等于没事）；它抛出的错（如 ROOT_INSTALL_COMMAND_REQUIRED、IMMUTABLE_IDENTITY_CONFLICT）在 `event_handler.__aenter__` 的 `try` 之外，整个编排起不来。

做法：

1. `install_native_root`：只有**新**安装（没有这条命令的回执）才写状态文件；已有回执的根不写回，末尾 `gate.require_execution()` 只核对——状态文件缺失 / 不符就是 `ROOT_QUARANTINED`。
2. `event_handler.py` 启动那一段：`assurance_root_setup` 调用挪进 `try`，任何 `AssuranceError` → 记 `_assurance_quarantine_code`、`_assurance_management_only = True`、返回——服务起来，但不装配（规划 / 执行图 / 保证通道）、不开执行池、不恢复、不派发；`_require_assurance_execution_root` 按码拒绝。别处没动。
3. `api/facade.py` 的 `assurance_root_diagnostic`：启动时根进了隔离就如实说 QUARANTINED，并带匿名阻塞码 `blocking_code`（原计划 §10.3 允许披露的一项）。只有这四个字段，没有标题、路径、对象 id。

边界（见第五节第 2 条）：首次安装在"库回执已提交、状态文件还没写"之间崩溃，下次启动就是隔离，没有自动补文件的路；原计划 §10.2 说"按同命令幂等补文件"针对的是明确的重新授权命令，本轮没有做这个命令。

改的文件：`orchestrator/assurance_root_commits.py`、`orchestrator/event_handler.py`（只启动那段）、`api/facade.py`（只诊断方法）。

### A40（B′-20）非披露诊断与隔离只读分支接进产品

现状：SDK 有 `MissionControlV1.assurance_root_diagnostic` 与读接口的 `ROOT_QUARANTINED` 分支，Host 没接；Host 启动后一律 `available`。

做法（Host）：

1. `service.py`：`_open` / `_rebuild` 进入编排后先读非披露诊断；不是 NATIVE → `_quarantine` 记下诊断、只留门面，不绑职责、不回填通知、不开策略读；`start` 把状态置为 **`quarantined`**（`available=False`，`reason` 写明"保证通道根已隔离……只开非披露诊断，不派发任务，不自动写回"），不开驱动循环；`_drive` 在重建后发现隔离就停。`status()` 新增 `assurance_root`（诊断原样；NATIVE 时 `{"state":"NATIVE",…}`）。新增只读方法 `assurance_root_diagnostic()`（诊断 + `host_state`）。
2. `handlers.py`：新动词 `mission_assurance_root_diagnostic`（不接任何字段）；`QUARANTINE_READS`（它 + 三个保证读动词）在 `quarantined` 状态仍开，其它一律 `orchestration_unavailable`——任务列表、通知等不开，不披露任务标题与正文。
3. `assurance.py`：根隔离时三个读动词一律答 SDK 的 `ROOT_QUARANTINED`（host-error-v1 正文，带 request_id），不看对象存不存在。

没做（留给主会话 / 界面车道）：`tauri-app` 的状态条与 `MissionAssurance.tsx` 显示 `assurance_root`；主对话工具 `chat_tool.py::mission_status` 把 `assurance_root` 念出来。都是读 `status()` 的新字段，不需要再动 Host 动词。

改的文件：`backend/deskpet/orchestration/service.py`、`handlers.py`、`assurance.py`；`backend/tests/orchestration/test_handlers_contract.py` 的动词集合加一项。

## 五、偏差与裁决

1. **A05 的"各自上限"**：条目写"分开两种状态与各自上限"。预算等待没有做次数上限：次数上限 / 转 MANUAL_REQUIRED 正是本条的缺陷；给它的上限是退避上限 60 秒（`BUDGET_WAIT_MAX_MS`），到期再看，直到预算条件变了（新事件把目标升上来）。另：车道硬约定"别的车道不加迁移"，所以也没有给待办表加预算等待的计数列；按现有列实现（`tries` 做退避的依据）。主会话若要次数上限，需要迁移 47。
2. **A02 的首装窗口**：首次安装在库回执提交后、状态文件写出前崩溃 → 下次启动隔离，没有自动补文件（原计划 §10.1 "两者之间崩溃保持 QUARANTINED"）。原计划 §10.2 的"按同命令幂等补文件"属于明确的重新授权命令，本轮没有这个命令；要不要补一个认证管理命令，留给主会话。
3. **A02 隔离的范围**：`assurance_root_setup` 抛出的所有 `AssuranceError` 都进隔离（含安装身份冲突 IMMUTABLE_IDENTITY_CONFLICT、ROOT_INSTALL_COMMAND_REQUIRED），按原计划 §10.1 "不匹配 → QUARANTINED"理解。非 `AssuranceError`（如库文件损坏抛 OSError）仍起不来。
4. **A40 的 Host 测试**：装的 opt.164 轮子里 SDK 还会自动写回状态文件，Host 侧造不出真隔离；Host 用例把 SDK 的非披露诊断钉成 QUARANTINED，只测 Host 怎么接。真·删状态文件的 Host 场景要等新轮子钉版后再跑一次（第六节）。
5. `api/facade.py` 不在车道文件表里，只改了 `assurance_root_diagnostic` 一个方法（非披露诊断要如实说隔离）；`event_handler.py` 只改启动那一段。没有新增跨边界错误码，`error_table.py` 未动。没有迁移。
6. **环境事故**：Xcode 27 更新后 `/usr/bin/git`、`/usr/bin/python3` 因未接受许可拒绝运行；本车道改用 `/Library/Developer/CommandLineTools/usr/bin/git` 与虚拟环境的 Python。另外本车道开头在工作树 backend 目录跑了一次 `UV_PROJECT_ENVIRONMENT=<主检出 backend/.venv> uv run`，把主检出的 Host 环境换回了旧轮子（协调者已通知并修复）；之后改为在工作树自建 `.venv` 跑 Host 测试，最后一轮按协调者要求改用主检出 `backend/.venv/bin/python -m pytest` + `PYTHONPATH=<工作树>/backend`，工作树里的临时 `.venv` 已删。
