## 1. 差异到底是什么

用草稿脚本逐字段比对实际值与 `pool_identity_baseline.json`。四种组合（有无向量模型 × 有无思考池）差异相同，只有三类字段：

| 字段 | 基线 | 现在 |
|---|---|---|
| `pools/*/authorization_policy`、`status/authorization_policy` | `host-deployment-policy:c38c398452440b12` | `host-deployment-policy:4ff130fb2a3fd60f` |
| `owner_contract.content_hash`（`host-owner:tenant-pool-identity`） | `45dadaae…` | `0f51f4ac…` |
| `control_caller`、`read_caller` 里的 `owner_contract_ref.content_hash` | 同上 | 同上 |

其余字段全部一致。包括执行池配置行 `arp_profile`、激活回执、根标记文件、目录命名空间、上下文策略。

三类字段是同一个源头：

- 授权政策编号 = 允许工具名排序后的摘要前 16 位（`native_pools.py` 第 80 行）。
- 允许工具 = 部署给的工具 ∪ `ASSURANCE_REVIEWER_TOOLS`。
- 主人合同哈希 = 摘要（租户 + 授权政策编号）（第 129～132 行）。
- 两种调用者都带主人合同引用。

已用草稿脚本验算：旧工具集算出 `c38c…` 和 `45da…`，与基线完全相等。

## 2. 从哪次改动开始变

**执行池部分：提交 `afc692b66`（10-06，第 2 批车道 G，K01）。**
它把 `ASSURANCE_REVIEWER_TOOLS` 从两件证据工具扩成四件，加了 `knowledge_list`、`knowledge_read`（`runtime/tool_gateway.py` 第 163 行）。允许工具集变了，所以授权政策编号变了，主人合同哈希也跟着变了。

**根要求书哈希：提交 `99788b2fa`（10-04，HTN 一致性补改 H-3）。**
它删了 `Criterion.phase`，`to_json` 不再输出 `"phase": null`。要求书哈希因此改变。
已验证：
- 用 `git archive` 取各提交的 SDK 源码逐个算哈希。`0f8d8d9fd` 及之前是 `41f2ce29…`，`99788b2fa` 起是 `12327571…`。
- 在当前输出的每条准则里补回 `"phase": null`，重算正好得到 `41f2ce29…`。

两处改动都是用户定过的产品决定（K01："审阅员通过黑板自己去取"；H-3：删没人生产的偏好分类）。

## 3. 政策哈希是否在执行池准入身份里

启动时有三道核对，政策哈希都不在里面：

1. **上下文身份旁文件**（`assembly.py` 中的 `_bind_context_identity`）。比对 `execution-*.db.context.json` 与 `RuntimeProfile.context_snapshot()`。快照只含：模型、上下文策略、分词器指纹、读分页参数、读工具说明哈希。不含授权政策或主人合同。不一致时报 "context identity differs from the existing execution pool"，服务起不来。
2. **在途意图核对**（`_check_intent_contexts`）。逐条比对历史执行意图里的 `runtime_context` 和 `provider_admission_fingerprint`。同样不含政策或主人合同。
3. **执行池配置行**（`arp_profiles`，以执行池编号和修订号为键）。行内容就是 `arp_profile` 字段，这次没有变。

主人合同只出现在两个地方：
- **建 Agent 的命令哈希。** `arp/creation.py` 的 `_command_hash` 把调用者（含主人合同引用）放进哈希。
- **控制通道回执。** 目录类命令的回执摘要含调用者。

这两处只在**同一创建键或同一命令编号重放**时比对。启动时不比对。

**实证：** opt.171 发版后做过开发数据副本启动检查（`.local-test-evidence/2026-10-07/datacopy171/backend-stdout.log`），日志有 `orchestration_ready state=available`。这份数据是 10-05 F2 联测留下的，比 K01 早，旧执行池按旧政策建成。所以政策哈希已经变过一次，旧池照样起来了。

另外只读查了原数据目录（`immutable=1` 打开，没有写入）：四个执行库里 `arp_creation_intents` 只有 512K 思考池有 186 行，全部是 `BOUND`，没有卡在半路的创建。

## 4. 留意但不阻断的一个窄窗口

升级前若有一次建 Agent 停在半路，会出问题。具体条件：Harness 的执行意图还是 `CLAIMED`，而 ARP 创建意图已经写下。升级后重放这次创建，命令哈希会因主人合同变化而不同，ARP 报 `CREATION_IDENTITY_CONFLICT`。

后果有限：
- `event_handler.py` 第 5179 行附近把它当作"该意图被按名拒绝"，只记一条日志、跳过这一个意图。
- 服务、执行池和其他任务都不受影响。

按开发期"不兼容旧数据"的规矩，这不算缺陷。如果以后要堵上：把建 Agent 命令哈希里的调用者换成"principal + 命令回执"，不带主人合同；或者让主人合同哈希不随审阅员工具集变化。这次不需要做。

要求书去掉 `phase` 还有一个附带影响：10-04 之前建的任务，库里存的准则可能带 `"phase": null`。严格解码（`fields_of` 拒绝未知字段）会读不进去。这同样属于"旧数据不兼容"，只影响那些老任务，不影响执行池启动。
