# TaskGraph 补全第四批 — 施工设计（改要求后按新要求重审沿用的叶子）

依据：方案第 3.4 版第 4 节。本文只记施工落点，不改方案口径。代码摸底由子代理（只读）完成，结论摘要如下（中文摘要，原报告英文）。

## 一、摸底结论（子代理只读报告摘要）

现行"验证 → 验收"整条链只服务"刚交上来、还没验收的结果"，对"已验收的同一份结果再按新要求审一次"有约十处挡住：

1. **调度**：只挑验证状态为"待验证 / 验证中"的结果（`event_handler.py` 约 :3781）；`_verify` 一开头要求尝试未结束并续租（约 :7895、:7898），已验收结果的尝试和任务都是"已完成"，续不了租。
2. **冻结范围**：`completion_inputs._current_scope` 只接受"除计划版本外完全相同"的范围；要求版本变了一律报过期——所有读结果冻结输入的地方都会失败。
3. **切包 / 验收核对**：`scoped_content_review.read_task_content_candidate`（冻结范围 ≠ 现行范围即拒）、`validate_scoped_command`（同上，且只认这份结果原来那条审阅员记录）。
4. **验证层记录**按（结果, 层）唯一，已验收结果的验证记录不可改（`commit_service.record_verification_layer`）。
5. **审阅员调用**：`assurance_review_runtime.run_task` 按尝试找旧记录、旧调用、尝试的保护预算，并要求尝试和任务还活着；同一份结果出现第二条审阅绑定后，`task_record` 与 `assurance_validity.official_record_for_result` 会报"来源有歧义"。
6. **本地检查**绑在结果冻结的范围上（`assurance_local_checks.prepare`、`assurance_check_import`）。
7. **验收编号**按（任务, 结果）算，与旧验收撞号；命令号 `accept:{结果}` 会被当成重放直接返回旧验收。
8. **验收提交**（`commit_service.accept_result`）对已验收结果是空操作；它会改尝试 / 任务 / 产物状态、结清预算，重审都不该做。
9. **打回**：`fail_result` 会把尝试改回重试等待——重审打回不能走它，应记修复请求交规划器。

已具备的：每次计划提交都为现行计划里所有步骤（含沿用的叶子）按最新要求冻结完成范围；该范围的检查口径由部署职责自动按无损映射批准。改要求只改根合同，叶子的任务合同不变。

## 二、落点

- **入口（新）**：`orchestrator/carried_review.py`。每轮扫描现行计划：普通步骤、已有通过结果、该结果的验收只在旧要求版本下成立、现行要求下不算数、它读的上游在现行要求下都已算数、这一版要求下还没重审过。每步每个要求版本一个重审键（带要求版本），不另计数。
- **冻结输入**：`load_completion_result_inputs` 加"重审"读法——原结果的冻结输入清单、端口认领、出现编号不变，范围取现行的；只在"任务合同不变、现行要求版本比冻结的新"时成立。正常验证路径不变。
- **键**（按裁决）：这条链上"每份结果一份"的键统一改为（结果, 要求版本）——内容审阅绑定的四处查找加要求版本条件；验证层记录原表加要求版本列、唯一约束改为（结果, 要求版本, 层）；验收编号与命令号带要求版本。不建新表、不改保证机制身份。
- **检查与审阅**：重审由 `carried_review.py` 直接驱动（不进 `_verify`），按现行范围对原产物的只读重建副本跑本地检查，再请审阅员独立会话按现行范围审；审阅预算记任务账户、不计尝试次数；存活看任务所在的现行计划，不要租约。
- **验收**：通过 → 带要求版本的新验收编号，写验收、输出、按现行范围的内容贡献；不动尝试 / 任务 / 产物状态、不结清预算。打回 → `CARRIED_RESULT_REJECTED` 修复请求（带不通过的准则与理由）。审阅没结论 → 现行"判不下来"出口。
- **派发处**：`ACCEPTED_UNDER_OLD_REQUIREMENTS` 改为"等审阅员按新要求重审"（新码登记进错误码表）；重审打回后这一步按现行要求仍不算数，原样等规划器处理。
- **登记**：新事件（重审请求、重审结论）与新码进全业务重放覆盖清单与错误码表。
- **提示词**：v24 内补一句（与第三批同一版）。
