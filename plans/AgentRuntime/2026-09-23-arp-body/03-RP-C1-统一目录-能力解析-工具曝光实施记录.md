## 2. 实现决定

1. **定义体 hash 互引方向**：`ProviderDefinition.capability_refs` 至少 1 项而 `Capability.provider_refs` 可空，pin 又是内容 hash，所以先登记能力再登记提供者；解析器候选 = 能力列出的提供者 ∪ 声明了该能力精确 pin 的已准入提供者。
2. **目录事件的 Run 归属**：`run_events` 外键到 runs，目录是 namespace 级；变化事件在给出 `run_id` 时绑定到触发命令的 Run，SDK 内 bootstrap 无 Run 则只推 epoch（epoch 行自带来源回执）。Host 侧目录 writer 接入时传它的命令 Run。
3. **曝光失败不判死 Turn**：请求的工具在目录里不可用时从本次请求移除并留具名原因（`exposed()` 返回），不是拒绝整个请求；模型看到的就是快照里的工具。
4. **消费方工具 effect_class**：SDK 内置工具按已知类别（历史检索 READ_ONLY、委派 SANDBOX_WRITE），其余缺省 EXTERNAL_EFFECT（保守），可由 `ArpPorts.extra["tool_effect_classes"]` 覆盖；真实实现与 policy 判定留给 Host 目录 writer。

## 4. 独立核验

一轮，opus 5.5 只读审阅，只报阻断级。结论：4 条阻断，全部处置：

| 审阅发现（大白话） | 处置 |
|---|---|
| 进程重启时 bootstrap 把运维已暂停的工具/部署又改回准入，撤权失效 | bootstrap 只推进 QUARANTINED 一段；SUSPENDED/TRIAL/RETIRED 一律不动。测试：暂停工具与部署后重建运行时仍 SUSPENDED，epoch 不变 |
| 内置部署健康 24h 过期后无人续探，常驻进程超一天所有工具失效 | 新增 `refresh_builtin_health`：剩余不足 1h 或已过期/非 READY 时重探（READY→READY 不推 epoch），`tick()` 每轮调用。测试：假时钟拨到临期 → 续探；再过一天工具仍可用 |
| 暂停能力或 schema 不会撤掉依赖它的工具 | `usable()` 对 TOOL/SKILL 追加其能力与输入/输出 schema 必须 ADMITTED，原因具名 `CAPABILITY_NOT_ADMITTED:<id>` / `SCHEMA_NOT_ADMITTED:<id>`。测试覆盖两种 |
| 能力解析没比较 provider 的输入/输出 schema | 硬过滤加 schema 精确相等。测试：schema 不同的最高优先级 provider 不被选 |

处置后 ARP 定向 269 passed。
