### 3. 改成什么

**一个签发入口。** 新文件 `SDK/orchestrator/assurance_point_use.py`。时点用途（PLAN、START、CONTEXT、RECOVERY）都走它：

1. 消费方报"这次用了哪些证据"（证据声明）：知识（编号、版本）、步骤摘要（结果编号、摘要哈希）、一步的开工地基（任务编号）。
2. 签发方按种类用**原有的那个判定**核每一项此刻是否当前：知识 → `knowledge_standing`；摘要 → `step_summaries` 现行行；开工地基 → 原 `_validity_refusal` 的逻辑（见证 `is_fresh_for` + `acceptance_is_current` + "已重做的上游算历史"），整段搬进来。签发方不加新的语义判断。
3. 每项钉住精确对象（验收、观察、消费方自己的任务契约或要求版本），逐个向现行授权取 ACCESS / POLICY 见证；到期取最早租期与见证期限。
4. 全部当前 → 组 `UseCertificate`（USABLE），在消费方自己的写事务里做最终核对（根实例、纪元、时钟、到期、授权，复用 `check_certificate_binding`），写证书表、依赖索引和一条使用回执（回执里记证据声明，供复核与恢复读）。任一项不当前 → 不签，返回具名原因（"哪一项、为什么"）。
5. MAINTAIN：签发方直接拒绝，原因 `MAINTAIN_MONITOR_UNAVAILABLE`。产品没有持续监测器，点状采样不冒充连续（§8.4）。

**各环节接法：**

| 用途 | 签在哪 | 消费方 | 不能用时怎么办 |
|---|---|---|---|
| START | `begin_handoff` 交接事务，写 HANDED_OFF 之前 | `ACTION` / 动作键 | 拒绝交接，原因仍是 `validity_stale:<具名原因>`（已登记为暂时性），动作留在可交接状态；地基不回来由卡死记录如实交给规划器（现行为不变） |
| CONTEXT | `create_attempt` 事务里，写尝试之前 | `ATTEMPT` / 尝试编号 | 不建尝试（`CommitRejected`，带具名原因），下一轮重新选上下文 |
| PLAN | `_create_planner_intent_now` 同一事务里，建意图之后 | `PLANNING_REQUEST` / 请求编号 | 不开这一轮（异常回滚整轮），下一轮重试 |
| PLAN（复核） | 规划回复准入 `_check_binding_revisions` | 同上 | 按 `REQUEST_BINDING_STALE` 退回（请求过期类，不扣规划器次数），字段路径 `/planning_evidence`，写明哪一项过时；新请求拿新包 |
| RECOVERY | `_recover_intent` 重新绑定在途尝试之前 | `ATTEMPT` / 尝试编号 | 读这次尝试的 CONTEXT 回执里的证据声明，按 RECOVERY 重签；签不出 → 不恢复这次尝试：按"被打断"记丢失（不扣次数），撤回执行，原因与哪一项过时写进失败明细；这一步下一轮拿当前上下文重做 |
| MAINTAIN | 无产品环节 | — | 写偏差单，停在这一处（见第 6 小节） |

格式重试沿用开头那次请求冻结的包（"请求事实不动"），不重签；它的回复照样过准入复核。

**计时与有效性观察。** 时点用途的证书在签发事务里就用掉了，之后是历史（`assurance_consumers.py:180` 原注释："消费过的证书是历史"）。它们不进 `live_usable_certificates`、不进 `emit_due`，否则每次来源变化都要重看每次开工、每轮规划的证书，还会把过时的历史证书翻成"证据失效"修复请求。用途分组写成 `certificates.py` 里一个常量 `POINT_PURPOSES`，两处 SQL 都读它。

### 4. 删掉的旧路径

- `action_commits._validity_refusal` 的旧核法整段删，搬进签发方的"开工地基"判定；交接处只看证书。
- 规划、上下文、恢复原来在使用点没有核对，没有可删的。选上下文、选规划包时的过滤（`_gather_knowledge`、`current_knowledge`）是"给什么"，证书是"给出去这一刻还能不能用"；两处调用同一个判定函数，不是两份判定。

### 5. 守什么保证

- 不按已失效的证据开工交接、装上下文、开规划、恢复在途尝试：证据此刻不当前就不用，原因具名。
- 判断不变：当前与否仍由原有判定说了算，Harness 不加语义规则；不能用时把事实交给规划器或下一轮，不替它决定。
- 证书只在消费方自己的事务里落地：用了就有证书，没用就没有。
- 时钟不可信、根实例变了、授权变了：一律不签（与 ACCEPT 同一个最终核对）。

### 6. 偏差（开工前已知）

1. **MAINTAIN 没有产品环节。** 分解只写 SELECT 前提；没有持续监测器。不编使用者。只在签发方挡住 MAINTAIN（具名原因）。停在这一处。
2. **执行尝试开工不另签 START。** 开工输入与前提已由执行图见证合同在派发事务里核（`admit_for_dispatch`），交接时再按见证合同复核；10-02/03 子代理裁决（`HTN补齐-开工前裁决-2026-10-02.md` 1.2 第 1 条）定"交接复用见证合同的核对函数，不另起一套"。在同一事务里再判一次是同一件事两条路。START 证书签在原计划 §9.4 举例的位置：对外操作交接（"下单前库存足够"）。停在这一处。

### 7. 怎么测

- 单元同形（`tests/orchestrator/full_target/assurance_exec/test_point_use_certificates.py`）：每种用途一条"证据当前放行并落证书 / 证据过期拒绝并给具名原因"；MAINTAIN 拒绝；时点证书不进有效性观察与到期唤醒。
- 产品同形（`product_world`，默认路径）：交接走通时有 START 证书（`test_validity_handoff.py` 两条原用例）；两步任务第二步开工有 CONTEXT 证书、规划轮有 PLAN 证书；崩溃重启后在途尝试的证据过时 → 不恢复、记丢失、重做后任务完成。
- 每种用途改坏一次：签发方不核那一项 / 消费方不看证书，绑定用例要红。
- 只跑改动直接相关的文件。

### 8. 按核心思想自查

- 判断是语义还是秩序？"这条证据现在还当前吗"由原有判定（引用还在、版本对、验收还撑着、见证没过期）回答，是秩序。证书只是把这次使用记下来并守住时点。✔
- 没有加"遇到某种情况就那样办"的分支：不能用时只如实停下或退回。✔
- 同一件事一条路径：交接核对搬进签发方后旧代码删；选与用两处调同一个判定函数。✔
- 不做兼容：时点证书是新行；旧库没有它们，不迁移。✔

## 二、做了什么（按用途）

方案提交：`a2aa93d4`。代码提交：`1eddf79f`。

### 1. 一个签发入口（新文件 `SDK/orchestrator/assurance_point_use.py`）

- `EvidenceClaim`：三种证据声明——知识（编号、版本）、步骤摘要（行编号、摘要哈希）、开工地基（任务编号）。
- `certify_point_use_locked`：在消费方事务里逐项用原判定核当前；全部当前才组 USABLE 证书，过 `check_certificate_binding`；`record=True` 时写证书表、依赖索引、使用回执（回执 kind 沿用 `AssuranceUseCertified`，正文多一个 `evidence` 列证据声明）。不当前返回 `refusals`（具名）。没报证据：不签也不拦。
- 读集：每个钉住对象一条 OBJECT + ACCESS + POLICY；一条 QUERY_SET（证据声明与钉住对象的指纹）。到期 = 授权租期与见证期限的最早者。
- 钉住对象：验收、观察、消费方自己的任务契约（`task`）或现行要求（`requirements`）。
- 时点证书不发事件：没有消费者要它；发 `AssuranceUseCertified` 会每次唤醒收尾消费者。
- `planning_evidence_stale`：按请求的 PLAN 回执重核（只核不落库）。`certify_recovery_locked`：按尝试的 CONTEXT 回执重签 RECOVERY。

### 2. START（对外操作交接）

- `action_commits.begin_handoff` 改调 `_start_use`：签 START（消费方 `ACTION`/动作键，证据 = 这一步的开工地基）。签不出 → `validity_stale:<具名原因>`，原文字与原交接核对一致，仍是已登记的暂时性拒绝。
- 证书在写 HANDED_OFF 之前、同一事务落库（`record_point_use_locked`）。被别的原因拒绝的交接不留证书。
- 旧 `_validity_refusal` 整段删，逻辑原样搬进 `_judge_step_ground`。

### 3. CONTEXT（装执行者上下文）

- `commit_service.create_attempt` 新参数 `context_evidence`；事务里写尝试前签 CONTEXT（消费方 `ATTEMPT`/尝试编号）。签不出 → `CommitRejected("CONTEXT_EVIDENCE_NOT_CURRENT: …")`，派发方照旧记一笔、下一轮重选上下文。
- `event_handler` 派发处用 `context_claims(knowledge, upstream)` 报证据：冻结的已验证知识、推送的摘要层、直接上游里核对过的摘要。

### 4. PLAN（开规划请求 + 回复准入复核）

- `_create_planner_intent_now`（一个事务）建意图并绑定请求后签 PLAN（消费方 `PLANNING_REQUEST`/请求编号，证据 = 包里 `views.knowledge` 的已验证知识与摘要）。格式重试不重签。
- 签不出抛 `PointUseRefused`，整轮回滚；`_try_planner_intent` 接住，记进度、这一轮不开、下一轮重来。等待唤醒路径上的同一异常按一轮故障原地重试。
- 准入：`AdmissionContext.planning_evidence_stale`（新可选字段），`_check_binding_revisions` 不为空时按 `REQUEST_BINDING_STALE` 退回，字段路径 `/planning_evidence`，说明里点名过时项。请求过期类不扣规划器次数（原有分类）。

### 5. RECOVERY（重启恢复在途尝试）

- `_recover_intent`：未终结的在途尝试，先按它的 CONTEXT 回执重签 RECOVERY。签出 → 照旧绑定、接着跑。签不出 → `mark_attempt_lost(reason="recovery_use_refused", detail={"refusals": …})`、意图记 FAILED、撤回执行（cancel）。
- `failure_classes._INTERRUPTED_REASONS` 加 `recovery_use_refused`：按"被打断"，不扣次数，同一步合计上限照旧。
- `mark_attempt_lost` 加可选 `detail`，写进失败明细与事件。

### 6. MAINTAIN

- 签发方见 MAINTAIN 直接返回 `MAINTAIN_MONITOR_UNAVAILABLE`，什么都不写。没有产品使用者（偏差 1）。

### 7. 计时与有效性观察

- `certificates.py` 加 `POINT_PURPOSES`（PLAN/START/CONTEXT/RECOVERY）与其 SQL 字面。
- `assurance_recheck.live_usable_certificates`、`expiry.AssuranceExpiry.emit_due` 排除时点用途。收尾证书集合、有效性观察者、到期唤醒都只看持有型证书（ACCEPT）。
