### A18：审阅员政策、上下文政策的钉住有登记读者

**1. 原计划怎么说**

| 出处 | 原文要点 |
|---|---|
| `P/contracts/review-binding-v2.schema.json:20,22,228,240` | 审阅绑定必带 `reviewer_policy_ref`、`context_policy_ref`，都是 pin（id、revision、content_hash） |
| `P/implementation/ref-resolution-map.json:2206-2224` | 读者：`registered reviewer policy exact reader`（正文 = 冻结的审阅员 / 独立性政策）；`registered Context policy exact reader`（正文 = 冻结的披露 / 装包政策）。版本规则：精确原版本，不可变正文可用 0，不许取最新。归属：同任务、同租户；缺失 / 歧义 / 哈希冲突一律拒绝 |
| `P/implementation/field-producers.json:1822-1842` | 写者：原有的审阅包构建方 → `ensure_assurance_review` |
| `P/ASSURANCE-EXEC-1.1.zh-CN.md:79`（§3.1） | policy 类：原部署冻结政策；静态声明不作结果证据；当前生效另核 |

**2. 现状**

- `SDK/orchestrator/assurance_content_review.py:240-246`、`SDK/orchestrator/assurance_purpose_reviews.py:336-342`：审阅员政策钉住是代码现算 `Pin(REVIEW_CODEC_VERSION, 1, 指令与编解码版本的哈希)`。两处各写一份。
- `SDK/orchestrator/assurance_review_runtime.py:70-79` `context_pin`：上下文政策钉住按执行池现算 `Pin("base-agent-context:"+档案, 1, policy_hash(...))`。
- `SDK/orchestrator/assurance_review_handoff.py:66-79`：交接时再现算一遍、与绑定比对。
- 没有任何地方存政策正文。钉住只是一个哈希，审计拿着它找不回"那一版政策是什么"；`revision` 恒为 1，改了内容看不出是第几版。

**3. 改成什么**

- 新文件 `SDK/orchestrator/assurance_review_policies.py`，一处定义两种政策正文：
  - 审阅员政策：编解码版本、指令版本、指令原文、审阅员可用工具名。
  - 上下文政策：执行池档案、模型、分词器指纹、`ContextPolicy` 全文。
- **登记 = 写一条不可变回执。** 不加新表（不加迁移，避免与别的车道撞迁移号）。回执种类 `AssuranceReviewerPolicyRegistered` / `AssuranceContextPolicyRegistered`，正文 `{mission_id, policy}`，编号由任务与正文哈希定出。同一正文重登幂等；同编号异正文拒绝（`IMMUTABLE_IDENTITY_CONFLICT`）。
- **钉住 = 这条回执的精确引用**：`Pin(回执编号, 0, 回执正文哈希)`（不可变正文用 0，§3.1 允许）。
- **登记读者 = 原有的回执精确读者** `AssuranceReader.read_exact_metadata(commit_receipt, receipt_kind=…)`：按编号取、核哈希、核归属任务、核写者种类。缺失 → `SOURCE_UNAVAILABLE`；哈希不符 → `REF_BODY_CONFLICT`；种类不符 → `REF_ISSUER_MISMATCH`。
- 写者：审阅运行时在调构建方之前登记两种政策（短事务），把钉住交给构建方；构建方不再自己现算。
- 读者：
  1. 交接门（`assurance_review_handoff.py`）：按绑定里的两个钉住用登记读者取正文；要求登记正文 = 当前部署的正文，且审阅请求里实际的指令与工具不超出登记正文。
  2. 审计：同一个读者函数，拿绑定里的钉住就能取回当时那一版政策全文。

**4. 删掉的旧路径**

- 两个构建方里的 `Pin(REVIEW_CODEC_VERSION, 1, …)` 现算。
- 交接门里的 `expected_policy` 现算与 `context_pin` 现算比对。
- `context_pin` 本身（改成"登记并返回钉住"）。

**5. 守什么保证**

- 每个审阅绑定的两个政策钉住都能被登记读者解析回正文；正文变了就是新的一条登记，旧绑定仍指向旧正文。
- 交接时政策不是当前部署的那一版 → 不交（`REVIEW_DEPLOYMENT_IDENTITY_MISMATCH`，原错误码不变）。
- 不改工具说明、不改审阅员指令文字、不改并发上限：执行池身份不变。

**6. 登记不出时怎么办**

- 登记失败（同编号异正文）：构建方不调，这一轮审阅不开，错误按原有方式进进度记录，下一轮再来。正文是部署常量算出的，同编号异正文只在库被改坏时出现。
- 交接时读不回正文：交接拒绝（具名码），审阅请求停在原处等待，与现在交接门拒绝的处理一样。

**7. 怎么测**

- 先红：新用例 `tests/orchestrator/product_world/test_review_policy_registry.py`（产品同形，默认路径）：跑一个任务到完成；每个审阅绑定的两个钉住用登记读者都能取回正文，正文与部署一致。先红在"读者不存在 / 钉住不是回执引用"。
- 改了政策正文（替换指令版本）后新审阅登记出新的一条，旧绑定仍读回旧正文；同编号异正文登记被拒；登记回执被改写后读者拒绝。
- 交接门：绑定钉住的政策不是当前部署那一版 → `REVIEW_DEPLOYMENT_IDENTITY_MISMATCH`。
- 改坏：交接门不读登记正文（跳过比对）→ 绑定用例红。

**8. 按核心思想自查**

- 只是"按哪版政策"的记账与核对，是秩序，不是语义判断。✔
- 同一件事一条路径：钉住只由登记产生，交接只读登记。✔
- 不做兼容：旧库里旧形状的钉住读不回 → 交接拒绝；开发期不迁移。✔

### A03：原生下载、审阅员披露、审阅员读黑板经使用证书

| 出处 | 原文要点 |

**2. 现状（四处披露，各核各的）**

| 披露 | 位置 | 现在怎么核 |
|---|---|---|
| 原生下载 | `SDK/api/facade.py:914-942` `_authorize_artifact_read` | 原生根下直接放行，只核租户；隔离根分支走 `root_gate.require_read`，但恢复已删（10-03 决定 ⑤），`require_read` 自己也要求原生根，这一支走不到 |
| 审阅员初始材料 | `SDK/orchestrator/assurance_review_handoff.py:96-123`（四个调用点：派发、建、交、每次模型请求前） | 逐项 `_permission`（只核授权），不核时钟，不留证书 |

**3. 改成什么**

- **一个签发入口。** 四处都调 `assurance_point_use.certify_point_use_locked(purpose="DISCLOSE")`，不另起核对。
- 签发方加两样：
  1. 证据声明多一种"精确对象"（`EvidenceClaim.exact(ref)`）：判定就是原有的精确读者 `read_exact_metadata`（存在、哈希对、归属对），再按原有授权取 ACCESS / POLICY。不加语义判断。知识声明照旧按 `knowledge_standing` 判。
  2. 可选的调用者身份（主体、租户）：原生下载时核调用者就是部署的那个主体，不是则拒（`ROOT_READ_NOT_AUTHORIZED`，原码）。
- DISCLOSE 进 `POINT_PURPOSES`：每次披露是一次时点使用，签发当场用掉，不进有效性观察与到期唤醒。产品没有"披露缓存"，所以 §8.4 补注里"将来的 DISCLOSE 缓存"仍无对应物（见偏差 1）。
- 各处接法：

| 披露 | 消费方 | 证据声明 | 钉住的自身对象 | 签不出时 |
|---|---|---|---|---|
| 原生下载 `artifact_read` | `NATIVE_READ` / 主体:产物编号 | 这个产物版本 | 任务现行要求 | 不给正文，`FacadeError("USE_EVIDENCE_NOT_CURRENT", 具名原因)`；读完字节后超出证书期限 → `RECHECK_REQUIRED`（原码） |
| 审阅员初始材料 | `REVIEW_INTENT` / 派发意图编号 | 审阅包、审阅对象、每条初始材料 | 绑定的所属步骤 | 交接拒绝，具名原因；审阅请求停在原处等（与现在交接门拒绝的处理一样） |
| 审阅员取证读 | `TOOL_CALL` / 这次工具调用编号（网关多传一个调用编号，工具说明不变） | 这条证据 | 绑定的所属步骤 | 工具拒绝，原因具名（原有 `EvidenceToolRefusal`），模型可换一条读或直接作答 |
| 审阅员读黑板 | `TOOL_CALL` / 这次工具调用编号 | 这条知识 / 摘要 | 绑定的所属步骤 | 不给正文，`standing` 写原因（与执行者同一个 `refused_handover_reply`） |

- 落库：只在真正交出去的那一刻记证书。审阅员初始材料在每次模型请求前（`mission_sources.require_current`）记；派发、建、交三处是前置门，只核不记（`record=False`），同一个判定。原生下载、两种工具读每次都记。

**4. 删掉的旧路径**

- `facade._authorize_artifact_read` 整段（含走不到的 `require_read` 分支）。
- `root_gate.require_read`、`FixedPrincipalAuthority.read`、`CommitService._assurance_read_authority`：唯一读者是上面那段，一起删。
- `assurance_review_handoff.py` 的逐项 `_permission` 循环与包 / 对象两次 `_permission`。
- `reviewer_evidence_tools._read` 开头的 `_permission` 预检。（钉住字节读取协议 `read_pinned_blob` 自带的"读前读后两次授权"是字节层的屏障，审阅包构建、检查使用也走它，不动。）
- `assurance_point_use.judge_claims`（唯一用处是审阅员读黑板）。

**5. 守什么保证**

- 任何把材料交给人或审阅模型的地方，交出前同一个签发方核：对象精确存在、授权当前、根实例、时钟可信、纪元；交出就留一张 DISCLOSE 证书。
- 时钟不可信时不披露（§8.4）；不披露诊断（`assurance_root_diagnostic`）不受影响。
- 判定不变：对象 / 知识当前与否仍由原有读者与判定说了算。

**6. 怎么测**

- 新用例 `tests/orchestrator/product_world/test_disclosure_certificates.py`（产品同形，默认路径）：
  - 跑一个任务到完成：每个发出去的审阅请求都有 `REVIEW_INTENT` 的 DISCLOSE 证书，读集里有审阅包与审阅对象；时点证书不进有效性观察。
  - 原生下载：读一个产物 → 有 `NATIVE_READ` 证书、正文与哈希一致；时钟回拨 → 不给正文、原因 `TIME_DISCONTINUITY`；换一个主体调 → 拒绝；产物行被换掉（哈希不符）→ 拒绝。
  - 审阅员取证读与读黑板：各一条证书；过时知识不给正文。
- 跟着改的旧用例：`test_batch2_g_reviewer_blackboard.py`（审阅员读黑板的门）、取证工具相关用例（`test_evidence_read_cap.py`、`test_review_findings.py`、`test_review_turn_limits.py`）只在断言了旧核法时改。
- 每处改坏一次：签发方不核时钟 / 原生下载不问签发方 / 交接不签 / 读黑板不签 → 绑定用例红。

**7. 按核心思想自查**

- 披露前核"能不能交"是秩序（存在、授权、时钟、根），不是语义；不加"遇到某种情况就那样办"的分支。✔
- 同一件事一条路径：四处披露同一个签发方；旧的只核归属 / 只核授权的核对全部删除。✔
- 不做兼容：旧库没有 DISCLOSE 证书，不补。✔

### 预先登记的偏差（开工前已知）

1. **"原生 summary" 没有单独的读者。** 计划 C.1 第 496 行写"原生下载 / summary"。产品里摘要只以两种方式出去：交给模型（规划包、装上下文、运行中读知识，A26 已签证书），以及在任务全量视图 `mission_get` 里给本人看（`facade.snapshot`，整张快照，含结果、知识、摘要）。把整张快照逐对象签证书是另一种做法，计划没写到这个粒度。本车道不动 `snapshot`，停在这一处，待主会话 / 用户定。
2. **DISCLOSE 定为时点用途。** §8.4 第 258 行补注写"持有型证书：ACCEPT，以及将来的 DISCLOSE 缓存"。产品没有披露缓存，每次披露当场签当场用，进 `POINT_PURPOSES`。请主会话确认，必要时改补注。
