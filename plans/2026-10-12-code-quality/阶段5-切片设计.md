## 改动会碰到的身份与约束

1. **执行图部署清单**：钉死 SDK 全部源文件字节，每片重生成（批次脚本已做）。
2. **改坏清单**（acceptance_assets/mutations.json）：按"文件 + 原文"定锚。原样搬到新文件时原文不变、文件变了，要把 `file` 改到新位置；结构改动后要重锚并用 run_mutations.py 验 KILLED。
3. **接缝清单**（seams_current.json）：按 `模块:限定名` 用 getattr 解析。方法搬进 mixin 后经类继承仍能解析；模块级函数搬家要改条目。
4. **契约文件 contracts/htn.py 被网络编解码器清单按字节钉死**（network_codec_manifest_v1～v5）：改字节会改变编解码身份，已存的网络文档解不开——这是行为改变，属禁区（ruff.toml、guard.py 都把它列为禁区）。
5. **执行池身份**：来自身份字符串，不来自代码字节，搬代码不影响。
6. **公开接口**（阶段 4）：公开清单里的模块路径不能少；搬出去的名字若被后端引用，要留在原模块的 `__all__` 可见（由导入提供），或把新模块加进清单。
7. **测试打桩与直接调用私有方法**：方法搬进 mixin 后仍在类上，调用与 `setattr(Orchestrator, "_x")` 照常生效；模块级函数搬家要改打桩目标。

## 与计划原文的出入（需裁决）

1. **5C 不拆 contracts/htn.py。** 理由见约束 4：拆它会改编解码身份，属行为改变；它在禁区里。建议记为整治范围外（或另立一个"编解码器换版"的计划，带迁移）。
2. **5A.2（mixin 改成领域仓库类、原类变组合门面、调用方改用仓库）的代价远超原估计。** 原计划写"调用方后端 11 处"，实测执行存储类公开方法在 SDK 源码、SDK 测试、后端产品代码里共有数千处调用（协议文件只声明了 44 个方法）。改成仓库意味着改写运行时协议与几千处调用点。可选：
   - (a) 照原计划做；
   - (b) 只做内部组合：mixin 改成领域仓库类，门面按协议保留公开方法并转交仓库——但这等于 213 个转交方法，违背"一条路径"；
   - (c) 停在 5A.1（按域 mixin）+ 拆长函数，5A.2 不做，在实施记录里写明理由。
   建议 (c)：mixin 已把 15000 行拆成每个 600～2500 行的领域文件，长函数拆掉后单文件可读；仓库化的收益主要是"构造时只拿需要的依赖"，而执行存储类的依赖就是一条数据库连接，收益小。
3. **5B.3（编排器 mixin 改成独立协作对象）的代价也被低估。** 测试直接调用编排器私有方法约 310 处（87 个文件）；协作对象化后这些方法离开编排器，测试要大面积改写。另一方面，SDK 循环依赖导入 87 处要在阶段末降到 ≤ 30，其中相当部分在编排器相关模块之间，协作对象化是解环的主要手段。可选：
   - (a) 照原计划做 5B.3，同片改测试；
   - (b) 5B.3 只对"测试不直接调用、且能解环"的协作者做（如上下文绑定、审阅流程、任务生命周期），其余停在 mixin；
   - (c) 停在 5B.2。
   建议 (b)，以循环依赖上限为验收口径：做到 SDK 循环依赖 ≤ 30 为止。
4. **全量回归次数。** 计划排 7 次，现已用 3 次（阶段 1、2、4 各一次；原排期阶段 1 不跑，所以比原排期多用了一次）。原排期阶段 5 用两次（5B 后、5F）。照此阶段 6、8、11 各一次就是 8 次，超出授权。建议：阶段 5 只在 5F 跑一次；5B 完成后改跑"编排器相关测试目录"（不算全量）。

## 独立裁决（2026-10-15，子代理，模型 Opus 5.5）

只读核验。没有改代码，没有跑测试。另跑了一次 SDK 全 src 的 mypy 计数。

### 裁决

- 出入 1（不拆 contracts/htn.py）：**采纳。** network_codec.py 在导入时逐个校验 10 个源文件的 sha256，v5 清单里 htn.py 的哈希就是现文件（95b806a3…）。改一个字节，SDK 编解码模块直接导入失败；换清单又会改掉编解码身份，已存的网络文档全部被拒。这是行为改变，不属于本计划。
- 出入 2（5A.2 不做仓库化）：**修改后采纳 (c)。** 停在"按领域 mixin＋拆长函数"，5A.2 不做，在实施记录里写理由。附加条件：每个 mixin 类 ≤ 1500 行（派生准入、派生续接与结清、提交、运行生命周期这四块估计 2000～2500 行，各再拆成两个 mixin），否则"超 1500 行的类"清零指标过不了。每个 mixin 都写 `__slots__ = ()`（主类有 `__slots__`，提供方记账 mixin 是先例）。(b) 要写 213 个转交方法，违反"一条路径"，驳回。
- 出入 3（5B.3 只做一部分）：**修改。** 设计里的理由不成立：87 处循环依赖里只有 1 处和编排器有关（recovery_coordinator ↔ event_handler），做协作对象化解不了环。改为：5B.1 照做。5B.3 按结构挑选：5B.1 之后，方法只读写一个状态对象、只被编排器通过少数入口调用的那组，就改成协作对象。测试里直接调私有方法的地方在同一片里机械改写（用 retarget/patch_targets 工具），这不是不做的理由。其余组停在 mixin，每个 ≤ 1500 行，在实施记录里逐组写理由。验收：编排器类本体 ≤ 800 行，每个 mixin 和协作者 ≤ 1500 行。
- 出入 4（5B 后不跑全量回归）：**修改后采纳。** 阶段 5 只在 5F 跑一次全量回归，算第 4 次。但替代手段不能是"编排器相关测试目录"：SDK 的 tests/orchestrator 有 415 个测试文件，全 SDK 共 658 个。按 10-01 硬规则，跑这个目录就算全量回归。5B 之后改用：纯移动片做 AST 逐字比对；5B.1、5B.3 先补特性化测试；跑名字扫描选出的"直接引用被改方法的测试文件"；对改坏清单里 event_handler.py 的 29 条做 KILLED 检验。选出的文件超过约 150 个时，先问用户再跑。5B 各步分开提交，5F 出问题时可以二分定位。

### 阻断级问题

1. **SDK 循环依赖 ≤ 30 没有可行的归属片。** 出入 3 把它挂在 5B.3 上，但 5B.3 只能解 1 处。要另开一片专门解环（建议叫 5G，放在 5C 之后、5E 之前），按阶段 3 的结构性根因做法（共用的东西下沉，包内改成直接导入子模块），从现在 87 处降到 ≤ 30。
2. **"超 1500 行的类"清零有缺口。** 一是 Store（1683 行）和 HtnStore（2049 行）没有归属片。二是如果按出入 2、3 停在 mixin，领域估计行数超过 1500 的 mixin 本身就算超长类。不补上，阶段 5 末验收过不了。
3. **出入 4 原来的替代方案违反用户硬规则。** "编排器相关测试目录"就是 SDK 测试的大头，跑它等于一次没经授权的全量回归。必须按上面裁决里的方式改。
