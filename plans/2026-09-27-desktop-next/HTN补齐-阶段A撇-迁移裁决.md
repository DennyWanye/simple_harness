## A1　修复时换不了做法

**结论：是产品缺口，本阶段补。**

**核实到的事实**
- 规划包里的"提新做法材料"`method_proposal_contexts` 只发给还没有做法的目标：`SDK/orchestrator/planner_views.py:193`（`open_goals` 取自 `method_selection`）和 `:205-208`。`method_selection` 又只列没有做法的目标，见 `SDK/orchestrator/hierarchical_dispatch.py:2870-2900`（`method_candidates`）。
- 被修复请求指向的已细化目标，其余材料其实都有：
  - 做法库行：`method_signatures(network, under_repair)`，`planner_views.py:88-92`；
  - 适用性报告：`hierarchical_dispatch.py:2771` 起，文档串明说"修复中的目标也评估"；
  - 修复标记：`views.goals` 里的 `under_repair`。
  - 唯独缺写新做法要用的材料：目标签名、算子、要求原文、建议编号。
- 提示词 `SDK/runtime/role_templates.py:124` 写的是"失败后重试还是换做法，都由你决定"。但 `:168-169` 又写明材料只给"每个还没有做法的目标"。桌面产品没有种子做法库，库里的做法全是规划器为某个目标提的。所以对已细化的目标，`REPLACE_METHOD` 实际上没有可换的东西。这个"判断"名义上交给了 LLM，事实却没有交过去。
- 这和 P2.3j 修过的缺陷是同一个形状（`T/test_root_review_repair_library.py` 文件头）：修复轮只给"没人细化过的目标"列材料。P2.3j 当时补了做法库和适用性，10-01 片 A 第 4 项新加的提议材料又只给了开放目标。
- 子代理有两点说法要更正：
  - "同一目标类型的提议做法共用一个 id"不对。建议编号按**目标任务**取哈希（`hierarchical_dispatch.py:2667`），而且规划器可以另起编号（`SDK/orchestrator/planning_method_proposal.py:57-68` 的提示里写着"或者用新的 method_id"）。
  - "再提只是升版"对，但不碍事。做法实例号里包含版本号（`SDK/planning/htn/grounding.py:105-124`），换成 v2 是一个新实例，不会撞上 `plan_commits.py:1232-1246` 的"同做法同参数"拒绝。
  - "同做法同参数去换被拒"是正确的秩序检查（这样换等于什么都没换），保留。
- 准入和提交都没有拦"给已细化目标提做法"：`prepare_method`（`planning_method_proposal.py:114-147`）不查目标是否开放；`decision_admission.py:1180` 对 `ProposeMethodDecision` 也没有额外规则。缺的只是材料和说明。

**最小产品改动**（只描述，不实现）
1. `planner_views.py:205-208`：发材料的条件由"目标在 `open_goals` 里"改成"在 `open_goals` 里，**或者**它的 `under_repair` 为真"。可以直接用 `repair_goal_occurrences`，`method_applicability` 已经在用它。
2. 提示词 `role_templates.py`：
   - `:168-169` 改成"为每个还没有做法的目标，以及 under_repair 的目标，给出写新做法的材料"；
   - `:197-199` 的 REPLACE_METHOD 补一句"替换的做法可以是库里别的做法，也可以先用 PROPOSE_METHOD 为这个目标提一个，审阅通过后再换"；
   - 版本号 v17 升到 v18，不留旧版。
   - 核实过的部分：规划器模板版本只在 `event_handler.py:4399` 取用，没有进部署组装。改之前再确认一次它不在执行池身份里，避免重演 09-26 的教训。
3. 准入、提交、做法库都不用改。每个目标最多提 3 次的上限（`planning_method_proposal.py:28`）照旧把关，修复轮提的也算在内。

**两条测试怎么办**
- `T/test_h1i_deferred_repair_resume.py`：**不删**。它钉的是"执行中延后的换做法决定，冷启动后不再调模型、本地续上"（`SDK/orchestrator/planning_repair_continuations.py`）。这条机制在产品上是真的：执行图绑定后，换做法遇到在跑的工作会延后，见 `decision_admission.py:1549`。
  - 落地：先写一个金丝雀，用严格预期失败：在产品同形世界里，让一步失败、审阅退回，断言修复轮的包里有这个目标的 `method_proposal_contexts`。产品改完它转为通过。
  - 然后把 h1i 这条重写为：在产品同形世界里，规划器为被修复目标提 v2，审阅通过，在叶子还在跑时发 `REPLACE_METHOD`，决定被延后；冷重开以后不调模型续上。
  - 不要转去代码领域世界借种子里的替代做法（`code.fix-by-revert`）来绕开。那样测的是产品进不去的入口。
- `T/test_root_review_repair_library.py`：
  - `retire_and_refine_replaces_the_root_method_in_one_revision` 的删除**暂缓**，等 h1i 重写落地再删（分诊表 259 行的前提是 h1i 那条能覆盖它）。
  - 同文件"替换要等退役叶子的未结尝试"那条，原来断言的是提交侧的 `RUNNING_WORK_UNRESOLVED`。这个码只在"没有执行图"那一支（`SDK/orchestrator/planning_admission_commits.py:257-258`）。执行图绑定后，产品走的是延后路径，见 A3。所以它不单独重写，并入 h1i 重写，断言延后和续上。

- 理由一：替身原则。用例靠 `insert_task(status=CANCELLED)` 加手插 RUNNING 尝试造出"已取消步骤上还有活跃尝试"。产品没有命令能造出这个状态：撤销执行权只撤销、不取消尝试，见 `SDK/orchestrator/plan_commits.py:971-981`。这属于①b2。

- 落地：
  - 删除，记偏离（O10 无覆盖。理由：状态造不出，读取器本来就不过滤）。
  - `planning_admission_commits.py:211-215`（`operation_gate`）和 `:257-258` 两处 `taskgraph is None` 分支是删除批二"48 处统一成必须已绑定"的漏网残留。先用金丝雀核实"检查函数从不在 `taskgraph=None` 下运行"，成立就删，列入孤儿核查。

## B1　`test_evidence_recheck`

**现状**：前两条还建在旧的 `AssuredRuntime`（接缝脚本夹具）上：
- 手插观察记录（`_add_observation`）；
- 收尾那条把 `_root_resolution`、`_drain_decision` 换成了 lambda。

第三条已迁到产品世界，但把 `closeout_stale_findings` 换成了一个伪造的发现。

**裁决：按内容拆开，不整条删，也不整条等。**

1. **"无关变化仍有效"和"读过的对象被改坏 → 过期并点名"**：现在就在产品同形世界写。
   - 跑主循环到叶子被接受；后面还有一步，执行者挂住。
   - 产品自己会产生无关写入，不用手写事件。
   - 再用 SQL 改坏 `review_records` 的字节，这是①b1，允许。然后直接调读侧的 `changed_items`（`SDK/orchestrator/assurance_recheck.py:45`）或有效性消费者的观察函数，断言 `REF_BODY_CONFLICT` 点名的就是那条记录。
2. **"验收公式读的观察表变了 → 过期"**：产品世界没有观察器，观察表没有写入方，手插就是①b2。这部分**等带观察器的测试世界**，并入分诊裁决⑥"前提 / 观测"的那 1 个参数化主循环用例，不在本文件里单写。
3. **"收尾遇到依据已变就不放行，规划器处理过就放行"**：不许再替换 `_root_resolution`/`_drain_decision`。
   - 子代理说"根结论到收尾在同一轮完成，没有插手窗口"。真实窗口其实有一个：**根终审员的模型调用**。可以用脚本化提供方挂住终审调用，在挂住期间做①b1 的字节改坏，再放行。这模拟的是"模型调用期间磁盘被改"，属于外界真会发生的事。
   - 放行后，如果产品走到"收尾 NOT_READY + EVIDENCE_STALE → 下一轮记证据失效请求 → 规划器被叫到"，这一条就把第三条也覆盖了。
   - 如果根结论在提交时就因为证据过期被拒、走不到收尾，那就以产品实际怎么处理为准写断言，并转到下面的疑似缺陷核查。
4. **已迁那条（补丁伪造发现）**：**违反替身原则**。`closeout_stale_findings` 是产品内部读出的结果，不是外界事件。伪造它等于在产品世界里测一条产品自己不会给的输入。
   - 第 3 点的真实路径写好以后，并入并删掉这条。
   - 在那之前，如果要留，就改名、改文档串，挪到"纯函数（E）"类里，明说它测的只是"发现 → 修复请求"这一层翻译。不许挂着"产品同形"的名义。

**疑似缺陷：改坏已验收的审阅记录后，既不终审也不修复。值得核实。**
- 疑点：证据失效的修复请求**只**从收尾评估写下的那一行来，见 `planning_repair_requests.py:100-118`（`stale_evidence_triggers`）和 `assurance_recheck.py:129-138`（`closeout_stale_findings` 只读 `assurance_closeouts` 表）。而收尾评估要等根结论出来才跑。如果叶子证据在根终审之前就失效：有效性消费者（`SDK/orchestrator/assurance_consumers.py:154`）记了"来源已变"、停了派发，根终审因此出不来，收尾也就不跑，规划器可能永远收不到这个事实。
- 按"如实把事实交给 LLM"，这是潜在的活性缺口，可能卡住，也可能静默结束。
- 核实方法（主会话做，一次性，不留成测试；或者直接写成第 1 点的延伸用例）：
  1. 产品同形世界，两步计划（同 `test_h1i_wait_lifecycle` 的 first/second）。first 被接受、second 的执行者挂住后，用 SQL 改坏 first 那条已验收审阅记录的字节。
  2. 放行 second，跑主循环，设轮数上限和超时（例如 50 轮 / 60 秒），配上看门狗。
  3. 收集事件，看有没有出现以下任何一种：
     - (a) `PlanningRepairRequested`，`trigger_source` 是证据失效或"没有可派发的工作"，而且请求里列出了这条过期原因；
     - (b) 规划器随后被叫到；
     - (c) 任务以具名停止原因结束。
  4. 判定：
     - 三种都没有，并且 run() 空转或返回、任务也没结束：**缺陷成立**；
     - 只有 (c) 而规划器从没被叫到：**也算缺陷**，事实没交给 LLM；
     - 规划器拿到了"没有可派发的工作"请求，里面写明了过期的原因：**不算缺陷**，只是路径绕一点。
  5. 卡住时按惯例先看后台 CPU 和调用栈。
- 如果缺陷成立，修复方向（只描述）：让有效性消费者判出"过期"这件事，和收尾判出的走**同一条**证据失效请求路径。也就是让 `stale_evidence_triggers` 的来源不只是收尾那一行。不要另加一条"遇到过期就自动做什么"的规则。

## B2　跨租户读：部分认可

## B4　计划提交时库写入出错：该改，不在本阶段

- 现状：`T/taskgraph_exec/test_commit_atomicity.py:35-76` 用触发器在真实事务里注入写入失败。断言了两件事：异常从 `world.step()` 一路抛出；什么都没写进去。
  - 后一件是这条用例的价值所在（原子性），要保留。
  - 前一件钉的是"错误逃出主循环这一轮、run() 中止"。
- 判断：
  - 库写入失败（磁盘满、数据库被锁、I/O 错误）是基础设施故障，不是模型做错，和 09-28 用户决定"服务端报错、重启打断不计次数、原地重试"是同一类。
  - 重试、超时、恢复属于 Harness 职责（核心思想第 3 条）。
  - 桌面上 run() 一停，整个编排服务都停了，连带别的任务一起停。这也违反"按任务隔离、具名拒绝不影响别的任务"（`commit_service.py:1531-1534` 的注释正是这个意思）。
- 建议的行为（只描述）：
  - 在每个任务一轮的边界上，接住这类错误。事务已经整体回滚。
  - 另开一个事务记一条基础设施失败事件，不计入规划次数。
  - 下一轮用已冻结的原始回复原地重做收集，不再调模型；`planning_repair_continuations` 已经有"凭冻结字节本地续上"的机制可以复用。
  - 同一处连续失败设上限（参照 `NON_MODEL_FAILURE_CAP`），到了上限就以具名原因停这个任务。
  - 约束违反类错误（`IntegrityError`）多半是代码缺陷，重试没有用，但上限会兜住，不必单独分支。
- 归属：这是行为改动，不属于"迁测试 + 删旧路"。**A′ 不做**，列为后续项，和"基础设施故障原地重试"一族放在一起。A′ 里这条用例：
  - 原子性断言照旧；
  - `pytest.raises` 那段加注释："错误逃出本轮是现状，待后续改为原地重试"；
  - 不要再新增依赖"run() 中止"的断言。

## B5　每轮约 1.5 秒纯 CPU：严重度高，A′ 之后立刻做

- 原因核实：
  - `SDK/storage/taskgraph_store.py:263-277` 的 `read_revision` 每次都把整条祖先链重读、重验（`:279-293`）；
  - 缓存键是全库的 `read_generation`，库里任何地方写一行都会让它失效；
  - 主循环每轮都会写库，所以缓存几乎永远不命中。
  - 每轮成本随计划版本数线性增长。修复越多，任务越慢。
- 严重度：桌面上任务进行期间，一个核会长时间接近满载，并且越跑越重。用户 09-28 对"CPU 满载"的口径是"现在就修"。它不影响正确性，所以不阻断 A′ 的迁移提交；但要排在 **A′ 合并之后、下一次真机运行或发版之前**。
- 修复方向（只描述）：
  1. 历史版本写入后不可变，缓存键改为"任务 + 版本号 + 清单哈希"，不再用全库的写入计数。失效条件只看执行图版本相关的几张表有没有变：可以给这几张表单独维护一个计数，或者在每轮开头比一次这几张表的行数加最大行号。这样仍然能发现对这几张表的篡改（①b1 的读侧检查不丢），又不会因为无关写入重验。
  2. 祖先链按增量验证：验第 n 版只需要第 n 版的记录，加上已经验过的第 n−1 版的哈希。不必每次走到第 1 版。
  3. 执行图通知每轮核对计划版本时，先比当前版本号和快照哈希，只有变了才读历史。
  4. 修完用一个金丝雀量化：计划第 1、2、5 版时每轮的 CPU 时间，作为回归门槛。
- 顺带：`_pending_planning_wait`（`event_handler.py:2896`）每次调用都遍历这个任务的全部事件，也是随任务变长而变慢的热点，可以一起看。不在本裁决范围。

## C1　同一做法只有最新版本可取（`registry.py` `retrievable`）：是

- 理由：
  - 准入时的做法库本来就是"一个编号一条"（`SDK/planning/decision_admission.py:1223`，`{view.method_id: view}`）。包里同时列出旧版本，规划器一引用就吃 `METHOD_STALE`，这是包和准入对"当前定义"口径不一致。
  - 改在 `retrievable` 这一个地方，编译（`compiler.py:272`）、候选、规划包、提议材料都走它，同一件事只有一条路径。
  - 判断的是"哪个是当前定义"，属于秩序，不是语义。
- 和 A1 的配合：给被修复目标提了 v2 以后，v1 就从库里消失。这没有问题：v1 已经被采用，再采用一次本来就会被同做法同参数拒绝。v2 被审阅打回时，规划器还能提 v3，上限 3 次。
- 不阻断的收紧建议：
  - 现在只要库里存在任何更高版本，旧版本就会被隐藏，不管那个高版本对本任务是否可取，比如它属于别的任务的试用范围，或者状态是不可检索的。
  - 桌面产品不会碰到：提议编号按目标任务取哈希，不跨任务。但代码领域等种子库可能碰到"新版被吊销、旧版也被藏起来、结果一个都没有"。
  - 建议把条件改成"存在一个**对本任务按状态可取**的更高版本"。等代码领域测试世界写好时顺手改，不急。
- 剩余风险（低）：
  - 已延后的换做法决定，如果在续上之前替换做法又升了版，编译会以"不可取"拒绝它。这是正确的过期判定，但要确认续上失败后会回到规划器，不会静默挂起。
  - h1i 重写时可以顺带覆盖一档。

## C2　后继步骤参数不再要求必填字段齐全：是，不要反过来统一

- 理由：
  - 后继步骤接替的是计划里已有的一步，它要守的合同就是那一步当初被接受时的合同。做法步骤的参数可以省略必填字段（种子库普遍这样写），后继却要求齐全，规划器就**不可能**照原样写出一个合法的后继。这是检查口径不一致，不是规划器的错。
  - 反过来统一成"都要求齐全"，种子做法库（AppWorld、代码等）会大面积在注册或落地时被拒，还会逼规划器给每一步都填满参数。这是在用规则替代判断，而且是一次与 A′ 无关的大改动。不做。
- 要改的一处事实：新注释说"与做法步骤参数同一规则：不许未声明字段、不许类型错"（`SDK/planning/htn/graph_repair.py:328-330`）。这和代码不符：
  - 做法步骤的参数**根本没有**按步骤类型的参数结构检查。落地时直接 `typed_parameters=dict(plan.arguments)`（`SDK/planning/htn/grounding.py:791`）。
  - 注册时只检查"参数引用的是做法声明过的参数"和端口（`registry.py:1593-1610`、`:1917-1935`）。
  - 所以现在后继反而比做法步骤严：它查未声明字段和类型错。这本身是合理的秩序检查，因为后继参数是模型直接写的字面值。但注释要改成实话："只查未声明字段和类型错；必填字段可以省略，和做法步骤一致"。
- 后续（不在 A′）：
  - 把"步骤参数按步骤类型结构检查"收成**一个**函数，做法步骤落地和后继共用（同一件事一条路径）。
  - 收之前先在种子库上跑一遍，看对做法步骤加上"未声明字段 / 类型错"会拒掉多少。
  - 同时定一下步骤类型结构里"必填"的含义：要么从上级继承，要么在世界定义里改成非必填。别让规划包里显示一个任何地方都不执行的"必填"。
