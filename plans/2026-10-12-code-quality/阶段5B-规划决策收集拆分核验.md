## 核验过程摘要

1. **把抽出的方法内联回去，再比较语法树。**
   - 脚本把各方法的方法体代回调用处。
   - 脚本把 `reply.X` 换回局部名，把 `return None` 换回 `return`。
   - 脚本把预览方法和读源方法的返回值，按调用处的解包顺序还原。
   - 然后对原函数和还原后的函数各做一次 `ast.unparse`，再逐行比较。
   - 剩下的差异只有下面 5 类，都不改变行为：
     - 别名 `record_decision` 换成 `store.record_planning_decision`（同一个对象上的同一个方法）。
     - 别名 `reject_planning` 换成 `self._planning_rejected`。
     - 删了一句纯注解 `codes: Sequence[str]`。
     - 新增两句初始化：`preview_command = None`、`source_principal = None`。
     - 预览被拒的两条路径多出一个不会执行到的 `return`（内联时产生的痕迹）。
   - 每个调用处都按同名关键字传参，没有出现换名代入。
2. **进度闭包改成方法 `_record_decision_progress`。**
   - 方法体与原闭包逐句相同，只差别名。
   - DECODED 和 ADMITTED 两次调用不满足 `status is COMPILED`，条件短路，不读预览三项。原代码也是这样。
   - COMPILED 时，只有预览走通，`planning_commit_admission` 才不是 None。预览走通时，`preview_command` 和 `source_principal` 已经赋值。所以传入的值和原闭包读到的值相同。
   - 三项都先初始化为 None，所以调用时求值不会报 UnboundLocalError。
3. **评估闭包 `evaluated`。**
   - 闭包仍定义在 `_collect_plan_decision` 里，每次调用时读 `canonical_hash`、`decoded_subject_key`、`autofilled` 的当前值。
   - 解码段（try 块）没有抽出去，所以闭包能读到解码后更新的值。`autofilled` 是同一个列表，原地修改。
   - `_record_decision_evaluated` 的方法体与原闭包逐句相同。参数用 `/` 标为仅位置参数，所以 payload 里的同名键不会冲突。
4. **模块级 `_commit_rejection_code`。** 去掉文档字符串后，语法树与原闭包相同。
5. **async/await。**
   - 脚本逐个检查对 `self.<本类方法>` 的调用。
   - 异步方法都带 await，同步方法都不带。
   - 所有被抽成同步方法的段，原来都没有 await。
6. **局部变量未赋值的风险。**
   - 脚本找出各新方法里"没作为参数传入、也没在方法内赋值、但在原函数里是局部变量"的名字。结果为空。
   - ruff F821（未定义名字）检查通过。
   - ContractError 解码分支没有抽出，它仍靠 `canonical_hash is not None` 短路，不读 `decision` 和 `canonical_json`。
7. **顺序。**
   - 写数据库、追加事件、结算意图、拒绝回调的先后顺序，与原代码逐句一致。
   - 事务块的边界没有变。
   - 共享秩序被拒和读不懂回复这两段，新代码仍在 except 块里调用，所以异常链不变。
   - 收敛任务没就绪时，原代码在事务块里提前 return。新代码是方法 return 后，调用处再 return，效果相同。
8. **解包顺序。**
   - `_PlanningPreview` 的字段顺序是：context、planning_commit_admission、preview_candidate、preview_command、source_principal。构造和解包都用这个顺序。
   - `_read_preview_sources` 返回 5 项：context、frozen_inputs、runtime_work、source_principal、taskgraph_sources。调用处按同样顺序解包。
9. **其他检查。**
   - 新加的方法名和类名，在 SDK 和 Host 里都没有同名定义，混入类的方法解析顺序不会冲突。
   - 测试里没有绕过真实编排器去调用这个函数的替身。
   - 别名改成调用时取值以后，只有运行中途换掉 `_planning_rejected` 或 `record_planning_decision` 才会有差别。现有测试都在运行前打补丁，所以没有影响。
   - 模块能正常导入。`PlanningReply` 带 `__slots__`，`_PlanningPreview` 的字段正确。
   - 部署清单里本文件的哈希（65c9ed24…）与当前文件一致。
