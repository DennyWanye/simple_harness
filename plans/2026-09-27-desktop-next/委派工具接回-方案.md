# 委派工具接回主对话（NEXT-TG-1.0 §9「委派工具」，收口第 4 项）一页方案

日期：2026-09-29｜作者：Claude｜状态：第 1 版经独立审阅（opus）发现 5 条阻断，已按下文"第 2 版修订"改定，照第 2 版实施

## 现状（调研结论，证据见本会话调研记录）

- 主对话（前台 Run）完全跑在 SDK kernel 上。`main.py::_build_product_sdk_runtime_stack` 只注册一个根 profile：`agent.general`，驱动 react。
- SDK 本身有完整的子运行链路：`uow.issue_profile_launch_ticket` 签发凭证 → `runtime.children.launch(ChildLaunchRequest)`，在同一事务里写入子 Run、启动快照、父子链接 → 子运行结束写终态，结果用 `read_child_terminal_result_for_run` 读回。
- Host 这一侧**一环都没接**：没有签发凭证，没有给子运行准备授权与预算，没有启动。`await_subagents` 拿到的 join 端口是 WorkflowService，而它根本没有这个方法。四个委派工具 + `await_subagents` 已于 09-28 从模型可见目录下架。
- 旧 harness 版本的 `build_subagent_batch_delegate` 依赖旧运行时的事件与上下文，不能直接用。能复用的只有 `normalize_delegation`（四种参数形状 → 一段委派文本 + 要求的工具 + 是否分离）和"按任务内容生成确定 ID"。

## 做法（只接线，不改任何已发布工具说明）

1. **一个 Host 委派服务**（新文件 `deskpet/sdk_adapters/delegation.py`）。在装配时通过闭包拿到：`uow`、`tool_authorities`、`provider_binding_resolver`、`_sdk_ingress.require_ready().runtime`。不在 TaskGraph 之外另建业务图；需要长期后台执行、要验收或有外部效果的活，仍然走 `mission_start`。
2. **子运行一律 DETACHED**。父 Run 此时正在一次工具调用里，ATTACHED 会把父 Run 改成 waiting，与 react 驱动冲突。
   - `agent`、`agent_parallel`、`spawn_team`：启动后在工具调用内等子运行结束，把结果当工具返回值。等待受父运行的墙钟与工具调用时限约束。
   - `spawn_subagents`：立即返回子运行 ID；结果由 `await_subagents` 收回。
3. **确定 ID、可重放**：凭证、命令、子运行 ID 由"父 run_id + 工具调用 ID"派生。同一调用重放时接上已有子运行，不会启动第二个（SDK 凭证与命令本身幂等）。
4. **授权交集**：子运行的工具目录 = 父运行本次冻结目录 ∩ 请求的 tools − 全部委派工具（防止递归委派）。通过 `tool_authorities.prepare_run` 按父 root_run_id 为子运行冻结一份授权。子运行继承父运行的项目/工作区绑定；未绑定项目的父运行调用委派，按原规则具名拒绝。
5. **预算**：用 `provider_binding_resolver.create_binding` 给子运行单独生成绑定，provider 与目录版本沿用父运行；上限取父运行的有效上限（先不做更细的拆分）。子运行结束时对它的授权和预算绑定执行 `mark_terminal`，与根运行 `finally` 里的做法一致。
6. **子运行的输出不进主会话视图**：给子运行登记一个"静默"的投递适配器，只收集文本和终态，不推给界面；界面在父运行的这次工具调用上显示"委派中 / 已完成"。
7. **回收**：`await_subagents` 先按父子链接（run_links）确认子运行属于当前父运行，再读终态结果，返回 `{run_id, status, value, error}`（沿用旧返回形状）。
8. **可见性**：只把真正接通的工具从 `UNWIRED_DELEGATION_TOOL_NAMES` 里移除，其余继续隐藏，保证"模型可见 = 可执行"。

## 测试（先写失败的）

- **服务层**：在真实 SDK kernel（最小 react profile + 脚本化模型）上，`spawn_subagents` 启动 DETACHED 子运行 → `await_subagents` 拿回结果。同一调用重放不启动第二个。子运行请求父目录之外的工具或委派工具时被拒。别的父运行拿不到这个子运行。
- **Host 目录**：接通的工具出现在模型可见目录，未接通的不出现；工具说明哈希不变。
- **真机**：主对话里让模型"用 agent 委派一个小任务"，子运行完成，主对话收到结果（开发模式控制通道，或获授权后点击）。

## 风险与处理

- **冻结目录指纹会变**：可见工具集合变了，已有会话恢复时会拿到新目录版本。开发期不做旧数据兼容，但要实测已有数据目录能启动。
- **重启恢复**：子快照里必须带齐 `run_binding` 和 `tool_authority`，启动时的 `ports_factory` 才能把可恢复的子运行扫进来。父运行卡在同步等待时被重启，这次工具调用结果按"不明"处理，由 SDK 已有的对账流程判定，不重复启动子运行。
- **规模**：本项预计是收口中最大的一块。若中途发现 kernel 缺必要接口（比如签发只能走 UoW 私有方法），先记录为 SDK 需补的公开接口，再决定走 SDK 小版本补齐还是在 Host 用受限适配层实现。

## 第 2 版修订（独立审阅 5 条阻断 + 注意点，2026-09-29）

| # | 阻断 | 改法（照此实施） |
|---|---|---|
| 1 | 子运行终态只有 `status/result(response_present, finish_reason)`，回答正文在 `conversation_output`；按终态结果读，`value` 恒为空 | 终态结果只用来判断状态；正文照根运行的做法，从子运行的上下文读最后一条 assistant 消息（`_sdk_context_port.load`，参照 `main.py` 恢复监视器） |
| 2 | 子运行快照带着 `run_binding`，重启时会被当成主对话运行：建界面投递、改写 `_sdk_run_ids_by_root`（主对话点"停止"会取消到子运行）、恢复监视器把子运行回答写进主会话；用量投影要么卡住（缺字段），要么把子运行用量记成主会话的上下文用量 | 子运行 `context_metadata` 加 `run_kind="delegated_child"` 和 `parent_run_id`。恢复时，子运行只恢复授权与预算绑定，交给委派服务接管，跳过投递路由、根映射和恢复监视器。投影时，子运行只记调用与费用，不写上下文用量样本 |
| 3 | Host 工具对账没有 observer，执行中途不明的调用永远判"仍不明"；父运行同步等待时被重启会永久卡住 | 给工具对账加委派专用 observer，按"父 run_id + 调用 ID"推出子运行：子运行不存在 → 确认未开始、可重发（幂等）；已结束 → 已完成，结果同正常路径；仍在跑 → 仍不明。`spawn_subagents` 只要子运行存在，就判已完成并返回 ID |
| 4 | 取消不往下传；`mark_terminal` 放在工具调用里，工具一返回就没人清理，授权和模型绑定一直占着（会拦住修改模型设置），子运行继续花钱 | 委派服务按父运行登记子运行，每个子运行一个后台监视器，结束时负责 `mark_terminal` 和清理。以下时机主动取消未结束的子运行：父运行取消、工具调用被取消、同步等待超时、父运行结束时还有没收回的子运行。每个父运行最多 8 个子运行 |
| 5 | 子运行要人确认时，界面看不到，父运行一直等到超时 | 第一版子运行目录去掉所有需要确认的工具（`confirm_only_tool_names`） |

注意点（照做）：
- 子运行不必单独注册 profile；凭证 profile_key 与启动载荷一致即可，驱动为 `react`。目录代次和指纹沿用父运行，用 `capability_snapshot.tools` 取子集，不另算子集指纹。快照不带 conversation 或上下文阶段字段。
- 重放顺序：先 `read_run(child_id)`，存在就接上，不再签发凭证。快照要能确定复现：不放时间戳，模型绑定从父运行已冻结的绑定推出。
- 同步等待的时长，按父运行剩余的墙钟时间封顶。
- 写文件类工具的效果门按子运行 ID 查路由回执，父运行的回执它用不了。**第一版子运行只开放不产生项目效果的工具**（读、搜、网页等），写文件类工具先不开放，并在工具返回里说明。
- 测试必须至少有一条走真实 Host 组装，并覆盖一次重启恢复，否则上面第 1～3 条暴露不出来。

## 实施记录（2026-09-29，照第 2 版实施，下面是与方案不同或补充的地方）

代码：`backend/deskpet/sdk_adapters/delegation.py`（委派服务）；`spawn_subagents_tool.py` 处理器改调服务；`tool_catalog/providers.py` 依赖加委派服务；`sdk_adapters/tools.py` 五个委派工具放进"无项目也可用"名单；`main.py` 组装服务、工具对账挂委派观察、启动恢复区分子运行。

| 项 | 实际做法 | 原因 |
|---|---|---|
| 一次调用几个子运行 | 每个委派任务一个子运行（`agent` 1 个，`agent_parallel`/`spawn_subagents`/`spawn_team` 按任务数，最多 8） | 真正并行；每个父运行累计最多 8 个 |
| 子运行能用的工具 | **明确白名单**：网页检索/抓取、读文件与搜索、文档读取、图片识字、工作区回忆、金价查询；再与父目录、请求的工具取交集，去掉需要确认的 | 独立审阅第 1 轮阻断 2：按"只读"类别推断会放进改主对话待办、写文件（下载/生图）、登记产物、弹选择器的工具 |
| 整批核对 | 一次调用里所有任务的工具请求先全部核对，全过才启动 | 审阅次级 4：避免"报拒绝但其实启动了一半" |
| 子运行用量 | 元数据"有效上限"置 0：模型调用照常记账，不写主会话上下文用量样本，投影代码不用改 | 真机核对：4 次调用全记、上下文样本只有主对话 3 条 |
| 无项目对话 | 可以委派（子运行继承无项目绑定，只拿父目录里的查询类工具） | 主对话大多是无项目的；委派本身不碰工作区 |
| 重启时的对账 | **从不判"确认未开始"**。子运行还在跑 → 仍不明（父运行挂起），接管的监视器在子运行结束时替父运行写"已完成 + 子运行结论"，再请内核唤醒；子运行没来得及启动 → 判"已完成、失败"，提示模型需要的话再调一次 | 真机第 3 轮：判"确认未开始"让 SDK 重放调用，而重放会重新签发授权票据，Host 授权记录按"同一调用、不同授权编号"判冲突，父运行失败。这是 Host 授权记录的通用缺口（任何工具重启后重放都会撞），另记欠项 |
| 挂起的父运行 | 启动恢复名单加入"卡在委派调用上的等待运行"，先恢复它们的模型绑定与工具授权；运行时就绪后扫一遍这类父运行并结算 | 真机第 2 轮：唤醒后因绑定没恢复而失败（与已有的"卡在模型调用上的等待运行"同理） |
| 关闭应用 | 中断的等待不取消子运行；父运行授权被释放但父运行没结束时也不取消（只有父运行真的结束/被取消才取消子运行） | 真机第 2 轮：关机时去取消子运行，取到已关闭的运行时而报错 |
| 监视器 | 读失败重试，只有读到终态才收尾；后台任务保留引用 | 审阅次级 3 |
| 去掉的东西 | 子运行结束后"触发对账"的回调 | 审阅阻断 1：那个触发点指向的对象没有这个方法，是空转 |
