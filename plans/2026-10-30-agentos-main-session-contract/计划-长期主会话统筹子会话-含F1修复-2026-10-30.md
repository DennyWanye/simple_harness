# 计划：长期主会话统筹多个子会话（含紧急缺陷 F1 修复）

日期：2026-10-30。基线：SDK `0.13.0.dev20260925+opt.222`（源码提交 `47fd34f0`）。
需求方：AgentOS（合同 v1.0）、AIPhone（统一交接）。两家原文与前两份调研在同目录。
方法：先回答"更深而不是更大"的四个问题，再把任务改写成正好要的那些，再排阶段。

## 0. 一句话

一个长期主会话，开多个长期子会话，子会话用现有 Mission/HTN/TaskGraph 干重活，结果自动回主会话，停止、取消、重启、换代都不丢身份。
**第一步不是加功能，是先修"点一次停止回答，会话就报废"。** 这条不修，"长期"两个字不成立。

> 在 opt.222 上，分五个阶段交付：

## 3. 阶段计划

### 阶段 0：F1 紧急修复 → opt.223（单独发版）

**范围**：只改执行者复用判断与回执，不碰编排、不碰池身份、不碰提示词。

**改动点**

1. `host/chat.py` 的 `_given_up`：加第三种情况——执行者开着、没有开着的回合、但它的预算快照 `has_unknown_charge` 为真 → 放弃，换下一代。旧执行者与它的不明费用记录原样留在执行库。
2. `host/session_chat.py` 的 `_agent`：只在"原执行者已提交该回合结果"时复用；新输入一律走父类判断（现状如此，加测试钉住）。
3. 回执：换代回合带 `history_reset=true`（opt.204 已有字段）与新字段 `executor_replaced_reason="unknown_charge_after_cancel"`，让宿主能诊断。
4. `Session.interrupt()` 文档写清：只停当前回合；之后同会话新 key 可继续；旧 key 不重放已交出去的请求。

**测试（先红后绿）**

| 测试 | 做法 | 期望 |
|---|---|---|
| 复现 | 假线路 `held`，回合进入线路后 `interrupt()`，线路永不 `release`（或 release 后报取消）；再发新 key | 修前：`react_cost_exceeded`、`model_calls=0`。修后：新 key 正常回答 |
| 不明费用不清零 | 修后查旧执行者的预算快照 | `has_unknown_charge` 仍为真；新执行者为假 |
| 不重放 | 旧 key 重试 | 返回原 failed 回执，线路没有第二次请求 |
| 重启 | 取消后关宿主再开，新 key | 仍能继续；代次 +1 只发生一次 |
| 委派在跑时取消主回答 | 先委派，再取消一条普通回答 | 任务不受影响，结果照常回收件箱 |
| 五个取消时机 | provider 接纳前 / 接纳后 / 文本流中 / 工具前 / 工具后 | 每个时机之后新 key 都能继续；用量不明的只有"接纳后"与"流中" |

**裁判**：仓库内测试矩阵；变异测试杀掉"去掉第三种情况"的变异；独立审阅；AIPhone 真机复验（他们的"必需复验"清单）。

**交付**：opt.223 轮子 + SHA256SUMS + 一页说明（现象、根因、改法、复验清单）。新根要求照旧。

3. `Session._command(command_id, kind, body, apply)` 统一写入口。

### 阶段 2：异步统筹（合同 M2；SDK-02 / 05 / 06 / 12；AIPhone A02 / A03 / A07 / A10 / A14）

**改动点**

1. `delegation.py`：委派到子会话时行写在子账本，子账本"一个在途"即每工作会话一个；主会话按 Goal 内并发上限（默认 2，可配）。宿主总容量仍由并发门管。
2. `send(..., wait=False)`：持久受理即返回 `accepted` 与 `input_id`；回合在驱动里跑；结果从 `events()` / `task()` 查。同会话串行，主与子互不阻塞。
3. 子会话排队输入处理：当前 Mission 终态后，排队输入作为子会话下一回合；终态后的新委派通过该 `input_id` 建唯一关联。
4. **结果驱动续办**：子结果镜像进父 inbox 后，先记 `result_received`；问宿主 `ContinuationPolicy`（默认实现：enqueue，只汇总）；`enqueue` 则生成一条 kind=`result_event` 的持久输入（冻结 event_id 集合，幂等键由集合派生），走 `send` 的串行锁；`hold` 只留待办；`deny` 记原因。处理完记 `result_applied`。`ack` 仍是人已读。
5. 合并窗口与预算：每 Goal 的续办模型调用、轮次、工具调用、时间、并发上限；合并窗口可配；用尽进可见等待，不重试；队列空不唤醒。
6. **语音期间路由（I12）**：有语音绑定时，续办不起文字回合，改走 `VoiceBinding._schedule` 的播报接缝，来源标 `task_result`；用户在说话或有当前播报时等安全窗口，超过最大等待记"忙时排队"事件。
7. 续办输入进模型时的来源标记与 F3 相关：标为资料，不是用户发言；语音侧不得把它记成 ASR 输入。

**故障注入边界**：子结果镜像前后、续办入队前后、续办回合提交前后、合并窗口中途崩溃、两子结果与用户输入同时到。

**测试**：容量 2 两任务真并行 + 主消息可受理（SDK-02）；子结果落库后父消费前崩溃、重复/乱序投递只形成一个续办输入（SDK-05 / I11）；两子结果与用户改 Goal 同时提交（SDK-06）；预算用尽、无新事件时模型调用数不增长（SDK-12）；语音绑定不 detach 时后台结果在最大等待内播报、不并启文字回合（A14）。

### 阶段 3：恢复与安全收口（合同 M3；SDK-08 / 09 / 10 / 11 / 13 / 14 / 15；AIPhone A04 / A06 / A08 / A11 / A12 / A13）

1. **授权回调** `AuthorizationPort`：命令受理、派发、每个连接器效果前各调一次；异常或超时等于不允许；可缓存但撤销要生效；`auto_mode` 作默认实现。
2. **取消范围** `cancel(target_kind=goal|delegation|session_tree)`：屏障前已交接的效果标已交接/完成/未知；迟到结果可审计，不触发已取消 Goal 的续办。停主回答、停子回答、取消 Mission、归档子会话四者行为不同且可查（A06）。
3. **owner 代次**：对外暴露 `owner_generation`；第二实例公开入口报 `owner_conflict`。
4. **关闭**：有未终态委派或未消费结果报 `active_work`；`archive` 另加。
5. **恢复报告** `RecoveryReport`。
6. **压缩断言**：关系、授权版本、回执在压缩前后 hash 一致；历史超 50 条后换代仍能回读早期约束（A12）。
7. **Goal**：`put_goal / finish_goal`，收口只核结构事实（委派全终态、无未应用结果、无待答），好坏交审阅员。

## 8. 工具层（2026-10-30 晚用户定：主会话也要有完整工具层，接入方可往主会话加工具）

### 8.1 现状

| 块 | 有什么 | 给谁 |
|---|---|---|
| 内置工具 | 工作区读/写/列、知识列/读、跑测试（沙箱可用时）、历史回读 | 只给任务池；主会话一个都没有 |
| 技能 | `skill_discover / skill_load / skill_execute`；脚本技能只跑 Python，在沙箱里 | 任务池 |
| 应用工具 | `DomainTool`，只读，宿主启动时注册，SDK 注入调用身份 | 任务池与主会话 |
| 连接器 | 有副作用的操作；申请单 → 审阅 → 审批 → 执行 → 回执核对 | 只在任务里 |

没有命令行工具。工具名单按任务冻结；工具说明文字是池身份。

### 8.2 原则调整（用户 2026-10-30 定）

旧：主会话只读，有副作用的事一律委派。
新：**主会话有完整工具层，可以做小而简单的事；需要时间、多步骤、要审阅的才委派。** 副作用仍只有一条路：连接器 + 授权。主会话调副作用工具，就是连接器的另一个调用方，不另开路径。

### 8.3 设计

**一个工具目录，四种来源，按角色给可见范围。**

| 来源 | 性质 | 注册方式 | 默认可见 |
|---|---|---|---|
| SDK 内置只读 | 工作区读/列、知识读、历史回读 | 自带 | 主会话、子会话、任务 |
| SDK 内置沙箱命令行 `sandbox_run` | 在沙箱里跑命令：关网络、限时、限输出、进程树清理；复用现有执行器（macOS seatbelt / Linux bwrap） | 自带，沙箱可用时 | 任务池默认有；主会话由宿主声明开不开 |
| 应用只读工具 | `DomainTool`（现有） | `OrchestrationHost.open(tools=[...])`（现有） | 主会话、子会话、任务 |
| 应用动作工具 | 连接器的一个操作暴露成工具：`action_tool(connector, operation)`，带风险等级与 `always_needs_approval` | 注册连接器时声明哪些操作可作工具、给哪些角色 | 主会话、子会话；任务里仍走申请单 |
| 技能 | 现有三件套 | 现有 | 任务池；主会话由宿主声明 |

宿主注册时给每个工具声明 `roles=("main","child","task")` 子集。只缩不放：子会话 ⊆ 主会话声明，任务步骤 ⊆ 任务 ∩ 角色 ∩ 部署（现有规则）。

**主会话调动作工具的路径（复用连接器机制，不另造）：**

1. 模型调 `photos.move(...)`。
2. SDK 生成稳定幂等键（会话 + 回合 + 调用槽位，与委派同法），算 `params_hash`。
3. 过授权：`auto_mode` 且等级 ≤ `max_action_level` 且非 `always_needs_approval` → 直接执行；否则发 `needs_response` 卡片，回合里告诉用户"等批准"，批准后执行，结果进 inbox（与委派结果同一条回流路）。阶段 3 的 `AuthorizationPort` 接进来后，这一步改为问宿主。
4. 执行走 `connector.execute(idempotency_key=...)`，回执记成 effect（`operation_key + params_hash + receipt`），发事件。重试走 `lookup`，不重复执行。
5. 每回合工具调用上限、预算仍按会话策略。

**ToolSearch。** 池身份只冻结：元工具（`tool_search`、`tool_schema`）、核心控制命令（委派、子会话、任务查询/取消）、历史回读。其余工具进一个单独版本化的目录（目录指纹记在账本，不进池身份）。模型按需搜、拿到说明、再调。底线：只在该角色的允许名单内搜；名单仍冻结在任务/会话上；搜到的工具照样过授权。执行层要补"一个回合内加载的工具说明进下一次模型调用"（Agent 执行层已有目录代次与指纹概念）。上线前用 DeepSeek flash 真跑一局验证两步调用可用，不行就退回全量下发。

**运行期加工具不重开宿主。** 放阶段 3 之后：目录新版本对新回合/新任务生效，在途任务按旧名单，审批卡不变。

### 8.4 落到阶段

| 阶段 | 工具层内容 |
|---|---|
| 1 | 工具目录与角色可见范围；主会话补内置只读工具；`sandbox_run`（任务池默认有，主会话按声明）；ToolSearch 元工具 + 目录版本化；聊天池升 chat-v3 一次到位 |

| 4 | 文档：三种注册方式、角色声明、ToolSearch 行为、不支持项；仓库外消费者各注册一个只读工具和一个动作工具 |

### 8.5 测试与裁判

- 角色可见范围只缩不放：子会话看不到主会话没声明的工具；任务看不到角色外的工具。
- `sandbox_run`：无网络、超时被杀、输出截断可见、进程树清理；主会话未声明时不可见。
- 动作工具：幂等键稳定，重放不重复执行；`always_needs_approval` 必出卡片、批准后只执行一次；拒绝后零效果；回执进 inbox 一次。
- ToolSearch：允许名单外搜不到；搜到后同回合可调；目录换版本不改池身份（池编号不变、旧会话能开）；真实模型一局两步调用成功。
- 主会话提示词第 1 条改写：小事自己做，大事委派；用 20 条输入对照委派/直做决策，漏委派 ≤ 20%、误委派 ≤ 5%（10-25 口径）。
