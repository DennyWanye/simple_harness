### 4. `_dispute` 改成什么样、争议条目从哪些字段派生

- 现有可用字段：`Claim.status`（`ClaimStatus.DISPUTED`，`contracts/state_machines.py:99`）、`Claim.disputed_by`（`contracts/models.py:918`）、`KnowledgeRecord.disputed_by`（`memory/verified_knowledge.py`）、`Claim.key / stance / content / source_task / result_id`、`ClaimDisputed` 事件（payload 有 `claim_id`、`contradicts`、`key`、`reason`、`other_status`，commit_service 2041-2054）。`Claim.conflict_id`（920）和 `Claim.resolved_by`（919）只由冲突表那一路写，删后恒空。
- 现状的缺口：后来的那条声明 C 被定成 DISPUTED，但**它自己不记对方是谁**（只有对方 X 的 `disputed_by` 里有 C；C 指向冲突记录靠 `conflict_id`）。删冲突表后，从 C 出发找不到对方。
- **建议**：`_dispute` 里给 C 也写 `disputed_by=(…, X.id)`（对称），"对方是谁"就恒能从声明本身读出；`Claim.conflict_id`、`Claim.resolved_by` 两个字段删掉（`contracts/models.py` 本来就要因 `TASK_KINDS` 改，见第 7 条，一次重算编码登记哈希）。不新增任何"语义规则"：X 若已是 VERIFIED 知识，**照现状保留在知识库、只标 `disputed_by`**（§25.3 没有 VERIFIED→DISPUTED 的边），最终报告如实列出这一对。要不要让已入库的旧知识也退出使用，属于新规则，不在本刀。
- 争议条目建议形状（报告、Host 投影共用一个派生函数）：`{"claim_id", "key", "stance", "status", "source_task", "disputed_by": [...], "in_knowledge": bool}`，取 `status is DISPUTED or disputed_by` 的声明。文档领域原来冲突记录里多带的 `source_versions / checked_scope / evidence_refs`（`_document_conflict_sides` 2086-2125）**不搬**——严格引用模式 A/B/C 还没定，等定了再说。

## 八、没核实清楚的地方

1. **冲突任务在分层下"派不出去"之外的副作用**：用户填了冲突预留、又真的出现矛盾时，分层任务里会多出一行永远 READY 的冲突任务。它会不会让任务收尾判定（`_require_accepted_work` / `_drop_compound_rows`，commit_service 4900-4903）或空闲判停（`NO_DISPATCHABLE_WORK`）出岔子，没有跑也没读完。删掉之后这个问题自然消失，只影响"删前行为"的描述。
2. **保证通道本地核验输入改 schema 的影响范围**（第〇节第 8 条）：`input_schema_ref` 是否冻结在任务级的核验绑定里、改了以后在途保证任务是单任务报错还是整体卡住；`implementation_hash` 的来源（`verification/assurance_local.py:117/136`、`orchestrator/assurance_local_checks.py:99/164`）是否也按源码字节算——没核实。
3. **`gap_phase1/test_are_orchestrator.py:479-481`**：按 `code-v1` 档案键逐个取 `ROLES[role]`，档案里有第一刀已删的五个变体，照理第一刀之后就该 KeyError；第一刀记录里 gap_phase1 全过，推测这条因本机缺 ARE 依赖被跳过。没确认。
4. **Host 场景能否造出可比较的声明**：分层+保证通道下，执行者只带文件证据的声明会被定成什么状态（`find_contradiction` 只看 VERIFIED/SUPPORTED/UNDER_REVIEW/DISPUTED，`verification/conflicts.py:36-38`），要写测试时再确认；必要时让脚本化审阅给出能定成 SUPPORTED 的证据。
5. **种类② judgment 人裁决在保证通道上走不走得到**：`_arbitrated`（9011）比的是独立裁判与各步 `critic_review` 层里的 `mission_criteria` 意见；保证通道的步骤审查是否写这一字段没查。本刀不动它，只是说明前端仲裁按钮在产品里可能很少出现。
6. **`KnowledgeRecord.from_json`、`Claim.from_json` 对旧 JSON 里多余键的容忍**：删 `confirmed_by`/`resolves`/`conflict_id`/`resolved_by` 后，旧库记录里还带这些键。`Claim.from_json`（983-1008）按键名取值、多余键被忽略；`KnowledgeRecord.from_json` 没看。
7. **`testing/fixtures.py` 知识共享段的精确边界**：按 grep，`_ToolStep`/`_tool_step` 只被 `compare_script_*` 用、`typed_claim`/`knowledge_envelope_step` 被记录器脚本用（1178-1182）；删的时候以导入与 `__all__` 为准再核一遍。
8. **`p35/test_first_request_guard_integration.py` 删 182 之后剩下的那条（35）**、`p35/test_first_protected_tail_hooks.py` 其余几条是否间接依赖系统尾池的表或钩子，没逐条读。
9. **前端 `MissionsView.test.tsx` 各条测试的结束行**只核了起始行；删时以 `it(` 块为准。
