## 一、方案（动代码前写定）

### A16 命题键加命名空间和作用域，哈希不截断

- 原计划：`P/ASSURANCE-EXEC-1.1.zh-CN.md:237`："命题键不拼接模糊文本：`canonical({predicate:{id,version,hash},typed_args,namespace,scope})`"。AER `design.zh-CN.md:295`：PropositionKey 含"谓词版本、类型化参数、对象版本、Mission/scope、时间范围"。
- 现状：`SDK/knowledge/predicates.py:294-301` 只哈希 `{predicate, arguments}`，结果截成 32 位。
- 计划没有说 namespace、scope 取什么值。AER 说的是 Mission/scope，也就是实例级的作用域。
- 代码里算键的是各个观察器（`observed()`/`denial()`，src 约 30 处）。观察器不知道当前任务和作用域。要带上实例级作用域，就要改观察器协议：5 个观察器类、约 30 处 src、约 150 处测试调用。这超出"小"的估计，也和计划对不上。
- 处理：
  1. **哈希不截断、字段名按计划**：现在就改。键 = `{id}@{version}#{完整 64 位哈希}`，哈希对象 = `{predicate, typed_args}`。
  2. **namespace / scope**：写偏差单（见第三节 偏差-1），停在这里，等主会话裁决。
- 删掉的旧路径：32 位截断的键格式。
- 守的保证：同一谓词版本加同一组类型化参数，得到同一个键；参数 1 与 true、缺失与 null 得到不同的键。
- 怎么测：新测试断言键尾是 64 位哈希，且等于 `sha256(canonical({predicate, typed_args}))`。现状下会红。
- 核心思想自查：只是身份计算，属于秩序，不判语义。

## 三、偏差单

### 偏差-1（编号待定）：A16 命题键的 namespace / scope 取值

- 原计划：`P/ASSURANCE-EXEC-1.1.zh-CN.md:237` 命题键 = `canonical({predicate:{id,version,hash},typed_args,namespace,scope})`。计划没说 namespace、scope 取什么。
- AER `design.zh-CN.md:295`：PropositionKey 要含"Mission/scope"。按这个读，namespace/scope 是实例级的（哪个任务、哪个作用域）。
- 代码现状：
  - 键由观察器在造观察记录时算（`observers/__init__.py:211` 的 `observed()`/`denial()`，src 约 30 处）。观察器协议 `observe(signature, arguments, *, now_ms)` 不带任务与作用域。
  - 算键的其他地方：`applicability.py:289`、`evidence_round.py:125`、`plan_preview.py:110`、`assurance_sources.py:103-120`、`htn_store.py:195`（存的问题要能算回键）。
  - 观察行本身已带 `mission_id`、`scope_id` 两列；但 `world.snapshot()` 按键合并同一任务所有作用域的观察。
- 冲突：带实例级作用域要改观察器协议：5 个观察器类、约 30 处 src、约 150 处测试调用（`test_predicate_observers.py` 一个文件就有 116 处）。和清单的"小"、和现有观察器结构都对不上。
- 选项：
  1. **实例级（贴 AER）**：namespace = 任务号，scope = 作用域号。观察器协议加一个必填的"命题框"参数（任务号+作用域号），观察器把它交给 `observed()`；快照加任务号；存的问题加这两项。工作量中等偏大，碰 HTN 观察器全线。
  2. **声明级（小）**：namespace/scope 取谓词声明里的值（如 `authority_scope`）。几乎不改调用点，但谓词哈希已覆盖声明，这样做不解决"不同作用域同名命题算同一键"，只是形式上对齐。
  3. **计划改条文**：写明产品里一个任务只用一个作用域（默认 `mission`），观察表按任务过滤，键里不放实例作用域；namespace/scope 两项删去或注明由存储列承担。
- 本车道建议：选 3；若要贴 AER，选 1 并单独开车道（不和第 2 批其它条目挤在一起）。
- 已做的部分（哈希不截断、字段名 `typed_args`）不依赖这三个选项。

### 偏差-2（编号待定）：A19 回执引用的存法，计划前后两种说法

- 补齐清单 A19：两个回执引用按合同用 JSON 引用字段（`source_receipt_ref`/`last_receipt_ref`）。
- 原计划三处：
  - `P/contracts/blob-pin-v1.schema.json`：钉住对象的两个字段是 JSON 引用，只收 `commit_receipt`。
  - `P/sql/assurance_additive.sql:227-228`：同一张表用 `source_receipt_id`/`last_receipt_id` 外键列；`P/sql/queries.sql:48-59` 也按这两列写与改。
  - `P/ASSURANCE-EXEC-1.1.zh-CN.md:513`（C.3）："commit 后 reader 形成 source_receipt_ref"——库里存回执号，读的时候再形成引用。
- 代码现状：`SDK/storage/assurance_schema.sql:227-228` 与计划 SQL 逐字相同。`SDK/storage/assurance_pins.py` 回读时按回执号取原回执，核种类、对象、钉住号、包号与哈希；`acquire_pin` 收到的就是 `commit_receipt` 引用并核哈希（`receipt_ref` 参数）。
- 冲突：照清单改成 JSON 引用列，就和计划自己的 SQL、queries、C.3 对不上；照计划 SQL 不改，就和 JSON 合同的对象形状差"由读方形成引用"这一步（现在读方核了回执但不产出引用对象，也没有消费方要这个对象）。
- 选项：
  1. **按 C.3 收口（建议）**：库表不动（与计划 SQL 一致）；在记录里改判"按计划在用"，注明 JSON 引用由读方形成、现读方已逐项核验。若主会话要求，可再补一个把钉住行投影成 `blob-pin-v1` 对象的读方，并用 schema 校验（目前没有消费方，属新增无人用的代码，不建议）。
  2. **按清单改表**：两列改成 `source_receipt_ref_json`/`last_receipt_ref_json`（存完整引用，触发器核 `kind='commit_receipt'` 与回执存在），读方解析后核哈希；同时改计划 SQL 与 queries 条文。需要迁移重建 `assurance_blob_pins`（含 6 个触发器与 2 个索引）。
- 本车道停在这里，没改代码。
