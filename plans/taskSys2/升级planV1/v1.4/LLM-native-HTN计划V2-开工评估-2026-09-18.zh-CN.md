# LLM-native HTN 执行计划 V2（HTN-LLM-NATIVE-2.0）开工评估

日期：2026-09-18　评估者：执行指挥　对象：`simpleharness-llm-native-htn-execution-plan-v2.zh-CN.md`（本目录，原文照录）
对照：上一轮《LLM-native-HTN计划-修订需求-2026-09-18》26 条；SDK 0.12.2 源码（c0e13a4 / 7f839f0）；H0 冻结基线 `baseline.json`。

## 结论

**第一阶段（H1）可以开工。** 26 条修订需求里，第一组 13 条裁定了 11 条半，第二组 6 条全部裁定，第三组 7 条从"十来行"补到了"有数字的设计裁定"。H1 的前三步（合同类型、存储、编解码）现在就能交给 Grok 做；下面「必须先答」的 3 条要在合同类型这一步收尾前答复，其余在对应步骤开始前答复即可。H2–H8 还不是代码级，各自开工前照 H1 的做法补一轮（先让编码代理对照源码出拆解，再由计划作者裁定）。

已核对的硬事实（与源码一致）：库结构现为第 18 版 → 迁移 19 成立；请求包整数版本现为 3 → 新包 4 成立；分层规划提示词现为 v7 → v8 成立；`MissionSpec` 在 `orchestrator/commit_service.py`；`contracts/` 下现无 `schemas/` 目录（属新增）。

## 必须先答（影响 H1-A 合同类型，答错要返工）

1. **方法实例的引用没有归属。** 第 25、27 节用到 `rejected_method_instance`、`consumer_method_instance_ref`，但第 17 节的引用种类里没有"方法实例"，而且这两处的样例没有 `kind` 字段；第 26 节的 `goal_type_ref` 又是第三种形状（id / version / content_hash）。建议裁定：引用种类增加 `method_instance`，所有正式引用一律用四元组；`goal_type_ref` 明确为独立的"版本化类型引用"并写进 Schema。
2. **每种引用的"语义修订号"和"内容哈希"从哪来。** 第 17 节要求四个字段全部必填、第 18 节要求逐字节匹配，但现网里任务、责任、能力、授权、操作这几类对象未必有现成的修订号与哈希。需要一张表：每个种类 → 取自哪张表哪个字段 → 没有现成值时用什么规范算法（建议：对象规范 JSON 的 sha256；修订号取对象自身版本，无版本者固定为 1）。
3. **几个小字符串字段没有给取值范围。** 不确定性的 `severity`、备选方案的 `disposition`、重规划提示的 `suggested_decision`、受阻声明的 `code` 与 `resumable_if`、`required_for` 的内容。顶层 Schema 里 `$defs` 的五个子结构也只有引用没有正文。建议：一律给封闭枚举并写进 Schema 文件；`suggested_decision` 复用决定类型枚举。

## 对应步骤开始前要答

4. **新事件的载荷与旧事件的关系**（影响 H1-B/H）。第 37 节只给了事件名 `PlanningDecisionEvaluated`，没给载荷字段；新协议任务里旧的"规划被拒"事件还发不发没说。现网修复轮、根评审修复、相同失败早停都读"规划被拒"事件和被拒展开列表。建议：新协议任务两个事件都发，旧事件语义与字段不变，新事件只带决定编号、类型、状态、拒绝码、请求编号。
5. **请求包有两个"版本"会撞名**（H1-D）。整数配对版本 3→4 没问题，但包内还有字符串标签，现值恰好是 `planner-package-hierarchical-v4`。需写明新包的字符串标签（建议 `…-v5`），以及关着开关的路径两个值都逐字节不变。
6. **格式重试与现有重问机制的关系**（H1-F）。第 39 节新增"同请求格式重试 1 次"，现网已有"提案不可读 → 带修复提示重问"。需写明是复用还是并存，以及 `attempt_ordinal` 的精确定义（每次重问加一）。
7. **何时转默认没有写成条件**（第 0 节说已裁定，正文只有"默认关闭"）。另外 Host 仓库的纪律是"测试阶段能力做完立即默认开"，与本计划"到 0.13.0 前默认关"相反。建议写明：SDK 侧默认关直到 0.13.0 全门禁通过；Host 侧在钉到对应候选版时显式为新建任务选新协议；这是对 Host 纪律的书面例外。
8. **真实模型专项怎么跑**（H1-I）。第 47 节要求四个场景，但没定义用哪几道题、通过标准、谁来开新协议。做题程序要能为任务选新协议（改动在做题程序，不在 SDK），并且要重新冻结。建议：沿用 0.12.2 验收的 7 道题各 1 遍 + 新协议开；通过标准 = 硬不变量全真、官方通过的局都被系统宣告完成、四个场景各至少出现 1 次（以新事件为证）。
9. **Schema 文件的打包**（H1-A）。新目录 `contracts/schemas/` 要进安装包（包数据配置），否则 Host 拿不到。
10. **提示词冻结的三处旧缺口**（H1-E）。H0 发现最早两版分层规划提示词不在冻结哈希表里、现行根评审提示词没有冻结字面量。建议在加 v8 的同一片补上。
11. **H0 产物的位置与文件名对齐。** 我已按上一版计划完成 H0（SDK `plans/2026-09-18-llm-native-htn/`：基线文档 + baseline.json + journal）。V2 要求 `plans/llm-native-htn/H0/` 下五个指定文件。已安排按 V2 重排并补齐缺的四个文件，数字不变。

## 风险提示（不需要改计划，执行时盯住）

- **过期即拒可能空转。** H1 规定请求发出后计划版本一变就拒绝。并行叶子多时规划回复更容易过期；有规划轮数上限兜底，但真实模型专项要统计过期率，过高就把 H2 的"无关变更精确重评"提前。
- **迁移 19 会碰到钉死库结构版本的旧测试**，属预期内改动，要在核验里逐个说明，不能算"旧模式行为变化"。
- **H1 共 36 个拒绝码，有些在 H1 走不到**（证据类、预算类）。第 33 节要求每码一条反例：走不到的码用准入层单元反例满足，不强求端到端。

## 建议的开工方式

1. 现在：Grok 对照源码做一次 V2 冲突检查（计划第 0 节要求的 BLOCKER 流程），同时起草 H1-A/B/C 三片的任务书；Codex 按 V2 重排 H0 产物。
2. 第 1–3 条答复后：H1-A（合同类型 + Schema + 黄金样例）→ H1-B（存储与迁移 19）→ H1-C（编解码），每片测试先行、另一会话独立核验、变异测试、归档。
3. 第 4–10 条在对应片开始前答复；不答复则按本文"建议"执行并在该片日志里写明假设。
