# HTN 后续方案 架构可行性评估（归档）

评估对象：`HTN-后续-方案.md` 第 2 版 + `plans/taskSys2/升级planV1/v1.4/HTN裁定变更-2026-10-01.zh-CN.md`。
评估员：独立 Opus 子代理，只读，118 次工具调用，约 15 分钟；只报阻断级。主代理抽查三条（规划包文件现役、合成器另有两个入口、Host 不为新做法审阅批准检查策略、注册协议按类型判据要求全覆盖）均属实。

## 摘要（大白话）

**结论：修改后可行。** 方向对，规划器"自己提做法"在决定协议上是放行的；但照第 2 版直接做会在七处做不成：

1. **新做法的独立审阅在产品里根本开不起来**：Host 只为内容、最终审查、操作申请、操作结果四类审阅批准检查策略，没有"新做法审阅"这一类；规划器一提做法就会被拒。
2. **子目标"只负责一部分要求"表达不了**：注册检查要求做法覆盖目标类型声明的全部判据；新做法审阅的判据取"类型判据 ∩ 任务要求"，通用子目标怎么声明都走不通（全声明 → 每个子目标都得覆盖全部；不声明 → 审阅没判据；声明一个本地判据 → 审阅仍没判据，且一个子目标负责两条父要求会撞"多重父映射"）。
3. **合成器的入口不止六处**：主循环每轮无条件调用一次、规划器"声明受阻"后也会转交合成。只改初始规划一处，合成器会和规划器同时起跑。
4. **"审阅通过才采用"缺唤醒和打回通道**：下一轮规划不等审阅结论；审阅打回后没人再问规划器，任务会以"没有可派发的工作"停机。
5. **写做法的上下文只在"0 个候选"时给**：根终审打回、只读越权、反复失败三种修复场景拿不到；提做法被拒后候选集不变，"同一候选集只问一次"的账本会把重提挡掉。
6. **"规划包已带全写做法所需信息"不属实**：合成器有而规划器没有的——真实判据原文（09-29 修过的缺陷会复发）、各做法不适用的原因、防撞车的新编号、根终审打回意见；规划器路径还缺"一步承担 ≥3 个文件打回重拆一次"（用户 09-26 决定）和"发布来源唯一"两项检查。
7. **`planner_package_v1.py` 不是旧文件**，是当前九视图规划包的组装器（名字误导），不能删。

另有 8 条实施须知：规划器现提示词里有一句"你不需要也不能自己合成方法"要删；"声明受阻"改问人以免无限循环；规划次数上限默认只有 2，去掉合成补偿后要给具体数字；没有程序上的层数上限（靠"递归做法必须写适用条件"间接限到三层）；改规划器提示词会改变执行池身份等。

## 评估员报告原文

总结论：修改后可行。方向成立，规划器"自己提做法"这条路在决定协议上是放行的。但方案在三处地方会直接做不成：新做法独立审阅在 Host 里根本开不起来；金丝雀阶段合成器还会被另一个入口同时叫起；子目标的验收判据和"审阅通过才采用"的接线，现有协议都承载不了。另外有两条事实陈述是错的：规划包已带全写做法所需上下文、`planner_package_v1.py` 是旧文件可删。

### 阻断级问题

**1. 新做法审阅在 Host 永远开不起来，规划器每次提做法都会被打回**
- `ensure_method_plan` 走到 `prepare_purpose_review`，查不到已批准的检查策略就抛 `CHECK_POLICY_UNRESOLVED`（`orchestrator/assurance_purpose_reviews.py:236-242`）；被捕获后这次提做法记为 `REJECTED / AUTHORIZATION_REQUIRED`（`event_handler.py:8774-8810`）。
- Host 的 `project_check_policies` 只投影 CONTENT / ACTION_PROPOSAL / OPERATION_OUTCOME / MISSION_FINAL（`backend/deskpet/orchestration/assurance.py:178-258`，键表 190-192）。METHOD_PLAN 的策略要以"规划主体任务"批准（`assurance_check_policy.py:85`），全库无调用方传 `planning_subject`。投影器在事务内不执行（`assurance_review_runtime.py:356`），而 `ensure_method_plan` 恰在决定事务内调用（同文件 293）。
- 改法：Host 增加 METHOD_PLAN 策略投影（按规划主体任务批准，判据与审阅包一致），事务外提前完成；根目标在任务开始时投影，子目标在父计划提交后投影。

**2. 子目标"只负责一部分要求"在现有协议下表达不了，子目标的新做法审阅也开不起来**
- 新做法审阅判据只取"目标类型覆盖判据 ∩ 需求判据"，空则 `SOURCE_UNAVAILABLE`（`assurance_purpose_reviews.py:427-430`）；注册检查要求覆盖目标类型全部判据（`planning/htn/registry.py:1921-1931`）；完成范围里子目标做法若链接 `c-user-*` 则全部归它（`planning/htn/completion_scopes.py:256-268, 316-325`）；同一本地判据挂两个父判据报"multiple parent mappings"（同文件 292-297）。
- 三种声明法都走不通（全声明 / 声明为空 / 声明一个本地判据）。
- 改法：第 5 步前先定设计。建议子目标类型声明一个本地判据；新做法审阅对子目标的判据改从"该子目标的完成范围或父做法链接过来的判据"取。

**3. 合成器入口不止六处，金丝雀阶段合成器会与规划器同时起跑**
- 主循环每轮对每个活动任务无条件调用 `_request_method_synthesis`（`event_handler.py:3724`），只看有没有挂起的等待（3910）；根目标无做法时 `goals_needing_method` 必返回它（`hierarchical_dispatch.py:3832-3857`）；`DECLARE_BLOCKED` 后转交合成（`event_handler.py:8950`）。
- 改法：金丝雀阶段同时关掉 3724 与 8950。

**4. "审阅通过才采用"缺少唤醒和打回通道**
- 下一轮规划由 `PlanningMethodProposed` 触发（3219），只在没有规划类在途请求时开轮（3208-3214）；方法审阅请求 kind=plan、角色 `method_reviewer`（`assurance_review_transport.py:34, 365`）不在 `NOT_PLANNER_ROLES`（311-313），下一轮只是碰巧等到这一回合结束，不等正式记录；复审 / 格式重试再开请求时唤醒已被消费；全库无代码把打回意见转成一轮规划；单候选时系统还会直接替规划器选上新做法（`planning_selection.py:128-140`）。
- 改法：新增"方法审阅正式记录已入库（通过 / 打回 / 人已裁决）"服务事件作为唤醒源，打回时带意见；等待期间在空闲判定里加等待项。

**5. 写做法的上下文只按选择路由给出；选择身份账本会挡住重提**
- `method_proposal_contexts` 只给路由为 `EVIDENCE_OR_SYNTHESIS` 的目标（`planner_views.py:210-215`）；选择只覆盖未采用做法的复合目标（`hierarchical_dispatch.py:3444-3451`）；提做法被拒后身份不变 → `SELECTION_ALREADY_ATTEMPTED`（`method_selection.py:358-370`）；包里没有 `planning_rejected` 时系统本地回 NO_CHANGE（`planning_selection.py:141-143`）。
- 改法：上下文按"目标需要做法"给出，与路由脱钩；身份摘要纳入提做法 / 审阅结果，或对"有待重提"的目标放行。

**6. "规划包已带全部写做法上下文"不属实**
- 合成器有、规划器没有：真实判据原文（`hierarchical_dispatch.py:3115-3123`；规划包用 `build_request` 默认值 `synthesis.py:638-644`）、各做法不适用原因（3085-3105）、`new_method_identity`（3124-3127）、`review_feedback`；编号撞车检查（4089-4098）、"一步 ≥3 个文件打回重拆一次"与"发布来源唯一"检查（4099-4118）在规划器路径不存在（`planning_method_proposal.py:15-31`）。
- 改法：搬进 `prepare_method` 与 `method_proposal_contexts`。

**7. `planner_package_v1.py` 不是旧文件**
- 文件头说明是当前九视图规划包组装器（`planning/htn/planner_package_v1.py:5-9`）；使用处 `orchestrator/planner_views.py:12-16`、`event_handler.py:4786`、`planning/htn/__init__.py:107`。

### 逐问要点

- **提做法这条路**：启用表放行（`planning_decisions.py:310, 316`）、授权包含（`planning_authorization.py:59-62`）、准入不另查 payload（`decision_admission.py:1190-1193`）、提交后以"本任务试用"登记并进入候选。被拒时规划器只看到一整段回执字符串，不如合成器逐条可修。
- **六处捷径**：初始（规划器无合法动作 → 有了提做法即可）；展开嵌套复合（每版只问一次 → 靠服务唤醒可行）；根终审打回后重编（需补上下文；重提与被打回做法内容相同会永远不适用、空转）；只读越权（需补上下文；保留"合成被拒就以只读越权原因停机"）；同样失败重复（RETRY / REPLACE 可表达）。共同要补：修复轮"先记一条规划被拒"会计入规划次数；合成成功原本多给一次规划机会（`_synthesis_credits`），删后要另设名额。
- **审阅闸门位置**：过滤阶段只适合展示；REFINE 准入来早了会被拒并计规划失败；**建议放在计划提交事务内**，读正式记录按"通过或人裁决通过"判。不能直接套 opt.109 的证书（METHOD_PLAN 按合约没有完成范围，证书准备会报 `USE_PURPOSE_UNSUPPORTED`）。
- **层数上限**：程序上没有（提交时只查同时存在的任务数和累计展开数，`max_depth` 不查）；要明确上限得加程序检查。
- **删合成器角色**：未发现会导致启动失败的硬依赖；要一并改 `NOT_PLANNER_ROLES`、`mission_sources.py:162`、ARP `SOURCE_KINDS`、`taskgraph_execution_view.py:250-256`、`hierarchical_dispatch.py:3239`；部署清单要重新生成。
- **选择身份账本**：提做法成功后候选集变了自然换新；被拒或审阅打回后候选集回到原样会被挡。

### 实施须知

1. 规划器提示词仍有"DECLARE_BLOCKED…你不需要也不能自己合成方法"（`role_templates.py:728-730`），与提做法矛盾。
2. DECLARE_BLOCKED 现转交合成；删合成器后若改成再开规划器会无限循环，建议改为问人。
3. Host 规划次数上限默认 2（`runtime/assembly.py:94`）；去掉合成补偿后"重提上限"必须给具体数字。
4. `governance/domains.py` 的 `synthesizer` 是文档领域"成果综合"角色，不是方法合成器，别误删。
5. `MethodSynthesizer.accept_response`、`SynthesisRequest.role_prompt_version` 引用 `METHOD_SYNTHESIZER`；解码器保留并改名，不能整文件删。
6. 修复场景里新做法用 REPAIR/REPLACE_METHOD 采用，不是 REFINE。
7. 写做法上下文占 96 KiB 包上限；接入代码领域（23 个类型）后要留意。
8. 改规划器提示词会改变执行池身份，本机已有执行池需重建。
