## 0. 裁定、来源与实施权限

**唯一默认：保留现有 ObligationId；增加明确的贡献范围和必需效果绑定，不强制把准备/效果拆成新的 Obligation。**

一个 Obligation 可以由内容贡献和多个实际效果共同满足。`effect_key` 是该责任内一个被明确要求的效果槽，不是新 Task、预算账户、OperationId 或独立生命周期。Task/Occurrence 的完成范围另有精确绑定；不能因为几个孩子共用 ObligationId，就让每个孩子承担全部动作要求。

```text
批准的 Requirements + 必需效果规格
  → 冻结的 occurrence 完成范围
  → 准备 Acceptance（内容可用，效果仍欠缺）
  → T0/T1/T2（沿上一补遗）
  → 真实效果事实 + official OPERATION_OUTCOME Review
  → 效果 Acceptance + 精确来源桥
  → 同一 CompletionReader → 组合/根审阅 → 原 GoalResolution/closeout
```

这是新裁定，不声称旧代码已经这样实现。上一补遗 §2.1/§3.1/§3.5 只给出了原则；§6.2 将 milestone 来源留给“Requirements/已批准准则”，缺少可读取的完整绑定。本文件补齐此处，不重开 H1–H8，不限制其他已明确工作。

- 原补遗实际附件 SHA-256：`a2657120e1c44479a268ca19e0ab0b3da1eb65d7b3db6512df7ef2e3d1520725`；ZIP：`3fbd3f3b5e3b634bcf128a3cf6441e5613401341c3642c28b647fcabc03c4237`，本轮容器已核对。

## 1. 三条必须同时成立的分离

| 对象 | 证明什么 | 不能代替什么 |
|---|---|---|
| 内容/准备 Acceptance | 指定输入和要求下，一份准备贡献可用 | 实际动作已发生、动作义务或整个 Task 已满足 |
| ACTION_PROPOSAL Review | 冻结操作候选合格 | 用户/政策授权、实际效果 |
| OPERATION_OUTCOME Review + 来源绑定 | 本次已观察效果满足本次指定要求 | 另一个动作、另一个要求版本或其他必需效果 |

`Task.COMPLETED`、`Acceptance.validity=CURRENT`、`DeliveryReceipt.operation_id!=None` 单独均不构成新操作 lane 的完整完成证明。

**不修改既有 Acceptance/DeliveryReceipt V1 canonical 字节。**用四类不可变 side binding 补足语义；历史对象原样保留。所有 side binding 由原 CommitService 写入，模型、UI 和 Resolver 均无裸写入口。

## 2. 统一身份与编码

新增内部模块 `contracts/operation_completion.py`。下列四种对象皆为 `frozen, slots, kw_only`；分别严格 codec。不得接任意 dict 后 `.get(..., [])` 放行。

内部 `CompletionPinV1={id:str, revision:int, content_hash:64位小写hex}` 是已有正式对象身份的投影；其类型由字段限定。producer 必须先解析原 TypedRef 的正确 kind，再取三字段。**不增加/修改 TypedRefKind，不丢掉原对象的 provenance 验证，不让 pin 自己成为读取权限。**

所有字段必填，允许空集合的位置明确规定；nullable 必须显式 null。整数拒绝 bool，拒绝重复 JSON key、NaN/Infinity、未知字段和重复 ID。每文档最大256KiB/depth16，项目已有更紧限制优先。保存 `canonical_json(obj).encode('utf-8')`，复用原算法；数组按语义保序，集合先验证重复再系统排序。附件参考 codec 只演示新内部文档，不替代原 SDK 的 TypedRef/权限/签名验证。

### 2.1 `OperationCompletionRequirementsV1`（以下简称 Spec）

```text
schema_version: 1
mission_id: str
requirements_ref: CompletionPinV1             # requirements_revisions 精确记录
mode: CONTENT_ONLY | REQUIRED_EFFECTS
content_criterion_ids: tuple[str,...]
effects: tuple[RequiredEffectSlotV1,...]       # <=64；本合同内均为 MUST
```

`RequiredEffectSlotV1`：

```text
effect_key: str                               # 本版 Requirements 中的明确 slot 身份
obligation_id: str                            # 已有责任，不新开预算
criterion_ids: nonempty tuple[str,...]
required_milestone: str                       # 注册语义，不是自由排序分值
milestone_policy_ref: CompletionPinV1         # milestone 定义/证据识别规则版本
evidence_policy_ref: CompletionPinV1
source_slot_key: str                          # 原批准命令中的明确效果 slot
```

约束：effect_key/source_slot_key 各自唯一；`CONTENT_ONLY ⇔ effects为空`，且至少有一项内容准则；`REQUIRED_EFFECTS` 非空。effect准则不得也列为纯内容准则。多个效果可共同关联一个根准则，但 **ALL 效果均必需**，一个回执不自动满足多个槽。原 Requirements 的全部强制准则必须有明确覆盖（ANY分支选择仍由原公式判断，不把所有互斥选项都改成必做）；不允许从绑定中静默省掉难要求。

本规格只列已批准的 **MUST** 效果。原 ALL/ANY 公式仍由既有实现求值；用户明确可选、互斥的动作不能未经裁定全变成 MUST。当前若无法把某动作是否必需解析成已批准规则，返回 `OP_REQUIREMENT_MAPPING_AMBIGUOUS`，按现有 clarification 处理，不猜测。

### 2.2 `OccurrenceCompletionScopeV1`（以下简称 Scope）

```text
schema_version: 1
mission_id: str
requirements_ref: CompletionPinV1
spec_hash: hash
plan_ref: {revision:int, snapshot_hash:hash}
occurrence_id: str
task_ref: CompletionPinV1                     # 精确 Task contract，不是 tasks.version
obligation_id: str
role: CONTENT | MIXED | AGGREGATE
content_criterion_ids: tuple[str,...]
required_effect_keys: tuple[str,...]
owned_effect_keys: tuple[str,...]
```

- CONTENT：这项工作只承诺内容；两个effect数组为空。它可以完成，不表示同 Obligation 下所有工作完成。
- MIXED：primitive 自身承诺准备和实际效果；required_effect_keys非空，准备后不能完成 Task。
- AGGREGATE：compound 的组合范围；根必须包含 Spec 全部必需效果。它不创建假 Worker Attempt。
- owned_effect_keys 是执行意图归属的 completion owner，不是额外权限；必须是 required_effect_keys 子集。一个 effect 在一次采用的计划中恰有一个 owner。
- **默认 owner 是该责任的根 occurrence**；准备子任务可以是 CONTENT。只有已批准 Method/明确任务合同已经将该效果分配给特定 child 时，才把 owner 移到该 child；仍由根聚合。
- 不按“同一 obligation_id”把所有 effects 塞给所有 sibling。也不凭动作文件出现、Task 文本相似度决定 Scope。

producer：`compile_completion_scopes(spec, plan, approved_criterion_coverage)`，纯函数；由计划编译/Commit 接缝调用，输出与原 PlanRevision **同事务持久化**。先有批准 Spec，再有 Scope，再派发 Worker。根 scope 缺任意 MUST、owner重复/丢失、Task合同声明动作却没有可核验scope归属，返回 `OP_COMPLETION_SCOPE_UNRESOLVED`。

部分展开允许尚待细化的 compound 持有 owner；它不表示效果完成。对当前已批准 Method 中明确只有准备工作的子节点赋 CONTENT。现有混合节点不能为让测试通过而重新标成 CONTENT；需要原已授权的合同/计划修订，不能重写历史。

### 2.3 `AcceptanceContributionScopeV1`（以下简称 Contribution）

```text
schema_version: 1
mission_id: str
acceptance_id: str
completion_scope_id: str
spec_hash: hash
kind: CONTENT | PREPARATION | OPERATION_EFFECT
content_criterion_ids: tuple[str,...]
effect_keys: tuple[str,...]
output_artifact_refs: tuple[CompletionPinV1,...]
outcome_binding_id: str|null
delivery_receipt_ref: CompletionPinV1|null
```

CONTENT/PREPARATION 的 effect_keys 必须为空，outcome/delivery必须null。CONTENT仅针对CONTENT Scope；MIXED/AGGREGATE上的准备贡献使用PREPARATION。它们只能覆盖已实际审阅的内容准则与确切产物。

OPERATION_EFFECT：**恰好一个 effect_key**、content_criterion_ids和output_artifact_refs为空、outcome_binding_id非空；DeliveryReceipt可为空（某些milestone不是用户消息交付阶段）。准备产物通过其独立Acceptance引用，不复制成效果产物。

Contribution 是原 Acceptance 的解释边界，不是新的 Acceptance 或当前有效性账本。同一个Acceptance只能有一种不可变范围。新增源码不能先写“无范围Acceptance”，稍后再补范围；两者必须同事务。

这是正式 OPERATION_OUTCOME Review 的冻结输入桥，**不是预先写好的“成功”状态**。

```text
schema_version: 1
mission_id: str
spec_hash: hash
effect_key: str
completion_scope_id: str
intent_id: str
operation_id: str
operation_occurrence_id: str
action_key: str
action_version: int
request_hash: hash
candidate_file_hash: hash
parameters_content_hash: hash
params_hash: hash
effect_contract_hash: hash
link_hash: hash
connector_profile_hash: hash
namespace_hash: hash
target_identity_hash: hash
milestone_policy_ref: CompletionPinV1
observed_milestone: str
covered_handoff_ids: nonempty tuple[str,...]
source_receipt_refs: nonempty tuple[CompletionPinV1,...]
```

对应表另存真实 `review_package_id`、源manifest hash及producer receipt，**不把 package_id放进binding的hash再让package反引自身**。先冻结binding内容hash，再构造引用该hash的ReviewPackage，最后一次事务保存二者。

`observed_milestone` 由原可信connector adapter解读真实服务回执产生，不由模型填写。该adapter若不能解释此回执，保留原事实，返回 `OP_OUTCOME_MILESTONE_UNVERIFIABLE`；不能生成默认binding。

### 2.5 系统身份与新增hash的精确定义

全部使用原SDK canonical/derive_id工具，不从文本相似性产生业务Operation：

```text
spec_id = derive("op-completion-spec", mission_id, requirements_revision, requirements_hash)
scope_id = derive("op-completion-scope", mission_id, plan_revision, occurrence_id)
namespace_hash = sha256(canonical(profile.namespace))
target_identity_hash = sha256(canonical({normalized_target_ref, expected_target_version}))
source_manifest_hash = sha256(canonical({
  source_receipt_refs: 按(id,revision,content_hash)排序的无重复实际refs,
  covered_handoff_ids: 排序的完整所覆盖ID,
  receipt_adapter: 原effect/profile固定的adapter身份,
  milestone_policy_ref: 批准Spec中的精确policy
}))
outcome_binding_id = derive("op-outcome-review", intent_id, spec_hash, effect_key,
                            completion_scope_hash, source_manifest_hash)
```

spec_hash/scope_hash/binding_hash分别是对应完整document canonical字节hash，不包含表中的写入时间、receipt_id或由其派生的ID。原三种hash按上一补遗§6.4计算，不互换。

OutcomeBinding字段来源：intent/三个revision来自T0 binding；Operation与envelope身份来自T1真实receipt；action_key/version/params来自精确link与原action；effect/parameters/candidate hash来自T0冻结payload与CAS；namespace/adapter来自冻结profile；milestone与handoff覆盖来自真实receipt adapter；Spec/Scope来自本章精确reader。任一环节来源无法读取，返回SourceUnavailable，不在Outcome importer内补对象或签发新Operation。

## 3. Spec 的唯一生产者：批准要求，不是从能力表选一个效果

### 3.1 SDK/Host入口

在现有认证 `MissionControlV1` 上增加 `approve_operation_completion_spec` 的委托，唯一writer：

```python
approve_operation_completion_spec(
    *, mission_id: str, command_id: str,
    expected_requirements_ref: TypedRef,
    proposal: OperationCompletionRequirementsV1,
    requirement_authority: ApprovedRequirementAuthority,
    principal: Principal,
) -> CompletionSpecReceipt
```

这是 **已授权 V1.4 的内部要求接线**，不是公开 PlanningDecision 扩容。caller来自现有已认证Host/facade，不接模型principal/approved布尔值。`ApprovedRequirementAuthority` 的两个来源：

1. `USER_CONFIRMED`：用户create/clarify/明确确认命令，确认规范化的 Spec hash 与原 Requirements hash；实际命令事务产生回执。
2. `REQUIREMENTS_POLICY`：已注册、明确获准解释这类**结构化输入**的现有policy及实际判定回执。必须证明批准了这份映射、全部准则和精确milestone；不存在这类授权时不能用服务身份自行批准。

`ApprovedRequirementAuthority` 只由 `api/operation_completion.py::bind_requirement_authority(authenticated_call, server_policy, normalized_spec)` 生产，不是Host请求体里的可填写对象。内部固定字段：`kind, tenant_id, issuer_id, command_id, command_body_hash, requirements_ref, normalized_spec_hash, policy_ref|null, check_receipt_refs[]`。USER_CONFIRMED必须来自本次实际确认command；REQUIREMENTS_POLICY必须带真实policy和判定receipt。API先绑定，Commit在事务内核对这些出处并签发Spec receipt；禁止测试issuer或`approved=True`进入生产链。

若原准则是“生成并送达”这一条合并文本，先在**原Requirements细化/批准链**中生成可追溯的内容子准则与效果子准则，保留对原准则的覆盖关系。不能把同一个未完成的效果准则标为内容PASS；该细化不降低原用户要求，也不要求Worker产出前已经有Operation。

LLM可以提出映射。对于“发给”“送到”等歧义，不静默选择 received/sent/delivered；走已有澄清/批准流程。仅当原输入或其既有批准已明确指定，才能自动固定。纯报告的新协议Mission在正常create/要求确认时同时产生显式 CONTENT_ONLY Spec；不额外要求用户批准模型自创的外部动作。

**缺记录不是CONTENT_ONLY。**对已存在但还未接上本合同的新协议Mission，允许读取/准备工作继续，但冻结最终完成；不能因没发现intent/action就当没有动作要求。旧协议按原行为。

### 3.2 权威与事务

原要求创建/更新事务：先建立Requirements、已有根Obligation→核对authority→保存Spec、真实批准回执及事件→再允许规划/根完成消费者读取。根scope在相应Plan提交时冻结。

已有`delivery_contract`如能明确表达同一要求，作为这次writer的**一个输入来源**，通过注册规则转换并绑定原来源hash。不得另存一个不一致的默认milestone。缺失delivery_contract不会删除Spec中的效果。反过来，Spec与已批准delivery_contract冲突必须拒绝，不任选其一。

`required_milestone`、效果定义及证据policy三者来自批准的Spec；connector profile只回答是否支持。默认匹配是语义policy相同且milestone精确相等。需要“delivered证明sent”等蕴含时，必须由**该已批准policy的显式规则及真实回执**支持；禁止用全局字符串/枚举大小比较。

同 `(mission,requirements_revision)` 只能有一个不可变Spec。修改milestone、target scope、效果数量、证据要求或覆盖关系，必须走新的RequirementsRevision及批准，不能原地更新。仅修实现代码不改Spec身份。

## 4. T0/T1 绑定补充：不改变原默认链

T0前已有Spec和Scope，但 **不要求已有intent/Operation**，避免循环。为让明确用户操作知道自己满足哪个已批准效果，新增认证命令 `SubmitOperationIntentV2`：保留原V1字段并增加必填 `completion_slot={spec_hash,effect_key}`。

- AUTHORIZED_SLOT V1：仅当原真实origin receipt/slot已有唯一Spec映射时可由系统适配；不按target猜。
- USER_COMMAND V1没有唯一批准映射：`OP_COMPLETION_SLOT_REQUIRED`，Host在提交界面发送V2。不得自己选择profile中最弱milestone。
- 用户在纯报告Mission上又明确要求发送：先创建批准的Requirements更新；终态Mission沿原规则使用新的Mission/执行周期。不能由candidate存在自动添加要求。
- owner可以是根compound，producer可以是某个CONTENT child。二者明确保存，不互相假冒；同一Obligation的资金/责任谱系不重置。

新增 `OperationEffectContractV2` = 原V1完整字段 + `completion_spec_hash,effect_key,milestone_policy_ref`；`required_milestone/milestone_criterion_ids` 必须与Spec精确一致。

新增 `FrozenActionProposalV2` = 原V1完整字段 + `completion_spec_hash,completion_scope_id,completion_scope_hash,effect_key,completion_owner_occurrence_id`。新lane的T0生产V2，原V1保持读取，不改旧字节。OperationParametersV1和OperationEnvelopeV1结构无需修改；Envelope通过effect/draft引用V2。新artifact metadata的object_revision仍为1，不能与payload.schema_version=2混淆；resolver按(object_kind,schema_version)显式分派V1/V2，旧记录不重编码。

原 `operation_intent_bindings.binding_json` 使用严格 **schema_version=2**，加 `completion` 子对象：

```text
{spec_id,spec_hash,effect_key,scope_id,scope_hash,completion_owner_occurrence_id}
```

V2 `request_hash` 使用上一补遗§6.3的原稳定投影，`kind`改为`operation-request-v2`，并加入`completion_spec_hash, completion_scope_hash, effect_key, completion_owner_occurrence_id`；不包含自身request_hash，不改旧V1记录。整体draft hash与该请求hash分开保存。

T0同事务核对Spec/Scope/Requirements当前版本、真实source slot、producer Acceptance范围/输入和owner当前采用；保存上述引用、原来源receipt、payload/Review dispatch。T1再次核对，仍按原事务创建envelope/action/link。没有新增action状态表。

同一completion slot只允许一个**未被正式替代且可作用的intent分支**。原supersedes链完整核对，不能用latest排序选择；两个非继承分支争同slot→`OP_COMPLETION_INTENT_AMBIGUOUS`。原动作UNKNOWN不允许新intent绕过。不同MUST effect_key必须分别取得结果，不克隆一次action/link填两个槽。

## 5. 接受准备产物：所有reader采用同一范围规则

### 5.1 `accept_result()` 的唯一新协议行为

接受候选的写事务中：

1. 核对冻结Scope、原Task contract/Requirements/input、official内容Review及实际checks。
2. 按ReviewPackage中的准则范围构造原Acceptance，同时写Contribution；只覆盖实际检查过的内容，不填效果PASS。
3. Attempt可按原成功转换到COMPLETED，并归档/结算实际用量；**Attempt结束不是任务目标满足**。
4. CONTENT Task可按原全内容验收完成。MIXED Task保留 **VERIFYING**，派生进展为`WAITING_REQUIRED_EFFECT`，不写Task.COMPLETED/Obligation.SATISFIED/GoalResolution。
5. scope-derived dispatch disposition阻止自动重开Worker来“继续生成同一报告”；原ACTION_PROPOSAL/approval/outcome/reconcile通道可继续。预算仍按真实Task原账户与新预留，不能复活已结算reservation。
6. 用原事件机制发PreparationAccepted/OperationCandidateAvailable；T0消费者监听它们，**不等待Task/Mission完成**。

同一原Task承诺内容和动作时，内容Review只覆盖Scope的内容部分，effect criterion保持待验；这不是降低根要求。必须使用冻结的Task-content review scope，不在Review后删掉难准则。已有整任务Reviewer要求效果现在就PASS的package要按新purpose范围重建，不伪造成功。

### 5.2 唯一读服务（NEW）

```python
class OperationCompletionReader:
    read_requirements(mission_id, requirements_ref) -> ApprovedCompletionSpec | SourceUnavailable
    read_scope(mission_id, plan_ref, occurrence_id) -> CompletionScope | SourceUnavailable
    read_contribution(acceptance_ref, purpose, consumer, read) -> ScopedContribution | Rejected
    read_current_effect(effect_key, spec, owner_scope, read) -> VerifiedEffectContribution | Pending | Rejected
    evaluate_occurrence(scope, read) -> CompletionEvaluation
    evaluate_root(spec, active_plan, read) -> CompletionEvaluation
```

参考覆盖函数仅检查其已批准的必需内容/effect集合，不替代原ALL/ANY公式。生产root reader从真实Spec派生必需effect集合，不允许调用方传空集合来缩减范围。

`CompletionEvaluation={status:READY_FOR_REVIEW|PENDING|INVALID, missing_content_ids, pending_effect_keys, reasons, source_read_set}`；它不自签GoalResolution。输入由同一Store一致读及原Validity服务产生，无数据库权限的纯函数不能发明`is_current=True`。

`read_current_effect`只能从本条Spec的effect_key出发查T0 binding→原envelope/link/action→exact outcome binding/official review/Acceptance；不能反过来扫描“找任意有operation_id的DeliveryReceipt”。无intent=AWAITING_INTENT；Review/审批未过、pending、UNKNOWN各给真实待办原因。

### 5.3 必改消费者（不能只改UI或Task状态）

| reader/writer | 新读取规则 |
|---|---|
| `leaf_acceptance.py`、`accept_result()` | Acceptance+Contribution原子写；用CompletionEvaluation决定Task完成，不能裸CURRENT完成 |
| `HierarchicalDispatch.accepted_outputs()` | 按精确artifact/port及Contribution/Validity取准备内容；**允许准备贡献被授权读取，不要求Task终态** |
| input resolver/T0准备读取 | `purpose=DATA_PREPARATION/ACTION_PROPOSAL`仅用获准输出/准则；不会把它转换成完整goal通过 |

| 根ready/贡献collector | CONTENT/PREPARATION可进审阅材料；效果准则只能由匹配OPERATION_EFFECT覆盖；不能仅按task/obligation聚合CURRENT行 |
| 终结predicate（handoff所指`commit_service.py:5241–5298`等） | mandatory调用`evaluate_root`，不要只依赖TaskStatus/primitive Acceptance数量 |

纯ORDER仍表达完整前置完成，不因有准备产物就释放；需要提前消费准备内容使用已有明确DATA/准备事件。不得为解锁操作偷偷把原ORDER.accepted改为“有任何Acceptance”。

同一Obligation下其他CONTENT子任务正常完成；其Acceptance不能令整个Obligation提前SATISFIED。原Obligation完成writer必须检查其全部已批准MUST effect及原组合条件。

## 6. T3唯一效果入口、official Review与DeliveryReceipt关联

### 6.1 原事实先落库，随后解释其是否完成用户要求

原 runtime/connector receipt importer继续唯一记录真实调用、回执与费用；**即使要求后来改变，也必须保存真实事实**，不因无法完成当前目标丢掉它。

新增 `orchestrator/operation_outcomes.py` 两个内部生产入口，由原持久事件消费者调用，不暴露给模型/裸UI：

```python
prepare_operation_outcome_review(*, intent_id, source_receipt_refs, command_id, principal)
    -> OriginalReviewDispatchReceipt | OutcomePending | Rejected
accept_operation_outcome(*, official_review_ref, command_id, principal)
    -> ScopedEffectAcceptanceReceipt | Rejected
```

prepare读取T0/T1全链和真实receipt，通过当前匹配版本的注册adapter核对原字节：OperationId、occurrence、action_key/version、三类hash、effect/request/link、namespace、target、handoff覆盖等全部匹配。`Action.APPLIED`但没有milestone事实，不能代替delivered；未知或只达较早阶段只保留原观察，不生成效果Acceptance。

满足候选milestone证据时：构建OutcomeBinding→构建原ReviewPackage（purpose=OPERATION_OUTCOME、subject为原Operation或原tool receipt；实际组合输入包含binding hash、effect artifact、原请求、要求与真实回执）→同事务保存binding/ReviewPackage/原dispatch intent/预算预留→事务后原独立Verifier执行。

**不用新增payload kind/假Worker Artifact或Attempt。**OutcomeBinding的canonical document在专用绑定表；Review context builder按表中package_id精确读取，形成冻结manifest，使用原ReviewPackage codec。不得把未知URI视为证据。Review新增的取证结果沿原机制追加，不改原已冻结binding。

### 6.2 `accept_operation_outcome()` 写事务

1. 验证service caller；按原command幂等取receipt，异体冲突。
2. 根据official Review读其ReviewPackage，精确找到唯一OutcomeBinding；核对purpose/subject/输入manifest、reviewer独立、verdict=ACCEPT、必需checks真实完成。
3. 从binding回到intent/source/Spec/Scope/Envelope/action/link和原始receipt；核对全链一致、没有新反证/不完整导入。检查用户要求仍为同版；handoff历史批准看原真实回执，不能以今天审批过期否认昨天的事实。
4. 用注册的milestone policy核对真实证据；模型PASS不能抹掉证据不足或wrong milestone。
5. 生成原Acceptance（task/obligation是**completion owner**，不是机械复制producer）。其ReviewRecord指向本次OPERATION_OUTCOME；artifact_refs可为空，实际证据仍由review/evidence refs保存，不制造效果文件。
6. 同事务写OPERATION_EFFECT Contribution、必要的原DeliveryReceipt、原事件/CommitReceipt、根/父重新评估的持久通知。强退整体rollback；不在该事务执行connector。
7. 重读CompletionEvaluation，能够完成的primitive按原合法转换完成；父/根有待组合Review时只唤醒原审阅链。Effect Acceptance本身不自动宣告Mission完成。

OutcomeBinding唯一来源可以重复消费，但**同binding只产生一个正式效果Acceptance**。相同operation后来的更高milestone是新的实际receipt/binding，不重写旧观察；某次received Review不能升级为delivered。

### 6.3 DeliveryReceipt是投影，不是独立证明入口

- SENT/CONFIRMED用于该lane效果时，receipt.acceptance_id必须指本次OPERATION_EFFECT Acceptance；其Contribution含精确`outcome_binding_id`和`delivery_receipt_ref`。互相核对ID/hash/Mission/Operation/实际milestone。
- 唯一生产writer是上述`accept_operation_outcome`调用的原DeliveryReceipt writer；旧writer对新lane的操作用途增加强制验证。接受裸DeliveryReceipt DTO不能绕过。
- 生成顺序无hash循环：内存分配Acceptance/Delivery IDs→形成原Acceptance和原DeliveryReceipt内容/hash→形成Contribution→同事务写入并检查交叉引用。DeliveryReceipt不反引Contribution hash。
- `received`默认不生成SENT/CONFIRMED。能否投影到ENQUEUED要看注册milestone定义，不等同于本地outbox已入队；没有合适旧stage可不写DeliveryReceipt，完成证据仍由Scope+OutcomeBinding+Acceptance表达。
- `sent→SENT`、`delivered→CONFIRMED`也须实际policy定义支持；CONFIRMED只是一种显示/交付阶段，不自动证明任意送达语义。
- 非操作的PERSISTED/ENQUEUED通知保留原行为，但绝不用于效果完成。

### 6.4 根完成不依赖delivery_contract是否存在

```text
原根成功公式通过
AND 对当前Spec每个MUST effect存在唯一合法来源的当前效果贡献
AND 当前采用计划/对应Scope覆盖未丢失
AND 原组合审阅和GoalResolution合法
AND 原closeout/未决Operation/费用/交付政策成立
```

最终GoalResolution的effect准则证据包含原Effect Acceptance与本次正式OPERATION_OUTCOME Review/receipt可核验引用。`resolution_commits`的引用validator必须通过CompletionReader追链；不能只检查同Mission和非空OperationId。即使调用方绕过ready直接请求最终Commit，同一检查仍在事务里执行。

completion reader输出的read-set包括 **当前批准Spec、所采用Scopes、effect→intent分支完整集合及各证据身份/Validity epoch**；不能只检查上一次看到的那几个正证据。Requirement更改、新的intent分支或相反receipt在ready后出现，最终Commit必须发现。

## 7. 变化、兼容与缺失规则

- Requirements/milestone改变：新Spec/新Scope；旧贡献和outcome事实原样归档，不直接满足新版。要重用相同外部事实，需新版本的正式outcome审阅及新接受，不重发操作来凑证据。
- 同版要求但准备输入/产物被替换或撤回：旧准备与相应操作的输入关联不能挪到新内容；Validity/purpose复核失败则拒绝新使用。
- T0/T1前Plan变化继续原H1严格规则。T1后无关Plan变化不否认已发生事实；完成引用要证明原owner task/contract、effect slot、requirement和输入仍在当前scope中合法。不能改写原plan provenance，也不要求重发。
- 图退休/取消不抹掉未决动作。UNKNOWN/审批中/无intent都可见且不满足效果；原D3和恢复政策不改。
- 旧协议：不填新表、不改canonical事件/原完成行为。新lane但Scope/Spec缺失：具名阻断最终完成，不推断为纯内容。对已保存的旧新lane贡献，通过原真实Review/Input核验后显式补binding；无法证明则重审，不伪造历史PASS。
- 纯报告：明确CONTENT_ONLY Spec、CONTENT Scope沿正常内容完成；即使Worker另带action candidate，也不能自行增加effect obligation或启动T0。
- 同一义务多个必需效果：逐slot验证，不能按“存在任意一个成功Operation”完成；不能把同一个outcome binding指派给两个effect_key。

## 8. 持久位置、reader与SQL

四张窄表的职责：

关键读取（参数均来自可信上下文，不拼模型SQL）：

```sql

SELECT * FROM operation_completion_specs
 WHERE mission_id=? AND requirements_revision=? AND requirements_hash=?;
SELECT * FROM operation_completion_scopes
 WHERE mission_id=? AND plan_revision=? AND occurrence_id=?;
SELECT s.*, a.* FROM operation_acceptance_scopes s
 JOIN acceptances a ON a.acceptance_id=s.acceptance_id
```

后三项结果必须继续核对原scope/acceptance/review/link/receipt，不能SQL命中即成功。consumer要明确完整集合读取，旧固定limit不能默默丢必需效果。
