## 行为风险与对策

1. **模块搬家后测试打桩失效。** 搬的模块没有被测试按字符串路径打桩（已查 0 处）；用模块别名打桩的，随引用方一起改。每片跑 patch_targets.py。
2. **导入期顺序。** 下沉的是叶子模块，导入它们不再连带加载 deskpet 包入口（派发上下文原来经 deskpet.execution 包入口会加载前台运行时），导入期只会更轻。每片跑启动快照、控制通道快照、启动耗时门。
3. **执行池准入身份与工具清单。** 搬的模块不在工具清单与构建清单的登记里（已查）；构建清单哈希随批次重生成。
4. **SDK 加 `__all__`。** 只影响 `from X import *`；全仓库查无星号导入这些模块后再加。新增的 `__all__` 字面量走禁区放行清单。
5. **公开清单初版"照现状收录"。** 清单的意义是以后不许再扩散；收窄清单（把内部模块搬走）属于阶段 5 拆分的事。

## 裁决（2026-10-15，独立裁决员，模型 Opus 5.5）与修订

四条出入：均同意，附条件。另指出设计里三处事实错误与四处遗漏，已全部按下面修订：

1. **产品代码引用 SDK testing 不是 0**：`backend/deskpet/sdk_adapters/conformance.py` 导入 `simple_harness.testing`，而这个文件只被测试用（3 个测试文件）。修订：把它搬进 `backend/tests/sdk_adapters/`，产品代码对 testing 的引用归零（4.4 一起做）。
2. **产品代码引用 sqlite 包根 4 处**（downgrade、composition、conformance、reset_agent_data 脚本）：计划第 1.1 节把包根定为公开接口。修订：`simple_harness.execution.sqlite` 包根进公开清单，它下面的子模块不进。
3. **公开清单放两份**：`simple_harness` 从不导入 `agent_orchestrator`，一份清单放在 simple_harness 里会把依赖方向倒过来。修订：`simple_harness/public_api.py` 与 `agent_orchestrator/public_api.py` 各列各的。
4. **空包入口**：不加 `__all__`，边界检查拒绝从空包入口导入名字；有内容但没 `__all__` 的包入口，进清单的补上。
5. **字符串打桩不是 0**：两个测试按字符串路径打桩端到端钩子（test_project_rules_component.py、test_context_os_e2e_product_hooks.py），随 4.4 一起改。启动耗时基线里记着 `agent.context_messages`，同片重生成。
6. **分层契约**：模型适配与提供方互相引用、deskpet 与旧 agent 互相引用，两组都写成"同层、不独立"（import-linter 的 `:` 写法），钉死 import-linter 版本。上下文报告 3 条向上引用写进 ignore_imports，由棘轮锁住不许增加。
7. **SDK 部署清单**：4.1 一改 SDK 字节就要同片重生成部署清单（不能等 4.6）。
8. 全量回归是第 3 次（阶段 1、2 各用一次）；计划排期表顺手改。

## 发版前补充决定（2026-10-15）

发版核验员指出：budget_accounts 不在公开清单里，Host 若改从它导入，边界检查会报错。决定：Host 继续从 commit_service 导入预算账户名字（这些名字在 commit_service 的 `__all__` 里，是它的公开接口，一条路径），budget_accounts 作为内部模块不进清单；阶段 3 交接里"Host 两处改从 budget_accounts 导入"一条作废。SDK 不再改动，发版核验回执保持有效。
