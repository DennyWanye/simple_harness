范围：收口后清单里需要动"层与层之间约定"或"触发规则"的四项。第 1 版交独立审阅员（opus，只读核对代码）从架构最佳实践角度挑战，报 3 条阻断、11 条应改、4 条建议；我逐条打开它引用的代码核对，全部属实。本版按裁定改写，第 1 版的错处在各项"第 1 版错在哪"里留底，完整审阅记录在文末。

## A. 重启后重做工具调用被授权记录拒绝

### 现状（第 2 版核准）
- 授权记录按"效果 id + 调用 id"查旧记录，指纹不同就先隔离旧记录再抛冲突：`backend/deskpet/product_state/authorization_saga.py:185-235`。
- 身份哈希含票据指纹（`sdk_adapters/tool_authority.py:2425-2437`）。票据编号是**确定推导**的（`permissions/runtime.py:184-251`，自动模式下 `grant_instance_id = effect_id`），同一调用重签编号不变；变的只有 `expires_at = now + 8h`（第 175、249 行）。所以重放 → 新过期时间 → 指纹变 → 身份变 → 冲突。
- 票据库 `product_state/task_grants.py:37-80` 已按编号存完整票据。`tool_authority.py:2380 restore_facts`（"不做策略读写、直接恢复已核过的冻结授权"）全仓库无人调用。
- 对账把"已取消 / 已过期 / 已撤销"三种终态也判成"确认未开始"（`sdk_adapters/reconciliation.py:27-38`）。

**第 1 版错在哪**：把冲突点写成 `authorization.py:428`（那是票据与身份的一致性校验）；以为每次签发都有新票据编号、要另建按调用的票据存储。都不需要。

### 做法（审阅裁定的更小做法）
`decide()` 开头先用授权记录的 `read_for_effect(效果 id, 调用 id)` 查旧记录；有 → 按记录里的票据编号从票据库取原票据 → `restore_facts` 恢复冻结授权，跳过重签。然后逐项判定：
- 票据过期 → 具名拒绝 `grant_expired`；
- 策略代数 / 策略模式变了 → `policy_generation_moved`；
- 授权记录已在终态（取消 / 过期 / 撤销）→ 具名拒绝，**不能**走到"激活票据"再抛"票据已撤销"（`task_grants.py:96-99`）；
- 参数哈希不同 → 按新调用处理。

### 不动的东西
身份哈希字段集、冲突规则、SDK 对账协议、票据有效期（复用沿用第一次签发的过期时间，不延长）。

### 明确不在本项内
委派服务"从不判确认未开始"的绕行**保留**。审阅指出：交出之后的重放会卡在交出绑定（`authorization.py:280-292`，SDK 交出回执含效果版本与栅栏代数，重启后都变），授权记录状态机里没有"已交出 → 再次交出"（`authorization_saga.py:299-315`）。要换回正常对账需单独设计。

### 测试（先写失败的）
- Host：签发 → 模拟重启 → 同一调用再来 → 复用同一票据、授权记录幂等通过；过期 / 策略代数变 / 三种终态 → 各自具名拒绝；参数变 → 新调用新票据。断言重启前后运行绑定版本与目录代数不变（`tool_authority.py:2454-2455`，否则复用票据仍冲突）。
- 端到端：真机在工具执行中强制退出，重启后运行继续并完成（现有重启验收配方）。

## C. 用户回答带的资料直接进任务

### 现状
- 收口第 6 项真机第 4、5 轮：规划器提问 → 用户回答并给数据 → 规划器没有合法路子把数据交给执行者。opt.90 已让回答进任务级备注，但备注不是文件。
- 资料是**按每次尝试冻结、只读挂载**的（`governance/domains.py:293-297`）：新尝试自动拿到现行版本。所以只要数据成为资料，规划器选"原方法重试"就够了。
- 回答接口只收 ≤12000 字文本、有选项时只能填选项键（`storage/planning_human_store.py:103-125`）；回答会写"规划问题已回答"事件，它本来就唤醒规划器。
- 资料路径必须在域的资料根目录下（`source_commits.py:208-210`；通用域与文档域根目录都是 `sources/`，`domains.py:302`）。信任标记数据库约束只允许 `untrusted_external`（`storage/schema.py:472`；引用校验 `source_dependencies.py:84`、`assessments.py:531` 同）。

**第 1 版错在哪**：路径写成 `answers/…`（会被判找不到，同事务连回答一起回滚）；要在信任标记上区分"用户提供"（约束不允许）；以为要靠 B 的触发和"换输入"决定（换输入只能绑到另一步骤的产出，`planning_decisions.py:1201-1229`，绑不到资料）。

### 做法
- Host 编排层（或 SDK 对外门面）加一条**组合命令**"回答 + 登记资料"：回答带内容时，同一事务里 `register_source(path="sources/answers/<问题id>.md", trust=untrusted_external)`，幂等键由问题 id 推出（重放回答时登记也幂等返回）。不带内容 → 只写回答与备注。存储层不去调登记（分层）。
- "谁提供的"记在事件已有的操作者 / 来源字段，不新增信任等级。
- 不加决定种类、不改规划包、不改模板。规划器在下一轮选"原方法重试"（未通过的步骤）或"提出后继"（已通过的），新尝试自动挂载这份资料。
- 界面：回答框加"作为资料附上"（默认勾选）。

### 测试
- Host：回答带内容 → 同一事务出现 `HumanCommentAdded` + `SourceRegistered`，引用同一问题 id，路径在 `sources/answers/` 下；不带内容 → 只有备注；重放同一回答 → 两者都幂等。
- 真实派发：提问 → 回答带数据 → 规划器原方法重试 → 执行者的冻结输入里有 `sources/answers/<id>.md` → 步骤通过。这就是收口第 6 项要补的那一局。

## B. 资料换版本 / 撤销 → 重新规划

### 现状（第 2 版核准）
- `SourceSuperseded` / `SourceRegistered` / `SourceRevoked`（`source_commits.py:514-560`）编排器里无人听。
- 派发时冻结的 `source_versions` 是**当时范围内全部现行资料**（`event_handler.py:6074-6080`），不是这一步用了哪些。唯一有证据的"用过"是引用谱系（`memory/source_dependencies.py`、`_selection_source_lineage`）。
- 验收时的当前性检查**只在结果里有引用时**才查（`commit_service.py:5019-5045`）；文档域另查选择谱系。终审判"包已过时"只看需求变了 / 贡献变了 / 范围代数变了 / 审阅被打断（`root_review.py:708-755`），**不看资料版本**。
- 修复请求来源是封闭词表五类（`planning/htn/repair_adapter.py:34-45`）；`htn.mark_dirty` → `collect_triggers` 已有循环（`planning_repair_requests.py:94-102`）会产出 `EvidenceInvalidated` 请求，且已有的影响分析沿依赖把下游一起算进去。
- 修复请求只有"提交了细化 / 修复 / 绑定已有目标，且目标与影响范围相交"才被消费（`planning_repair_requests.py:179-202`）；消费不掉的请求会出现在之后每个规划包里、让"还欠修复"一直为真，任何一轮被拒都逼着开新轮直到"修复规划次数用完"任务失败（`event_handler.py:7251-7263`、7873-7879）。

**第 1 版错在哪（两条阻断）**：①以为终审是安全网（"旧版贡献没重做终审会拒"）——不存在；通用任务用旧资料会**静默完成**。②影响范围按冻结版本算 = 之前派发过的所有步骤，全错。另外漏了撤销、"告知"请求消费不掉、新来源没映射进词表。

### 前置（用户 2026-09-29 已定：两条都按我的建议）
1. **通用任务要不要资料当前性关卡？** 现在带资料的通用任务没有任何一关查"你用的资料还是不是当前版本"。选项：(a) 验收时对通用任务也查"冻结版本 vs 当前版本"，旧了就判 `stale_source`（和文档域同口径，但通用任务不引用，只能按冻结版本粗判）；(b) 不设关，靠 B 的触发 + 规划器；(c) 终审加一条"资料版本变了"的过时原因。我的建议：(c) + B，验收不加粗判（粗判会把"冻结了但没用"的步骤也判失败）。
2. **修复请求要不要"已确认无需改动"的出口？** 现在只有计划改动能消费请求。建议加一种消费：规划器用已有的 `DECLARE_RUNTIME_BLOCKED`/`RETRY_SAME_METHOD` 之外的表达？不行，那是新决定语义。可行的最小做法：由**系统**消费——请求的影响范围里所有步骤都已重新验收通过（或已被后继替代）时，系统记 `PlanningRepairAddressed`。这样不改协议。

### 做法（前置定下后）
1. 换版本 / 撤销：对**有证据**的受影响步骤调 `htn.mark_dirty`（映射为"证据失效"），由已有循环产出请求，不自建遍历：
   - 正在跑的步骤：按冻结版本判定（它们确实拿着旧挂载）→ 脏；
   - 已通过的贡献：只按引用谱系有引用该路径的 → 脏，标"建立在旧版资料上"；
   - 未派发的步骤：不算（下次派发自动拿新版）。
2. 新登记资料（含 C 的回答资料）：**不发请求**——下次尝试自动挂载；规划器已因"问题已回答"被唤醒。
3. 撤销比换版本更需要重新规划：同上处理，且引用了被撤销资料的已通过贡献必须脏。
4. 去重沿用 `dirty:` 键。

### 不动的东西
验收时的引用当前性检查；规划决定协议、规划包版本、模板。

### 测试
- 单元：换版本后只有"在跑且冻结旧版"与"已通过且引用了它"的步骤被标脏；未派发不算；新登记不产生请求；撤销让引用者脏；同一事件不重复。
- 真实派发：A 已通过且引用旧版、B 在跑 → 换版本 → 请求影响范围 = {A, B} → 规划器对 B 原方法重试、对 A 提出后继 → 第 2 版计划完成。

## D. 按角色换模型 / 失败升级 / 服务商回退（推迟）

### 现状（第 2 版核准）
- 任务选池后所有角色同池：`event_handler.py::_router_for`（1173-1198）、`_validate_mission_profile`（1112-1137）。每个原生池一个 ARP 执行库（`native_plane.py:373`）。路由器本身支持按角色 / 升级 / 回退（`runtime/model_router.py:155-161`、288-310）。
- 策略版本里的路由只读"按任务种类"和"几次失败后升级"（`event_handler.py:1119-1127`、1205-1220）；按角色 / 升级阶梯 / 回退只在部署级规则里，**不按任务冻结**；用户已关策略晋升。
- 升级计数现在包含格式错误（`envelope_invalid`）与服务商解析错误（`turn_failed` + `provider_error`）：`model_router.py:45-51`、325-334。

### 原设计真正要保的三条不变量（审阅裁定）
1. 每个请求派发时冻结自己的池，重启恢复按请求找库（尝试带 `runtime_profile_id`）。
2. 准入身份与价格快照各池独立，不合并。
3. **任务的路由由创建时冻结的事实决定**（`_router_for` 注释、`_frozen_default_route`）。

### 做法（"任务主池 + 角色覆盖"，改法按裁定修正）
- **D1 角色覆盖**：创建任务时把"主池 + 非执行者角色的覆盖池"一起冻结进任务记录；`_router_for` 从冻结值构造 `RoutingRules(default=主池, by_role=覆盖)`，不读部署级规则（保不变量 3）。`_validate_mission_profile` 的冲突判定只对执行者角色与任务种类生效。单步预算下限按请求实际所在池取。任务级令牌总账仍在编排器一处。**开工前核实**：审阅员的工具绑定走编排器共享网关（`event_handler.py:6572-6586`），原生平面下跨池审阅是否会撞上按池划分的工具目录。
- **D2 执行者升级**：只在同上下文大小的池之间定义阶梯；计数改为只数"模型做错"（`failure_classes`），这是路由语义变化，**同时升路由器版本号**（`model_router.py:31`）。技能工具两池都要声明，否则拒绝该阶梯配置。升级计数与"每步非模型失败合计 6 次停下"分开。
- **D3 服务商回退**：与现有"服务出错原地重试、不扣次数"重叠，价值最低，最后做或不做。

### 前置
第二个模型作为独立执行池接入（自己的执行库、准入身份、价格快照、技能工具声明）。用户已决定不做 DeepSeek 官方端点；候选 Grok（密钥 6 小时寿命，要看门狗续期）。

### 测试
单元：角色覆盖只影响非执行者；覆盖执行者被创建事务拒绝；升级只数模型做错；重启后新请求路由与创建时冻结一致。真实派发：执行者池 A、审阅池 B，两库各自记账，总账 = 两池之和。真机：一局带发布任务在 D1 下走完。

### B 已实施（SDK opt.92）
- **触发**（`planning_repair_requests.source_change_triggers`，在 `collect_triggers` 里先跑）：对每条 `SourceSuperseded` / `SourceRevoked` 事件算有证据的受影响对象——正在跑（非终态）且冻结版本等于旧版（撤销则任何版本）的尝试；已通过（`verification_state=DONE`、`verdict=PASS`）且 claims 引用了该路径旧版的结果。有 → 一条 `EvidenceInvalidated` 修复请求（`trigger_refs` = 这些尝试 / 结果 id，影响范围由既有影响分析沿依赖算到下游；`source_key = "source:<事件幂等键>"` 去重；detail 记 reason / path / old_version / new_version / affected）。没有 → 只记一条 `SourceChangeAssessed`（同键），下一轮不再重算。新登记的资料不发请求。
- **前置 1**（`root_review.py`）：切包事件多记 `source_versions_hash`（现行资料 path→version 集合的哈希；域没有资料根目录记 None）；`stale_reasons` 比对现值，变了报 `SOURCES_MOVED`，包按既有机制重切。
- **前置 2**（`planning_repair_requests.settle_addressed_requests`，同样在 `collect_triggers` 里先跑）：未处理的请求，影响范围没有新增工作、且每个受影响的**叶子**步骤（任务 / 步骤实例 / 尝试 / 结果 / 验收 id 都折算到叶子任务；复合目标与采纳的方法实例经叶子了结）都有晚于请求的 `AcceptanceCommitted` 或 `TaskCompleted` 时，系统记 `PlanningRepairAddressed`（`decision_type=SYSTEM_REVALIDATED`、`decision_id=None`、`settled_by` 记每个任务的验收事件键）。影响范围含义务 / 操作 / 其它只认计划改动的对象时不由系统消费。
- 与第 2 版的差异：受影响判定没有走 `htn.mark_dirty`（脏标记是有效性重检的语义，会牵动重用钉住），而是直接以尝试 / 结果 id 作触发引用记请求——影响分析的传递性一样保留。
- **opt.93 修正（用户 2026-09-30 要求做的小改）**：真实模型第 1 局（`.local-test-evidence/2026-09-30/b-real/`）里，尝试还在跑时当轮发请求，规划器只会回 WAIT 等它跑完，修复轮又拒绝 WAIT，白花两轮规划次数。改为：拿着旧版**还在跑**的尝试先不评估，等它到终态再评估——它跑完后验收本来就对照当前资料（审阅员按现行版本判、引用按当前性判），被拒走普通的验收失败请求；评估记录把拿旧版跑过的尝试记在案（`affected.attempts_on_old_version`）。资料变更本身发请求的情形只剩"已通过的结果引用了旧版"。
