# 阶段 5 偏差单：解环（5G）与"公开名字只走门面"规则的冲突

日期：2026-10-16
依据：
- 整治计划 5G：SDK 标了"循环依赖"的函数内导入从 87 降到 ≤ 30，做法同 3.3（共用部分抽到下层模块，或改成参数传入）。
- 阶段5-偏差单-存储类拆分.md 的裁决口径：子包以外的代码导入公开名字只能走公开模块（门面）；子包内部从定义处导入。已由 tests/test_facade_import_paths.py 锁住。

## 实测

现有 86 处，静态导入图上全部仍成环（scripts/code_quality/cycle_paths.py 列出每处最短成环路径）。其中有一类环是门面规则直接造成的：

- 存储组（7 处）：store_domains/core 与 events 要按需导入 source_records、assurance_changes。环路：source_records → store（门面，只为取 StoreError）→ store_domains.* → core。assurance_changes → assurance_work → store（门面，取 Store、StoreConflict）→ … → core。
- 规划人工存储组（6 处）：planning_human_store 从 store 门面取 StoreConflict、从 htn_store 门面取 HtnStore、从 hierarchical_dispatch 门面取 append_hierarchical_event；而 store_domains.core → schema → planning_human_store 在顶层。
- 分层派发相关的若干环也经过 hierarchical_dispatch 门面。

门面要在顶层导入全部 mixin 才能组合出类。所以任何"被某个 mixin（顶层或经由别的模块）依赖、又要用门面里某个记录/异常类型"的下层模块，只要走门面就必然成环。按现行规则，这几组只能一直留在函数内导入。

## 选项

- **A 维持规则，这几组不解。** 5G 的 ≤ 30 要从其余组里凑。其余组多是两个业务模块直接互相导入（31 处长度为 1 的环），要逐个抽共用定义，工作量大，且凑不凑得够没把握。
- **B 给规则加一条窄例外：同一个包（如 agent_orchestrator.storage）里、处在门面"下层"的模块，从子包的 records/support 直接导入记录与异常类型。** 门面仍是包外唯一路径。守卫测试改为按"导入方是否在门面所在包里"判定，并列出允许直接导入的名字只限 records/support 里的定义（不含 mixin 类、公共基类）。
- **C 把这些下层模块也挪进子包。** source_records、assurance_changes 有包外使用方（observability、commit_service_domains、policy_commits、method_library_store 等），挪进去后它们又要经门面转出，门面变胖，且同样会碰到环。

## 我的建议

选 B。理由：records/support 本来就是"最下层、只有数据定义"的模块，下层模块直接依赖它正是 3.3 说的"共用部分在下层"。例外只在门面所在的包内部生效，包外仍只走门面，SDK 公开接口不变。

## 待裁决

1. 选哪个？
2. 如选 B，例外的精确边界怎么写进计划与守卫测试？
3. 5G 的 ≤ 30 目标是否维持（目前 86，按 B 解掉门面相关的约 15 处后，其余仍需逐个抽共用定义）？

有出入的：

2. 规划人工存储组 6 处数对，但成因写错了：

   - 对 hierarchical_dispatch 的 3 处（80、177、270），从定义处 support 导入也成环。路径是 support → plan_commits → method_plan_reviews → planning_human_store。B 解不了这 3 处。
3. "按 B 解掉门面相关的约 15 处"估多了。模拟结果：

   - 只做 DDL 下沉：解 3 处（60、120、241）。

4. 分层派发那 13 处经过门面节点，是因为门面在顶层组合 mixin，mixin 又在顶层导入业务模块。它们大多不是"从门面取名字"。从门面取名字的只有 method_plan_reviews:253、deployment/root.py:285 和上面 3 处。只有 root.py 改从 support 导入能解，而且是跨包。
5. assurance_work 的 Store 只出现在类型标注里（语法树核实，文件有 `from __future__ import annotations`）。可以挪进 TYPE_CHECKING，不需要例外。它需要例外的只有 StoreConflict。
6. C 的事实对。source_records 包外有 business_replay、method_library_store、mission_lifecycle 和 1 个测试。assurance_changes 包外有 policy_commits、htn 的 semantics_methods 和 1 个测试。assurance_work 包外有 20 多个模块。C 比单子说的更不可行。

### 二、裁决：选 B 的收窄版，再加一项 D（表结构下沉）

D 表结构下沉：

- planning_human_store 的 DDL 逐字搬到新模块 storage/planning_human_schema.py。
- schema.py 改从新模块导入，别名 DDL_V24 不变。
- planning_human_store 的 `__all__` 去掉 DDL。全仓库只有 schema.py 导入它，后端没有。
- 理由：这正是 3.3 说的"共用部分下沉"。它不碰门面规则，解 3 处，和现有 13 个 *_schema.py 的做法一致。

B 收窄：

- 不按"同一个包"放开，按显式清单放开。
- 理由一：按包放开，storage 里 19 个模块从门面取名字，它们会同时有两条合法路径，违反一条路径。
- 理由二：按包强制改，要动 19 个模块，而组合类 Store 仍要从门面取，一个文件两处来源。
- 显式清单只有 2 条，每个导入方仍只有一条合法路径（由清单决定）。这与 10-15 裁决"按位置定路径"的口径一致。

否决：

- A：放弃能解的 9 处，没有理由。
- C：前提不成立，见第一节第 6 条。
- B 原文（按包放开）：见上面理由一、二。
- 把例外扩到 hierarchical_dispatch：support 不是纯定义模块（顶层导入 plan_commits、htn_store），放开也解不了 planning_human_store、method_plan_reviews 的环。只多解 root.py 1 处，不值得开跨包例外。

### 三、回答待裁决三问

1. 选 B 收窄版加 D。
2. 例外的精确边界：
   - 只对 `<门面>_domains/records.py` 生效。
   - 该 records 模块的顶层导入不许指向门面所在包。现只有 store_domains/records 满足（只导入 contracts）。htn_store_domains/records 顶层导入 store 门面，不满足。
   - 导入方只限显式清单。每条写导入方、名字、成环路径。现清单 2 条：storage/source_records.py 的 StoreError；storage/assurance_work.py 的 StoreConflict。
   - 清单内的导入方，这些名字只能从 records 导入，不许再从门面导入。
   - 只许异常类、记录类、常量。组合类、mixin、core 基类不在例外内。组合类只作标注的，挪进 TYPE_CHECKING。
   - 清单要加条目，先写偏差单。
   - 守卫写进 tests/test_facade_import_paths.py：清单与实际导入双向集合相等。附三个改坏检验：清单外文件加这类导入，红；清单内文件改回门面导入，红；清单多一条没有对应导入，红。
3. ≤ 30 不维持。改为 ≤ 40。依据：
   - 起点按现在的 66 算。
   - B 加 D：减 9，到 57。
   - 长度 1 里一侧只用小定义的，抽样看了全部 23 对。容易抽的约 8 处：WEIGHTS 与 ALLOCATOR_VERSION 常量、4 行的 OperationMaterializationInputError（顺带解 action_commits:973）、2 行的 audit_hash 与 audit_error_code、5 行的 read_binding、6～9 行的 held_guarded_grants 与 held_legacy_slots、5 行的 managed_elsewhere、9 行的 WorkflowSpawnToolContext。到约 49。
   - 换边（一侧多处函数内导入时，挪到少的一侧）再减约 4，中等难度的几对（assurance_purpose_reviews 三角、observability、assurance_reads 与 assurance_blobs、system_operations 与 operation_runtime）再减约 5。到约 40。
   - 剩下约 35～40 处集中在三团：分层派发门面加 mixin 的枢纽（13 处）；completion_inputs、leaf_acceptance、resolution_commits 这一团（约 8 处）；运行驱动包与执行存储包的包根。还有 justifications 与 bounded_closure、runner 与 replay、delegate 与 agents.runtime 这类大类互相依赖。
   - 拆这几团要改顶层导入顺序和协作关系，属架构调整。5B.3 已定这类事不在本计划内。
   - 所以 ≤ 30 只能靠架构调整或改标注释达到。前者越界，后者是造假。≤ 40 可达且仍要实打实做。

关于换边：

- 换边只是把函数内导入挪到出现次数少的一侧，环还在。
- 它确实减少函数内导入，可以算数。
- 实施记录里单独计数，不叫解环。
