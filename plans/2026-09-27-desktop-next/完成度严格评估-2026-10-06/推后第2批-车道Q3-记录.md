### 1.1 T09：策略行改经存储层，补四个读写接口

**原计划原文**（`plans/TaskGraph/v1/simpleharness-taskgraph-code-execution-plan.zh-CN.md`）

- 第 307 行（§6.2 写入者与读取者）：`taskgraph_policy_bindings` 的唯一写入口是认证过的 `enable_taskgraph_contract()`，读取方是 `TaskGraphStore.policy`。
- 第 318 行（§6.3）：接口放 `storage/taskgraph_store.py`，组合原 Store 连接，不自建连接。
- 第 321 行：`policy(mission_id) -> PolicyBinding | Missing`。
- 第 322 行：`insert_policy(binding, receipt) -> PolicyBinding  [需外层事务]`。
- 第 325、326 行：`list_member_pins(mission_id, revision)`、`list_method_pins(mission_id, revision)`。
- 第 339 行：`insert_*` 同键不同哈希是冲突，不用 `INSERT OR REPLACE`。
- 第 1097、1098 行（启用第 5、6 步）：同一个写事务里写策略行、版本化事件、命令回执；同一任务已有不同策略不改旧行。

**现状**

- 写：`SDK/orchestrator/taskgraph_policy.py:137-149` 在服务里直接 `SELECT` 旧行、直接 `INSERT INTO taskgraph_policy_bindings`。
- 读（带回执核对）有三份，各写一遍同样的核对：
  - `SDK/orchestrator/taskgraph_policy.py:60-78` `read_installed_graph_policy`；
  - `SDK/storage/taskgraph_store.py:126-142` `TaskGraphStore._verify_policy`；
  - `SDK/orchestrator/taskgraph_sources.py:70-80` `read_structure` 里内联一份。
- 只取启用命令号的直读：`SDK/orchestrator/taskgraph_sources.py:121-122`、`SDK/orchestrator/taskgraph_operator.py:36-37`。
- "绑定没有"的直读：`SDK/orchestrator/plan_commits.py:334-337`、`SDK/orchestrator/taskgraph_followups.py:145`，与存储层已有的 `require_bound`（`SDK/storage/taskgraph_store.py:58-66`）是同一件事。
- 钉的读：`TaskGraphStore._pins`（`taskgraph_store.py:112-124`）内联读三张钉表；`SDK/orchestrator/taskgraph_dispatch.py:107-110` 另直读 `taskgraph_member_pins`。
- `policy / insert_policy / list_member_pins / list_method_pins` 四个接口不存在。

**改成什么**

1. `InstalledGraphPolicy`（策略正文）从 `orchestrator/taskgraph_policy.py` 挪到 `storage/taskgraph_store.py`（存储层不能反向依赖编排层）。新增 `PolicyBinding`（任务号、内核版本、策略正文、启用命令号、回执哈希、回执、写入时间）。
2. `TaskGraphStore.policy(mission_id)`：没有行返回 `None`（即原计划的 Missing）；有行就核对正文规范、正文哈希、启用回执（种类、任务、内核、策略哈希、命令号、回执哈希）、部署验收来源通道，不过就按名字抛 `StoreError`（沿用现有码 `TASKGRAPH_POLICY_RECEIPT_CORRUPT` 等）。
3. `TaskGraphStore.insert_policy(binding, receipt)`：必须在外层事务里；核对回执与绑定一致；同任务已有完全相同的行就返回它，有不同的行就抛 `TASKGRAPH_POLICY_ALREADY_BOUND`；写入后用 `policy()` 读回返回。
4. `TaskGraphStore.list_member_pins / list_method_pins`：按（任务、版本）读，按编号排序；`_pins` 改用它们。
5. 调用方收口：
   - `enable_taskgraph_contract` 改为：先写命令回执，再 `insert_policy`，再记事件（同一个事务）。服务里不再有策略表 SQL。
   - `read_installed_graph_policy` 只剩"要一份已安装策略"：调 `TaskGraphStore.policy`，没有就抛 `TASKGRAPH_POLICY_UNAVAILABLE`。
   - `_verify_policy` 改调 `policy()`，把 `StoreError` 转成原来的 `GraphIntegrityError`（错误类型不变）。
   - `taskgraph_sources.read_structure` / `read_seed_structure`、`taskgraph_operator` 改从 `PolicyBinding` 取策略和启用命令号；`read_structure` 把 `StoreError` 转成原来的 `SourceUnavailable`。
   - `plan_commits`、`taskgraph_followups` 的"有没有绑定"改调 `require_bound`。
   - `taskgraph_dispatch` 的钉核对改调 `list_member_pins`。

**删掉哪条旧路径**：服务里的策略表直写；三份重复的回执核对只留 `policy()` 一份；两处启用命令号直读；两处绑定存在直读；调度里的钉表直读。

**不动的**：`require_bound` 本身（已在存储层，只看有没有绑定、不做回执核对，热路径用）；`taskgraph_notifications.tick` 列出所有已绑定任务、`recovery_coordinator` 数已绑定任务、`commit_service._terminal_binding` 查"是否在任何版本里当过成员"——这三处是读、且原计划接口清单里没有对应接口，记进第五节留给主会话，不在本条扩接口。

**守什么保证**：策略行只有一个写入口、写入在外层事务里、同键不同内容是冲突不覆盖；读策略必须带原启用回执；各边界抛出的错误类型不变（存储层 `StoreError`，历史读 `GraphIntegrityError`，来源读 `SourceUnavailable`）。

**怎么测**（新文件 `tests/orchestrator/full_target/taskgraph_exec/test_t09_policy_store_interfaces.py`，先红后绿）

- 四个接口存在；没绑定时 `policy()` 返回 `None`。

- `insert_policy` 不在事务里被拒；同任务写不同内容被拒（冲突）、写相同内容返回原行。
- 静态守卫：`orchestrator/` 下除存储层外，源码里不再出现 `INSERT INTO taskgraph_policy_bindings`，也不再出现 `FROM taskgraph_policy_bindings WHERE mission_id`（单任务读）。

- 相关老文件：`test_production_seed.py`、`test_taskgraph_required.py`、`test_commit_atomicity.py`、`test_read_not_enabled.py`、`test_read_history_protocol.py`、`test_revision_read_cache.py`、`test_view_contracts.py`、`product_world/test_unbound_legacy_mission.py`、`full_target/test_plan_commits.py`。

**按核心思想自查**：这是写入口和读核对的秩序问题（谁能写、写在哪个事务、读时核对回执），不涉及任何语义判断；只删重复路径，不加新分支、不留兼容。

### 1.2 K06：检索的图距离、分支相关按分层结构算

**原计划原文**（`plans/taskSys2/agent-orchestration-layer-complete-design.md`）

- 第 669～689 行（§10.1）：检索综合"语义相关性 + Task DAG 距离（第 676 行）+ 知识可信等级 + 知识新旧 + 分支相关性（第 682 行）+ 历史复用价值 − 重复内容 − 已被取代内容"。

**现状**

- `SDK/context/retrieval.py:119-154` `dag_proximity` / `_ancestor_ids` / `_roots` 按 `Task.dependency_ids` 算：自己或依赖祖先 1.0，同一依赖根 0.6，其余 0.3。
- 分层计划下 `Task.dependency_ids` 恒空（`SDK/orchestrator/worker_context.py:6` 模块说明）。所以除了自己，所有知识都是 0.3，等于常数（对照 C3）。
- `SDK/orchestrator/event_handler.py:10464` 为此专门读一遍全部任务行（`all_tasks`），只传给检索用。

**改成什么**

1. 新增 `SDK/context/retrieval.py` 里的 `GoalTree`（纯数据、纯函数）：由分层网络快照建。
   - 树边：每个已采用做法实例的"被细化目标出现"→"它的子出现"（`effective_goal_occurrence_id` → `child_bindings`），根是 `root_occurrence_ids`。
   - 先后边：网络里的数据边（生产者→消费者）与顺序约束（前→后）。
2. 两个打分分量都从结构读：
   - `proximity`（图距离）：在"树边 + 先后边"的无向图上，从这一步的出现到知识来源步骤的出现的最短边数 d，取 `1/(1+d)`；自己是 1.0；不连通或来源步骤已不在现行计划里是 0。
   - `branch`（同一分支）：在目标树上，两者最近公共祖先的深度占这一步深度的比例（这一步在根上时算 1.0）。同一做法下的兄弟步骤高，跨顶层分支是 0。
   - 一个步骤有多个出现（共享）时取最好的一对。
3. 权重：原 `proximity` 1.0 拆成 `proximity` 0.5 + `branch` 0.5，普通最高分仍是 7.0，明确引用 8.0 仍压过它。`RETRIEVAL_VERSION` 升为 `retrieval-v4-hierarchy-structure`。
4. `rank_knowledge` 的参数 `tasks_by_id` 换成 `goal_tree`。`_gather_knowledge` 从同一份网络建树；网络读不到就抛 `RetrievalUnavailable`（调用方按配置降级或拦住，不假装"没有知识"）。`_next_attempt` 里网络只读一次，K04 的父目标/上游也用这一份。
5. 先后边一并算进图距离，理由：分层执行图的"DAG"就是分解边加先后边；只算树边时，两层计划（根下直接挂一排步骤）里所有兄弟距离都是 2，又退回常数，"相关上游"挑不出来。这仍是结构顺序，不看内容。

**删掉哪条旧路径**：`dag_proximity`、`_ancestor_ids`、`_roots` 整段删；`_gather_knowledge` 的 `tasks_by_id` 参数和 `_next_attempt` 里只为它读的 `all_tasks` 删。不留按 `dependency_ids` 的回落。

**守什么保证**：同一任务内只排本任务知识（权限预过滤不变）；去重、已取代、超上限、零相关丢弃都不变；排序结果确定（同分按编号）。

**怎么测**（新文件 `tests/orchestrator/step04/test_k06_hierarchy_retrieval.py`，先红后绿）

- 纯函数：手工建一棵两层目标树（根 → A、B 两个复合目标；A → 步骤 a1、a2；B → b1、b2；a1 → a2 有数据边）。给 a2 排序：来自 a1（相关上游）的知识距离最近、同分支最高；来自 b1、b2 的距离远、同分支 0。
- **超上限用例**：五条内容同等相关的知识，分别来自 a1、b1、b2、根下另一个分支的步骤、已不在计划里的步骤；`limit=1` 时挑出的是 a1 那条，其余进 `over_limit`。
- 两层平面计划（根 → s1、s2、s3，s1 → s3 数据边）：给 s3 排序，`limit=1` 挑出 s1（上游），不是 s2。
- 产品同形：用 `production_fixture` 两步链跑完一局，从真实网络建树，`continue` 步看 `write` 步距离 1。
- 改相关老文件：`step04/test_retrieval_context.py` 的排序用例改用目标树。相关老文件还有 `test_batch2_h_context_attribution.py`（K04 共用网络读）、`step08/test_policy_snapshot.py`（版本号差异）。

**改坏**：把 `proximity` 改回对所有非自己来源返回常数，超上限用例应红。

**按核心思想自查**：只按计划结构（树和先后边）排序，是"给执行者看什么、先看哪条"的秩序；不看知识内容说了什么，不加关键词或任务名规则；用不用、怎么用这些知识仍由执行者判断，它也还能用知识工具翻全目录。
