# HTN 一致性补改 — 阻断核验

- 日期：2026-10-04
- 范围：`git diff 57560720..HEAD -- sdk backend tauri-app`（提交 bbce635b、99788b2f、5dfaaade、b6c09637、f02f6856）
- 口径：只报会让主流程出错或卡住的缺陷；风格、可以更好但不出错的地方不报
- 验证：只跑了一个临时用例（放在临时目录，跑完已删，没有改仓库代码）：按"第 1 步验收后、改要求前"和"任务完成后"各取一次任务快照，"不再算数的步骤"都是空的（1 passed）。确认了正常情况下已验收的步骤不会被误报成"不再算数"（原有用例只测了"不再算数"这一种情况）。

## 结论：阻断 1 条

### 阻断 1：停下后核对结果的通知扫描没有放进"按任务分开兜错"的边界，出一次错整个编排循环每轮都卡在第一步

- 位置：`sdk/simple-harness-sdk/src/agent_orchestrator/orchestrator/event_handler.py` 的 `_notice_actions_settled_after_stop`，由 `_reconcile_actions` 末尾调用（第 2210 行附近）。
- 问题：`_reconcile_actions` 里逐个动作的核对都放在 `_mission_round`（按任务分开兜错）里，新加的这段扫描却直接写在外面。它要跨所有已停的任务读任务、读动作、查证明、开事务写事件和通知请求，其中任何一处抛出异常（比如某个任务的数据读出来校验不过、写事件时被库约束拒绝），异常都会直接冲出 `_reconcile_actions`。
- 什么情况下出错：`run()` 一开头就调 `_reconcile_actions()`（第 2252 行），所以这个异常会让每一次 `run()` 在第一步就退出。Host 的 `_drive` 接住后只是计数、退避、重建，下一轮还是同一行出错，结果是所有任务（包括新建的）都不往前走，Host 最后进入"编排循环连续失败"的降级状态。一个已经停掉的旧任务的坏数据，就能把整个编排卡死。本项目已有的约束（`_round_boundary` 的说明）就是：全局扫描里每个任务那一份都要包在边界里，出错只算那个任务的。
- 触发概率：目前没找到必然触发的路径（只扫最终报告里带 `unresolved_actions` 的任务，旧数据进不来），但后果是全局卡死、每轮都重复，所以算阻断。
- 建议修法（几行）：循环里每个任务那一份包进 `with self._round_boundary(str(mission_id), "settled_after_stop"):`，扫描结束后和其它全局扫描一样调一次 `await self._settle_parked_faults()`（`_reconcile_actions` 本来就是 async，可以直接 await）。补一个用例：让其中一个已停任务读取时抛错，另一个已停任务的核对结果照样发出通知，`run()` 不抛异常。

## 其余重点逐项结论（都不是阻断）

1. **`_notice_actions_settled_after_stop` 的开销、写库、只发一次**：每轮不写库，只读。写库只在"列出的动作这次刚有结果、而且还没发过"时发生一次；用幂等键 `ActionSettledAfterMissionStopped:<动作>:<状态>` 先查再写，和 `_emit` 拼出的键完全一致（events 表这一列有唯一索引）。列出的动作有结果后状态就不会再变，所以每个动作最多通知一次；用例也测了只出一条。开销：每次核对都会把所有"已取消/已失败"任务的 JSON 用 `json_extract` 扫一遍，已停任务越多越慢，但只在每次 `run()` 开头、每 50 个有进展的轮次、空闲收尾时各跑一次，频率由 Host 的节拍控制，不会空转、也不会占满 CPU。异常问题见上面阻断 1。
2. **`_note_unresolved_actions` 在三处停任务的事务里调用**：在同一个连接、同一个写事务里读动作和操作关联，读到的就是事务里的最新数据，安全。`runtime/operation_reconciliation.py` 顶层只导入 contracts/storage 和 runtime 里的模块，不导入 orchestrator，而且 commit_service、event_handler、actions 里都是函数内导入，不会循环导入。
3. **`_failed_unproven` 改写**：原来的条件是"失败 + 至少交出去一次 + 没在等人 + 有操作关联 + 没有存好的证明"；改写后是"失败 + 没在等人 + `action_outcome_unresolved`"，而后者对失败状态正好检查"至少交出去一次 + 有操作关联 + 没有证明"。语义完全一样。
4. **`precondition_triggers` 会不会每轮重复发请求**：去重键是"步骤编号 + 这组前提摘要的哈希 + 前提纪元"。开工许可的编号本身由（步骤、纪元、证据版本、范围、前提集合）算出，同一轮重算拿到同一个编号，不会新增行；纪元只在某个观察真的从真变假/从假变真、或用户改要求时才加一。所以同一组前提每翻一次只记一条请求，不会每轮重复。已经开过工（有尝试）的步骤跳过，前提真假未知的也不触发，符合方案。
5. **快照里的 `steps_no_longer_counting` 开销**：每个当前有效的验收会做一次完成度读取（几条查询），步骤数几十个时是毫秒级到几十毫秒级；任务详情本来就会读规划网络、预算去向等，这次是同量级的追加，不会卡住。读不出（ContractError/StoreError）时返回空列表，不会让任务详情整个报错。临时用例确认正常情况下不会误报。
6. **contracts 删字段**：删了 `phase`、`authority_ref`、`satisfaction_policy`、`PREFERENCE`。解析是严格模式，旧数据里带这些字段的任务会读不出来——开发期不要求兼容，可以接受。新建任务：全仓库（SDK、Host、前端）已经没有任何地方再写这些字段，部署清单和变异资产也一起更新了，新建任务不受影响。任务列表只读任务行本身，不解析这些结构，旧任务读不出也不会把列表弄挂。
7. **Host `pending_notices` / `_notice_line` / settings**：每条未确认的通知按主键查一次事件，代价很小；`_notice_line` 两种卡片的字段都有兜底。settings 改成默认 512K、只有显式写 262144 才用 256K；两种窗口的执行池都照常注册，只影响新建任务选哪个池，已有任务仍用它冻结时的池，不会让已有执行池起不来。

## 附带观察（不算阻断，记一笔）

- `fail_planning`（规划失败停任务）和"任务要求没达到"判失败这两条停任务的路径没有调用 `_note_unresolved_actions`。如果对外操作已经交出去了，这两种停法的最终报告里不会列出结果不明的操作，之后也不会补发核对结果。不会卡住或报错，只是 H-2 的承诺在这两条路径上没做到；要不要补由主会话定。
