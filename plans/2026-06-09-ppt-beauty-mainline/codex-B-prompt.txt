== B-1：修 receipt 序列化(registry.py) ==
根因：execute_tool(~line 686) 把 per-session 注入上下文 merge 进 merged_params：
    merged_params.update(self._session_context.get(session_id, {}))  # 注入 _session_id / _image_worker / _write_scope_root 等
    merged_params.update(dict(params or {}))
然后 ~line 818 建 receipt 时 `args=dict(merged_params or {})` 把整个 merged_params(含 _image_worker 这种不可 JSON 序列化的对象)塞进 receipt → receipt_store_provider 序列化 args 时炸 → line 827 warning。
修法：
- 建 receipt 的 args 只用「LLM 真正传的参数」或至少剔除注入的内部键。最稳：定义内部注入键前缀约定——所有 _session_context 注入的键都以 "_" 开头(_session_id/_image_worker/_write_scope_root 等)，建 receipt 前过滤掉以 "_" 开头的键：
    receipt_args = {k: v for k, v in merged_params.items() if not (isinstance(k, str) and k.startswith("_"))}
  用 receipt_args 替换 line 818 的 `args=dict(merged_params or {})`。
- 额外稳健：即使过滤后仍有非 JSON 值，receipt 序列化也不该让工具执行报 warning/失败。确认/保证 receipt 构建对不可序列化值兜底(若 receipt 模型/provider 自己 json.dumps，加 default=str 或 try/except 降级)。最小改动优先用上面的前缀过滤；若 receipt_store_provider 内部还会炸，补一层 best-effort(default=str)。
- 不要改 execute_tool 的工具执行语义(merged_params 仍照常传给 handler，注入键工具照常能用)；只改「进 receipt 的那份 args」。

== B-2：修工具路由(让"生成图片"走 generate_image 不走 web_fetch) ==
根因分析：capability_gate PASS 后，整个 toolset(含 web_fetch + generate_image)都给 LLM，gpt-5.5 对「生成一张图片并保存到本地」误选了 web_fetch(把它理解成"下载网图")。这是工具描述区分度不够。
请先读 image_tools.py 的 _SCHEMA["description"] 和 web_tools.py 里 web_fetch 的 description，然后：
- 强化 generate_image 描述：明确「**AI 文生图/原创生成**图片(画/生成/做海报/插画/图标/头像)时**必须用本工具**；本工具会真生成并保存到本地返回路径。**不要用 web_fetch/网页搜索去找图**」。
- 弱化/澄清 web_fetch 描述：明确「web_fetch 用于抓取**网页文本内容**做调研，**不是用来生成或获取图片**；用户要生成/画图片请用 generate_image」。(若 web_fetch 描述里有诱导"下载/图片"字样，去掉或限定。)
- 不改这两个工具的入参 schema/handler 行为，只改 description 文案。
- 注意：真正验证 LLM 路由对不对需要真机 live test(relay+LLM)，本任务只把描述区分度做到位 + 单测覆盖「描述含正确关键词」。在最后说明这点。
