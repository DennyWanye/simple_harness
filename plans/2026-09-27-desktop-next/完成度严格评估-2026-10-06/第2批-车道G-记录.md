# 第 2 批 · 车道 G（知识与黑板）记录（2026-10-06）

工作树 `simple_harness-b2g`，分支 `batch2-g`，基线 main `63337eff`。四条：K01 审阅员黑板读工具、K03 规划器读黑板、K05 读后复核、K02 知识三字段（迁移 45）。全部完成，各带测试与一次改坏。

## 一、每条做了什么

### K02 知识记录补三个字段（迁移 45）

- `memory/verified_knowledge.py`：`KnowledgeRecord` 加 `validity_interval`（三键对象：`valid_from_ms`、`valid_until_ms`（可 None）、`mission_epoch`）、`permitted_uses`（字符串元组）、`assurance_level`（文本）。默认都是 None。形状不对拒绝。
- `storage/schema.py`：`DDL_V45` + `Migration(45, "orchestrator-knowledge-validity-uses-level")`。表重建照迁移 43：新表、整行搬过去、删旧表、改名、索引重建。旧行三列 NULL（开发期不兼容旧数据，不从旧 JSON 猜）。knowledge 表没有触发器。
- `storage/store.py`：`upsert_knowledge` 三列与 JSON 同一次写入。None 落 NULL。
- `orchestrator/commit_service.py`：验收时把这次用的使用证书（`licensed.certificate`）也交给 `_grade_and_project`；新函数 `_knowledge_registration`。审阅确认入库的知识：有效期取证书的 `issued_at_ms` / `not_after_ms` / `mission_epoch`；保障等级取任务的保证通道（`AssuranceStore.lane`，即 `ASSURANCE_1_1`）；允许用途没有任何记录写它（审阅回复与证书都没有这一项），一律 None。系统测试观察入库的知识三项都是 None。
- 展示：`context/retrieval.py knowledge_view` 与 `context/knowledge_tools.py` 目录行都带三项；规划包 `views.knowledge` 也带。

### K05 读取知识后再复核一次有效性

- `context/knowledge_tools.py`：`knowledge_read` 把一条已验证知识的正文取出后、交出去之前，用同一个判定 `knowledge_standing` 再判一次；不再当前的返回 `not_current_reply`——没有正文、`standing` 写明现状（`SUPERSEDED` / `STALE:<原因>`），提示重新取目录、不能引用。编号是本任务的一条知识、只是不在现行目录里的，也走这个回答（原来笼统报"没有这条"）。编号对不上照旧拒绝。
- 没写第二套判定；没用保证通道纪元（`read_epochs_locked` 要在事务里、且任务要在保证通道上，知识读工具不一定在这两个条件下跑；`knowledge_standing` 已经是"验收是否仍当前 + 产物是否最新 + 上游知识是否当前"三合一的判定）。

### K03 规划器能读黑板

- 二选一选了 **规划包加一节**，不给规划器工具。理由：规划器回合是一次性决定回合——模板 `tool_names=()`、`max_tool_calls_per_turn=1`、没有 `_bind_planner` 之类的网关绑定；整个请求包有 `package_hash`、`visible_refs` 要能重算、请求绑定要能复核；给它工具就得改成多回合，破坏"一轮回复只提出一个决定"的协议，还要再写一条工具绑定路径。
- `planning/htn/planner_package.py`：第十二个视图 `knowledge`；`knowledge_rows(records, summaries, limit=MAX_KNOWLEDGE=16)`：已验证知识在前（最新在前）、再核对过的步骤摘要；超限计入 `omitted_counts.knowledge`；加进 `_SHRINKABLE`（放不下先裁它）。行里带 `ref`（编号@版本）不带规划引用四元组，不进 `visible_refs`（`ReadItemKind` 没有 knowledge 一类，决定引用它会过不了读集核对）。
- `orchestrator/planner_views.py`：用 `current_knowledge`（与读工具、推送上下文、审查包同一个判定）和 `step_summaries` 装这一节。
- `runtime/role_templates.py`：规划器提示词加 `views.knowledge` 一段（怎么读、不是引用四元组、不要写进 reason_refs）；`planner-hierarchical-v26 → v27`，`PLANNING_DECISION_PACKAGE_VERSION 13 → 14`。旧配对不合法，没留旧版本。"九类事实视图"改成"各类事实视图"（原文的数字早就不对了）。

### K01 审阅员给黑板读工具

- `runtime/tool_gateway.py`：`ASSURANCE_REVIEWER_TOOLS = (*ASSURANCE_EVIDENCE_TOOLS, "knowledge_list", "knowledge_read")`；审阅绑定（`review_key` 不为空）不碰工作区（原来只对两件证据工具跳过）；知识工具在审阅绑定上先过 `assurance_review_refusal`（审阅已停就拒）。工具 schema 一字未改。
- `verification/reviewer_evidence_tools.py`：绑定只收这四件。
- `orchestrator/assurance_review_runtime.py`：两处审阅意图 `tool_names=ASSURANCE_REVIEWER_TOOLS`，`prompt_version` 改用新常量 `REVIEW_INSTRUCTIONS_VERSION`。
- `orchestrator/assurance_review_handoff.py`：部署身份核对允许四件。
- `deployment/native_pools.py`：执行池策略并进四件（策略身份随之变，已有执行池起不来属预期）。
- `assurance/review_input.py`：提示词加一段说明两件知识工具（按本任务范围、只列当前有效；查到的不是证据，不能写进 evidence_ids；相关条目仍在审查包里）；新常量 `REVIEW_INSTRUCTIONS_VERSION = "assurance-review-instructions-v2"`。`REVIEW_CODEC_VERSION` 没动——它是回复编解码版本，不是提示词版本。提示词的钉哈希是运行时按正文算的（`fingerprint({"instructions", "codec"})`），没有静态基线文件；静态基线只有部署清单，已重生成。
- 过滤口径：知识读器按审阅绑定所在的任务（Mission）范围、只列当前有效的条目；审阅员身份本身只读。没按被审步骤剔除候选层——候选层标着"未验证"，提示词说明它不是证据。
- 审查包里的 `related_entries` 原样保留。
