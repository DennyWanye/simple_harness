# HTN 精简 片 B 实施记录（中间目标）

日期：2026-10-01。依据：`HTN-后续-方案.md` 第 4 版"片 B"与 `中间目标判据-试验结论.md`（按备选设计做）。
版本：SDK opt.115。

## 一句话

规划器现在可以把一组步骤交给一个**中间目标**：中间目标的做法单独规划、单独过新做法审阅，做完后先过一次组合审阅，后面的步骤才开工。程序这边只加了秩序：能放几层由类型的层级决定；交给中间目标的要求保持用户的原编号；中间目标的做法必须恰好覆盖分给它的要求。要不要拆出中间目标、怎么拆，由规划器判断。

## 做了什么

### 1　目标类型带"层级"，层数上限由类型结构保证

- 任务类型多一个可选字段"在第几层"（只有目标类型能有）。注册做法时查：做法的目标类型在第 L 层，它里面的子目标必须是更深一层的类型；同层、更浅、或没有层级的子目标一律拒收。
- 这样不需要另写计数器：根目标 0 层，第一层子目标里还能放第二层，第二层没有更深的类型可放，只能由普通步骤组成。互相嵌套出环（第 1 层 → 第 2 层 → 第 1 层）在注册时就被拒。
- 没有层级的类型（代码领域、旧夹具）不受影响；不带层级的类型，定义正文与哈希不变。
- Host 按层注册两个子目标类型（`desktop.sub-goal-1`、`desktop.sub-goal-2`），都不声明判据、不声明端口；根目标标为 0 层。

### 2　交给中间目标的要求保持原编号

- 中间目标的类型不声明判据。它负责哪几条要求，是上级做法用链接交给它的，编号与用户要求相同，审阅员在每一层看到的都是用户原话（试验里"声明一个本地判据"的写法，审阅员只能看到一句程序合成的话）。
- 注册检查新增一条：链接到子目标步骤时，下传的编号必须与上级编号相同。换了编号的做法在注册时就被指出，不用等到计划提交才以"多重父映射"这种看不懂的原因失败。

### 3　新做法审阅的判据 = 类型声明的 + 分给这个目标实例的

- "分给这个目标实例的要求"就是当前计划为它推导的完成范围里的内容要求（`assigned_criterion_ids`）。
- 审阅包、Host 批策略用的无损映射、策略批准时的核对，三处共用同一个定义（`planning_subject_criteria`），所以 Host 那边不用改：计划提交后子目标出现，Host 下一轮循环就为它批好策略。
- 根目标不受影响（它的类型本来就声明全部内容要求）。

### 4　中间目标的做法：覆盖完整、归属唯一

同一条检查做两次，口径相同：

- **提做法时**（`planning_method_proposal`）：漏了分给它的要求、链接了没分给它的要求、有步骤没落到任何要求上——逐条写明，不送审。
- **计划提交时**（完成范围推导）：库里的做法不经过"提做法"，所以在这里再查一次；不满足则提交被拒，原因里点名是哪条要求。

试验里发现这两种写错此前都能提交：漏一条，没被链接的那一步会按它类型的一揽子声明去审全部要求；多一条，同一条要求同时归两处。

### 5　"目标还没有做法"改成通用请求的一种触发源

- 新增第六种触发源"目标还没有做法"。当前计划里有目标没有做法时，记一条通用请求（每个计划版本一条，幂等键 `open-goals:<计划版本号>`），请求里只有事实：哪几个目标、各是什么类型。它和步骤失败、证据失效走同一条"请求 → 叫醒规划器"的路。
- 规划器为其中任何一个目标提交了做法，这条请求就算处理；剩下没做法的目标由新计划版本的请求接着问。计划因为别的原因到了新版本时，旧版本的那条请求由系统了结，不让两条请求指着同一个目标。
- 上限与此前相同：同一个计划版本只问一次。规划器不改计划，就不再为这个版本重问。
- 主循环里专用的"展开未细化目标"入口整条删除（专用事件、内存标记、专用规划轮）。
- 请求的"影响范围"如实填写：要的是还不存在的工作，不把上级目标和兄弟步骤报成"待重新验收"。

### 6　规划器写做法时拿到的材料

- "这个目标要负责的要求"：类型声明的加上分给这个实例的，每条带用户原文。
- "可以往下放的子目标类型"：比这个目标更深一层的那些类型（类型引用、层级、参数）。列表为空就只能用普通步骤。
- 提示词（当前这一份，原地修改）补了四点事实与秩序：请求里的"目标还没有做法"是什么意思；子目标类型从哪里抄、子目标步骤怎么写；交给子目标的要求保持原编号；中间目标的做法恰好覆盖分到的要求。加了一个带子目标的完整示例。写明"是否需要中间目标由你判断"。

## 顺手删掉的一条过时规则

计划预检里有一条"可约性"检查：计划里的子目标如果库里一个做法都没有，就判整份计划结构无效，理由是"之后什么都改变不了它"。片 A 之后规划器可以自己为目标提做法，这句话不再成立——没有库做法的子目标只是规划的前沿。桌面库里没有任何子目标做法，这条检查不删，带中间目标的计划一份都提交不了。已删除（含问题种类与对应测试）。

## 与方案 / 试验结论不一样的地方、当场决定

1. **覆盖检查在提做法时也做一次。** 试验结论只说"计划提交时"。提做法时就能知道分给这个目标的要求，早查可以省一次审阅，问题也能逐条说给规划器；计划提交时那次是闸门，保留。
2. **"下传保持原编号"做成注册检查。** 试验结论把它当作写法约定。约定不查的话，写错只会在计划提交时以别的原因失败。
3. **提示词原地修改，不换版本号。** 开发期只保留一份当前版本；历史版本与版本表在片 C 一起收。
4. **Host 的子目标类型不声明端口。** 子目标下面的步骤写进同一个工作区，后续步骤靠先后顺序接着做。声明端口就要求做法写端口映射，多一处模型容易写错的地方，而桌面步骤本来就从工作区读文件。
5. **一轮只问一次的口径没有变。** 多个目标同时没有做法时，一条请求列出全部，规划器一轮处理一个，处理完产生新计划版本，再由新版本的请求接着问。
6. **计划预检函数里 `registry` 参数已无人读取**，与此前的 `catalog` 一样留着签名；几十处调用方的清理并入片 C。

## 独立核验（一名 Opus 子代理，只读，只报阻断级）

**结论**：1 个阻断问题，已修；其余六个方向没有发现阻断问题。

**阻断问题：发布来源规则与新加的覆盖检查互相矛盾。** "要发布的文件必须恰好由一个步骤写出"这条规则原来按整个任务的要求去查每一份做法——片 A 时只有根目标会被提做法，没有问题。片 B 之后，要发布的文件如果归收尾步骤或别的中间目标，那么为这个中间目标写的任何做法都会被拒（"那份文件链接到 0 个步骤"）；规划器照提示把它链进来，又被覆盖检查判越界。两条规则不可能同时满足，这样的中间目标永远提不出做法，任务以"答错次数用完"失败。

修法：发布来源规则只查这个目标自己负责的要求（类型声明的，加上上级做法分给它的）。仍是秩序检查。测试两条（先红后绿）：文件不归它的中间目标正常提出做法并送审；文件归它时，链到两个步骤仍被拒。变异第 19 项抓住。

**其余方向的结论**

| 方向 | 结论 |
|---|---|
| 会不会卡死或无限重问 | 不会。叫醒全靠落库的事件，每条请求只叫醒一次，幂等键含计划版本号，重启后接得上；规划器不改计划时请求挂着但不重问，没做法的目标照常进入"没有可派发的工作"的停滞判定 |
| 请求了结是否正确 | 正确。系统了结只碰"目标还没有做法"这一种、且不是当前版本的；带"要新做的工作"的请求不会被"步骤重新验收通过"了结 |
| 覆盖检查能否绕过 | 没找到。所有计划提交只走一条路，库做法和修复都过闸 |
| 层级规则 | 层数有界、成环在注册时被拒；不带层级的类型正文不变 |
| 新做法审阅的判据 | 根目标在第一份计划前后判据相同；子目标的任务编号由"上级做法实例 + 步骤名"决定，同一个任务的份额不变，Host 缓存的策略不会对不上 |
| 删"可约性"检查的后果 | 没有别处依赖它 |
| 有没有新增按任务语义分支的规则 | 没有。新增的都是集合比对、层级比较、类型声明 |

**非阻断、记录在案**

1. Host 为子目标批策略如果赶在规划器提做法之后（按循环间隔一般不会），这次提案会被拒并算一次答错，随后重问。
2. Host 按"任务 + 合同修订 + 要求版本"记一次批准；判据现在还取决于当前计划分给它的份额。目前同一个任务的份额不会变；以后若允许同一个任务换份额，这里要跟着改。

## 发布与真机

**发布**：SDK opt.115（`ac5b2a89`）+ Host 钉版（`217a51bd`），Host 按层注册子目标类型（`a5fa5fb2`），已推送。钉版后 Host 三份定向测试 11 条通过。

**真机第 1 局（三层题，opt.115）** `mission-b7f141d03731fb40`——前半段完全按设计走，卡在中间目标的组合审阅，取消。

| 顺序 | 发生了什么 |
|---|---|
| 1 | 规划器为根目标提出做法：一个中间目标"整理资料"（交给它前两条要求）+ 最后一步写总结 |
| 2 | 独立审阅通过，规划器采用，第 1 版计划提交；中间目标出现在计划里，还没有做法 |
| 3 | 系统记一条"目标还没有做法"的通用请求（第 1 版计划），规划器被叫醒 |
| 4 | 规划器为中间目标提出两步的做法；独立审阅按分给它的两条要求审，通过 |
| 5 | 规划器采用，第 2 版计划提交，请求了结 |
| 6 | 中间目标下的两步依次执行并验收通过；最后一步一直没有开工（在等中间目标） |
| 7 | 中间目标进入"组合审阅"阶段后，此后 9 分钟没有任何事件，任务停在"排队" |

当时的判断（后来证明只对了一半）：开组合审阅那一步出错时异常被静默吞掉，所以库里没有线索。先补了可见性——中间目标这一轮出不了结论且原因是报错时，记一条事件（同一个目标同一个原因只记一次，原因原样写入），只陈述事实。SDK opt.116（`ca0d9205`，Host 钉版 `dd15de4f`）。这条可见性本身该有，保留。

**真机第 2 局（opt.116）** `mission-9ae33baa5f28b9c5`——停在更早的位置：第 1 版计划提交后，"目标还没有做法"的请求没有发出来，15 分钟无事件，取消。

两局停的位置不同，说明问题不在某一步的逻辑。后端进程 CPU 占满；向它发信号转储调用栈，主循环停在每轮开头的"执行图后续任务"里：

- 库里有一个 9 月 30 日就已取消的旧任务，它的执行图收敛作业一直停在"等待"。收敛的唤醒调度每 5 秒给它排一次唤醒，没有次数上限，也不看任务是否已经终止——累计一万三千多次。
- 每次唤醒都要重读这个任务的全部执行会话，其中一条查询没有索引、要扫整张会话表。库一天天长大，这一步从毫秒级涨到约 5 秒，正好等于唤醒间隔：一次还没处理完，下一次已经到期。
- 主循环每轮开头最多连续处理 16 条后续任务，于是每轮循环要一两分钟，新任务几乎得不到处理。片 A 的两局是在这个临界点之前跑完的。

**修法（SDK opt.117，`4aff485a`，Host 钉版 `dbefa198`）**：已终止（完成 / 失败 / 取消）的任务不会再提交计划，它的收敛作业没有可以等的东西——不再为它安排唤醒，也不把它算作待办。作业与围栏原样保留，不谎称已静止。这是生命周期上的秩序，不涉及任何语义判断。测试两条（进行中的任务照常唤醒；已取消的不唤醒、作业状态不变），先红后绿；执行图那一组 46 条通过。顺带发现并更正一条片 A 遗漏的过时断言（那条测试不在片 A 的相关清单里：它断言"建第一份计划不问模型"，片 A 之后做法由规划器选，会问一次）。

重启后确认：一分钟内 0 次唤醒，后端 CPU 回落。

记两条教训：
- 任务"卡住"先看后端 CPU 和调用栈（`kill -USR1 <后端进程号>` 会把各线程的调用栈打到启动日志里），再怀疑刚改的逻辑。这次在"组合审阅为什么开不起来"上绕了不少路，其实它根本没轮到执行。
- 没有上限的周期性唤醒 + 一次处理的耗时随库增长，迟早会把主循环拖死。会话表上那条没有索引的查询还在（现在只有活着的任务会走到），记为后续项。
