## 二、事实（第 3 版已按评估更正）

真机库（隔离环境，只读统计）：初始做法由程序定 103 次、由模型定 0 次；合成器现编 107 次；规划器自己提做法 0 次；新做法独立审阅 0 次；中间目标组合审阅 0 次；规划器模型的决定以修复为主（约 236 次）。

代码：
- Host 只注册根目标（复合）与两种叶子（`backend/deskpet/orchestration/hierarchical.py:44-46`）。
- 选择规则 0 / 1 / ≥2 个候选 → 合成 / 程序直接用 / 规划器选（`planning/htn/method_selection.py:339-377`）。
- 合成器入口共八处：六处"跳过规划器"（initial / method_synthesis / compound_refinement / root_review_repair / read_only_rewrite_repair / repeated_verification_repair），**外加**主循环每轮无条件调用一次（`event_handler.py:3724`）和规划器"声明受阻"后转交（`event_handler.py:8948`）。
- 规划器"自己提做法"在决定协议上放行（启用表、授权、准入均通过），提交后以"本任务试用"登记并进入候选。
- 新做法审阅只有一处发起、**没有任何消费者**；且**在 Host 里根本开不起来**：Host 只为内容 / 最终审查 / 操作申请 / 操作结果四类审阅批准检查策略（`backend/deskpet/orchestration/assurance.py:190-192`），缺"新做法审阅"，一发起就报 `CHECK_POLICY_UNRESOLVED`，这次提做法被记为拒绝。
- 写做法的上下文只在"0 个候选"路由下给规划器（`planner_views.py:210-215`），且**比合成器拿到的少**：缺真实判据原文、各做法不适用的原因、防撞车的新编号、根终审打回意见；规划器路径还缺两项检查——"一步承担 ≥3 个文件打回重拆一次"（用户 09-26 决定）与"发布来源唯一"。
- "同一候选集只问一次"的选择身份账本：提做法被拒或审阅打回后候选集不变，会把重提挡掉（`method_selection.py:358-370`）。

- 同一类型嵌套自身属递归，注册协议要求写适用条件作终止保证（`registry.py:1859-1871`）；**程序上没有层数上限**。

## 三、问题（不变）

1. 产品里只能拆一层。
2. "怎么拆"没有任何模型把关。
3. 原计划要求的新做法独立审阅从没发生，且在产品里开不起来、结论也没人读。
4. 同一件事两套做法、三档开关、大量历史版本。

## 四、目标流程（不变）

```
目标需要做法
  └─ 程序筛掉跑不了的候选
       └─ 编排 Agent 回一个决定：
            ├─ 采用某个候选
            ├─ 自己提一个新做法 → 解码 + 注册检查 → 独立审阅
            │       ├─ 通过 → 可采用
            │       ├─ 打回 → 意见回到规划器，重提（有上限）
            │       └─ 判不下来 → 新会话复审 → 仍不行问用户
            ├─ 先取证
            └─ 问用户
```

口径：只在"为一个目标选定做法"这一刻必须由编排 Agent 判断；其它唤醒规则不变。

## 五、分三片做，每片可单独发布、单独验收

### 片 A　编排 Agent 判断 + 自己提做法 + 审阅闸门（先只在根目标、平铺计划上）

对应评估阻断 1、3、4、5、6。

1. **Host 为"新做法审阅"批准检查策略**：按规划主体任务批准，判据与审阅包一致；在事务外提前做好（根目标在任务开始时）。
2. **关掉合成器的全部入口**：主循环那一处、"声明受阻"转交那一处、六处捷径——同一片里一起关，否则两条路并行。"声明受阻"改为问用户（改成再开规划器会无限循环）。
3. **选择规则只留一档**：程序过滤后，0 / 1 / 多个候选都开一轮规划器。删去另两档、`legacy` 分支、"单候选时系统替规划器选上"的本地代答。
4. **写做法的上下文按"目标需要做法"给**（与选择路由脱钩，修复 / 重提场景也给），并补齐合成器独有的四样：真实判据原文、各做法不适用原因、新编号、根终审打回意见。
5. **规划器路径补上两项检查**："一步 ≥3 个文件打回重拆一次"、"发布来源唯一"；以及编号撞车检查。被拒时逐条给出可修正的问题清单（现在只有一整段字符串）。
6. **审阅闸门放在计划提交事务里**：采用"本任务试用"的做法时，读它的新做法审阅正式记录，"通过或人裁决通过"才提交。不套用完成范围证书（新做法审阅按合约没有完成范围）。
7. **唤醒与打回通道**：新增"新做法审阅结论已入库"服务事件（通过 / 打回 / 人已裁决）作为下一轮规划的唤醒源，打回时带审阅意见；等待审阅期间在空闲判定里算"在等"，不判无事可做。判不下来 → 复审 → 问用户，复用审阅升级那套并给新做法审阅接上消费方。
8. **重提与次数**：选择身份里纳入"提做法 / 审阅结果"，被拒或打回后允许再问。每个目标最多提 3 次做法（首次 + 2 次重提），用尽时如实停机并写明原因；修复轮"先记一条规划被拒"不再占用名额；原"合成成功多给一次规划机会"改为"提做法成功不计入规划失败次数"。重提内容与被打回做法完全相同的，准入时直接拒并说明。
9. **规划器提示词（只留一份）**：并入合成器积累的经验；删掉"你不需要也不能自己合成方法"；说明修复场景里新做法用"替换做法"采用。

片 A 验收（真机，平铺任务）：模型做的初始选择 ≥1；新做法审阅正式记录 ≥1；不再出现"跳过规划器""合成轮"两种事件；任务完成交付。另跑一局故意让审阅打回的题，看到重提后通过。

### 片 B　中间目标

对应评估阻断 2 与"没有层数上限"。**先做验证性试验再定稿**——评估指出通用子目标类型的三种判据声明法都走不通，这是真正的设计问题，不能凭推断定。

待验证的设计（试验通过才采用）：
- 子目标类型声明**一个本地判据**（"该子目标陈述已达成"），父做法把父要求链接到它；
- 新做法审阅对子目标的判据**改从父做法链接过来的要求取**，不再用"类型判据 ∩ 任务要求"；
- 一个子目标承担多条父要求时的"多重父映射"报错，在完成范围推导里放开为"一个本地判据可承接多条父要求"；
- 组合审阅的判据来自完成范围，随上一条一起得到非空判据。

试验内容：用夹具搭"根 → 子目标 → 两个叶子"，子目标只承担部分父要求，走完成范围协议与保证通道，看注册、新做法审阅、组合审阅、形成中间结论四步是否都成立。不成立则换设计（备选：子目标类型不声明判据，注册覆盖检查与审阅判据都改按"这个目标实例被分配到的要求"）。

其余：
- Host 注册通用子目标类型；写做法的上下文里提供可用的子目标类型。
- **程序上的层数上限**（提交时检查，≤3 层），不靠提示词。
- 提示词写明：什么时候用子目标、什么时候不要为拆而拆。

片 B 验收（真机三层题）：中间目标出现；它的做法也经过审阅；组合审阅正式记录 ≥1 并形成中间结论；后续步骤在其后才开工；任务完成交付。

### 片 C　清理

- 删方法合成器角色余下的代码：提示词全部版本、派发、轮次记账；解码器与请求构造保留并改名（它们被规划器路径复用）。连带改五处角色清单（规划器角色排除表、任务来源种类两处、执行图角色映射、分层派发里的一处）。
- 各角色提示词只留当前一份，删历史版本与历史链、钉历史哈希的测试断言，基线按当前版本重生成。
- 删按旧规划包版本号的分支（**不删** `planner_package_v1.py`）；删选择策略配置项。
- 改 SDK 21 个、Host 2 个依赖合成器角色的测试文件。
- 重新生成部署清单；本机已有执行池因提示词变化需重建（开发期，不迁移）。

片 C 验收：全量回归全绿；提示词登记表每个角色一份；全库搜不到合成器角色名。
