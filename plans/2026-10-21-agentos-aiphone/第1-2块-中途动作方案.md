# 第 1、2 块：步骤中途提议动作 + 动作兜底（一页方案）

日期：2026-10-21

## 现状

- 动作只能来自建任务时写下的 `action:` 要求；全部步骤验收后，系统才准备申请单、审阅、批准、执行。
- 叶子尝试不能在一个回合里挂起等批准；系统已有的模式是"结束这次尝试 → 处理 → 开新尝试带反馈"（资源申请就是这样）。
- 动作账本（`actions` / `approvals`）、自动代批、人批、交接、结果不明的查询与封口都已成熟。

## 做法

动作有两个来源，共用一个账本：

| 来源 | 冻结 | 交接前核对 |
|---|---|---|
| 建任务时的要求（已有） | 申请单 + 审阅 + 物化 | 申请单链路（已有） |
| 步骤中途提议（新增） | 步骤动作请求行 + 操作身份 | 请求行与动作一致、这一步仍在当前计划里且没被验收 |

流程：

1. **提议**：叶子模型在结果块里写 `action_request: {connector, operation, target, params, reason}`，结果为 `blocked`。工作包里列出这次任务可用的动作（名字、说明、参数说明、风险、要不要人批）。
2. **检查**：形状、连接器与操作存在、必填参数、规范 JSON、不像密钥、风险等级不超过部署上限；连接器可选的 `prepare(operation, target, params, context)` 做应用自己的检查和参数整理（超时或异常 = 不执行）。
3. **冻结**：和结果同一个事务，写请求行、操作身份与绑定、动作行与审批请求；参数哈希、引用产物的哈希、要求版本、策略版本都钉进去。批准绑定这一份。
4. **授权范围**：建任务时写 `allowed_actions: ["photos.move", ...]`。名单内的按平常规则（自动模式代批，"总要人批"等人）；名单外的提议也不丢，变成必须有人批准的请求，卡片上标"超出任务授权"。完成要求不变；要改要求只能走"改要求"。
5. **执行**：批准后，交接前再跑一次 `prepare`，结果必须和冻结的一致；再按已有规则交接、记回执、结果不明就查询。
6. **继续**：动作结案（成功、失败、被拒、过期、取消、人裁定），系统给同一步开新尝试，反馈里带结构化结果；不问规划器。结果不明在人裁定前不继续。
7. **身份**：任务主人、尝试、调用都由 SDK 填；模型写的身份字段不算数。

## 兜底（第 2 块）

- 一个逻辑动作 = 一个请求号 + 动作号；同一结果重复提交不重复建；每次交接一个新键只在封口证明后才有。
- 新增"只交接一次"的连接器（`delivery="at_most_once"`）：不要求幂等与查询；结果不明直接等人裁定，从不重发。
- 持久上限（宿主设置）：每个任务的中途动作数、每个动作的交接次数；跨尝试、重启累计。超限的提议记为拒绝，返回给模型。
- 取消任务：没交接的动作取消；已交接的照样对账，显示真实结果。

## 规则：中途动作不改完成要求

中途动作是完成既定目标的手段，不是新要求。任务完成仍按原要求判断；任务在动作结果不明时不会判完成（已有的收尾核对）。

## 验收

仓库外只装轮子：搜索 → 提议归档 → 自动代批执行 → 继续 → 回答（A01）；参数改写与越界（A02）；总要人批、拒绝、过期、重启等待（A03）；回执丢失后查询（A05）；只交接一次的点击超时（A07）。
