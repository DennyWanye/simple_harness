## 2. 改法（五处，都在 SDK）

按架构核心思想：不加"遇到这种情况就那样办"的语义规则，只补"如实呈现事实"和"人的决定有合法出口"。

1. **说明与准入同口径**（`runtime/role_templates.py`，planner-hierarchical-v33 → v34）。能重试：调用被打断、线路出错、结果或用量不明（旧调用按上限记账，不会少算；未记录的回复不会执行任何工具）。不能重试：这一步的真实外部操作（连接器动作）结果还没核对、结果已被接受。DECLARE_RUNTIME_BLOCKED 一节加一句：只因用量不明失败的一次调用不算环境坏了；人工接管总会唤醒阻塞，不必列进 `resumable_if`。
2. **人工接管纳入唤醒来源**（`planning_runtime_block.runtime_binding`）。`human_takeovers`（任务下所有 `takeover_*` 接管记录号）无条件进唤醒摘要。接管一记，下一拍 `wake_blocks` 就发 `PlanningRuntimeBlockWoken`，规划服务按原有机制开一轮。
3. **人工重试走决定管道**（`planning_selection.native_decision`）。开一轮前先看：失败收场的那一步有没有晚于这次失败的"带话重试"接管。有就以 `human_takeover_retry` 来源直接提交 RETRY_SAME_METHOD，不问规划器（与 09-28 系统原地重做同一管道、同一准入 `retry_binding`，真实外部操作未决仍拒）。两条护栏：`impact.unresolved_operations` 非空不提交；每笔接管只提交一次：账本里 `NativePlanningDecisionPrepared` 记着为哪笔接管提交过，提交过的不再提交，被准入拒了就交回规划器，不每轮反复（独立核验指出：原先从包里的失败索引推断，而那一节会被裁剪到 16 行或按体积删掉，依据会丢，已改）。来源记在意图配置 `native_planning_decision_origin`，`stop_conditions.NATIVE_DECISION_ORIGINS` 两种来源都不算规划轮。
4. **接管回执说清处置**（`human_commits.takeover`）。新增三字段 `disposition / blocker / next_step`：`retry_queued`（已排队原样重做）、`attempt_cancelled`（开着的尝试已关）、`recorded`、`stopped / skipped / prioritized`，以及 `blocked`（`step_action_unsettled` 这一步外部动作未结案 / `operation_unresolved` 操作账对不上 / `operation_read:*` 账读不出，下一步 `resolve_unknown`）。在写入记录前算好，同号重复点击原样拿回。
5. **阻塞如实报出**。`api/facade.snapshot` 的 `waiting_on` 多一行 `kind="runtime_block"`：`decision_id`、`blockers`、`resumable_if`、`woken`、`since`、受影响 `task_ids`、恢复入口 `recovery`（对这些步骤点带话重试）。`host/recovery_report` 看到这一行就把委派记 `held_refs`（`runtime_blocked:<阻塞码>`），不再记 `resumed_refs`。

不做：不加新的 `resumable_if` 取值；不改会话配置版本与公开方法签名；人工重试不绕过操作核对；预算、尝试次数上限都不加。

## 3. 对照对方的 7 条 SDK 要求

| 要求 | 做了什么 |
|---|---|
| 1 说明与准入从同一份政策投影，分清四种情况 | 说明按准入改写（v34），四种情况写明；没有做成代码生成（说明是给模型看的文字，准入是代码，口径一致即可） |
| 2 已持久化的阻塞要有安全恢复路径；人工重试幂等、绑定原任务/尝试/版本并唤醒 | 接管是唤醒来源；重做以人工来源进决定管道，`retry_binding` 绑定原尝试、计划版本、做法实例、操作读数；同 `command_id` 重复点击不重做；由内核执行（不是规划器授权）——契约写在 CHANGELOG 与接入说明 §4d |
| 3 回执分 recorded / queued / blocked，重复 command_id 不再派 | `disposition / blocker / next_step`；重复同号原样返回 |
| 4 恢复报告与快照镜像阻塞 | `waiting_on` 新行 + `held_refs`；主会话事件流不另加事件（任务卡读快照即可见） |
| 5 确定性复验：注入失败 → LOST → 阻塞 → 接管 → 新尝试 → 完成；中间点崩溃 | `test_human_retry_wakes_runtime_block.py` 第 1 条走完整条链（新尝试 `retry_of` 原尝试、阻塞解除、规划器未被再问、旧账不动、次数上限不变）。**中间点进程崩溃没有做**：产品同形测试世界没有现成的"关掉再开"夹具，接管、唤醒、决定、新尝试每一步都是各自事务里的持久事件，重开按同一账本重放，这一点由既有的重开测试覆盖；本次没有为这条链单独加崩溃注入 |
| 6 反例：真实外部操作未决仍被拦；上限不增加 | 第 2 条：外部动作未结案时回执 `blocked`，不开新尝试；第 3 条：选择器对 `unresolved_operations`、接管早于失败、同一笔接管已提交过三种情况都不提交 |
| 7 新数据根 + 公开接口构造同一失败链的命令 | 提示词换版，**要换新的数据根**。复现命令：在 SDK 目录 `.venv/bin/python -m pytest -q tests/orchestrator/full_target/test_human_retry_wakes_runtime_block.py`（产品同形世界、公开 `control.takeover / control.snapshot` 入口）。旧根的证据保留，不用新根跑通来宣称原任务已恢复 |
