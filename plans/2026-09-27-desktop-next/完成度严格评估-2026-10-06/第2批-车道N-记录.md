## 二、每条做了什么

### A01 定稿事务重读"权限"（原计划 §7.2"最终事务重读当前 epoch/权限/effect/运行集合"）

读清"权限"是什么：收尾依据 = 根结论 + 它依赖的使用证书（根结论 / 中间目标结论 / 每条贡献验收，消费方还现行的那些，`assurance_recheck.closeout_certificates`）。证书签发时记的 ACCESS / POLICY 读项来自部署的当前权威 `FixedPrincipalAuthority`（主体、租户、根化身、环境纪元、冻结的保证策略 + 部署策略指纹）。`authorization.planning_snapshot` 是规划车道的授权，根批准回执只钉完成规格（`completion_spec_hash` 已钉），都不是收尾依据。所以"权限"= 当前权威对每张所依赖证书的身份就根结论重新签的 ACCESS / POLICY 见证。

做法：

1. `assurance_recheck.closeout_authorization(authority, store, mission_id, root_ref, now_ms)`：对每张所依赖证书的身份（任务 / 消费方 / 范围 / 主体 / 用途 / 根化身）调当前权威 `authority(identity, root_ref)`，收 ACCESS / POLICY 两项读项；同一键两种指纹 → `RECHECK_REQUIRED`。
2. `AssuranceCloseoutConsumer` 构造时必须给 `authority`（拼装处传 `FixedPrincipalAuthority`）；`_evaluate_locked` 每次评估都算一份 `authorization`（内部字段）并并入 `read_set`。
3. `require_final_consistency`：定稿（READY）那次，除纪元三元组 / 时钟外，`authorization` 与整个 `read_set` 都必须等于依据读取时的，不等 → `RECHECK_REQUIRED`，退回重算。`VOLATILE` 加 `authorization`、`read_set`（没到 READY 不比，和纪元同一口径）。

测试：纯规则部分（权限见证变 / 读集变 → RECHECK_REQUIRED；DRAINING 不比）+ 世界部分（跑完一局，评估正文的 `authorization` 有 ACCESS 与 POLICY 两类、都在 `read_set` 里；把权威的策略指纹换掉再评一次，见证不同，`require_final_consistency` 拒绝；换回去再评，放行）。

### A17 收尾正文过 closeout-v1 校验

对照资产：`plans/Assurance/specs/1.1/contracts/closeout-v1.schema.json`（14 个必填、`additionalProperties:false`、`read_set` minItems 1、`root_resolution_ref` 是 pin）、`common.schema.json`（SDK 包内 `assurance/schemas/common.schema.json` 与它逐字节相同）、`implementation/field-producers.json`（`read_set` 的生产者 = complete snapshot reader + canonical_read_set；其余 = 定稿写入）、`schema-source-rules.json`（closeout 的来源 = 定稿写入器）。把 `closeout-v1.schema.json` 原样复制进 SDK 包 `assurance/schemas/`，测试从包里读。

做法：

1. **文档与内部字段分层**。评估结果仍是一个字典，但写进收尾行正文 `check_body_json`、任务最终报告 `assurance_closeout`、收尾事件 `root_resolution_ref` 的只有 `closeout_document()` 取出的 14 个字段（`CLOSEOUT_V1_FIELDS` 与 schema `required` 相等）。内部核对字段（`mission_version`、`mission_status`、`epochs`、`root_incarnation_id`、`authorization`、`stale_certificates`、`open_intents`、`success_judgment`、`usage_counted_at_upper_bound`、根出现 / 缺的根义务 / 未满足或被挡的根……）只进这次评估的回执（`assurance-closeout:*`，正文 = 完整评估 + 触发 + 行版本）；定稿回执（`assurance-finalized:*`）= 文档 + 判定 / 版本字段 + `mission_version` / `root_incarnation_id` / `epochs` / `authorization`。`check_body_hash` 现在是文档的指纹。
2. **`root_resolution_ref` 改为 pin**：`{id, revision, content_hash}`（种类由字段名定）。读方改：`_write_locked`、`finalize_assured_mission`（`["pin"]["id"]` → `["id"]`）、接缝脚本 `final-writer-seam.py` 的作废评估样本、第 1 批测试。
3. **`read_set` 如实写**：根结论（OBJECT，真的按引用经 `AssuranceReader.read_exact_metadata` 重读，正文不符就拒）、要求版本（OBJECT，同上）、每个根的完成范围（OBJECT，`completion_scope`，按 `scope_id` + 文档指纹）、加 A01 的 ACCESS / POLICY 见证；`canonical_read_set` 排序去重，同键异指纹 → `RECHECK_REQUIRED`。
4. 读内部字段的两处读方改走回执：`assurance_recheck.closeout_detail(store, mission_id)` 返回 (收尾行, 最近一次回执)；`closeout_stale_findings` 与 Host 诊断 `api/assurance.py` 的 CLOSEOUT 项（根化身 / 纪元判 ROOT_CHANGED / SOURCE_CHANGED）用它。
5. `report_ref` 保持指向定稿回执（`commit_receipt` 引用，B 车道口径）；非定稿状态为 null，schema 允许。

测试：没有 JSON Schema 引擎（项目不引 `jsonschema`），在测试里写了一个只认 closeout-v1 / common 用到的关键字的最小校验器（`$ref` 跨文件、`oneOf`、`const`、`enum`、`type`、长度 / 范围 / 条数、`uniqueItems`、`required`、`additionalProperties:false`），并有一条自测（缺必填 / 多余键 / ref 当 pin / 空读集都要报）。世界用例：收尾行正文严格通过且键集 == `required`；最终报告的收尾记录严格通过；定稿回执的文档部分严格通过且带内部字段；历史上每次评估的回执：有根结论的，文档部分都严格通过；`read_set` 有 resolution / requirements / completion_scope 三类 OBJECT 与 ACCESS / POLICY。

### A07 已交出未收敛的动作挡住收尾（原计划 §7.2"实际写者未收敛 → DRAINING"）

做法：`_evaluate_locked` 把 `HANDED_OFF` 的动作键交给 `_drain_decision(open_operations=...)`；有则 DRAINING、原因 `OPEN_OPERATIONS`（排在 OPEN_INTENTS / OPEN_RESERVATIONS / USAGE_UNKNOWN 之前），并且不走"按上限结清"。收尾状态枚举已有 DRAINING，没有新加状态。动作收敛（结果回来）后由现有收尾来源事件（`OperationOutcomeAccepted` / `ActionFailed` / …）触发再评，这个原因消失。`unsettled_operation_refs` 仍点名它，`dangerous_work_refs` 只收 UNKNOWN（不变）。

`OPEN_OPERATIONS` 是收尾原因（closeout-v1 `reasons` 自由字符串），与 OPEN_RESERVATIONS 同类，不跨边界抛出、不经 `classify`，所以不进 `error_table.py`（与第 1 批评估第三节第 6 条对 `REVIEW_PACKAGE_STALE` 的口径一致）。

测试：步骤跑着时插一条 HANDED_OFF、租约未到的动作 → 任务 ACTIVE、收尾行 DRAINING / `["OPEN_OPERATIONS"]`、`unsettled_operation_refs` 点名、`dangerous_work_refs` 空；把动作改成 SUCCEEDED 再评 → 不再 DRAINING、原因消失、`unsettled_operation_refs` 空。

## 六、偏差与裁决

1. **没有根结论时的评估不是 closeout-v1 记录。** 根结论还没有（`ROOT_RESOLUTION_MISSING` / `ROOT_NETWORK_UNAVAILABLE`）时评估早返回，`root_resolution_ref` / `requirements_ref` / `completion_spec_hash` 为 null、`read_set` 为空；这种评估本来就不写收尾行（`writes_row` 要有 resolution_id），只留回执里的投影。严格校验只对有根结论的记录。记为已知口径，不改 schema。
2. `OPEN_OPERATIONS` 不进 `error_table.py`：收尾原因不是跨边界码（见第二节 A07）。
3. 定稿回执多了 4 个内部字段（`mission_version` / `root_incarnation_id` / `epochs` / `authorization`）：Host 诊断对 FINALIZED 行判 ROOT_CHANGED / SOURCE_CHANGED 要靠它们；回执本来就不受 closeout-v1 约束（文档部分严格过）。
4. 越界改了 `assurance_final_writer.py`、`assurance_assembly.py`、`api/assurance.py`，都是收尾正文形状变化的必然读方，范围最小，见第三节。
5. 收尾消费者现在依赖当前权威；没有权威不能构造（`CURRENT_READ_AUTHORITY_REQUIRED`）。`install_assurance` 是唯一构造点（已 grep），测试世界经它拼装。
