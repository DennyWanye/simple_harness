## 1. 结论与对上一轮的修正

**桌面端不是没有接入 SDK 的 UI 外壳。任务页、Host 服务、HTN、Assurance、Operation 完成接口和原生 Agent Runtime 已有真实装配代码。上一轮“Host 无法读取、接线未核实”的状态，现在应改为“已核对主要源码接线”。**

但不能把这升级成“所有最初规划的能力都已进入默认生产路径”。本轮最重要的三个区别是：

1. **当前产品里的执行图是 HTN 运行视图，不是已启用的严格 TaskGraph 内核。** 严格组件仍被安装，但普通 Mission 没有启用它，UI 改走 `mission_live_graph`。
2. **原生 ARP 确实进入了特定模型池，但使用 `STANDALONE_CHAT` 模式；完整 `MISSION` 来源绑定尚未实现。** SDK 对后者直接具名拒绝，而不是已经完整支持。
3. **多池目录仍按 profile 分别形成 namespace，不能签收为原规格的同一部署 realm 单一目录权威。** Host 文档还明确记录在目录统一前不开放相应 `agent_` 路由。应将“已有 SDK / Host handler”与“已通过产品入口开放”分开。

因此，当前更准确的阶段是：**已有可执行主流程和局部真实运行记录的集成系统；仍处于默认路径与完整合同对齐、故障修复、同版本验收阶段。**

这份复评更新上一轮报告的 Host、默认启用状态和影响范围判断；不抹掉上一轮针对同一个 wheel 得到的 SDK 缺陷证据。

### 本轮范围

聚焦 TaskGraph → Assurance → Operation → Agent Runtime 及其桌面接线。不覆盖桌宠渲染、全部语音链、全部前台聊天功能或所有扩展工具。源码审查不等于连接到你本机正在运行的进程；本机未提交改动、安装实例、模型目录和运行设置仍可能不同。

## 3. 源码中真实存在的主链

```text
桌面任务页 / 完成要求与操作面板
   │
   ▼
控制通道与 handlers
   │  固定本地 principal / tenant，不由任务 payload 自报
   ▼
OrchestrationService
   │
   ├─ 原 MissionControlV1 / Commit / Store
   ├─ Requirements + Operation Completion Spec
   ├─ 每 Mission 的 HTN world、根合同与 Obligation
   ├─ 原 Orchestrator / 恢复 / 预算 / 派发
   │     └─ 原模型池 或 原生 ARP 模型池
   ├─ Assurance：Review / Validity / Closeout / Notify
   └─ 有效果要求时：Operation intent / 审阅 / 审批 / connector / 效果验收

展示读链：
任务详情 → mission_live_graph → HTN 表、Task 状态、CompoundPhaseChanged 事件

已装配但未进入普通 Mission 的完整新语义：
严格 TaskGraph 的显式启用、严格读令牌 / 历史 pins / 新图消费链
ARP 的 MISSION 精确来源模式
```

`service.py::_open` 通过 startup assembly 依次安装 hierarchical、TaskGraph、Assurance，再绑定 native plane；不是在 UI 中伪造完成状态。`wiring.py` 则将该服务挂入桌面生命周期，并装配状态推送。[H03][H04]

`hierarchical.py` 为任务创建独立 world；根 Requirements 与 Assurance 使用同一份内容，根责任、语义和要求在原事务中登记。规划启动还要求已有获准的 Operation Completion Spec；缺 Spec 不自动解释为无需效果。[H05]

**注意：上述是任务页 / 编排服务这条链，不能据此声称所有前台聊天入口都已自动转成相同 Mission 和 ARP 协议。**

## 4. TaskGraph：必须拆成三个完成状态

### 4.1 原 HTN / TaskNetwork 基础能力

原有分解、方法实例、Occurrence、ORDER / DATA、依赖执行、预算和接受等能力已经存在，桌面端也在使用这条主干。不能因为严格 TaskGraph 未启用，就说“没有任务图”或“不能分解任务”。

### 4.2 严格 TaskGraph 内核

`service.py::_install_taskgraph` 安装了真实的 TaskGraphDeploymentPorts 和 `InstalledHtnWiringAcceptance`，但安装组件本身不等于为 Mission 启用新内核。

当前 `ARCHITECTURE/TASKGRAPH.md` 的 9 月 26 日说明、`live_graph.py` 的模块说明，以及前端 LiveGraph 的实际请求都一致：普通桌面任务没有启用严格 TaskGraph，严格读取会返回 `NOT_ENABLED`，界面改读运行视图。[H06][H07][H08]

**结论：代码与装配存在；普通业务路径未启用；不能签收为严格 TaskGraph 已在默认任务中完成闭环。**

### 4.3 现在看到的执行图

`live_graph.py` 做了有价值的产品工作：先核对 Mission 所有权，再以 SQLite `mode=ro` 打开原库，并在同一读事务中取得事件水位、计划成员、任务状态、尝试数和复合阶段。前端会关联请求、处理推送重读、展示状态与结构。[H07][H08]

但它不是严格 TaskGraph Read API：

- 节点状态来自 Task 表及阶段事件，不生成执行许可。
- 返回 `through_seq` 和计划版本，不等同于完整 TaskGraph 的 source/read-token/validity 证明。
- 选择旧 revision 时，结构按旧计划取，Task 状态和尝试数仍来自当前表。因此它不是完整“回到当时状态”的审计重放。
- 悬空展示边会被过滤，越界 parent 会改作根并记录日志；这适合容错展示，不能用作严格执行图完整性验证。

应把 UI 标为**“计划结构与当前运行状态”**，而不是让“有图、有版本下拉”成为严格 TaskGraph 已完成的证据。

### 4.4 来源清单问题仍在，但影响范围需要修正

**修正后的解释：这是启用和验收严格 TaskGraph 的制品来源阻塞，不是所有桌面普通 Mission 都无法运行。** 运行视图绕开的是严格读接口，不是让一个已经失败的执行授权强行通过。

不能直接更新哈希后把 NOT_RUN 改成 PASS；应在真实当前候选上合法派生来源清单，并对同一制品做相应验收。旧 TaskGraph23 的阶段验收记录不能自动给 opt.27 签名。

### 4.5 仍保留上一轮输入准入缺陷

同一个 wheel 仍有 `result.manifest is None → 空 InputManifest` 的回退，以及准入时没有精确绑定原 readiness 所检查 manifest 的问题。上一轮最小反例证明的是**准入边界可产生不合要求的 eligible token**，不是证明已经穿过后面所有检查并执行了外部动作。

本轮没有重新把该反例全跑一遍；沿用原证据并用 wheel 哈希建立版本连续性。修复仍应覆盖 resolver → readiness → admission → frozen input → handoff 的同源绑定。

## 5. Assurance：Host 接线和默认启用已确认

`OrchestrationSettings.assurance_profile` 默认 `on`。Host 安装 Assurance root、AssurancePolicy、Requirements builder、check-policy projector 和通知端口；这些接回原 Orchestrator，而非第二套调度服务。[H09][H10]

前端 `MissionAssurance.tsx` 通过三个实际动词读取：

```text
mission_assurance_snapshot
mission_assurance_review
mission_assurance_use_check
```

它检查请求 ID、Mission、当前/历史视图、分页状态水位和重复条目。任务变化后会标注画面已旧；结果可用性检查也明确只是只读诊断，不发放许可。[H11]

因此上一轮“仅确认 SDK 已接通，Host 未核实”应更新为：

> **Assurance 的 Host 装配、默认选择和 UI 读链已在源码确认；当前提交的相应前端组件测试也有 CI 通过证据。**

这不等于完整效果场景、恢复、真实模型多场景验收都已完成。仓库保留了少量真实完成记录；本轮没有重新启动原生程序验证它们。

## 6. Operation：从 SDK 完成合同走到了桌面产品接口

`OperationWorkspace.tsx` 不只是静态展示。它构造包含精确 Requirements 引用的完成要求确认命令，区分 CONTENT_ONLY 与 REQUIRED_EFFECTS；超时重试保留同一 command/body 身份，不把“没有响应”解释为操作未发生。[H12]

`handlers.py` 已接入完成要求确认、操作意图提交/状态、审批读取与决策等 Host 方法。[H13]

纯内容自动确认也不是把所有任务都默认当作已完成：Host 只在 auto 权限模式、任务仍 CREATED、没有 `action:` 成功条件、且存在待确认映射时，走原批准接口确认内容规格。动作审批没有因此被跳过。这是当前项目记录的产品决定，不应把它重新列成“缺人工点击”。[H03][H14]

**默认能力范围需要如实报告。** 本轮读取的任务编排生产装配主要启用经过目录与文件系统探测的 `file_publish` connector，操作等级上限 L2；这不证明所有 ERP、邮件、浏览器、系统工具已经接入同一个 Operation 完成合同。前台其它工具能力也不能反向作为这条完成链的验收证据。[H03]

上一轮 Operation 完成合同 168 项通过属于同一 wheel 的历史本轮对话证据；这次增加了 Host/UI 源码和当前前端 CI 的补证，未再把 168 项记为新增复跑。

## 7. Agent Runtime：原生层确实接入，但 MISSION 模式没有完成

### 7.1 已经接入的内容

`HostNativePlane` 实际提供工具授权、token meter、每池会话根、AssuranceSkillAcceptance、产物读取、可选 embedding、可用时的 sandbox script runner，并由已认领 dispatch intent 派生创建 caller。[H15]

新 native profiles 与旧池并列；默认 `native_plane=on`，但只有受支持 DeepSeek 协议/显式兼容端点及可用计量配置时才能形成相应 native 池。旧任务保留冻结 profile，不能把该开关解释为所有提供方、所有历史 Agent 都已经迁移。[H09][H16]

没有 BGE-M3 资源时可明确降为 lexical-only；没有已验证脚本执行器时，SCRIPT 能力被具名拒绝。不能把“端口写好了”记成你的机器已经装好模型或验证过沙箱。

### 7.2 MISSION 模式是已确认的实现缺口

Host 当前代码：

```python
ArpRuntimeProfile(..., owner_mode="STANDALONE_CHAT", ...)
```

SDK 当前创建入口：

```python
if profile.owner_mode != "STANDALONE_CHAT":
    raise ArpError("SOURCE_UNAVAILABLE", "MISSION owner mode needs exact sources")
```

这不是只从注释推测：SDK 的实际判断直接拒绝其它 owner mode。Host 的实施记录也把 TaskGraph/InputManifest/Assurance 精确来源集列为遗留。[H15][S01][H17]

这里的缺口是 **ARP 层没有完整履行 MISSION 模式的来源合同**，不是说原 HTN 派发中完全没有任务目标、预算或认证 caller。当前任务仍能经冻结 intent 创建 Agent、调用模型和回收结果；两种事实应同时保留。

只把 `STANDALONE_CHAT` 字符串改成 `MISSION` 会触发现有拒绝，不是修复。需要实现真实来源的生产、冻结、重读、撤销/版本变化检查及其与原派发身份的绑定。

### 7.3 多池目录与技能产品入口

原规格要求同一 deployment realm 单一 catalogue owner，各 execution pool 是其读客户端。[H18]

Host 当前 `root_id` 包含 `profile_id`，并以此生成 namespace；每池还各有验收 reader、runtime 和会话根。单独的会话根和 reader 是合理隔离，但**不能因此就认为能力目录的唯一权威已经统一**。[H15]

UI 架构记录明确：`agent_` 前缀在目录统一前有意不放行；同时 handlers 中已经存在 `agent_runtime_request` 和技能评估 handler。本轮没有逐行遍历全部 main.py 控制循环，因此这里将“入口延后”标为项目记录，并未把仅有 handler 当作可从产品完整操作的证明。[H13][H19]

当前应记为：**SDK 生命周期与 Host handler 已有；跨池目录统一和新技能管理链完整产品开放尚不能签收。** 不建议为让按钮工作，直接取消入口限制而不先统一权威和撤销语义。

## 8. 恢复与上一轮 intent.id 缺陷的影响范围

SDK 的收集异常分支仍访问 `intent.id`，而正式字段为 `intent_id`，上一轮已经复现其 AttributeError。同 wheel 的身份连续性支持保留该缺陷结论。

但 Host `OrchestrationService._drive` 有外层 Exception 捕获、失败计数、指数退避、重建和 degraded 状态。默认策略为达到相应阈值重建/降级；degraded 时读、取消等控制请求仍可保留。[H03][H09][H13]

因此应改成：

> SDK 原本想隔离的单项收集拒绝，可能被错误处理代码扩大成整个编排轮次失败，进而触发 Host 退避或重建；不是已经证明整个桌面进程直接崩溃。

修复应验证：Mission A 的 BudgetError / CommitRejected 不阻塞 Mission B；A 的原结果与费用被保留；不会额外创建调用、反复重建或重复效果。不要用吞掉所有异常代替正确字段与局部恢复。

| 多池 catalogue / 新技能产品闭环 | 部分 | SDK/Host handler 与分池源码 | 同 realm 单一目录与产品入口仍需统一 |
| 代码/脚本执行 | 依赖已探测沙箱 | 本轮读取到 Seatbelt 及 frozen 限制 | 跨平台/打包运行不能一概签收 |
| 异常恢复 / 重建 / degraded | 已实现保护层 | Host 源码 | intent.id 故障仍可能触发轮次失败与恢复 |
| 统一发布验收 | 未全绿 | 当前前端 CI 有 3 失败；宽套件未完成 | 同版本测试、目标平台和原始证据闭合 |

不计算一个把不同层级和后置项目混合的“总体百分比”。UI 能显示、SDK 类存在、局部测试通过、默认任务启用、完整独立验收是不同事实。

## 11. 建议的实施顺序与最小验收

### 第一批：修当前主链中已确认的问题

- 修两处 `intent.id`，加真正双 Mission 的拒绝隔离回归。
- 删除无来源空 manifest 回退；把 resolver 成功、readiness、准入、冻结和 handoff 的身份绑定起来。
- 解释并修复当前凭据 CI 的类型问题；保留真哈希测试，同时在目标 WebView 验证。

### 第二批：让严格 TaskGraph 进入有证据的真实任务路径

先合法派生当前制品来源清单，保持未跑门禁的真实状态；再在新建受控 Mission 上走真实启用命令/事务。旧 Mission 不伪造历史 APPLIED、pins 或启用回执。验收必须证明实际执行确实消费新 TaskGraph，而不只是 UI 有图。

最小场景：一个真实桌面入口创建的三节点任务，包含 ORDER 和非空 DATA；检查输入冻结、任务状态与接受；中断恢复后无重复调用/效果；严格读接口能解释当前与历史结构。保留现有 LiveGraph 作为展示选择，但清楚标注来源。

### 第三批：补 ARP MISSION 来源，并统一能力目录

由原生产者提供 Task/plan/manifest/Assurance 的精确当前来源，ARP 创建和 handoff 复核它们；不能靠改 owner_mode 或填空值过门。测试过期输入、错误 occurrence、撤权、旧 generation、跨 Mission 引用与崩溃重放。

为同一部署 realm 建立明确 catalogue owner，各模型池读取同一权威；验证一个池准入/撤销后其他池得到一致结果。之后再将现有 Runtime/Skill handler 接进受信产品入口。

### 第四批：用少量跨层场景收口当前阶段

1. 多步骤纯内容，非空 DATA，独立审阅与根完成。
2. 准备已通过、真实效果尚未完成时不误报；审批后只发布一次，Outcome 才贡献效果完成。
3. 在原调用交接/结果收集附近中断；重启保留原身份、费用和已发生效果。
4. 一个 Mission 收集被拒绝时另一个继续；UI 显示当前事实而不推断完成。

当前场景收口后再进入用户已后置的完整矩阵，不擅自把 NanoJev、长期用户记忆或重写 Runtime 加回本轮前置。

## 12. 最终判断

**桌面端的加入显著提高了“真实接线已完成”的可确认程度，但没有消除严格 TaskGraph 和 ARP MISSION 合同的未完成项。**

下一步不是重新搭一套 Harness，而是修复已确认缺陷，把严格图与原生 Runtime 的来源合同接入默认任务链，并用同一版本的桌面场景证明它们被真正使用。
