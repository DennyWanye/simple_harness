## 3. 三项各做了什么（对照第 3～5 节"SDK 必须补齐"）

### G1 授权内续办

两道门分清：`ContinuationPolicy` 决定"这条结果进不进主回合、带哪些控制动作"；`AuthorizationPort` 决定"这个当事人在这个 Goal 下能不能带这些控制动作续办"。授权来自可信宿主端口与 Goal（`goal_ref / grant_ref / policy_revision`），不来自子结果正文、模型声明或伪造的用户消息。

| 要求 | 做法 |
|---|---|
| 1 保留默认只读；宿主显式授权才可建 / 复用工作会话、追加指令、委派 | 默认策略 `enqueue()` 不带控制动作，行为与 opt.225 完全一样；策略回 `enqueue(controls=...)` 且结果带 `goal_ref` 时才放开 |
| 2 复用 ContinuationPolicy 与 AuthorizationPort，持久绑定 goal 版本、grant_ref、policy_revision、动作范围 | 策略放行后 SDK 立刻以 `continue_within_goal` 问授权端口；允许 → 授权请求（含上述字段）冻结进结果行与排队输入；要人批 / 拒绝 / 超时 → 结果 `hold(<授权码>)`，人批后由宿主调重评接上。停止条件与预算引用在 Goal 规格里，端口可据此决策 |
| 3 分清"结果进主回合"与"主回合执行控制动作"；排队冻结、执行前重校 | 派发前（`claim`）对冻结授权再核：撤销 / 过期 / 取消 / Goal 已关或改版 → 撤回控制动作、退成只读汇总（事件 `continuation_controls_withheld`），结果仍被消费；回合内每条控制命令执行前再核一遍（不在冻结名单或授权失效 → `permission_denied` / 对应码），随后仍走各自原有的 `create_child / delegate / accept_input` 授权，Goal 引用取冻结版本 |
| 4 下游仍走 Mission / TaskGraph / Assurance、审批与效果回执 | 没有放开任何业务写入；续办回合里的 `delegate_task` 建的是普通 Mission；需要新授权的委派照常 `authorization_required` + `needs_response` |
| 5 稳定逻辑身份；重复结果 / 崩溃恢复不重复建 Mission；预算约束 | 续办回合号由冻结事件集合推出，委派键 `session:<会话>:<回合>:slot:<n>` 随之稳定；重复终态通知在收件箱按任务终态事件去重；预算沿用 `continuation_max_turns_per_session` 与 `SessionPolicy.max_model_calls`，用尽进 `waiting`，不另建计数 |

### G2 暂缓后公开重评

| 合同列 | 做法 |
|---|---|
| 输入 | 可信根宿主、`command_id`、`event_ids`（不给 = 当前所有 hold / deny / waiting 的结果）、`policy_revision`、`expected_goal_version`（不等于当前 Goal 版本报 `stale_version`）；范围受理时冻结 |
| 受理 | 持久回执；同号同参原回执、异参 `idempotency_conflict`；受理与重评工作登记同一事务 |
| 执行 | 泵下一拍对范围内每条仍可重评的结果再问一次 `ContinuationPolicy.decide`（上下文 `reevaluation_id`）；hold 可保持或转 pending；deny 只有显式重评才会变，普通唤醒不再问策略 |
| 去重 | 同一结果最多一个有效逻辑输入；重评再入队的输入身份带重评号，不复用失败过的输入；并发重评 / 旧命令重试 / 重启不生成第二个输入；已排队 / 已处理原样返回 |
| 防复活 | 已应用、已排除、已取消、Goal 已关、版本不符 → `skipped:<原因>`，不问策略、不调模型 |
| 可观察 | `continuations()` 行 `decisions` 历史（旧态、新态、原因、策略版本、命令号、重评号、时间）；事件 `continuation_reevaluation_requested / continuation_reevaluated`；`recovery_report()` 把未处理的重评记 `resumed_refs` |
| 失败恢复 | 策略异常 / 超时保持 `hold("policy_unavailable")`；受理后崩溃重开照常处理；没有可信重评事件不轮询模型 |

重评不产生新的结果身份；上一轮输入若已执行过，其效果与用量照原账保留。

### G3 目标完成绑定验收记录

| 合同列 | 做法 |
|---|---|
| 条件身份 | 每项必需条件有 `criterion_id`，绑定 `goal_id + goal_version`；用户改条件 = 新版本（`put_goal` 升版），旧版本记录对新版本无效 |
| 验收结论 | `criterion_id`、`pass / fail / unknown`、`validator_id / validator_version`、`method`、`checked_at`、SDK 填 `source_principal_id / recorded_at / goal_version / record_id` |
| 证据 | `evidence[]` 非空（pass 必须）；每项 `ref` + `content_hash`（64 位十六进制）或 `receipt_ref`。`artifact:<mission_id>:<artifact_id>` 对本树任务快照核哈希，`effect:<operation_key>` 对本树已提交效果核回执身份，`result:<event_id>` 必须在本树收件箱；其他前缀视为业务回执只核形。不属本树报 `not_found_or_forbidden`；不一致报 `invalid_argument`；事件与错误不带证据正文 |
| 写入规则 | 只有可信根宿主能登记（模型没有命令、子会话没有入口）；`command_id` 去重、参数哈希防漂移、`expected_version` 不符报 `stale_version`；模型输出只是候选资料 |
| 修订 | 同一条件后来的记录接替先前的（`superseded_by`），历史保留；登记与收口都在命令账本事务里串行 |
| 成功收口 | 结构事实之后，每个 `required` 条件在当前版本有 current 记录、`verdict=pass`、证据复核仍一致；否则 `acceptance_incomplete`，`goal()` 的 `acceptance_blockers` 列 `criterion_unmet:<id>:<missing | fail | unknown | stale_version | evidence_invalid>`；通过时回执与 Goal 行带 `accepted_records{record_ids, digest}`。`failed / cancelled` 如实记录，不要求记录 |

`basis` 保留为说明；`exclude_result` 不豁免条件；SDK 不写任何业务校验规则、不自动把 Assurance 审阅结论映射成 pass（按你们的分工由 AgentOS 适配器按条件登记）。

## 5. 独立核验与一处修正

Opus 子代理按七条核了两轮。第一轮阻断 1 条：派发前撤回控制动作时把排队输入正文也改了，若回合已提交后崩溃、停机期间授权被撤销，重开会撞幂等冲突、回合失败。已修：回合已提交就不改正文，只清名单并把回合行的名单也清空；回合内命令由执行前的再核拦住。加了对应回归测试，第二轮复核通过。

## 6. 示例

- hold → 重评：`test_continuation_reevaluation.py::test_hold_then_trusted_reevaluation_consumes_the_result_exactly_once`（策略替身 `SwitchPolicy`，宿主拨开关后调 `reevaluate_continuation`）。
- 授权内后续委派：`test_continuation_controls.py::test_real_host_authorized_continuation_delegates_within_the_same_goal`（策略 `enqueue(controls=["delegate_task"])`，默认自动模式授权端口）。
- 两者连起来 + 验收记录 + 收口：`examples/orchestration-host/goal_chain_game.py`（主局）与 `goal_chain_finish.py`（续收口；真实模型，见 INT-01）。
- 一个值得你们知道的细节：主会话**自己**委派（不带 `child_key`）的任务，其结果按设计由用户下一句消费，不走自动汇总；要让结果自动回流并可续办，委派时指定工作会话。
