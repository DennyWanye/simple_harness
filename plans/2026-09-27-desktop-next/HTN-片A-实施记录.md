# HTN 精简 片 A 实施记录（编排 Agent 判断 + 自己提做法 + 审阅闸门）

日期：2026-10-01 起。方案：`HTN-后续-方案.md` 第三节片 A（十项）。交接：`HTN-开工交接-2026-10-01.md`。

范围：根目标、平铺任务。中间目标是片 B 的事。

## 一句话

选哪个做法、要不要新做法、失败后怎么办，全部交给规划器判断；程序只做过滤和秩序检查。规划器自己提的新做法要过独立审阅才能用。方法合成器的运行路径整条删掉。

## 实际做的顺序

原打算"先建新路（第 1、6、7、4、5 项）再删旧路（第 3、2、9 项）"。动手后发现新旧两条路互相缠着——程序替规划器选做法、合成器抢在规划器前面起跑、规划次数阶梯里夹着"合成成功多给一次"——新路的测试在旧路还在时根本跑不通。于是改成一起做，一次发布：

1. Host 为新做法审阅批准检查策略（第 1 项）。
2. 搭了一个此前没有的测试夹具：保证通道 + 真实循环 + 脚本化模型（见下文"夹具"）。
3. 审阅闸门与唤醒源（第 6、7 项）。
4. 选择规则只留一档（第 3 项）。
5. 删合成器运行路径与四个程序判定（第 2 项）；"卡住了"并成问用户一种（第 9 项）。
6. 规划次数并成一处判断（第 8 项）。
7. 写做法上下文与准入检查（第 4、5 项）。
8. 规划器提示词重写成一份（第 10 项）。

## 各项做了什么

### 第 1 项　Host 为新做法审阅批准检查策略

- SDK 新增"规划主体任务的无损映射"：新做法审阅的判据 = 这个目标类型声明的判据里、任务要求中确有的那些。未知任务、不是复合目标、没有判据的都明确拒绝。
- 批准检查策略的接口允许"新做法审阅"这一类：它按规划主体任务批准，不带完成范围（提做法时还没有计划，也就没有完成范围）。
- Host 每轮职责里先批策略、再给规划授权——规划器被问到之前策略必然已在，不需要 SDK 另加保证。对每个未结束的保证通道任务的每个复合目标批一次，键是"目标任务 + 契约版本"。

### 第 6 项　审阅闸门

- 位置：计划提交事务里，结构检查之后。
- 规则：这次要采用的做法里，凡是**规划器在本任务里提出的**，必须有通过（或人裁决通过）的新做法审阅正式记录，否则提交被拒。闸门只读审阅包与正式记录表，不读事件，不判断做法好不好。
- 只在保证通道生效：独立审阅只在那里存在。
- 拒绝原因用规划决定拒绝码清单里现成的 `METHOD_NOT_AUTHORIZED`。这份清单是封闭的 36 项（有测试钉数），不为它新增一项；拒绝详情里写明审阅状态和审阅员原话。

### 第 7 项　唤醒源

- 规划器提出做法 → 做法登记、开审阅、落一条"做法已提出"事件。保证通道上这条事件**不再叫醒规划器**。
- 每轮循环看未结论的提案：
  - 正式记录通过 → 记"新做法审阅结论已入库"（通过）；
  - 打回 / 拒绝 → 同一事件（打回），带审阅员每条没通过判据的原话；
  - 两位审阅员都判不下来 → 问用户裁决（与根终审、组合审阅同一个问答通道、同一种回执），裁决前不记结论；裁决后按通过或打回记结论，事件里带裁决；
  - 审阅给不出结论（审阅员回复两次都读不懂、或审阅的全部回合都结束了却没有正式记录）→ 同一事件，结果标"没有结论"并写原因。
- 这条事件是新的唤醒源；一个提案只记一次。裁决题的回答本身不开规划轮（沿用已有规则），由裁决后的结论事件开。
- 等审阅期间任务算"在等"，不算卡住、不被停滞检测判停。
- 做法库条目新增 `review`：本任务里提出的做法各自审到哪一步、审阅员原话、用户裁决。

### 第 3 项　选择规则只留一档

- 做法选择模块只剩过滤：把候选按能力与类型分成"能跑的 / 全部"，没有路由、没有策略档位、没有"选择调用账本"。
- 删掉两条程序代答：只有一个候选时程序直接替规划器采用；同一组候选问过一次就回"无变更"。
- 删掉部署配置里的选择策略项；任务冻结的"部署身份"随之少一个字段（旧任务按"部署身份不一致"在主循环入口被停掉，片 0 已有这条路）。
- 规划包里的候选清单只列"每个待定目标有哪些能跑的做法"，不再带路由、身份、选中项；不再把规划主体收窄到第一个候选目标。
- **保留**非模型故障的原地重做（格式没写对、服务出错、执行或审阅被打断）。它仍走决定的准入与提交管道，但来源如实标为"系统基础设施重试"，不再标成"确定性做法选择"。

### 第 2 项　删合成器与四个程序判定

- 删掉"要不要新做法"的四个程序判定：需要做法的目标清单、空规划器跳过、值得合成的拒绝分类、取证是否饱和。
- 删掉合成器的全部运行路径：发起、收回复、重问、合成轮次记录、"跳过规划器"记录、合成成功给规划多加一次机会、合成在途时的各种等待判断。主循环每轮不再调它。
- 合成器的提示词模板和角色清单留到片 C 删；做法草案的解码与结构检查（纯函数）保留，规划器这条路在用。
- "一步承担 3 个以上文件就打回重拆"随之不再由程序检查（方案第六节第 1 条，用户已确认）。

### 第 9 项　"卡住了"并成一种

- 启用表里"声明受阻"和修复里的"升级问人"改成只解码、不可执行：规划器写了会被准入按"本阶段未启用"拒绝并告知。
- 留下的出口：问用户（一般情况）和"运行环境受阻"（基础设施事实，带恢复条件）。
- 删掉"声明受阻后转方法合成 / 转问人"的专用处理。

### 第 8 项　规划预算

被拒之后"还能不能再问"原来是六条各自计数的阶梯，现在一处判断、两个数：

| 数 | 值 | 含义 |
|---|---|---|
| 答错次数 | 3（原默认 2） | 自上一次提交成功起，被拒的回答——读不懂、不被准入、提交被拒，不分种类——累计到上限即停。同一请求的格式重试计入其中 |
| 服务故障宽限 | 6 | 没拿到回复的回合不算答错；超出按"运行环境不可用"停 |

另外三个数各在其位：每个目标提做法 3 次（准入处）、最终审查打回后交规划器的次数（片 0 已并）、审阅重问（格式重问 1 次 + 复审 1 次 + 问人，三类审阅共用审阅消费者里的同一处）。

- 被接受的服务类决定（提做法、问用户、取证）不是答错，不计数。
- 已有计划的任务答错次数用完：只有还欠着规划（有待处理的修复请求、有步骤在等重试决定、有目标还没有做法）才判停，原因名 `planning_attempts_exhausted`；什么都不欠就带着现有计划继续。
- 还在首次规划的任务答错次数用完：按最后一次被拒的原因判规划失败（与原来一致）。
- 不再出现的停止原因名：`planning_format_retry_exhausted`、`repair_planning_exhausted`、`method_synthesis_refused`。

### 第 4、5 项　写做法的上下文与准入

- 写新做法要用的材料对**每个还没有做法的目标**都给，不看候选有几个：每条要求的编号和原文、现有做法各自为什么不适用、可用的步骤类型、新做法该用的编号与版本。去掉了只对合成器角色有意义的字段。
- 规划器这条路的准入补了秩序检查，被拒时逐条列出问题（结构化条目，规划器下一轮在"上次被拒"里逐条看到）：
  - 草案是为这次规划的目标写的；
  - 编号撞车（同一编号与版本已有不同定义，或属于别的任务）；
  - 发布来源唯一（要发布的文件，它的"写出该文件"要求恰好链接到一个步骤）；
  - 注册协议自己的结构检查（端口、无环、每条要求都有链接等）原话；
  - 每个目标最多提 3 次。

### 第 10 项　规划器提示词

- 重写成完整的一份（第 14 版），不从旧版本拼接。旧的第 8～13 版是六层叠加，留着"你不需要也不能自己合成方法""单候选由系统本地处理"这类已经不成立的话。
- 只并入合成器提示词里的通用协议部分：做法的字段形状、一个完整示例、被拒后怎么读问题清单。领域补丁（修代码必须有写仓库的步骤、每个文件单独一步等）不并入。
- 规划包升到第 9 版，只配这一份提示词。旧版本模板对象留到片 C 一并删。
- 拆得够不够细写进了审阅员的指令（新做法审阅的判断口径），由审阅员按任务要求逐条判断；没有为它新增判据编号。

## 夹具：保证通道 + 真实循环 + 脚本化模型

此前没有任何测试能在保证通道上跑完整循环——规划器自己提做法这条路，库里 107 个真实任务一次都没走过，测试里也只有解码层面的覆盖。新夹具 `tests/orchestrator/full_target/assurance_exec/_assured_loop.py`：真实的保证通道装配、存储、提交、审阅消费者与导入器，只有模型回复是脚本；代替 Host 做三件事（根目标初始化、确认完成要求、批新做法审阅的检查策略）。

## 夹具试出来的真实缺陷（生产上同样会发生）

| 现象 | 原因 | 修法 |
|---|---|---|
| 规划器在第一份计划之前为根目标提做法，新做法审阅开不起来，数据库触发器直接报错 | 审阅以被规划的目标为归属任务，要读它的任务行；根目标的任务行原来只在第一份计划提交时才建 | 开审阅前先给这个目标建任务行——就是计划提交会建的同一行，之后的提交按"已存在的行原样复用"处理 |
| 做法被打回后用新版本号重提，第二次开审阅撞唯一键 | 审阅输入清单的请求编号只含做法编号，不含版本 | 请求编号带上版本与内容哈希 |
| 做法草案被拒后，下一轮组规划包时异常冲出主循环 | 被拒详情里的问题清单是纯文本，而规划反馈要求结构化条目 | 问题清单写成结构化条目；反馈构造对非结构化的旧条目容错，不再让"上一次怎么被记下来的"拖垮下一轮 |

## 与方案 / 审计不一样的地方、当场决定

1. **闸门不能按"本任务试用"这个标记判。** 方案写的是"采用本任务试用的做法须有通过的审阅记录"。实际上登记表给**每一个**被准入的做法——包括部署自带的库做法——都标着"在某个任务里试用"，这个标记分不出"规划器提的"和"库里原有的"。改成：这个任务为这个做法开过新做法审阅，就必须有通过记录。规划器提的做法在同一个事务里登记并开审，所以"开过审阅"就是"在本任务里提出"的持久事实。
2. **合成器的运行路径在片 A 一次删完**，不只是方案说的七个调用点；依赖它的测试也在片 A 处理（方案把这部分排在片 C）。原因见"实际做的顺序"。片 C 只剩删模板、角色清单、改名。
3. **"交接后结果未知连续两次即停"没有并入服务故障宽限。** 它管的是"请求可能已经到了模型、不能重发"这件传输层的事，和"没拿到回复再问一次"不是同一个上限。
4. **首次规划时不再带"后继步骤类型"清单。** 规划器被真正问到之后，规划请求超出了测试用模型的上下文预算（约 4.5 万对 3.3 万）。量了一下：整份请求约 72 KB，其中这份清单 38 KB——它只在"给已有步骤提后继"时有用，第一份计划之前没有任何步骤可接替。改成计划里有步骤时才带。规划包的整体收口仍是片 C 的事。
5. **系统原地重做没有改成"不经决定管道直接重做"。** 只把来源标记改成如实的。直接重做要另写一条提交路径，收益只是少一条审计记录的形状差别。
6. **声明受阻、升级问人的类型定义还在**（只解码），片 C 收口启用表时再定是否连类型一起删。
7. **预算视图里"还能合成几次"这个字段名暂留**，含义改成"还能提几次做法"；片 C 收口规划包时改名。
8. **嵌套目标"每个计划版本问一次规划器"的专用入口保留**，片 B 改成通用请求的一个触发源。

**结论**：闸门绕不过去（计划提交是唯一采用入口，闸门在同一事务里）；没有无限重问（答错次数、每目标提做法次数、服务故障宽限三个上限都有界）；合成器运行路径删除干净；审计"必须保留"的 15 项都在；没有新增按任务语义分支的规则。
